# Teamchat（团队聊天）

Puter 上的团队消息工具：工作区、公开与私有频道、话题串、
私信、表情回应、提及与文件附件。使用原生
JavaScript（无框架）、Vite，并以 [Puter.js](https://developer.puter.com)
作为唯一后端。

## 功能

- **工作区**：创建一个工作区，用链接或邀请码邀请他人（链接会过期
  （1 天、7 天或 30 天；随时可替换或停用））或**通过电子邮件**：邀请对话框有"邀请链接"标签页和"电子邮件"标签页
  （地址、一段可选附言、由应用唯一的共享邮件 worker 撰写并发送的邮件——见下文"邀请邮件"），
  创建工作区后可直接进入邀请队友的流程，
  管理员的侧边栏也始终有一行"邀请他人"。可管理角色（所有者、管理员、成员、访客）、
  移除成员、退出、删除。管理员还可以把**访客**邀请到单个频道：
  这是一个限定频道范围的邀请（相同的链接与邀请码形式、
  相同的有效期与暴力破解预算），加入者会带着访客角色落入那一个频道。访客只能看到他们所在的频道
  以及与之共享频道的人，不能浏览、加入或创建频道、
  不能邀请他人、也不能给陌生人发消息，这些限制在每条路由上都由 worker 强制执行；
  凡是出现人物的地方都会标注访客身份，含访客的频道会明确说明，
  管理员可以把他们加入更多频道、把他们转为正式成员，
  或在工作区设置中撤销其访问权。每个工作区都运行在其
  所有者的 Puter 账号中的一个小服务器上，由应用在他们第一次需要时创建。
- **频道**：任何工作区成员都可浏览并加入的公开频道、
  带受邀成员的私有频道、主题（简短，显示在头部）与描述（较长，显示在详情与频道简介中）、
  归档、删除。创建频道后会进入添加人员的第二步：
  公开频道可一步选择"工作区中的所有人"或
  指定具体人员，私有频道需要指定具体人员，两者
  都可以跳过；公开频道中的任何人都可以把工作区成员
  拉进来（是否拉访客由管理员决定），而频道简介中"添加人员"背后是同一个对话框。新成员
  会进入默认频道。头部带有一个星标、名称与
  主题，一个成员按钮（显示最近几位发言者的头像，不会额外读取消息）与成员数、
  通知设置、在本频道中搜索、详情，以及一个菜单（详情、复制链接与名称、收藏、
  通知、编辑、退出）。管理员可以把某个频道的发帖限制为仅管理员
  （即公告频道：所有人都能阅读与回应，
  该频道在侧边栏中带一个扩音器图标），并可独立地把话题串回复设置为
  所有人、仅管理员或关闭；两者都由 worker 强制执行，
  而成员仍可编辑与删除自己较早的消息。
- **私信**：一对一与群组会话（最多 9 人）。
  同一组人始终对应同一个会话。
- **详情**：点击频道或会话名称会以对话框形式打开其详情，
  分为若干标签页：关于（主题、可见性、创建者、
  置顶、书签、搜索、文件、复制链接、退出）、成员（可搜索，
  可添加人员或访客与访客邀请链接），以及供管理员与创建者使用的设置（名称、发帖规则、归档、删除），
  顶部还有收藏与通知控件。该路由（`/details`）使其可分享，
  并允许用返回键关闭它。话题串仍然在侧面板中打开。
- **消息**：markdown-lite 格式（粗体、斜体、删除线、行内代码、
  代码块、引用、链接）、带自动补全的 @提及、就地编辑
  （消息会变成一个带保存与取消的框，位置不变；Enter
  保存，Escape 取消；在空白输入框中按方向键上可编辑你上一条消息）、删除、
  带语言标签的围栏代码块、复制按钮、超过 20 行时折叠，
  以及 js/ts、json、html、css、sh、python、
  sql、diff、markdown 与 yaml 的语法高亮（高亮器只在首次显示带语言提示的代码块时才加载；
  未知提示按纯文本渲染）、
  带完整选择器的表情回应（搜索、分类、肤色、常用行，
  每条消息最多 24 种不同回应）、
  `:shortcode:` 的自动补全与渲染、输入框中的表情按钮、仅含表情的消息更大渲染、
  `@channel`、`@here`（最近五分钟内活跃的人）与 `@everyone`（仅限默认频道）三种广播，
  它们会通知整个频道，在提及自动补全中会显示其覆盖的人数，
  发送前需确认（可在设置中跳过；管理员可按频道限制广播，
  且在默认频道中仅管理员可用）、
  链接预览（在消息第一个链接下方显示一张带站点、标题、描述与缩略图的卡片；
  图片直接预览；作者与管理员可移除卡片；可在设置中按工作区关闭）、
  最大 10 MB 的文件附件并带内联图片预览（每张位于其文件名下方，
  点击可收起预览并记住这一状态）、输入框行首的"+"菜单
  （从你的电脑上传、代码片段）、拖放与粘贴以添加附件，
  以及草稿：
  未发送的文本（以及已上传完成的文件）会按会话保存在设备上，
  因此切走、重载或关闭标签页后它依然在；
  带草稿的侧边栏行会戴上一支小笔，而频道列表上方的**草稿与已发送**视图会把它们连同预览与删除入口汇总在一起，
  旁边是"已排期"标签页（等待发出的内容）与"已发送"标签页（你发出的最新消息，
  来自搜索索引，每条可就地打开）。输入框上方的一行格式按钮（粗体、斜体、删除线、链接、引用、代码、代码块）
  会用应用已能识别的 markdown 包裹或解包选区，
  并配以常用快捷键（`Cmd/Ctrl+B`、`I`、`Shift+X`、`Shift+C`、`Shift+Alt+C`、
  `Shift+9`、`Shift+U`）；"Aa"按钮可隐藏与显示该行。消息
  上限为 4,000 字符，并在输入框中倒数显示。悬停某条消息会显示三个快捷回应（你最常用的那几个，
  或"完成"、"已阅"与"谢谢"），以及添加回应、回复、稍后保存
  与一个菜单（标为未读、提醒我、回复时通知我、复制链接与文本、置顶、保存、编辑、删除）；
  当消息处于焦点中或指针悬停时，`U`、`L`、`P`、`S`、`R`、`E` 与 `Delete` 可直接执行这些操作，
  菜单中也会显示这些按键。**转发**（在工具栏与菜单中）
  会把一条消息以引用的形式发到另一个频道或会话，带上作者、
  返回原消息的链接与其附件，并可附上一段说明；
  引用中的提及会被置为无效，以免有人被重复提醒。
- **话题串**：可以回复任意消息；话题串在桌面上于侧面板打开、
  在移动端全屏打开，父消息上显示回复数。回复下方的"同时发送到 #频道"复选框
  会把该回复也发到会话中，并附上返回话题串的链接。
- **话题串、动态、稍后、草稿与已发送**：话题串与草稿与已发送位于
  频道列表之上；动态与稍后是导航栏条目（手机上也是侧边栏行）。话题串
  列出你发起过、参与过或关注的每一个话题串，按最近活动排序并统计未读回复，
  每条以卡片呈现：它在哪里、有谁参与、
  根消息、最新三条回复（"显示另外 N 条回复"可打开话题串），
  以及一个自己的回复框；动态是一个收件箱，收纳提及
  （含广播）、你关注的话题串中的回复，以及对你消息的回应，可筛选，
  每条可就地打开所在语境；稍后
  保存你从菜单中保存的消息，并带一个完成开关。消息上的"从此处标为未读"
  （或侧边栏行上的"标为未读"）会把你的已读游标往回移，
  使"新消息"分隔线与加粗重新出现。
- **稍后发送与提醒**：发送按钮旁的箭头可安排一条消息
  （一小时后、今晚、明天 9 点、周一 9 点，或你所在时区的自定义时间）；
  "稍后"视图列出已排期的内容，可编辑、
  改期、立即发送或在其发出前删除。任意消息上的"提醒我这件事"
  会在所选时间把它带回来，作为动态中的一条记录与你空间中的一条指向该消息的行，
  并可稍后提醒与标记完成。投递是诚实的：一个 Puter worker 只在处理请求时运行，
  因此到期内容由时间之后任何打开了该工作区的人的首次同步轮询投递
  ——通常在 20 秒内（即下文实时一节的安全轮询下限；开着多个标签页时更快，
  而它写入的消息会像实时发布一样唤醒所有其他标签页）；界面会显示"大约 9:00"并说明这取决于什么。
- **置顶与书签**：可从频道、私信或话题串的消息菜单中置顶任意消息
  （每个会话最多 100 条；由置顶者或管理员取消置顶）。消息上方的"3 条置顶"横条可展开该列表，
  详情对话框中也会显示，每一条可就地打开消息。频道可在头部下方携带
  最多 10 个具名书签（链接，或来自该频道的附件），
  由频道中任意成员整理并可重新排序。
- **收藏**：可从头部、侧边栏行的菜单或头部菜单为频道或会话加星，
  也可把它的行拖到"收藏"区（再拖出即可取消收藏）；收藏项会移到侧边栏顶部那个
  始终存在的分区里，它为空时会说明自己是做什么用的。星标保存在你自己的 Puter 账号中，
  因此会跨设备跟随你，而不会触及工作区。
- **目录**：频道列表上方的一行会打开工作区中的所有人，
  以卡片呈现（可按姓名、用户名或职务搜索，每张卡片带一个"发消息"按钮与一张资料卡），
  以及你能看到的每个频道（带成员数、主题与"加入"或"打开"），位于主列中。
- **自定义分区**：按你自己的方式在侧边栏分区中对频道与会话分组。可从侧边栏齿轮或某行的
  "移动到…"菜单创建分区，可从该菜单或通过拖动把行移入
  （也可拖出到"频道"或"私信"），可从分区标题重命名或
  删除它。一行只存在于一处：收藏、某个分区，
  或它的默认列表。分区与你的星标一起保存在你自己的 Puter 账号中，
  因此会跨设备跟随你，别人看不到。
- **管理我的侧边栏**：工作区名旁的齿轮可按字母顺序或最近活动排序频道与会话，
  隐藏已静音的项（它们在打开期间或被提及时会回来），创建分区，
  并把全部标记为已读。排序与静音行的选择保存在本设备上。
- **查找会话**：侧边栏顶部的过滤框会随输入收窄这些列表：
  你所在的频道、你可以加入的公开频道、私信，
  以及你尚未发过消息的人（选中其一即打开会话），
  最后一行是"搜索……的消息"；Enter 打开第一个匹配项，Escape 清空。
- **文件与链接**：每个会话名称下方都有一个标签页（紧挨"消息"），
  按时间从新到旧列出其中分享过的内容，可按文件、
  媒体或链接筛选，也可按名称筛选，顶部还有一条照片横条；
  每个条目会打开该文件或链接，或它所属的消息。它读取搜索索引
  （限定在该会话内的 `has:file` 与 `has:link`，各自是一个发布列表），
  因此不额外消耗存储，也只看到索引所知道的内容；
  每次一页，更早的内容用"加载更多"。
- **搜索**：你可以访问的每一个频道与会话，都可通过顶部横条中的输入框搜索
  （输入时结果即时出现；`Cmd/Ctrl+K` 会把光标放到那里，
  横条的箭头可在你到过的地方前后移动，其旁的时钟列出你最近打开最多的会话，
  保存在本设备上；输入框为空时下拉显示"在 #频道中搜索"以及你最近的搜索，
  每条都可移除），并支持 `in:#channel`、`in:@person`、
  `from:@person`、`has:file`、`has:link`、`before:` 与 `after:` 过滤条件，
  结果按会话分组并标出匹配词，位于"消息"、
  "文件"（同一查询，仅文件）、"频道"（你能看到的名称与主题）
  与"人员"（姓名、用户名、职务，带"发消息"按钮）等标签页下。每个结果都会就地打开该消息。
  结果只会来自阅读者有权查看的会话。
- **跳转到某一天**：视口顶部的那一天会浮在消息列表上，呈现为一个小药丸；
  它会打开一个菜单（昨天、上周、上月、
  最早、某个具体日期、最新消息），把会话打开到该日当天或之后的第一条消息。
  该日期通过在单条消息读取上的二分查找被转换为序号
  （五千条消息约需十三次），因此没有新增任何索引或路由。
- **永久链接**：任意消息上的"复制链接"会给出一个链接，
  打开会话时会滚动到那条消息并高亮，包括话题串内部的回复；
  历史会从那里向两个方向加载。
- **未读状态**：加粗的频道、提及徽标、私信计数、
  记录你上次停留处的"新消息"分隔线、当你向上滚动时新消息到达所出现的跳转小药丸、
  标签标题上的徽标，以及当未读行滚出侧边栏时，
  列表该边缘处出现的"未读提及"/"未读"小药丸（点击滚动到最近的一条）。
- **工作区图标**：管理员可为工作区设置一张方形图片
  （在浏览器中裁剪并缩小，放得下时用 PNG，以便 logo 保留其透明背景），
  它会显示在导航栏上代替名称首字母的位置、
  工作区菜单与切换器中，以及手机的侧边栏头部；加载完成前以及没有图片时显示字母。
- **资料**：显示名、职务与颜色，外加可选照片
  （在浏览器中裁剪为方形并缩到 256 px，因此服务器永远不必缩放任何东西），
  凡出现头像之处都会显示它，并以姓名首字母作为回退；
  还有状态，即一个带几个词与有效期的表情
  （一小时、四小时、今天、本周或永不），
  显示在消息行、成员卡片、侧边栏与提及列表中的姓名旁。
- **在线状态**：活跃、免打扰（暂停通知）、离开（最近一天内见过）
  或离线，它由轮询已携带的心跳推导，而心跳只在标签页处于可见状态
  且最近十分钟内被操作过时才算数（一场 huddle 算作在场）；
  标签页关闭时会说明这一点，于是这个人会在几秒内被标为离开，而不是等心跳超时
  （除非他的另一个标签页仍然可见）；给处于免打扰的人发私信会显示一个安静的提示。此外还有
  会话下方的输入提示行（"Ana 正在输入"、"Ana 与 Ben 正在输入"、
  "多人正在输入"），并在侧边栏行上带一个安静的标记。
  它会在一个轮询周期内出现，并在他们停止后几秒淡出；
  输入框最多每四秒报告一次输入状态，停止时再报告一次，
  因此给所有者的开销是有界的。已静音的会话
  什么都不显示，而且为请求减少动效的人不会看到这些圆点跳动。
- **Huddles（快速通话）**：在你所在的任意频道或任意私信中发起实时通话：
  头部中的耳机图标可发起一个
  （或加入正在进行的那一个，并显示其中的人脸与人数；在其中时按钮为按下状态，
  此时点击即离开），`Cmd/Ctrl+Shift+H` 也一样，详情对话框中也有该操作。
  当 huddle 进行中时，它的侧边栏行会戴上耳机，
  消息上方的一根横条会说明谁在其中、从何时开始，并带一个"加入"按钮，
  会话在开始时会留下一行记录，在最后一个人离开时会留下一行说明其持续了多久。
  私信中的 huddle 会响铃：标签页可见时弹出带"加入"的吐司，
  不可见时发送浏览器通知（应用关闭时为推送通知），
  两种情况都会在动态中留下一条记录，
  全部遵循该会话自身的通知设置；频道的 huddle 只会标记该行。
  在 huddle 中，一个小窗口会浮在侧边栏底部之上，无论你在应用中走到哪里都在：
  其中的人、正在说话者外的一圈光环、已用时长、
  静音、摄像头、共享屏幕与离开。它以音频为先；
  当有人打开摄像头或屏幕时，窗口会扩展为宫格（共享屏幕居首），
  你可以自行调整大小。在手机上它是消息框上方的一根横条（会话、
  他人的面孔、时钟、静音、离开），不遮挡任何内容，
  而"放大"会打开窗口。同一时间只能有一个 huddle；加入另一个会先询问再离开前一个。
  没有麦克风（或没有麦克风权限）时你仍可加入并收听。每个 huddle 最多 20 人。
  媒体通过 Puter 的 Peer API 在其中的人之间直连（见架构一节的 *Huddles*）；
  工作区的服务器只保存谁在哪个 huddle 中。
- **通知**：可选的浏览器通知，在标签页处于后台时生效，
  每个频道与会话各有设置（所有消息、
  仅提及、无），并有一个静音开关，可从侧边栏行的菜单
  （右键或 kebab，会在指针所在处打开：详情、复制
  链接与名称、收藏、"关于……通知我"含所有
  新消息、仅提及或静音、已读状态、退出）、会话头部或详情
  对话框中设置；已静音的会话会变暗，绝不加粗，也不计入标签标题。
  话题串可以被关注与取消关注（作者与回复者默认关注），
  父消息上会统计未读回复。免打扰时段与"暂停 30 分钟/
  一小时/直到明天"会让一切安静下来而不丢失未读状态，
  通知中的消息预览也可以关闭。默认值不变：提及与私信。
- **共享频道**：管理员可从频道详情中
  把一个频道与另一个工作区共享（"与另一个工作区共享"：
  一个会过期、可替换、可撤销的链接或邀请码，与访客邀请类似）；
  另一个工作区的管理员打开该链接，选择要把它加入自己的哪个工作区、
  在那里叫什么名字，该频道就会出现在那个工作区的侧边栏的**外部连接**之下，
  并带有实时的未读状态与通知。他们的
  成员从那里加入它并照常参与（消息、话题串、
  回应、文件、置顶、提及、在频道内搜索、稍后保存、稍后发送、提醒），
  同时看不到宿主工作区的其他任何东西；每个人都会标注其工作区名称
  （在消息行、成员列表、资料卡以及私信旁），
  头部会带一个写明对方名称的小药丸，
  输入框上方的一行会说明哪些工作区在阅读该频道。频道详情带有一张
  **工作区**卡片（频道所有者、每个已连接工作区及其人数、宿主管理员的"移除"、
  分享链接），且每个工作区都自己为该频道命名。在共享频道中结识的人之间可以私信，
  跨两个工作区都可以。任何一方都可以结束它：
  宿主的管理员把一个工作区从该频道断开，
  对方的管理员把该频道从自己的工作区移除；工作区设置会列出每一个共享频道。访客不能成为其中一部分
  （被设为访客的成员会离开他们原先所在的共享频道），
  而来自已连接工作区的人永远不会被提升或加入其他频道；
  其中一人被宿主管理员移除后会一直留在外面（其频道会说明这一点）
  直到从成员对话框中恢复，无论其所在工作区怎么说。
- **集成**：管理员可创建绑定到某个频道的 incoming webhook
  （用一条 `curl` 即可发布，采用我们的 `{ text }` 结构或 blocks/attachments 负载）
  以及 bot 令牌，它们可向其被加入的频道发布、读取与回应，
  权限被限定为这三项。来自集成的消息带有 APP 标签，附在集成自身的名称与颜色之下，
  且永远不会被记到某个成员名下。令牌只显示一次，
  只以哈希形式存储，每分钟限 60 次调用，且可轮换或撤销。
- **主题**：系统（默认）、浅色或深色；在首次绘制前应用，
  并保存在你的 Puter 账号中，因此会跨设备跟随你。
- **可安装、可离线，且关闭后仍可达**：一个 service worker
  预缓存应用外壳（按构建版本化，并提示"新版本已就绪，请重新加载"），
  因此安装后的应用无需网络即可打开，并显示最近打开过的会话的最后一页（只读），
  并标记为保存在本设备上。离线时写下的消息会进入发件箱（IndexedDB，
  含附件字节），可在重载后存活，并在连接恢复时按顺序发送；
  每次发送都携带一个客户端 id，worker 会据此去重，
  因此响应丢失后的重试绝不会重复发布。
  提及与私信的推送通知在应用关闭时仍会送达，并遵守静音、
  按会话的级别、免打扰时段、暂停与预览偏好；
  在 iPhone 与 iPad 上，安装应用才会启用推送。可从设置中安装（或使用浏览器自己的提示）。
- **导航栏**：位于最左侧的窄列，带有
  工作区标识（及其菜单）、主页、私信、动态、文件（在频道与会话中分享过的一切，
  与某个会话的"文件与链接"标签页是同一份列表但覆盖整个工作区，
  每一行都说明它在哪里被分享）、以及稍后，
  底部还有一个"新建"菜单、主题开关与你的头像（状态、暂停
  通知、设置、退出登录）。主页显示频道侧边栏；私信、
  动态与稍后会把它换成一个列表窗格（私信及最后一句话与一个"未读"开关；
  动态收件箱；已保存项），
  并在旁侧打开你选中的内容，窗格状态保存在路由中
  （`#/ws/:ref/dms/c/:conv`），因此重载或返回会回到同一处。
  未读私信与动态会在导航栏上带徽标。在手机上导航栏会隐藏，侧边栏保留动态与稍后两行。
- **键盘快捷键**：`Cmd/Ctrl+/` 在侧面板中打开一份可搜索的完整快捷键列表。
  除了搜索、消息与
  格式相关的按键之外：`Alt+Up/Down` 按侧边栏顺序在会话间步进，`Alt+Shift+Up/Down` 在未读会话间步进，
  `Cmd/Ctrl+Shift+K` 开始撰写消息，
  `Cmd/Ctrl` 加 `Shift+T`、`M`、`S`、`D` 分别打开话题串、
  动态、稍后与私信，`Cmd/Ctrl+[` 与 `]` 在历史中前后步进，
  `Cmd/Ctrl+.` 关闭侧面板，`Shift+Esc` 把全部标记为已读
  （需确认），`Cmd/Ctrl+Shift+Y` 打开你的状态。
- **类应用体验与无障碍**：桌面上是导航栏加三个窗格，
  手机上是无抽屉的双屏流程，适配安全区域，可用键盘操作（漫游式列表、
  焦点被锁住的对话框、可用方向键操作的菜单、Escape 关闭侧面板），
  为侧边栏、会话与面板设置了地标（landmark），
  为新消息设置了实时区域，支持减少动效，两种主题下文本对比度均为 4.5:1。
- 当应用运行在 Puter 内部（`puter.env === 'app'`）时，退出登录会被隐藏。

## 架构

一个团队聊天应用需要许多用户都能读写的数据。Puter 的键值存储与文件系统严格按用户隔离，
因此 Teamchat 使用 [Puter Serverless Workers](https://docs.puter.com/Workers/) 作为共享后端，
并通过**让每一位工作区所有者拥有自己的 worker、放在自己的账号中**来保持 Puter 按用户计费的模型：
用户第一次创建工作区时，应用会把它随包分发的
worker 包（`public/worker/teamchat-worker.js`）复制到他的云盘，并调用
`puter.workers.create()`。该 worker 的 KV 与文件系统保存该用户拥有的每一个工作区；
存储与执行费用由所有者的 Puter 额度支付。没有任何东西运行在应用开发者的账号之下。

成员通过工作区所有者的 worker 访问该工作区，使用
`puter.workers.exec()`，它会转发已登录用户的 Puter 会话。
worker 用 `user.puter.auth.getUser()` 识别调用者，
并针对工作区成员身份校验每一个请求；只有运行该 worker 的账号可以在其上创建工作区。
身份信息一概不从请求体中信任。

```
Alice 的浏览器 ──exec()──> Alice 的 worker (teamchat-x7k2q9pw1a.puter.work)
Bob 的浏览器   ──exec()──>   me.puter.kv   Alice 的工作区，全部数据
                              me.puter.fs   附件
Bob 的浏览器   ──exec()──> Bob 的 worker (teamchat-m3r8t2vq0z.puter.work)
                              ...           Bob 的工作区

每个浏览器 ── puter.kv ──> 用户自己的账号：资料、偏好设置、
                             工作区列表、哪个 worker 属于他
```

因此工作区用**引用**来寻址，即 `{wsId}@{server}`，其中
`server` 是该 worker 的 puter.work 名称（`abc123def0@teamchat-x7k2q9pw1a`）。
路由、邀请链接（`#/join/teamchat-x7k2q9pw1a/XXXX-XXXX-XXXX`）
与用户的工作区列表都带有它，因此仅凭一个链接就足以找到
一个工作区，任何地方都不需要目录服务。

### 什么存在哪里

| 用户自己的账号中（`puter.kv`，一个文档 `tcu:me`） | 工作区所有者的 worker 中（`me.puter.kv`） |
| --- | --- |
| 资料卡（姓名、职务、头像颜色、状态、照片版本）、按工作区存放的收藏会话与自定义侧边栏分区 | 每个成员资料卡的一份副本，按工作区存放 |
| 照片本体，保存在用户的云盘中（`teamchat/avatar.jpg`） | 每个 worker 一份照片副本（所有者云盘中的 `teamchat-avatars/{uuid}`），与附件一样由所有者付费 |
| 偏好设置（主题、通知、Enter 发送） | 工作区、频道、成员、消息、文件 |
| 工作区列表：`[{ ref, name, icon }]` | 邀请码、已读游标、提及计数、在线状态 |
| | 工作区的图标（所有者云盘中的 `teamchat-icons/{ws}`），其版本存放在工作区文档上 |
| 用户自己的 worker：`{ name, url, path, build }` | `tc:config`：这个 worker 归谁所有 |

用户账号中的那份列表是一份缓存：启动时应用会询问它知道的每个 worker
自己在哪些工作区中，并加以核对（被移除或已删除的工作区会退出列表，
重命名会传播）。资料变更时会推送到用户拥有工作区的每个 worker，
并在创建与加入时一并发送，好让新来者的资料从第一条消息起就是正确的。

照片遵循同样的规则：用户的云盘保存权威副本，
而他拥有工作区的每个 worker 都得到自己的一份副本，
在照片变更以及用户首次到达某个 worker 时上传，
这样工作区的头像由它自己的 worker 提供给它自己的成员（会检查成员身份），
不依赖指向他人账号的 URL。这种重复是有意为之：
照片很小，而替代方案——用户云盘上的一个公开 URL——
会让每个工作区的渲染都绑定到一个它并不掌控的账号上。

### 让 worker 保持最新

每位所有者都运行一份 worker 副本，因此发布一个修复意味着要更新很多部署。
`npm run build:worker` 会把 worker 源码哈希成一个构建 id，
编译进包中，并写在包的第一行。
worker 会在 `/health` 与 `/api/me` 中报告其构建；当所有者打开应用、
而其 worker 的构建与应用所带的版本不同时，应用会覆盖其云盘中的 worker 源文件
（Puter 会在同一 URL 上重新部署），工作区随即在新代码上继续运行。
其所有者许久未打开应用的工作区，其成员会继续与较旧的构建对话，
因此路由变更必须在相当长一段时间内保持向后兼容。

worker 调用的 puter.js 运行时是在同一次部署中烘焙进去的，
不会自行更新——只有重新部署源码才会带上新的运行时。
`worker/` 下的任何改动都会改变构建 id，
因此会在每位所有者下次访问时重新部署其 worker，并连同代码一起刷新其运行时。
`/health` 会把烘焙进去的 puter.js 作为 `runtime` 报告。

### 每位所有者一个 worker 的取舍

- 工作区的数据在物理上属于其所有者，因此数据被做成可移植的：任何管理员都可以**导出**
  整个工作区（一个分页、可续传的 `GET /api/ws/:ws/export`；
  它遍历的会话列表保存在 worker 中、由游标命名，
  绝不从游标中取得，因此导出永远只能读到自己的工作区），
  导出到他们自己的 Puter 云盘，形式为 `messages.json`
  加上纯 HTML 页面与附件字节；一次导出可以**导入**到另一个账号的 worker 上且 id 保持不变
  （接收端 worker 上 id 已被占用的会话会获得新的 id，
  而私信会根据新工作区重新推导，因此导入绝不会写入另一个工作区的历史）；
  所有者还可以**转移**工作区，方式是指定一位管理员，
  其应用随后会用他们自己的会话把工作区复制到他们自己的服务器上，
  把每一位成员一并带过去而无需重新加入，并把旧副本标记为已转移。
  旧副本保持只读（写入会返回 423 并附上新的引用；旧引用仍会被跟随，
  被带过去的成员其旧邀请链接也仍然有效，
  而新来者会被告知索取新的邀请，因为该副本已经自行签发了自己的），
  直到其所有者删除它，因此一次中断的转移不会丢失任何东西。删除所有者的 Puter
  账号仍会删除其工作区，这正是工作区设置会要求那些有团队却没有第二位管理员的所有者
  指定一位的原因。
- 创建第一个工作区要花几秒钟（部署），而不是几毫秒。
- 没有一个中心位置可供热修：修复会随着所有者打开应用而逐步铺开。
- 作为交换：没有共享基础设施，没有开发者账单，没有需要维持运行的东西，
  滥用的成本由滥用者自己承担。

单一共享 worker（最初的设计）仍然可用：自行部署这个包，
用 `PUT /api/server { open: true }` 打开它，
并用 `?worker=https://my-teamchat.puter.work` 或 `VITE_WORKER_URL` 把应用指向它。`?worker=` 链接
只对 `https` 的 puter.work 主机生效，因为它会被记住，
并从此把用户的会话交予该主机；别处的主机则由运营者在构建时设定。

由于 `puter.workers.exec()` 会把调用方的 Puter 会话附加到它被给予的任意 URL 上，
应用只调用它有理由信任的主机：任意 `*.puter.work` worker
（这正是设计意图：成员与工作区所有者的 worker 对话）
以及它所配置的共享 worker。任何指向其他主机的
路由、邀请链接或 `movedTo` 引用都会被拒绝而不是跟随（`src/lib/refs.js`）。

### 存储布局（在 worker 内部）

每一次读取都是对某个已知键的直接 `get`。从不使用 `kv.list()`
（测试套件对此有断言），因此没有扫描，也没有索引需求。

| 键 | 内容 |
| --- | --- |
| `tc:config` | `{ owner, open }`：该 worker 运行所在的账号，以及他人是否可以在此创建工作区 |
| `tc:user:{uuid}` | 成员的资料卡（姓名、职务、颜色）及其在该 worker 上的工作区 id 列表 |
| `tc:ws:{id}` | 工作区：名称、所有者、邀请码、`channels{}`、`members{}`、`former{}`（最近离开的一百人及其姓名，以便他们的消息仍能显示作者） |
| `tc:ws:{id}:u:{uuid}` | 一位成员的状态：已加入的频道、私信、已读游标、提及计数、通知设置、未读的话题串回复 |
| `tc:ws:{id}:act` | 动态：按会话的 `{seq, ts, lastAuthor, overlayTs}`（一旦该映射超过一千条，轮询会每次一百条地把线程条目静置一个月；一次回复会写回一条）、在线状态、版本戳、谁正在输入，以及进行中的 huddle（`h.{conv}`：谁发起、何时发起、每位参与者的心跳与对等邀请） |
| `tc:invite:{code}` | `{ ws, exp }`，或针对频道限定邀请码的 `{ ws, ch, role, exp }`：`guest`（访客邀请）或 `connect`（用于另一个工作区的分享链接） |
| `tc:connect:{id}`、`tc:connect:{id}:partner` | 两个共享一个频道的工作区之间的一条连接：宿主方的记录 `{ ws, ch, partner, name, secret }` 与对方方的 `{ ws, ch, ref, rch, secret }`；之所以是两个键，是因为双方可能位于同一个 worker 上 |
| `tc:conv:{conv}:seq` | 消息计数器 |
| `tc:conv:{conv}:b:{n}` | 第 *n* 个消息块：*`{ m: [...], x: {overlays} }`* |
| `tc:file:{id}` | 附件元数据；字节存放在 `me.puter.fs` 中 |
| `tc:hook:{id}`、`tc:bot:{id}` | 一个集成：工作区、频道、名称、颜色、权限范围，以及其令牌密钥的 SHA-256 |
| `tc:ws:{id}:idx:m{yyyymm}:{n}` | 搜索索引，一个月一个桶，第 *n* 个分片（共 64 个）：`{ word: [postings] }` |
| `tc:ws:{id}:idx:meta` | 索引的计数器与月份：`{ c, folded, failed, months }` |
| `tc:ws:{id}:idx:log:{s}` | 日志段 *s*：等待折叠进分片的 50 条消息的 postings |
| `tc:ws:{id}:idx:walk` | 索引重建期间：该次遍历可以读取的私信，因此某一步带回的会话列表被限定在该工作区自身之内 |
| `tc:ws:{id}:idx:{n}` | 月份桶出现之前的索引（所有时间共用一套分片），与日志并行读取，直到工作区被重建 |
| `tc:ws:{id}:pins:{conv}` | 某个会话的置顶消息：`{ items: [{ seq, by, ts }] }`，上限 100 |
| `tc:ws:{id}:u:{uuid}:inbox` | 成员的动态收件箱，一个 `{ k, c, s, by, ts }` 的环形缓冲，上限 300，由提及、回复与回应路径追加 |
| `tc:ws:{id}:u:{uuid}:threads` | 成员参与的话题串：`{ [threadId]: { c, s, at } }`，上限 300 |
| `tc:ws:{id}:u:{uuid}:saved` | 稍后保存：`{ items: [{ c, s, ts, done }] }`，上限 200 |
| `tc:ws:{id}:sched` | 到期队列，按 id 索引的已排期消息与提醒；`act.nd` 保存最早的到期时间 |
| `tc:ws:{id}:ev:s{n}` | 变更信号分片 *n*（共 4 个）：`{ t: <ms> }`，每当发生订阅者应当被唤醒的事情时写入（见下文"实时"）；它不携带主题、成员或变更种类，只有一个桶与一个时间戳 |
| `tc:ws:{id}:ev:r{n}:k{k}` | 环形分片 *n*（共 8 个）、槽位 *k*（共 16 个）：一条已封存的变更条目 `{ n, g, d, e }`（见下文"环形条目"） |
| `tc:ws:{id}:ev:o{n}` | ping 分片 *n*（共 8 个）：`{ t }`，用于环形条目不携带的变更 |
| `tc:ws:{id}:evn` | 环形分片的条目计数器，`{ s0..s7 }` |

回应的键是 emoji 短代码（`tada`、`wave-tone3`），
在成为叠加层路径之前会在 worker 中对照 `src/shared/emoji-codes.js` 中的表进行校验；
八个原创图标回应仍然有效且照常渲染。
emoji 表由 GitHub 的 gemoji 数据库通过 `node scripts/build-emoji.mjs` 生成并提交。

### 消息：块、计数器与指针

每个会话（频道、私信或话题串）都有一个整数计数器
和一系列定长的块文档，每个块保存 50 条消息。

1. **计数器。** 发布时执行 `seq = kv.incr('tc:conv:{conv}:seq')`。
   该自增是原子的，因此并发发送者会得到唯一且有序的编号，无需读-改-写。
2. **块。** 消息进入块 `floor((seq - 1) / 50)`，通过
   `kv.add(blockKey, { m: [message] })`，即在嵌套路径上的原子数组追加。
   落入同一块的两位发送者不会互相覆盖。下一个块会在当前块填满时提前创建。
3. **指针。** 头部块索引由计数器推导，因此读者确切知道哪个键保存着最新消息：
   读取计数器，再读头部块（若头部块较短则连同上一个一起读）。
   向前翻页永远只需每 50 条消息一次 `get`，无需任何列举。
4. **叠加层。** 编辑、删除、回应与话题串计数从不重写数组。
   它们是对块的 `x` 映射的路径更新：
   `kv.update(block, { 'x.s42.t': text })`、
   `kv.incr(block, { 'x.s42.rc': 1 })`。客户端渲染时把 `x` 合并到 `m` 之上。
   4,000 字符的文本上限使最坏情况下的块也远低于 400 KB 的取值限制。
5. **话题串**是 id 为 `{conv}_t{seq}` 的会话，**私信**则有一个
   由工作区 id 与排序后的成员 uuid 推导出的确定性 id
   （工作区 id 出现之前创建的会话仍可通过成员文档找到），
   因此两者复用完全相同的代码路径。

### 搜索：按月分桶、由日志喂养的倒排索引

从不使用 `kv.list()`，因此搜索无法扫描；它读取一个索引。消息的每个词
（小写化、去除重音、去掉停用词、取前 24 个不重复的词）被哈希到
该消息发布月份中 64 个分片之一，`tc:ws:{id}:idx:m{yyyymm}:{n}`，
其中保存 `{ word: [postings] }`，一条 posting 为 `{conv}:{seq}:{ts}`。
按月分桶正是成本可控的原因：存储按写入目标整个文档的大小计费，
因此向一个保存着工作区全部历史的分片追加一条 posting，
每次都要付出整段历史的代价。一个月的一个分片只保存一个月。

Postings 通过一段日志进入分片。发布一条消息是索引它对所有者的全部成本：
对索引计数器（`tc:ws:{id}:idx:meta`）做一次原子自增，
以及向当前日志段（`tc:ws:{id}:idx:log:{s}`，每段 50 条消息）
做一次 `kv.add`，写入一个小条目 `{ posting, tokens }`。
一个段的第一条消息会提前创建下一个段，
并把两个段之前完成的那个段（刚完成的那个可能仍有追加在途）
折叠进月份分片：每个被触及的分片对这 50 条消息只写一次，
按最老的段在前进行，并在 `meta.folded` 越过该段后删除该段。
编辑只记录新增的词，删除则什么都不记录。
每个词的列表上限为每月最新的 2,000 条 posting
（仍在增长的过大分片会自行降低上限），这是安全网而非它过去的工作上限。
一次分片写入失败会计入 `meta.failed`，而每个搜索回答都会带上它，
因此一个正在悄悄丢失写入的索引对管理员而言是可见的，而不是无声无息。

一次查询会读取 meta 文档（与成员检查一并进行）、
尚未折叠的日志段（最多四个小文档：自上次折叠以来发布的内容），
以及每个查询词一个分片（最多六个），先从最新的有 posting 的月份开始，
再往前一个月、每次跳两个月，直到其页已满或已用完四跳；
游标会指明从哪个月份继续，因此一个藏在长历史深处的罕见词
是在"加载更多"的过程中被找到的，而不是在一次无界的调用中。
`before:` 或 `after:` 过滤会跳过它排除的月份，
因此针对去年春季的搜索从那里开始，而不是一路翻页回去。
候选结果按月求交集，跨来源去重，
过滤为调用者有权读取的内容（他们不在其中的私有频道、他人的私信），
按最新在前排序，然后才去获取保存该页的块：每一跳最多 12 次块读取。
日志中的条目可能来自任意月份（一次编辑会以其原始时间戳记录新词），
因此日志产出的内容要等到已读月份抵达其所在月份后才会被检视，
这保证了分页顺序且没有缺口或重复；
并且它的词会计入每个月的交集，因此一条其词分散在日志与分片中的消息
仍能被一个查询全部这些词的查询找到。
每条被取回的消息都会再次对照查询校验，
因此编辑与删除留下的过时 posting 永远不会出现。

每条消息还会以作者的伪 token（`_by:{uuid}`）建立索引，
因此"我发出的一切"（"已发送"标签页，或不带任何词的 `from:@me`）
读取的是一份 posting 列表而非一次扫描；查询中带词时，
则在取回的消息上检查作者。
`_file`、`_link` 与 `_by:` 这些伪 token 还会按会话再索引一次
（`_file@{conv}`，话题串归到其父级之下），
因此某个频道的"文件与链接"标签页，或 `from:@ana in:#ops`，
读取的是一份只关于该会话的列表，
而不是把工作区最新的几千条筛下来。

在月份桶出现之前建立索引的工作区保留着它们旧的分片集
（`tc:ws:{id}:idx:{n}`），查询会与日志一并读取它
（它的 postings 跨越所有月份，因此被同等对待），
且限定作用域的伪 token 会回退到工作区范围的那些，
直到管理员在工作区设置中重建：一个可续传的过程，
它先每隔一段时间丢弃旧索引的一部分，然后每次走少量会话的块，
直接写入月份分片。在此期间发布的消息仍照常通过日志进入分片。
在搜索出现之前创建的工作区没有索引，只能找到此后发布的消息，直到重建为止。
新工作区与示例工作区从一开始就建立了索引。

### 离线、发件箱与推送

`dist/sw.js` 由一个 Vite 插件产出，带有该次构建的资源清单
与一个版本哈希：带哈希的资源以缓存优先方式提供，
导航请求以网络优先、离线时回退到缓存的应用外壳，
Puter SDK 采用 stale-while-revalidate 以便应用能离线启动，
而 API 流量（`puter.workers.exec`）则不做处理。
应用把每个工作区的引导数据与它打开过的每个会话的最新一页存入 IndexedDB，
只在网络中断时读回，并标记为已过期。

发件箱是一个包含未发送消息（含 blob）的 IndexedDB 存储。
每条消息都携带一个客户端 id（`cid`）；worker 把它保留在记录上，
并在写入之前，在最新的两个块中查找来自同一发送者的同一 id，
若已存在则直接返回既有消息而不再发一条。
这使得发件箱的重试与输入框自身的重试都是安全的。

推送保持按所有者的模型：每位所有者的 worker 首次使用时
生成自己的 VAPID 密钥对，并保存在所有者的 KV 中（`tc:config.vapid`），
用它为推送签名，并按 RFC 8291 用 WebCrypto 加密负载；
没有任何东西运行在应用开发者的账号之下。
一台设备按工作区订阅（`POST /api/ws/:ws/push`，每位成员最多五台设备），
并一并发送其免打扰时段、暂停状态与预览偏好，
以便应用关闭时 worker 仍能遵守它们。
推送从写入提及或私信的那次请求发出，每条消息最多 50 个接收者
（超出此数的广播通过应用内徽标触达），
并在发送前检查每位接收者对该会话的静音与级别；
推送服务返回 404/410 会取消该订阅。
由于浏览器每源只允许一个应用服务器密钥，
一台订阅了位于不同 worker 上的多个工作区的设备，
会用它打开的那个 worker 的密钥重新订阅；
其他 worker 的推送会在它再次打开它们时恢复。
普通频道消息从不推送，即使级别是"所有消息"：
该级别管辖的是标签页打开时的应用内通知。

### 实时：由变更事件唤醒的轮询

数据平面仍然是轮询：`GET /api/ws/:id/sync?since=ts` 仍是唯一的事实来源，
其回答没有发生任何变化。worker 读取动态文档
（连同工作区，用于成员检查，以及调用者自己的成员文档，用于确定其可见范围），
并只返回比 `since` 更新的条目：哪些会话前进了（未读加粗、提及徽标，
以及为打开的会话"取回新增内容"）、谁在线
（来自可见标签页每 30 秒一次的心跳，且该标签页最近十分钟内被操作过，
因此在副屏上开着很久的标签页既不会连读数小时的"当前在线"也不会白写；
它以 worker 的时钟为准，而每个回答都带有该时钟，而不是设备的；
可见标签页会随引导数据发出第一次心跳，
因此成员在工作区打开的那一刻即被视为在线，
而关闭的标签页会在其最后一次心跳旁留下 `off` 字样，
并带一个 keepalive 的 `DELETE .../presence`，五秒后即被采信，
因此重载不会产生闪烁），
以及告诉客户端在结构变化时重新获取工作区文档或自己成员文档的版本戳。
一个条目会指明最后是谁在何处写入、以及谁正在向谁输入，
因此一次轮询只携带调用者的频道与私信，
以及他们可能浏览的公开频道；私信与私有频道的任何内容都不会传到圈外。
每次轮询三次 KV 读取（动态与成员文档并排，
在工作区已说明是谁在问之后），心跳的写入会在回答发出前被等待；
小增量保持出口流量低。输入状态随行携带：
`t.{conv}.{uuid}` 由输入框在有人输入时最多每四秒写入一次
（在发送或停止时删除），而轮询只返回比八秒更新的条目，
因此关闭的标签页不会留下卡住的指示，
安静的工作区也不会多发任何东西。
一次发现输入映射超过二十条目的轮询会移除那些早已过期的条目，
以免它永远为每位成员、每个会话累积一个键。

改变的是标签页**何时**轮询。Puter Events 允许一个账号订阅键值区域上的变更，
并通过应用已经持有的同一个会话套接字获知变更；
Teamchat 只用它来决定何时更早轮询，绝不把它当作第二事实来源，
因此漏投递或重复投递都无害。
在每一次值得唤醒订阅者的写入——一条消息、一次
编辑、一次删除、一个回应、一次置顶、一个展开预览、一次 huddle 的开始、加入或结束、
与某人开启一次私信、`bumpWorkspace`、有人被"戳"了一下、
以及一次输入突发的首次写入——worker 还会向一至四个**分片**键写入一个
微小的 `{ t }` 文档，`tc:ws:{id}:ev:s0`..`s3`
（`src/shared/events.js`），并批量合并为一次调用。
一个分片不指明任何东西，只是一个桶：绝不是某个会话、某个成员或某种变更。
在线状态心跳、首次之后的输入状态刷新，
以及常规清理从不发信号——它们各自按下面的节奏走。
只有在平台确实能够投递时 worker 才为一次信号付出代价：
在用户作用域的 worker 上完全不会写入（它没有自己的应用身份——
没有人能订阅它，无论是自有模式还是句柄），
在缓存的判定说该区域 `events.enabled` 本身已关闭时也不会写入
（这是唯一一个连所有者自己的订阅都会阻止的拒绝；
其他每一个拒绝都只会阻止成员，因此它仍会为所有者的利益继续发信号）。
输入状态的 `first` 标志在不同客户端版本间优雅降级：
太旧而无法发送它的客户端会被视为在每次写入时都发送 `first: true`，
而旧客户端自己的输入框本就把写入限制为每个会话每几秒一次，
因此成本不超出此限；新客户端只标记突发的首次写入，
而 worker 把任何非显式 `first: false` 的东西都视为需要发信号。

有两种观察一个区域的方式，因为存储位于 worker 自己的账号中
（即部署它的那个账号——未必是某个工作区的创建者：
一个共享 worker，见下文，可以承载由其他账号创建的工作区），
而其他人都是不同的账号，在观察别人的数据：

- **所有者**直接订阅自己的命名空间
  （`kv:<appUid>:tc:ws:{id}:ev:s{n}`）——无需句柄、无需同意，
  除 Events 处于开启状态外也不需要额外的平台开关。
  一旦所有者所在区域满足这一点，他自己的标签页就获得更快的节奏。
- **其他每一位成员**则通过一个 **KV 共享句柄**订阅：
  这是另一个账号可以授予观察权的区域。
  worker 会在第一次能够时为每位成员铸造一个（在加入时，
  并在引导时惰性地补上），把它缓存在该成员自己的文档上，
  并且绝不重新铸造（铸造按所有者账号限流）。
  这需要所有者的一次性同意——一个有边界的授权
  `manage:kv-share:<owner>:<app>:tc:ws`，覆盖他将来拥有的每一个工作区——
  以一个可关闭的吐司呈现，仅在平台第一次给出"仍然缺少同意"的确定答复时出现；
  在尚未有任何探测发生时，这个问题会留待之后对工作区的某次改动再解决，
  而不是把本会话唯一的机会花在一个从未真正给出的答复上。
  拒绝会被记住（`tcu:me`，`prefs.evConsent`），吐司也不会再出现——
  但工作区设置会在一个**实时更新**行中说明该工作区处于哪种状态，
  该行带有同一个开关，因此先前关掉吐司的所有者之后仍可打开它。
  成员关系结束时——被移除、离开、一个外部席位终止、工作区被删除
  （那里每个请求会批量处理有限数量的句柄）——worker 会收回该成员的句柄，
  于是他们不再收到那些不透明的分片 ping，
  而他们占据的槽位也被释放给仍在这里的人。
  在平台拒绝时（较旧的构建、被撤回的同意、两者共用的铸造/撤销额度），
  该授权会一直存在，直到所有者从一个真实的 Puter 会话中收回它，
  而在它存续期间，它所说的仍然只是"某个分片有变化"。

所有这些都要求 worker 以与跟它对话的标签页相同的 Puter 应用运行。
从应用自身部署的 worker 满足这一点；
而从 Puter GUI 或 CLI 用用户令牌部署的 worker 会以自动创建的
`sandbox-<name>` 应用运行，于是每个标签页都回退到轮询。
一个共享句柄绑定到它所共享的应用所属的命名空间，
因此 worker 会在铸造前读取调用方自己的令牌，
并跳过应用不匹配的成员，
而不是把所有者一个宝贵的存活句柄槽位花在一个永远用不上的句柄上
（只有所有者撤销它才会释放）。

无论标签页以何种方式订阅，一次投递（包括一个 `gap` 标记，
按约定其含义是"有事情发生了，重新读取"）只有一种含义：尽快轮询，
下限为 2 秒，因此一串写入会合并为一次轮询。
在订阅健康时——这个标签页自己的订阅，
以及它打开的每一个共享频道在宿主上的健康订阅（见下文"共享频道"）——
经典的 4 秒节奏会被 20 秒的最后手段下限取代；
隐藏的标签页无论如何仍每 30 秒轮询一次，
完全忽略投递，并在连续隐藏 60 秒后放弃订阅，
因为隐藏标签页所忽略的投递仍是成员自己的账号在付费。
重新可见时会重新应用上次引导所说明的一切，
而不只是实际被拆除的部分：
在标签页离开期间被轮换的句柄或被关闭的区域不会仍作为一个
已经不存在的对象的订阅留存，而标签页仍在等待的退避也不会因隐藏而失效，
因此一个关闭了该功能的区域不会在每次隐藏/显示循环中都被反复询问。
当有人在屏幕上的会话中输入时，客户端改为每两秒轮询一次，与以往完全相同。

在线状态是唯一的例外，而且是有意为之：
一个可见标签页本来每三十秒就写一次心跳，无论是否有其他变化，
为每一次心跳发信号都只是一次无人等待的 KV 写入，
因此在线状态心跳从不被发信号。
在订阅健康时其他一切都变快了，有些快得相当多；
唯独在线状态没有，因为它仍然搭乘它一直以来的那次轮询——
有人转为活跃或离开、免打扰开关的切换、
成员的标签页此刻出现，在别人的标签页中最多需要 20 秒才显现，
而不是原来的 4 秒——这与其他每一种变更在最坏情况下得到的
最后手段下限相同。降级检测器对此无话可说：
它监视的是 worker 总会发信号的那类变更出现在一次普通轮询中、
而中间没有投递的情形，
而在线状态变化从来不属于那类，因此这一切看起来并不像
一个安静下来的订阅——它正是一个按预期正常工作的订阅。

事件唯一无法通报的失败模式是一个看起来活着却已安静的订阅——
某个分片超过其约 50 个观察者的保真度上限、
某项授权被从 Puter GUI 撤销、某个区域关闭了派发——
因此客户端会自行监视它：
连续三次安全轮询（不是被戳醒、也不是由信号驱动的）
都发现了 worker 总会发信号的那类变更，
就会回退到经典节奏五分钟，然后重试；任何一次真实投递都会重置这个计数。
这一切都是特性探测的，
并且都以完全相同的方式回退到今天的轮询，别无其他：
SDK 中没有 `puter.events`、平台区域关闭了 Events 或 KV 共享句柄、
没有所有者的同意、worker 没有自己的应用身份（用户作用域部署）、
应用 uid 不匹配、老 worker 与新客户端对话（没有 `events` 键）
或反之（出现未知键，被忽略）——这张矩阵的每一行都以同一种方式收尾：
完全按今天的方式轮询。

### 环形条目

引导数据中带有 `ring` 块的客户端从事件而非轮询中读取变更。
worker 把每次会话变更（一条消息、一次编辑、一个回应、一次置顶、
一张链接卡片、一次删除、一次回复在其根消息上的计数、
有人开始输入）封存为一条条目，
并用一次计数器 `incr` 与一次批量 `set`，
把它写入其受众所属的每个环形分片的一个槽位
（公开频道 8 个分片，私有频道或私信则是成员的各自分片）。
标签页监视自己的分片（`r{rs}:*`，带 `includeValue`）与 `o{rs}`，而非 `s{n}`。
条目直接作用于打开的窗口、动态时间戳与输入状态，
因此一次变更不耗费任何请求。
`o{n}` 只为环形条目不携带的内容而写（工作区与成员文档、huddles、提及计数），
那些仍然轮询。

- **键。** 每个会话的根键是 `HMAC(secret, ws, conv, ke, access)`。
  密钥存放在 `tc:config.evs` 中，`access` 是私有频道的成员列表，
  `ke` 是一个工作区纪元，在有人以其他方式失去访问权时递增
  （被移除、被设为访客、访客或外部人员离开公开频道、一条连接结束）。
  引导数据只发放调用者有权读取的那些键。
  条目使用由根键派生并带不透明 id 标记的密钥，以 AES-GCM 加密，
  因此分片上的其他成员只会看到有东西变了以及何时变的。
- **顺序与缺口。** 条目按分片编号。
  一个缺失的编号会等待 `RING_GRACE_MS`，然后转为轮询。
  一个缺口标记、或 Events 遗漏的一个取值（超过 16 KB，
  或超过 128 个匹配的订阅）也是如此。
  同步回答中的 `rn` 说明编号进行到何处。每一条目都是幂等的。
- **规模。** 8 个分片在 300 名成员、每人两个标签页的情况下，
  每个上可容纳约 75 个标签页，仍低于会导致取值被丢弃的 128 个订阅。
- **兼容性。** `s{n}` 仍会为每一次变更写入，因此来自环形条目之前的标签页可以毫无改动地工作。
  没有 `ring` 块时（较旧的 worker 或主机），
  客户端照旧使用 `s{n}`。

### 广播提及

`@channel`、`@here` 与 `@everyone` 在 worker 中于发布时解析：
该频道的成员（公开频道的成员列表按每位工作区成员一次成员文档读取取得，
与列举他们同价）、最近五分钟内有心跳的人，
或整个工作区。消息只存储其种类（`bc`），绝不存储展开后的列表，
因此一个块保持很小，而后来加入的成员仍会看到它被渲染为一次提及。
扇出会递增每位接收者的提及计数器并并行批量追加到他们的动态收件箱，
并每五十人一次多路径写入动态文档来"戳"所有人；
它受工作区成员上限 500 的约束，这是有据可查的天花板
（每位接收者约四次写入）。

### 没有时钟的定时投递

worker 没有 cron 也没有后台定时器，因此一条已排期的消息或一个提醒
都由某个人的请求来兑现：那次同步轮询。
队列是每个工作区一个文档，`tc:ws:{id}:sched`，按 id 索引，
而最早的到期时间保存在轮询本就会读取的动态文档中的 `nd`，
因此一次什么都没到期的轮询（几乎所有轮询都是如此）完全不做额外工作。
当某个到期时间已过，轮询会用其认领计数器的一次原子自增来认领每个到期条目
（只有把它从零变为一的那次轮询会投递，因此两次竞争的轮询不会都发出），
投递它、移除它，并重新计算 `nd`。
一条已排期的消息通过与实时消息相同的 `postMessage` 路径投递，
以其作者身份，因此提及会通知、计数器会变动、话题串会计数，索引也会被写入；
如果作者已无法在那里发布（被移除、频道被删除或改为仅管理员可发），
该条目会被丢弃而不是发到别处。
一个提醒会变成一条收件箱记录，
以及成员自己空间中一条指回该消息的行，
而针对已删除消息的提醒永远不会被触发。

因此投递受"下一个轮询的人"约束，而不是受时钟约束：
在事件健康时（见下文"实时"），那是 20 秒的安全下限，为最坏情况；
投递所写入的消息会像任何其他发布一样发信号，
因此每一个打开的标签页都会同时得知它，
而不必等上它自己的下一次轮询。

### Huddles：媒体在人与人之间，名册在 worker 上

一次 huddle 就是一次通话，而 worker 无法承载它：它只在回答请求时运行。
因此 huddle 的音视频从不接触 worker。
它们通过 [Puter's Peer API](https://docs.puter.com/Peer/) 在参与者的浏览器之间直连，
它为每位参与者提供一条 WebRTC 连接，并处理信令与 TURN 中继
（中继按每个人自己的账号计费，以保持按用户付费的模型）。
worker 只保存名册：
`act.h[conv] = { by, at, m: { [uuid]: { at, j, inv, s } } }`，
写在轮询本就会读取的动态文档中，
因此某个会话的成员会在带来在线状态与输入状态的同一次轮询中
得知那里有一个进行中的 huddle
（名册携带其参与者所服务的邀请码，
因此只有该会话自身的成员会收到它），
而 `src/shared/huddle.js` 为双方描述了这一结构。

没有人担任主机。每位参与者都运行自己的对等服务器
（`puter.peer.serve()`），并把它的邀请码发布到
`POST /api/ws/:ws/conv/:conv/huddle`，该接口占用这个席位
（在无人在线时启动 huddle，并发布"已开始"那一行）并返回名册。
新来者随后拨号给名册上列出的每个人
（`puter.peer.connect(invite)`）；此外，当两位参与者彼此都知道对方
且双方都没有已建立的链路时，id 较大的那一方发起拨号，
这也决定了双方同时拨号时保留哪条连接。
每侧的问候都会指明它所服务的服务器，
因此一个来自某个账号的、来自非该链路服务器的第二次连接，
意味着该账号的席位发生了转移（到另一个标签页，或重新提供），
并会替换掉原链路；而对一个指向某服务器的链路说再见，
在名册已把该账号列在另一个服务器下之后就没有意义了。
结果是全网状连接，因此谁离开都不会让其他人断开，
也没有主机需要迁移。身份来自信令方而非链路：
服务器从 `event.user.uuid` 得知是谁连接上来，
拨号方从 `conn.owner.uuid` 得知回应的是谁的服务器，
而在链路承载任何内容之前，该账号必须是对话成员的私信对象之一，
或在频道中是该会话工作区的成员。
在每条链路上，Puter 数据通道承载一个小型 JSON 协议
（hello、state、signal、bye），
而 `src/lib/rtc.js` 在其下把麦克风、摄像头与屏幕轨道挂到 `RTCPeerConnection` 上，
并通过同一条通道重新协商（"完美协商"模式，其中被拨方为礼貌方）。
一条传输中断而通道看似仍然打开的链路，
会通过其连接状态被发现并被重新拨号。

席位由心跳维持：同一个 `POST`，每 15 秒一次。
90 秒内没有音讯的参与者视为已离开
（其标签页关闭了，或网络断了），
发现此事的轮询会把他从名册上移除
（之所以长于一分钟，是因为浏览器会把隐藏几分钟的标签页的定时器
放慢到每分钟唤醒一次，除非它维持着一条 WebRTC 连接——
而独自在 huddle 中的人正是如此；
重新可见的标签页会立即重新发布其席位）；
当没有活人留下时，同一次轮询会结束该 huddle 并发布"已结束"那一行，
先用一个保存在名册旁的原子自增认领它
（放在该 huddle 的开始时间戳之下，因此它比条目本身活得更久），
这样两次同时发现的轮询也只会写一次。
`DELETE .../huddle` 会立即离开，而关闭的标签页会在 `pagehide` 时把它作为
keepalive 请求发出，因此浏览器会让它在页面之后完成。
每个账号一个席位，由一个标签页持有：每次发布都指明标签页（`sid`）
以及这是加入还是心跳；一次加入会从同一账号的另一个标签页那里取走席位，
而那个标签页的下一次心跳会被拒绝（`replaced`）而不是把席位拿回来，
因此最后加入的那个标签页无论谁先心跳都保有席位，
而离开只会放弃离开标签页自己的席位。
在私信中发起 huddle 还会为其他人写一条动态记录并发送推送，
遵循该会话的通知设置，因此一次通话能够触达应用已关闭的人。
共享频道的做法相同：名册位于频道的宿主上，
客户端像其他每一次写入那样把通话路由到那里。

### 访客：第三级台阶

访客是 `role: 'guest'` 的成员，其成员文档只列出他被邀请到或被加入的频道。
这条规则在数据被返回之处强制执行，而不只是在执行动作之处：
`resolveConv` 对访客而言把每个频道都当作私有频道处理，
因此读取、发布、置顶、话题串、搜索、收件箱等全都由一次检查推导出来；
引导数据只返回他们的频道（绝不含某个频道自己的邀请码），
以及与之共享频道的成员（私有频道的名单，
或公开频道按每位工作区成员一次成员文档读取，每次引导一次）；
涉及访客的私信要求其中每个人都与该访客共享一个频道，双向皆然；
一个文件只有在曾于访客有权读取的某处被分享过（作为附件或书签）时才会提供给访客，
这一点由该文件的记录跟踪；
而访客不能重命名、重新设置主题或重新设置书签所在的频道。
广播与普通提及一样，只触达有权读取发布位置的人。

### 共享频道：一个频道，两个 worker

与另一个工作区共享的频道依然存活在它被创建的地方：
宿主工作区的 worker 上，所有者的账号中。
对方工作区为它保留一条**条目**
（`channels[id].shared = { ref, ch, conn, host }`：宿主的引用、
它在那里的频道 id、连接、宿主的名称），并拥有自己的名称，
而它的成员以**外部**成员的身份在宿主上参与，
这是 owner、admin、member、guest 之外的第四种角色。
外部成员是带标签的访客：同样的规则（`isLimited`）
把他们的读取范围限定在他们所在的频道及其中的人，
他们的资料卡带有 `org: { ref, name }`，
他们不能被赋予角色或加入其他频道，
而宿主的 `/api/me` 绝不把宿主列在他们的工作区之中。

两个 worker 从不互相通信；一切由客户端携带，
而让宿主相信他们的正是一条**连接**：

1. 宿主的管理员铸造一个分享码（`POST .../channels/:ch/connect/invites`），
   这是一个 `role: 'connect'` 的频道限定邀请，
   其字母表、有效期与暴力破解预算与任何邀请相同；
   `/api/join` 会拒绝它，因此分享链接永远不会制造出一个访客。
2. 对方的管理员打开 `#/connect/:server/:code`。其应用会预览它
   （`GET /api/connect/preview`），并在接受时调用宿主
   （`POST /api/connect/accept`，带上对方的引用与名称），
   宿主铸造一个连接 id 与一个 32 位符号的密钥，并只返回一次；
   应用随后把它们存到对方的 worker 上
   （`POST /api/ws/:ws/channels/shared`），从而创建该条目。
   为同一工作区再次接受会在同一条连接上续期该密钥。
3. 对方成员在自己的 worker 上加入该条目
   （`POST .../channels/:ch/join`），它会记录此事并交回一份
   **证明（attestation）**：`{ conn, uuid, kind: 'join', exp }`，
   用该密钥签名（HMAC-SHA256，十分钟有效）。
   客户端把它出示给宿主（`POST /api/connect/join`），
   宿主会把签名与该连接的密钥比对，
   并把 uuid 与调用者的 Puter 身份比对，
   然后把他变成该频道的外部成员。
   因此一个令牌只对它所指明的那个人、在几分钟内有效。
4. 客户端随后以该外部成员的身份引导并轮询宿主，
   与它自己的工作区并行（`src/lib/store.js`，"shared channels"）：
   对宿主的所有者而言，每次轮询多一次很小的读取，
   这是你的频道里多出一个工作区的代价。
   宿主所说的内容会在本地 id 之下折叠进 store
   （该频道及其话题串用条目的 id，直接消息用 `h_` 加宿主的 id），
   因此会话界面读一个共享频道与读一个本地频道完全一样，
   而每一次写入都由 `store.hostOf()` 路由回宿主。
   频道内的动态、话题串、稍后与文件都会一并询问宿主。
   只有对外部成员而言，宿主上的直接消息才以这种方式承载；
   同时属于两个工作区的人其私信就在宿主自身中，
   而从对方给宿主成员发消息会在宿主那里打开他们。

外部成员资格**一天后过期**，除非续期：宿主会回答 `reattest`，
客户端则从自己的 worker 静默取得一份新的证明，
而该 worker 只为仍在其工作区中且仍在该频道里的人签名。
被移出对方工作区、或在那里被设为访客的人会立刻失去席位：
对方的 worker 会针对每个共享频道给管理者的移除操作一份签名撤销书
（`kind: 'revoke'`），管理者的应用把它带到每个宿主
（`POST /api/connect/revoke`）；
宿主像处理一次断开那样终止其席位，
并在加入令牌存续期间一直记着这个词，
因此在移除之前签发的令牌不会让任何人获得席位。
应用从未到达的宿主会让席位在一天内失效，因为证明会到期；
一个配合的客户端会立刻离开宿主。
反方向则由对方继续担保：被宿主管理员移除的外部成员会被记住
（`ws.removed`，仅管理员可见），
`/api/connect/join` 会对他们回答 `removed`，
直到管理员恢复他们（`DELETE /api/ws/:ws/removed/:uuid`）
或他们以自己的身份加入宿主；
其客户端会把该频道显示为对他们已关闭，
并按其惯常节奏再次询问，因此恢复会自行发生。
任何一方都可以结束这条连接：
宿主管理员用 `DELETE .../channels/:ch/connections/:conn`，
对方管理员则先用一份断开证明（`POST /api/connect/disconnect`）
再移除该条目。两者都让对方的人离开该频道
（当他们在宿主工作区已不属于任何共享频道时，也离开该宿主工作区）；
他们写下的话会保留其姓名与其工作区的标签，
取自工作区保留的"已离开的人"的名单（`former`）。
对方的名称与引用是它对自己的说法，就那样显示且不经任何验证；
密钥只经过接受的管理者的浏览器一次；
被窃取的密钥会让其持有者以自己的身份加入该频道，
并带上对方的标签，就像一个泄露的访客邀请那样，
而断开连接会撤销它。

有意不做的事：共享频道的推送
（设备按工作区订阅，而对方成员不属于宿主）、
跨宿主的全工作区搜索（在频道内搜索可用），
以及绑定到对方条目的集成（它们在宿主上设置）。
一个工作区按其原样导出连接，并导入一份未共享的副本。

### 谨慎对待链接预览

浏览器无法读取其他源的 `<meta>` 标签，因此是工作区的
worker 负责抓取页面，这让预览成为所有功能中唯一一个
所有者的 worker 会触及开放互联网的功能。
发送者的客户端在发布后立即请求预览
（`POST .../messages/:seq/unfurl`），因此发送保持快速；
结果存储在消息的叠加层上（`x.sN.uf`），
因此它只被计算一次且对每位读者完全相同，并随消息一起消失。
防护措施：只允许 http 与 https；拒绝环回、私有、链路本地、
组播以及 `.local`/`.internal` 主机；重定向手工跟随（最多三次），
每一跳都做同样的检查；不转发任何调用方请求头或 cookie。
额度：五秒超时，正文只读取到 `</head>` 或 200 KB 为止，
每位成员每十分钟最多 30 次预览、每个工作区每十分钟最多 300 次，
以及按 URL 的缓存（`tc:unfurl:{sha256(url)}`，七天；失败一小时），
因此在五个频道中分享的同一个链接只被抓取一次。
代码跨度与代码块内的链接永远不会被展开。

缩略图不做热链：热链图片会把每位读者的地址泄露给目标站点，
因此 worker 会把小于 300 KB 的图片副本存到所有者的云盘，
并通过 `GET /api/ws/:ws/unfurl-image/:hash` 提供给成员。
这会花掉所有者一点存储，但保护了读者，
这正是本 README 所推荐的取舍，也是设置中的开关所解释的。
有一处限制值得知道：运行时没有提供 DNS 解析器，
因此一个解析到私有地址的公共主机名无法被检测出来；
防护措施作用于 URL 本身与每一次重定向。

### 邀请的安全性

邀请码取自 32 个字母的字母表中的 12 个符号（2^60 种可能），
用 `crypto.getRandomValues` 生成。
每一次猜测都需要一个已登录的 Puter 账号，
每个账号每 10 分钟只有 8 次失败机会，之后加入路由会回答 429 而不触碰存储，
邀请码会过期（默认 7 天，管理员在替换时可选择 1、7 或 30 天），
而缺失、过期与被替换的邀请码都会以完全相同的方式失败。
管理员还可以直接停用工作区链接
（`PUT /api/ws/:ws { revokeInvite: true }`）：该邀请码即失效，
在他铸造新的之前不会有新的。

### 邀请邮件：一个共享的发送方

工作区的 worker 永远无法发送邮件——对外发信是一项只有应用开发者才持有的能力，
这是平台的安全特性，而非功能缺口。
因此邀请邮件都通过**一个**共享 worker 发送，即 `worker/email.js`，
由开发者部署一次（`npm run deploy:email-worker`，它会执行
`puter worker deploy worker/email.js teamchat-email`；
客户端在 `src/config.js` 的 `EMAIL_WORKER_URL` 处找到它）。
应用通过 `puter.workers.exec()` 调用它，这会转发已登录发送者的 Puter 令牌：
worker 自己的令牌授权发送，发送者的令牌付费，
因此开发者绝不会为垃圾邮件发送者买单。
它是手工部署的，不像工作区 worker 那样自动更新，
因此要换用新的 puter.js 运行时需要提升 `WORKER_VERSION` 并重新运行 `npm run deploy:email-worker`。

它不是中继。调用方交出的是一份邀请的*组成部分*——
种类（`workspace`、`guest` 或 `connect`）、
服务器、邀请码、名称、一段可选附言——绝不是一条消息或一个 URL。
主题、两段正文与那唯一的链接都在 worker 中撰写；
链接的来源必须是应用实际所在之处（puter.com、`*.puter.site`/`work`/`com`，
或开发中的 localhost），否则会回退到规范的应用 URL，
名称与附言会被限制长度并做 HTML 转义，
换行无法进入主题，
每位请求的收件人上限为 10、每位发送者每个 UTC 日上限 100
（在 worker 自己的 KV 中按发送者 id 的 SHA-256 计数——任何地址都不会被存储），
而没有 Puter 会话的调用方会得到 401。
邀请对话框的"电子邮件"标签页、
访客邀请对话框与共享频道对话框都通过它发送；
当 worker 不可达时，界面会提示改为复制链接，
而在 mock（`/mock.html`）中发送记录到 `__mock.emails()` 而不会被投递。

### 已知限制

- 工作区成员与频道存放在一个文档中，这在数百名成员规模下是宽裕的。
  超过之后，成员映射应当分片。
- 删除一个工作区会移除其头部块以及存放附件字节的目录；
  很长会话的深尾块以及附件的小元数据键会被留下
  （保留它们不花什么，而且已不可达）。
- 在线状态与通知取决于轮询节奏；预期有几秒延迟。
- 搜索匹配整个词，而不是前缀或短语，
  而一个月内出现在超过 2,000 条消息中的词只能找到该月最新的 2,000 条。
  藏在长历史深处的罕见词需要几次"加载更多"：
  每次调用最多回溯八个月（`before:` 过滤会从它指定的月份开始计数）。
- 索引在发布消息的那次请求中运行；每第 50 条消息还会把一个日志段折叠进分片，
  因此那一次发送会比其他发送稍慢。
- worker 会在成员关系结束时撤销该成员的 KV 共享句柄（见上文"实时"）。
  当平台拒绝撤销时（较旧的构建、被撤回的同意、铸造/撤销额度），
  该授权会一直存在，直到所有者从一个真实的 Puter 会话中收回它，
  而被移除的人会继续学到"某个分片在这个时刻有活动"
  （仅此而已：没有内容、没有会话、没有参与者）直到那时为止。
- 平台对每个应用命名空间与每种套餐都设有存活句柄上限
  （其限流页面有具体数字）；撤销会释放槽位，
  因此这个上限跟踪的是所有者当前在其各工作区中的成员数，
  而不是所有曾经加入过的人。超过之后，铸造会回答 409，
  那些成员便回退到轮询——是优雅的降级，但确实存在。

## API（worker 路由）

除 `/health`、`/webhook/:token` 与 `/bot/:token/...` 之外的所有路由
都需要一个 Puter 会话（经由 `puter.workers.exec`）。
令牌路由不需要会话：令牌本身就是凭据
（webhook 为 `tch_{id}_{secret}`，bot 为 `tcb_{id}_{secret}`；
只存储密钥的哈希，并以常数时间比较），
每个令牌每分钟限 60 次调用，
超过 16 KB 的请求体会在读取任何存储之前被拒绝。
错误为 `{ error, code, message }`。

| 方法 | 路由 | 用途 |
| --- | --- | --- |
| GET | `/health` | 存活检查与构建 id（不需要会话） |
| GET/PUT | `/api/server` | 构建、归属、`open` 标志，以及（仅所有者）事件同意状态；PUT 接受 `{ open }` 与 `{ events: true }` |
| GET/PUT | `/api/me` | 调用者的资料卡（姓名、职务、颜色、状态）及其在该 worker 上的工作区列表 |
| POST/DELETE | `/api/me/avatar` | 在该 worker 上上传或移除调用者的照片（PNG、JPEG、WebP，最大 300 KB） |
| GET | `/api/ws/:ws/members/:uuid/avatar` | 某成员的照片，供该工作区的成员查看 |
| POST | `/api/workspaces`、`/api/workspaces/sample` | 创建工作区或创建演示（仅所有者） |
| POST | `/api/join` | 用邀请码加入（请求体可携带调用者的资料卡） |
| GET/PUT/DELETE | `/api/ws/:ws` | 引导（当可订阅变更事件时会携带 `events`）、重命名、轮换邀请码、`unfurl` 开/关、删除 |
| GET/POST/DELETE | `/api/ws/:ws/icon` | 工作区的图标；管理员可上传（PNG、JPEG、WebP，最大 300 KB）或移除 |
| GET | `/api/ws/:ws/sync` | 动态增量、在线状态心跳、谁正在输入 |
| DELETE | `/api/ws/:ws/presence` | 标签页正在关闭：其人从此刻起视为离开 |
| GET/POST/DELETE | `/api/ws/:ws/push/key`、`/api/ws/:ws/push` | 该 worker 的 VAPID 公钥；注册或移除本设备的推送订阅 |
| POST | `/api/ws/:ws/conv/:conv/typing` | "我正在这里输入"（突发的首次写入用 `{ first: true }`，或 `{ stop: true }`），一次路径写入 |

| POST/DELETE | `/api/ws/:ws/members/:uuid[/role]` | 角色、移除、退出 |
| POST/PUT/DELETE | `/api/ws/:ws/channels[/:ch]` | 创建、编辑（名称、主题、描述、`postPolicy`、`threadPolicy`、`broadcast`、`bookmarks`）、归档、删除 |
| POST | `/api/ws/:ws/channels/:ch/join`、`.../leave`、`.../members` | 成员关系（管理员可把访客加入公开频道） |
| POST/DELETE | `/api/ws/:ws/channels/:ch/invites` | 管理员：铸造或撤销该频道的访客邀请 |
| POST/DELETE | `/api/ws/:ws/channels/:ch/connect/invites` | 管理员：铸造或撤销把该频道与另一个工作区共享的链接 |
| GET | `/api/connect/preview` | 一个分享码通向何处（`code`），供决定是否接受的管理员查看 |
| POST | `/api/connect/accept` | 对方的管理员为其工作区接受一个分享码（`code`、`partner: { ref, name }`）：铸造连接并只返回一次其密钥 |
| POST | `/api/connect/join` | 凭自己 worker 出具的证明加入共享频道所在的宿主（`conn`、`token`，可选的 `profile`） |
| POST | `/api/connect/disconnect` | 对方用一份断开证明结束连接（`conn`、`token`） |
| POST | `/api/connect/revoke` | 对方声明其某人已出局（被移除或被设为访客）：一份指明该人的撤销证明（`conn`、`token`）；宿主会终止他在共享频道中的席位 |
| DELETE | `/api/ws/:ws/channels/:ch/connections/:conn` | 宿主管理员：把一个工作区从该频道断开 |

| POST | `/api/ws/:ws/channels/shared` | 对方管理员：把一条连接记录为宿主频道的条目（`ref`、`ch`、`conn`、`secret`、`name`、`host`） |
| POST | `/api/ws/:ws/channels/:ch/attest` | 面向宿主的签名证明（`kind`：`join`，或管理员的 `disconnect`） |
| GET | `/api/ws/:ws/guests` | 管理员：访客及其可见的频道 |
| GET | `/api/ws/:ws/export` | 管理员：存档，每次调用一页块，可由游标续传 |
| POST | `/api/workspaces/import`、`/api/ws/:ws/import`、`.../import/file`、`.../import/finish` | 在该 worker 上从一份存档重建工作区（仅所有者），随后是它的消息、文件，并打开它 |
| POST | `/api/ws/:ws/transfer`、`.../transfer/begin`、`.../transfer/cancel`、`.../transfer/complete` | 所有者指定一位管理员；被指定者的应用会为这次转移冻结写入（`sid` 指明会话；用同一次调用续期），转移失败时放行，并把副本标记为已转移到一个新引用 |
| GET | `/api/ws/:ws/channels/:ch/members` | 谁在某个频道中 |
| POST | `/api/ws/:ws/dms` | 开启一次私信 |
| GET/POST | `/api/ws/:ws/conv/:conv/messages` | 读取一页（`before`、`after`、`from`/`to`）、发布 |
| PUT/DELETE | `/api/ws/:ws/conv/:conv/messages/:seq` | 编辑、删除 |
| POST | `/api/ws/:ws/conv/:conv/messages/:seq/reactions` | 切换一个回应 |
| POST/DELETE | `/api/ws/:ws/conv/:conv/messages/:seq/unfurl` | 构建（或移除）该消息的链接预览 |

| POST | `/api/ws/:ws/conv/:conv/read` | 移动已读游标 |
| PUT | `/api/ws/:ws/conv/:conv/notify` | 调用者的 `level`、`mute` 与（话题串的）`follow` |

| GET | `/api/ws/:ws/inbox`、`/api/ws/:ws/threads`、`/api/ws/:ws/saved` | 动态、话题串与稍后列表，附带消息 |
| POST | `/api/ws/:ws/inbox/read` | 清除动态徽标 |
| POST | `/api/ws/:ws/saved` | 保存（`conv`、`seq`）、切换 `done` 或 `remove` |
| POST | `/api/ws/:ws/scheduled`、`/api/ws/:ws/reminders` | 安排一条消息（`conv`、`text`、`attachments`、`dueAt`）、设置一个提醒（`conv`、`seq`、`dueAt`、`note`） |

## 开发

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # vitest
```

`npm run dev` 会先构建 worker 包（应用从 `public/worker/` 提供它，
该目录已被 git 忽略），然后启动 Vite。运行 UI 有两种方式：

- **`/mock.html`** 在页面内针对一个由 localStorage 支撑的假 KV
  运行真实的 worker 代码，无需 Puter 账号。它伪造
  `puter.kv`、`puter.fs`、`puter.workers` 与 `puter.peer`（标签页之间真实的
  `RTCPeerConnection`，通过 `BroadcastChannel` 信令，
  因此两个 mock 用户可以一起 huddle；`?fakemic=1` 用一个音调与一块画布
  代替麦克风与摄像头，因此不需要设备权限），
  于是每个 mock 用户都像真实用户那样部署自己的假 worker，
  而每个假 worker 都看到 store 中属于自己的那一部分。标签页共享同一个 store：
  并排打开 `/mock.html?as=alice` 与 `/mock.html?as=bob`，
  以 alice 的身份创建一个工作区，把邀请码粘给 bob，
  看着消息、在线状态与未读状态流动起来。`?reset=1` 会清除一切；
  `?env=app` 模拟运行在 Puter 内部；`?shared=1` 运行单一共享 worker 模式。
- **`/index.html`** 使用真实的 Puter SDK：登录、创建一个工作区，
  一个真实的 worker 会在你的 Puter 账号中创建。

要为演示填充应用，登录并等待它加载完成，然后在浏览器控制台中运行
以下代码（开发版与已部署版本均可用）：

```js
await teamchat.populateSampleData()
```

它会创建并打开一个新的 **Northwind Studio** 示例工作区，
其中有六名虚构的队友、六个频道、消息历史、话题串、回应与私信。
它返回该工作区的 `id`、`name` 与 `sample` 标志。
每次完成的调用都会创建一个新的工作区；既有工作区保持不变。
数据在重载后依然存在。用完后通过示例工作区的设置将其删除。
在 `/mock.html` 上它使用本地 mock 存储；
使用真实 SDK 时，它会在你的账号中创建示例，必要时还会部署你的工作区 worker。
正常的工作区限制依然适用。

测试套件针对同一个假运行时启动 worker，
并端到端覆盖各条路由（块边界、并发发送者、权限、服务器归属、
资料初始化、话题串、提及与已读游标、私信、文件、
搜索及其索引、示例工作区），
此外还有块计算、id、
引用与邀请解析、格式化与转义、搜索分词
与查询解析、时间分组及路由的单元测试。

## 部署

改动根目录的 `icon.png` 后，运行 `npm run build:icons`（需要 ImageMagick 的 `magick` 命令）
并把生成的文件提交到 `public/` 中。
这会更新 favicon、登录与启动画面素材、通知图标、
Apple touch icon 与 manifest 图标，包括带留白的 maskable 版本。

除了静态应用之外没有什么需要部署的：

```bash
npm run build               # worker 包 -> public/worker/，应用 -> dist/
```

`dist/` 完全静态并使用相对路径，且包含 worker 包，
因此可以托管在任何地方，包括 Puter 自己的托管服务
（`puter.hosting`）。用户从它创建自己的 worker；
当你发布新构建时，所有者的 worker 会在那些所有者下次打开应用时自行更新
（见*让 worker 保持最新*）。

唯一的例外是邀请邮件：共享发送方由开发者一次性部署，
放在持有邮件能力的账号下
（见*邀请邮件：一个共享的发送方*）：

```bash
npm run deploy:email-worker # puter worker deploy worker/email.js teamchat-email
```

没有它应用依然可用——邮件标签页与"或通过邮件发送"这些行
只会报告邮件不可用，并指向那个可复制的链接。

### 可选：单一共享 worker

若要运行一个所有人都创建工作区于其上的 worker：

```bash
npm run build:worker        # -> public/worker/teamchat-worker.js
npm install -g @heyputer/cli
puter login
puter worker deploy public/worker/teamchat-worker.js my-teamchat
```

然后，以部署账号登录后，通过 `puter.workers.exec` 向
`PUT https://my-teamchat.puter.work/api/server` 发送
`{ "open": true }`，
并用 `VITE_WORKER_URL=https://my-teamchat.puter.work` 构建应用，
或用 `?worker=https://my-teamchat.puter.work` 打开一次
（记在 localStorage 中；`?worker=` 会清除它）。
发布变更时覆盖同一个文件；不要创建第二个 worker，
否则调用者会被分散到两个 store 中。

事件发信号（见上文"实时"）的 `own` 模式取决于*部署*账号，
而不是某个工作区的创建者：只有当工作区创建者同时也是该 worker 被部署时所用的账号时，
他才得到 `mode: 'own'`；
共享 worker 上的其他每一位工作区创建者都会像其他成员一样拿到一个 KV 共享句柄。
从 CLI 执行 `puter worker deploy` 是以用户身份登录的，
因此该 worker 会获得自己的 `sandbox-my-teamchat` 应用，
而不是站点运行所用的那个应用，那里不会有任何标签页获得事件
（见上文"实时"）。
工作区设置现在会在其**实时更新**行中为所有者说明这一点：
该 worker 与该标签页正作为不同的应用运行，两者必须匹配。
一个其令牌完全没有承载任何应用的 worker——连 `sandbox-` 的都没有——
会在那里得到它自己的一句话。无论如何，修复办法是从 Teamchat
自身部署一个 worker：worker 的应用身份在它被创建时就已确定，
因此覆盖它所运行的文件永远改变不了它。
