# 003 执行

本文档跟踪一个已被接受的工单，贯穿执行、送达与恢复的全过程。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个未结工单都处于一个阶段，由它正在等待什么决定。请自上而下阅读表格，第一行匹配者胜出。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| 人员 / 送达 | 向执行者会话投递 Input 失败；2 秒后重试，再以倍增的延迟重试，最长到 1 分钟，成功、新的 Assignment 或工单结束都会清除该状态 | Input 未送达 |
| 人员 / 答复 | 存在一个待处理事项 | 等待答复 |
| 人员 / 评审 | 最新的 Report 为 `ready` | 等待评审 |
| 人员 / 阻塞、失败 | 最新的 Report 为 `blocked` 或 `failed`，且此后没有任何人员消息到达该工单 | 阻塞 · 失败 |
| 工作中 / 排队中 | 没有 Assignment，或有一个待处理的 Assignment | 排队中 |
| 空闲 | 最新的 Report 为 `waiting`，或 Assignment 已结束 | 等待触发器 |
| 工作中 | 其他所有情况 | 工作中 |

`person` 阶段意味着没有人工输入工单就无法继续。一条新的人员消息会把 `blocked` 或 `failed` 的工单释放给其执行者，于是它进入下一个匹配的阶段，通常是 `working`。

处于 `idle` 的工单已经结束回合且没有未决问题。订阅会话线程上的一个触发器可以继续它。

## 执行者

每个工单都会获得一个名为 `worker-<ticket id>` 的执行者会话，以及一个以工单短名命名的目录。目录在配置的执行根目录下创建，该根目录默认为 `<stateDir>/work`。

执行者会话以操作者的操作系统用户身份运行命令，无需审批。它们的 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令转为后台作业。这样执行者就能在下一步接收新消息，而不必等待长时间的命令结束。

主会话使用 `dsh-superagent-router`，具有相同的 5 秒 shell 与作业等待限制，以及用于路由的较小工具集。会话保留创建时选定的预设。执行者子代理使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与执行者槽位

当一个回合结束时仍有 shell 作业或子代理在运行，工单会保留其执行者槽位并保持工作中状态。它不会被报告为等待，主会话也不会收到等待报告。完成的作业或子代理会在同一槽位中以结果唤醒执行者。一旦某个回合在没有后台工作的情况下结束，执行者会正常报告等待。

每个回合结束后，后台工作最多有 30 分钟完成。达到该上限时，shell 作业会被杀死，工单被报告为等待。该报告包含执行者最后的话语，以及哪些作业被杀死或哪些子代理仍在活动。子代理被允许继续。执行者会在下一个回合读取被杀死作业的结果。

向人员交接会立即释放槽位，并让 Report 保持有效。这适用于 `ready` Report 或一个问题之后，除非此后有另一个 Input 到达，也适用于任何 `blocked` 或 `failed` Report 之后。

交接时子代理停止。shell 作业，比如为评审提供的服务器，可以继续运行直到 Assignment 结束。它们不占用槽位，并豁免 30 分钟限制，包括之后的回合。它们完成时不会唤醒执行者；执行者在下一个回合读取结果。

人员也可以直接在执行者会话中书写以开始一个回合。其后台工作遵循同样的规则。

当一个 Assignment 结束时，它的 shell 作业会被杀死且不唤醒会话。它的子代理被释放，它们唤醒的任何完成回合都会被丢弃。替代的 Assignment 及其等待中的 Input 在该关闭流程结束后才开始。

在 DeepSeek Harness 进程内部停止或重启插件会走同样的关闭路径。尚未进入会话历史的 Input 会被保留。关闭时每个执行者的后台工作最多等待 10 秒；进程重启会直接终止该工作。繁忙中被中断的 Assignment 会带着一条恢复说明重启。

执行者子代理，包括嵌套的子代理，使用 DeepSeek Harness 的 `standard` 预设并带有执行者的权限。它们只保留执行者允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转为后台。子代理结束时其作业被杀死。

### 准备工单目录

在第一个 Assignment 之前，如果工单目录不存在，准备命令会在执行根目录下用 `sh` 运行一次。它有十分钟完成。没有准备命令时，执行者在一个空目录中启动。

失败的命令会使工单失败并记录其输出。重试，或人员在工单的某个会话线程上发消息，都会再次尝试准备。典型的命令使用 `git worktree` 创建一个检出。当一个拉取请求的分支最后一段路径与工单的短名匹配时，该拉取请求属于该工单。

### 并发

工单从启动开始就占用一个执行者槽位，包括准备阶段，或从唤醒其空闲执行者的送达开始。它在整个活跃回合期间也持有该槽位。

配置的并发限制适用于这些槽位，并为人员消息或状态请求额外提供一个槽位。当常规槽位已满时，此类唤醒可以使用额外槽位，并在新启动之前占用下一个空闲槽位。因此新工作无法阻止人员继续已有的工单。

其他 Input，比如 CI 结果，需要等待常规槽位。启动会处于 `working / queued` 状态直到有槽位空闲。启动并发执行，因此一条缓慢的准备命令只会延迟它自己的工单。

### 执行变量

准备命令和执行者指令接收相同的执行变量。命令读取环境变量；执行者在其提示词中读取这些变量的值和说明。它们都不包含凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行者 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行者 | 执行者不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | Source 监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 代理账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或拉取请求，以及当它是拉取请求时的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动该工单的群 |

工单专属的值来自其目录和起源触发器。其他值来自当前的部署设置。只有面板能更改执行环境设置；发给主会话的文本无法更改已配置的 shell 命令。

执行者通过代理账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令在按名称调用时会失败。

这些包装器和目录建立的是默认值，而不是安全边界。执行者仍然可以用绝对路径执行程序。

## 合并

自动合并由 **Delivery requirements** 提示词管理。宿主没有针对合并的专门决策逻辑。

默认情况下，执行者绝不会以代理账号启用自动合并：GitHub 会把合并归属给启用它的人。Delivery requirements 必须指定另一个账号的 CLI 用于合并。若没有指定，则由人工来合并拉取请求。

默认指令仅在以下情况下允许自动合并：为该工单开启的拉取请求、它已就绪、所需批准覆盖 head commit，且新增行数加删除行数少于 200 行。在推送另一个修订版之前，执行者会撤销自动合并。

没有正文的评审（例如批准）也会作为触发器到达，并能唤醒等待评审的执行者。这些指令管理的是代理，而不是 GitHub 的合并规则。要强制执行批准，请在分支保护中要求它们，并清除过期的批准。省略合并 CLI 或删除自动合并段落，即可要求手动合并。

## 工单如何结束

- **无拉取请求的就绪：** 一个 `ready` Report 会以完成状态结束工单。
- **无事可做：** 执行者发现没有需要人工处理的工作时，比如一个无法复现或已被取代的请求，会报告 `dropped`。工单在没有消息的情况下结束，除非有匹配的规则要求发消息；人员之后在其会话线程上发的消息会恢复它。
### 拉取请求

工单从其执行者报告起，就跟随它起始的那个拉取请求。从其分支开启的每个拉取请求，在被执行者报告或被 GitHub Source 发现后，也会被跟随。重新打开的拉取请求会再次被跟随。

当它开启的拉取请求都不再处于开启状态时，工单即告完成。如果它没有开启任何拉取请求，那么它所跟随的所有拉取请求都必须已关闭。随后它以最后一次相关关闭的结果结束，并保留其订阅，从而允许之后的人工评论恢复它。

当被恢复的、重试的或恢复处理的工作尚未完成时，关闭不会结束工单。如果执行者已确认或答复了它所拥有的某条跟进，但在阅读该消息之后尚未做出非进展 Report 或结束回合，它也会等待。之后的一个 `ready` Report 会在满足同一拉取请求完成规则后结束工单。

聊天频道会收到一条关于拉取请求结果的最终通知。GitHub 本身已经在拉取请求上显示了结果。移除工单对某个拉取请求的订阅，也会让它停止跟随该拉取请求。

因此"等待评审"意味着一个带拉取请求的 `ready` Report。

### 跟进与上下文会话线程

执行者决定其工单自身会话线程上的人工跟进。它处理范围内的请求，并把超出范围或属于另一个工单的请求退回。一旦没有任何执行者持有该消息，它就成为主会话的候选。除此之外，主会话只能应人员请求停止工作。

一条 Input 在会话将其纳入某个步骤、随后报告或结束回合之后，就算已读。工单结束时，未读且未被确认、答复或退回的消息会退回 Eval，如 [002 授权](002-authorization.md) 所述。已读但没有动作的消息，比如致谢，不在此列。

仅为上下文而关注的会话线程仍会送达消息，但不会让工单拥有人工跟进，也不会恢复已结束的工单。那些消息可以被独立评估。

在存活工单订阅期间，以及在最后一次触发器和订阅工单结束两者中较晚者之后的两周内，Source 会轮询订阅的会话线程。此后，消息只能通过常规入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行者阻塞或失败

当执行者会话报告 `blocked` 或 `failed`，或启动失败或报错（记录为 `failed`）时，工单不会自动接收任何 Input。

模型提供方或网络的一次性失败、HTTP 408、429 或 5xx，或者被拒绝、被重置或超时的连接，会先重试三次，退避时间逐步增长：启动会再次运行，回合失败的执行者会被告知继续；失败的准备命令不会重试。

一旦失败，CI 和机器人消息会被记录在其上，但不会被送达，也不会唤醒会话。

它的工具保持可用，因此人员可以直接在该会话中继续工作。

失败的启动不会自行重试。

人员的一条消息、一个既不是 `blocked` 也不是 `failed` 的后续 Report，或一次重试，都会结束该保持状态。

它根据已存储的 Report 和 Input 推算出来，因此重启后会保留。
### 重试

当一个未结工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新的 Assignment 会重新启动其执行者并接收等待中的 Input，是对每种情况的补救措施。

一旦人员消息到达一个阻塞或失败的工单，执行者就已有该消息，因此工单显示为工作中，或在失败启动重新运行时显示为排队中，并且不提供重试，除非该消息本身的送达失败。

一次重试会结束当前 Assignment，并在同一执行者会话、目录、分支和拉取请求中启动新的 Assignment。

执行者模型仅在会话创建时生效；已存在的会话保留其模型。
### 重启

运行中的 Assignment 以"host restarted"结束，新的 Assignment 带着一条恢复说明启动，该说明要求执行者在重复任何对外动作之前先检查其目录、git 历史和 GitHub，并按最老的工单优先。

处于等待、就绪、阻塞或失败的 Assignment 保持原样，除非在该 Report 之后有 Input 到达它们，那种情况下它们也会重新启动。

会话、目录、订阅、待处理消息以及下面存储的工作在重启后依然存在，各个执行者会话纳入其历史的消息记录也一样：某个步骤在认领消息之后、在其模型调用之前执行该记录；被重启切断的回合所取走的消息，在其后有 Report 或回合结束时算作已读，而被步骤认领但被取消或错误在写入历史之前切断的消息算作未读。

一次重试或重启会再次把已投递给被替代 Assignment、而其执行者会话未取走的消息交给新的 Assignment，这些消息可能被取消或被切断的步骤丢弃；仍留在会话中等待的一份拷贝，无论是重启保留的还是跨崩溃持久化的，都会在新 Assignment 的第一条消息之前被取走，因此新的送达是唯一的一份拷贝。
### 存储的工作

dsh-superagent 在作出决策之后所做的事，比如把候选、跟进或报告转交主会话、启动 Assignment 或投递 Input，都会先存储、之后执行。

转交或投递失败时，比如其会话无法到达，会在 2 秒后重试，再以倍增的延迟重试，最长到 1 分钟；启动失败会使其工单失败，除非如上所述那是一次性失败。

每类工作只有在连续三次失败之后，才会在概览的系统问题中报告一个错误；失败的 Input 送达则显示在其工单上。

转交到主会话的消息保持顺序，通知也一样；某条失败会挡住同类的后续消息。
### Source 失败

GitHub Source 各自读取每个 Issue、拉取请求和会话线程：读取失败会把错误保留在其会话线程上，下次轮询时会再次读取，并计入 Source 的错误中，默认在连续三次轮询失败后报告；任何一次成功的轮询都会重置计数。

即使代理失去了对私有仓库的访问权限，GitHub 也会回答 404，因此 404 会被重试。

一个已通知但读取持续失败的 Issue 或拉取请求，会在首次读取失败一天后被丢弃；当 GitHub 报告它已被删除时则立即丢弃。此后它不再导致轮询失败，其会话线程保留错误，Source 的状态会标出它。

它的读取位置保持原样，因此之后对该会话线程的通知或轮询会读取失败读取所遗漏的内容。

飞书事件消费者会报告每一次失败，对订阅主题的轮询也会把每次失败保留在其会话线程上。

GitHub 列表或飞书页面中的畸形条目会被跳过，并计入 Source 的状态计数。
### 频道失败

外发消息会被存储，并作为存储的工作发送，从 5 秒开始以倍增退避重试，最长到 300 秒。

工单发往同一个会话的消息按入队顺序发出，因此它的确认消息出现在它之后答复或结果之前：只要同一工单发往同一会话的较早一条消息尚未发出，它就要等待，直到那一条连续失败三次并显示为问题。

其他工单的消息以及不属于任何工单的消息，不为它等待。

一条有失败尝试的消息在发出或被撤回之前，都是系统问题。

消息只有在其 Source 不再监听该会话，或 Source 回答该会话永远无法接收它时，才会被丢弃；在其 Source 关闭期间，它会等待。

对于已删除的 Issue 或 GitHub 上被锁定的会话，以及被撤回的消息或飞书上已找不到的消息，Source 会给出这样的回答。

对已不存在的评审评论的回复，会改为发往该拉取请求的会话。

被丢弃的消息会保留其记录，包括何时以及为何被丢弃、以及它是为哪个工单的，因此它永远不会被再次入队；一条被丢弃的确认读起来是已丢弃，而不是已发送。
### 暂停处理

停止派发、新的 Eval、Eval 超时、Input 送达和回复；已经在进行的启动会等待处理恢复。

Source 继续记录触发器，正在运行的执行者回合不会被打断。

发给已结束工单的人员消息会等待：暂停后的第一轮处理会恢复该工单，前提是其 Mandate 在当前 Policy 下仍然成立。

进行中的 Eval 在暂停期间不会过期；其截止时间按暂停时长向后顺延。
### 无效配置

被存储的 Source 配置若其种类拒绝该配置，该 Source 实例会被禁用。
