# 002 授权

授权决定了谁可以启动工作，以及这些工作可以包含什么内容。本文档建立在 [001 领域模型](001-domain.md) 之上。

宿主强制执行允许名单、规则和 Mandate。消息、评论和被引用的文档都是决策的输入，它们无法改变这些权限。

## 触发器的两条路径

### Eval：决定是否启动工作

Source 记录一条消息是否在向代理发出诉求：`mention` 表示提到了机器人或代理账号，`direct` 表示私信。准入关卡检查发送者以及 Source 的 Policy：

- 名单内的允许人员向代理提出明确请求。
- 某人在带有工单的会话线程上做跟进时，遵循下面的规则。
- 其他人员消息按其接收范围使用准入表。
- Source 机器人列表上的机器人可以产生推断候选，但永远不会产生明确请求。其他机器人不予准入。

### 订阅：延续已有工作

订阅的会话线程上的每条消息都会作为上下文送达其订阅的工单，包括来自机器人和 CI 的消息。这种送达绕过准入关卡，也不授予任何新权限。每个工单仍然受其 Mandate 限制。

某人在某个工单自己的会话线程上发的消息，归该工单的执行者决定。主会话把消息挂接到工单时同样如此。只要执行者持有该消息，它就不做 Eval，也得不到裁决。每个执行者要么在自己的工单范围内处理该请求，要么把它退回以便路由到别处。

在工单存活期间，持有关系持续有效，即使有人移除了它的订阅。它也涵盖那些已结束但未被人工停止、并且有消息在等待以恢复的工单。

主会话会收到跟进通知。在执行者持有消息期间，主会话只能应人的请求停止工作；接受、挂接、忽略和重新入队都会被拒绝。停止操作仍然要经过准入关卡，并带有下文所述的跟进强度。

### 退回与释放跟进

当执行者请求超出工单范围的工作，或该消息属于另一个工单时，它会把消息退回一次。工单保留其订阅。如果挂接的会话线程与之无关，执行者会退掉它在那里持有的消息。

只有在没有任何工单仍持有某条消息之后，这条消息才会进入一次全新的 Eval。它的候选包含执行者给出的理由。准入关卡把它当作该会话线程上的一条普通消息来判断，主会话可以接受它、把它挂接到别处，或者忽略它。退回一条工本并不拥有的消息，比如机器人消息，或某人已经送入 Eval 的消息，不会产生任何入队。

当工单结束时，它会释放执行者未读也未接手的后续消息。这些包括从未送达给执行者的消息，以及在其最后一次 Report 或回合结束之后送达的消息，前提是执行者既未确认、也未答复、也未退回它们。每条被释放的消息在没有其他工单持有它时进入 Eval。一次停止只结束被停止工单的工作。

被人工停止的工单不会再次把它的停止消息送入 Eval，除非另一个工单把它退回了。停止它的主会话可以把该消息的其余部分接受为新工作。

人员可以从面板把一条被持有的跟进送入 Eval。如果主会话随后把它重新挂接到一个存活工单，执行者会再次收到它。当没有任何有效裁决覆盖该消息时，面板也提供重新评估的选项。

### 仅用于上下文的订阅

执行者可以关注相关的会话线程，比如另一个 Issue 或拉取请求，仅用于获取上下文。它的消息会送达工单，但不授予任何权限或跟进强度。那里的用户消息不会恢复已结束的工单，除非主会话把来自该会话线程的消息挂接过来。主会话关于其他工作的说明同样只是上下文。

没有到达任何工单的用户消息，包括工单被人工停止的会话线程上的消息，走 Eval 路径。机器人消息无论是否送达给订阅的工单，都独立地走这条路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| 明确 | 名单上的人员向代理发出诉求，或在一个已有工单的会话线程上做跟进；准入表中某个单元格设置为明确请求 |
| 推断 | 不在名单上的人员在一个有工单的会话线程上做跟进，除非其准入表单元格为明确；准入表中某个单元格设置为推断候选；Source 机器人列表上的机器人的消息向代理发出诉求，或出现在 Source 接收所有消息的位置 |
| 不予准入 | 其他任何机器人的消息、准入表忽略的一切，以及在接受模式为 `off` 时的所有推断情形 |

对于不在名单上的人员，即使在有工单的会话线程上，明确的准入单元格也优先，并且适用于所有接受模式。否则他们的跟进属于推断，在 `off` 模式下不予准入。仅用于上下文而关注的会话线程上的消息，使用准入表而不是跟进强度。

## 准入

每个 Source 的 Policy 都有一张准入表。它的各行是接收范围：

- **飞书：** 每个已配置的群、机器人收到提及的其他群，以及私信。其他群只有在飞书卡片上把 **其他群** 设置为 **仅 @** 时才会被接收。
- **GitHub：** 新建 Issue、新建拉取请求、评论，以及默认分支的 CI。

一行最多有三个单元格。每个单元格决定一条消息成为明确请求、推断候选，还是什么都不成为：

| 单元格 | 可选值 | 默认值 |
| --- | --- | --- |
| 在名单上，且未向代理发出诉求 | 推断、忽略 | 推断 |
| 不在名单上，且向代理发出诉求 | 明确、推断、忽略 | 忽略 |
| 不在名单上，且未向代理发出诉求 | 推断、忽略 | 忽略 |

针对未向代理发出诉求的消息的单元格，仅在 Source 接收所有消息的位置可用，例如设置为 **全部消息** 的飞书群，或启用了全量接收开关的 GitHub 范围。CI 结果没有发送者，因此它所在行只提供最后一个单元格。机器人消息使用机器人列表，而不是这些单元格。

把"不在名单上且向代理发出诉求"的单元格设为明确，可以让该范围内任何提到代理的人请求工作。这对一个专用支持群很有用。推断候选仍取决于接受模式。跟进通常绕过这张表，但明确单元格仍会授予明确强度。

准入表是 Policy 版本的一部分。弱化某个单元格不会立即停止依据它被接受的未结工单。在恢复之前重新校验时，可以撤销这些工单的 Mandate。

### 机器人和自动评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名，以及飞书机器人识别为机器人。Source 可以列出诸如 `dependabot[bot]` 这样的机器人，它们的消息可以成为推断候选。它们必须要么向代理发出诉求，要么发布在接收所有消息的范围内。它们不能提出明确请求，也不能停止工单。

使用普通账号的自动评审者，在宿主看来算作人员。它的评论会送达订阅的工单，并产生跟进通知。团队提示词必须把这类账号标识为自动评审者。

## 路由候选

主会话用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接受、挂接、停止或忽略的决策。每一项都独立处理：某项被拒绝或某个字段缺失，不会妨碍其他项执行。

推断候选通常需要一次完整评估。有一个捷径：如果它的卡片明显不涉及任何已启用的规则，比如普通闲聊或无关讨论，主会话可以直接忽略它。裁决会记录 `ignoredFromCard`，以便把它与规则评估区分开。主会话在其 Policy 提示词部分读取已启用的规则。

接受推断候选始终需要评估。直接接受会拒绝准入关卡未判定为明确的触发器。

## 接受模式与规则

接受模式是 Policy 的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断都不会成为候选，比如未向代理发出诉求的消息、机器人的消息，或不在名单上人员的跟进 |
| `observe`（默认） | 推断候选会被评估；肯定的评估记录为标注"本会接受"的忽略，且不会接受任何内容 |
| `auto` | 对推断候选的肯定评估会接受它 |

明确请求在所有模式下都有效。建议从 `observe` 开始，在检视已记录的裁决之后再切换到 `auto`。每次评估对每个已启用的规则恰好判断一次，无论是否匹配。主动接受至少需要一条匹配的规则。

每条规则描述一类主动型工作。工单的 Mandate 记录匹配的规则，其执行者会收到这些规则的名称和指令。

对该工单而言，某条规则的流程与沟通要求会覆盖默认值。静默规则可以抑制确认；评审规则可以指定所需的评审者以及合并前的批准。适用于每个工单的要求应当放在团队提示词部分中。

## Policy 版本

规则、接受模式以及每个 Source 的 Policy 共同构成 Policy 版本。每个 Mandate 都记录它被接受时所依据的版本。

版本变更会丢弃正在运行的 Eval，并重新排队其触发器。它还会向每个受影响的存活工单发送一条策略已变更的 Input。该 Input 说明：

- 某条匹配规则发生了改变，包括其新文本，或不再适用；
- 请求者可能已无法启动工作；或
- 主动型工作不再被接受，例如因为模式从 `auto` 变了。

未受影响的工单不会收到通知。该变更不会立即撤销存活工单的 Mandate。

Source 配置与 Policy 是分开的。它控制什么内容进入系统：读取哪些群，以及某个范围是接收全部消息还是仅接收提及。Mandate 记录其 Source 和接收范围。恢复需要 Source 仍在监听该会话线程，但不要求它仍在那里接收所有消息。

当 Source 关闭时，回复处于等待状态。如果 Source 已不再监听其目标，回复会被丢弃。

关于执行者能如何处理自身结果的条件，比如它何时可以合并，并不决定谁可以授权工作。这属于代理的指令，而不属于 Policy。

## 恢复与停止

已结束的工单保留其 Mandate。某人在它自己的某个会话线程上发的消息可以恢复同样的工作，无需新的 Eval 或裁决，无论是谁发送的。机器人和 CI 不会唤醒已结束的工单。执行者决定该请求是否符合范围，若不符合则结束本轮。

只有三种操作会改变 Mandate：接受创建它，人员的停止撤回它，重新校验失败撤销它。被人工停止的工单保持结束状态，不再接收任何内容。在那里请求的工作需要一次新的接受。

### 恢复前的重新校验

Source 必须仍在监听原始会话线程。其余检查取决于 Mandate 的依据：

- 明确的跟进 Mandate 通过。
- 推断的 Mandate 需要 `auto` 模式，且其匹配规则仍然启用。
- 由表格单元格准入的 Mandate，在今天的表格和发送者成员关系下必须仍能获得至少其原有的强度。因此，把某个发送者从名单中移除，可能撤销通过"名单内发送者"单元格接受的 Mandate。
- 机器人的 Mandate 要求该机器人仍在 Source 的机器人列表上。推断的表格 Mandate 和机器人 Mandate 还需要 `auto` 模式和已启用的匹配规则。
- 其他 Mandate 要求发送者仍在 Source 的允许名单上。

如果重新校验失败，工单保持结束状态，不接收其任何等待中的消息。每条消息都被视为没有到达任何工单；如果没有其他工单持有它，它就进入 Eval。主会话不会得知它曾到达某个执行者。处理暂停之后同样适用。挂接到该工单会被拒绝，进一步的工作需要一次新的接受。

- **某人在会话线程中说"停止"是一个普通触发器，** 由 Eval 决定是否停止。执行者不能宣称某人要求它停止。
- **在面板中停止是一条命令。** 它直接作用于工单，并被记录为手动停止。
- **等待条件属于 Source。** 诸如"N 小时内无处理人"这样的条件，应当由一个自行等待并再次检查的 Source 来实现；Eval 从不等待。

## Eval 未完成时

时限从候选到达主会话时开始。等待送达的时间不计入其中，未送达的候选永不过期。

过期的 Eval 会为其触发器排队以备再次尝试。连续两次重试之后，第三次过期记录 `unavailable`。评估失败同样记录 `unavailable`；之后来的触发器可以启动一次新的 Eval。Policy 变更，或针对过期 Policy 作出的裁决，都记录 `unavailable`，并立即在当前版本下重新排队该批次。

`evals` 健康项报告最近一小时内未解决的 unavailable 裁决。`scripts/dsh-superagent status` 包含该错误。

只有当 unavailable 裁决不到 24 小时、仍是其会话线程上最新的裁决、尚未被忽略，且该会话线程既未排队也未在评估时，面板才会请求人工关注。人员可以重新评估该触发器，或忽略该问题。
