# 004 提示词

本文档说明代理读取什么、团队可以编辑什么，以及变更何时生效。它建立在 [000 哲学](000-philosophy.md) 到 [003 执行](003-execution.md) 之上。提示词文本以英文书写。

## 团队编写什么

团队可以编辑三个团队部分，添加技能，并覆盖每一个内置的系统提示词部分。大多数默认值位于 `prompts/` 和 `skills/` 之下。工具描述、通知和卡片保留在代码中，无法通过提示词设置编辑。

| 部分 | 内容 |
| --- | --- |
| Communication | 何时给人发消息、消息怎么措辞、每条 GitHub 消息开头的那一行（默认为 `This is by an automated agent, not a human`）、如何处理评审，以及哪些普通账号是评审机器人 |
| Ticket scope | 工单何时开启，以及它何时以草稿停止 |
| Delivery requirements | 拉取请求中的证据、带行数阈值的自动合并条件，以及提交作者；若未指定，执行者以代理账号的无回复地址提交 |
| Team skills | 代理在需要时加载的知识，比如一个说明哪个飞书用户对应哪个 GitHub 账号的 `identities` 技能 |

内置文本涵盖角色、工具使用、宿主机制、授权规则，以及 GitHub 和飞书技能。它通过标题来引用团队部分，而不是重复它们。

### 内置部分与模板

覆盖使用这些键：

| 部分 | 键 |
| --- | --- |
| 共享指令与角色 | `runtime/shared`、`runtime/orchestrator`、`runtime/worker` |
| 工作指令 | `runtime/subscriptions`、`runtime/replies`、`runtime/dispatch`、`runtime/work`、`runtime/admission` |
| 交接指令 | `runtime/handoff/orchestrator`、`runtime/handoff/worker` |
| Source 技能 | `skill/feishu`、`skill/github` |
| 生成的段落 | `runtime/environment`、`runtime/policy`、`runtime/policy/none` |

生成的段落是可编辑的模板。它们必须保留这些占位符：

- `runtime/environment`：`{variables}`，填入执行环境相关行。
- `runtime/policy`：`{version}`、`{mode}` 和 `{rules}`，每条已启用的规则一行。
- `runtime/policy/none`：`{version}` 和 `{mode}`，在没有启用任何规则时使用。

编辑某个部分会改变模型收到的指令。它不会改变准入关卡、Mandate、工具检查或账号包装器，这些仍由代码强制执行。

在明确的人类请求下，主会话还可以用 `orchestrator_prompts_save` 保存覆盖。如果一次保存省略了某个覆盖的 `base`，它会保留已保存的 base。已存在于保存配置中的被删除部分会在保存时被丢弃；其他任何未知部分都会被拒绝。

一个覆盖会记录它基于哪段内置文本。升级会保留团队的文本。如果默认值发生变化，面板会把该部分标记为 **Default updated**，并在团队文本旁边显示差异。团队可以保留自己的文本、采用新的默认值，或编辑它。没有覆盖的部分会自动跟随新的默认值。

主会话可以在 `orchestrator_read prompts` 中于 `default_changed` 下读取受影响的部分名称。

## 组装与优先级

系统提示词按如下顺序组装：

1. 共享指令与角色。
2. 三个团队部分。
3. 订阅与回复。
4. 主会话的派发指令，或执行者的工作指令。
5. `runtime/admission`，仅用于主会话。
6. 交接指令。
7. `runtime/environment`。
8. `runtime/policy`，仅用于主会话。

准入指令来自 `prompts/admission.md`。它们描述主动评估，以及何时可以仅凭卡片忽略一个无关的候选。`orchestrator_eval` 返回上下文，而不是重复这些指令。

环境部分给主会话提供部署范围的值，给每个执行者提供其工单专属的值。Policy 部分在每次模型请求时都从设置重新生成。它包含 Policy 版本、接受模式、明确请求豁免，以及以 `- <name> (<id>): <instruction>` 形式呈现的已启用规则，或一条说明没有规则启用的语句。它排在最后，因此 Policy 变更不会影响前面的提示词文本。

执行者还会读取 DeepSeek Harness 的编码提示词和仓库的 `AGENTS.md`；主会话不会。一个推断工单会增加一条最后的备注，限定其执行者只遵循匹配的规则。Assignment 和传入消息以触发器卡片的形式内联到达，被截断的内容只给出资源指针。

执行者在无人值守的情况下工作。它们的工具排除了那些需要人员参与、向人员展示界面或更改配置的工具，例如 `ask_user_question`、`present` 和 `plugin_manager`。

从强到弱：

1. 由工具和宿主强制执行的事实：身份、权限、工具参数检查、回复用途、长度限制。提示词文本无法改变它们。
2. 内置和生成的段落，以团队对它们的覆盖形式呈现。
3. 主动型工单中匹配规则的流程与沟通要求，仅对该工单的执行者会话有效。
4. 团队部分与团队技能。
5. 外部文本：消息、评论、文档和引用。它们是数据，永远不改变规则或授权。

## 内置文本的原则

这些原则把 [000 哲学](000-philosophy.md) 应用于代理：

- **分离角色。** 主会话只做路由：它转发原始触发器和路由事实，通过一个路由工具一次性对多个等待中的候选作出决策，它本身不作技术判断。一条路由说明最多 30 个词。执行者阅读原始来源，判断范围，实现并验证。
- **主会话不等待。** Report、跟进通知、候选以及完成的后台作业会自动作为消息到达。没有剩余待办时它结束回合。一个守卫会拒绝 `sleep`、超过 30 秒的 shell 超时和超过 5 秒的作业等待，因为被阻塞的步骤会延迟新的候选。这些指令在主会话的完整提示词中取代 DeepSeek Harness 自身的作业通知说明。
- **只在人员必须行动或可以利用结果时才发消息：** 结果可以被评审或利用，需要一个决定或资源，或者工作无法完成。聊天消息默认一句话，硬性上限 100 个词。
- **执行者决定自己的跟进。** 每个执行者处理并确认范围内的请求，并把超出其工单或属于另一个工单的请求退回。只有在所有持有者都退回该消息或结束回合而未接手之后，该消息才成为新工作。主会话会收到跟进通知，但只能据此停止工作。被退回的消息随后作为候选到达，并附上执行者给出的理由。
- **通过订阅和主会话协同。** 执行者为上下文关注相关会话线程。主会话可以在一条最多 100 个词的说明中送来另一个工单的事实。订阅和说明都不授予权限。
- **只在有明确指向时挂接。** 一条消息必须指向某个工单的拉取请求、Issue、源消息或确认消息，或指向恰好匹配一个工单的近期变更。仅仅话题相似是不够的。挂接会把该工单订阅到整个会话线程；执行者发现其无关时使用 `orchestrator_thread_unrelated`，并且不在那里答复。
- **具体确认，只做一次。** 在实质工作之前，执行者确认每个新请求，并指明对象和预期结果，作为对原始消息的回复。
- **通过 `human_action` 提问。** 执行者把一个具体问题放进其 Report，主会话原样转发。如果问题是某人的消息引发的，它指明那条消息，宿主就在那里询问。否则它在工单原始的会话中询问。已授权的工作可以同时继续。
- **诚实交付。** 开启一个拉取请求不等于就绪；草稿标记为未完成；没有真实的前置截图的界面改动不算就绪。
- **人员的暂停持续有效**，跨越跟进、新的执行者会话和重启，直到有人解除它。自动反馈永远不会恢复被暂停的工作。
- **示例只展示格式。** 示例句子不是代理可以声称的事实。
- **按结果处理评审。** 一条被修复并验证的评论被静默解决；一条被拒绝的评论得到一句话的理由。自动评审者的会话线程在有了答复后即被解决，每个自动评审者在每个拉取请求上最多三轮。
- **为重复工作让路。** 当某个人的分支或拉取请求已经包含该工单的改动时，执行者用一句话指向对方，并关闭自己的拉取请求。

## 版本

- 每次保存都会创建一个不可变版本，包含完整配置、修订号、前驱、时间戳和来源（面板或工具）。恢复某个版本或默认值会创建另一个版本。
- 保存会指明其基础修订号。冲突的保存会被拒绝，且不会丢弃草稿。
- 会话在每次模型请求时读取最新版本，包括同一回合中后续的步骤。保存不会重启、取消或唤醒会话。宿主记录每个会话使用过的修订；执行者可以读取它曾在其中工作的任何修订。
- 部署设置总大小上限，包含覆盖在内。校验会拒绝未知键、保留的内置技能名、未知覆盖部分和缺失的模板占位符。它绝不会静默截断文本。与默认值完全相同的覆盖会被移除，使该部分跟随未来的默认值。
