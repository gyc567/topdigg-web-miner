# 6800 星的 shuohao-skills：AI 短劇真正的門檻不是生成，是「誰敢把品質門寫成程式碼」

**結論先行：** GitHub 上有個 6800 星、960 多個 fork 的開源專案 `shuohao-skills`，做的是把一本小說變成能直接下單給影片模型的短劇投產包。7 個 skill，6 個製作階段，60 道品質門，1600 多項自測斷言。

但它真正值錢的東西不是那 7 個 skill，而是它敢做的一件反潮流的事：**把「檢查清單」從提示詞裡趕出去，寫成確定性程式碼，讓模型過不了門就走不下去。**

這是我今年讀到的最乾淨的「AI 工程化」樣本。下面把它拆開講透：專案是什麼、怎麼跑、裡面藏了什麼設計哲學，以及——對做短劇生意的人，這套東西到底值多少錢。

---

## 一、專案說明：一個把短劇生產拆成六段的檔案管道

`shuohao-skills` 的作者是「爍皓」（X: @eternityspring），Apache 2.0 授權，2026 年 8 月開坑，兩個多月做到 6800 星。倉庫定位一句話說清：

> 面向各類 Agent 的 AI 短劇製作 skill 集合，從一本小說到直接交給生成管線的製作素材。

它不綁定任何 Agent 執行環境。Claude Code 和 Codex 只是「兩個受支援的例子，不是前提」——只要你的 Agent 能讀 `SKILL.md`、能跑 Node 腳本，就能用。

### 1.1 七件套

| Skill | 幹什麼 | 品質門 |
|---|---|---|
| `novel-outline` | 把小說改編成短劇大綱五件套：改編說明、人物表、爽點表、分集梗概、資產清單 | 14 道 |
| `novel-characters` | 把大綱定下的角色做成角色設定集：人物畫像、形象提示詞、音色提示詞、三視圖版面指令 | — |
| `character-refs` | 真正生成角色參考圖：正面全身錨點 + 派生視圖 | 檢查門 |
| `novel-art` | 美術設定集：場景一致性錨點、光照狀態變體、敘事道具表、白底可去背 | 10 道 |
| `novel-script` | 劇本：場次 + 節拍流（動作與台詞交替）、逐集時長確定性換算、台詞本 | 10 道 |
| `novel-staging` | 每場開場站位：誰在哪件東西的哪一側、坐還是站、面向哪 | 8 道 |
| `novel-storyboard` | 分鏡：段（≤15 秒）→ 分鏡（2–5 秒硬門）→ 分鏡圖，H3 與 Seedance 投產包 | 18 道 |

流程圖長這樣：

```
小說原文 → 大綱 → 角色 → 美術 → 劇本 → 開場站位 → 分鏡 → 視頻投產包
                ↑        ↕        ↕
              角色 ←──────┴────────┘
                └→ 角色參考圖（喂給分鏡）
```

注意 `novel-characters` / `novel-art` / `novel-script` 三者之間是**雙向箭頭**——角色、美術、劇本是同步迭代的三條線，不是瀑布。這是有意的：劇本寫到一半發現角色沒戲份，要回去改大綱；美術發現道具撐不起這場戲，要回去改劇本。

### 1.2 它交付什麼形態

每個階段產三件套：`*.json`（機器讀的工作資料）、`*.md`（給人讀的文字匯出）、`*-report.html`（雙擊就能開的單頁評審報告）。

報告不是裝飾。舉 `novel-outline` 的報告：

- **KPI 帶**：總集數、爽點數、角色分檔、主場景數、生成難點、改編幅度
- **爽點節奏圖**：劇情時間軸上標出每個爽點，空檔直接標在軸上（「— 4 集空檔 —」），超閾值變紅
- **每集調度矩陣**：60 集 × 25 角色的格線，一欄直著讀就是那一集的需求單
- **品質門面板**：✓/✗ 烘進頁面，未過的項目直接彈出問題橫幅
- **匯出 JSON**：下載的就是 `outline.json` 原樣

作者的定位很明確：**這是一份業內評審用的單頁報告，讀者拿它拍板砍不砍、排產備不備。** 報告的預設交付形態決定了它是被用來決策的，而不是被歸檔吃灰的。

`novel-staging` 更進一步，交付的是**可互動的 HTML 工具**：每場一張俯視平面圖，人可以直接拖動換位置、點一下改坐站和朝向，改完點「匯出 JSON」下載的就是新的 `staging.json`，不用手改 JSON。

### 1.3 工程限制

| 項 | 要求 |
|---|---|
| Node | ≥ 18，**只用標準函式庫，零 npm 相依** |
| API key | **不需要**，用目前工作階段額度 |
| Agent | 任何能讀 SKILL.md + 跑 Node 腳本的 Agent |
| 出圖模型 | 只有 `character-refs` 需要（Qwen Image / Codex / GPT Image 2 / 自訂命令） |

零相依這條不是炫技，是**可攜性的前提**。你要把一個 skill 單獨拷走，它得能跑。

## 二、詳細教學：從零跑通一整條管線

### 2.1 安裝

```bash
git clone https://github.com/eternityspring/shuohao-skills.git
cd shuohao-skills
./scripts/install.sh
```

安裝腳本做的事很樸素：把每個 skill 目錄**符號連結**到偵測到的 Agent skills 目錄。符號連結不是複製，所以 `git pull` 之後立刻生效，不用重裝。

```bash
./scripts/install.sh novel-characters   # 只裝一個
./scripts/install.sh --codex            # 只裝到 codex
./scripts/install.sh --uninstall        # 拆軟鏈
```

手動裝也行：

```bash
ln -s "$PWD/skills/novel-characters" ~/.claude/skills/novel-characters
ln -s "$PWD/skills/novel-characters" ~/.codex/skills/novel-characters
```

裝完先跑一遍全部自測，確認環境沒問題（這步別跳）：

```bash
for f in skills/*/scripts/selftest.mjs; do node "$f"; done
```

自測不調模型、不花額度，全部跑完約一秒。**注意：上游只在 macOS + Node 24 上驗過，Linux 和更低版本 Node 理論上沒問題但沒驗。**

### 2.2 工作目錄約定（別平鋪）

一整條管線跑完會產出大量 json / md / html。倉庫裡固定的目錄約定是：

```
<demo>/
├── outline/       ← <劇>-outline.json / .md / -report.html
├── characters/    ← <劇>-cast.json / .md / -report.html
├── art/           ← <劇>-art.json / .md / -report.html
├── script/        ← <劇>-script.json / .md / -report.html
├── staging/       ← staging-report.html（主交付）+ staging.json
├── storyboard/    ← <劇>-storyboard.json / .md / -report.html
│   ├── manifest.json
│   ├── E01-01/        ← export 的分鏡投產包，每段一個文件夾
│   └── E01-02/
├── docs/
└── scripts/
```

有個坑值得單獨拎出來：**段資料夾不要再往下收一層**（比如塞進 `segments/`）。分鏡報告裡的圖走相對路徑 `<段號>/f<切序>.png`，預設要求報告 html 和段資料夾同級。多套一層又不改路徑，報告裡的圖會**靜默**全變成「未生成」佔位——上游實測把 10 個段資料夾移進 `segments/` 之後，內嵌圖從 2 張變 0 張，**報告不報錯**。

這條是「靜默失敗」的典型樣本：檔案在，圖在，連結錯了，頁面假裝一切正常。

### 2.3 Stage 1：改編大綱

```bash
node skills/novel-outline/scripts/novel-outline.mjs chunk <book.txt> <workdir>
node skills/novel-outline/scripts/novel-outline.mjs validate <workdir>/outline.json --stage beats
node skills/novel-outline/scripts/novel-outline.mjs validate <output>/<劇名>-outline.json
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<劇名>-outline.json --md   > <劇名>-outline.md
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<劇名>-outline.json --html > outline-report.html
```

**流程裡最值錢的一條規矩：先拍板，再細化。**

骨架（砍了哪條線、合了哪些人、大爆點落在第幾集）必須先出**快版**給使用者點頭，之後才允許寫分集梗概。這不是口頭約定，是**流程門**：寫分集前必須過 `validate --stage beats`，爽點間隔和 major 時機錯了當場攔下。

作者的邏輯很實在：**快版錯了只損失一輪骨架，分集寫完才發現方向錯，全廢。** 60 集的分集還是分批寫，每批 ≤ 10 集——一口氣寫後半段必崩。

14 道門長這樣：

| 門 | 預設閾值 |
|---|---|
| 主角組（男女主 + 主反派） | 1–5 人 |
| 有名字的重要配角 | ≤ 10 人 |
| 功能性角色（占臉不占名） | ≤ 10 人 |
| 主場景上限 | **隨集數動態**：4 + ⌈集數/10⌉，夾在 5–15（6 集→5，60 集→10，110 集起封頂 15） |
| 敘事道具上限 | ≤ 8 件 |
| 一次性場景有規避方案 | — |
| 爽點間隔無真空區 | ≤ 3 集 |
| 第 1 集有鉤子 | — |
| 大爆點不壓最後一集 | — |
| 每集三欄齊全（梗概/鉤子/懸念） | — |
| 三人以上同框有拆解方案 | — |
| 生成難點進預警清單（雨戲/肢體接觸/人群/手部特寫） | 關鍵字掃描 |
| 引用完整：無失業角色、無空轉場景、ID 都存在 | — |
| 梗概是敘述體，無引號對白 | — |

兩個閾值的設計值得拆開講，因為它們暴露了「AI 短劇」和「實拍短劇」的根本差異。

**角色為什麼分三檔而不是一刀切**：一刀切混淆了兩件不同的事——「觀眾要記住誰」和「製作要維護多少張臉」。主角組上限守的是戲份和記憶負擔；配角和功能性角色的上限守的是**AI 角色資產成本**（每一檔的一致性投入都完全不同）。功能性角色「沒有人物弧」是正常的——醫生就是來縫針的，校驗器不會強求。

**場景上限為什麼比實景劇寬得多**：實景時代「≤ 5 個景」是經濟學（搭景要錢）；AI 短劇裡場景是生成的，**沒有搭景錢**，實景時代那條經濟學不成立。上限守的只剩場景的**跨集一致性資產**和觀眾的空間認知，觀賞性直接吃場景多樣性，所以隨集數放寬到 15。

順便：五件套的第五件「資產清單」**永遠是腳本算出來的**，模型手寫必漏。

### 2.4 Stage 2：角色設定

```bash
node skills/novel-characters/scripts/novel-characters.mjs seed <outline.json> > <workdir>/seed.json
node skills/novel-characters/scripts/novel-characters.mjs chunk <book.txt> <workdir>
node skills/novel-characters/scripts/novel-characters.mjs merge <workdir> --apply merges.json | tee <workdir>/merged.json
node skills/novel-characters/scripts/novel-characters.mjs validate <cast.json>
node skills/novel-characters/scripts/novel-characters.mjs render <cast.json> --html > cast-report.html
```

**seed 機制是這套架構的通用範式**：上游已拍板的事實（角色 ID、名字、分檔、人物弧、合併來源）由腳本確定性搬運過來，留空的是這一層才該做的設計（別名、一句話畫像、形象提示詞、音色）。文件裡反覆強調的一句：

> **這些事實不要讓模型重新想一遍。**

同一句話在 `novel-art`、`novel-script`、`novel-staging`、`novel-storyboard` 四個 skill 裡各出現一次。**避免重複推理是 AI 管線裡最便宜的優化**——模型每重新想一遍，就多一次跑偏的機會。

別名歸併這塊有個細節值得一提。腳本只能做**精確比對**收斂（某塊把「陸」列成「陸行遠」的別名，兩條就併成一個人），剩下的 `mergeCandidates` 是語意判斷，腳本做不了，必須人／模型逐條複核。候選來自名字包含關係（`「陸」⊂「陸行遠」`），但作者明確標註這是**強訊號不是判決**——同姓的父子、兄弟不能合。而「陸先生」和「行遠」沒有包含關係，壓根不會進候選，得自己看出來。

上游的樣例《渡口》專門造了這個用例：貨郎全程只有綽號、船夫只被叫過「老伯」。

### 2.5 Stage 3：美術設定

```bash
node skills/novel-art/scripts/novel-art.mjs seed <outline.json> > <workdir>/art.json
node skills/novel-art/scripts/novel-art.mjs validate <art.json> --cast <cast.json>
node skills/novel-art/scripts/novel-art.mjs render <output>/<劇名>-art.json --html > art-report.html
```

這個 skill 的前提刻在骨子裡：**這是 AI 生成，不是實拍。** 沒有勘景搭景置景採買，環境和道具都是要被生成幾十次還得長得一樣的資產。所以全部交付都圍繞一致性：

| 交付 | 解決什麼 |
|---|---|
| 一致性錨點（每景 3–5 個） | 觀眾靠它認場景，QC 靠它核對生成鏡頭有沒有漂 |
| 光照時段變體 | AI 換時段是**重新生成**不是重新打燈，每個狀態落成完整提示詞 |
| 空景出圖提示詞 | 環境和角色是兩層資產，參考圖裡混進人，一致性全毀 |
| 變體機制（`variantOf`） | 生成新景便宜，但變體複用母場景資產更一致 |
| 道具狀態變體 | 皮箱的合上與打開是兩張參考圖——道具有狀態弧，場景沒有 |
| 道具尺度參照 | AI 經常把手持道具畫成家具尺寸，提示詞必須帶尺度短語 |
| 道具白底無手 | 道具圖要被貼進各種鏡頭，必須可去背；拿著道具的手是最常見污染 |

「道具只收敘事道具」這條邊界定得很清楚：有特寫、跨集、承載劇情的，通常 3–8 件。場景陳設歸場景錨點，一次性手部道具鏡頭級提示詞解決，都不單獨建資產。

「皮箱這種跟人走的道具，就該在這一層」——塞進場景錨點或角色畫像都不對。

10 道門裡最實用的兩條：**提示詞全英文**（中文提示詞餵影像模型效果普遍更差，這是被門強制執行的最佳實務，不是靠自覺），以及**提示詞不含角色名**（角色名由影像模型自己去關聯參考圖，名字反而會干擾）。

### 2.6 Stage 4：劇本

```bash
node skills/novel-script/scripts/novel-script.mjs seed <outline.json> --eps 1-3 > <workdir>/script.json
node skills/novel-script/scripts/novel-script.mjs validate <script.json> --outline <outline.json> --art <art.json>
node skills/novel-script/scripts/novel-script.mjs render <output>/<劇名>-script.json --html > script-report.html
```

**前提刻在骨子裡：劇本管戲，分鏡管拍。** 台詞要反覆推翻重寫，綁上鏡頭分解後每改一句都得重排鏡頭。所以這層只有集、場次、節拍流，沒有鏡號。

但有一條底線：**台詞必須是結構化資料，不能寫成散文。** 每句台詞是獨立項目（說話人 + 台詞 + 語氣），動作是獨立節拍。這是全部確定性檢查的地基。

時長是**算出來的**：台詞按 4.5 字／秒換算，動作按 2.5 秒／拍，一集三分鐘就是三分鐘，超了欠了當場攔下，不流到生成環節才發現。

10 道門裡兩條最見功力：

- **鉤子具象在前 3 拍內兌現**（`hookBeat` 認領）——鉤子不是標籤是第一拍。短劇的生死線必須落在紙面，而不是靠模型「記得寫個懸念」。
- **每場至少一個動作節拍**——純對白的場是廣播劇，AI 生成時沒有畫面可寫。

寫超了先砍動作節拍再壓台詞；寫欠了**補戲不灌水**——加衝突不加寒暄。

### 2.7 Stage 5：開場站位（最有意思的一個 skill）

```bash
node skills/novel-staging/scripts/novel-staging.mjs seed <script.json> --art <art.json> --outline <outline.json> > <workdir>/staging.json
node skills/novel-staging/scripts/novel-staging.mjs validate <staging.json> --script <script.json> --art <art.json>
node skills/novel-staging/scripts/novel-staging.mjs render staging.json > staging-report.html
node skills/novel-staging/scripts/novel-staging.mjs blocking staging.json
```

**為什麼要單獨排站位？** 短劇的每一段影片是一次獨立生成，各段自己決定誰坐哪。群戲裡六個人圍一張長桌，第一段桌邊多出五個沒名字的賓客，第三段端酒坐著的人穿著主角的衣服。

分鏡的走位句一段接一段地交接，可每一場**第一段**的那一句是分鏡自己編的——**人看不到、改不動**。所以在分鏡之前，每場先定一份站位，分鏡照抄。

流程是**先認圖再排位**：從場景圖主視角裡認出人會站在旁邊、坐在上面的東西（4–20 件），寫名字、圖上的框、俯視平面上的位置。然後按劇本排誰在哪件東西的哪一側、沿這一側多遠、坐還是站、面向哪。

兩條鐵律：

- **圖裡看不到的不寫**（提示詞裡有、圖上沒有的 一律不寫）——否則人坐上高台，每段影片都不一樣
- **`plan` 按透視推算**，不是照抄 `box`——透視場景圖上的「桌子北側」只是一條窄縫，前後深淺說不清，擺平了從上往下看才一目了然

排位規則同樣寫死：**後來才進來的人開場不在**；**劇本沒寫有別人就沒有群演**；**只使用認出來的東西**。

走位句由程式寫，一字不差交給分鏡：

> 「胡二爺坐在第三排座板上，面向北；其餘座位空著，沒有其他人。」

這個 skill 是 2.2.0 才加的（2026-10-14），是最新的一個，也是最能說明作者在真實專案裡踩過坑的一個。

### 2.8 Stage 6：分鏡

```bash
node skills/novel-storyboard/scripts/novel-storyboard.mjs seed <script.json> --eps 1-3 --aspect 16:9 > <workdir>/storyboard.json
node skills/novel-storyboard/scripts/novel-storyboard.mjs validate <storyboard.json> --script <script.json> --outline <outline.json> --cast <cast.json> --art <art.json>
node skills/novel-storyboard/scripts/novel-storyboard.mjs render <output>/<劇名>-storyboard.json --html > storyboard-report.html
node skills/novel-storyboard/scripts/novel-storyboard.mjs export <storyboard.json> --protocol h3 --out storyboard
```

**前提刻在骨子裡：鏡頭是生成出來的，多切一鏡的成本幾乎為零。** 所以這裡不心疼鏡頭數量，上限只有一個：影片模型單段生成的時長（預設 15 秒）。

三層結構：

```
段（segment）= 一次視頻生成調用，≤ 15 秒，不跨場次
 ├─ 分鏡（cut）= 段內剪切，每切 2–5 秒（硬門），各自認領劇本節拍
 ├─ 分鏡圖     = 每切一張關鍵幀：主圖釘 0.00 秒，子圖釘各自切點
 └─ H3 提示詞  = 一段一條，多圖對齊指令 + [Shot k] 切點時刻逐字對賬
```

幾個關鍵機制：

- **節拍認領**：每個分鏡宣告它覆蓋劇本某場的哪幾個連續節拍，不許跨場次——換景必換鏡。這讓分鏡和劇本的關係變成**可機械對帳**的。
- **對話正反打在同一段裡一次生成**：全景、A 近景、B 近景各是一個 2–5 秒的分鏡，每格構圖由自己的分鏡圖控制，**不靠文字賭**。
- **對齊指令是推導出來的，不是寫出來的**：`Picture 2 aligns with the 3.00-second mark…` 和 `[Shot k] At 00:0X.XXX` 全部由分鏡秒數推導，validate **逐字對帳**——改了秒數忘改提示詞，當場攔。
- **H3 與 Seedance 並列**：H3 提示詞用 MiniMax 官方 I2VA 結構（對齊指令 + `integrated_multimodal_description` + `overall_soundscape` + `non_diegetic_music`）；Seedance 提示詞**由腳本按官方結構現拼**，模型只寫每切的 `shot`，不寫秒數、編號和圖片引用。
- **構圖量化欄位**：每段 `blocking`（誰在左誰在右、間距），每鏡焦距／機位／構圖／視線落點／焦點／穩定性。理由寫得很直白——純參考圖出片時沒有分鏡圖，「多近、多滿、誰在哪、眼睛看哪」這些資訊**要麼寫成字，要麼就地消失**，實測消失的正是它們：景別偏遠、動作偏小、人物擺位隨意。

18 道門裡最硬的幾條：**分鏡時長 2–5 秒是硬門不是建議**（3 秒左右的短劇注意力節奏）；**台詞裝得下**（認領節拍的台詞秒數 ≤ 分鏡秒數，逐切檢查）；**單鏡同框 ≤ 3 人**（超了必須帶拆解說明）；**H3 台詞逐字**（改一個標點都過不去）；**影片提示詞不含角色名**（H3 與 Seedance 官方規範要求）。

### 2.9 合頁與匯出

五個階段的報告可以合成一張單頁：

```bash
node scripts/report.mjs --from <demo目錄> --out report.html
```

**它是組裝器，不是第六個 skill。** 不 import 任何 skill 的程式碼，而是調各自的 `render --html` 拿產物再拼裝。所以五個 skill 一行不改，各自仍然獨立可跑、可以單獨拷走；某個 skill 改了渲染，這邊自動跟上。

合併要解決三件事，**全部在組裝器裡做，不侵入 skill**：

- **樣式串味**：五份報告共用 57 個類名，其中 13 個同名不同定義（`.copy` `.kpis` `.badge` `.chip`…），給每條選擇器加作用域前綴
- **腳本串味**：各報告腳本都是 `document.querySelector('.expo')` 這種全域查詢，合成一頁只會命中第一個——五個匯出按鈕會全廢。做法是套一層 Proxy 把 `document` 換掉
- **圖片路徑**：各報告的圖相對自己那份 json 的目錄，合成後按輸出檔案位置重算

組裝器自己踩了三個坑，每個坑現在都有一條自測斷言盯著：

1. `<script type="application/json">` 是各報告內嵌源 JSON 給匯出按鈕讀的**資料**，當成腳本抽出來執行，瀏覽器直接甩 `Unexpected token ':'`，五個面板一起廢
2. 規則之間的 CSS 註解會黏進下一條選擇器，註解裡的逗號會把選擇器切斷——實測讓 18 條規則漏掉了作用域
3. 角色報告的縮圖走內嵌 `background-image:url(…)`，只查 `src` 屬性會漏掉。表現是大圖正常、縮圖 404，很難排查

### 2.10 單獨跑一個角色（不改編小說）

`character-refs` 不依賴小說：

```bash
node skills/character-refs/scripts/character-refs.mjs config --model qwen --confirm-anchor yes
node skills/character-refs/scripts/character-refs.mjs intake-check <角色>-intake.json
node skills/character-refs/scripts/character-refs.mjs gen <asset.json> --tier 1   # 先只出錨點
node skills/character-refs/scripts/character-refs.mjs gen <asset.json>           # 補齊第二檔
node skills/character-refs/scripts/character-refs.mjs render <asset.json> --html > report.html
```

**核心規則：一組圖只有一個根——正面全身錨點。** 只有它是文生圖，其餘全是「錨點 + 一句改圖指令」。頭髮、臉、領口三類細節額外掛確認過的正臉大頭照。圖與圖之間不再互相參照——所以任何一張出壞了，單獨重出這一張就行，**不會連鎖**。

分檔出圖：

| 檔位 | 內容 | 什麼時候出 |
|---|---|---|
| 1 | 正面全身（錨點） | 總是，第一張 |
| 2（預設） | 正臉大頭照、90° 側面、背面 | 預設出齊 |
| 3 | 細節圖（最多 8 張） | 有配飾或服裝局部特寫 |
| 4（預設不出） | 45° 大頭照 | 使用者明確要 |

為什麼預設出到第二檔？H3 實測：**只給正面全身，服裝和背影都對，但臉會走樣；加一張大頭照，臉最接近。**

**模型不鎖定**：主圖與派生圖可以用不同模型，一致性來自「同一張錨點」而不是「同一個模型」（實測 Qwen 錨點 + GPT 派生、GPT 錨點 + Qwen 派生、同組混用都銜接得上）。

**凍結的只有三樣**：錨點檔案（sha256）、畫風快照、文字描述指紋。任何一樣變了，依賴它的圖自動標為「過期」——只標記，不刪除，舊版本全部留著。

## 三、設計哲學：這套專案真正想說的是什麼

下面八條，是我認為這個倉庫最值錢的部分。

### 哲學一：檢查清單交給模型自覺是靠不住的

這是整個專案的第一性原理，出處就在 `novel-outline` 的 README 裡，一句話：

> **checklist 交給模型自覺是靠不住的。**

所以每一道門都是 `validate` 裡的確定性檢查，不是給模型讀的文字。14 道、10 道、10 道、8 道、18 道，共 60 道。

配套要求更狠：**自測裡每一道門都有擊穿用例**——故意構造一個違規資料，確認校驗器真的會報出來。證明它真的會攔，不是永遠為真的假測試。

這一條的分量怎麼估都不為過。絕大多數「AI 工作流程」專案停留在「我給模型寫了 20 條要求，它大概會遵守」。這裡的要求是：**你連一條要求都不要寫給模型聽，寫給程式碼。** 模型的輸出是機率性的，只有程式碼是確定性的。

### 哲學二：出圖那一刻才能決定的事，全部移出 skill

這是 2.0 版本的破壞性變更核心，也是整個專案最容易被忽略但最激進的一次取捨。

1.x 版本裡，角色、美術、分鏡三個 skill 自己出圖，自己選模型、自己定畫風、自己管畫幅。2.0 把這些全刪了。理由寫在 changelog 裡：

> **出圖那一刻才能決定的事（用哪個模型、哪種畫風、哪個畫幅），全部移出 skill，skill 只交提示詞和結構化資料。**

配套的硬限制是：**skill 不出圖。** `novel-art` 的 README 裡明確寫「不要說『已出圖』——這一步不存在了，交付的是提示詞」。

為什麼這麼做？因為選模型、選畫風、選畫幅是**專案級決策**，不是階段級決策。同一部劇的角色圖和場景圖應該用同一個模型、同一套畫風、同一個畫幅。如果這些參數散落在三個 skill 裡，你要麼在三處重複設定（不一致的風險），要麼得加一層共享設定（破壞自包含性）。移出去，兩難消失。

唯一的例外是 `character-refs`——它就是「那一刻」本身，所以它保留出圖能力。**規則要留例外，例外要能說清為什麼。**

### 哲學三：每個 skill 自包含，可以單獨拷走

```
skills/<skill-name>/
├── SKILL.md          給 agent 讀的工作流（必需）
├── README.md         給人讀的說明
├── scripts/
│   ├── <name>.mjs    確定性工具，零依賴
│   └── selftest.mjs  自測，不調模型（必需）
├── references/       按需加載的詳細指令
├── examples/         自帶樣例，同時當測試夾具
└── assets/           截圖
```

兩條硬要求：必須有 `SKILL.md`，必須有 `scripts/selftest.mjs` 且**不調模型、不花額度**。

配套的 AGENTS.md 行為規則更狠：

> **skill 必須自包含、可單獨拷走：不依賴任何第三方 skill（包括官方 skill）。外部方法論學習後內化成本倉庫自己的 references 文件，註明學習來源。**

所以 H3 官方方法論被內化成了 `references/h3-prompt.md`，而不是掛一個外部相依。

**這個限制的代價是真實的**：程式碼有重複（組裝器要自己解決 57 個類名串味，而不是各 skill 統一 CSS 變數）。作者選擇付這個代價——因為一個能被單獨拎出來用的 skill，價值遠高於消除重複帶來的那點整潔。

### 哲學四：模型寫四件，腳本算一件

大綱五件套裡，前四件（改編說明、人物表、爽點表、分集梗概）是模型寫的，第五件（資產清單）**永遠是腳本彙總的**。

理由一句話：「模型手寫必漏。」

同樣的原則散落在各處：報告裡的角色位統計、大爆點列表、場景概覽卡的承載爽點，全部是算出來的，模型一個字不寫。

**判斷標準很清晰：能機械計算的，絕不交給模型。** 凡是「模型要數一數、算一算、對一對」的活，都應該是程式碼。

### 哲學五：先拍板再細化，錯了只損失一輪

前面講過，不再展開。但值得強調它的形態：**這不是流程建議，是流程門。** 寫分集前必須過 `validate --stage beats`，過不了就不許往下走。

AI 管線的失敗有個特殊之處：早期的小錯誤會**級聯放大**並浪費大量算力。骨架錯了，60 集分集全部作廢；角色定錯了，美術和劇本全部重做。**在最便宜的地方攔截，是 AI 管線唯一 sane 的設計。**

### 哲學六：一致性靠「錨點」，不靠「同一個模型」

角色參考圖那套「一個根、其餘派生」的思路，其實貫穿整個專案：

- 場景一致性 → 每景 3–5 個錨點
- 道具一致性 → 狀態變體（合上/打開各一張）
- 角色一致性 → 正面全身錨點，派生圖只參照它
- 光照一致性 → 從分集反推的具體狀態，每個狀態落成完整提示詞
- 跨集一致性 → 變體機制 `variantOf`，複用母場景資產

統一的思想是：**把「一致性」這件模糊的事，壓縮成一個可以傳遞、可以校驗、可以版本化的具體檔案。**

### 哲學七：逐字對帳，不靠人眼

`validate` 的很多門本質是「逐字比對」：

- H3 提示詞的對齊指令必須由分鏡結構推導出來，一個字元都不能差
- 認領的台詞必須逐字出現在 `<d>` 塊裡，改一個標點都過不去
- 切點時刻必須等於前面分鏡秒數的累計
- 提示詞語言必須與 `promptLang` 雙向對帳

**「逐字」這個詞是關鍵詞。** AI 生成的東西最容易出的不是「完全錯」，而是「對，但不完全對」——差一個字、差半秒。這類偏差肉眼極難發現，但在流水線上會累積成廢片。逐字對帳把這類偏差變成紅燈。

### 哲學八：門失敗會累積，stats 告訴你模型最常違反哪條

`novel-storyboard` 每次 `validate` 都把門的結果追加到目前目錄的 `.gates.jsonl`：

```bash
node scripts/novel-storyboard.mjs stats
```

累積幾十次之後，統計告訴你**模型最常在哪條規則上翻車**，你就能去改那條規則。

這是一條自進化的設計。而且作者的處理方式非常克制：

> **門失敗累積目前只在 novel-storyboard 上。這是有意的：先在真實專案裡用一段時間，確認 stats 出來的東西真的指向了該改的規則，再決定要不要推廣到其餘五個。如果長期沒人打開它，說明這個功能不該做，推廣只會把錯誤複製五份。不要主動再提推廣。**

**「如果長期沒人打開它，說明這個功能不該做」**——這句話的分量比它看起來大。它承認自己可能做錯，並且提前規定了「錯了就刪掉」的判據。這是一種非常健康的工程態度：功能的價值由使用證明，不由設計者的熱情證明。

同一種克制還體現在「鏡頭配方」的處理上。配方卡庫是可選掛載的，卡片裡的**建議景別與運鏡刻意不設門**，只在報告裡加個 `≠` 標記。作者的理由：

> **配方是語彙不是法條，可選掛載的東西一旦變嚴就沒人掛了，誤攔的門比沒有門更糟。**

**「誤攔的門比沒有門更糟」**——這句值得單獨裱起來。品質門一旦誤報，使用者的反應不是「這個門有 bug」，而是「這個工具愛挑刺，我不用了」。門禁系統一旦失去信任就等於不存在。

## 四、歸納總結：八條觀點

結合這個專案，我自己的判斷如下。

**觀點一：AI 短劇的真實門檻，已經從「能不能生成」轉到「能不能驗收」。**

模型生成一段 5 秒影片已經不難了。不難的是：跑 600 集時，怎麼知道第 387 集的第 2 段沒有崩。這套專案把 60 個具體判據寫成了程式碼，等於把「驗收」從人工目視變成機器可執行。**誰先建成這套驗收體系，誰的產能才敢往上翻。**

**觀點二：把檢查清單寫成程式碼，比寫一百條提示詞更值錢。**

這是本專案最可移植的一條。任何 AI 工作流程都適用：提示詞是軟限制，程式碼是硬限制。區別不在措辭強度，在**能不能被違反**。

**觀點三：判斷一個 AI 管線專不專業，看它把「決策權」交給誰。**

這個倉庫的態度很清楚：結構、計數、校驗、拼接、匯出——全給程式碼。模型只做它真正擅長的兩件事：寫內容、審美判斷。**分工越清楚，管線越可靠。**

**觀點四：一致性是資產，不是氛圍。**

「氛圍感」是形容詞，「3–5 個錨點 + 狀態變體 + 尺度參照 + sha256 凍結」是資產。前者每次生成都可能漂，後者能跨集複用、能 QC、能版本化。**AI 內容生產最終拼的是資產管理能力，不是靈感。**

**觀點五：「可單獨拷走」是好架構的試金石。**

一個元件能不能單獨拷走而不散架，暴露了它對脈絡的隱性依賴。這個倉庫把自包含寫成了硬要求，代價是程式碼重複，收益是**每一個 skill 都能當成獨立產品賣**。這是典型的「用可控的重複換結構自由」。

**觀點六：把「必須拍板」設成門，而不是建議。**

AI 管線的返工成本極高。方向錯了，後面白做。所以「先拍板再細化」必須寫成程式碼門，不是流程圖上一句話。**任何有 AI 參與的流程，越早的決策點越要硬。**

**觀點七：作者判斷「這功能不該做」的勇氣，比他做成的功能更值得學。**

「如果長期沒人打開它，說明這個功能不該做」「不要主動再提推廣」——這兩句話在開源專案裡是稀罕的。多數專案只會加功能，很少會預先寫好自己的撤銷條件。

**觀點八：這個專案的真實產品是那 1600 多項自測斷言，不是那 7 個 skill。**

1600 多項斷言不調模型、不花額度、一秒跑完、每一道門都有擊穿用例。這套東西才是「品質門體系」真正的資產——它讓任何一個團隊都能在自己的內容類型上複用這套方法論。**skill 可以抄，方法論抄不走，因為它長在測試裡。**

## 五、對做短劇生意的人，這套東西意味著什麼

如果你是拿 AI 做短劇生意的老闆，這幾點更實際：

**第一，這套東西直接壓的是「不可控的返工率」。** AI 短劇最貴的不是生成，是「跑完 200 集才發現角色崩了、場景穿幫了、鉤子沒兌現」。60 道門把這類返工從「事後抽查」變成「事前攔截」。

**第二，零相依零 API key 意味著試錯成本幾乎為零。** 一整條管線跑起來只需要 Node 18+ 和你自己的工作階段額度。跑一遍全本大綱的成本，可能比請人喝一頓咖啡還低。**這種成本結構適合「先大量試、再集中投產」的策略。**

**第三，「劇本管戲、分鏡管拍」這條邊界值得單獨記住。** 很多人做 AI 影片時把寫戲和切鏡攪在一起，結果改一句台詞要重排幾十個鏡頭，時間全耗在返工上。分開的代價是多一次交接，收益是**兩個環節可以並行迭代**。

**第四，2–5 秒的切鏡硬門，是可以直接抄的行業預設值。** 短劇觀眾的注意力節奏、生成成本、影片模型的時長上限，三條限制在這裡交匯成一個數字。你自己拍短劇，這個數也該是 2–5 秒。

**第五，「誤攔的門比沒有門更糟」是所有 AI 工具產品的教訓。** 如果你要把類似體系賣給自己的團隊，**第一件事不是加門，是保證已有的門零誤報**。一個誤報一次的工具，團隊就再也不用了。

## 六、最後

`shuohao-skills` 不是一個「AI 短劇生成器」，它甚至不生成影片。

它做的是更基礎也更難的事：**定義 AI 短劇生產過程中每一個「什麼叫做對了」，並把這些定義變成機器可以執行的判斷。**

6800 星買的是這個認知密度。7 個 skill 是骨架，60 道品質門是肌肉，1600 多項斷言是回歸測試。**真正的稀缺品不是會寫提示詞的模型，是知道「什麼叫對」並且能把它編碼出來的人。**

如果你在找 AI 短劇的工具，先別急著看它能不能出片，先看它**敢不敢把驗收標準寫成程式碼**。這是分水嶺。
