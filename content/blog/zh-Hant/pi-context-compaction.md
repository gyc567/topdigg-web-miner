## 引言

在人工智慧輔助編碼領域，上下文窗口限制一直是困擾開發者的核心挑戰之一。當使用LLM進行長時間編碼會話時，對話歷史不斷增長，最終超出模型的處理能力，導致請求被拒絕或上下文被截斷。Pi編碼助手透過引入**Compaction（壓縮）機制**，優雅地解決了這一難題。

本文將深入解析Pi編碼助手中的上下文壓縮機制，探討其設計哲學、核心演算法以及最佳實踐。

## 問題背景

### LLM的上下文窗口限制

現代大語言模型（LLM）具有有限的上下文窗口。以Claude系列模型為例，其上下文窗口從32K到200K不等。這意味著：

- 模型一次能處理的Token數量是固定的
- 隨著編碼會話進行，對話歷史不斷累積
- 當歷史超過上下文限制時，LLM會拒絕請求或遺失早期上下文

### 長會話的挑戰

在實際的軟體開發過程中，編碼會話往往需要持續數小時甚至數天。開發者會：

- 多次修改同一個檔案
- 討論架構設計和實現細節
- 回顧之前的技術決策
- 處理複雜的除錯場景

這些需求與有限的上下文窗口形成了尖銳的矛盾。

## 核心設計哲學

Pi編碼助手的上下文壓縮機制基於一個核心理念：**保留關鍵資訊，壓縮冗餘內容**。

### 分層記憶策略

Pi採用分层記憶策略來處理上下文：

1. **最近對話**：完整保留最近的消息，保持上下文連貫性
2. **早期對話**：透過摘要壓縮，保留核心資訊的同時減少Token消耗
3. **工具結果**：始終完整保留，因為它們與工具調用緊密關聯

### 摘要而非截斷

與簡單的上下文截斷不同，Pi使用**結構化摘要**來壓縮歷史消息。這種方法：

- 保留了對話的語義完整性
- 允許跨會話恢復完整上下文
- 支援多種模型間的移植

## Compaction壓縮機制詳解

### 工作原理

Compaction壓縮機制透過以下步驟工作：

```
┌─────────────────────────────────────────────────────────────┐
│                    壓縮觸發條件                              │
│  contextTokens > contextWindow - reserveTokens              │
│  預設reserveTokens: 16,384                                  │
│  預設keepRecentTokens: 20,000                               │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  步驟1: 找到切分點                                          │
│  從最新消息向後步行，直到達到keepRecentTokens（預設20k）     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  步驟2: 提取消息                                            │
│  收集從前一個邊界到切分點的消息                              │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  步驟3: 生成摘要                                            │
│  調用LLM生成結構化格式的摘要                                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  步驟4: 追加條目                                            │
│  保存CompactionEntry，包含摘要和元資料                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  步驟5: 重建上下文                                          │
│  使用摘要 + 最近消息用於下次請求                             │
└─────────────────────────────────────────────────────────────┘
```

### 切分點規則

有效的切分點包括：

| 消息類型 | 可否切分 | 說明 |
|---------|---------|------|
| 使用者消息 | ✓ | 使用者輸入的自然語言 |
| 助理消息 | ✓ | LLM的回覆內容 |
| BashExecution消息 | ✓ | 命令執行結果 |
| 自定義消息 | ✓ | 擴展自定義消息 |
| 工具結果 | ✗ | 始終與工具調用一起保留 |

### 摘要格式

Pi生成的摘要包含以下結構化欄位：

```json
{
  "目標": "項目的核心目標或當前任務",
  "約束與偏好": "技術約束、代碼風格偏好等",
  "進度": {
    "已完成": ["已完成的里程碑1", "已完成的里程碑2"],
    "進行中": "當前正在進行的工作",
    "已阻塞": "遇到的阻塞問題"
  },
  "關鍵決策": "做出的重要技術決策及其理由",
  "下一步": "接下來的工作計劃",
  "關鍵上下文": "需要記住的重要資訊",
  "檔案追蹤": ["file1.py:變更內容", "file2.js:變更內容"]
}
```

### 觸發方式

Compaction壓縮有兩種觸發方式：

#### 1. 自動觸發

當滿足以下條件時自動觸發：

```
contextTokens > contextWindow - reserveTokens
```

其中：
- `contextWindow`: 模型的上下文窗口大小
- `reserveTokens`: 預留的Token緩衝（預設16,384）

#### 2. 手動觸發

使用者可以透過`/compact`命令手動觸發壓縮：

```
/compact
```

這在使用者知道即將進行大量新對話時非常有用。

## 兩種摘要機制對比

Pi編碼助手實現了兩種互補的摘要機制：

| 特性 | Compaction壓縮 | Branch摘要 |
|------|---------------|-----------|
| **觸發時機** | 上下文超過閾值或/compact命令 | 透過/tree導航觸發 |
| **目的** | 在切換分支時保留上下文 | 防止上下文溢出 |
| **應用場景** | 長會話的持續編碼 | 分支切換時的上下文保存 |

### Compaction壓縮

- **自動觸發**：當contextTokens接近contextWindow限制時
- **手動觸發**：使用者主動呼叫`/compact`
- **保留內容**：最近20K Token的完整歷史 + 更早歷史的摘要

### Branch摘要

- **觸發時機**：透過`/tree`命令導航到不同分支時
- **目的**：確保分支切換不遺失上下文
- **保留內容**：切換前分支的完整摘要

## 配置與調優

### 基本配置

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

### 參數說明

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `enabled` | true | 是否啟用壓縮機制 |
| `reserveTokens` | 16384 | 觸發壓縮前的Token緩衝 |
| `keepRecentTokens` | 20000 | 保留的最近Token數量（5-20個對話輪次） |

### 調優建議

1. **增加keepRecentTokens**：如果需要保留更多最近對話的完整上下文
2. **減少reserveTokens**：在上下文窗口較大的模型上可以減少預留
3. **監控Token使用**：透過日誌觀察壓縮觸發的頻率，調整參數

## 擴展機制

Pi的壓縮機制支援透過事件擴展，允許自定義摘要邏輯。

### 事件類型

#### session_before_compact

在自動壓縮或`/compact`之前觸發，允許：

- 自定義摘要內容
- 添加額外的上下文資訊
- 跳過預設壓縮流程

#### session_before_tree

在`/tree`導航之前觸發，允許：

- 為分支切換準備特殊摘要
- 保存分支特定的上下文資訊

### 自訂摘要範例

```python
# 在session_before_compact事件中自訂摘要
def on_session_before_compact(session_context):
    # 添加自訂的上下文資訊
    session_context.add_metadata("build_status", "passing")
    session_context.add_metadata("test_coverage", "85%")
    return session_context
```

## 使用範例和最佳實踐

### 範例1：長會話開發

```bash
# 開始一個新的編碼會話
$ pi "幫我實現使用者認證模組"

# 進行多輪對話
$ pi "添加密碼重設功能"
$ pi "實現雙因素認證"
$ pi "添加OAuth2登入"

# 當上下文接近限制時，Pi自動壓縮
# [Pi] 上下文壓縮已自動觸發，產生了會話摘要

# 繼續編碼，上下文仍然完整
$ pi "現在添加session管理"
```

### 範例2：手動觸發壓縮

```bash
# 在知道即將進行大量新對話前手動觸發
$ pi "接下來我要重構整個資料訪問層"
$ /compact

# [Pi] 上下文已壓縮，保留了關鍵資訊
# 開始新的重構工作
$ pi "將所有SQL查詢改為使用ORM"
```

### 範例3：分支摘要

```bash
# 在不同分支間切換時保留上下文
$ pi "在feature/payment分支上工作"
$ /tree feature/payment

# [Pi] 已為當前分支產生摘要

# 切換到另一個分支
$ /tree feature/refactor

# [Pi] 已載入feature/payment分支的摘要，可以繼續工作
```

### 最佳實踐

1. **定期手動壓縮**：在進行大規模重構前手動觸發`/compact`
2. **注意切分點**：了解哪些內容會被保留，哪些會被壓縮
3. **監控Token使用**：關注日誌中的Token使用情況
4. **利用擴展事件**：在session_before_compact中添加專案特定的上下文
5. **摘要可讀性**：保持摘要格式清晰，促進跨會話理解

## 關鍵觀點總結

### 核心價值

1. **突破上下文限制**：透過智慧壓縮實現無限制的編碼會話
2. **保持上下文連貫性**：摘要保留關鍵資訊，支援會話延續
3. **跨模型移植**：純文字摘要格式確保在不同模型間通用

### 技術亮點

1. **分层記憶策略**：最近對話完整保留，早期對話結構化摘要
2. **智慧切分點**：基於消息類型的智慧切分，確保語義完整
3. **自動與手動結合**：適應不同使用場景的需求
4. **事件擴展機制**：支援高度自定義的摘要邏輯

### 適用場景

- 長時間的開發會話
- 需要回顧歷史決策的複雜專案
- 多分支並行開發的場景
- 需要在不同會話間保持上下文連貫性的專案

## 結論

Pi編碼助手的上下文壓縮機制是解決LLM上下文窗口限制的優雅方案。透過保留最近對話的完整性、對早期對話進行結構化摘要，Pi實現了既不遺失關鍵資訊、又不超出上下文限制的目標。

這一機制不僅提升了編碼效率，還為AI輔助編程的發展提供了新的思路。隨著LLM上下文窗口的不斷擴大，壓縮機制將繼續進化，為開發者提供更加流暢的編碼體驗。
