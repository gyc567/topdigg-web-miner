# DeepSeek-Bot 深度解析：讓 DeepSeek Harness 變成一支部有長期記憶的 AI 團隊

## 引子：一個被問爛了的問題

我們用 AI 程式設計工具的時候，幾乎都遇到過同一個情境：

你叫它寫一個功能，它寫了一半，你說「等等，這裡不對」，它改；改完你說「還有問題」，它再改。改到第七輪的時候，你發現它已經忘了你第一次的要求，整個思路開始飄走。

於是我們發明了一堆修補方案：把系統提示詞寫得更長、每輪手動貼上下文、隔一會兒開一個新的工作階段、讓模型自己做摘要……每個修補方案都在補另一個修補方案的補。

DeepSeek-Bot 這個專案，本質上在做同一件事，但它的解法不是「幫一個 Agent 打補丁」，而是**換一個抽象層級**：不再把 AI 當成一個持續對話的工作階段，而是把它當成一個**有身分、有記憶、有同事的團隊成員**。

這就是這個專案最值得研究的地方。

---

## 一、專案說明：它到底是什麼

**DeepSeek-Bot（簡稱 DS Bot）** 是建構在 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）之上的外掛與桌面應用程式。它的官方定義一句話講清楚：

> 一支長期駐留的 Bot 團隊。

### 1.1 兩種形態

| 形態 | 說明 |
|---|---|
| `ds-bot` 外掛 | 標準 DSH 外掛，跑在 DSH Desktop 和 DSH Web 裡。全部 Bot 能力都在這裡 |
| DS Bot 桌面應用程式 | 打開就是 DS Bot。自帶鎖定版本的 DSH、獨立的 profile 與資料目錄，會匯入你在 DSH 裡既有的團隊，並安裝 DSH 相容外掛，形成自己的外掛生態系 |

兩種形態跑的是**同一份** `ds-bot` 外掛程式碼。桌面應用程式的意義在於：DS Bot 自己掌握 profile、介面和 DSH 版本，不再受 DSH 通用介面與全域設定的束縛。

### 1.2 十個核心需求（官方願景）

專案在 `docs/vision.md` 裡列了十條核心需求，這基本上就是它的設計憲法：

1. **建構在 DSH 之上，彼此獨立。** 每個 Bot 都以 DSH 為基礎，Bot 之間互不干擾。
2. **可靠。** Bot 要與目標保持一致、依據證據行動、不越界、結果可檢查。
3. **記憶與持久化。** Bot 具備長期記憶。可以讀其他 Bot 的記憶但不能改（只有 Main Bot 能改），群組聊天共用一份記憶。
4. **分級權限。** Main Bot 權限最高（建立、修改其他 Bot），其他 Bot 沒有這些權限。只有使用者能刪除 Bot。
5. **群組聊天。** 群組聊天是 Bot 協作的主要形式，可以有管理員 Bot，預設由管理員回覆使用者訊息。
6. **工作資料夾。** 每個 Bot 有自己的工作目錄，群組聊天可以為所有成員設定一個。
7. **瀏覽器。** 每個 Bot 有自己的瀏覽器，互不影響。
8. **介面與動效。** 打磨過的介面，平滑的動效。
9. **獨立應用程式。** DS Bot 要做成獨立應用程式，不對 DSH 做太多讓步。
10. **本機 Agent。** 可以把本機 agent CLI 接進來當 Bot（規劃中）。

### 1.3 專案規模

| 指標 | 數值 |
|---|---|
| 授權條款 | Apache 2.0 |
| 目前版本 | v0.2.0（2026-10-21 釋出） |
| 相依的 DSH | 0.2.1-rc.2 |
| host 端程式碼 | 106 個檔案，約 12,500 行 |
| client 端程式碼 | 約 14,400 行 |
| 單元測試 | 93 個測試檔案 |
| 設計文件 | 11 篇中文設計稿（`docs/plans/`） |
| 已知問題 | 3 個（`docs/known-issues.md`） |

**注意這個比例：設計文件 900 多行，程式碼 2.7 萬行。** 這個比例本身就是一種訊號——這個專案的複雜度不在寫程式碼，在想清楚「Bot 之間到底該怎麼協作」。

## 二、設計哲學：六個我認為真正厲害的思想

下面這部分是本文的核心。專案文件裡的很多設計，我讀完是拍案叫絕的。

### 思想一：上下文管家——不是「壓縮」也不是「切斷」，而是「判斷」

**問題**：Bot 是長期的。使用者跟一個 Bot 聊幾週、幾個月，上下文一定會滿。兩種常見做法都不對：

- **一遍遍壓縮同一個對話**：摘要的摘要越來越虛，細節掉了找不回來。
- **到線就硬切新階段**：做到一半的活被切斷，Bot 像失憶。

**DS Bot 的做法**：一個 Bot 是**一個長期不變的身分**，它的對話由多段 DSH Session 組成。快滿的時候，喚起一個輕量的「上下文管家」（context steward），讓它讀最近的訊息，判斷一件事：

> 活是告一段落了，還是仍在進行中？

- **仍在進行** → 原地壓縮成一個「檢查點」（checkpoint）：一份交接摘要加上使用者近期訊息的原文。活接著干，不中斷。
- **告一段落** → Bot 自己寫一份交接筆記，切換到新的一段繼續。

**這個設計精妙在哪裡？**

管家不是靠 token 數判斷，而是靠**語意判斷**。它被明確要求「逐條核對使用者要的和 Bot 實際做的，有沒有 Bot 問了但使用者還沒答的問題」。哪怕 Bot 自己說「我做完了」，只要有一個子項沒做完，就判定為「仍在進行」。

還有一條特別反直覺但特別正確的規則：

> **壓縮過的次數越多，越應該把合理的停頓當作告一段落。** 因為摘要的摘要損失更大。

這是對「壓縮耗損」的量化理解，比「每次壓縮損失一點」這種直覺式判斷高明得多。

**對使用者的體感**：完全無感。沒有「上下文已用 80%」的提示，也沒有「切換工作階段」的工具。你看到的始終是一條連續的對話。

**工程細節**（這些細節決定了這不是簡報專案）：

| 項目 | 值 |
|---|---|
| 視窗 W | 模型宣告的 `contextWindow`，沒宣告則依 500,000 |
| 可用 U | W 減去回覆預留（`maxTokens`），不少於 W/2 |
| 硬線 H | 0.95 × U |
| 檢查線 C | `checkRatio` × U（預設 0.8），不超過 H |
| 管家看的訊息 | 最近約 6,000 tokens，單則最長 1,500 字元 |
| 管家輸出 | 一行 JSON：`{"action":"switch"|"compact","reason":"…"}` |

**程式碼裡沒有寫死任何 token 數**，全部跟著模型走。這是「不為某個模型寫死數字」的極致堅持。

**一項安全細節**：管家失敗或答不出來，就直接換段。不猜。

### 思想二：派活樹——把「訊息鏈」變成「工作樹」

這是我認為整個專案**最有價值的單點設計**。

**問題**：Bot 之間派活，早期是用數量擋的。結果是什麼？

- **Bot 看不到對方在做什麼。** `list_bots` 只給名字、角色、模型、資料夾。連發 5 則訊息，5 則「已送達」，0 則回覆。
- **對方沒讀就拒絕接收。** 對方積壓 10 則未讀時直接拒收，但寄件人不知道原因。
- **按數量擋分不出正常和空轉。** 訊息鏈 6 跳截斷，使用者上次發言後全團隊最多 40 則，Bot 在一個群組裡最多發起 3 輪。結果是：每一步都換人、都有結果的長派活鏈在第 7 手被截斷；而 A→B→A 的繞圈要轉滿 6 手才停。

**DS Bot 的解法：把「活」建模成一棵樹。**

> 下面交回的活還沒回來，上面的回覆就先不交；下面全部交回，上面接著做，做完連同下面的結果一起交上去。

**結果自己會往上走。** Bot 不需要替上游補訊息，因此**不需要靠跳數、條數來防繞圈**。於是：

> **訊息鏈 6 跳、對方 10 則未讀、Bot 在一個群組裡最多發起 3 輪、使用者上次發言後全團隊 40 則——全部拿掉，不留後備機制。**

這是我認為整份設計文件裡最激進也最正確的一次決定。**上限從來不是解決方案，是掩蓋問題的OK繃。** 一旦結構對了，許多限制就不需要存在了。

配合這個設計，還做了兩件事：

**1. 狀態是一等公民。** 每個 Bot 的狀態是五種之一：等待使用者核准 / 換新工作階段中 / 在做事 / 在等別的 Bot / 閒置。`list_bots` 一次給全，還帶未讀訊息數和問題卡片狀態。

**2. 只擋一種訊息。** 唯一被拒絕的是「傳給正在等這件活結果的 Bot」——因為結果會自動交回去，傳過去既是繞圈也是多餘。其他全部允許，同一個 Bot 在一件活裡出現幾次都行（設計、審查、退工、驗收的接力鏈）。

**未讀訊息合併成一則**：X 傳給 Y 的訊息 Y 還沒讀時 X 又傳一則（同一件活），就合併成一則。這樣**收件匣裡每個寄件人最多一則未讀訊息**，堆積的根本原因被消除了，於是上限也就不需要了。

### 思想三：三級權限——角色權限與沙盒權限徹底分離

這是很多多 Agent 專案做糊的地方，DS Bot 分得很乾淨。

**兩層互相獨立的權限**：

- **角色權限**：誰能管理 Bot、群組和團隊記憶。**由 DS Bot 自己檢查。**
- **沙盒權限**：一個 Bot 的工具能碰到什麼（讀檔案、改檔案、跑命令）。**用 DSH 提供的權限預設，由 DSH 執行。**

| 誰 | 範圍 | 能做什麼 |
|---|---|---|
| 使用者 | 全部 | 一切操作，包括設定/取消 Main Bot，設定沙盒權限 |
| Main Bot | 整個團隊 | 建 Bot、改任何 Bot、停止別的 Bot 的回合；建群改群刪群；寫團隊記憶；讀寫別的 Bot 的記憶；掛上摘要能力 |
| 群組管理員 | 自己管理的群組 | 改自己的群組；在群組裡發言；寫團隊記憶。不能刪群，不能改群的工作資料夾 |
| 一般 Bot | 自己 | 改自己的名稱、角色、顏色、模型、工作資料夾、指令；替自己掛上摘要能力；群組裡發言、`@` 點名；私訊裡用 `message_bot` 傳訊息給任何 Bot |

**三條極關鍵的設計細節**：

1. **只有使用者能設定沙盒權限。** Bot 發起的修改一律拒絕，`update_bot` 和 `update_group` 都沒有這個參數。Bot 不能替自己提權。
2. **越權時告訴 Bot 該怎麼辦**，而不是單純報錯。工具回傳「只有 Main Bot 能建立 Bot，請讓 Main Bot 來做」——讓 Bot 能自己改道，而不是卡住。
3. **「完全權限」在介面上這幾個字一直是紅色**，還要再確認一次。

### 思想四：三層記憶——上下文管「這次在做什麼」，記憶管「跨對話該記住什麼」

這兩條線分得很清楚：

| | 上下文 | 記憶 |
|---|---|---|
| 管什麼 | 這次對話在做什麼 | 跨所有對話都該記住的事 |
| 誰維護 | 上下文管家（判斷壓縮/換段） | 模型整理（每段對話閒置後） |

**記憶的關鍵設計**：

**三層作用域**：
- 每個 Bot 有自己的記憶
- 每個群組聊天有群記憶，**只在這個群裡讀**
- 團隊記憶，所有 Bot 都讀

**「群裡說的話留在群裡」**：群記憶只進這個群成員的群組對話，不進他們的私訊，也不進別的群和群外的 Bot。成員被移出群後立刻讀不到、也寫不了。

**記憶不能只靠 Bot 想起來才呼叫。** 每段對話閒置後有一次自動的「記憶整理」，由模型讀這段對話新增的內容，像人談完話之後那樣保留、修改或刪除項目。私訊由 Bot 自己的模型整理寫進它自己的記憶；群組聊天**按群整理一次**（不是每個成員各整理一次），用管理員的模型，只寫進群記憶。

**格式極簡**：沿用 Agent MemoryRepo 的 Markdown 格式，一行一則，行尾帶 `[source: …; added: …]`。

**固定大小上限**（字元）：一則 300，`MEMORY.md` 4,000，一個主題 16,000，一個作用域 40 個主題。超限直接失敗並告訴你怎麼騰空間。

**安全**：記憶是資料，不是指令。看起來像金鑰的項目會被拒絕；Bot 被明確告知不要儲存網頁、檔案或工具結果裡「要求它記住」的東西。

**快取相容性**（這個細節很專業）：每個 Session 第一次算繪時把記憶段落凍結下來，之後提示詞保持**逐位元組不變**，供應商的前綴快取才能命中。換段或做檢查點（檢查點本來就會打破快取）才重新凍結。代價是「一段對話開始之後才儲存的項目不會出現在這段的提示詞裡」——所以提示詞明確要求 Bot：**在回答「不知道」之前先呼叫 `recall`**。

**不用 git 管記憶**：檔案原地修改，`journal.jsonl` 記下每次改動替換了什麼。

### 思想五：安全模型——網頁不可信，金鑰不能外洩

> **瀏覽器由使用者操作，Bot 只能讀。金鑰的值只有使用者輸入、只存在本機。Bot 只拿到環境變數名稱；值在離開本機之前一律換成佔位符。**

具體到實作：

**Bot 瀏覽器（僅 DSH Desktop）**：
- 每個 Bot 一個儲存分區（`bot:<id>`），登入狀態互不相通
- `read_browser` 讀的是 **DOM 不是螢幕截圖**，轉成 Markdown，連結和控制項標成 `[#n]`
- **只讀可見內容**：`display:none`、`visibility:hidden`、零高度、收合的 `<details>` 內容全部跳過
- **絕不讀取**密碼、信用卡（`autocomplete="cc-*"`）、一次性驗證碼欄位
- 硬上限：40 萬字元、15 萬節點、每張表 5 千列、3 千連結、1.5 秒
- **不能點擊、不能輸入、不能捲動、不能開啟網址**
- 頁面內容一律**當作資料，永不當作指令**
- 雲端主機中繼資料位址（`169.254.x.x`）禁止存取——它會發放帳號憑證

**金鑰**：
- Bot 呼叫 `request_secret`，使用者在自己的聊天卡片裡輸入，**Bot 永遠看不到值**
- 值存 `secrets.json`，權限 600，原子寫入，不進 `state.json`、不進日誌
- 透過 `$DSH_SECRET_<NAME>` 環境變數注入
- 工具結果儲存前、每次請求送給模型前，值全換成 `[secret:<NAME>]`
- 8 字元以下的短值（PIN）只在「獨立出現」時取代，避免誤傷一般文字
- 明確的誠實警告：**只有完全相同的副本會被遮蔽，一個把值編碼、拆解或反轉的 Bot 仍然能印出來。不要把重要金鑰交給你不信任的 Bot。**

**網路搜尋**：
- 絕不借用另一條路徑的金鑰（每把金鑰都在自己的帳戶上計費）
- 原生搜尋不可用時，退回不需要金鑰的方式（抓取 Bing / DuckDuckGo 公開結果頁並解析）
- 每筆結果開頭有 `Search backend: …` 說明走的是哪條路徑
- 全部失敗時告訴模型**不要猜網址**

### 思想六：檢視卡片——把「模型寫 HTML」否決掉

這是一個被外部評審否決兩次後定下來的方案，值得單獨說，因為它代表了一種**安全設計的現代思維**。

**第一版方案**：模型寫 HTML，用 iframe 算繪。**被否決**。理由：

- 任意 HTML 沒有壓縮序列化策略：上下文管家和交接包要嘛塞爆要嘛全部遺失
- iframe 在聊天的虛擬捲動中卸載就會遺失內部狀態
- **模型產生的指令碼可以自動送出，造成回合劫持死循環**
- 為 widget 內容開 GET 路徑、設 CSP 需要依賴 DSH 未文件化的能力，風險由外掛承擔

**第二版方案（現行）**：**不執行模型產生的程式碼。**

> 模型只從一份固定元件目錄裡挑元件、填資料，算繪用 DS Bot 自己的元件。**安全性來自「沒有程式碼執行」，不靠沙盒。**

第一版元件目錄 8 個：`stack`（縱向容器）、`text`（Markdown 文字）、`metric`（數值指標）、`table`（唯讀表格）、`options`（選項）、`confirm`（確認）、`form`（短表單）、`progress`（進度快照）。

硬上限：序列化後 8 KiB、元件樹深 8 層、節點 64 個、表格 50 列 8 欄、form 6 欄位、options 8 個選項。

**一次送出結算整張卡**，其他元件未送出的輸入丟棄。**檢視不進群組聊天**（和 `ask_user` 同一句提醒）。

> **安全設計的本質變化**：從「把不可信程式碼關進籠子」，變成「根本不提供籠子」。

## 三、其他值得一提的細節

### 3.1 群組聊天：一次只有一個人發言

早期讓成員平行書寫、送出前再檢查新訊息，**連報數都會亂**：模型會沿用亂掉的數字硬送。把排序交給模型做不好。

結論：**群裡一次只有一個人發言**，每個成員開口前讀到的都是最新的群組狀態。

回應方式兩種：
- **管理員先答**（新群組預設）：沒有 `@` 的一般訊息只給管理員，管理員用 `@名字` 叫人。**這是成本考量**——每叫一個成員，就要帶上它整個對話的上下文跑一次模型，成本隨發言人數線性成長，係數很大。所以預設少叫人。
- **全員輪流**：每個成員依序回答，管理員第一個。

進度可見性做得很好：成員第一次呼叫工具後 15 秒仍在做事，本輪就繼續往下走，不再等它；但它做事中說的第一句話和帶 `@` 的話**立刻發到群裡**（間隔不到 30 秒的幾句合併成一則）。結果由派活的 Bot 接話。

### 3.2 長訊息：熱檔案只放有上限的資料

原本 Bot 之間的訊息整段存進 `state.json`，而 `state.json` 每次儲存都整份重寫。一則 500 萬字的 `message_bot` 讓它漲到 6.5 MB，之後**改個顏色也要重寫這麼多**。

現在：
- `state.json` 只存前 2,000 字元 + 總長度 + 全文在哪
- 超過 20,000 字的訊息**原樣存成 DSH 附件**（內容定址，相同內容只存一份）
- 訊息裡只留一句說明、開頭 1,000 字元和一個檔案區塊
- 群組紀錄的長行放到 `bot/group-lines/<群>/<seq>.txt`，行被擠出最近 60 行或群組被刪時檔案一起刪

### 3.3 DSH 讓步總帳：一份罕見的坦誠帳本

`docs/plans/2026-10-13-dsh-concessions.md` 記錄了 14 條「因為 DSH 本身的限制而做的妥協」。每條寫明：日期、相關 Issue/PR、**DSH 的限制**、**現在的做法**、**代價**、**桌面應用程式之後怎麼處理`。

舉幾條：

| # | DSH 的限制 | 現在的做法 | 代價 |
|---|---|---|---|
| C1 | PTC 預設下模型只能直接呼叫 `run_code`，一次程式執行最長約 10 分鐘 | 工具展示和伺服器端都會遍歷子呼叫 | 每個工具相關功能都要同時處理頂層和子呼叫 |
| C2 | 命令全域註冊，不能依工作階段過濾 | Bot 工作階段一律不支援 goal | `/goal` 仍出現在命令選單裡，但用不了 |
| C5 | patch 沒有條件語法；網頁搜尋選擇器在 id 沒註冊時不回退 | 只寫文件 | 關掉 `web-search-auto` 時必須同時改 `web.searchProvider`，否則**所有工作階段**的 `web_search` 都失效 |
| C7 | 其他外掛的 CSS 能覆寫 ds-bot；ds-bot 依賴 DSH 的私有類別名稱 | 幾處版面屬性加 `!important` | DSH 每次改結構或換皮都可能弄壞版面 |
| C11 | 模型串流卡死時沒有看門狗，回合不會結束 | 沒讀的請求合併成一則，狀態可見 | 卡死的 Bot 要使用者手動停止 |

**判斷一個 Issue 是 DS Bot 的 bug 還是 DSH 的限制時，先看這張表。** 這種文件在開源專案裡極其罕見，也是我認為這個專案品質最高的證明之一。

### 3.4 硬性規則：五條

專案根目錄的 `AGENTS.md` 給 AI 程式設計代理定了五條硬性規則，我摘錄一下（已翻譯）：

1. **建構在 DSH 之上；絕不打補丁。** 絕不修改 DeepSeek Harness，也不依賴 DSH 安裝目錄內部的檔案。**如果 DSH 中缺少某項能力，就停下來並說明；不要用打補丁的方式繞過去。**
2. **不帶金鑰。** 絕不寫入、列印或提交 API key、token、cookie 或 `DSH_HOME` 的內容。
3. **只用原創素材。** 不從其他產品或網站複製程式碼、文字、圖示、logo 或圖形。
4. **`client.js` 是建置產物。** 改 `src/client/`，然後 `npm run build`，絕不手動編輯。
5. **不要動使用者自己的 DSH 資料。** 匯入唯讀 `~/.dsh`，絕不寫入那裡。

第 1 條和第 3 條特別值得共鳴。**「如果 DSH 中缺少某項能力，就停下來並說明」**——這句話背後是克制。

### 3.5 專案自己的設計文件審查流程

`docs/plans/` 下的設計稿有非常明確的格式要求：**為什麼 / 已定的行為 / 不做什麼 / 已知限制 / 變更**。

「**不做什麼**」這一節是很多專案設計文件裡最缺的東西。例如：

- 群組聊天：**不做**平行發言後再檢查衝突；**不做**「一直輪到沒人說話為止」的多輪討論；**不讓**成員把長任務一直占著發言位
- 派活：**不把狀態寫進系統提示**（為了快取）；**不主動通知**派活的 Bot「對方卡住了」（每則通知都會讓派活的 Bot 再跑一次模型）；**不設**總量、鏈長或輪數的後備上限
- 記憶：**不告訴** Bot 或使用者上下文占用了多少；**不給** Bot 切換段的工具；**不用** git 管理記憶
- 檢視卡片：**不算繪**模型產生的 HTML/JS；**不引入** iframe；**不自建** MCP Apps host

而且設計稿要經過**多輪外部評審並簽核**。widget-views 那篇的變更紀錄寫著：

> 2026-10-20：初稿（宣告式目錄，第二版）。評審：Antigravity 否決第一版 iframe 方案；Codex 一審（ship with changes）……二審（ship with changes）……三審簽核（ship，無需再改）。

**讓不同的 AI 評審同一份設計稿，並記錄每一輪的修改意見。** 這在我見過的開源專案裡是頭一份。

## 四、歸納總結：我的六個判斷

### 判斷一：這是「Agent 產品化」而非「Agent 編排」的思路

市面上絕大多數多 Agent 框架（AutoGen、CrewAI、LangGraph 等）關心的是**怎麼把任務拆開、平行跑、彙整**。它們的隱含假設是：任務是一次性的、上下文是短的、結果是要交付的。

DS Bot 關心的是**怎麼讓一群長期存在的同事一起工作**。它的每個設計都指向這個目標：

- 長期駐留的身分（不是一個 task）
- 長期記憶（不是一次性上下文）
- 派活樹（不是任務 DAG）
- 群組聊天（不是平行 worker）
- 權限分級（不是人人均等）

**這是從「編排一個流程」到「經營一個團隊」的轉變。** 前者最佳化的是吞吐量，後者最佳化的是持續性。

### 判斷二：最重要的設計決策是「刪掉限制」，而不是「加更多規則」

我數了一下，DS Bot 在演進過程中**刪掉**的限制：

- 訊息鏈 6 跳截斷 → 刪
- 對方 10 則未讀上限 → 刪
- Bot 在一個群組裡最多發起 3 輪 → 刪
- 使用者上次發言後全團隊 40 則訊息 → 刪

同時它**新增**的約束只有一個：**不給正在等這件活結果的 Bot 傳訊息**。

**淨效果是約束大幅減少，可靠性反而提高。** 原因很簡單：刪掉的是「症狀級」限制（計數），保留的是「結構級」約束（等待關係）。

這就是好的系統設計的味道——**約束應該來自系統的結構，而不是來自計數器。**

### 判斷三：「上下文管家」是模型能力提升帶來的新設計空間

傳統的長上下文方案裡，「什麼時候壓縮」是一個**工程問題**，用 token 門檻解決。

但當模型足夠聰明時，它能**讀懂對話的語意結構**——「這件事做完了嗎」是一個語意問題，不是計數問題。

於是設計上出現了質變：DS Bot 不再問「上下文還剩多少」，而是問「**這件事告一段落了嗎**」。

這是我認為整個專案裡最有前瞻性的部分。**它把一個原本具決定性的工程問題，交給了一個非具決定性的模型判斷，並且為這個判斷設計了一整套後備機制（失敗就換段）。**

同樣的思路用在記憶整理上：不是讓 Bot 決定要不要記，而是**每段對話結束自動整理一次**。Agent 的行為不再依賴它「想起來」做某件事。

### 判斷四：安全上的思路是「拒絕能力」而不是「加強管控」

比較一下兩種思路：

| 思路 | 例子 |
|---|---|
| 加強管控 | 讓模型在沙盒裡跑得更安全；給 HTML 加更嚴格的 CSP；給 iframe 加更細緻的來源檢查 |
| **拒絕能力** | **根本不提供模型寫 HTML 的能力**；Bot **唯讀**不寫瀏覽器；**金鑰值永不進入模型上下文** |

後者更徹底，也更省心。**DS Bot 在這兩處都選了後者**，而且都給了明確的理由（「安全性來自沒有程式碼執行，不靠沙盒」）。

值得注意的是它並不假裝自己萬無一失。金鑰那一節的誠實警告——「一個把值編碼、拆解或反轉的 Bot 仍然能印出來」——這種把已知限制明白說出的寫法，比任何免責聲明都更值得信賴。

### 判斷五：可讀性本身就是架構品質的一部分

看它的幾個設計：

- **`state.json` 只存前 2,000 字元。** 因為它每次儲存都整份重寫。這個約束直接來自「熱檔案只放有上限的資料」。
- **長訊息存成附件。** 因為 DSH 有 `ctx.attachments`，內容定址、相同內容只存一份。
- **狀態不寫進系統提示。** 因為系統提示必須逐位元組穩定才能重複使用供應商的前綴快取。

這三條看起來是三個孤立的技术決策，但它們背後是同一條原則：**資料放在最合適的地方。** 大物件放檔案系統，熱點放記憶體，短小高頻放提示詞。

**DSH 讓步總帳、known-issues、「不做什麼」章節**，這些也都是同一件事：**把設計決策的理由寫在程式碼旁邊，讓後來的人不用重新推導。**

### 判斷六：這是「開源專案」和「產品」的混合體，值得警惕地樂觀

先說值得樂觀的：

- Apache 2.0，程式碼完整，93 個測試檔案，CI 在每個 PR 上跑測試
- 設計文件 11 篇，每篇都有「為什麼」和「不做什麼」
- 桌面應用程式、外掛、Docker 映像三種形態都在
- 進度很快：從 0.1.7 到 0.2.0 只隔了 5 天，但改動巨大

需要警惕的：

- **v0.2.0，還是預覽版。** 官方自己寫「Early release (v0.1). Features, tools and the saved data format can still change.」
- **桌面應用程式未簽章。** Windows SmartScreen 會警告，macOS 首次啟動需要管理員密碼手動放行。
- **已知問題裡有「外掛載入失敗」這種基礎問題**，排查步驟長得像一篇獨立文章（要看 `cordis.patch.yml`、跑 `--dump-config`、刪 profile 目錄）。
- **Docker 部署只有一個權限預設：完全權限。** 因為 DSH 自己的核心沙盒（bubblewrap / Landlock）在 Docker 預設 seccomp 下跑不起來。這在 NAS 情境下意味著**你必須手動控制掛載哪些目錄**。
- **群組聊天在 PTC 預設下舊工作階段，一輪最長約 10 分鐘**會被中止。
- **工作資料夾被刪或改名後，訊息會被吞掉**（DSH 0.2.1-alpha）。

**結論**：這是一個**架構成熟度遠超版本號**的專案。可以放心研究與試用，但要把它當早期產品對待，別當穩定基礎設施。

## 五、完整教學：從零部署一個 DS Bot 團隊

### 5.1 環境需求

| 項目 | 需求 |
|---|---|
| 桌面應用程式 | Windows x64 或 macOS（Apple 晶片 / Intel） |
| DSH Web | Node.js **22.19+**，pnpm |
| Docker | Docker 24+，Compose v2.24+，Linux x86-64 |
| 模型 | DeepSeek API key，或其他 Anthropic-Messages 相容端點 |

### 5.2 路線 A：桌面應用程式（最簡單）

**Windows (x64)**：
1. 前往 [Releases](https://github.com/Fei2411/DeepSeek-Bot/releases) 下載 `DeepSeek-Bot-<version>-win-x64.exe`
2. 執行安裝。**只安裝給目前使用者，不需要管理員權限**
3. 如果 Windows 跳出「Windows 已保護你的電腦」，點**更多資訊** → **仍要執行**

**macOS**：
1. Apple 晶片下載 `DeepSeek-Bot-<version>-mac-arm64.zip`，Intel 下載 `mac-x64.zip`
2. Safari 會自動解壓縮，把 **DeepSeek Bot** 拖進「應用程式」並打開
3. macOS 提示「無法檢查應用程式」時：**系統設定** → **隱私權與安全性** → **仍要打開**（需要管理員密碼）

**首次啟動**：
1. 問你兩件事：**資料放哪**（預設 `~/.ds-bot`）、**Bot 的檔案放哪**（預設 `~/DeepSeek Bot`）
   - 兩個位置不能一個在另一個裡面，也不能在使用者 DSH 的資料裡
2. 偵測到你 DSH 裡已有團隊時，問要不要匯入。**只問一次，匯入唯讀你的 DSH，一個位元組都不改**
3. 在設定裡設定一個模型
4. 打開就是一個叫 **Chief** 的 Main Bot。跟它說話，它會帶你走完設定

> **給第一次玩的人的建議**：別急著建十個 Bot。先只跟 Chief 聊，讓它理解你的工作方式，然後讓它建第一個專職 Bot。

### 5.3 路線 B：作為 DSH 外掛

先裝好 DSH，並在裡面設定好至少一個模型。**DS Bot 直接用 DSH 的模型。**

**DSH Desktop（Windows / macOS）**：
1. 側邊欄選 **Plugins** → **Add plugin**
2. **Package name or address** 填 `ds-bot`
3. **中國大陸使用者**：把 **Registry** 設為 **Mainland China mirror**
4. 點 **Install**，然後 **Enable now**
5. 如果提示下次啟動生效，**完全結束** DSH 再打開

**DSH Web（Windows / macOS / Linux）**：
```sh
npx @deepseek-ai/dsh@0.2.1-rc.2 plugin --profile web add ds-bot
npx @deepseek-ai/dsh@0.2.1-rc.2 web
```

**npm 不通時的備援**（第 2 步）：
- 填 Releases 裡下載的 `ds-bot-0.2.0.tgz` 完整路徑
- 或 `github:Fei2411/DeepSeek-Bot#v0.2.0&path:/ds-bot`（需要安裝 Git）

**從原始碼检出開發**（把外掛當成 linked dependency 加進 profile）：
```json
{
  "dependencies": { "ds-bot": "link:/path/to/ds-bot" },
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "ds-bot"] } }
}
```
然後在 profile 目錄跑 `pnpm install`，再從 deepseek-harness 儲存庫啟動：
```sh
pnpm -s dsh --profile web --no-open
```

### 5.4 路線 C：Docker 部署（NAS / 常開伺服器）

**方式一：根目錄 compose（建議）**

編輯根目錄 `docker-compose.yml`：
- 填 `DEEPSEEK_API_KEY`
- 把 NAS 的 IP 加進 `DSH_TRUSTED_HOST`
- 把 `PUID` / `PGID` 設成共用目錄擁有者的 ID

```sh
docker compose up -d --build
docker compose logs ds-bot
```

日誌裡會印出一行：
```
dsh web: http://127.0.0.1:3080/?token=*** (LAN: http://172.x.x.x:3080/?token=***
```

**注意連接埠**：印出的是**容器內**的連接埠，你要用 `ports:` 裡映射的**主機連接埠**（根目錄 compose 預設 **13080**）。第一次打開用 `http://<NAS IP>:13080/?token=***`，token 會設成一個簽章 cookie（有效期 30 天），之後直接連 `http://<NAS IP>:13080/` 就行。

**方式二：docker/ 目錄下的 .env 方式**
```sh
cd docker
cp .env.example .env
# 編輯 .env：DEEPSEEK_API_KEY、DSH_TRUSTED_HOST、PUID/PGID
docker compose up -d --build
```
這個方式預設發佈**主機連接埠 3080**。**兩種方式選一種，別同時跑在同一個資料目錄上。**

**預先建置映像（GHCR）**：
```yaml
services:
  ds-bot:
    image: ghcr.io/fei2411/deepseek-bot:dev
    ports:
      - "13080:3080"
    environment:
      DEEPSEEK_API_KEY: ""
      PUID: "1000"
      PGID: "1000"
      DSH_TRUSTED_HOST: "localhost,127.0.0.1"
    volumes:
      - ./data:/data
      - ./workspace:/workspace
    extra_hosts:
      - "host.docker.internal:host-gateway"
    restart: unless-stopped
    stop_grace_period: 15s
```

**⚠️ Docker 部署的安全警告（務必閱讀）**：

> DSH 自己的核心沙盒（bubblewrap / Landlock）**在 Docker 預設 seccomp profile 下或大多數 NAS 核心上跑不起來**。所以映像只提供**一個權限預設：完全權限**——每個 Bot 的命令都直接執行，不詢問。
>
> **所以：只把 Bot 需要改動的目錄掛進 `/workspace`。容器能看到的其他一切，Bot 都能改。**

**HTTPS 強烈建議但不強制**：UI 在純 HTTP 下能跑，但那個頁面**不是安全內容**——你輸入的 API key 和金鑰值會**明文穿過區域網路**。日常使用請在前面放一個反向代理。

### 5.5 設定詳解

外掛選項在 profile 的 `cordis.patch.yml` 的 `bot` 項目下，**全部選填**：

```yaml
- id: bot
  name: ds-bot
  config:
    workspace: /path/to/workspace   # Bot 做事的地方；預設 <home>/workspace
    home: /path/to/bot-data         # 團隊資料存放處；預設 $DSH_HOME/bot
    checkRatio: 0.8                 # 管家判斷的上下文占比
    browser: true                   # 強制開關 Bot 瀏覽器；預設只在 Desktop 開
    memory: true                    # false 關閉記憶：沒有記憶工具、區塊和面板
    memoryReview: true              # false 則記憶完全交給 Bot 自己的 remember 呼叫
    diagnosticsFile: false          # 錯誤日誌只留在記憶體；預設 <home>/logs/diagnostics.jsonl
    updateCheck: true               # 視窗開啟時檢查新版本；預設 true
    updateRegistry: https://registry.example/   # 只向這個 npm registry 查更新
    github: false                   # 隱藏 GitHub 連接器；預設在 Connectors 裡顯示
```

**關於 `contextWindow`**：務必為每個模型填上 `contextWindow`。

> 可用視窗 = 視窗 − 回覆預留（`maxTokens`）
> 硬線 = 可用視窗 × 0.95
> 檢查線 = 可用視窗 × `checkRatio`（預設 0.8）
>
> 沒填 `contextWindow` 的模型會拿到轉接層預設值（`llm-pi-ai` 是 262,144），**這個值對該模型可能是錯的**。完全沒宣告視窗的依 500,000 計算。

**自訂模型端點**（OpenAI 相容轉接等），在首次啟動前建立 `DATA_DIR/cordis.patch.yml`：
```yaml
- id: llm-pi-ai
  config:
    providers:
      relay:
        apiKeyEnv: RELAY_API_KEY
        api: openai-completions          # 或 openai-responses / anthropic-messages
        baseURL: http://host.docker.internal:3425/v1
        models:
          - id: my-model
            contextWindow: 131072
            maxTokens: 8192
- id: agent-default-model
  config:
    provider: relay
    model: my-model
```
然後在 compose 的 `environment` 裡加上 `RELAY_API_KEY`。

### 5.6 從原始碼開發

需要 Node 24、pnpm，以及一份裝好相依套件的 deepseek-harness 检出，放在本儲存庫旁邊（`../deepseek-harness`，或設定 `DSH_HARNESS`）。Desktop 測試台還需要 `xvfb-run` 和 `ffmpeg`。

```sh
npm ci                                   # esbuild，僅用於用戶端建置
npm run harness                          # 僅一次：安裝測試和 linter 用的 DSH 套件
npm run build                            # src/client → client.js
npm test                                 # 單元測試
npm run lint                             # oxlint
```

**測試台**：
```sh
dev/bench.sh dev 3100 8800 start         # Web 測試台：mock 模型 + dsh Web
dev/desktop-linux/desktop.sh dev start   # Desktop 測試台（Xvfb）
dev/check.sh                             # 全部檢查
```

**完整檢查項目**：`unit`、`build`、`lint`、`smoke`、`web`（側邊欄、聊天、群組、Bot 設定等截圖）、`desktop`。首次下載後約 3 分鐘。

**連接埠**：每個指令稿都接受 `SLOT=n`（0-9，預設 0），Web 測試台 `31n0`、mock `88n0`，避免多人同機衝突。

**改完 `src/client/` 之後必須 `npm run build`**（`client.js` 是提交進儲存庫的產物，`npm test` 會檢查它是否過期）。改完 `index.js` 或 `src/host/` 之後要重啟 dsh。

### 5.7 典型使用流程

```
1. 打開 DS Bot → 出現 Chief（Main Bot）
2. 跟 Chief 說清楚你的工作方式
3. 讓 Chief 建專職 Bot：
   "建一個叫 Reviewer 的 Bot，角色是審校，
    負責檢查我的文件邏輯是否自洽"
4. 建群組聊天，讓多個 Bot 協作：
   "建一個群叫 寫作組，成員是 Chief、Writer、Reviewer"
5. 在群裡 @ 點名，或直接跟 Main Bot 說，讓它調度
6. 需要金鑰時，Bot 會跳卡片，你在卡片裡填，它永遠看不到
7. 用設定 → Usage 看 token 消耗
```

### 5.8 資料與備份

資料在 `config.home`，未設定則 `$DSH_HOME/bot`，再預設 `~/.dsh/bot/`（Windows 是 `C:\Users\<user>\.dsh\bot\`）。

| 檔案 | 內容 |
|---|---|
| `state.json` | 團隊：Bot、群組、Bot 之間訊息、偏好、待答問題 |
| `group-lines/` | 長群組行，每行一個檔案 |
| `chat-index.sqlite` | 舊聊天全文索引（`read_own_chat`）；刪了會重建 |
| `usage.sqlite` | 用量統計；刪了從日誌重建 |
| `memory/` | 記憶：`bots/<id>/`、`groups/<id>/`、`team/`，`journal.jsonl`、`archive/` |
| `secrets.json` | 金鑰。**當密碼對待** |
| `logs/diagnostics.jsonl` | 最近的錯誤和警告（已去識別化） |

**聊天本身不在 `bot/` 裡**，在 `~/.dsh/sessions/`。

**備份步驟**：
1. **完全結束 DSH**（Web 服務和 Desktop 都要關），確保 `state.json` 是最新的
2. 複製整個 `~/.dsh/`（至少 `bot/`、`sessions/`、`storages/`）
3. **只複製 `bot/` 會遺失聊天**
4. 還原：結束 DSH，把資料夾放回原處，再啟動

**換電腦**：路徑相同的話直接複製。路徑不同（例如使用者名稱變了）**尚未測試** DSH 能否找到舊的 Session。

**Web 和 Desktop 同時開**：預設共用同一個 `~/.dsh`。先載入團隊的 DSH 拿到 `bot/state.lock`，另一個變成**唯讀**——它能看到團隊並跟隨檔案變化，但拒絕修改（回報 `bot/read-only`）。想讓兩邊都能改，給其中一個設定不同的 `DSH_HOME`。

## 六、常見問題排查

### Q1：DS Bot 載入不了，日誌報 `disabling profile plugin row "bot"`

```
dsh: disabling profile plugin row "bot": its declared peer dependencies cannot be validated: Cannot read properties of undefined (reading 'startsWith')
```

**原因**：DSH 載入外掛前會檢查 profile 的每一行。這則訊息表示有一行 id 是 `bot` 但沒有 package name。DS Bot 加的行 name 是 `ds-bot`，所以**多半是 profile 目錄裡某個檔案留了一行沒有 name 的 `- id: bot`**（例如一個不再符合的 `cordis.patch.yml` 覆寫）。

**解決**：
1. 結束 DSH
2. 打開 profile 目錄的 `cordis.patch.yml`（`~/.dsh/profiles/web/`，Windows 是 `C:\Users\<user>\.dsh\profiles\web\`；Desktop 用 `profiles/desktop/`）
3. 找到沒有 `name: ds-bot` 的 `- id: bot` 行，刪掉它。**先備份檔案**
4. 檢查同目錄 `package.json` 的 `dependencies` 裡有沒有 `ds-bot`，沒有就重新加：
   ```sh
   npx @deepseek-ai/dsh@0.2.1-rc.2 plugin --profile web add ds-bot
   ```
5. 重啟 DSH

**排查指令**：
```sh
npx @deepseek-ai/dsh@0.2.1-rc.2 --profile web --dump-config
```
它會印出每一行外掛及其來源檔案。

> 刪掉整個 profile 目錄也能修好，但那會連其他外掛和設定（如模型設定）一起刪掉。Bot 團隊在 `~/.dsh/bot/`，不受影響。

### Q2：關掉 "web-search-auto" 後，所有工作階段的搜尋都失效

```
Error: configured web provider "auto" is not registered
```
錯誤碼 `WEB_PROVIDER_CONFIGURED_MISSING`。

**原因**：DS Bot 的 `cordis.patch.yml` 無論 `web-search-auto` 開不開，都把 `web` 行的 `searchProvider` 設成 `auto`，而 DSH 在指定的 provider 沒註冊時**不會回退**。

**解決**：在 profile 的 `cordis.patch.yml` 裡加一個 `web` 行（**這行會取代 `web` 行的整個 config，所以 `fetchProvider` 要保留**）：
```yaml
- id: web-search-auto
  name: ds-bot/web-search
  disabled: true
- id: web
  name: '@deepseek-ai/dsh-web'
  config:
    searchProvider: deepseek-official
    fetchProvider: http
```

### Q3：`@Name` 在訊息還沒送出時顯示成檔案圖示

**原因**：DeepSeek Harness 自己畫這些等待行，並且把 `@` 讀到下一個空格為止。外掛目前改不了它的畫法。

**不影響誰回答**：DS Bot 用自己的規則讀 `@Name`，被點名的 Bot 會被叫到。訊息送出後就正常顯示。

**變通**：名字後面加個空格（`@Anvil 你看一下`）。

### Q4：從舊的 `dsh-bot` 套件升級

早期建置用的套件名稱是 `dsh-bot`。**先把 `dsh-bot` 從 profile 移除，再加 `ds-bot`**——兩個套件都用 `bot` 這個外掛 id。

團隊、聊天和金鑰會留在原處；儲存的瀏覽器設定、佈景主題和 Bot 顏色會在 DS Bot 首次打開時遷移。

## 七、結語：這個專案在提醒我們什麼

看完這個專案，我最強烈的感受不是「這個專案很好」，而是：

**多 Agent 系統真正難的地方，從來不是「怎麼讓它們平行」，而是「怎麼讓它們在長時間裡保持一致」。**

一致性的敵人有三個：

1. **上下文漂移**——聊久了忘了目標
2. **狀態不一致**——不知道別人在幹什麼
3. **協作失序**——重複勞動、繞圈、結果遺失

DS Bot 對這三條各有明確對策：**上下文管家**治漂移，**狀態一等公民**治不一致，**派活樹**治失序。

而所有這些對策背後，是同一個設計哲學：

> **不要用計數器限制行為，要用結構約束行為。**

刪掉 6 跳截斷、10 則未讀上限、3 輪上限、40 則上限，新增的唯一約束是「不要傳給正在等結果的 Bot」。**淨約束減少，可靠性提升。** 這是只有真正想清楚系統結構的人才能做出的決定。

還有一點：

> **「如果 DSH 中缺少某項能力，就停下來並說明；不要用打補丁的方式繞過去。」**

在一個普遍傾向於「能跑就行、先繞過再說」的開源生態系裡，把這句話寫進硬性規則並且貫徹到桌面應用程式的架構決策裡，是需要一點底氣的。
