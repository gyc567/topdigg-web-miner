# FDE Guide 深度解析：在自主性之前先工程化價值——面向 FDE 與 AI 工程師的生產級交付方法論

> 核心思想：**Tokens 是輸入（Tokens are an input）。自主性是設計選擇（Autonomy is a design choice）。被接受的結果才是產品（Accepted outcomes are the product）。** davidahmann/fde-guide 是作者 David Ahmann（雲、資料與 AI 平台負責人，前 Field CTO）維護的獨立開源指南與工程套件，目標只有一個：**把一條真實的客戶或內部工作流，變成一個可度量、可營運的 AI 服務。** 它的第一原則是「在自主性之前先工程化價值」——從一個模型或 agent 拓撲出發是錯的，要從**工作本身和它被接受的結果**出發。生產級 AI 系統不能只產出貌似合理的答案，它必須知道：誰有權行動、哪條資訊是當前的、失敗如何被限制、完成如何被驗證、整個服務成本多少、誰能營運它或叫停它。Agent 只是組件選項之一；對每個關鍵決策，要在確定性軟體、最佳化、經典 ML、檢索、基礎模型呼叫、有界 agent 工作流與人工審查之間做比較，選擇**最小的充分機制（smallest sufficient mechanism）**，並保留它的證據、權威、成本、回退與退役路徑。該專案的「12 因子 AI 價值工程」把這一原則轉成顯式的價值、驗證者、採用、權威、成本、證明與生命週期門禁。

## 一、專案說明

### 1.1 它是什麼？

本文解析的是 **GitHub 開源倉庫 `davidahmann/fde-guide`**——副標題為 *"Value engineering and production architecture for FDEs, applied-AI engineers, product teams, and operators"*（面向 FDE、應用型 AI 工程師、產品團隊與營運者的價值工程與生產架構）。它定位為「一份獨立的開源指南和工程套件」，用於**把真實客戶或內部工作流轉化為可度量、可營運的 AI 服務**。

它不是又一個 agent 框架，而是一套**工程方法 + 可執行證據**的複合體：方法（The Guide）教你怎麼想，手冊（The Handbook）支撐你的判斷，工程套件（The Engineering Kit）讓主張、權威、行為與變更可檢視、可測試。三者是同一方法的三種深度，不是三套獨立框架。

**三種深度，按需取用：**

| 層級 | 何時使用 | 入口 |
|------|---------|------|
| **The Guide（指南）** | 想要心智模型、核心原則與完整交付循環，約 20 分鐘 | `guide/README.md` |
| **The Handbook（手冊）** | 正在評估、設計、交付、移交或營運一條真實工作流 | `playbooks/` 生命週期 playbooks + `library/00-start-here.md` |
| **The Engineering Kit（工程套件）** | 需要實作工件、架構、機器可讀契約、發布控制、可執行範例或測試 | `examples/`、`blueprints/`、`templates/`、`controls/`、`schemas/`、`operations/`、`tests/` |

### 1.2 關鍵資料與資訊

- 倉庫：`https://github.com/davidahmann/fde-guide`（Apache-2.0 授權，21 stars / 2 forks，17 commits，含 `CITATION.cff` 引用元資料）
- 作者：**David Ahmann**——雲、資料與 AI 平台領導者，具備 Field CTO 經驗；獨立專案，不代表任何現任或前任雇主的背書

### 1.3 它解決什麼問題？

文章開頭就點出核心痛點：**AI 有一個記帳問題（AI has an accounting problem）。** 團隊度量 token、模型呼叫、生成的程式碼、部署的 agent、「號稱節省的工時」——這些度量描述的是智慧的生產與消耗，**並沒有確立任何有價值的事情發生**。組織最終為的是被改變的結果：發票異常被解決並在帳本中確認；貨運案件在影響服務前到達正確的協調人；發布到達生產、通過檢查並保持健康。

**一個被接受的結果（accepted outcome）** 是一個完成的、被獨立驗證者、權威系統或負有責任的評審者接受為正確的工作單元。AI 價值工程把這個結果與合格需求、採用、歸因、全成本與風險連結起來。

它解決的問題因此是：**如何把「AI 活動」變成「被接受的結果」？如何確保交付的系統不是 demo、不是提示詞、不是模型呼叫、不是 agent、不是儀表板，而是一個對真實工作的有主變更（owned change）**——帶有被接受的結果、可信的驗證者、有界的權威、全成本的價值主張、營運團隊與退役路徑。

## 二、核心思想

### 2.1 一句話世界觀

> **"Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."**
> （**Tokens 是輸入。自主性是設計選擇。被接受的結果才是產品。**）

這是全專案的座右銘，也是它與大多數「agent 狂熱」內容的分界線：**最大化智慧、token、自動化或自主性都不是目標，目標是在被接受的成本與風險上限內改進一個有主的結果。**

### 2.2 在自主性之前先工程化價值

> **"Start with the work and the accepted outcome—not with a model or agent topology."**
> （**從工作與被接受的結果出發——而不是從模型或 agent 拓撲出發。**）

生產級 AI 系統必須回答的七個問題：誰可以行動、哪條資訊是當前的、失敗如何被限制、完成如何被驗證、整個服務成本多少、誰能營運它、誰能叫停它。Agent 是一個組件選項；對每個關鍵決策，比較 7 種機制（確定性軟體 / 最佳化 / 經典 ML / 檢索 / 基礎模型呼叫 / 有界 agent 工作流 / 人工審查），選擇最小的充分機制，並保留其證據、權威、成本、回退與退役路徑。

### 2.3 FDE 的四項職責與「有主變更」的輸出

一個前向部署工程師（Forward-Deployed Engineer, FDE）把**模糊的營運問題**變成**產生可度量結果的受支援軟體服務**。工作橫跨四項職責：

1. **發現（Discovery）**：理解工作、判斷、延遲、風險與價值實際發生在哪裡。
2. **產品（Product）**：決定使用者應該改變什麼、什麼應保持人工、本機或手動。
3. **工程（Engineering）**：構建能改進工作流的最小可靠系統。
4. **營運（Operation）**：證明結果、移交所有權、支援服務、從生產中學習。

**輸出不是 demo、提示詞、模型呼叫、agent 或儀表板**，而是一個**對真實工作的有主變更**：帶有被接受的結果、可信的驗證者、有界的權威、全成本的價值主張、營運團隊與退役路徑。同一方法適用於公司內部——內部應用型 AI 工程師即使沒有 FDE 頭銜，也必須連接業務上下文、產品判斷、軟體架構、採用與生產營運。

### 2.4 一條貫穿始終的交付循環

整個倉庫只遵循一個生命週期（7 階段），不為每個客戶、模型或框架建立平行方法：

```
觀察工作 → 章程化價值與範圍 → 選擇機制 → 構建一個受控切片 → 用案例與使用者證明 → 上線並移交所有權 → 營運、學習或退役 → （回到章程）
```

每個階段都以**決策 + 可被他人檢視的證據**結束。停止、收窄或重新設計薄弱的工作是有效結果——一個漂亮的模型分數、贊助人、續約、上線或使用數字，**無法平均掉失敗的價值、權威、安全、所有權或生產門禁**。

## 三、詳細教學：7 階段交付循環 + 12 因子價值工程

### 3.1 階段 1：先觀察工作，再設計系統（Observe）

**上下文提取不是收集所有文件，而是發現做出關鍵設計決策所需的最小營運真相。** 與執行、接收、評審和支援該工作的人一起觀察真實案例，記錄：

1. 觸發點與工作介面；
2. 正在做的決策；
3. 輸入及其權威來源；
4. 被允許的行動與最大可容忍影響；
5. 正常路徑、異常、變通做法與恢復；
6. 擁有業務結果的人；
7. 能獨立接受結果的人或系統；
8. 將營運變更後工作流的團隊。

**訪談產生假設；操作者走查、源工件、系統 trace 與對帳記錄產生更強的證據。** 如果工作流只在簡報投影片裡是清晰的，發現就沒有完成。

警告：**在問「工作流、策略、源系統或交接是否應該被修復」之前，不要自動化一個變通做法。** AI 能讓一個破碎的流程跑得更快，同時讓底層問題更難被看見。

### 3.2 階段 2：工程化價值契約（Charter）——一個用例可構建的七個欄位

一個用例在它的結果**能被擁有、被度量、被質疑**時才可構建。在架構之前定義這些欄位：

- **合格族群（Eligible population）**：哪些工作可以合法使用該系統，含排除項。
- **基線（Baseline）**：當前效能、狀態、日期、族群與信賴度。
- **被接受的結果（Accepted outcome）**：工作被獨立接受的事件——不是模型「生成」或「完成」了。
- **驗證者（Verifier）**：確立接受的人、規則、對帳或真相來源事件。
- **目標與護欄（Target and guardrails）**：期望的變化，以及絕不能變差的東西。
- **歸因（Attribution）**：團隊如何區分系統效應與其他變化。
- **全成本（Full cost）**：發現、交付、變更、模型、基礎設施、工具、人工審查、支援、事故、恢復與維護。
- **殘餘損失（Residual loss）**：未包含在其他收益或成本項中的預期或已實現損害。
- **所有者（Owner）**：對指標及其驅動的決策負責的角色。

有用的營運單位：

```text
每個被接受結果的成本 =
  總營運與分攤生命週期成本
  / 獨立接受的結果數
```

```text
已實現淨價值 =
  被接受結果的可歸因價值
  + 不重疊的避免損失
  − 生命週期成本
  − 未淨額化的殘餘損失
```

**把預測、已證明的試點證據與已實現的生產價值分開。** 不要把狹窄的試點年度化，除非有顯式、有主的推斷。不要透過節省時間、單位價值、避免損失或減員來重複計算同一收益。

### 3.3 階段 3：選擇最小的充分機制（Select）

**「用 AI」不是架構決策。** 把工作流分解成關鍵決策步驟，為每一步單獨選擇機制：

| 機制 | 適合 | 警示訊號 |
|------|------|---------|
| **確定性軟體** | 穩定規則、轉換、驗證、路由、授權 | 自然語言歧義被藏進脆弱的 if-else 分支 |
| **最佳化演算法** | 分配、排程、排序、規劃（有顯式目標與約束） | 目標或約束無法被擁有或度量 |
| **經典 ML** | 重複預測（有標籤、校準的不確定性、漂移監控） | 不存在代表性結果或回饋路徑 |
| **檢索** | 證據必須跨受治理來源查找 | 檢索輸出被允許成為策略或權威 |
| **基礎模型呼叫** | 有界的解釋、提取、分類或起草 | 流暢的輸出被當作已驗證的事實 |
| **有界 agent 工作流** | 多步判斷確實依賴變化的證據或工具使用 | 步驟是已知的，普通工作流程式碼會更簡單 |
| **人工審查** | 判斷弱可驗證、高風險，或策略要求問責 | 審查被用來掩蓋不可用系統或無界工作量 |

一個生產系統可以組合多種機制。保持每條路徑可觀察、可測試、可替換、可計成本。**模型路徑不會削弱身分、授權、資料、發布或普通軟體工程控制。** 只有在有界多步判斷真正有用時才加 agent；只有當權限、工具、上下文、所有權或延遲的**真實差異**證明協調成本合理時才加多個 agent。

### 3.4 階段 4：構建一個受控的垂直切片（Build）

第一個切片應穿過**真實的介面與控制邊界**，而無需嘗試完整產品。它應示範：

- 一個代表性觸發點與使用者；
- 具有真實權限行為的權威上下文；
- 選定的決策路徑；
- 最終操作者工作介面；
- 模擬、暫存、可逆或以其他方式有界的影響；
- 顯式的失敗與升級狀態；
- 遙測、成本與接受證據；
- 有主的恢復或回退路徑。

**在試點期間就開始採用與移交。** 接收團隊應在交付團隊退出前，配對參與評估、發布、支援、策略變更、事故、回退與退役。

**預先聲明試點的最大時長、證據截止點，以及獨立的（技術 / 操作者 / 採用 / 價值 / 經濟 / 生產就緒）畢業門禁。** 一個 demo 不應因為打動了贊助人就悄悄變成生產。

### 3.5 階段 5：在代表性工作上證明主張（Prove）

**評估是「在聲明條件下的發布主張」，不是永久分數。** 使用代表性正常案例、困難切片、已知異常、對抗性輸入、依賴失敗、策略變更、逾時、重試、取消、恢復與人工審查容量。**保留重放結果所需的完整環境與行為版本。**

分離三個問題：

1. **能力（Capability）**：機制能執行任務嗎？
2. **行為（Behavior）**：整個系統走對路徑並安全停止嗎？
3. **結果（Outcome）**：工作流是否在護欄內為目標族群改進了被接受的結果？

確定性檢查對封閉不變量最強；統計度量需要分母與不確定性；模型裁判需要校準的 rubric 與人工比較；生產回饋不能靜默污染保留集，也不能讓候選模型控制自己的評估者。透過**離線評估 → 影子營運 → 金絲雀 → 命名生產段**等有界階段晉升；**先定義回退再上線**。

### 3.6 階段 6：營運服務並移交所有權（Launch + Operate）

**生產是一個反覆出現的決策，不是最後的部署步驟。** 監控整個系統：被接受的結果、價值、採用與護欄；來源、權限、新鮮度與對帳；路徑、模型、提示詞、工具與策略版本；延遲、成本、重試、步驟與終止原因；被拒/被禁/重複/效果未知/回讀不匹配事件；評審者負載、糾正、放棄、培訓與支援；所有者連續性、事故就緒、回退與退役能力。

**移交在接收團隊能不靠交付團隊的英雄主義營運、變更、恢復、支援與退役該服務時才算完成。文件本身不證明營運能力，演練才證明。**

### 3.7 階段 7：把現場學習變成產品能力（Field learning）

FDE 工作的複利優勢不是可複用的客戶資料或堆砌的自訂程式碼，而是**把本地上下文與可移植的工程知識分離**的能力。預設保持客戶/業務單元特定的：策略、閾值、身分、權限、機密資料、來源細節與營運決策。可複用的候選包括：契約形狀、失敗類別、評估方法、工作介面模式、整合原語、控制、runbook 與平台缺口。

**只有證據顯示在獨立環境中反覆出現、候選已消毒、存在目的地與所有者、目標特定驗證成功、走正常發布路徑時，才產品化。** 先分類（客戶配置 / 目標自有擴充 / 共享產品或平台能力 / 有時限實驗 / 被禁或延期），再做實作。**不要製造依賴，保留負面與停止的證據，保留退出路徑。**

### 3.8 教學核心：12 因子 AI 價值工程（Valuemaxxing）

這是全專案的「帳本」框架——把 AI 活動換算成被接受的結果：

| # | 因子 | 一句話要點 |
|---|------|-----------|
| 1 | **觀察真實工作** | 別自動化簡報投影片裡的流程；變通做法不自動等於領域專長（`FDE-002`） |
| 2 | **擁有結果** | 先定義營運結果再選技術；「生成回覆」是輸出，「解決異常並在帳本確認修正餘額」才是結果（`FDE-001`, `VAL-001`） |
| 3 | **界定合格工作** | 明確哪些工作合格哪些不合格；先聲明分母再算採用率；「處理大多數簡單案例的系統」可能比「處理少數昂貴案例的系統」價值更低（`VAL-001`） |
| 4 | **建立反事實** | 先度量當前工作流再聲稱改進；前後對比圖不自動是因果證據，聲明已知混雜因素與歸因方法局限（`VAL-001`, `VAL-002`） |
| 5 | **命名驗證者** | 生產系統不應是它是否成功的唯一裁判；驗證者必須能否決結果；接受 ≠ agent 走到工作流末尾（`FDE-001`, `EVA-001`, `REL-003`） |
| 6 | **工程化工作流與採用** | 技術成功但沒人用 = 零價值；如果使用者必須重建每個結果才敢信，工作就沒有被自動化（`FDE-003`, `ADP-001`, `ADP-002`） |
| 7 | **使用最小充分智慧** | 別一開始就決定問題需要 agent；分解成決策再逐個比較；升級困難案例而不是讓每個決策都走最強模型（`ARC-004`, `ARC-005`） |
| 8 | **界定權威與損失** | 能力不授予權威；單個被允許的行動可以組合成不可接受的結果，審查完整行動路徑（`IAM-003`, `SEC-004`, `REL-001/003/005`） |
| 9 | **為整個服務定價** | Token 只是成本之一；更便宜的模型可能讓周邊工作流更貴；技術正確的結果仍可能經濟上不可接受（`CST-001`, `CST-002`） |
| 10 | **在代表性工作上證明** | 成功的示範證明路徑可行，不證明系統可上線；試點預先聲明最大時長、證據截止、決策所有者與獨立畢業門禁（`EVA-001/003`, `DEL-001`） |
| 11 | **度量可歸因的已實現價值** | 合格工作→到達工作流→完成工作流→被接受結果→度量的業務影響→持續淨價值；報告不採用、覆蓋、返工、評審者負載、事故、恢復與全成本（`VAL-002`, `OPS-004/006`, `CST-001`） |
| 12 | **基於證據擴張、約束或退役** | 自主性與投資必須靠前進的成果贏得繼續的權利；更強的基準、更大的模型或更高的使用數字不自動證明更多權威（`VAL-003`, `ADP-002`, `OPS-007`） |

**四個硬性門禁（硬性，不可平均）：**

1. 一個有主、可度量的結果（owned outcome）
2. 一個可信的獨立驗證者（credible independent verifier）
3. 有界的權威與預期損失（bounded authority and expected loss）
4. 全成本後仍為正的、合理的價值主張（plausible positive value case after full cost）

任一門禁缺失，正確的決策可能是 `defer`（推遲）、`redesign`（重新設計）或 `do_not_build`（不構建）。其餘因子按 **0 — 未定義 / 1 — 已聲明 / 2 — 已證明** 評分；分數支援對話，不是認證，強因子不能平均掉失敗的門禁。

**價值公式：**

```text
預期淨價值 =
  合格量 × 預期採用率 × 預期增量被接受結果率 × 每個被接受結果的價值
  − 預期生命週期成本
  − 未從避免損失或單位價值淨額化的預期殘餘損失
```

### 3.9 教學範例 1：受控寫入系統（invoice-exception，發票異常解決）

示範目標：**模型提議；可信軟體授權並提交；真相來源回讀證明結果。** 目標流：

```text
發票異常事件 → 收集帳本/供應商/策略證據 → 提議解決方案 → 驗證不變量
  → 授權並暫存 → 批准确確提案摘要 → 冪等重新授權並提交
  → 對帳任何'效果未知'逾時 → 回讀帳本狀態 → 完成回執 | 補償 + 事故
```

核心機制與不變量（這就是「受控寫入」的示範）：

- `resolution_commits(tenant_id, business_operation_id) <= 1`（冪等：一個業務操作只能提交一次）
- 提交前執行時期發布摘要 == 准入的解決方案發布摘要；提交的發票修訂 == 當前發票修訂；提交的提案摘要 == 批准的提案摘要；策略修訂 == 當前策略修訂
- 呼叫者租戶 == 發票租戶；每個資料/影響邊界都檢查當前呼叫者作用域與當前策略修訂
- `committed == true` 只在真相來源回讀之後；`effect_unknown` 在重試或完成前對帳
- `completed == true` 只在可信回執與回讀證明驗證之後；步驟、牆鐘時間與成本在聲明執行時期預算內；**`model_access(credentials) == false`（模型永遠接觸不到憑證）**

配套工件：可執行執行時期 `reference-loop.mjs`、授權策略 `authorization-policy.mjs`、型別化工具契約（讀/暫存/提交/回讀）、能力清單與出處記錄、威脅模型、評估用例（授權提交 / 未授權寫入 / 重複重試 / 修訂漂移重試 / 提示注入）、獨立評分器、評估報告與僅評審的解決方案發布。回歸覆蓋：授權、租戶隔離、陳舊策略、重複重試、批准時機、發布撤銷、回執驗證、效果未知恢復與真相來源回讀。

### 3.10 教學範例 2：混合系統（shipment-risk-triage，貨運風險分診）

證明 **AI 系統不必 agent 優先**：經典 ML 打分 → 確定性策略路由 → 可選模型解釋 → 人工保留營運決策。四種機制在一個有界工作流裡組合，每個組件都有選型記錄（`intelligence-selection.md`）、評估用例與回歸測試。它是「混合智慧系統藍圖」的可執行伴侶。

### 3.11 系統設計的八個顯式層

模型是一個更大軟體與營運邊界內的一個組件。設計這些層（對應 `design-production-ai-system`）：

- **領域與狀態（Domain and state）**：物件、身分、修訂、生命週期狀態、不變量與真相來源系統
- **上下文（Context）**：來源、權限、出處、新鮮度、充分性、信任與失效
- **行為（Behavior）**：程式碼、規則、模型路徑、提示詞、工具、護欄與相容性
- **權威（Authority）**：呼叫者或工作負載身分、租戶、範圍、策略、批准與最大影響
- **能力（Capabilities）**：型別化輸入輸出、精確目的地、憑證模式、失敗契約、重複安全與回讀
- **執行時期（Runtime）**：持久狀態、取消、逾時、資源預算、重試、熔斷與顯式終止狀態
- **工作介面（Work surface）**：持久工件、證據、狀態、不確定性、替代方案與被允許的人工行動
- **營運（Operation）**：trace、服務目標、告警、runbook、變更路徑、回退、所有權與退役

**核心行動規則**：模型可以提議（propose）。可信軟體授權並提交（authorize and commit）。真相來源回讀（source-of-truth readback）證明結果。秘密與憑證保持模型可見上下文之外；在執行關鍵影響（consequential effect）的邊界重新檢查當前身分、租戶、範圍、策略、發布准入與批准；用穩定的業務操作身分推導重複安全；產生影響後在權威系統中驗證結果，再報告完成。

### 3.12 架構不可妥協項與反模式

**不可妥協項：**

- 模型使用時：模型提議，確定性軟體驗證、授權、執行、持久化並驗證關鍵工作（`ARC-002`）
- 每個組件都有命名的目的、版本、所有者、權威上限、證據、成本分配、監控、回退與退役路徑（`ARC-005`, `DEL-001`）
- 真相來源狀態、身分、批准與完成證明位於提示詞與瞬時模型上下文之外（`CTX-001`, `IAM-001`, `REL-003`）
- 發布單元綁定資料、領域、智慧組件、工具、策略、評估、使用者介面與營運——不只是程式碼（`DEL-001`）
- 基礎模型或 agent 被保留是因為它在要求的護欄下改進了被接受的結果，而不是因為它新穎或可用（`ARC-004`, `VAL-002`）

**反模式：** 把確定性策略決策稱為「agent 推理」；把模型路徑當作架構而狀態/存取/影響/恢復仍隱式；給排程、分配、驗證或分類問題加 LLM 而不比較更簡單機制；訓練或路由 ML 模型卻沒有穩定標籤、錯誤度量、漂移監控或所有者；最佳化推理成本卻忽略工具、評審、恢復與客服成本；把沒有狀態轉換、信任邊界、失敗行為或發布測試的架構圖當作完整。

## 四、設計哲學

### 4.1 「AI 有記帳問題」：從活動度量轉向結果度量

設計哲學的起點是對現狀的批判：**團隊度量 token、呼叫、程式碼、agent 與「聲稱節省的工時」，這些只描述智慧的生產與消耗，不確立任何價值發生。** 組織最終為被改變的結果買單。因此「valuemaxxing（價值最大化）」不意味著最大化自動化——它意味著**從一個可驗證、可營運、可停止的系統中最大化持久淨價值**。

### 4.2 「在自主性之前先工程化價值」：模型不是起點

專案的第一原則與行業主流敘事相反：**不要從「用哪個模型」或「要什麼樣的 agent 拓撲」開始，從工作與被接受的結果開始。** Agent 是一個組件選項。對每個關鍵決策，7 種機制（確定性軟體/最佳化/經典 ML/檢索/基礎模型/有界 agent/人工）逐一比較，選最小充分機制。**「更 AI」可能意味著工作流從未被正確分解。**

### 4.3 「能力不授予權威」：信任的最小化設計

**模型永遠只能提議。** 可信軟體（確定性程式碼）負責授權、執行、持久化與驗證關鍵工作。權威綁定到工作流、行動者、租戶、目的、任務、目標、時長與後果；單個被允許的行動可以組合成不可接受的結果，所以要審查完整行動路徑。真相來源狀態、身分、批准與完成證明永遠在提示詞與瞬時模型上下文之外——**秘密與憑證模型永遠接觸不到（`model_access(credentials) == false`）**。

### 4.4 「驗證者必須能否決」：生產系統不能給自己打分

評估三問分離能力/行為/結果；**生產系統不應是它是否成功的唯一裁判**——驗證者（確定性檢查、真相來源對帳、獨立評估、下游確認或可問責的人工評審者）必須能否決結果。「接受」比「agent 走到工作流末尾」要求更多。這個哲學與「別讓 agent 自我驗證」一脈相承，但把它升級成了**價值契約裡的一個硬欄位（命名驗證者）**。

### 4.5 「評分支援對話，門禁不可平均」：證據倫理

0/1/2 評分框架與 4 個硬性門禁的分立是全專案最鋒利的哲學主張：**示範與複合分數不能平均掉失敗的門禁；預測、已證明試點與已實現價值必須分開；零是證據，不是預設值。** 停止、收窄或重新設計薄弱工作是有效結果——強模型分數、贊助人、上線數字都不能掩蓋失敗的價值/權威/安全/所有權/生產門禁。**評估是「在聲明條件下的發布主張」，不是永久分數。**

### 4.6 「變通做法不是領域專長」：對現場的謙遜

觀察真實工作（而不是簡報投影片裡的流程）；分類每個觀察到的行為為保留/修復/移除/升級。**AI 能讓破碎流程跑得更快，同時讓底層問題更難被看見。** 現場學習的複利優勢是把本地上下文與可移植工程知識分離的能力；不要製造依賴，保留負面與停止證據，保留退出路徑。

## 五、評估總結：觀點與結論

### 5.1 核心觀點清單

1. **價值定義：** 被接受的結果（獨立驗證者/權威系統/可問責評審者接受為正確的工作單元）才是產品；token 與自動化只是輸入與手段。
2. **起始點：** 從工作與被接受的結果出發，而不是從模型或 agent 拓撲出發；Agent 是一個組件選項，不是架構。
3. **最小充分機制：** 對每個關鍵決策在 7 種機制間比較並選最小充分者；「用 AI」不是架構決策；更 AI 可能意味著工作流從未被正確分解。
4. **觀察優先：** 先觀察真實工作（操作者走查/源工件/系統 trace）再設計；訪談只產生假設；別自動化簡報投影片裡的流程，也別在修復前自動化變通做法。
5. **價值契約欄位：** 合格族群/基線/被接受結果/驗證者/目標護欄/歸因/全成本/殘餘損失/所有者——九欄位先於架構。
6. **12 因子 + 4 硬性門禁：** 有主結果 / 可信獨立驗證者 / 有界權威與預期損失 / 全成本後仍正的價值主張；任一缺失 → defer / redesign / do_not_build；0/1/2 評分支援對話但不可平均門禁。
7. **權威邊界：** 能力不授予權威；模型提議、可信軟體授權提交、真相來源回讀證明；秘密與憑證永遠在模型上下文之外；冪等（一個業務操作一次提交）與效果未知對帳是硬不變量。
8. **採用與營運：** 技術成功但沒人用 = 零價值；移交以「接收團隊可營運/變更/恢復/支援/退役」為完成標準（演練而非文件）；生產是反覆決策而非最後部署步驟。
9. **反 agent 優先：** 混合系統範例證明確定性策略 + 經典 ML + 人工審查可以是正確架構；只有有界多步判斷真正有用時才加 agent。
10. **現場學習：** 複利優勢 = 分離本地上下文與可移植知識；產品化需跨獨立環境重現證據 + 消毒 + 目的地所有者 + 正常發布路徑；不要製造依賴。

### 5.2 關鍵金句（值得 memo 的）

- "Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."（**Tokens 是輸入，自主性是設計選擇，被接受的結果才是產品。**）
- "Start with the work and the accepted outcome—not with a model or agent topology."（**從工作與被接受的結果出發，而不是從模型或 agent 拓撲出發。**）
- "Capability does not grant authority."（**能力不授予權威。**）
- "The model may propose. Trusted software authorizes and commits. A source-of-truth readback proves the result."（**模型可以提議；可信軟體授權並提交；真相來源回讀證明結果。**）
- "AI has an accounting problem."（**AI 有一個記帳問題。**）
- "The system producing the work should not be the sole judge of whether it succeeded."（**生產工作的系統不應是它是否成功的唯一裁判。**）
- "A workaround is not automatically domain expertise."（**變通做法不自動等於領域專長。**）
- "A more capable model will not repair an undefined task."（**更強的模型不會修復一個未定義的任務。**）
- "The point is not to use more AI. The point is to make the outcome worth the system required to produce it."（**重點不是用更多 AI，而是讓結果值得為產生它所需的系統。**）

### 5.3 與本站其他深度解析的銜接（讀者下一步）

- **Graph Engineering Guide (2026)**（`graph-engineering-guide-2026-analysis`）：圖工程討論「什麼時候把 agent 織成圖」；fde-guide 回答更早的問題——**先決定這個工作流值不值得變成系統、機制怎麼選、結果怎麼驗收**。兩者互補：圖是結構選擇，FDE Guide 是價值與治理前提。
