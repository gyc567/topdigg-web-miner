# anything2explainer 深度解析：給一個主題，產出一條用程式碼畫出來的講解影片

## 引子：你想讓 AI 講清楚一件事，但影片是個麻煩

設想一個很具體的需求。

你剛讀完一篇論文，或者剛搞懂一個技術概念，想發一條三分鐘的科普影片到影片號。選題有了，稿子也大致想好了。現在卡住的是：畫面怎麼辦？

找素材？版權不清，而且拼起來的素材永遠拼不成一條有邏輯的片子。找 AI 影片生成模型？目前生成的片段接不上、字寫不對、每幀都在漂。用口播數位人？技術上沒問題，但一個會說話的腦袋不會解釋任何機制，它只是念稿。

再退一步，讓 AI 程式設計 agent 寫程式碼來畫每一幀？

這個方向是對的，但立刻會撞上第二個問題：Remotion 本身只給你一個畫布，它不告訴你一部片子該長什麼樣子。第一個 agent 畫出來的鏡頭漂亮，第二個 agent 畫出來的像 PPT，第三個直接忘了字幕帶在哪裡。五個 agent 的產出拼在一起，像五家不同的公司做的。

那到底該怎麼做？

anything2explainer 給出的答案很直接：別只寫程式碼，把整套方法也寫出來。它把「怎麼拍一條 AI 生成的科普影片」這件事，拆成了風格規範、動效詞彙表、構圖與光的硬規則、agent 分工協議、量化品質檢測腳本，再加一條完整的樣片作為品質標尺。

這不是一個能跑的命令列工具，它更像一本寫給 AI 的電影製作手冊。

## 一、專案說明：倉庫裡到底裝了什麼

### 1.1 一句話定位

輸入一個主題，或者一篇你想改成影片的文章，輸出一條 1280×720 的 H.264 MP4：帶 TTS 配音、逐字對齊的字幕、章節卡、頂部 HUD 和底部章節進度條，中文或英文都行。

關鍵在於每一幀都是程式碼畫出來的。沒有素材庫，沒有生成式影片模型，也沒有從別人影片裡拿的任何一幀。

作者 Vincentwei1021 在 CITATION.cff 裡的定位是「software」，發布於 2026-09-09，授權用的是 PolyForm Noncommercial 1.0.0，非商用免費，商用需要事先授權，但用它做出來的影片歸你自己。

### 1.2 它不是 CLI

這一點值得單獨說，因為很多人會拿它當工具去試，試用完發現「沒反應」。

倉庫裡裝的是讓 AI 程式設計 agent 把片子做出來的整套方法。真正會被執行的只有三樣東西：

- 一個可編譯的 Remotion 4 模板工程（`template/`），你用 `new_project.sh` 把它複製成工作目錄；
- 一堆寫給主會話和各個 agent 看的規範文件（`reference/`）；
- 一條已經做完的樣片（`examples/rag/`），連同它的調研底稿、解說詞、分鏡表、44 個鏡頭的原始碼和 5 份 QC 報告。

作者給 skill 裝了一個 Claude Code 的徽章和一個 Codex 的徽章，也就是說它是被這兩種 agent 載入的「技能包」，不是讓人敲指令的軟體。

### 1.3 倉庫結構速覽

```
SKILL.md                  流程主幹：9 個階段、4 個確認點、品質標尺
reference/                寫給主會話和各 agent 的規範
  style-guide.md            安全區、調色盤、字體、圖元目錄、版式規律
  motion-vocabulary.md      入場/強調/光效/離場/運鏡的公式與幀數
  composition-and-light.md  主體尺寸三檔、光跟主角、高光時刻編排、QC 量化判據
  narration-guidance.md     口播文案寫作原則（純英文，已譯中文）
  narration-storyboard.md   解說詞格式與預算、配音參數、分鏡令牌、鏡頭模式表
  research-brief.md         研究員 prompt 與事實規則
  agent-build-rules.md      建構 agent 協議
  agent-qc-rules.md         QC agent 協議
  prompts.md                六種 agent 的 prompt 模板
  lessons.md                五部片子的踩坑紀錄與根因
template/                 可編譯的 Remotion 4 工程
  src/common/               霧底、星點、點陣波、glitch、緩動、字幕、進度條
  src/ui.tsx  src/fx.tsx    圖元與調色盤/光效、縱深、運鏡圖元
  src/overlay/              片頭、章節卡、HUD、流程軌、片尾
  scripts/                  配音、分鏡、still、測渲、渲染、QC 度量腳本

```

`examples/contrast/` 這個目錄特別值得注意，它是一張「評分表」。左邊是作者 2026-09-08 用 skill 做的另一部片子《eCPM 與廣告競價》的幀，右邊是樣片《RAG 與知識庫》的幀，六組對照，每組都指向一個具體缺陷：主角太小、主角沒光、高光時刻沒編排、結果項字太小、背景撒碎屑、收尾沒象徵物。

### 1.4 和其他工具的差別

作者自己列了一張對照表，我把它當成選型依據：

| 工具類別 | 產出 | anything2explainer 的不同 |
|---|---|---|
| 生成式影片模型（Sora、Veo、Runway） | 從 prompt 合成素材 | 產出是確定性的程式碼不是像素。畫面上每個數字都能追到一個來源 URL，任何一幀都能靠改一個鏡頭檔案修好 |
| 數位人 / 主播工具（HeyGen、Synthesia） | 一個數位主播念稿 | 不要主播。用動效圖解講機制，由旁白驅動畫面 |
| 手寫 Remotion / Motion Canvas | 一個可程式化的影片畫布 | 它在畫布之上交付整套方法：調研 → 解說 → 分鏡 → 並行建構 → QC，帶風格規範、動效詞彙表和一條樣片作為標尺 |
| Manim | Python 數學動畫 | agent 驅動的端到端流水線，帶 TTS 對齊字幕、章節與 QC；React / TypeScript 而非 Python |

第二行那個「不要主播」的決定，比聽起來重要得多。數位人影片的視覺資訊量等於零，你只是把稿子念了一遍。而動效圖解可以同時展示結構、順序和數量。README 裡有一句很到位的表述：解說負責理由、後果、比較和判斷，畫面負責結構、順序和數量。

## 二、核心思想：為什麼堅持用程式碼畫

### 2.1 三條不可妥協的原則

**第一，畫面全部程式碼繪製。** 可選的實拍 B-roll 只允許免版權來源，並且要登記 MANIFEST（sha256、來源 URL、授權、用途）。不能使用任何現有影片的幀或片段。

**第二，事實必須有出處。** 畫面上出現的每個數字、年份、機構、人名和英文術語，都必須能在這一部片子的調研文件裡找到來源 URL。調研沒核實的內容，不上畫面，也不進配音。

**第三，全片一個貫穿示例。** 解說和畫面用同一個例子從頭到尾。樣片用的是「差旅報銷」這個場景：問句是「差旅報銷的上限是多少？」，幻覺的答覆是「每天 1000 元，全國統一」，正確答覆是「住宿上限每天 600 元[1]，一線城市 800 元[2]」，來源是「員工手冊 p.12」和「差旅補充規定 2025」。所有組共用同一套示例文本，這是硬約束。

第二條是整個專案最有價值的設計。因為影片的觀眾無法點擊來源，一旦一個數字錯了就是錯了，糾錯的成本遠高於文章。把它前置成「調研階段不核實就不許上畫面」，比事後靠 QC 從像素裡認字要可靠得多。

### 2.2 「用程式碼畫」到底換來了什麼

這是理解這個專案的關鍵。影片生成模型和程式碼渲染看起來都是「讓電腦畫出畫面」，但換來的東西完全不同。

**確定性。** 每一個動畫都是幀號的純函式，隨機數用帶種子的 `rnd(...)`，文字寬度是算出來的而不是在 DOM 裡量出來的。所以重新渲染一遍，出來的幀是完全一樣的。影片生成模型做不到這一點，同一個 prompt 跑兩次給你兩個東西。

**可編輯性。** 任何一個鏡頭出問題，agent 改一個 `SCxx.tsx` 檔案裡的一個數字，重新渲染。影片生成模型做不到這一點，你只能重新生成整段，而且不保證這次更好。

**可追溯性。** 畫面上每個數字都能追到調研文件裡的一個 URL。因為畫面本來就是從那份文件「畫」出來的。

**可驗證性。** 這是最被低估的一條。因為畫面是程式碼，所以可以靜態分析。`selfcheck.py` 能在不渲染的情況下，掃描所有鏡頭原始碼，數出有幾處閃爍、把它們和分鏡表裡的白名單對帳、把所有會上畫面的字面值抽出來和事實清單對帳。這三件事幾秒鐘跑完，而 QC agent 是從像素裡查的，看不到沒被抽到的幀。作者在 `lessons.md` 裡說得很直接：這三個檢查抓到的都是 QC 從像素查不到的問題。

### 2.3 一個反直覺的判斷

很多人第一反應是「AI 畫影片應該用生成模型，程式碼渲染是老派做法」。作者用一組資料反駁了這個判斷。

他拿自己用 skill 做的《eCPM 與廣告競價》和樣片《RAG 與知識庫》逐幀對比，兩片動效數量、節奏、柔光總面積幾乎完全相同：

| 指標（成片逐幀，內容區） | 廣告競價 | RAG 樣片 |
|---|---|---|
| 每幀平均變化量 / 動效事件每分鐘 | 0.47 / 72 | 0.56 / 76 |
| 最大物體高度中位數 | 172px | 219px |
| 最大物體 <110px 持續 ≥1.5s 的時長占比 | 29% | 12% |
| 原始碼光效詞 halo / sweep / ghost | 0 / 0 / 0 | 14 / 12 / 5 |
| 原始碼 skew / perspective / rotate | 1 / 0 / 4 | 7 / 1 / 15 |

差距全在「畫多大、誰發光、高光時刻怎麼編排」這三件事上，跟「動得多不多」沒關係。

這解釋了一個很多人會踩的坑：初版 skill 寫了安全區、白名單、歸零、節拍這些紀律項，新片在這些項上甚至做得更好，但「主體該畫多大、光該打在誰身上」只在做樣片的那個人腦子裡。結果就是畫面小而暗、四輪 QC 全過還是難看。

修法不是加動效，是加硬規則。這是 `composition-and-light.md` 存在的全部理由。

## 三、詳細教學：從零跑通一條片子

下面是完整的 9 階段流程。階段 0 到階段 8，加上穿插其中的 4 個確認點。

### 3.1 階段 0：建專案（5 分鐘）

```bash
git clone https://github.com/Vincentwei1021/anything2explainer.git
ln -s "$PWD/anything2explainer" ~/.claude/skills/anything2explainer   # Claude Code
ln -s "$PWD/anything2explainer" ~/.codex/skills/anything2explainer    # Codex
```

依賴：

```bash
# Node ≥18（模板的 npm install 会装 remotion 4.0.507 / react 19）
brew install ffmpeg          # 抽帧 / 转码，必需

python3 -m venv ~/.venvs/a2e && source ~/.venvs/a2e/bin/activate
pip install 'edge-tts==7.2.8' numpy pillow scipy   # edge-tts 必须锁版本
```

`edge-tts` 那個鎖版本不是強迫症。README 裡寫得很清楚：它追蹤一個微軟的端點，跨版本會壞，7.2.0 之後需要顯式請求詞邊界。`scipy` 只有 `frame_metrics.py` 用得到。

只做英文片的話再裝 `kokoro soundfile` 和 `espeak-ng`。

樹莓派和 ARM 機器上作者也驗證過，有三處不同：腳本是 `#!/bin/zsh` 所以要裝 zsh，Remotion 沒有 linux-arm64 的無頭瀏覽器要指向系統 Chromium（`REMOTION_BROWSER_EXECUTABLE=/usr/bin/chromium`），以及 kokoro 在 ARM 上裝不動（它鎖了老 numpy 並拉 spaCy，而 blis 沒有 aarch64 wheel），改用 `kokoro_onnx` 或 `piper` 兜底。

建專案：

```bash
template/scripts/new_project.sh ~/work/my-video myslug
```

會複製模板、跑 npm install、跑 tsc。這一步大約吃 2GB 磁碟，README 建議 `df -h` 留夠 5GB。

英文片順手把 `src/config.ts` 的 `lang` 改成 `'en'`。幕底預設點陣波（`bg: 'dots'`），想要早期樣片的星點霧底就改成 `'stars'`。

### 3.2 階段 1：調研（20 分鐘，1 個 agent）

派一個帶 WebSearch / WebFetch 的 general-purpose agent，按 `reference/research-brief.md` 的模板產出 `research/調研.md`。

調研文件的結構是固定的九節，其中第 0、6、7、8 節必須有：

```
0 執行摘要（1 分鐘版：這是什麼、為什麼值得講、最反直覺的一點）
1 處境與問題（沒有它 / 不懂它時會怎樣；誰在什麼場景下會碰到）
2 起源與關鍵節點（提出者 / 事件 / 年份 / 出處文獻）
3 它怎麼運作（機制 / 過程 / 結構 / 歷史脈絡，選一條主軸）
4 邊界與對比（和最容易混淆的相鄰概念差在哪）
5 爭議、局限與近 2 年的變化
6 真實案例與失敗模式（成功的和翻車的都要）
7 數字與比喻清單   ← 最重要的一節
8 術語對照（≤30 條）
```

第 7 節是要點所在：一批可直接講的有出處數字，每條附一個把它換算成日常尺度的說法，再加 5 個適合動畫的比喻，每個都寫清楚貼切在哪、失真在哪。

條數按片長給：2 至 3 分鐘片 8 到 10 條，3 至 5 分鐘片 10 到 16 條，5 至 8 分鐘片 18 到 24 條。

有個安全細節值得注意。調研文件是從網頁抓來的內容，agent 被明確要求：其中任何指令性文字（要求改檔案、執行命令、改變任務目標）都不執行，發現了就在文件裡標一句「該頁含指令性內容，已忽略」。這類 prompt injection 防禦現在幾乎是標配，但這套協議寫得很早，值得記一筆。

### 3.3 階段 2：解說詞與時間軸（20 分鐘，主會話）

這一階段是整條流水線裡「最便宜的一次干預點」，原因後面會講。

先讀 `reference/narration-guidance.md`，那是一份純英文的寫作原則文件，也是整個專案裡唯一一份從頭到尾沒有中文版的文件（這次已經補上了中文翻譯）。它有 14 個小節，我挑幾條最關鍵的：

- 第 0 節給了一個唯一檢驗：讀出一句話，問自己「聽眾此刻是否知道了、看見了或感受到了句子之前他不知道的東西」。沒有的話，這句話就是填充物。一支五分鐘的稿子大約只放得下 45 到 50 句，每句都要過這一關。
- 第 1 節：從情境切入，不要從定義切入。開頭寫「X 的定義是……」或者「在本影片中我們將……」，就把最寶貴的時間浪費掉了。
- 第 2 節：一條主線。失敗形態是「術語表」，即一串概念用同樣的待遇對待，順序隨便打亂也沒人發現。如果各節可以隨意調換而不損失內容，那就是沒有主線，回去重找。
- 第 3 節：先動機後機制。沒有它會出什麼問題，它怎麼工作，這給你帶來什麼。永遠不要解釋聽眾還不想聽的機制。
- 第 5 節：比喻是工具不是裝飾。一個好比喻貫穿幾個節拍，勝過六個只用一次的聰明比喻。
- 第 11 節：說出畫面說不出來的。旁白負責理由、後果、比較和判斷，畫面負責結構、順序和數量。只描述畫面上有什麼的句子直接刪。
- 第 13 節：在接縫處交接。上一節的末尾要留下一個問題、代價或缺口，下一節的第一句先回指上一節的成果再開題。「接下來我們看 X」這種只報幕的過渡要刪。

解說詞格式長這樣：

```
# CHAPTER 1 章名（≤6 字，進度條章名）
一句話|按豎線切成字幕塊|每塊 ≤16 字        ← 一行一句
同一段的下一句                                ← 段內句之間只隔 10 幀
                                              ← 空行 = 段落分隔：一段 = 一個鏡頭
新的一段（= 下一個鏡頭）
## gap 20                                     ← 可選：額外插空白
```

豎線只切字幕，不影響朗讀。空行是鏡頭邊界，這一條是全片結構的地基。

樣片的解說詞開頭是這樣的，可以直接感受一下節奏：

```
大模型很聰明|但它有三個天生的短板
第一|它的知識有截止日期|訓練之後發生的事|它一概不知
第二|它讀不到你公司內網裡的文件|也不知道你昨天剛寫的會議紀要
第三|遇到不知道的問題|它不會說我不知道|而是一臉自信地編一個答案|這就是幻覺
怎麼辦|重新訓練一遍|成本太高|而且明天資料又變了
於是工程師們想出了一個辦法|讓模型開卷考試
考試前先把資料整理成一本手冊|答題時先翻手冊|再作答
這套方法就是今天的主角|RAG|檢索增強生成
```

注意它沒有一句在介紹概念，全部在講處境。

確認點 2 就是在這裡：把解說詞全文、章節劃分、字數和預估時長貼給使用者，問「這版文案可以嗎」。章名和 HUD 小節名單獨列一行，因為進度條上就這幾個詞，作者還給了個自檢三問：只看這幾個詞，沒看過片子的人能說出每章講什麼嗎？每個都是名詞短語嗎？連起來是不是一條看得懂的主線？

作者專門寫了反例。第六片被使用者點名，進度條章名是「感覺還行 / 搭台留痕 / 兩把尺子 / 診斷與證明」，這是評價句和俏皮話，觀眾瞄一眼猜不出內容。正例是樣片的「為什麼要RAG / 知識庫建構 / 檢索與生成 / 評估與進階」，抄出來給沒看過片子的人，他也能說出每章講什麼。

確認點 3 緊接著問一句「配音有沒有偏好的 TTS」。沒有就用預設：中文 edge-tts `zh-CN-YunxiNeural`（雲希，男聲，原速不加速，約 5.5 字/秒），英文 kokoro-82m `am_liam`（Liam，男聲）。有偏好就用自己的 TTS 生成成品 wav 放進 `public/assets/<slug>/audio.wav`，再手填 `src/common/timeline.ts` 和 `subs.ts`，後續流程完全不變。

然後跑配音：

```bash
python3 scripts/tts_build.py
```

它逐句合成，用 WordBoundary 切出字幕塊，輸出配音 wav、幀級時間軸和字幕表。停頓策略寫在腳本裡：段內句間 10 幀，段末再加 20 幀，章前 45 幀。

**停頓只放在段末，不放在每句之後。** 這一條是使用者回饋逼出來的，加每句都停會讓整片顯得拖。段末 30 幀差不多 1 秒，觀眾覺得「這句話講完了，畫面也落位了」，然後才切。

腳本還會在終端列出末塊不足 45 幀的段末句，帶 `¶` 標記。那些句子後面要加 `## gap 15-30`，或者在分鏡時把末拍元素前掛到上一塊。

跑完核對成片時長是否落在使用者要的區間，差超過 15% 就加刪句子重跑，別靠改語速硬湊。

然後就凍結。定稿之後不再改詞，因為每個鏡頭的幀號都硬編碼在建構組的程式碼裡，改一個字就要全片重對位。

### 3.4 階段 3：分鏡（25 分鐘，主會話）

寫 `script/storyboard_src.md`，用令牌代替幀號，然後渲染成 `分鏡表.md`：

```bash
python3 scripts/render_storyboard.py
```

令牌長這樣：`{S12.from}` `{S12.to}` `{S12.c3}`（第 3 個字幕塊起始幀）`{C2}`（第 2 章起始幀）`{TOTAL}`，可以帶偏移，比如 `{S12.from-8}`。

每個鏡頭一行，欄位是：鏡頭 / 幀 / 節拍 / 畫面 / 動效 / **主角·尺寸** / **光**。

後兩欄是後加的，這也是最值錢的一次改版。原來分鏡表只有「畫面」和「動效」，建構組就不知道該把主體畫多大、光該給誰，結果主體中位高度只有 172px，主角全是無光白線框。補上這兩欄之後，樣片是 219px。

動效欄每行末尾必須有「持續：…」和「停留：…」兩句：

- **持續**：這個字幕塊的動詞靠哪個動作撐到下一拍（資料流、脈衝光點沿箭頭跑、逐行打字、逐格點亮、生長、旋轉、閘門開合、佇列壓緊）。沒有其它運鏡的鏡頭寫「1.0→1.05 慢推」。**不寫漂浮、飄動、呼吸。**
- **停留**：末拍元素落位幀到離場起點的幀數，≥30，目標 30 到 45。不夠的三選一：末拍元素前掛、回文案加 `## gap`、併入相鄰鏡頭。

分鏡表末尾的「全域約束」要寫七塊內容：示例語境、事實清單、閃爍白名單、複用圖元清單、章界清單、高光時刻清單、掃光白名單，外加 §9 持續動作與落位停留的規則全文。

### 3.5 階段 4：覆蓋層與圖元（10 分鐘，主會話）

模板自帶片頭、章節卡、HUD、流程軌、片尾，圖元庫在 `src/ui.tsx`，光效和運鏡圖元在 `src/fx.tsx`。你只需要按主題補 2 到 5 個語意圖示進去。

樣片補的是 `DocIcon`（文件）、`DBIcon`（資料庫）、`ChunkCard`（文字塊）、`LLMIcon`（大模型）。

然後出一張 still 看一眼：

```bash
scripts/still.sh Overlay 40,<章节卡帧>,<有轨帧>,<片尾帧> <绝对路径> ov
```

### 3.6 階段 5a：打樣（15 分鐘，1 個 agent）

只派 G1（第 1 章上半），完工後渲前 30 秒：

```bash
scripts/preview.sh 30
```

這是確認點 4。使用者要改的東西（配色、字號、語速、片頭、示例語境）在這裡一次改完。

作者對這一點的判斷非常清醒：在這裡改一次是 1 個組的成本，等整片渲完再改是全部組的成本。

### 3.7 階段 5b：並行建構（40 分鐘，其餘各組各 1 個 agent）

組數按片長定，樣片檔 8 組，派 G2 到 G8。每組 5 到 7 個鏡頭，一個鏡頭一個檔案 `src/shots/Gn/SCxx.tsx`。

派單用 `reference/prompts.md` 的建構 prompt，附 `reference/agent-build-rules.md`，而且要把 G1 作為已驗收的風格樣例點名讓它們讀。

這裡有幾個硬約束，是建構協議裡反覆強調的：

- 幀號 `N = useCurrentFrame() + F0`，所有動畫是 N 的純函數，隨機只用 `rnd()`，禁用 `Math.random`，不要用 useState / useEffect 做動畫。
- 只能改 `src/shots/Gn/**`，不碰 Main / Root / common / 別的組。
- 硬切前離場必須歸零：用 `opacity = 1 − (n/N)^1.5`，不能用每幀 6.7% 的 exitFade（末幀還剩 40% 到 60% 會「啪」）。
- 入場軌跡不得穿字幕帶：自下滑入 Δ ≤ 120，要從畫外進來就用側向滑入 Δ 260 到 320。
- 效能紅線：禁 `feConvolveMatrix`，`filter: blur()` 的 σ ≥ 1，單幀 DOM 節點 ≤ 600，SVG filter 實例 ≤ 6。違反會讓整片渲染慢 10 到 50 倍。
- 完工前必須跑 `npx tsc --noEmit`、每鏡頭至少出 6 張 still、30 幀測渲，以及 `python3 scripts/motion_check.py <Gn>`。

最後這條是最新的，量化的是持續動作和落位停留：每鏡頭最長靜止 ≤3 秒，末拍穩定期 ≥30 幀。

### 3.8 階段 6：渲染（5 分鐘）

```bash
npx tsc --noEmit
VER=v1 scripts/render.sh
```

8000 幀約等於 4 分半片長，渲 3 到 4 分鐘，concurrency 6。產出 `renders/<slug>_v1.mp4` 加 `fin_frames/`。

然後主會話自己拼 6 張 contact sheet 通讀一遍，再跑：

```bash
python3 scripts/frame_metrics.py --out qc/frame_metrics_v1.md
```

這一步量的是：每鏡頭最大物體高度、主角區柔光面積、紫色碎片指數、靜止段。

### 3.9 階段 7：QC 與修復（60 到 90 分鐘）

每章 1 個 QC agent，按 `reference/agent-qc-rules.md` 跑，輸出 `qc/qc_v1_Cn.md`。按組派修復 agent，一個 agent 只修一到兩組。

渲 v2，2 個複驗 agent 逐條核 v1 的問題加回歸通讀，小修，渲 v3。

終檢要做四件事：閃爍白名單掃描、掃光白名單核對、frame_metrics 構圖與光複核、motion_check 成片複測。

作者反覆強調一件事：**組級 motion_check 過了不等於成片過。** 第四片 v1 組級 48 個鏡頭全部達標，成片複測卻有 11 個鏡頭超限，3 個是真靜，8 個只有小面積動作。原因是組級是低解析度渲染，讀數偏鬆。所以流程裡成片複測是必須的，不能省。

### 3.10 階段 8：交付

產出 `交付說明.md`：成片、配音來源、事實出處、示例語境、質檢結論、已知保留項、目錄。片尾預設署名 `built by Anything2Explainer skill`，`config.builtBy` 設成空字串可以去掉。

然後把新經驗寫回 `reference/lessons.md`。這一條讓整個倉庫變成一個持續學習的系統，前面五部片的教訓都還躺在那。

## 四、多 agent 分工協議：一條片子要開多少個 agent

這是整個專案裡最「工程」的部分，也是別人照搬不走的東西。

### 4.1 六種角色

`reference/prompts.md` 定義了六種 agent prompt 範本，加上 `research-brief.md` 和兩份規則文件，一共八份文件構成了完整的調度協議。

| 角色 | 數量 | 職責 | 產出 |
|---|---|---|---|
| 研究員 | 1 | 帶 WebSearch/WebFetch 查證事實 | `research/調研.md` |
| 建構組 | 8（樣片檔） | 每組 5–7 個鏡頭，一個鏡頭一個檔案 | `src/shots/Gn/**` + `BUILD_NOTES.md` |
| QC | 每章 1 個 | 按書面判據逐幀檢查 | `qc/qc_vN_Cn.md` |
| 修復 | 每 1–2 組 1 個 | 修 QC 報告裡的條目 | 程式碼 + BUILD_NOTES 追加小節 |
| 複驗 | 每兩章 1 個 | 核 v1 問題是否真修好 + 回歸通讀 | `qc/qc_vN+1_recheck_C**.*.md` |
| 終檢 | 1 | 閃爍合規、掃光白名單、frame_metrics、motion_check 成片複測 | `qc/qc_vN_final.md` |

### 4.2 派單的第一條紀律：一個 agent 只派一件重活

作者在 `lessons.md` 裡寫死了這條：建構 5 到 7 個鏡頭算重活，QC 一章算重活，修 1 到 2 組算重活。第二件只派輕活。

理由是他踩過坑：讀過大量圖片的 agent 再派重活，有大約 30% 的機率直接陣亡，回報 "input too long"。

這跟另一個常見誤區正好對著：QC agent 被要求「邊查邊 append」到檔案，不是建議，是硬要求。有一片一個 QC agent 攢到最後寫盤，跑了一小時零產出、訊息也不回，只能 TaskStop 重派。理由很簡單：如果它中途被打死，前面積累的結論全丟了。

### 4.3 併發上限：pane 是全機共享的

這是最反直覺的一條。作者在第三片踩到：pane 上限比上次更早撞上，同時開著 14 個其他會話，派的第 5 個 agent 就 `respawn pane failed: fork failed: Device not configured`。

修法是按 4 個一波派，一波完成並釋放後再派下一波，派單前先 `ListAgents` 看全機佔用，預留 1 到 2 個 pane 給後面的 QC 和修復輪。

這一條在 Claude Code 和 Codex 裡都是一樣的，作者在 prompt 範本末尾專門寫了一段「派單與看門狗」：完成的 agent 適時 TaskStop 釋放，被 API 錯誤打死的先 SendMessage 叫一次，10 分鐘零產出就 TaskStop 重派（重派時明確告訴它「複用磁碟上的半成品，只補未完成部分」），每 30 到 40 分鐘核一次各組 index.ts 和 BUILD_NOTES 的 mtime。

### 4.4 不要照抄 agent 的自評

作者抽驗過一個組的自評：「中間年份模糊不可讀」——實際出圖清晰可讀，那個組自己在複盤時也承認這條自評過於樂觀。

但他的結論不是「agent 會說謊」，而是兩句一起說：報告要抽驗，但也別急著斷定 agent 說錯了，先把證據看全。另一條他查下來是自己誤讀，報告其實是對的。

### 4.5 建構組會發現分鏡表本身的錯

這是作者最看重的資產之一。第三片最有價值的三條改進全部來自建構組：價值柱公式與畫面標註矛盾、年份轉盤的事實合規漏洞、以及據此主動偏離不給毫秒數做計數。

他的處理方式是：一條一句話裁定，然後把裁定推廣成全片通則寫回分鏡表，而不是只批准這一個單點改動。

配套的還有一條硬性要求：建構組合理偏離（換示例文字、加中文全稱、改拓撲）只要有出處就放行。

### 4.6 主會話自己也要做靜態檢查

作者不滿足於只靠 QC。他自己保留三項不渲染就能跑的檢查：幀覆蓋靜態分析（幀區間空洞與重疊）、原始碼字面值與事實清單對帳、閃爍白名單原始碼級計數。

這三項幾秒鐘跑完，抓到的全是 QC 從像素查不到的問題。第四片裡，原始碼對帳一次性抓出一個即時計數器——畫面上顯示「本秒 +2405」，正下方灰小字寫「一天幾十億次」，兩者差 30 倍，四個 QC agent 全漏了。

## 五、歸納總結：這個專案的核心觀點

讀完整套協議，我把它的觀點歸納成七條。

### 觀點一：AI 創作的品質瓶頸不在生成能力，在規範

這個專案所有 agent 的產出品質都很依賴規範密度。`reference/` 下面十一份文件，加上範本裡的一百多個組件和函式，程式碼量其實不大，規範的體量比程式碼還厚。

對照 `lessons.md` 裡的記錄就能看出規範的作用：初版 skill 有安全區、白名單、歸零、節拍這些紀律項，新片在這些項上做得比樣片還好，但「畫多大、誰發光」沒寫，新片就小而暗。規範裡沒寫的東西，agent 不會自己想到。

### 觀點二：確定性和可編輯性比畫面驚豔更重要

第 2.2 節已經展開過了。核心是：因為畫面是程式碼，所以能靜態分析、能精確修一幀、能追到來源。這三條加起來，比「這一幀很好看」值錢得多。

一個直接的推論是：不要用生成模型做這個活。

### 觀點三：約束要寫在明面上，不要指望 agent 領會

「全片一個貫穿示例」、「每鏡頭一個主角」、「每鏡頭最多一處閃爍」——這些不是建議，是硬規則，而且要能被機器檢查。

`selfcheck.py` 存在的意義就在這兒：它把「閃爍白名單」從一句口號變成了一次計數對帳。白名單裡有 23 項，腳本掃出來必須正好 23 處，多一處少一處都算問題。

作者舉過一個反面例子：分鏡表裡「glitch」這個詞如果只寫在一格，建構 agent 會給所有文字加閃爍，成片出來 102 處，使用者直接否決。後來改成「每鏡頭最多 1 處 glitch，只給該鏡頭的重點詞」，降到 21 處才過。

### 觀點四：敘事品質取決於有沒有主線，不取決於資訊量

`narration-guidance.md` 第 2 節和第四片的複盤是同一件事的兩面。第四片第一版 48 句按參考書的小節順序寫，使用者第一反應是「太死板無趣」；按寫作原則獨立重寫的版本盲評 8.2 對 4.3。

根因不是文筆，是沒有主線。章可以隨意調換順序而不損失，那就是沒有主線。

這裡有個值得學的做法：作者把「怎麼寫得不無聊」從「分鏡規範」裡拆出來，單獨成了一份 `narration-guidance.md`，並且在 SKILL.md 裡規定階段 2 必讀。`narration-storyboard.md` 不再規定固定章法，只保留格式、預算和畫面介面，鏡頭模式表的左列也改成題材無關的「畫面關係類型」。

**規範要按抽象層級放對位置。** 敘事原則是通用的，掛在具體題材的範本下面就會被當成範本。

### 觀點五：先定稿再配音，因為幀號會被硬編碼

這是整條流水線裡最反直覺的工程決策，也是四個確認點的設計依據。

一旦配音定稿，幀號就寫進了每個鏡頭的程式碼裡。改一個字 = 全片重對位 = 所有建構組重跑。所以作者把確認點 2（解說詞定稿）放在配音之前，並且在 README 裡說得很直接：這是全流程最便宜的一次干預點。

反過來說，第一、第二個確認點比第三、第四個更值錢。第一個（時長與語言）決定了句數、鏡頭數、建構組數，也就是這條流水線的規模；第二個（文案定稿）決定了一旦錯了要重跑多少。

### 觀點六：量化判據要分清「組級」和「成片」

第四片留下的教訓：組級 motion_check 48/48 全部達標，成片複測 11 個鏡頭超限。

低解析度渲染讀數偏鬆。作者的修法是把組級渲染改成 0.5 倍加 JPEG q80，並讓 `--frames` 模式多給一列「最長靜止段內全解析度變化像素數」，用來區分真靜（<800）和小面積動作（800–2500）。

還有一條更細的：小面積動作的修法是**加大幅度**，不是加元素。運動元素更亮更大更密、主角本體 30 幀呼吸 ±2%，而不是往上糊更多小圖示。

這個區分很關鍵。「給靜止的物體加漂浮、飄動、呼吸」是明確禁止的，作者給的理由是：動作必須是動詞本身的動作，找不到動詞動作的鏡頭寧可靜著，靜止 ≤3 秒不是缺陷。

### 觀點七：教會 agent 之後，還要教它怎麼被考核

這一條我覺得是最容易被忽略、也最有價值的。

作者不滿足於「讓 agent 寫程式碼」，他給 agent 寫了判據、寫了量化腳本、寫了終檢清單、寫了「每個鏡頭至少給出一行結論（OK 也要寫）」這種看似機械的要求。

甚至有一條是關於反例的：`examples/contrast/` 裡放了 6 組反例幀，建構 agent 開工前必須先用 Read 看 `contrast_sheet.jpg` 和至少 6 張 `ref_*.jpg` 建立標尺。

這是把「品味」變成「可傳遞的參照物」。品味沒法寫進 prompt，但可以給一組對照幀。

## 六、設計哲學拆解

把散落在各處的原則歸攏一下，這個專案的設計哲學大概是這七條。

### 6.1 顏色即語意

調色盤裡每一個顏色都有固定含義，沒有一個是「好看」就用了：

| 顏色 | 值 | 語意 |
|---|---|---|
| PURPLE | #6630F8 | 當前重點 / 啟用 / 品牌 |
| ORANGE / CORAL | #F05F41 | 指標數字、警示、「另一方」、查詢點 |
| RED_DEEP | #EC081F | 深紅警示區塊（幻覺、不靠譜） |
| GREEN | #8FF740 | 綠勾（正確） |
| GREY 系 | #A0A0A1 起 | 非重點文字、灰塊、網格線 |

規則是「一幀裡紫色重點不超過一處大面積」。配色不是審美問題，是資訊問題。

### 6.2 光只給當前的主角

主角必帶光（`GLOW_PURPLE` 雙層紫柔光，或腳下 `HaloRing`，或大字紫硬投影 `6px 6px 0 PURPLE`），配角不發光。

光有三個層次：白 bloom（結構線條常駐）< 紫柔光（主角常亮 + 當前重點）< 白閃（事件，3–6 幀）。全片只用這三種，光的顏色只用紫、橙、紅。

還有幾條精細的規則：主角光 30 幀週期呼吸 ±15%；重點轉移時前一處的光 8 幀內滅掉；離場時光先滅（6 幀）再整體淡出，不要帶著滿光硬切。

### 6.3 三檔尺寸，不容第四檔

主角 ≥170px 或大字 ≥96px 且整行寬 ≥300px；配角 60–110px；標籤與說明 22–30px。配角 ≤4 個，標籤 ≤6 個。

「三檔之外不再有第四種尺寸」這條約束的價值在於，它自動淘汰了「這個圖示要不要稍微放大一點點」這類無窮的微調。

配套的判據是空場：內容區最大物體高度 <110px 持續 >45 幀是中度缺陷，<80px 持續 >45 幀是重度。

### 6.4 掃光是最貴的一招，全片最多兩次

三輪紫光橫掃 + 舞台光線 + 幽靈輪廓這套登場型編排，是全片最貴的視覺效果，作者給的預算是 **≤2 處**：核心概念首次登場必有 1 處，第 2 處可選給結尾回扣。

理由是使用者回饋。第五片 47 個鏡頭用了 8 處三輪掃光，使用者看成片說「太頻繁」。樣片 44 個鏡頭只用了 1 次。

分鏡表裡為此單列一個「掃光白名單」，不在名單裡的鏡頭一律不用 `LightSweep` / `StageLine` / `GhostText`，`selfcheck.py` 按檔案計數，終檢按幀核對。

這是一個很值得學的設計：與其在 prompt 裡說「少用閃亮效果」（模型聽不懂），不如給一個硬配額和一張白名單。

### 6.5 持續動作 + 落位停留

這是全專案最晚成型、也最重要的運動學規則，它對應兩種相反的失敗：

- **「入場即停」**：元素按節拍進來就停著等下一拍，只有柔光呼吸。第四片量化後：4/6 鏡頭靜止幀 42% 到 72%，最長靜止 2.8 秒。
- **「落位即切」**：按「不許靜止 >30 幀」修過了頭，47 鏡頭 34 處推近、48 句「持續」，末拍元素剛落位就進入末 8 幀離場。使用者原話是「所有動畫剛剛落位，馬上就切到了下一個鏡頭，幾乎沒有停留」。

規則一是**持續**：每個字幕塊講的動詞，畫面上要有一個持續到下一拍的動作；元素入場後不許完全靜止超過 3 秒（90 幀）；但**不為湊指標給靜止的物體加漂浮、飄動、呼吸**。

規則二是**停留**：每個鏡頭末拍元素落位後要有 30 到 45 幀（1 到 1.5 秒）穩定期再離場。穩定期內不新增元素、不運鏡、不換 HUD，已在跑的動詞動作可以繼續。運鏡不進末拍。

時間從哪來？使用者裁定的：允許成片比純語音長 5% 到 8% 換停留。停頓只放在段末，不放在每句之後。

作者在文件裡把這套規則和它的量化腳本 `motion_check.py` 一起交付，而不只是寫在規範裡。

### 6.6 銜接要寫清兩側

作者踩過一個很典型的坑。如果分鏡表只寫「硬切」，兩邊會各自理解成「我不動、你從節拍幀才入場」，結果組界出現 6 到 8 幀空場，一片裡 5 處。

所以規定寫法是：「A 末 8 幀歸零淡出 + 輕微下搖；B 首幀起首批元素 SoftIn」。

配套的還有承接優先於清場：一個節拍講完的短句跟在前一鏡頭裡，用承接位移 16 幀讓位，不要為它清場重畫。

章界更嚴格：章首第一個鏡頭必須承接上一章末鏡頭的主角或象徵物（同組件同參數，可縮小移位），解說同時要承上啟下。作者給的反例是「章首從零起頭」和「章首只報幕」，兩者的區別是：報幕不要，承上啟下要。

### 6.7 事實合規是審美問題

這一條最有意思。表面上是 QC 規則，實際上是設計哲學。

作者的判據是：畫面上出現的每個數字都必須能追到來源。帶來的直接設計後果是：

- 計數動畫的中間值也是「上畫面的數字」。年份 1995→1998 線性計數會讓 1995、1996、1997 清晰可讀 4 到 6 幀；毫秒 0→120 會閃出「37 ms」「88 ms」。這些都不在事實清單內，所以要嘛讓它不可讀，要嘛不做計數。
- 讓年份不可讀要夠狠：blur 6.3→1.3px 中間年份仍清晰可讀；12→2px 時倒數第二個年份仍可辨約 2 幀；最終 12→9px 全程 + 落定幀歸 0 才乾淨。作者把這封成了範本裡的 `YearRoll` 組件。
- 範例數據（型號、相似度分、金額）在交付說明裡標「示意值」。

這不是在為難作者自己，這是在保護觀眾。影片沒辦點擊來源，沒辦核對，觀眾只能信你。

## 七、局限、質疑與後續看點

### 7.1 三個我要先說清的現實限制

**第一，它不是一個「輸入主題就出片」的產品。** 它需要人（或者說需要一個 agent 主會話）在四個點上做決策：時長與語言、解說詞定稿、配音引擎、前 30 秒樣片。四個確認點一個都省不掉，作者也沒打算省。

從「給你一個輸入就能拿到成片」的角度看，這離產品還很遠。但從「讓 agent 獨立完成一條片子」的角度看，這已經很遠了。

**第二，成本不低。** 樣片檔 8 個建構組並行 40 分鐘，加兩輪 QC 60 到 90 分鐘，整條流程約 2 小時，磁碟 2GB 起。而且這還是在你自己已經有 Remotion 熟練度的前提下。

**第三，授權是個坎。** PolyForm Noncommercial 1.0.0，非商用免費，商用要事先獲得作者授權。做科普、教學、個人專案沒問題，想用在商業產品上得先談。

### 7.2 我認為最值得追問的兩個問題

**第一個問題：這套方法在沒有作者在場的機器上能重現嗎？**

整個倉庫的語氣是「一個人做了一條又一條片，每次踩坑就寫回 lessons.md」。協議的完備性高度依賴這些踩坑記錄，而它們是 2026-09-07 到 09-10 之間四天裡攢出來的。

這種「經驗沉澱型」文件的優點是每一條都有真實返工支撐，分量足；風險是它只在作者那台機器、作者那套 Claude Code 設定、作者那個 pane 上限的環境裡被驗證過。README 說「Linux 應該能行，Windows 未測試」，樹莓派跑通了，這已經算誠實的交代，但畢竟不是「任何人任何機器都能跑」。

**第二個問題：這條流水線的瓶頸到底是什麼？**

作者把所有注意力放在了「讓畫面變好」上——主體尺寸、光、高光時刻、掃光配額、持續動作、落位停留，全是視覺。但他自己却在 `lessons.md` 裡承認過一件更有意思的事：

> 風格傳遞（2026-09-08 複盤）：skill 寫了禁令沒寫審美驅動……但「畫多大、誰發光、高光時刻怎麼編排」只在做樣片的人腦子裡。

也就是說，他花了大量篇幅治「AI 畫面做得爛」這個症狀，動了兩年。但從 `lessons.md` 的整體結構看，**真正稀缺的不是審美規則，是「怎麼把一個人的審美判斷拆成可傳遞、可檢查、可迭代的形式」這套方法論**。這個專案目前是在這個方向上的一次成功嘗試，而不是一套已經成熟的通用方法。

一個旁證是他自己的複盤結論：「差距不在『動得多不多』，別往加動效的方向修。」這句話的價值在於它是一個否定性判斷——排除了一個方向，而不是給出了一個方向。真正難的是找到該往哪修。

### 7.3 後續可以期待什麼

- **直式螢幕。** README 明確說不支援 9:16，範本和所有安全區規則都假設 1280×720 橫式。短影音平台基本都是直式，這是最明顯的一塊空白。
- **更多語言。** 現在只支援中英，各有一套語速模型、字幕預算和預設音色。`lang` 欄位的架構留了擴充口子。
- **更高品質的 TTS。** 現在的路徑是「自帶 TTS」——使用者自己生成成品 wav，手填時間軸。作者明確說了預設的 edge-tts 和 kokoro「夠用但不是最好」。這意味著整條流水線對語音複製、強制對齊這類技術是開放的。
- **反例庫的擴充。** `examples/contrast/` 現在只有 6 組，而且正例全部來自同一部片（樣片）。多幾部不同題材的正例，對傳遞審美標準會有幫助。

### 7.4 那個最值得學的設計決定

如果只能從這個專案帶走一樣東西，我選這個：

**把「品味」變成「參照物 + 判據 + 計數器」三件套。**

- 參照物：`examples/contrast/contrast_sheet.jpg` 裡的 6 組正反例幀，agent 開工前必須看。
- 判據：`composition-and-light.md` 裡的尺寸三檔、光的歸屬、空場閾值、掃光配額。
- 計數器：`selfcheck.py` 數閃爍白名單，`frame_metrics.py` 量主體高度和柔光，`motion_check.py` 測靜止時長。

單靠前兩樣，agent 會理解但會走樣。加上第三樣，偏差會被立刻發現。

作者在第四片結尾給了一個很實在的觀察：當一組 agent 反饋「中間年份模糊不可讀」時，實際出圖清晰可讀。他沒有把這當成 agent 不可靠，而是把「從原始碼靜態抽取所有會上畫面的字面值，和事實清單對帳」補成了一個檢查步驟。

**這就是一個能持續改進的系統該有的樣子：每次失敗都變成一個新的檢查項，而不是一次性的抱怨。**

## 八、一句話總結

anything2explainer 把「讓 AI 做一條科普講解影片」這件事，從一個提示詞問題變成了一個工程問題。

它不生成像素，它生成確定性程式碼；它不靠模型領會審美，它靠參照物、判據和計數器傳遞審美；它不指望 agent 一次做對，它把每次返工寫進 lessons.md 變成下一片的檢查項。

對一個想做技術內容的人來說，這個倉庫最實用的可能不是那 9 個階段，而是那 11 份 `reference/` 文件裡攢下來的東西：主體該畫多大，光該打給誰，高光時刻怎麼排，掃光最多用幾次，停頓該放在哪，為什麼「入場即停」和「落位即切」都是缺陷，以及怎麼用三個幾秒鐘跑完的腳本，去檢查 agent 到底有沒有做到。
