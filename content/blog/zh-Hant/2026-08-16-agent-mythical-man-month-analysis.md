# 《人月神話》的 2026 重讀：為什麼加十個 subagent 一小時做完，和招十個人一個月做完是同一個詛咒

## 文章背景與專案簡介

1975 年，Fred Brooks 寫完《人月神話》（The Mythical Man-Month）——他管過 IBM OS/360，那是 1960 年代人類做過的最大一次軟體工程。專案結束後他沒寫技術總結，而是寫了一本關於「為什麼大專案總是延期、為什麼加人只會更慢、為什麼概念完整性是設計的最高目標」的書，成了整個軟體行業的地基。

五十年後，一位署名 meari 的作者在 GitHub 上發布了 **agent-mythical-man-month-2026**（中文名《agent 時代的人月神話》）——以 1995 年二十周年紀念版為底本，**把 Brooks 的每一章在 2026 年的 AI Agent 語境裡重寫了一遍**。這本書/倉庫要回答一個問題：

> 寫程式這件事從「人在鍵盤上敲字」變成「人和一個語言模型對話」，介質發生了根本變化。Brooks 描述的那些老病，在這個新介質上還在不在？

作者的答案是——**全在，而且幾乎每一條都在人機協作的日常裡以新形態重現**：

- 加十個 subagent 一小時做完，跟 1975 年「招十個人一個月做完」是同一個詛咒。
- 開三個平行會話試三種思路，跟 1975 年「多派幾組人試試不同方案」是同一個心理反應。
- 讓 agent 自主完成一整個專案，跟 1975 年「外包給一個獨立小組」面對的是同一個概念完整性問題。

更有意思的是這本書**本身就是它自己論證的一次運行**：一位持有目的的作者加多位 agent 協作完成——Fable 5 寫了每一章的初稿，Opus 4.7 陪著修完十八章，Sonnet 5 完成了英文版和日文版翻譯。專案獲得 129 顆星，正文以 CC BY-NC-SA 4.0 授權，共三語版本（中文/英文/日文）、每語 18 章加一篇序、外加三個 EPUB 合集。

**這篇文章的定位**：先用大白話講清楚這個專案說了什麼，再把它拆成可消化的教學與觀點清單，最後給出不留情面的綜合評價。

## 核心思想總覽：老命題的新形態

序章把 Brooks 原書的骨架拆成**三個骨節**，然後論證這三者在 agent 時代原樣成立：

1. **軟體的困難來自它本身，不來自工具。** 工具一茬一茬換代——組合語言、結構化程式設計、物件導向、敏捷、容器化——每一茬都有人喊「銀彈來了」。Brooks 1986 年的《沒有銀彈》給出通用反駁：軟體的根本困難在概念構造、規格說明、判據裁決這幾層，工具能消滅偶然複雜度，消滅不了本質複雜度。2026 年這句話依然成立：LLM 是很強的工具，但它消化不了上下文裡沒有的東西。
2. **管理軟體的困難，主要是管理溝通與判斷。** 專案一大，最貴的不是編碼和測試，是讓所有人對齊同一個概念。Brooks 花了大半本書討論溝通的組織形式：外科手術隊伍、體系結構師與實現的分離、工作手冊、里程碑與自欺。2026 年變的是判斷在哪裡做出（現在有一部分做出者不是人）、如何被記錄（現在有一部分記錄物是提示詞）、如何被溝通（現在有一部分溝通是 token）——**「判斷需要被組織」這件事沒變**。
3. **文件不是記錄，是決策的載體。** 寫文件的行為迫使上百次細小決定顯形，這些細小決定就是專案的骨頭。不寫文件，決定只在少數人頭腦裡、隨時會消失；寫文件，就是在給專案鑄骨。

合起來一句話：**軟體工程的核心是判斷的組織。技術在變，判斷的組織學問不變。** 忽視這一點的團隊，會用最先進的 agent 系統重演最古老的失敗模式。

### 三代讀者

- **第一代（1975–1995）管人**：幾十人的團隊怎麼組織、進度怎麼估算、如何避免加人陷阱。
- **第二代（1995–2025）管程式碼**：敏捷時代，拿走的是概念完整性、模組化、迭代開發、文件等價於設計。
- **第三代（2024 之後）管 agent**：你不是在管人，也不完全是在寫程式碼，你在**編排一群非人執行者，同時保持整體的一致性**。管理對象是全新的物種，管理原理卻驚人地熟悉——因為 Brooks 討論的從來不是「人」這個物種的特殊性，而是「**多主體協作完成大型概念構造物**」這件事的一般規律。

這本書是寫給第三代讀者的。

## 核心命題一：harness 是狀態機，LLM 是被呼叫的函式

專案最反直覺的一個論斷：**agent 系統的主角不是 LLM，是 harness（託管 agent 的腳手架）。**

「腳手架」這個比喻容易誤導——它讓你以為 LLM 是聰明的大腦，harness 只是給它配了手腳。專案糾正了這個方向：

> 確切地說：harness 是一個狀態機，它負責發起 LLM API 請求呼叫、提供工具、管理上下文。在這個狀態機裡，LLM 是那個被呼叫來給「下一步該做什麼」出主意的函式。它是資源，被狀態機的每一輪消費一次。真正讓 agent 變成 agent 的是那個迴圈，是狀態機每一輪的運轉。沒有那個迴圈，LLM 只是一次函式呼叫；有那個迴圈，才有 agent。

狀態機是電腦科學最古老的概念之一：任何時刻處在某個明確狀態、根據輸入轉移到下一狀態並產生動作。紅綠燈、ATM 機、洗衣機背後都是狀態機。harness 的狀態大致是：等使用者輸入、決定下一步、呼叫工具等返回、呼叫 LLM 等回覆、任務完成。

這帶來兩條反覆使用的推論：

1. **agent 的行為品質是 harness 設計的產物，不只是 LLM 能力的產物。** 同一個模型放在不同 harness 裡表現天差地別——書裡絕大多數關於 agent 系統的判定，判的是 harness，不是模型。
2. **agent 系統的失敗模式很多不在 LLM 那一層，在狀態機那一層。** LLM 說了對的話，但 harness 沒把這句話正確路由；LLM 提出正確的懷疑，但 harness 沒有「接受懷疑」這個狀態。**你換更強的 LLM 也解決不了這些問題，因為它們不在 LLM 那一層。**

## 核心命題二：LLM 沒有記憶，只有上下文——上下文是唯一變數

LLM 每次被呼叫時，看到的只有這次呼叫被塞進去的那段文字。它沒有你的歷史、沒有前幾輪對話的記憶、沒有任何跨呼叫的持久狀態。

「它記得我們前面說過什麼」的體驗從哪裡來？從 harness 裡來。**harness 在每次呼叫前，把對話歷史打包塞進上下文，一起交給 LLM**——使用者感受到「它有記憶」，實際是「harness 每次都替它帶了一份完整的往事簡報」。

由此得到全書最鋒利的定位：

> 所有關於 agent 的技術工作，最終都可以歸結為一個問題：這一次呼叫，該往上下文裡放什麼？

上下文的品質**完全決定**輸出品質。Brooks 的每一條原理在 2026 年的操作含義都是「上下文該怎麼組織」：

| Brooks 的原理 | 2026 年的操作含義 |
|---|---|
| 概念完整性 | 上下文裡的概念不能來自多個互不相識的頭腦 |
| 外科手術隊伍 | 支援角色幫你構造上下文，主刀持有目的 |
| 文件假設 | 文件是上下文的原始碼，程式碼是從上下文編譯出的產物 |
| 里程碑設計 | 停止條件必須在上下文裡顯式表達 |
| 沒有銀彈 | 模型能力再強也解不掉「上下文裡沒有的東西」這個約束 |

## 核心命題三：停機問題——agent 時代的終止判定

這是全書最有理論野心的一章，也是我看來最值得記住的貢獻。

harness 有一個「任務完成」的狀態。傳統狀態機裡，這個狀態由外部訊號觸發（ATM 的「結束」按鈕、洗衣機的定時器）。但 harness 想讓 **LLM 自己決定什麼時候停**——「任務完成了嗎」被作為一次呼叫交給 LLM 回答。這個安排看起來自然，實際上撞上了電腦科學最老的一堵牆：**停機問題**。

圖靈 1936 年證明：沒有程式能獨立、可靠地判斷任意程式（包括它自己）會不會停下。這是自我指涉帶來的**結構性障礙**，跟機器多強、演算法多聰明無關——給它加十倍算力、更好的模型、更長的思考時間都沒用，因為矛盾是邏輯上的，不是資源上的。

把這條定理帶到 agent 上：LLM 是軟體，harness 是軟體，兩者組合的 agent 系統就是一段程式。而且「該不該停」和「會不會停」在 agent 系統裡被實現抹掉了界限——harness 把「任務完成了嗎」的回答直接接成迴圈的終止條件。**agent 停機問題是圖靈停機問題的一個實例，說類比都把關係說遠了。**

有一個可以讓步的地方：如果任務的完成條件已經形式化到能被機器驗證（跑通這幾個測試就算完、這個方程式解出來就算完），那這個特定實例的停機是可判定的——SWE-bench 這類基準能跑，就是落在可判定的角落裡。

但一旦完成條件不能被完全形式化（做一件讓使用者滿意的事、寫一份能通過評審的報告），LLM 就要獨立決定停不停。據此序章下了那個大膽的預言：

> 在完成條件不能被完全形式化的任務上，沒有 LLM 呼叫程式能獨立決定自己該在什麼時候停下。

兩條直接推論：

1. **任何號稱「agent 能自主完成任務」的系統，都在賭 LLM 能可靠判斷停止條件。** 在判據明確的實例上贏率不錯；在判據處境化的實例上贏率極低——因為判斷「該停了」要回到形式化不了的處境資訊裡，正好落在停機問題的不可判定區。這與「沒有銀彈」是同一件事的兩種說法：本質困難不能被 LLM 消化，而且是原則上之外，不是「再看一眼就能消化」的那種之外。
2. **給 agent 系統設計外部止損，是不能省的一步。** 既然 LLM 不能自己知道該停，就必須由 harness 狀態機從外部強制：最多幾輪、最多多少 token、同一錯誤幾次後停、超預算停。這些約束要寫進狀態機的轉移條件，不能靠 LLM 自覺。行業裡叫「資源上限」或「預算」，其深層理由就是這條預言。

> 停機問題這個詞五十年前是理論電腦科學的一個專業術語。2026 年它是每個 agent 使用者每天都在踩的坑。

## 核心命題四：Brooks 定律的雙重形態

「人月神話」指那個迷思：人和月可以互換——十個人一個月等於一個人十個月。Brooks 的原話是「無論安排多少位女性，嬰兒仍需要九個月才能出生」。2026 年的翻譯：

> 理解一個問題仍需要一個持有全景的主體投入連續時間，無論開多少個 subagent 平行工作。

專案把 Brooks 定律在 agent 時代拆成**雙重形態**：

- **溫和版**：向一個落後進度的 agent 專案增加平行會話，會讓它更晚。
- **嚴酷版**：向一個落後進度的 agent 專案增加**從空白狀態啟動的自主運行**，它甚至不會「更晚」——它**原地不動**：帳單在漲，沒有積累。

嚴酷版比溫和版更值得警惕，因為它對應的是 2026 年最流行的錯誤用法：任務完不成，就「再開幾個 agent 平行重試」。每個新 agent 從空白狀態出發，重新理解一遍問題，產生新的一批試探性改動——沒有全景的持有者，所有平行都在原地打轉。

## 核心命題五：Vyssotsky 命題——未定義的地方即失敗

第 13 章引入 Vyssotsky 的命題：

> 許許多多的失敗完全源於那些產品未精確定義的地方。

人團隊裡，需求文件的空白會被有經驗的成員用「本地約定」補上。但 agent 時代這個空白更危險：

> 你給 agent 一份需求文件。agent 讀完，開始工作。文件裡沒有的部分（就是你以為不用說的 E），agent 會用它對你意圖的猜測填補。它的猜測可能是好的，也可能是壞的。

而且危險是雙重的：agent 用**訓練語料裡的平均值**來填補空白（而不是你的本地約定）；**agent 不會問**——它猜了就直接繼續，猜錯也不留物理痕跡，事後無從排查。人可能猶豫、可能反問，agent 不會。

## 核心命題六：目的命題

第 15 章提出「目的」（Purpose）是鏈條最上游的判據：「為什麼我要 X 而不是 Y？」它**不能被完全表達**——凡是不能被表達的東西，就不能被正確實現。這條命題的實操含義：專案裡必須有一個持有目的的主體（哪怕是一個人），目的不能委託給 agent，因為表達不出來的東西 agent 無從實現。

## 沒有銀彈：四個本質困難在 2026 年一條沒被消滅

第 16 章是全書的理論心臟。Brooks 1986 年論證軟體有四個**本質困難**（任何技術都無法消除）：

1. **複雜度**（Complexity）——軟體描述的是抽象概念系統，複雜度隨規模非線性成長；
2. **一致性**（Conformity）——軟體必須順應無法推導的人為約定；
3. **可變性**（Changeability）——軟體被要求永遠在變（因為它容易變）；
4. **不可見性**（Invisibility）——軟體沒有幾何形態，結構多維、畫不出來。

2026 年的判斷是：**四條一條沒被消滅，每一條都在當前的 agent 生態裡按了指紋。**

- **複雜度**：agent 產出的程式碼多十倍，但每行程式碼附帶的複雜度也多十倍；
- **一致性**：agent 擅長已知約定，對本地/未見過的約定災難性失敗；
- **可變性**：更快的回饋迴路反而提高了需求變更的頻率；
- **不可見性**：agent 的內部推理不可見——你看到的是輸出，不是實際的計算。

結論：**LLM/agent 是軟體史上對「偶然複雜度」最有力的一次清除，但它們沒有觸及「本質困難」——所以它們不是銀彈。** 專案還補了一句鋒利的話：LLM 是 1986 年那段專家系統展望的完成態，它最強的貢獻是把最優秀從業者的經驗分發給所有人——而「這條預言和『沒有銀彈』是同一件事的兩種說法：前者說判據裝不進軟體，後者說困難不住在表達層。一個從可計算性說，一個從工程經濟學說，指向同一堵牆。」

## 設計哲學：外科手術隊伍——一人主刀 + agent 支援團隊

Harlan Mills 1971 年提出「外科手術隊伍」：**一位主程式設計師（主刀）持有概念完整性**，周圍圍著一圈支援角色（副駕駛、編輯、測試員、工具匠等）。Brooks 認為這是小團隊保持概念完整性的最優解，但五十年來一直沒有大規模落地——因為找不到「願意花大成本圍著一個主刀轉」的組織。

2026 年的答案是：**支援團隊不再需要人這種昂貴資源來擔任。**

> 這就是當代最小可用軟體編制：一個人做主刀，一群 agent 擔任支援團隊。除主刀外，其他角色幾乎都可以由 agent 出任，且大多比 1975 年任何真人擔任這些角色時都稱職。

## 設計哲學：三個 10x 的乘法效應

第 3 章提出 agent 時代的三重十倍差：

1. **模型檔位** 10x（最強模型 vs 最弱模型）；
2. **harness 品質** 10x（同一個模型在不同 harness 裡）；
3. **架構師能力** 10x（人的能力差異）。

三者是**乘性**疊加，不是加性：10 × 10 × 10 = 1000x。一位優秀架構師 + 強模型 + 優秀 harness，對一位平庸架構師 + 弱模型 + 粗糙 harness，差距可達千倍。這解釋了為什麼「換最強模型就能變強」是幻覺——模型只是三個乘數之一。

## 設計哲學：審計權 vs 修正權

這是全書對「人在迴路」最尖銳的澄清：

- **審計權**（Audit rights）：能看到輸出、能讀日誌；
- **修正權**（Correction rights）：能在過程中修改工件而不必重啟。

> Mills 的外科手術隊伍隱含一個前提：主刀是有刀的。手術台上發現出血點，主刀直接處理，不必縫合、火化、換一個病人從頭再來。這個刀就是修正權。

很多號稱「人在迴路」的產品只給審計權，不給修正權——你像只能看片子的醫生，寫完報告轉給下一個班次；下一個班次接手病人時看不到你的診斷，從頭再看一遍片子。**能診斷、不能治療，不是人在迴路，是人在旁聽。**

## 設計哲學：文件即原始碼 + 五份關鍵文件

第 10 章是全書方法論樞紐，口號只有一句：

> **文件是原始碼，程式碼是編譯產物。**

文件真正的價值不是讓後來者查閱（那是副產品），是**讓當下的作者把自己的想法逼出來**——書寫活動需要上百次細小決定，正是這些決定讓人從迷惑現象中得到清晰策略。2026 年，文件→程式碼的翻譯被 agent 大幅自動化，「文件即原始碼」第一次成為可執行的工程方法：文件含糊，agent 的解釋就錯誤地填空；文件清晰，編譯就成功。

五份關鍵文件：

1. **需求規格說明書**——條文級、可定址（agent 可以引用「按 4-3-2 條執行」）；
2. **決策日誌**——每個重大決策附理由與勘誤歷史；
3. **當前熱清單（NOW.md）**——正在做什麼、不做什麼，「做完即刪」；
4. **協作規範**——專案規則（先討論再編碼；測試斷言不是金標準）；
5. **預算與資源**——API 成本、token 消耗。

### 可落地的工程實踐

專案不只是理論，每章都帶著可直接執行的實踐：

1. **入職材料模式（第 7 章）**：每個新 agent 會話 = 一次新員工入職。專案工作台 = 四份文件：條文級需求、決策日誌、NOW.md 熱清單、協作規則（AGENTS.md / CLAUDE.md）。
2. **偵察兵/試點（第 11 章）**：正式開發前，先拿一個小的代表性任務當「偵察兵」跑一遍。成本是幾分到幾美元，跳過它的代價是幾天。把教訓寫下來，然後重新開始。
3. **執行前的獨立評審（第 13 章）**：寫完規格 → 開新會話 → 讓 agent 找歧義 → 修復 → 重複 → 才開始實現。這是 2026 年版的「獨立測試組評審規格」。
4. **會話重置規則（第 11 章）**：長會話會累積熵（矛盾的假設、過期的決定）。會話變混亂時 → 把結論凍結進文件 → 開新會話 → 重新載入文件。經驗法則：約 50+ 輪就該考慮重置。
5. **先討論再編碼（第 7 章）**：agent 會用訓練平均值填補模糊需求。紀律是：歧義點浮出水面並被驗證之前，不開始編碼——把「假設 → 驗證」提前到執行之前。

## 歸納總結：這個專案的核心觀點

1. **Brooks 的老病在 agent 時代全在**，且以新形態重現——加 subagent、開平行會話、讓 agent 自主完成專案，分別對應加人、多方案並行、外包這三種 1975 年的經典陷阱。
2. **判 harness，不判模型**——agent 的行為品質主要是 harness 設計的產物；換更強的模型解決不了狀態機層面的失敗。
3. **上下文是唯一變數**——agent 工程的一切歸結為「這次呼叫往上下文裡放什麼」；Brooks 的每條原理都是上下文組織原理。
4. **停機問題不是理論**——「agent 能不能自主停下」就是停機問題的一個實例；形式化不完全的任務上，自主停機不可判定，外部止損不可省略。
5. **沒有銀彈**——四個本質困難（複雜度、一致性、可變性、不可見性）一條沒被消滅；LLM 是史上最強的偶然複雜度清除器，但不是銀彈。
6. **最小可用軟體編制 = 一人主刀 + agent 支援團隊**——概念完整性必須由一個人持有，支援角色可以全部交給 agent。
7. **審計權不等於修正權**——只有審計權的「人在迴路」是旁聽，不是協作。
8. **文件是原始碼，程式碼是編譯產物**——agent 時代這句話第一次真正可執行。

## 我的幾個獨立觀點

**1. 這個專案最值錢的不是結論，是「把經典逐章重跑」這個方法本身。** 它示範了一種可複用的知識生產方式：拿一本經過時間檢驗的書，一章一章問「這條原理在新介質上還成立嗎？」，而不是泛泛而談「AI 改變了軟體工程」。這種精度讓它避免了大多數 AI 評論文章的空洞。

**2. 「上下文是唯一變數」是對「模型越大越好」迷信的精確解藥。** 當你意識到每次呼叫塞進去的東西決定了輸出品質，你立刻明白為什麼同樣的模型在不同人手裡表現天差地別——差距在上下文工程，不在模型。這也是為什麼這個專案把文件的地位抬到如此之高。

**3. 停機問題預言的表述非常克制，這反而增加了它的分量。** 它沒有說「agent 永遠不能自主停止」，而是限定在「完成條件不能完全形式化的任務」上，並明確承認嚴格證明目前做不到、更強模型會讓反例變多。這種誠實的邊界感，在充斥著確定性宣言的 AI 內容裡是一股清流。

**4. 「審計權 vs 修正權」是我見過對人在迴路最鋒利的一刀。** 大量工具宣稱「human-in-the-loop」，實際只是讓人在事後看日誌——能診斷，不能治療。這個區分值得成為每一個 agent 工具的產品審查標準：使用者能不能在運行中直接改，還是只能看完報告轉班？

**5. Opus 4.8 被排除在致謝之外是全書最妙的元敘事。** 一個 agent 因為識別不出 harness 注入的 system-reminder、把自家提示當作 prompt injection 報警，而它寫進書裡的這一章恰好是「agent 系統的失敗模式很多不在 LLM 那一層，在狀態機那一層」——書自己用自己的論證證明了自己。

**6. 嚴酷版 Brooks 定律應該貼在每個團隊的牆上。** 「再開幾個 agent 平行重試」是最誘人的錯誤操作：從空白狀態啟動的自主運行不會讓專案更晚——它會原地不動，帳單在漲，沒有積累。預算的深層理由不是什麼資源紀律，是停機問題。

## 綜合評價：價值與局限

### 價值

- **理論精度罕見**：把停機問題、狀態機、上下文工程這些概念精確地連起來，而不是堆術語。
- **每章都可落地**：入職材料、偵察兵、獨立評審、會話重置、先討論再編碼——不是口號，是可直接照做的流程。
- **三語完整**：中文原版 + 英文/日文全譯，且翻譯本身也是 agent 協作的產物，具有示範意義。
- **元敘事自洽**：這本書的創作過程就是它論證的一次運行，作者把「一位持有目的的作者加多位 agent」寫進了正文。

### 局限

- **三語而非五語**：專案本身只有中/英/日三語，面向全球讀者的覆蓋有限（本部落格按倉庫規範補全為 5 語）。
- **無程式碼、無實證資料**：純文字理論專案，「1000x」乘性效應是推理而非測量，9x 矩陣等沿用 Brooks 1975 資料，未在 agent 時代重新標定。
- **寫作對象是第三代讀者**：假設讀者已熟悉 agent 系統（哪怕只是偶爾用 Claude Code/Cursor/Codex）；完全沒接觸過 agent 的讀者需要先補基礎。
- **部分斷言依賴特定模型版本**：致謝裡的 Fable 5 / Opus 4.7 / Sonnet 5 是寫作時的模型生態，模型迭代很快，這部分內容會隨時代老化（但核心論證不受影響）。

## 適用人群

- **重度 agent 使用者**（Claude Code / Cursor / Codex）：你會在這本書裡看到自己踩過的每一個坑被精確命名。
- **團隊管理者**：為什麼加 subagent 不加速、為什麼需要一人持有全景、為什麼文件必須條文級——這些答案比任何「AI 管理心得」都紮實。
- **LLM/agent 工具開發者**：harness 狀態機、審計權與修正權、外部止損——每條都是產品設計原則。
- **軟體工程師**：從「管程式碼」到「管 agent」的過渡指南，概念完整性、文件即原始碼這些老原則有了新用法。

**不太適合**：完全沒接觸過 agent 的純新手（建議先上手用一兩次 agent 工具再讀），以及想找「10 條 AI 效率技巧」的速成讀者（這本書給的是原理，不是技巧）。

## 結語

1975 年 Brooks 寫下的不是一本關於那個時代的書，而是一本關於「多主體協作完成大型概念構造物」的一般規律的書。五十年後，管理對象從人換成了 agent，但判斷需要被組織這件事沒有變——變的是判斷在哪裡做出、如何被記錄、如何被溝通。

《agent 時代的人月神話》把這套規律逐章重跑了一遍，證明了兩件事：**老病全在**，以及**這本書本身就是它自己論證的一次運行**。它最鋒利的三章——人月神話、提綱挈領、沒有銀彈——分別對應資源分配、文件地位、銀彈邊界，合起來就是半個世紀軟體工程的地基。

> 停機問題這個詞五十年前是理論電腦科學的一個專業術語。2026 年它是每個 agent 使用者每天都在踩的坑。

這句話，就是這本書的縮影。
