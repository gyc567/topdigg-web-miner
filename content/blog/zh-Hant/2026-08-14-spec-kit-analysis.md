# GitHub spec-kit：規範驅動開發讓AI編程代理「先想清楚再寫程式碼」

## 專案介紹與概述

**spec-kit** 是 GitHub 官方推出的一款開創性工具，專注於**規範驅動開發（Spec-Driven Development）**。該專案在 GitHub 上獲得了 127.4k Stars 和 11.4k Forks，採用 MIT 開源協議，展現了極高的社群認可度。

### 核心理念

spec-kit 的核心思想是：**將規範文檔從「一次性草稿」轉變為可執行、可生成實現的「核心資產」**。

傳統開發模式往往是：需求文檔 → 編碼實現 → 修修補補。這種模式導致的問題是，開發者在編碼過程中需要不斷做決策、反覆確認需求，最終產出的程式碼可能與原始意圖產生偏差。

spec-kit 提出的新範式是：

> **「定義要構建什麼，再開始構建——與任何 AI 編程代理配合使用」**

規範驅動開發徹底翻轉了傳統軟體開發模式，讓 AI 代理在編寫程式碼之前，先充分理解要做什麼、為什麼要這樣做。

## 核心設計哲學

### 規範作為核心資產

在傳統的軟體工程中，規範文檔往往被視作「一次性草稿」——在專案初期編寫，隨後便被遺忘，程式碼實現與原始規範漸行漸遠，最終變成無用的參考文檔。

spec-kit 反其道而行之，將規範提升為專案的**核心資產**：

1. **規範是可執行的** - 規範不僅描述需求，還能直接驅動程式碼生成
2. **規範是可驗證的** - 實現的正確性可以透過規範來驗證
3. **規範是活的** - 規範與實現保持同步，成為專案的真實來源

### 與 AI 編程代理的協同

spec-kit 明確提出可以與**任何 AI 編程代理**配合使用，包括：

- GitHub Copilot
- Claude
- Cursor
- 各類 AI 編碼工具

這種設計理念基於一個觀察：AI 代理在缺乏明確規範時，容易產生「幻覺」或偏離預期方向。而有了清晰的規範，AI 代理可以：

- 準確理解需求意圖
- 生成符合預期的程式碼
- 減少反覆修改的成本
- 提高程式碼品質與一致性

## 規範工作流詳解

spec-kit 定義了一套完整的規範工作流，從抽象原則到具體實現，環環相扣：

```
constitution（原則）→ specify（需求）→ plan（技術方案）→ tasks（任務分解）→ implement（執行）
```

### 1. Constitution（原則）

**原則層**定義了專案的核心價值觀和不可違背的準則。這包括：

- **設計原則** - 程式碼應該遵循什麼樣的設計哲學
- **約束條件** - 技術選型、架構風格等硬性約束
- **品質標準** - 效能要求、可維護性目標等

原則層是整個工作流的基石，為後續所有決策提供指導方向。

### 2. Specify（需求）

**需求層**詳細描述系統應該做什麼。這不是簡單的功能列表，而是：

- **清晰的用例描述** - 使用者如何與系統互動
- **明確的輸入輸出** - 資料的格式、邊界條件
- **行為規範** - 系統在各種場景下的預期行為
- **錯誤處理策略** - 異常情況的處理方式

需求規範應該做到：任何閱讀者都能基於此規範理解系統要做什麼。

### 3. Plan（技術方案）

**方案層**將需求轉化為具體的技術實現路徑：

- **架構設計** - 系統的整體結構、模組劃分
- **技術選型** - 採用的技術棧、框架、庫
- **介面設計** - 模組之間的 API 契約
- **資料模型** - 資料庫 schema、資料結構設計

方案層承上啟下，將「做什麼」轉化為「怎麼做」。

### 4. Tasks（任務分解）

**任務層**將大型方案拆解為可執行的小任務：

- **任務列表** - 具體需要完成的工作項
- **依賴關係** - 任務之間的執行順序
- **驗收標準** - 每個任務完成的判定條件
- **時間估算** - 工作量評估（可選）

任務分解讓複雜專案變得可控，也讓 AI 代理能夠逐步完成工作。

### 5. Implement（執行）

**執行層**是實際編寫程式碼的階段。在這個階段：

- AI 代理根據規範生成程式碼
- 程式碼自動符合預先定義的標準
- 減少了理解偏差導致的返工
- 保持了實現與規範的一致性

## AI 集成與擴展系統

### 30+ AI 集成

spec-kit 支援與超過 30 種 AI 編程工具的集成，包括但不限於：

| 類別 | 代表產品 |
|------|----------|
| 程式碼補全 | GitHub Copilot, Tabnine, Kite |
| 對話式編程 | Claude, GPT-4, Cursor |
| 程式碼審查 | CodeRabbit, PR Reviewer |
| 測試生成 | Diffblue, CodiumAI |

這種廣泛的相容性確保了團隊可以使用自己喜歡的 AI 工具，同時享受規範驅動開發的好處。

### 擴展系統

spec-kit 提供了靈活的擴展機制：

#### Extensions（擴展）

擴展允許開發者為 spec-kit 添加新功能：

- 自定義驗證規則
- 新的輸出格式
- 與外部系統的集成

#### Presets（預設）

預設是預先配置好的規範模板：

- 常見專案類型的最佳實踐
- 行業特定的規範模板
- 開箱即用的配置方案

#### Bundles（角色化配置包）

Bundles 是 spec-kit 的一大亮點，它將規範配置打包成**角色化**的形式：

- **開發者角色** - 面向開發團隊的規範集
- **審查者角色** - 面向程式碼審查的規範集
- **運維角色** - 面向部署運維的規範集

這種角色化設計讓不同角色的參與者都能專注於自己的領域。

### 自管理能力

spec-kit 還具備自我進化的能力：

- **自動檢查更新** - 監控規範的新版本
- **自動升級** - 平滑地將規範演進到新版本
- **向後相容** - 確保升級不會破壞現有實現

## 專案結構

spec-kit 的原始碼結構設計清晰，便於理解和使用：

```
spec-kit/
├── src/
│   └── specify_cli/      # CLI 核心原始碼
├── extensions/           # 擴展插件目錄
├── presets/              # 預設模板目錄
├── bundles/              # 角色化配置包
├── integrations/         # AI 代理集成
├── docs/                 # 專案文檔
├── templates/            # 規範文檔模板
├── tests/                # 測試程式碼
└── examples/
    └── bundles/          # 角色配置示例
```

### 核心目錄解析

**src/specify_cli/** - CLI 工具的核心實現，提供了命令列界面和核心邏輯。

**extensions/** - 社群貢獻的擴展插件，可根據需要選用。

**presets/** - 官方維護的預設模板，覆蓋常見場景。

**bundles/** - 角色化配置包，包含針對不同場景的預設組合。

**integrations/** - 與各 AI 代理的集成程式碼，確保 spec-kit 能與各種 AI 工具協同工作。

**templates/** - 規範文檔的模板文件，幫助快速啟動新專案。

**examples/bundles/** - 具體的使用示例，展示如何配置和使用 bundles。

## 適用場景

### 綠地開發（0-to-1）

從零開始的新專案是 spec-kit 發揮價值的最佳場景：

```
規範 → 方案 → 程式碼
```

在沒有任何歷史包袱的情況下，可以完全按照 spec-kit 的工作流來構建專案。AI 代理從一開始就知道要做什麼，減少了溝通成本和返工。

### 創意探索

當需要探索多種技術方案時，spec-kit 也能大顯身手：

- **並行方案生成** - 同一套需求規範，生成多種技術方案
- **方案對比** - 基於相同的驗收標準評估不同方案
- **快速原型** - 快速驗證想法的可行性

### 增量增強

對於現有專案的功能迭代，spec-kit 同樣有用：

- **功能規範** - 為新功能編寫清晰的規範
- **現代化改造** - 在保持功能不變的前提下，規範驅動程式碼重構
- **技術債務管理** - 用規範來指導技術債務的償還優先順序

## 使用示例與最佳實踐

### 快速開始

使用 spec-kit 的典型工作流程：

```bash
# 1. 初始化新專案
spec-kit init my-project

# 2. 建立規範文檔
spec-kit specify create feature-x

# 3. 基於規範生成方案
spec-kit plan generate

# 4. 分解任務
spec-kit tasks decompose

# 5. 執行實現
spec-kit implement run
```

### 最佳實踐

#### 1. 規範先行

在編寫任何程式碼之前，先完善規範。規範的品質直接決定了最終程式碼的品質。

#### 2. 保持簡潔

避免過度設計。規範應該清晰明瞭，而不是晦澀難懂的技術文檔。

#### 3. 迭代演進

規範不是一成不變的。隨著對問題的深入理解，規範也應該相應更新。

#### 4. 團隊共識

確保團隊所有成員都理解並認同規範。規範是團隊的共同約定，而非個人偏好。

#### 5. 善用 AI

讓 AI 代理參與規範的 Review 和優化。AI 可以幫助發現規範的遺漏和矛盾。
