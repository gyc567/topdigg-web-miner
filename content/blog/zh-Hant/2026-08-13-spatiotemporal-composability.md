# 時空可組合性：重新定義動態軟體架構的編程範式

## 專案與論文介紹

**paper** 是 cordiverse 組織發布的一份學術預印本論文（2026年8月草稿），提出了一種名為**動態組合（Dynamic Composition）**的編程範式，旨在解決現代軟體架構中元件之間動態互動和依賴管理的根本性問題。

### 核心問題：為什麼需要動態組合？

傳統的軟體架構強調模組化和組合性，但在執行期動態載入、替換和組合元件方面存在顯著不足。現代應用場景——從微服務架構到前端框架的熱模組替換（HMR），再到插件系統——都對執行期組合提出了更高要求。

論文指出，當前的編程範式在處理以下場景時顯得力不從心：

- **熱模組替換**：在不重啟應用程式的情況下動態更新程式碼模組
- **插件系統**：執行期載入和卸載功能擴展
- **響應式依賴管理**：當依賴項發生變化時自動更新依賴方
- **事務性回滾**：在元件失敗時完全撤銷其所有副作用

## 核心設計哲學

### 兩個正交維度

論文識別出組合性的兩個根本維度，它們相互獨立卻又共同決定了系統的表達能力：

### 1. Temporal Composability（時間可組合性）

**時間可組合性**指的是移除元件時**完全撤銷其副作用**的能力。傳統的資源管理只關注獲取和釋放（acquire/release），但忽略了在元件生命週期中產生的更深層副作用。

舉例來說，當一個元件執行了以下操作：
- 修改了全域狀態
- 建立了後台任務
- 註冊了事件處理器
- 建立了網路連線

時間可組合性要求：移除該元件時，這些副作用必須被**完全、可預測地撤銷**，彷彿該元件從未執行過。

### 2. Spatial Composability（空間可組合性）

**空間可組合性**指的是**宣告和響應式管理元件間依賴關係**的能力。在一個元件系統中，元件不是孤立的——它們依賴於其他元件提供的資料和服務。

空間可組合性關注的是：
- 元件如何**宣告**其依賴
- 當依賴項**變化**時，元件如何**響應**
- 依賴關係的變化如何**傳播**到依賴它們的元件

### 為什麼需要兩個維度？

論文的核心觀點是：**時間和空間的可組合性是正交的，不能相互替代**。

- 只有時間可組合性：元件可以被安全移除，但無法管理依賴關係
- 只有空間可組合性：依賴關係被宣告和管理，但沒有撤銷機制

兩者結合才能實現真正的動態組合系統。

## 核心概念詳解

### Revertible Effects（可撤銷效應）

#### 概念起源

傳統的 **Effect** 描述的是程式在執行過程中對外部世界產生的**可見影響**——如檔案操作、網路請求、狀態修改等。Effect 系統（如 Haskell 的 mtl、Effect-TS）允許程式設計師以型別安全的方式追蹤和管理這些副作用。

**Revertible Effects** 在此基礎上增加了一個關鍵能力：**追蹤逆變換（inverse transformation）**。

#### 核心思想

每個 Effect 不僅描述了「做什麼」，還附帶了一個**撤銷操作（reverter）**的上下文。當需要移除元件時，系統可以執行這個撤銷操作來恢復狀態。

```typescript
// 概念性示例
interface RevertibleEffect<State, Effect> {
  perform: (state: State) => Effect;
  revert: (state: State, effect: Effect) => State;
}
```

#### 應用場景

1. **資料庫交易**：自動回滾未提交的更改
2. **UI 狀態管理**：撤銷使用者操作
3. **資源獲取追蹤**：精確釋放所有已分配資源
4. **日誌審計**：記錄並可撤銷的操作歷史

### Reactive Coeffects（響應式協同效應）

#### 概念起源

**Coeffect** 概念來自函數式編程，描述的是函數**需要什麼**才能執行——即函數的**上下文依賴**。例如，一個讀取設定檔的函數「需要」設定資料；一個記錄日誌的函數「需要」日誌記錄器。

傳統的 Coeffect 系統關注的是**靜態依賴宣告**，而 **Reactive Coeffects** 將其擴展為**動態、響應式的依賴管理**。

#### 核心思想

當元件依賴的上下文發生變化時，系統**主動通知**該元件，而不是讓元件輪詢或手動檢查。這種模式借鑒了響應式編程（Reactive Programming）的思想，但應用於依賴注入的領域。

```typescript
// 概念性示例
interface ReactiveCoeffect<T> {
  // 宣告依賴
  dependsOn: () => T[];
  // 當依賴變化時的回調
  onChange: (newValue: T, oldValue: T) => void;
}
```

#### 與傳統依賴注入的區別

| 特性 | 傳統依賴注入 | Reactive Coeffects |
|------|-------------|-------------------|
| 依賴解析時機 | 構造時 | 執行期動態 |
| 變化通知 | 無 | 有（推模式） |
| 依賴追蹤 | 顯式 | 隱式宣告 |
| 懶載入支援 | 有限 | 原生支援 |

### Context Types（上下文類型）

#### 統一 effect 和 coeffect

論文提出了一個統一的概念框架，將 **Effect**（元件對外部的影響）和 **Coeffect**（元件對外部的依賴）統一為**上下文類型（Context Types）**。

在傳統的 effect/coeffect 系統中，這兩個概念是分開處理的。Context Types 提供了一個統一的型別系統，可以在其中同時表達：

- **產出效果（produced effects）**：元件產生的副作用
- **消費協同（consumed coeffects）**：元件需要的依賴
- **效果追蹤（effect tracking）**：追蹤已執行的效果以便回滾
- **協同解析（coeffect resolution）**：動態解析依賴並傳播變化

#### 形式化定義

```typescript
// Context Type 的概念性形式
interface ContextType<S, E, C> {
  // 狀態類型
  state: S;
  // Effect 類型（可撤銷的效果）
  effects: RevertibleEffect[];
  // Coeffect 類型（響應式依賴）
  coeffects: ReactiveCoeffect[];
}
```

## Cordis 元框架架構

### 框架概述

**Cordis**（拉丁語「心臟」）是實現論文思想的概念性框架，展示了如何在實踐中應用動態組合的理論。

### 核心元件

#### 1. 核心庫（@cordis/core）

負責最基礎的機制：
- **Effect 追蹤**：追蹤所有可撤銷的效果
- **Coeffect 解析**：管理依賴解析和變化傳播
- **Context 管理**：維護執行期的上下文狀態

#### 2. 元件系統（@cordis/component）

提供了動態組合的**組合機制**：

```typescript
// 元件定義示例（概念性）
const myComponent = component({
  name: 'my-component',
  // 宣告依賴的 coeffects
  coeffects: [databaseService, configService],
  // 提供或觸發 effects
  effects: [loggingEffect],
  // 元件邏輯
  setup(ctx) {
    // 使用依賴
    const db = ctx.coeffects.databaseService;
    // 執行操作
    ctx.effects.log('Hello');
  },
  // 可選的拆卸邏輯
  teardown(ctx) {
    // 清理工作，effects 會被自動撤銷
  }
});
```

#### 3. 宣告式載入器（@cordis/loader）

用於**宣告式地載入和設定元件**：

- 宣告式依賴：描述元件需要什麼，而不是手動注入
- 設定協調：管理元件的設定和初始化順序
- 生命週期管理：處理元件的建立、更新和銷毀

#### 4. 熱模組替換（HMR）能力

Cordis 框架特別強調了**熱模組替換**能力，這是動態組合的實際應用：

- **增量更新**：只更新變化的元件，不影響其他元件
- **狀態保持**：在更新過程中保持必要狀態
- **自動清理**：移除舊元件的 effects，應用新元件的 effects

## 動態組合演算

### Calculus of Dynamic Composition

論文提出了**動態組合演算（Calculus of Dynamic Composition, CDC）**，這是對動態組合理論的**元理論（meta-theory）**描述，提供了形式化的數學基礎。

### 演算的核心要素

#### 1. 元件（Components）

元件是動態組合的基本單位，每個元件包含：
- **介面（Interface）**：描述元件提供的服務和依賴
- **實作（Implementation）**：元件的具體邏輯
- **效果追蹤（Effect Traces）**：記錄元件執行過程中的效果

#### 2. 組合器（Compositors）

組合器定義了元件如何組合：
- **串列組合**：一個元件的輸出作為另一個的輸入
- **平行組合**：多個元件獨立執行，共用狀態
- **覆蓋組合**：新元件替換舊元件

#### 3. 撤銷語義（Reversion Semantics）

定義了在移除元件時：
- 哪些效果需要被撤銷
- 撤銷的順序是什麼
- 如何處理部分撤銷失敗的情況

### 形式化保證

動態組合演算提供了以下形式化保證：

1. **可組合性定理**：組合後的元件仍然保持時間/空間可組合性
2. **撤銷完整性**：移除元件時，所有效果都被完全撤銷
3. **依賴傳遞性**：依賴關係的變化正確傳播到所有依賴方

## 關鍵觀點總結與結論

### 核心貢獻

1. **識別了兩個正交維度**：時間和空間可組合性共同構成了動態組合的基礎

2. **提升了 effect 和 coeffect 概念**：
   - Revertible Effects 將 effect 從「追蹤」提升到「可撤銷追蹤」
   - Reactive Coeffects 將 coeffect 從「靜態宣告」提升到「動態響應」

3. **統一的形式化框架**：Context Types 統一了 effect 和 coeffect 上下文

4. **實際框架實作**：Cordis 展示了理論的實際可行性

### 重要觀點

> 「動態組合不是關於如何編寫元件，而是關於元件如何在執行期相互作用、依賴和撤銷。」

### 局限性

論文也誠實指出了其局限性：

- 目前僅是**概念驗證**，效能開銷尚未優化
- **形式化證明**仍在完善中
- 對於**大規模系統**的可擴展性有待驗證
- **實際應用案例**還不夠豐富

## 應用場景和實踐意義

### 適用場景

1. **前端框架**
   - 熱模組替換（HMR）
   - 響應式狀態管理（如 Redux 的時間旅行除錯）
   - 插件系統

2. **後端服務**
   - 微服務架構中的動態服務編排
   - 資料庫交易的巢狀管理
   - 資源獲取和清理的精確追蹤

3. **嵌入式系統**
   - 元件的確定性載入和卸載
   - 資源受限環境下的精確資源管理

4. **IDE 和開發工具**
   - 即時程式設計環境
   - 增量編譯和更新

### 實踐意義

對於軟體開發者的實際價值：

| 方面 | 目前狀態 | 引入動態組合後 |
|------|---------|---------------|
| 元件卸載 | 手動清理資源 | 自動完全撤銷 |
| 依賴變化 | 手動檢查更新 | 自動響應通知 |
| 熱更新 | 有限支援 | 原生支援 |
| 狀態回滾 | 手動實作 | 框架級支援 |

### 未來展望

動態組合範式為以下方向提供了理論基礎：

- 更安全、更易推理的執行期組合系統
- 原生支援熱更新的程式語言和框架
- 自動化的資源管理和清理
- 形式化驗證的執行期系統
