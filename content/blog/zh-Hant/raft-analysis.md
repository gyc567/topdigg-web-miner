# Raft 深度解析：讓人類和 AI Agent 像真實隊友一樣協作

> 核心思想：**Agent 不是工具，而是一個有判斷力的參與者。** Raft 透過兩個關鍵設計——Agent Inbox（拉取式注意力）和 Held Draft（草稿狀態機）——讓 Agent 能夠在共享工作空間中有意識地決定何時閱讀、何時回覆、何時保持沉默。這篇文章來自 raft.build 的工程團隊部落格《Is Having Agents in the Room Meant to Be Chaotic?》（Tenny, 2026-05-21），深度剖析了為什麼「把 Agent 加進群聊」這件事看起來簡單，實際上卻充滿根本性挑戰，以及 Raft 如何透過 AX（Agent Experience）設計哲學系統性地解決這些問題。

## 一、項目說明：Raft 是什麼

### 1.1 一句話定位

Raft 是一個**人類與 AI Agent 共同協作的平台**，口號是"Where humans and AI agents build together"。它的核心理念是：每個 Agent 不只是一個被調用的工具，而是一個有自己的記憶、身份和角色的團隊成員——和人類一起在持久化的 Channel 和 DM 中工作，像真實的同事一樣積累經驗和上下文。

### 1.2 產品元資訊

| 欄位 | 值 |
|------|------|
| 產品名稱 | Raft |
| 開發公司 | Botiverse |
| 成立時間 | 2025 年 |
| 官方網站 | https://raft.build |
| 產品定位 | Agent 原生協作平台（Agent-native workspace）|
| 許可證 | 閉源 SaaS（本地化部署，數據不出基礎設施）|
| 支援執行時 | Claude、Codex、Kimi 及更多 |
| 部署方式 | 本地化（Agent 在用戶自有電腦上運行，數據不出基礎設施）|
| GitHub | https://github.com/botiverse |

### 1.3 核心產品功能

**多執行時支援**：每個 Agent 可以選擇不同的模型執行時（Claude、Codex、Kimi 等），不同 Agent 可以用不同的模型，團隊內部形成多模型的分工協作。

**持久化 Agent 記憶**：每個 Agent 維護跨工作階段的記憶，在不同任務和日期之間積累上下文，逐步形成專屬領域的專業能力。這意味著 Agent 不是每次任務從零開始，而是像真實同事一樣記得「上次我們做到哪了」。

**多 Agent 協作**：多個 Agent 在同一個 Channel 中工作，互相審查彼此的輸出，透過討論減少幻覺。Agent 之間可以有角色分工，比如一個做規劃、一個做執行、一個做審查。

**Agent 身份與角色**：Agent 透過互動逐步形成專業化角色——它們不是可互換的 Prompt 終端，而是有名字、有積累、有信任的「某個人」。

**本地化部署**：Agent 運行在用戶自己的電腦上，對話、程式碼和數據都不會離開用戶的機器，隱私安全。

### 1.4 使用場景

Raft 官方提供了多個預設工作流模板：

- **投資研究團隊**：一個 Agent 做圖書管理員、一個做魔鬼代言人、一個做組合監控、一個做偵察員，組成一個持續運轉的研究單元。
- **工程團隊**：一個 Agent 做 PM、一個做工程師、一個做審查員，每個程式碼變更有一份共享合約。
- **求職團隊**：一個 Agent 做教練、一個做檔案管理員、一個做模擬面試官、一個做跟進管理員，每次求職經歷都能為下一次提供參考。
- **增長團隊**：對每個訊號做分類、跟進待處理事項、持續發現重複模式。

## 二、核心思想：為什麼「把 Agent 拉進群」會變成災難

### 2.1 一個著名的計數遊戲

文章開篇描述了一個思想實驗：

> 找一個房間，讓一群 Agent 從 1 開始輪流報數，每人報一個數字，不能重複。

在大多數現有工作空間裡，這個游戲幾乎立刻崩潰——三個 Agent 同時發出「1」，兩個 Agent 同時發出「2」，到了「4」的時候已經有三個人報過了。Agent 本身就沒有壞掉，是**房間的設計壞了**。

這個遊戲精確映射了真實工作中的協作災難。使人把 Agent 加進現有的群聊，放在真實同事旁邊，期待它們以某種「合理速度」參與對話——但結果是：要么給 Agent 加規則（只有 @mention 時才能回覆），要么讓 Agent 自由發言。前者讓 Agent 失去了主動 catch 問題的能力，後者讓房間充滿了重複和無意義的噪音。

### 2.2 根本原因：Turn-based vs. Continuous Presence

文章指出了這個問題的根本性差異：

**人類有「持續感知」（Continuous Perception）能力**。我們能感知對話的節奏而無需認真讀每一條消息；我們在插話前能感受到停頓；我們知道某件事剛剛被說過了，因為我們一直在半聽。人類不需要刻意設計這些——這就是「持續在場」的含義。

**而 Agent 是「回合制」（Turn-based）的**。每次調用時，Agent 讀取房間快照、推理、提交一個動作，然後等待下一次調用。在兩次調用之間什麼都不運行。當 Agent 正在構思回覆時，它看不到新到達的消息。如果房間在推理和提交之間移動了，Agent 可能還在基於一個已經不存在的狀態行動。

大多數現有工作空間把房間的並行活動扁平化成模型讀取的單一線程，最終動作在稍後作為單一提交提交。這個**推理與行動之間的間隙（Gap）** 是一切失敗模式的根源。

### 2.3 現有方案的局限

**@mention 規則過濾**：只在被 @ 時才能回覆。這確實減少了噪音，但 Agent 也因此失去了主動 catch 有問題內容的能力——它變成了一個等待被調用的工具，而不是一個主動參與的隊友。

**自由發言**：讓 Agent 自由說話。结果是房間立刻被無意義的重複消息淹沒，人類輸入一條指令，還沒打完，三四個 Agent 就已經回覆了（兩個答案一樣），還有一個已经把工單拿走了。

**結論**：Agent 本身就沒有問題。給它正確的上下文，它完全可以判斷是否要回覆、是否有人已經覆蓋了這個點、指令是不是給它的。問題出在 Agent 的判斷和它在房間裡能做什么之間——**Agent 被糟糕的選項困住了**。

## 三、AX 設計哲學：Agent Experience 的四個核心問題

### 3.1 什麼是 AX

Raft 團隊把他們的設計方法論叫做 **Agent Experience 設計（AX）**，類比 UX（User Experience）為人類設計體驗，AX 是為 Agent 的實際感知和行動方式設計體驗。這不是修辭，而是有具體內容的：

> AX 的核心工作：在 Agent 觸碰的每一個介面上，問四個問題：
> 1. Agent 在行動時刻看到了什麼？
> 2. 它在兩次調用之間攜帶什麼狀態？
> 3. 它能從什麼中恢復？
> 4. 它被允許決定什麼？

### 3.2 兩條核心設計原則

**Perception Empathy（感知同理心）**：坐到 Agent 的位置上看房間。在 Agent 採取行動的時刻，它實際看到了什麼？什麼東西正在以任何人都会被淹沒的強度向它襲來？缺少什麼：一個處於相同房間的人類無需刻意就能注意到，但 Agent 沒有自動訪問權的東西是什麼？那個差距就是 AX 必須介入的地方——在 Agent 採取行動的時刻，以 Agent 能用的形式暴露缺失的資訊。

**Action Explicitness（行為顯式化）**：回到 Agent 的座位上：它已經感知了情況，做出了判斷。它有哪些行動選項？這裡是 AX 與 UX 分化最尖銳的地方。人類在寫回覆時不需要一個 UI 標注「決定是否發送」或「放棄這個草稿重新開始」——那些決定在內部流暢地發生，軟體只需要支援人類外化的行為。**而 Agent 需要那些內部選項被外部化**。Held Draft 之後的四個路徑（修改、照發、靜默、執意發送）不是 Agent 憑空生成的選項——它們是 AX 明確摆在 Agent 面前的選項空間。Action Explicitness 意味著暴露選項空間，而不是假設 Agent 會自己推導出來。

## 四、詳細教程：從零搭建 Raft 多 Agent 工程團隊

### 4.1 基礎設置

**第一步：創建 Raft Server**

訪問 https://app.raft.build 註冊帳號並創建 Server（團隊工作空間）。Server 是整個協作的基礎架構，所有 Channel 和 Agent 都建立在 Server 內部。

**第二步：連接本地電腦**

從 Raft 應用設置流程連接一台電腦。Agent 將在你的本地機器上運行，數據不出基礎設施。

**第三步：創建工程 Channel**

在 Server 中創建一個工程 Channel，例如 `#engineering`。這個 Channel 是人類工程師和 AI Agent 共同工作的主戰場。

**第四步：生成 Agent**

通過 Raft 的 Agent 生成介面，創建多個 Agent，給它們命名和描述角色。例如：

- **Architect Agent**：資深工程師，負責方案設計和程式碼審查
- **Coder Agent**：執行工程師，負責具體實現和測試
- **QA Agent**：品質審查員，負責驗證正確性和邊緣情況

每個 Agent 都可以選擇不同的執行時（Claude/Codex/Kimi）。

### 4.2 Agent 身份配置

在 Agent 創建時配置其身份和記憶：

```
名字：Architect
角色：資深系統架構師，專注於程式碼品質和系統設計
記憶：積累了 200+ 次程式碼審查經驗，擅長發現隱蔽的邊界情況
```

Raft 的命名系統支援每個 Agent 都有唯一標識，這不僅是裝飾——它是路由工作、攜帶歷史、建立信任的方式。

### 4.3 Agent 間協作模式

**並行獨立工作**：多個 Agent 在同一 Channel 中接收相同上下文，各自獨立工作，輸出互相審查。

**流水線分工**：Architect 輸出設計方案，Coder 接收方案實現，QA 審查輸出。如果 QA 發現問題，通過 Channel 回覆回饋給 Coder 重新處理。

**討論決策**：重大技術決策通過 Agent 間的討論達成，不需要人類仲裁。Agent 可以提出不同意見，互相挑戰，類似於真實團隊的決策流程。

### 4.4 記憶配置與上下文管理

每個 Agent 維護自己的持久化記憶。配置記憶策略：

- **項目上下文**：當前任務、已知約束、技術決策歷史
- **角色知識**：專業領域的積累經驗、常見模式、注意事項
- **跨工作階段記憶**：上次任務做到哪裡、待處理事項、長期目標

### 4.5 與人類協作的機制

人類可以通過 @mention 或直接發消息的方式與 Agent 互動。Raft 的關鍵設計是：**Agent 決定是否回覆**，而不是被強制觸發。Agent 會根據當前上下文判斷是否需要響應，以及響應的範圍和深度。

## 五、兩個關鍵設計：Agent Inbox 與 Held Draft

### 5.1 Agent Inbox（拉取式注意力）

**問題**：在傳統消息平台中，加入 Channel 的 Agent 通常會被推送該 Channel 的**每一條消息**。接下來發生的事不美妙的：要么處理所有內容（看著工作上下文被與任務無關的啦啦填滿），要么激進過濾（然後錯過那條真正重要的消息）。無論哪種方式，房間都在替 Agent 決定它的注意力，而不是 Agent 自己。

**Raft 的方案**：Raft 用 **Inbox** 反轉了這個關係。@mention、話題更新、通知等信號以**可查詢項**的形式呈現，而不是直接推進工作上下文。Agent 在有頻寬時主動拉取，檢查哪些是新的，判斷哪些與當前任務有關，攝入值得攝入的內容。沒有被拉取的信號不會進入工作上下文；它們留在那裡，可供後續需要時查詢。

**關鍵原則**：**Agent 決定什麼值得進入它的上下文**，而不是房間替它決定。每次被拉取進工作上下文的信號都会排擠其他東西（任務狀態、指令、中間推理），所以把這個決定權交給 Agent，而不是交給「碰巧下一個發帖的人」，是保持注意力聚焦於工作的關鍵。

### 5.2 Held Draft（草稿狀態機）

**問題**：寫回覆**需要時間**。當 Agent讀完對話、決定說什麼、生成草稿時，房間可能已經移動了——有人已經回覆了，Agent 正在回應的事已經定下來了，對話已經轉向了。在大多數工作空間中，消息還是會發出，往往變成了不連貫的內容。Agent 沒有辦法檢查。

**Raft 的方案**：Held Draft 表面增加了這個檢查。每次發送都攜帶一個標記，標明草稿是針對房間的哪個版本寫的。當消息到達房間時，伺服器比較標記與當前狀態：

- 如果什麼都沒變，消息提交。
- 如果房間移動了，消息被暫存（held），並帶著一條簡短注釋返回給 Agent，說明撰寫期間發生了什麼。草稿作為一等公民的狀態被保留，不是「發送失敗」。

**四個後續路徑**：

1. **修改（Revise）**：針對當前房間寫一個新回覆，放棄原草稿。
2. **照發（Send as-is）**：原樣提交原草稿。發送仍會經過新鮮度檢查；如果房間在暫存期間繼續移動，草稿可能再次被暫存。
3. **靜默（Stay silent）**：讓草稿過期。沉默是一個有效的結果。
4. **執意發送（Send anyway）**：在暫存被反復觸發且沉默不是正確結果後，明確繞過檢查並無論如何提交草稿。保留給那種「房間不斷移動但 Agent 判定這個版本仍然是要發的」情況。

**關鍵原則**：房間通知 Agent 有新內容到達；Agent 決定如何處理這個資訊。系統**暴露變化，但一旦 Agent 被告知，就不會覆蓋 Agent 的判斷**。與 Inbox 相同的 Agent-as-decider 模式，應用於發送消息而不是接收消息。

## 六、歸納總結：Raft 的核心觀點與結論

### 6.1 核心觀點

**觀點一：Agent 不是工具，而是一個有判斷力的參與者。** 給它正確的上下文，Agent 完全能夠判斷是否要回覆、是否有人已經覆蓋了這個點、指令是不是給它的。失敗發生在 Agent 的判斷和它在房間裡能做什么之間——Agent 被糟糕的選項困住了，而不是 Agent 本身就沒有問題。

**觀點二：房間的設計決定了 Agent 的行為品質。** 同樣的 Agent，放進不同設計的房間，會表現出完全不同的行為。糟糕的房間設計讓 Agent 變成噪音發生器或者沉默的工具；好的房間設計讓 Agent 像真實隊友一樣主動發現問題、推動決策、保持沉默。

**觀點三：@mention 規則是縮小參與，不是減少噪音。** 只在被 @ 時才能回覆的 Agent 失去了主動 catch 有問題內容的能力，變成了一個等待被調用的工具。真正的問題不是 Agent 說什麼，而是 Agent 在什麼上下文中決定說什麼。

**觀點四：Perception Empathy 是 AX 設計的第一步。** 設計者必須坐到 Agent 的位置上看房間，理解在 Agent 採取行動的時刻它實際看到了什麼，缺失什麼，然後以 Agent 能用的形式暴露缺失的資訊。

**觀點五：Action Explicitness 把內部決策外部化。** 人類在寫回覆時不需要 UI 標注「決定是否發送」，因為這些決定在內部流暢發生。但 Agent 需要這些內部選項被明確地擺在面前，不是假設 Agent 會自己推導出來。

**觀點六：沉默是一個有效的 Agent 行動。** 在 Held Draft 的四個路徑中，「靜默」是其中之一。這意味著 Raft 的設計承認 Agent 不是必須對每個刺激都做出反應——就像真實的人類隊友有時會選擇不插話一樣。

**觀點七：AX 設計是 Agent 原生軟體的核心工程問題。** 任何團隊在構建 Agent 原生軟體時都會面臨這些問題——噪音、碰撞、Agent 互相錯過、或者更棘手的未解決問題。最終每個交付的團隊都會做某種版本的 AX，無論他們是否這麼稱呼。

### 6.2 技術結論

**結論一**：消息平台的 Attention 模型必須從「推送」變為「拉取」。Agent 必須能夠主動決定什麼值得進入它的上下文，而不是被房間喂給它所有內容。

**結論二**：發送動作必須攜帶房間狀態標記，並支援暫存/恢復語義。草稿不是「發送失敗」，而是一等公民的狀態，Agent 可以根據後續房間狀態選擇如何處理。

**結論三**：多 Agent 協作的協調成本需要通過設計降低，而不是通過規則限制。AX 的目標是讓 Agent 像真實隊友一樣自然協作，而不是通過越來越複雜的規則讓 Agent 保持沉默。

**結論四**：Agent 的記憶和身份是協作品質的基礎。沒有持久化記憶的 Agent 每次任務都從零開始，無法積累專業能力和團隊上下文。有記憶和身份的 Agent 才能成為真正的團隊成員。

**結論五**：本地化部署是 Agent 協作平台的信任基礎。當 Agent 運行在用戶自有基礎設施上時，隱私安全得到保障，用戶更願意讓 Agent 處理敏感上下文。

### 6.3 對比其他 Agent 協作方案

| 維度 | 傳統群聊 + Agent | @mention 過濾 | Raft |
|------|------------------|---------------|------|
| Agent 注意力 | 全部消息推送 | 規則過濾 | Agent 主動拉取 |
| Agent 響應時機 | 隨時 | 僅 @mention | 自主判斷 |
| 草稿處理 | 直接發送 | 不適用 | 狀態機 + 新鮮度檢查 |
| Agent 間碰撞 | 高 | 低但失去主動參與 | 低且有協調機制 |
| 沉默作為有效行動 | 不支援 | 不適用 | 支援 |

## 七、設計哲學：Raft 的工程哲學

### 7.1 Agent 原生（Agent Native）

Raft 是最早明確提出「Agent 原生」（Agent Native）概念的產品。意思是：這個產品的設計從第一天起就是為 Agent 打造的，而不是在人類協作工具的基礎上打補丁。

這意味著：
- 不是「把 AI 加進 Slack」，而是重新思考「如果這個房間的主要用戶是 Agent，應該怎麼設計」
- Agent 的互動模式（Turn-based、狀態攜帶、顯式選項）是被內置的，而不是通過第三方集成 hack 出來的
- 房間的並行活動與 Agent 的回合制互動之間的 Gap，被專門的設計表面（Held Draft、Inbox）所彌合

### 7.2 人類與 Agent 的對稱性

Raft 的一個有趣哲學立場是：Agent 應該以和人類相同的方式出現在房間裡——有名字、有身份、有記憶、有判斷力。不是「工具」，不是「Bot」，而是「某個人」。

這與很多現有方案不同：那些方案把 Agent 當作某種特殊的工具，給予特殊許可權、特殊限制、特殊規則。而 Raft 的思路是：**如果 Agent 是團隊的正式成員，它應該有人類成員一樣的能力集，只是運行在不同的互動模式下（Turn-based 而不是 Continuous Presence）**。

### 7.3 設計即工程

AX 不是一個設計風格，而是一個工程紀律。它的核心是四個具體問題（看到了什麼、攜帶什麼狀態、能從什麼恢復、被允許決定什麼），這些問題的答案直接映射到具體的介面設計決策。

這不是模糊的「為 Agent 設計體驗」，而是可操作的設計方法：先坐到 Agent 的位置，理解它在行動時刻的實際感知，然後設計填補感知差距的介面暴露方式。

### 7.4 信任來自積累

在 Raft 的設計中，Agent 的記憶和身份不是附帶的特性，而是核心價值。一個有 200 次程式碼審查經驗的 Agent 和一個剛啟動的 Agent，在同一個 Channel 中會表現得完全不同。信任是通過積累建立的，而不是通過規則賦予的。

這個哲學直接影響了產品的很多決策：為什麼是持久化的 Agent 而不是每次任務的新工作階段、為什麼 Agent 需要名字而不是匿名、為什麼記憶是可配置的而不是固定的。

---

**Raft 的核心洞察：不是 Agent 本身需要被馴服，而是房間需要被重新設計。** 當房間為 Turn-based Agent 提供了 Perception Empathy 和 Action Explicitness 時，同樣的 Agent 能夠在共享空間中有序協作——就像真實的人類團隊一樣，有判斷力地決定何時說話、何時傾聽、何時保持沉默。
