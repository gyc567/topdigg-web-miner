## 一、Harper 是什么？一句话说清

**Harper 是一款免费、开源的英文语法检查器，所有检查都在你自己的设备上完成，一个字节都不会上传到云端。**

如果你用过 Grammarly，可以把 Harper 理解为它的"开源平替"——但这个类比其实低估了它。Harper 的目标不是复制 Grammarly，而是回答一个更根本的问题：**语法检查这件事，真的需要把文字发到别人的服务器上吗？**

先看基本信息（以下数据均经 GitHub 官方仓库与官网交叉验证）：

| 项目 | 信息 |
|------|------|
| 定位 | 本地优先（local-first）的英文语法检查器 |
| 作者 | Elijah Potter，现任 Automattic Code Wrangler |
| 名字由来 | 致敬小说家 Harper Lee（《杀死一只知更鸟》作者） |
| 技术栈 | Rust 编写，可通过 WebAssembly 在浏览器运行 |
| 开源协议 | Apache-2.0，完全免费 |
| 所属 | 2024 年 11 月 21 日被 Automattic（WordPress.com 母公司）收购 |
| GitHub 热度 | 约 13.4k Star，持续高频更新（2026 年仍在密集发版） |
| 支持语言 | 仅英文（含英、美、加、澳、印五种方言） |

## 二、诞生背景：一个开发者对行业现状的"双重不满"

Harper 的作者 Elijah Potter 在官方 README 里说得很直白：他做 Harper，是因为受够了现有工具。他的吐槽值得逐条保留，因为它们精准命中了两款主流产品的结构性问题。

**对 Grammarly 的不满：**

1. **太贵，且太强势**——订阅价格高，建议还常常脱离上下文，"经常是错的"；
2. **隐私噩梦**——你写的每一个字都会发到 Grammarly 的服务器。隐私政策说不卖数据，但不代表不会拿去训练大模型；
3. **网络延迟破坏心流**——每次检查都要走一次网络往返，改稿的节奏被拖慢。

**对 LanguageTool 的不满：**

1. **内存怪兽**——需要好几个 GB 的内存，还要下载约 16GB 的 n-gram 数据集；
2. **太慢**——检查一篇中等长度的文档要数秒。

于是 Potter 给自己定了一个工程目标：检查延迟压到**毫秒级**、内存占用做到 **LanguageTool 的 1/50 以下**、且**完全私有**。Harper 就是这三个约束条件下的产物。

这里有个值得注意的细节：Harper 的官网写着"建议在 10 毫秒内给出"，而 Automattic 的收购公告说的是"20 毫秒以内——不到某流行在线语法工具耗时的 1%"。两个数字口径不同，但指向同一结论：**本地计算的延迟，比云端方案低了至少两个数量级。**

## 三、核心原理：为什么它能又快又私密？

这部分是给想搞懂"它是怎么做到的"的读者准备的，我们尽量说人话。

### 1. 不用大模型，用规则引擎

在人人都在往产品里塞 LLM 的时代，Harper 做了一个反潮流的决定：**检查规则完全由人工编写的确定性规则构成，没有 LLM 参与，没有遥测，没有云端往返。**

这带来三个直接好处：

- **快**：规则匹配是纯粹的本地计算，Rust 的性能加上极小的内存占用，让反馈快过打字速度；
- **稳**：同样的输入永远得到同样的输出，不会像大模型那样"看心情"给建议；
- **小**：整个引擎小到可以编译成 WebAssembly，直接在浏览器标签页里跑。

### 2. Rust + WebAssembly：一次编写，到处运行

Harper 的核心是 `harper-core`（Rust 库），往上分出三条产品线：

- **harper-ls**：语言服务器（LSP），任何支持 LSP 协议的编辑器都能接入——VS Code、Neovim、Helix、Emacs、Zed、Sublime Text 一次全覆盖；
- **harper.js**：JavaScript/WebAssembly 封装，Obsidian 插件、浏览器扩展（Chrome/Firefox）、WordPress 插件都建立在它之上；
- **原生应用**：桌面客户端（近期版本已支持 Slack 和 Discord 场景）。

这套架构的聪明之处在于：**语法规则只维护一份，分发渠道却几乎无限。** 每新增一个编辑器支持，边际成本接近零。这是典型的"协议红利"——LSP 本来是给代码补全设计的协议，Harper 把它变成了语法检查的分发管道。

### 3. 只检查代码里的"人话"

对开发者特别贴心的一点：在代码编辑器里，Harper 只会检查注释、文档字符串这些自然语言部分，不会对着你的变量名指手画脚。这也是它"为开发者而生"标签的由来。

## 五、犀利观点：Harper 真正的价值与被高估的部分

### 观点一：Harper 的护城河不是"免费"，而是"确定性"

很多人把 Harper 归类为"免费的 Grammarly"，这是看浅了。它真正的差异化是**架构层面的确定性**：本地运行意味着隐私不是一个"政策承诺"，而是一个"物理事实"——数据根本没有离开设备的通道。对律师、记者、企业法务这些对文本外泄零容忍的人群，这种"无法泄露"比"承诺不泄露"高了一个维度。Grammarly 的隐私承诺依赖信任，Harper 的隐私依赖架构，后者无法被一次政策更新推翻。

### 观点二：Automattic 买它不是要做"Grammarly 杀手"

2024 年 11 月收购时，多数报道把 Harper 放在"Grammarly 竞品"的叙事里。但看 Automattic 的动作就明白：它计划把 Harper 集成进 WordPress.com、WooCommerce 和 Jetpack。**WordPress 驱动着全球约四成的网站**——Automattic 要的不是抢 Grammarly 的用户，而是给整个 WordPress 生态装上写作基础设施。Matt Mullenweg 自己的话说得很清楚："我们在云端做的事情太多了，边缘端有大量的算力和潜力。"Harper 是他边缘计算布局里的一颗棋子，和 Gutenberg、Playground 并列。

换句话说：**Grammarly 做的是一门订阅生意，Harper 被买下来是做一层协议。** 这是两种完全不同的战争。

### 观点三："不用 LLM"在今天反而成了稀缺资产

2026 年回看，Harper 最反常识的决策恰恰是它最值钱的地方。当所有写作工具都在比谁的模型更大时，Harper 证明了另一条路：语法错误里有一大类（拼写、大小写、主谓一致、固定搭配）是**确定性问题**，根本不需要概率模型。用大模型检查这些问题，就像用火箭送外卖——贵、慢、还会偶尔送错地址。规则引擎在这类问题上的性价比和可靠性，短期内不会被颠覆。

### 观点四：但别神化它——天花板同样明显

客观地说，Harper 的短板和它的优点一样突出：

1. **仅支持英文**，且团队明确表示要先把英文做到极致再扩展，多语言遥遥无期；
2. **规则引擎有天花板**——涉及语义理解、风格润色、语气调整的需求，规则天然做不到，这正是 LLM 方案的主场；
3. **误报与漏报并存**——It's FOSS 的实测标题就很微妙："我喜欢它……呃，算是吧"。规则写得再勤奋（社区贡献者几乎每天都在加新规则），覆盖面也追不上语言本身的复杂性；
4. **商业化路径未明**——完全免费 + Apache-2.0，它的存续目前绑定在 Automattic 的战略耐心上。

一句话总结这部分：**Harper 是"够用、可信、零成本"的最优解，但不是"最强"的解。** 它赢下的是隐私和速度这两个战场，而不是智能程度那个战场。

## 七、谁该用 Harper？怎么上手？

**推荐人群：**

- 写英文技术文档、README、博客的开发者（VS Code/Neovim 用户几乎零成本接入）；
- Obsidian 重度用户（官方插件开箱即用）；
- 对隐私敏感的文字工作者——合同、病历、未公开的稿件，不适合进任何云端；
- 想给自家产品嵌语法检查能力的开发者（`harper.js` 或 `harper-core` 直接集成）。

**不推荐人群：**

- 需要中文或其他非英文检查的用户；
- 指望它做深度润色、改写、语气优化的用户——那不是它的战场。

**上手路径：** 普通用户装 Chrome/Firefox 扩展即可；开发者在自己编辑器的 LSP 配置里挂上 `harper-ls`；Obsidian 用户在社区插件市场搜 Harper。全部不需要注册账号。

Harper 证明了一件被行业淡忘的事：**不是所有问题都需要上云、上模型、上订阅。** 把工程约束做到极致，本身就是一种产品力。如果你的工作是"写正确的英文"，而不是"写出惊艳的英文"，Harper 目前是这个星球上性价比最高的选择——毕竟，免费且不卖你数据的工具，通常意味着你也不用成为商品。
