# 编程Agent如何完成大型软件任务？Factory AI研究揭示关键转折点

## 引言

当AI在数学奥赛上拿金牌、在组合优化问题上突破几十年旧有边界时，人们开始相信AI编程已经不成问题。

但事实是：**AI模型擅长的是那些"成功标准紧凑且稳定"的问题**。而大型软件任务恰恰相反——需求描述的是结果，但从来不说明"必须运行什么、必须检查什么、必须比较什么，才能说这项工作完成了"。

Factory AI最近发布的研究深入探讨了这一问题：为什么相同的模型，在面对大型软件重构任务时，单Agent表现远低于预期？引入"外部可执行完成标准"后，同一个模型的表现为何能产生质的飞跃？

---

## 一、问题：为什么单Agent会"提前停止"

### 1.1 一个真实的实验

Factory AI在ProgramBench基准测试上设计了一个对照实验：

**任务**：从零开始重建GDAL（地理空间数据处理的事实标准工具，1998年启动至今，支持200多种光栅和矢量格式）。

**实验条件**：
- 单Agent模式：Droid独立实现、自我检查、自我判断何时完成
- 系统模式：一个Validator角色先建立"完成标准"，然后用这个标准来"考核"Implementer的工作

**结果震惊了研究者：**

| 模式 | 代码行数 | 行为覆盖率 |
|------|---------|-----------|
| 单Agent | 17,000行 | **36%** |
| 系统（含独立标准） | 115,000行 | **90%** |

同样的模型、同样的时间——唯一的区别是：**是否有一个人提前建立好了"怎么才算完成"的标准**。

单Agent停下来，是因为"按照自己的评估，它已经完成了"。

### 1.2 本质原因：局部验证无法覆盖整体

编程Agent通常的验证方式是：实现一个模块，写几个检查，跑一下，看看结果。这在小型任务中很有效。

但大型任务必须被分解为多个特性、子系统和多轮工作。当Agent到达每个局部时，它也决定"什么算证据"以及"这些证据是否足够"。**这些检查继承了产生它们的工作范围**——它们可以验证Agent计划要构建的一切，但不包括它从未代表的特性、交互或约束。

Agent可以做出稳步的、局部正确的进展，然后在大部分结果仍然缺失的情况下停下来。问题不在于它无法实现其余部分——而是它**从未建立一个关于"还有什么没做完"的完整说明**。

## 二、解决方案：建立外部可执行完成标准

### 2.1 三角色系统架构

Factory AI设计的系统包含三个角色：

```
┌─────────────────────────────────────────────────────────────┐
│                    Orchestrator（编排器）                    │
│  委托任务给Implementer和Validator，决定何时交付              │
├──────────────────────────┬──────────────────────────────────┤
│    Implementer（实现者）  │      Validator（验证者）          │
│  调查参考程序            │  在实现之前先建立"完成标准"        │
│  构建候选程序            │  用这个标准测量Implementer的输出   │
│  执行开发循环            │  不向Implementer暴露测试用例       │
└──────────────────────────┴──────────────────────────────────┘
```

**关键设计："信息墙"（The Wall）**

Validator构建的instrument和原始结果留在Validator侧，只有汇总后的发现穿过信息墙传递给Orchestrator。Implementer永远看不到测试用例或原始输出。

### 2.2 Validator如何建立"完成标准"

以GDAL为例，Validator构建的instrument包含数百个测试用例：

```python
D('hillshade.combined', ['raster', 'hillshade', '--variant', 'combined', 'dem.tif', 'out.tif'])
D('contour.levels', ['raster', 'contour', '--levels', '120,150,180', 'dem.tif', 'out.geojson'])
```

评分策略比较四个通道：退出码、stdout字节、stderr字节、完整工作树增量。

### 2.3 外部循环如何运作

```
1. Orchestrator选择应该测量什么
2. Validator测试当前candidate并解释失败
3. Orchestrator决定哪些发现是真实的，下一步该做什么
4. Implementer独立调查参考程序并推进candidate
5. 当instrument停止揭示有意义差异时，扩展薄弱区域
```

## 三、实验结果

### 3.1 三个模型的表现

| 模型 | 单Agent中位数 | 系统模式中位数 | 差距缩小 |
|------|-------------|--------------|---------|
| **Fable 5 (xhigh)** | 56.7 | **89.3** | **73%** |
| **Kimi K3 (high)** | 45.1 | **75.4** | **42%** |
| **GPT-5.6 Sol (max)** | 48.6 | **66.2** | **25%** |

关键数字：**GDAL重建从36%→90%，7-Zip从54%→95%，DuckDB从34%→80%**。

### 3.2 重要发现

**计算预算不是瓶颈**——每个单Agent活动结束，都是因为Agent自己决定结束它。额外的计算无助于一个不愿花费它的Agent。真正改变的是**完成的判断标准**。

---

## 四、设计哲学归纳

### 4.1 验证必须在实现之前建立

完成标准不能悄悄地围绕已经构建的内容坍塌。它应在实现将任务缩减为单个工作项之前，从需求和相关真实来源中推导出来。

### 4.2 "信息墙"设计防止了标准被"污染"

如果Implementer能看到测试用例，那些用例就变成了目标。保持Validator的instrument对Implementer不可见，确保了测量的公正性。

### 4.3 外部标准比模型能力更重要

单Agent不是缺乏技能，而是**缺乏完成标准**。对于大型软件任务，瓶颈在于判断力而非实现力。

---

## 五、核心观点总结

**结论一：AI擅长"紧凑标准"的问题，大型软件任务不属于此类**

AI在数学、约束优化等领域的突破，是因为"成功"可以被完整定义和验证。但软件任务的"完成"往往是模糊的。

**结论二：单Agent会"提前停止"，不是因为能力不足，而是因为没有完整的"未完成清单"**

它不知道自己做完了多少，只知道自己做了多少。

**结论三：引入外部Validator建立完成标准，可以让同一模型的表现产生质的飞跃**

Fable 5在GDAL上从36%→90%的跨越，不是模型升级带来的，而是"建立标准"这个动作带来的。

**结论四："信息墙"设计防止了标准被"污染"**

一旦测试用例变得可见，它就变成了目标，通过它不代表它所代表的整体行为空间。

**结论五：这套方法可以泛化到真实软件工作**

产品任务可能从用户批准的流程和设计中提取标准；迁移任务可能从被替换的系统中提取标准。通用的是**需要一个外部的、可执行的完成标准**。

---

## 结语

这项研究最深刻的意义，是一个**认知框架的转变**：

过去我们认为，要让AI更好地完成软件任务，关键在于提升模型的代码能力。但Factory AI的实验表明，**问题不在于"能不能写"，而在于"知不知道写完了没有"**。

当我们设计下一个编程Agent系统时，或许应该问的不是"这个模型有多强"，而是"这个系统有没有一个外部的、可执行的完成标准"？

答案不同，系统的架构就会完全不同。
