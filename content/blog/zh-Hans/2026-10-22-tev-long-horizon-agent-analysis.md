# Tev 深度解析：用「潜在世界」造数据，用稠密奖励训长程智能体

> 论文：*Tev: Scaling Long-Horizon Agentic Environments with Dense Progress Rewards*
> 作者：Wenbo Hu、Shraman Pramanick、Krishna Kumar Singh、Nanyun Peng、Kai-Wei Chang、Yong Jae Lee（Adobe Research + UCLA）
> 论文主页：https://arxiv.org/abs/2610.18868 ｜ HTML 版：https://arxiv.org/html/2610.18868v1
> 项目主页：https://tev-agent.github.io/
> 模型权重：https://huggingface.co/gordonhu/Tev-27B ｜ https://huggingface.co/gordonhu/Tev-320B

## 引子：一个被数据卡死的领域

过去两年，AI Agent 的能力曲线几乎完全由「任务有多长」划定。

短任务和中等任务是甜蜜区。SWE-Smith 有 5 万个环境，TMAX-15K 有 1.46 万个，CLI-Gym、SETA、Endless Terminals 各有几千到上万不等。这些数据集足够大，训练流水线足够成熟，模型确实在进步。

但当你把任务时间尺度拉长到「数小时到数天」——真正的开放式数学问题、自动化机器学习研究、生产事故根因分析——整个领域撞上了一堵墙。

这堵墙由两个缺口构成。

**第一个缺口是数据。** 长跨度任务只以人工编写的评测集形式存在。Agents' Last Exam（ALE）和 Terminal-Bench（TB）里的每一个实例，都需要专家投入数周时间。ALE-CM 全集只有几十到几百个题目，而且它们只能被用来评测，不能被用来训练。这造成了一个极其尴尬的结构性矛盾：

> 智能体训练语料很多，但都很短；长任务确实存在，但只是少量人工评测集。

中间那块「大规模长跨度训练数据」，是彻底空白的。

**第二个缺口是奖励。** 就算你想造数据，长任务的奖励是稀疏的。终局奖励只在任务完成时才出现，而长任务上模型的通过率往往只有 5% 甚至更低。这意味着在 GRPO 这类组内相对的强化学习算法里，绝大多数采样组全部失败，优势值处处为零，对梯度的贡献完全是零。

论文用了一个非常具体的数字来说明这件事：如果任务通过概率 $p=0.05$、每组 $G=8$ 条 rollout，那么 **66% 的采样组被完全浪费**；当 $p=0.01$ 时，浪费率高达 **92%**。而这恰恰是训练早期、策略最弱、最需要信号的阶段。

Tev 这篇论文做的事情，一句话概括就是：

> **从「已知正确答案的世界」反向造出任务，再用这个世界的真值给训练的每一步打分。**

下面我们把它的核心思想、方法结构、实验结论和可复现教程完整拆开。

---

## 一、核心思想：潜在世界优先（Latent-World-First）

### 1.1 与传统流水线的根本分歧

目前主流的合成数据流水线大致是这样的：让语言模型生成一个任务描述，再生成对应的输入文件，再生成验证器或测试用例。整个链条没有任何一处存在「正确答案」——只有看起来合理的东西。

这种做法有三个众所周知的问题：

1. **验证器不可靠。** 生成的测试用例可能本身就写错了。
2. **任务与验证器可能对不上。** 这是最致命的。论文称之为**制品漂移（artifact drift）**：环境、任务、验证器被分别生成，各自单看都成立，合起来却在描述两个不同的问题。
3. **没有中间状态。** 只有终局是非黑即白的，你不知道 agent 到底做对了哪一步、离目标还有多远。

Tev 的做法是把整个链条倒过来。

**先构造一个潜在世界（latent world）$W$**：它是这个任务领域完整且正确的状态。比如一个零售仓库的客户、产品、交易记录；一个分布式 checkpoint 的张量分片和拓扑；一个 Kubernetes 集群的资源清单。

在这个世界里，**正确答案天然存在**。因为世界本身就是「一切正常时的样子」。

然后，把这个世界**渲染（render）**成 agent 实际会看到的输入文件，再施加**受控的、可逆的损坏**，得到 agent 拿到的初始工作区 $s_0$。

关键在于：**潜在世界 $W$ 同时充当了任务提示、输入文件、验证器、进度打分器四者的共同来源。**

论文把这个关系写成了一个简洁的式子：

$$E=(x,\;s_{0},\;\operatorname{ver}_{W},\;\Phi_{W}),\tag{1}$$

一个环境 $E$ 的四个组成部分，全部是同一个 $W$ 的函数：

- $x$：任务提示（agent 能看到的唯一描述）
- $s_0$：输入目录树（agent 的初始工作区）
- $\operatorname{ver}_{W}$：严格的通过/不通过验证器，依据 $W$ 检查 agent 的输出文件
- $\Phi_{W}$：进度势能，第 3 节详述

这一个锚点，从根上杜绝了制品漂移。因为真值在构造上就是正确的，因为渲染可以往返还原（round-trip），因为损坏是已声明且可逆的，所以 **agent 的初始工作区 $s_0$ 完全决定了 $W$**——正确答案可由 agent 实际看到的内容计算得出，不需要运行求解器。

### 1.2 三个推论

这个设计的漂亮之处在于，它顺手解决了三个别的方案要靠额外东西才能解决的问题。

**推论一：难度是可控的旋钮，不是碰运气。**

因为 $W$ 是先造出来的，所以「变大一点」是纯代码操作，不需要重新让模型生成任何东西。规模档位（scale tier，默认 unit / small / full）控制 $|W|$，工作流 DAG 的依赖深度控制「必须完成多少阶段才能拿到正确输出」。两个旋钮互相独立。

**推论二：中间状态免费。**

因为每个正确中间态都是 $W$ 的渲染，所以打分不需要人工标注步骤、不需要训练一个 process reward model、不需要语言模型当裁判。$\Phi$ 是确定性的、可复现的、零模型调用的。

**推论三：边际成本极低。**

生成一个环境（含跑两个参考求解器、封存隐藏测试套件、预览进度势能）中位数只需 **30 秒 CPU 时间**（90 分位 82 秒），**零模型调用**。这是对比手工编写的专家工时（数小时/题）的量级差异。而一次性的生成器编写成本，可以被它所有种子和规模档位摊薄。

更狠的是：论文指出 Tev-Gym 可以被进一步规模化——让 coding agent 去写生成器，生成器跨种子、跨规模档位批量产出新环境，**全程不需要再调用任何模型**。

## 二、方法拆解：六阶段环境合成流水线

第 2.1 节把环境合成拆成六个阶段。整个流水线**没有一个语言模型参与**。

### 阶段 0：任务来源

针对 ALE-CM 的七个计算与数学子域（对应 Tev-Gym 的七大领域），每个领域先建立一个**真实任务规格池**：

| 子域 | 名称 | 覆盖范围 |
|------|------|----------|
| 9.1 | Software Engineering | 功能实现、调试、重构、测试编写 |
| 9.2 | Data & Analytics Engineering | ETL/ELT 流水线、推荐排序系统、特征工程 |
| 9.3 | AI Engineering, Safety & CS Research | 模型训练评测流水线、论文复现、checkpoint 管理、对齐实验 |
| 9.4 | Mathematical & Operations Research | 组合优化、博弈均衡、应用数学与数论、概率估计与滤波 |
| 9.5 | Cybersecurity & Digital Forensics | 逆向工程、恶意软件配置提取、网络包分析、事件取证 |
| 9.6 | Infrastructure Engineering & Cloud Operations | K8s 迁移与配置、生产事故根因分析、OS 加固、IaC |
| 9.7 | Quantum Computing | 量子线路构建与模拟、纠错码分析、噪声模拟 |

规格池的来源包括：从互联网挖掘的规格、MLE-bench 的 82 个 Kaggle 竞赛，以及量子计算域（没有任何 benchmark 覆盖）使用的公开参考材料（MQT Bench 线路套件、Qiskit Experiments 手册、TeNPy 的 DMRG 示例）。

从池中随机采样规格，然后**围绕每条规格自己写一个生成器**。注意这里的边界：生成器参考规格的结构和难度，**绝不复制**它的 prompt、输入、答案或评分文本。

三道过滤：
- **可行性过滤**：只保留「真值在构造上可知」且「纯 CPU 可批量执行」的规格，排除依赖线上服务、音视频、重型工具链、GPU kernel、开放式「优化一下」类任务。
- **相似度闸门**：新生成器的代码、规格、生成数据与所有已注册生成器比对，拒绝近重复。
- **对抗评审**：攻击每个通过前两关的规格，寻找隐藏捷径、过短跨度、伪装来源。

### 阶段 1：世界构建

每个生成器都是一个**带种子的程序**。给定 `(seed, scale_tier)`，它程序化生成潜在世界 $W$，并做两件事：

1. **校验不变量**：唯一标识、合法连接、有限度量。
2. **抽取缺陷计划（defect plan）**：精确指明 $W$ 中哪些记录、分片、字段将被损坏，以及由哪个已声明的算子损坏。

这个缺陷计划是「种子派生」的，所以同一个生成器在两个不同种子下，必然产出两个可证明不同的世界。

### 阶段 2：工作流图

把环境的工作流编译成**有向无环图（DAG）**，带显式依赖、允许并行性、每阶段语义工作量估算。例如零售仓库 ETL 场景：

```
profile-sources → reconcile-facts / normalize-dimensions → load-facts
                → aggregate-validate → package-sidecars
```

**这个 DAG 由代码依据 $W$ 的规模生成，过程中没有模型参与。**

DAG 的两个关键性质：

- **关键路径**（最长的依赖阶段链）定义任务的**跨度（horizon）**。
- **各个阶段构成进度势能的骨架**（第 3 节）。

注意论文这里的一个方法论选择：**用 DAG 关键路径而不是实际 rollout 长度 $T$ 来度量跨度**，因为 $T$ 会随着 agent 的绕路而虚高。DAG 深度是结构性的、可控的。

### 阶段 3：制品渲染

把 $W$ 投影到环境声明的公共接口上，物化成目标线格式：

- CSV / TSV 分区
- JSON 记录
- SQLite 数据库
- safetensors 分片
- 去除符号的二进制文件
- 基础设施清单

**渲染是 $W$ 的纯函数。** 并且在继续之前，流水线会**断言它能往返还原**——即从渲染后的文件里能精确恢复出 $W$。

### 阶段 4：受控损坏

把阶段 1 的缺陷计划施加到渲染后的文件上，注入模式漂移（schema drift）、重复与缺失记录、类别漂移、打乱的分片索引、过期缓存等。

被损坏的树 $s_0$ 就是 agent 收到的任务，未被改动的 $W$ 就是真值。

### 阶段 5 与阶段 6：公开规格与隐藏测试套件

**阶段 5** 输出公开契约 $x$：输入角色、所需输出制品及其模式、有序的需求、权威优先级规则、允许的工具链。这是 agent 能看到的**唯一**描述。

**阶段 6** 在 agent 视野之外封存隐藏套件，用于验证阶段：
- **变形变换（metamorphic transform）**：保持语义的重写，**不得**改变评分。
- **陈旧输出反事实（stale-output counterfactual）**：貌似合理但错误的状态，**必须**判为不通过。

这一层的作用是防止验证器过窄，以及防止「提交一个陈旧但看起来合理的结果」蒙混过关。

### 2.2 覆盖度、校准与八道准入门槛

**多样性。** 每个环境在 **19 条覆盖轴**上被标注：子领域、规模、四条跨度轴、工作流阶段、工具能力、制品角色、关系类型、损坏类别等。

论文特别强调「行为性轴」的价值：改变某个轴的取值，会改变 agent **必须修复什么**（损坏类别）、**如何修复**（工作流阶段、工具能力）、**通过哪些文件修复**（制品角色、关系类型）。

**可控难度。** 两个控制项：规模档位（unit / small / full）拉长操作跨度；DAG 依赖深度 + 损坏类别数量决定「必须完成多少阶段、必须按什么顺序」。

一个具体的数字感受：对于在三个规模档位都实例化的生成器，输入树中位数从 **17 个文件 / 51 KB（unit）** 增长到 **20 个文件 / 168 KB（small）**，再到 **28 个文件 / 586 KB（full）**，而**工作流 DAG 保持不变**。

**八道准入门槛。** 一个合成环境只有在通过全部八道与基准无关的门槛后才被接纳，每道门槛在生成时自动检查，并对应一个具名的失败类别：

| 门槛 | 强制要求 | 针对的失败类别 |
|------|----------|--------------|
| 奖励因果性 | 每个奖励分量在因果被变异时必须掉分 | 奖励了错误的结果 |
| 抗利用性 | 全部 **14 个作弊探针**必须得 0 分 | 验证器漏洞、抄近路被接受 |
| 角色独立性 | 参考求解器 / 替代求解器 / 严格验证器 / 进度打分器**代码闭包互不相交** | 求解器与打分器共享偏差 |
| 求解器一致性 | 两个独立编写的求解器必须在每个种子上产出完全相同的输出树 | 仅验证器通过、规格未解决 |
| 进度有效性 | 部分正确状态上 $0<\Phi<1$；沿参考轨迹单调升到 1；倒退时产生负增量 | 无效的过程信号 |
| 变形不变性 | 保义重写不改变评分；陈旧输出必须失败 | 验证器过窄、陈旧状态被接受 |
| 六种子多样性 | 至少 6 个种子产出不同的世界身份 / 公共树哈希 / 任务 ID | 退化环境、模板重复 |
| 公开契约卫生 | prompt 和公共树中不得出现任何私有权威、参考答案或验证器代码 | 答案泄漏 |

关于**作弊探针（gaming probe）**，论文列了 14 种作弊策略，包括：空输出、最小但 schema 合法的输出、复制输入、单种子硬编码、路径穿越、私有查询等。每一种都必须在严格验证器和进度打分器下同时得 0 分。

关于**角色独立性**，这一条值得单独强调。它要求：

$$\operatorname{ver}_W(\pi^{\mathrm{ref}}(s_0))=\Phi_W(\pi^{\mathrm{ref}}(s_0))=1,\quad \pi^{\mathrm{ref}}(s_0)=\pi^{\mathrm{alt}}(s_0)$$

参考求解器 $\pi^{\mathrm{ref}}$（分数恰好 1.0）和**独立编写**的替代求解器 $\pi^{\mathrm{alt}}$ 必须在每个种子上产出完全相同的输出树。**一旦不一致，就视为规格未解决，直接拒绝该环境。**

论文解释了这个设计的意义：求解器审计独立于验证器——两个求解器都不 import 验证器代码，所以它们的一致性是关于**规格本身**的证据，而不是关于**打分器**的证据。

## 三、稠密奖励：从进度势能到 PPRS

### 3.1 为什么终止奖励会「饿死」组内相对 RL

先看 GRPO 的组内相对优势值：

$$\hat{A}_i=\frac{R_i-\operatorname{mean}(R_{1:G})}{\operatorname{std}(R_{1:G})+\epsilon}\tag{2}$$

其中 $R_i=\mathds{1}[\tau_i\ \text{passes}]$，即只有 rollout 提交且严格验证器 $\operatorname{ver}_W$ 接受时才为 1。

**核心问题**：如果一组 $G$ 条 rollout 全部失败，那么 $R_1=\cdots=R_G=0$，于是所有 $\hat{A}_i=0$。这个任务对梯度的贡献是零，这 $G$ 条 rollout 全部作废。

浪费比例是 $(1-p)^G$：

| 通过率 $p$ | $G=8$ 时的浪费组比例 |
|------------|---------------------|
| 0.05 | 66% |
| 0.01 | 92% |

论文还点出了一个更隐蔽的问题：**即使一组里只有一条成功，也好不了多少。** 那一条正样本面对的是 $G-1$ 条负样本，所有负样本拿到相同的负优势值，梯度**无法区分「差一点点」和「完全没进展」**。

在长跨度任务上，未训练开源模型的 $p$ 大约在十分之一甚至更低。所以「丢掉全失败组」或「重采样」这类做法，在长任务上直接扔掉了大部分 batch。

### 3.2 进度势能：来自潜在世界的确定性刻度

每个 Tev-Gym 环境都提供一份**进度契约**：一个节点集合 $V$，每个节点是输出工作区的一个可检查状态，派生自阶段 2 的工作流 DAG。节点带权重 $w_v>0$，$\sum_v w_v=1$，以及前置依赖集合 $\mathrm{pre}(v)$。

部分打分器 $c_v(s)\in[0,1]$ 直接对着潜在世界给 agent 当前的工作区 $s$ 打分。

**信用是前置依赖门控的（prerequisite-gated）**：$\tilde{c}_v(s)$ 取 $v$ 及其所有直接和间接前置节点中最小的部分分数。

于是进度势能为：

$$\Phi(s)=\sum_{v\in V}w_v\,\tilde{c}_v(s)\in[0,1]\tag{3}$$

这个设计带来三个由门槛强制保证的性质：

- **锚定（抗利用性）**：未改动的公共树和每一个作弊探针都严格得 $\Phi=0$；严格验证器接受时严格得 $\Phi=1$。
- **单调（进度有效性）**：随节点完成而上升，随已完成工作被破坏而下降。
- **独立（角色独立性）**：打分器代码闭包与验证器、参考求解器**互不相交**，一个打分器的缺陷不会被另一个继承。而且这些打分代码**不随公共树发布**。

论文特别强调「可扩展的奖励设计」：因为潜在世界在任务生成之前就定义了，每个正确的中间状态都能被直接渲染出来并被 $c_v$ 评估。这提供了**精确、确定性**的进度反馈，**不需要**人工步骤标签、不需要训练奖励模型、不需要语言模型裁判。

这是与主流方案最本质的分野。

### 3.3 PPRS：进度势能奖励整形

设一条 rollout 的工作区状态为 $s_0,\dots,s_T$，其中 $s_0$ 是未改动的公共树，故 $\Phi(s_0)=0$。

参照基于势能的奖励整形（PBRS，Ng et al. 1999），每步的整形奖励是势能的变化量：

$$r_t=\Phi(s_t)-\Phi(s_{t-1})$$

rollout 总奖励为：

$$R(\tau)=\mathds{1}[\tau\ \text{passes}]+\lambda\sum_{t=1}^{T}r_t=\mathds{1}[\tau\ \text{passes}]+\lambda\,\Phi(s_T),\tag{4}$$

其中 **$\lambda=0.25$，所有实验运行均使用此值**。

这里有四个设计细节，每一个都值得单独拎出来。

**细节一：PPRS 故意不保持最优策略不变。**

标准 PBRS 会把终止势能归零，从而保证最优策略不变。PPRS 保留了 $\lambda\Phi(s_T)$，**故意改变了优化目标**。这是一个明确的、承担了风险的偏离，论文在附录中坦诚地讨论了「什么被保留了、什么没有被保留」。

**细节二：提交是动作，不是状态。**

$\Phi$ 打分的是工作区，终局项打分的是策略**提交**的工作区。一条耗尽了回合或 token 预算但没提交的 rollout，**不会被终局打分**，只拿 $\lambda\Phi(s_T)$。这正是图 4 里那条「完整构建但未提交」的 rollout 能够达到 $\Phi=1$ 而终局奖励为 0 的原因。

**细节三：奖励只依赖最终状态。**

因为 $\Phi$ 只是工作区的函数，$R(\tau)$ 只通过最终状态 $s_T$ 依赖 rollout。这意味着**两条通过不同路径、步骤顺序不同、实现方式不同但最终工作区相同的 rollout，拿到完全相同的奖励**。这杜绝了奖励对「过程风格」的意外偏好。

**细节四：终局奖励的排序仍在最顶端。**

因为 $\Phi\le 1$，任何通过的 rollout 拿到 $1+\lambda=1.25$，严格高于任何失败的 rollout。所以没有任何一条 rollout 会因为「用完成度换部分进展」而获益。附录 B 对随机策略下偏好何时可能反转给出了界。

**代入 GRPO 之后，饥饿问题被修复了。**

一组中没有 rollout 通过时，奖励变成 $R_i=\lambda\Phi(s_T^{(i)})$。只要不同 rollout 进展到了不同深度，这些奖励就不同，组内优势值非零，且**按进展深度给 rollout 排名**。

论文的图 4 直观展示了这个效果：同一个仓库环境，$G=8$ 组 rollout，每轮实时打分。

- **仅终止奖励（红）**：所有 rollout 全部得 0。
- **渐进式奖励**：2 条提交了不完整仓库（圆圈）、5 条耗尽了 65k token 上下文（叉号）、1 条构建出完整仓库。

组内奖励终于有了差异，梯度终于有东西可学。

### 3.4 与已有做法的对比

| 方案 | 进展粒度 | 需要额外模型 | 主要缺陷 |
|------|---------|------------|---------|
| 终止奖励（稀疏） | 终局 | 否 | 全失败组优势值为零，浪费 66%–92% |
| 过滤相同奖励 / 选接近难度的任务 / 加专家前缀 | 终局 | 需要专家前缀 | 只是绕开问题，且丢弃 batch |
| 学习式评委 | 中间 | 需要训练评判器 | 引入额外偏差与训练成本 |
| 测试通过率等代理信号 | 粗粒度 | 否 | 只捕捉终局结果 |
| **PPRS（本文）** | **每个工作流阶段** | **否** | 需保证潜在世界正确构造 |

### 4.5 消融实验

消融在 9B 设定下进行。

**数据构造方式的消融：**

| 方法 | World | DAG | 隐藏真值 | 信号 | S@1 | S@5 | P@1 | P@5 | GPU-h/step |
|------|-------|-----|---------|------|-----|-----|-----|-----|------------|
| Qwen3.5-9B (base) | – | – | – | 无 RL | 0.25 | 0.33 | 0.06 | 0.06 | – |
| **Tev-9B (ours)** | ✓ | ✓ | ✓ | ΔΦ + 终止 | **0.29** | **0.40** | **0.07** | **0.11** | 9.0 |
| Public-view verifier | ✓ | ✓ | LLM | 终止 | 0.24 | 0.35 | 0.04 | 0.06 | 22.3 |
| Prompt-first | LLM | LLM | LLM | 终止 | 0.23 | 0.32 | 0.06 | 0.06 | 11.8 |
| Sparse (仅终止) | ✓ | ✓ | ✓ | 终止 | 0.25 | 0.32 | 0.06 | 0.06 | 16.7 |
| PPRS, pooled norm. | ✓ | ✓ | ✓ | ΔΦ + 终止 | 0.28 | 0.35 | 0.06 | 0.06 | 10.9 |
| Direct reward (additive) | ✓ | ✓ | ✓ | Φ + 终止 | 0.29 | 0.35 | 0.06 | 0.06 | 9.7 |

三个读数：

**读数一：两种「退化为 LLM 生成」的变体都不奏效，而且更贵。**

- **Public-view verifier**：让模型从 agent 视角写验证器（放弃隐藏真值）。**88% 的采样组在训练中被丢弃**，GPU 耗时 22.3 GPU-h/step，是完整方法的 2.5 倍。
- **Prompt-first**（标准 self-instruct 基线）：整条流水线换成「先出 prompt，再出输入、验证器、解法」，没有潜在世界也没有 DAG。

两种变体的 S@1 分别是 0.24 和 0.23，**都不超过基线的 0.25**；而完整方法领先它们 0.05–0.06（S@1）和 0.05（P@5）。

**读数二：稠密奖励必须「整形」，不能只是「相加」。**

- **Sparse（仅终止）**：S@1 = 0.25，且 GPU 耗时最高（16.7）。
- **PPRS, pooled norm.**（每条 rollout 归一化）：S@1 = 0.28，有提升但 P@1/P@5 没动。
- **Direct reward (additive)**（$\gamma=0$，直接用 $\Phi(s_t)$ 相加）：S@1 = 0.29，但 P@1 仍是 0.06。

完整 PPRS 相对稀疏奖励 **S@1 提升 0.04**，且**唯一一个把 P@1 从 0.06 抬到 0.07、P@5 从 0.06 抬到 0.11 的方案**。

论文对为什么 additive 不行的解释很关键：**直接相加会反复奖励高势能状态而不向前传播信用**，导致更多 rollout 在提交前耗尽上下文窗口，产生更长的轨迹。而完整 PPRS 用 return-to-go（$\gamma=1$）把进展向前传播信用，用**按回合索引归一化优势值**保留了后期回合的信用（避免把后期更小的 return 拿去跟整条 rollout 的均值比较）。

**读数三：27B 规模下差距进一步拉开。**

论文明确指出：在 27B 上，shape 后的奖励能训到完成，而**仅终止奖励产生的组几乎全是零优势值，一个完整的优化器 step 都走不出去**。

### 4.6 定性案例：k8s 支付 API 根因分析

论文给了一个 ALE-CM 上 Coding & System 域的具体案例（模型从一次 kubectl 抓取、Deployment/HPA YAML 和一个崩溃 pod 的日志，写出带逐字证据串和回滚结论的 JSON 根因报告）：

## 六、详细教程：如何复现 Tev-Gym 的方法

论文**尚未发布 Tev-Gym 的代码和数据**（项目主页的 Code 和 Data 按钮仍标记为 "soon"），**只发布了模型权重**。所以下面这份教程是**方法复现指南**——照着论文描述自己实现一套等价的流水线——而不是开箱即用的脚本。

### 步骤 0：准备环境

```bash

python3 -m venv .venv && source .venv/bin/activate
pip install numpy pandas scipy pytest

# 确认你的环境是「纯 CPU 可执行」的，这是可行性过滤的要求
```

工具链要在每个环境的公开契约里声明（例如 `python3`、`sqlite3`），agent 的工作区初始只放公共树。

### 步骤 1：写生成器（阶段 1–4 的核心）

一个生成器就是一个**带种子的纯函数**：`make_world(seed, scale_tier) -> World`。它必须做到：

```python
import random, hashlib

def make_world(seed: int, tier: str = "unit"):
    """生成潜在世界 W。必须是 seed 的纯函数，无副作用，无模型调用。"""
    rng = random.Random(seed)

    # 规模档位决定 |W|
    n_customers = {"unit": 30, "small": 240, "full": 480}[tier]
    n_tx_per_month = {"unit": 48, "small": 480, "full": 960}[tier]

    world = {
        "customers": [
            {"id": f"C{i:05d}", "name": f"cust_{i}"}
            for i in range(n_customers)
        ],
        "products": [
            {"id": f"P{i:05d}", "sku": f"sku-{i:04d}", "price": round(rng.uniform(1, 500), 2)}
            for i in range(n_tx_per_month)
        ],
        "transactions": [],
    }

    # ---- 不变量校验（阶段 1）----
    assert len({c["id"] for c in world["customers"]}) == n_customers, "ID 必须唯一"
    assert all(t["qty"] > 0 for t in world["transactions"]), "度量必须有限"

    # ---- 缺陷计划（阶段 1）：精确指明要损坏什么 ----
    defect_plan = {
        "operators": ["duplicate_records", "missing_records", "schema_drift"],
        "targets": rng.sample(range(len(world["transactions"])), k=2),
    }
    world["_defect_plan"] = defect_plan
    return world
```

**三条硬性纪律**：

1. **纯函数。** 不读时间、不读环境变量、不调用网络、不调用模型。相同 `(seed, tier)` 必须产出完全相同的世界。
2. **缺陷计划写在世界里。** 破坏发生在渲染之后，且计划是种子派生的——这样「哪些被破坏」本身就是世界的一部分，可以被独立重建。
3. **不 import 验证器代码。** 这是角色独立性门槛的要求，后面评分阶段会检查代码闭包互不相交。

### 步骤 2：定义工作流 DAG（阶段 2）

DAG 决定跨度，也决定进度势能的骨架。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Stage:
    name: str
    depends_on: tuple[str, ...]      # 显式依赖
    weight: float                     # 进度节点权重
    parallel_with: tuple[str, ...] = ()  # 允许并行

WORKFLOW = (
    Stage("profile-sources",   (),                    0.15),
    Stage("reconcile-facts",   ("profile-sources",),   0.25),
    Stage("normalize-dimensions", ("profile-sources",), 0.15),
    Stage("load-facts",        ("reconcile-facts", "normalize-dimensions"), 0.20),
    Stage("aggregate-validate",("load-facts",),        0.15),
    Stage("package-sidecars",  ("aggregate-validate",), 0.10),
)

def critical_path():
    """最长依赖链 = 任务跨度。这是结构性的度量，不受 agent 绕路影响。"""
    memo = {}
    def depth(s):
        if s.name in memo: return memo[s.name]
        memo[s.name] = 1 + max([depth(d) for d in s.depends_on], default=0)
        return memo[s.name]
    return max(depth(s) for s in WORKFLOW)
```

权重和必须归一化到 1（对应式 (3) 的 $\sum_v w_v=1$）。

### 步骤 5：写严格验证器与进度打分器（阶段 5–6）

两者**必须是两份互不相交的代码**。

```python
# verifier.py —— 严格通过/不通过，只看最终产出
def verify(world, output_dir) -> bool:
    """对照 W 检查 agent 的输出文件。严格、确定性、无副作用。"""
    for path, checker in world["_verifiers"]:
        if not checker(world, os.path.join(output_dir, path)):
            return False
    return True

# progress.py —— 进度打分器，独立代码闭包
def partial_score(world, output_dir) -> dict:
    """对每个进度节点给出 [0,1] 的部分分数。"""
    return {v: checker(world, output_dir) for v, checker in world["_partial_scorers"].items()}

def progress_potential(world, output_dir) -> float:
    """式 (3)：前置依赖门控的加权求和。"""
    scores = partial_score(world, output_dir)
    gated = {}
    for v, s in scores.items():
        pre = world["_prereqs"][v]
        gated[v] = min([scores[v]] + [gated[p] for p in pre]) if pre else scores[v]
    return sum(world["_weights"][v] * gated[v] for v in scores)
```

前置依赖门控的实现要点：**必须拓扑序计算**，因为 $\tilde{c}_v$ 依赖前置节点的 $\tilde{c}$，而不只是原始分数。

### 步骤 7：实现 PPRS 奖励

```python
import numpy as np

LAMBDA = 0.25  # 论文中所有运行均为 0.25

def rollout_reward(workspace_states, passed: bool) -> float:
    """
    式 (4)：R(τ) = 1[passes] + λ * Φ(s_T)

    注意 telescoping：Σ ΔΦ = Φ(s_T) - Φ(s_0) = Φ(s_T)，因为 Φ(s_0)=0。
    """
    phi_final = workspace_states[-1]
    return (1.0 if passed else 0.0) + LAMBDA * phi_final

def grpo_advantages(rewards):
    """式 (2)：组内相对优势值。"""
    r = np.asarray(rewards)
    return (r - r.mean()) / (r.std() + 1e-6)
```

**训练的三个配置要点**（这些是论文明确给出的，也是最容易搞错的）：

1. **按回合索引归一化优势值**（per turn），不是按整条 rollout 归一化（pooled）。前者保留了后期回合的信用。
2. **$\gamma=1$ 的 return-to-go**，把进展向前传播到更早的动作。
3. **$\lambda=0.25$**。

对比一下反面做法：

```python
# ❌ 反面：直接相加的奖励（论文消融里 S@1=0.29 但 P@1=0.06）
def bad_reward(workspace_states, passed):
    return (1.0 if passed else 0.0) + LAMBDA * sum(workspace_states)

# ❌ 反面：仅终止奖励（论文消融里 S@1=0.25，27B 上一个完整优化器 step 都走不出去）
def bad_reward2(workspace_states, passed):
    return 1.0 if passed else 0.0
```

**这两种做法在 S@1 上看起来差不多，但完全解出率 P@1 会卡在基线水平不动。** 论文的消融表就是靠这个差异揭示了「形状」与「相加」的实质区别。

## 七、归纳总结：论文的主要观点与结论

### 观点一：长跨度智能体的瓶颈不是算法，是数据与奖励

论文的整个框架建立在一个观察上：**开源模型在长跨度任务上的失败，主要不是因为优化算法不够好，而是因为既没有训练数据，也没有可行的配方**。

两个瓶颈互相纠缠：长任务难以为之构造和验证，奖励又极其稀疏。分开解决都不行——单独造数据会得到稀疏奖励下训不动的模型；单独设计稠密奖励但没有「正确答案已知」的世界，势能分数本身就是不可信的。

### 观点二：正确的合成方向是「从答案反推问题」

这个论断比论文的具体实现更普适。

> 「与那些让语言模型在没有真实答案的情况下生成任务、输入和检查器的流水线不同，我们的潜在世界充当了精确的答案本，用于可靠验证。」

论文把它归入一个成熟的家族——从已知解反推任务：去噪、受控错误注入、代码变异、环境回溯、指令回译、程序化谜题生成。但它们的区别在于：**这些方法损坏的是单个制品的 ground truth，而 Tev 损坏的是整个潜在世界的一个渲染**。

这个区别带来了原子性上的差异：任务、验证器、进度信号都是同一个世界的函数，不会互相漂移。

### 观点三：进度奖励应该「可证明」而非「学出来」

稠密奖励的主流方案要么训练一个 process reward model，要么用学习式评委，要么用语言模型当裁判。这些方案都引入了额外模型、额外偏差和额外训练成本。

Tev 的做法是：**因为潜在世界在任务生成之前就定义了，所以每个正确中间态都能被直接渲染出来并被确定性评估**。不需要 critic，不需要 judge，不需要人工步骤标签。

这是全文方法论上最有价值的一条：**把「奖励从哪来」的问题，从「怎么学一个奖励模型」变成「怎么保证真值已知」。**

### 观点四：奖励整形必须刻意偏离「最优策略不变」

标准 PBRS 会把终止势能归零以保证最优策略不变。PPRS 保留了 $\lambda\Phi(s_T)$，**故意改变了优化目标**。

这是一个明确的风险承担。论文没有回避它，而是在附录中讨论了「什么被保留、什么没有被保留」，并给出随机策略下偏好何时可能反转的界。

**很多论文会把这种偏离藏起来或者假装不存在，Tev 把它摆在了台面上。** 这是研究态度问题。

### 观点五：数据质量与数据规模在这个领域是反向的

表格 1 的读法很反直觉：

| | SWE-Smith | Tev-Gym |
|---|---|---|
| 规模 | 50.1k | 1,170 |
| 域数 | 1 | 7 |
| Agent 时间中位 | 2.0 min | 12.4 min |
| 渐进奖励 | ✗ | ✓ |
| P@1 | 47% | 29% |

**Tev-Gym 只有既有语料的 1/40 大小，却支撑了最强的结果。** 因为在长跨度任务上，「环境数量」早就不是瓶颈了——**「环境里有没有可验证的中间状态」才是。**

这也解释了为什么 1170 个环境能训出追平 GPT-6 Astra 的模型，而 5 万个环境训不出。

### 观点六：消融实验给出的操作性教训

三条可以直接搬走用的结论：

1. **让模型自己写验证器 = 88% 的组被丢弃 + 2.5 倍算力 + 更差的性能。** 用 LLM 生成检查器省下的时间，会在训练阶段以更贵的方式还回去。
2. **稠密奖励的「形状」比「密度」更重要。** 直接相加的 $\Phi(s_t)$ 在 S@1 上看起来不错（0.29），但 P@1 完全不动（0.06）——它反复奖励高势能状态却不传播信用，导致 agent 绕圈直到耗尽上下文。
3. **规模越大，纯终止奖励的崩溃越彻底。** 27B 上仅终止奖励产生的组几乎全是零优势值，**一个完整的优化器 step 都走不出去**。

### 结论

论文自己的结论段落说得很克制：

> 我们提出潜在世界优先的方法来扩展可验证的长跨度智能体训练。每个任务从一个已知正确的潜在世界反向构建，被渲染成相互关联的文件，通过受控损坏被修改，并被复用于精确验证与稠密进度奖励。我们把这套方法实例化为 Tev-Gym——横跨七个领域的 1,170 个已验证环境——并表明训练在 ALE-CM 上同时改进了 9B 和 27B 开源模型，且增益能迁移到不同跨度的 Terminal-Bench 任务以及一个 320B 基座模型。

它也明确承认了局限：

> 当前研究的一个局限是聚焦于合成的终端环境，且最难的 benchmark 上我们的模型与前沿智能体之间仍存在差距。支持新工作流还需要编写并验证额外的环境组件。

## 八、设计哲学拆解

把论文的做法抽象到哲学层面，我看到五条相互支撑的原则。

### 原则一：唯一锚点原则（Single Anchor）

一个环境只有一个真值来源。所有产物——任务、输入、验证器、进度信号——都是它的函数。

**这对抗的是「分布式生成」的熵。** 当四个组件由不同过程分别生成时，它们的联合分布会漂移；有一个共同锚点时，漂移在结构上不可能发生。

**推论**：只要你发现自己在「生成任务」和「生成答案」两个步骤之间做对齐工作，就该考虑倒过来做。

### 原则二：真值先于任务原则（Ground Truth Precedes Task）

任务不是被「生成」的，是被「导出」的。

在 agent 时代之前，这句话听起来平淡。在 LLM 生成内容的时代，它变得激进：**你要求一个模型在它自己都不知道答案的地方生成一道需要答案的题。** Tev 的整篇论文在某种意义上是对这种做法的系统性质疑。

### 原则三：确定性优于学习原则（Determinism Over Learning）

当一个量可以被确定性计算出来时，就不要训练一个模型去估计它。

| 需求 | 常见做法 | Tev 做法 |
|------|---------|---------|
| 判断步骤对错 | 训练 PRM / 学习式评委 | 渲染正确中间态并确定性打分 |
| 判断最终对错 | 生成测试用例 | 对照 $W$ 严格校验 |
| 判断难度 | 让模型试跑打分 | 定义在生成时的结构量 |

**代价是你必须先把世界造对。** 这就是为什么 Tev 要花大力气做六种子多样性、双求解器一致性和角色独立性审计——**因为一旦势能不可信，整条训练链路都是毒化的。**

### 原则四：门槛先于规模原则（Gates Before Scale）

在生成时就把不合格的环境挡掉，而不是靠下游 RL 去软过滤。

论文明确对比了这种选择：「与那些跳过验证、依赖下游 RL 软过滤不可解任务的流水线不同，我们在生成时就设卡，因为稠密进度信号只有在因果性强且抗作弊时才有用。」

**这句话是全文最实用的工程建议。** 在数据生成侧偷的懒，会在训练侧以算力浪费和信号污染的形式还回来——论文的消融里 Public-view verifier 那 22.3 GPU-h/step 就是账单。

### 原则五：过程即产物原则（Process as Artifact）

进度势能被定义成**节点集合 + 前置依赖 + 权重**的显式数据结构，而不是一个黑箱分数。

带来的好处不只是可解释性：

- DAG 的关键路径直接就是跨度的结构度量
- 前置依赖门控天然实现了「上游没做好，下游不给分」
- 消融实验可以精确控制「数据变了」还是「奖励变了」

**当奖励被显式建模成结构时，它才能被审计、被质疑、被分解。**

### 一条隐藏的哲学线索：从「生成内容」到「生成世界」

我认为这才是这篇论文最深的一层。

过去两年，AI 内容生成的范式是：**给定 prompt，采样输出。** 所有质量问题——幻觉、一致性、不可验证——都源于一个根本限制：**没有独立于模型的知识来源。**

Tev 的做法把范式翻转了：**给定一个完整正确的世界，导出所有产物。** 模型从「知识的来源」退回到「问题的求解者」。

在这个框架下：

- 幻觉问题变成了「渲染往返还原失败」的工程问题
- 验证器不可靠变成了「代码闭包是否相交」的静态检查问题
- 奖励稀疏变成了「势能函数是否单调」的形式化性质
- 难度控制变成了「规模档位 × 依赖深度」两个旋钮

**每一个原本模糊的 AI 问题，都被转化成了一个可以被证明、可以被测试、可以被审计的工程问题。** 这才是「潜在世界优先」这个方法真正值钱的地方——它不只是一个更高效的造数据技巧，它是一种把 AI 系统问题工程化的思路。

而这也解释了为什么 Tev-Gym 只有 1,170 个环境却能赢：因为**当问题被正确形式化之后，数据的「量」这个维度的重要性会急剧下降。**

## 九、局限、质疑与后续看点

我的评价，不是论文的自我陈述。

### 论文自己承认的局限

1. **聚焦合成终端环境。** 没有覆盖 GUI、真实线上服务、多智能体协作等场景。
2. **最难的 benchmark 上仍有差距。** TB 4.0-CM 上 Tev-27B 的 0.10 相比 Claude Opus 5 的 0.52，差着一个数量级。
3. **支持新工作流需要额外投入。** 每加一个领域都要写生成器、验证器、打分器，并过八道门槛。这是实打实的人力成本，论文没有量化它。
4. **代码与数据尚未发布。** 项目主页的 Code 和 Data 按钮至今仍标记为 "soon"，只有模型权重可得。**这意味着当前无法独立验证数据集质量，也无法直接复用。**

### 我的额外质疑

**质疑一：$s_0$ 真的完全决定 $W$ 吗？**

论文的论证是：渲染可往返还原 + 损坏已声明且可逆 ⟹ $s_0$ 完全决定 $W$。但这个推导依赖于「损坏算子集合是封闭的、且每种算子的逆可计算」。如果某个算子（例如「类别漂移」）在某些数据上不可逆（两个不同的原值映射到同一个漂移值），那么严格意义上 $s_0$ 只能确定 $W$ 的一个**等价类**，而非 $W$ 本身。

论文提到隐藏套件里的「变形变换」和「反事实」正是用来处理这类歧义的，但公开树层面的确定性论证我认为仍有边界。

**质疑二：0.03 的 base P@1 是不是太低了？**

Tev-Gym 上未训练 Qwen3.8-27B 只有 3.2% 的环境被完全解出，平均评分分数 0.06。这确实符合「长跨度任务很难」的现实，但也意味着：**大部分训练信号来自 $\Phi$ 而不是来自「真的做对了」。** 模型可能在优化「势能函数的爬升路径」，而不是「任务本身的正确解法」。

论文的变形不变性门槛和陈旧输出反事实门槛部分缓解了这个问题（它们直接针对「抄近路」），但「沿着势能函数的最短爬升路径优化」与「真正理解任务」之间的差距，论文没有直接测量。

**质疑三：泛化到 TB 的结果需要谨慎解读。**

TB 3.0/4.0 的 "CM" 子集是**用 Claude 判断每个任务是否属于计算与数学域**构造出来的。虽然论文验证了子集与全集的高相关（r=0.96 / r=0.97），但这意味着子集划分本身带有一个前沿模型的判断。用 Claude 构造的子集去评测一个与 Claude 对比的模型，这个循环性虽然不构成致命问题，但值得读者知道。

**质疑四：P@5 追平前沿模型的表述需要限定。**

Tev-27B 的 P@5 = 0.28 与 GPT-6 Astra、Claude Opus 5 的 0.28 持平，这是一个非常亮眼的数字。但：

- Tev-27B 用的是 Vanillux2 harness，前沿模型用的是 Codex / Claude Code，**harness 本身对 agent 行为影响巨大**
- 前沿模型在 ALE-CM 上的 S@5 明显更高（0.58 vs Tev-27B 的 0.54，且 GPT-6 Astra 的 S@5/S@1 都是 0.58），说明**前沿模型在「已经做对的任务上做得更彻底」**
- P@5 = S@5 = 0.28 这个「饱和」形态，和 Tev-27B 的 0.16/0.28（S@1/P@5）形态，含义并不相同

**我的判断：这是一个真实的、可复现方向上的显著进步，但「追平前沿模型」这个表述在跨 harness 比较下应当打折理解。**

**质疑五：可扩展性的瓶颈会转移到「写生成器」上。**

论文指出 Tev-Gym 可以通过让 coding agent 写生成器来进一步规模化，且**不再需要模型调用**。但生成器代码本身需要过八道门槛，而双求解器一致性要求「两个独立编写的求解器产出一致」——**人工写一个生成器容易，为它写两个独立求解器并保证一致，难度高得多。**

当规模从 1,170 往 10,000 推的时候，人工审核生成器的产能会成为真正的瓶颈。论文没有讨论这一点。

### 后续看点

1. **代码与数据何时发布**——这是最关键的观察窗口。如果发布，社区能独立验证 1,170 个环境的实际质量。
2. **能否扩展到非终端环境**（浏览器、GUI、真实工具链）——这决定「潜在世界优先」是终端任务的专用技巧还是通用范式。
3. **成本曲线**——每个新领域需要多少人工工时？这个数字决定了方法的可规模化上限。
4. **$\Phi$ 与真实解题能力的相关性**——如果能直接测量「势能更高的轨迹是否更可能真正解对任务」，就能回答我上面的质疑二。
5. **Tev-320B 的完整评测**——论文只在 TB 子集上评测了 320B 版本，ALE-CM 上的表现未知。

---

## 十、一句话总结

> **让模型自己去出题，它就会连答案一起编错。**
>
> Tev 的做法是把顺序倒过来：先有一个完整正确的世界，再从它导出任务、输入、验证器和进度刻度。因为答案在构造上就已知，验证是精确的，中间状态是免费的，而训练信号可以稠密到每一步。
>
> 1,170 个环境，一个 27B 的开源模型，在 Agents' Last Exam 的计算与数学分片上 Pass@5 达到 0.28，与 GPT-6 Astra 和 Claude Opus 5 持平；同时零样本迁移到从未见过的 Terminal-Bench 4.0 子集，P@1 提升 150%。
>
> 数量从来不是这个领域的主要矛盾。**「答案从哪来」才是。**
