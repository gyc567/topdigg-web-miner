# 6800 星的 shuohao-skills：AI 短剧真正的门槛不是生成，是「谁敢把质量门写成代码」

**结论先行：** GitHub 上有个 6800 星、960 多个 fork 的开源项目 `shuohao-skills`，做的是把一本小说变成能直接下单给视频模型的短剧投产包。7 个 skill，6 个制作阶段，60 道质量门，1600 多项自测断言。

但它真正值钱的东西不是那 7 个 skill，而是它敢做的一件反潮流的事：**把「检查清单」从提示词里赶出去，写成确定性代码，让模型过不了门就走不下去。**

这是我今年读到的最干净的「AI 工程化」样本。下面把它拆开讲透：项目是什么、怎么跑、里面藏了什么设计哲学，以及——对做短剧生意的人，这套东西到底值多少钱。

---

## 一、项目说明：一个把短剧生产拆成六段的文件管道

`shuohao-skills` 的作者是「烁皓」（X: @eternityspring），Apache 2.0 协议，2026 年 8 月开坑，两个多月做到 6800 星。仓库定位一句话说清：

> 面向各类 Agent 的 AI 短剧制作 skill 集合，从一本小说到直接交给生成管线的制作素材。

它不绑定任何 Agent 运行时。Claude Code 和 Codex 只是「两个受支持的例子，不是前提」——只要你的 Agent 能读 `SKILL.md`、能跑 Node 脚本，就能用。

### 1.1 七件套

| Skill | 干什么 | 质量门 |
|---|---|---|
| `novel-outline` | 把小说改编成短剧大纲五件套：改编说明、人物表、爽点表、分集梗概、资产清单 | 14 道 |
| `novel-characters` | 把大纲定下的角色做成角色设定集：人物画像、形象提示词、音色提示词、三视图版面指令 | — |
| `character-refs` | 真正生成角色参考图：正面全身锚点 + 派生视图 | 检查门 |
| `novel-art` | 美术设定集：场景一致性锚点、光照状态变体、叙事道具表、白底可抠图 | 10 道 |
| `novel-script` | 剧本：场次 + 节拍流（动作与台词交替）、逐集时长确定性折算、台词本 | 10 道 |
| `novel-staging` | 每场开场站位：谁在哪件东西的哪一侧、坐还是站、面朝哪 | 8 道 |
| `novel-storyboard` | 分镜：段（≤15 秒）→ 分镜（2–5 秒硬门）→ 分镜图，H3 与 Seedance 投产包 | 18 道 |

流程图长这样：

```
小说原文 → 大纲 → 角色 → 美术 → 剧本 → 开场站位 → 分镜 → 视频投产包
                ↑        ↕        ↕
              角色 ←──────┴────────┘
                └→ 角色参考图（喂给分镜）
```

注意 `novel-characters` / `novel-art` / `novel-script` 三者之间是**双向箭头**——角色、美术、剧本是同步迭代的三条线，不是瀑布。这是有意的：剧本写到一半发现角色没戏份，要回去改大纲；美术发现道具撑不起这场戏，要回去改剧本。

### 1.2 它交付什么形态

每个阶段产三件套：`*.json`（机器读的工作数据）、`*.md`（给人读的文本导出）、`*-report.html`（双击就能开的单页评审报告）。

报告不是装饰。举 `novel-outline` 的报告：

- **KPI 带**：总集数、爽点数、角色分档、主场景数、生成难点、改编幅度
- **爽点节奏图**：剧情时间轴上标出每个爽点，空档直接标在轴上（「— 4 集空档 —」），超阈值变红
- **每集调度矩阵**：60 集 × 25 角色的网格，一列竖着读就是那一集的需求单
- **质量门面板**：✓/✗ 烘进页面，未过的项弹病灶横幅
- **导出 JSON**：下载的就是 `outline.json` 原样

作者的定位很明确：**这是一份业内评审用的单页报告，读者拿它拍板砍不砍、排产备不备。** 报告的默认交付形态决定了它是被用来决策的，而不是被归档吃灰的。

`novel-staging` 更进一步，交付的是**可交互的 HTML 工具**：每场一张俯视平面，人可以直接拖动换位置、点一下改坐站和朝向，改完点「导出 JSON」下载的就是新的 `staging.json`，不用手改 JSON。

### 1.3 工程约束

| 项 | 要求 |
|---|---|
| Node | ≥ 18，**只用标准库，零 npm 依赖** |
| API key | **不需要**，用当前会话额度 |
| Agent | 任何能读 SKILL.md + 跑 Node 脚本的 Agent |
| 出图模型 | 只有 `character-refs` 需要（Qwen Image / Codex / GPT Image 2 / 自定义命令） |

零依赖这条不是炫技，是**可移植性的前提**。你要把一个 skill 单独拷走，它得能跑。

## 二、详细教程：从零跑通一整条管线

### 2.1 安装

```bash
git clone https://github.com/eternityspring/shuohao-skills.git
cd shuohao-skills
./scripts/install.sh
```

安装脚本做的事很朴素：把每个 skill 目录**软链**到检测到的 Agent skills 目录。软链不是复制，所以 `git pull` 之后立刻生效，不用重装。

```bash
./scripts/install.sh novel-characters   # 只装一个
./scripts/install.sh --codex            # 只装到 codex
./scripts/install.sh --uninstall        # 拆软链
```

手动装也行：

```bash
ln -s "$PWD/skills/novel-characters" ~/.claude/skills/novel-characters
ln -s "$PWD/skills/novel-characters" ~/.codex/skills/novel-characters
```

装完先跑一遍全部自测，确认环境没问题（这步别跳）：

```bash
for f in skills/*/scripts/selftest.mjs; do node "$f"; done
```

自测不调模型、不花额度，全部跑完约一秒。**注意：上游只在 macOS + Node 24 上验过，Linux 和更低版本 Node 理论上没问题但没验。**

### 2.2 工作目录约定（别平铺）

一整条管线跑完会产出大量 json / md / html。仓库里固化的目录约定是：

```
<demo>/
├── outline/       ← <剧>-outline.json / .md / -report.html
├── characters/    ← <剧>-cast.json / .md / -report.html
├── art/           ← <剧>-art.json / .md / -report.html
├── script/        ← <剧>-script.json / .md / -report.html
├── staging/       ← staging-report.html（主交付）+ staging.json
├── storyboard/    ← <剧>-storyboard.json / .md / -report.html
│   ├── manifest.json
│   ├── E01-01/        ← export 的分镜投产包，每段一个文件夹
│   └── E01-02/
├── docs/
└── scripts/
```

有个坑值得单独拎出来：**段文件夹不要再往下收一层**（比如塞进 `segments/`）。分镜报告里的图走相对路径 `<段号>/f<切序>.png`，默认要求报告 html 和段文件夹同级。多套一层又不改路径，报告里的图会**静默**全变成「未生成」占位——上游实测把 10 个段文件夹移进 `segments/` 之后，内嵌图从 2 张变 0 张，**报告不报错**。

这条是「静默失败」的典型样本：文件在，图在，链接错了，页面假装一切正常。

### 2.3 Stage 1：改编大纲

```bash
node skills/novel-outline/scripts/novel-outline.mjs chunk <book.txt> <workdir>
node skills/novel-outline/scripts/novel-outline.mjs validate <workdir>/outline.json --stage beats
node skills/novel-outline/scripts/novel-outline.mjs validate <output>/<剧名>-outline.json
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<剧名>-outline.json --md   > <剧名>-outline.md
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<剧名>-outline.json --html > outline-report.html
```

**流程里最值钱的一条规矩：先拍板，再细化。**

骨架（砍了哪条线、合了哪些人、大爆点落在第几集）必须先出**快版**给用户点头，之后才允许写分集梗概。这不是口头约定，是**流程门**：写分集前必须过 `validate --stage beats`，爽点间隔和 major 时机错了当场拦下。

作者的逻辑很实在：**快版错了只损失一轮骨架，分集写完才发现方向错，全废。** 60 集的分集还是分批写，每批 ≤ 10 集——一口气写后半段必崩。

14 道门长这样：

| 门 | 默认阈值 |
|---|---|
| 主角组（男女主 + 主反派） | 1–5 人 |
| 有名字的重要配角 | ≤ 10 人 |
| 功能性角色（占脸不占名） | ≤ 10 人 |
| 主场景上限 | **随集数动态**：4 + ⌈集数/10⌉，夹在 5–15（6 集→5，60 集→10，110 集起封顶 15） |
| 叙事道具上限 | ≤ 8 件 |
| 一次性场景有规避方案 | — |
| 爽点间隔无真空区 | ≤ 3 集 |
| 第 1 集有钩子 | — |
| 大爆点不压最后一集 | — |
| 每集三栏齐全（梗概/钩子/悬念） | — |
| 三人以上同框有拆解方案 | — |
| 生成难点进预警清单（雨戏/肢体接触/人群/手部特写） | 关键词扫描 |
| 引用完整：无失业角色、无空转场景、ID 都存在 | — |
| 梗概是叙述体，无引号对白 | — |

两个阈值的设计值得拆开讲，因为它们暴露了「AI 短剧」和「实拍短剧」的根本差异。

**角色为什么分三档而不是一刀切**：一刀切混淆了两件不同的事——「观众要记住谁」和「制作要维护多少张脸」。主角组上限守的是戏份和记忆负担；配角和功能性角色的上限守的是**AI 角色资产成本**（每一档的一致性投入完全不同）。功能性角色「没有人物弧」是正常的——医生就是来缝针的，校验器不会强求。

**场景上限为什么比实景剧宽得多**：实景时代「≤ 5 个景」是经济学（搭景要钱）；AI 短剧里场景是生成的，**没有搭景钱**，实景时代那条经济学不成立。上限守的只剩场景的**跨集一致性资产**和观众的空间认知，观赏性直接吃场景多样性，所以随集数放宽到 15。

顺便：五件套的第五件「资产清单」**永远是脚本算出来的**，模型手写必漏。

### 2.4 Stage 2：角色设定

```bash
node skills/novel-characters/scripts/novel-characters.mjs seed <outline.json> > <workdir>/seed.json
node skills/novel-characters/scripts/novel-characters.mjs chunk <book.txt> <workdir>
node skills/novel-characters/scripts/novel-characters.mjs merge <workdir> --apply merges.json | tee <workdir>/merged.json
node skills/novel-characters/scripts/novel-characters.mjs validate <cast.json>
node skills/novel-characters/scripts/novel-characters.mjs render <cast.json> --html > cast-report.html
```

**seed 机制是这套架构的通用范式**：上游已拍板的事实（角色 ID、名字、分档、人物弧、合并来源）由脚本确定性搬运过来，留空的是这一层才该做的设计（别名、一句话画像、形象提示词、音色）。文档里反复强调的一句：

> **这些事实不要让模型重新想一遍。**

同一句话在 `novel-art`、`novel-script`、`novel-staging`、`novel-storyboard` 四个 skill 里各出现一次。**避免重复推理是 AI 管线里最便宜的优化**——模型每重新想一遍，就多一次跑偏的机会。

别名归并这块有个细节值得一提。脚本只能做**精确匹配**收敛（某块把「陆」列成「陆行远」的别名，两条就并成一个人），剩下的 `mergeCandidates` 是语义判断，脚本做不了，必须人/模型逐条复核。候选来自名字包含关系（`「陆」⊂「陆行远」`），但作者明确标注这是**强信号不是判决**——同姓的父子、兄弟不能合。而「陆先生」和「行远」没有包含关系，压根不会进候选，得自己看出来。

上游的样例《渡口》专门造了这个用例：货郎全程只有绰号、船夫只被叫过「老伯」。

### 2.5 Stage 3：美术设定

```bash
node skills/novel-art/scripts/novel-art.mjs seed <outline.json> > <workdir>/art.json
node skills/novel-art/scripts/novel-art.mjs validate <art.json> --cast <cast.json>
node skills/novel-art/scripts/novel-art.mjs render <output>/<剧名>-art.json --html > art-report.html
```

这个 skill 的前提刻在骨子里：**这是 AI 生成，不是实拍。** 没有堪景搭景置景采买，环境和道具都是要被生成几十次还得长一样的资产。所以全部交付都围绕一致性：

| 交付 | 解决什么 |
|---|---|
| 一致性锚点（每景 3–5 个） | 观众靠它认场景，QC 靠它核对生成镜头有没有漂 |
| 光照时段变体 | AI 换时段是**重新生成**不是重新打灯，每个状态落成完整提示词 |
| 空景出图提示词 | 环境和角色是两层资产，参考图里混进人，一致性全毁 |
| 变体机制（`variantOf`） | 生成新景便宜，但变体复用母场景资产更一致 |
| 道具状态变体 | 皮箱的合上与打开是两张参考图——道具有状态弧，场景没有 |
| 道具尺度参照 | AI 经常把手持道具画成家具尺寸，提示词必须带尺度短语 |
| 道具白底无手 | 道具图要被贴进各种镜头，必须可抠；拿着道具的手是最常见污染 |

「道具只收叙事道具」这条边界定得很清：有特写、跨集、承载剧情的，通常 3–8 件。场景陈设归场景锚点，一次性手部道具镜头级提示词解决，都不单独建资产。

「皮箱这种跟人走的道具，就该在这一层」——塞进场景锚点或角色画像都不对。

10 道门里最实用的两条：**提示词全英文**（中文提示词喂图像模型效果普遍更差，这是被门强制执行的最佳实践，不是靠自觉），以及**提示词不含角色名**（角色名由图像模型自己去关联参考图，名字反而会干扰）。

### 2.6 Stage 4：剧本

```bash
node skills/novel-script/scripts/novel-script.mjs seed <outline.json> --eps 1-3 > <workdir>/script.json
node skills/novel-script/scripts/novel-script.mjs validate <script.json> --outline <outline.json> --art <art.json>
node skills/novel-script/scripts/novel-script.mjs render <output>/<剧名>-script.json --html > script-report.html
```

**前提刻在骨子里：剧本管戏，分镜管拍。** 台词要反复推翻重写，绑上镜头分解后每改一句都得重排镜头。所以这层只有集、场次、节拍流，没有镜号。

但有一条底线：**台词必须是结构化数据，不能写成散文。** 每句台词是独立条目（说话人 + 台词 + 语气），动作是独立节拍。这是全部确定性检查的地基。

时长是**算出来的**：台词按 4.5 字/秒折算，动作按 2.5 秒/拍，一集三分钟就是三分钟，超了欠了当场拦下，不流到生成环节才发现。

10 道门里两条最见功力：

- **钩子具象在前 3 拍内兑现**（`hookBeat` 认领）——钩子不是标签是第一拍。短剧的生死线必须落在纸面，而不是靠模型「记得写个悬念」。
- **每场至少一个动作节拍**——纯对白的场是广播剧，AI 生成时没有画面可写。

写超了先砍动作节拍再压台词；写欠了**补戏不注水**——加冲突不加寒暄。

### 2.7 Stage 5：开场站位（最有意思的一个 skill）

```bash
node skills/novel-staging/scripts/novel-staging.mjs seed <script.json> --art <art.json> --outline <outline.json> > <workdir>/staging.json
node skills/novel-staging/scripts/novel-staging.mjs validate <staging.json> --script <script.json> --art <art.json>
node skills/novel-staging/scripts/novel-staging.mjs render staging.json > staging-report.html
node skills/novel-staging/scripts/novel-staging.mjs blocking staging.json
```

**为什么要单独排站位？** 短剧的每一段视频是一次独立生成，各段自己决定谁坐哪。群戏里六个人围一张长桌，第一段桌边多出五个没名字的宾客，第三段端酒坐着的人穿着主角的衣服。

分镜的走位句一段接一段地交接，可每一场**第一段**的那一句是分镜自己编的——**人看不到、改不动**。所以在分镜之前，每场先定一份站位，分镜照抄。

流程是**先认图再排位**：从场景图主视角里认出人会站在旁边、坐在上面的东西（4–20 件），写名字、图上的框、俯视平面上的位置。然后按剧本排谁在哪件东西的哪一侧、沿这一侧多远、坐还是站、面朝哪。

两条铁律：

- **图里看不到的不写**（提示词里有、图上没有的一律不写）——否则人坐上高台，每段视频都不一样
- **`plan` 按透视推算**，不是照抄 `box`——透视场景图上的「桌子北侧」只是一条窄缝，前后深浅说不清，摆平了从上往下看才一目了然

排位规则同样写死：**后来才进来的人开场不在**；**剧本没写有别人就没有群演**；**只使用认出来的东西**。

走位句由程序写，一字不差交给分镜：

> 「胡二爷坐在第三排坐板上，面朝北；其余座位空着，没有其他人。」

这个 skill 是 2.2.0 才加的（2026-10-14），是最新的一个，也是最能说明作者在真实项目里踩过坑的一个。

### 2.8 Stage 6：分镜

```bash
node skills/novel-storyboard/scripts/novel-storyboard.mjs seed <script.json> --eps 1-3 --aspect 16:9 > <workdir>/storyboard.json
node skills/novel-storyboard/scripts/novel-storyboard.mjs validate <storyboard.json> --script <script.json> --outline <outline.json> --cast <cast.json> --art <art.json>
node skills/novel-storyboard/scripts/novel-storyboard.mjs render <output>/<剧名>-storyboard.json --html > storyboard-report.html
node skills/novel-storyboard/scripts/novel-storyboard.mjs export <storyboard.json> --protocol h3 --out storyboard
```

**前提刻在骨子里：镜头是生成出来的，多切一镜的成本几乎为零。** 所以这里不心疼镜头数量，上限只有一个：视频模型单段生成的时长（默认 15 秒）。

三层结构：

```
段（segment）= 一次视频生成调用，≤ 15 秒，不跨场次
 ├─ 分镜（cut）= 段内剪切，每切 2–5 秒（硬门），各自认领剧本节拍
 ├─ 分镜图     = 每切一张关键帧：主图钉 0.00 秒，子图钉各自切点
 └─ H3 提示词  = 一段一条，多图对齐指令 + [Shot k] 切点时刻逐字对账
```

几个关键机制：

- **节拍认领**：每个分镜声明它覆盖剧本某场的哪几个连续节拍，不许跨场次——换景必换镜。这让分镜和剧本的关系变成**可机械对账**的。
- **对话正反打在一段里一次生成**：全景、A 近景、B 近景各是一个 2–5 秒的分镜，每格构图由自己的分镜图控制，**不靠文字赌**。
- **对齐指令是推导出来的，不是写出来的**：`Picture 2 aligns with the 3.00-second mark…` 和 `[Shot k] At 00:0X.XXX` 全部由分镜秒数推导，validate **逐字对账**——改了秒数忘改提示词，当场拦。
- **H3 与 Seedance 并列**：H3 提示词用 MiniMax 官方 I2VA 结构（对齐指令 + `integrated_multimodal_description` + `overall_soundscape` + `non_diegetic_music`）；Seedance 提示词**由脚本按官方结构现拼**，模型只写每切的 `shot`，不写秒数、编号和图片引用。
- **构图量化字段**：每段 `blocking`（谁在左谁在右、间距），每镜焦距／机位／构图／视线落点／焦点／稳定性。理由写得很直白——纯参考图出片时没有分镜图，「多近、多满、谁在哪、眼睛看哪」这些信息**要么写成字，要么就地消失**，实测消失的正是它们：景别偏远、动作偏小、人物摆位随意。

18 道门里最硬的几条：**分镜时长 2–5 秒是硬门不是建议**（3 秒左右的短剧注意力节奏）；**台词装得下**（认领节拍的台词秒数 ≤ 分镜秒数，逐切检查）；**单镜同框 ≤ 3 人**（超了必须带拆解说明）；**H3 台词逐字**（改一个标点都过不去）；**视频提示词不含角色名**（H3 与 Seedance 官方规范要求）。

### 2.9 合页与导出

五个阶段的报告可以合成一张单页：

```bash
node scripts/report.mjs --from <demo目录> --out report.html
```

**它是组装器，不是第六个 skill。** 不 import 任何 skill 的代码，而是调各自的 `render --html` 拿产物再拼装。所以五个 skill 一行不改，各自仍然独立可跑、可以单独拷走；某个 skill 改了渲染，这边自动跟上。

合并要解决三件事，**全部在组装器里做，不侵入 skill**：

- **样式串味**：五份报告共用 57 个类名，其中 13 个同名不同定义（`.copy` `.kpis` `.badge` `.chip`…），给每条选择器加作用域前缀
- **脚本串味**：各报告脚本都是 `document.querySelector('.expo')` 这种全局查询，合成一页只会命中第一个——五个导出按钮会全废。做法是套一层 Proxy 把 `document` 换掉
- **图片路径**：各报告的图相对自己那份 json 的目录，合成后按输出文件位置重算

装配器自己踩了三个坑，每个坑现在都有一条自测断言盯着：

1. `<script type="application/json">` 是各报告内嵌源 JSON 给导出按钮读的**数据**，当成脚本抠出来执行，浏览器直接甩 `Unexpected token ':'`，五个面板一起废
2. 规则之间的 CSS 注释会粘进下一条选择器，注释里的逗号会把选择器切断——实测让 18 条规则漏掉了作用域
3. 角色报告的缩略图走内联 `background-image:url(…)`，只查 `src` 属性会漏掉。表现是大图正常、缩略图 404，很难排查

### 2.10 单独跑一个角色（不改编小说）

`character-refs` 不依赖小说：

```bash
node skills/character-refs/scripts/character-refs.mjs config --model qwen --confirm-anchor yes
node skills/character-refs/scripts/character-refs.mjs intake-check <角色>-intake.json
node skills/character-refs/scripts/character-refs.mjs gen <asset.json> --tier 1   # 先只出锚点
node skills/character-refs/scripts/character-refs.mjs gen <asset.json>           # 补齐第二档
node skills/character-refs/scripts/character-refs.mjs render <asset.json> --html > report.html
```

**核心规则：一组图只有一个根——正面全身锚点。** 只有它是文生图，其余全是「锚点 + 一句改图指令」。头发、脸、领口三类细节额外挂确认过的正脸大头照。图与图之间不再互相参考——所以任何一张出坏了，单独重出这一张就行，**不会连锁**。

分档出图：

| 档位 | 内容 | 什么时候出 |
|---|---|---|
| 1 | 正面全身（锚点） | 总是，第一张 |
| 2（默认） | 正脸大头照、90° 侧面、背面 | 默认出齐 |
| 3 | 细节图（最多 8 张） | 有配饰或服装局部特写 |
| 4（默认不出） | 45° 大头照 | 用户明确要 |

为什么默认出到第二档？H3 实测：**只给正面全身，服装和背影都对，但脸会走样；加一张大头照，脸最接近。**

**模型不锁定**：主图与派生图可以用不同模型，一致性来自「同一张锚点」而不是「同一个模型」（实测 Qwen 锚点 + GPT 派生、GPT 锚点 + Qwen 派生、同组混用都衔接得上）。

**冻结的只有三样**：锚点文件（sha256）、画风快照、文字描述指纹。任何一样变了，依赖它的图自动标为「过期」——只标记，不删除，旧版本全部留着。

## 三、设计哲学：这套项目真正想说的是什么

下面八条，是我认为这个仓库最值钱的部分。

### 哲学一：检查清单交给模型自觉是靠不住的

这是整个项目的第一性原理，出处就在 `novel-outline` 的 README 里，一句话：

> **checklist 交给模型自觉是靠不住的。**

所以每一道门都是 `validate` 里的确定性检查，不是给模型读的文字。14 道、10 道、10 道、8 道、18 道，共 60 道。

配套要求更狠：**自测里每一道门都有击穿用例**——故意构造一个违规数据，确认校验器真的会报出来。证明它真的会拦，不是永远为真的假测试。

这一条的分量怎么估都不为过。绝大多数「AI 工作流」项目停留在「我给模型写了 20 条要求，它大概会遵守」。这里的要求是：**你连一条要求都不要写给模型听，写给代码。** 模型的输出是概率性的，只有代码是确定性的。

### 哲学二：出图那一刻才能决定的事，全部移出 skill

这是 2.0 版本的破坏性变更核心，也是整个项目最容易被忽略但最激进的一次取舍。

1.x 版本里，角色、美术、分镜三个 skill 自己出图，自己选模型、自己定画风、自己管画幅。2.0 把这些全删了。理由写在 changelog 里：

> **出图那一刻才能决定的事（用哪个模型、哪种画风、哪个画幅），全部移出 skill，skill 只交提示词和结构化数据。**

配套的硬约束是：**skill 不出图。** `novel-art` 的 README 里明确写「不要说『已出图』——这一步不存在了，交付的是提示词」。

为什么这么做？因为选模型、选画风、选画幅是**项目级决策**，不是阶段级决策。同一部剧的角色图和场景图应该用同一个模型、同一套画风、同一个画幅。如果这些参数散落在三个 skill 里，你要么在三处重复配置（不一致的风险），要么得加一层共享配置（破坏自包含性）。移出去，两难消失。

唯一的例外是 `character-refs`——它就是「那一刻」本身，所以它保留出图能力。**规则要留例外，例外要能说清为什么。**

### 哲学三：每个 skill 自包含，可以单独拷走

```
skills/<skill-name>/
├── SKILL.md          给 agent 读的工作流（必需）
├── README.md         给人读的说明
├── scripts/
│   ├── <name>.mjs    确定性工具，零依赖
│   └── selftest.mjs  自测，不调模型（必需）
├── references/       按需加载的详细指令
├── examples/         自带样例，同时当测试夹具
└── assets/           截图
```

两条硬要求：必须有 `SKILL.md`，必须有 `scripts/selftest.mjs` 且**不调用模型、不花额度**。

配套的 AGENTS.md 行为规则更狠：

> **skill 必须自包含、可单独拷走：不依赖任何第三方 skill（包括官方 skill）。外部方法论学习后内化成本仓库自己的 references 文档，注明学习来源。**

所以 H3 官方方法论被内化成了 `references/h3-prompt.md`，而不是挂一个外部依赖。

**这个约束的代价是真实的**：代码有重复（组装器要自己解决 57 个类名串味，而不是各 skill 统一 CSS 变量）。作者选择付这个代价——因为一个能被单拎出来用的 skill，价值远高于消除重复带来的那点整洁。

### 哲学四：模型写四件，脚本算一件

大纲五件套里，前四件（改编说明、人物表、爽点表、分集梗概）是模型写的，第五件（资产清单）**永远是脚本汇总的**。

理由一句话：「模型手写必漏。」

同样的原则散落在各处：报告里的角色位统计、大爆点列表、场景概览卡的承载爽点，全部是算出来的，模型一个字不写。

**判断标准很清晰：能机械计算的，绝不交给模型。** 凡是「模型要数一数、算一算、对一对」的活，都应该是代码。

### 哲学五：先拍板再细化，错了只损失一轮

前面讲过，不再展开。但值得强调它的形态：**这不是流程建议，是流程门。** 写分集前必须过 `validate --stage beats`，过不了就不许往下走。

AI 管线的失败有个特殊之处：早期的小错误会**级联放大**并浪费大量算力。骨架错了，60 集分集全部作废；角色定错了，美术和剧本全部重做。**在最便宜的地方拦截，是 AI 管线唯一 sane 的设计。**

### 哲学六：一致性靠「锚点」，不靠「同一个模型」

角色参考图那套「一个根、其余派生」的思路，其实贯穿整个项目：

- 场景一致性 → 每景 3–5 个锚点
- 道具一致性 → 状态变体（合上/打开各一张）
- 角色一致性 → 正面全身锚点，派生图只参考它
- 光照一致性 → 从分集反推的具体状态，每个状态落成完整提示词
- 跨集一致性 → 变体机制 `variantOf`，复用母场景资产

统一的思想是：**把「一致性」这件模糊的事，压缩成一个可以传递、可以校验、可以版本化的具体文件。**

### 哲学七：逐字对账，不靠人眼

`validate` 的很多门本质是「逐字比对」：

- H3 提示词的对齐指令必须由分镜结构推导出来，一个字符都不能差
- 认领的台词必须逐字出现在 `<d>` 块里，改一个标点都过不去
- 切点时刻必须等于前面分镜秒数的累计
- 提示词语言必须与 `promptLang` 双向对账

**「逐字」这个词是关键词。** AI 生成的东西最容易出的不是「完全错」，而是「对，但不完全对」——差一个字、差半秒。这类偏差肉眼极难发现，但在流水线上会累积成废片。逐字对账把这类偏差变成红灯。

### 哲学八：门失败会累积，stats 告诉你模型最常违反哪条

`novel-storyboard` 每次 `validate` 都把门的结果追加到当前目录的 `.gates.jsonl`：

```bash
node scripts/novel-storyboard.mjs stats
```

积累几十次之后，统计告诉你**模型最常在哪条规则上翻车**，你就能去改那条规则。

这是一条自进化的设计。而且作者的处理方式非常克制：

> **门失败累积目前只在 novel-storyboard 上。这是有意的：先在真实项目里用一段时间，确认 stats 出来的东西真的指向了该改的规则，再决定要不要推广到其余五个。如果长期没人打开它，说明这个功能不该做，推广只会把错误复制五份。不要主动再提推广。**

**「如果长期没人打开它，说明这个功能不该做」**——这句话的分量比它看起来大。它承认自己可能做错，并且提前规定了「错了就删掉」的判据。这是一种非常健康的工程态度：功能的价值由使用证明，不由设计者的热情证明。

同一种克制还体现在「镜头配方」的处理上。配方卡库是可选挂载的，卡片里的**建议景别与运镜刻意不设门**，只在报告里加个 `≠` 标记。作者的理由：

> **配方是语汇不是法条，可选挂载的东西一旦变严就没人挂了，误拦的门比没有门更糟。**

**「误拦的门比没有门更糟」**——这句值得单独裱起来。质量门一旦误报，用户的反应不是「这个门有 bug」，而是「这个工具爱挑刺，我不用了」。门禁系统一旦失去信任就等于不存在。

## 四、归纳总结：八条观点

结合这个项目，我自己的判断如下。

**观点一：AI 短剧的真实门槛，已经从「能不能生成」转到「能不能验收」。**

模型生成一段 5 秒视频已经不难了。不难的是：跑 600 集时，怎么知道第 387 集的第 2 段没有崩。这套项目把 60 个具体判据写成了代码，等于把「验收」从人工目视变成机器可执行。**谁先建成这套验收体系，谁的产能才敢往上翻。**

**观点二：把检查清单写成代码，比写一百条提示词更值钱。**

这是本项目最可迁移的一条。任何 AI 工作流都适用：提示词是软约束，代码是硬约束。区别不在措辞强度，在**能不能被违反**。

**观点三：判断一个 AI 管线专不专业，看它把「决策权」交给谁。**

这个仓库的态度很清楚：结构、计数、校验、拼接、导出——全给代码。模型只做它真正擅长的两件事：写内容、审美判断。**分工越清楚，管线越可靠。**

**观点四：一致性是资产，不是氛围。**

「氛围感」是形容词，「3–5 个锚点 + 状态变体 + 尺度参照 + sha256 冻结」是资产。前者每次生成都可能漂，后者能跨集复用、能 QC、能版本化。**AI 内容生产最终拼的是资产管理能力，不是灵感。**

**观点五：「可单独拷走」是好架构的试金石。**

一个组件能不能单独拷走而不散架，暴露了它对上下文的隐性依赖。这个仓库把自包含写成了硬要求，代价是代码重复，收益是**每一个 skill 都能当成独立产品卖**。这是典型的「用可控的重复换结构自由」。

**观点六：把「必须拍板」设成门，而不是建议。**

AI 管线的返工成本极高。方向错了，后面白做。所以「先拍板再细化」必须写成代码门，不是流程图上一句话。**任何有 AI 参与的流程，越早的决策点越要硬。**

**观点七：作者判断「这功能不该做」的勇气，比他做成的功能更值得学。**

「如果长期没人打开它，说明这个功能不该做」「不要主动再提推广」——这两句话在开源项目里是稀罕的。多数项目只会加功能，很少会预先写好自己的撤销条件。

**观点八：这个项目的真正产品是那 1600 多项自测断言，不是那 7 个 skill。**

1600 多项断言、不调模型、不花额度、一秒跑完、每一道门都有击穿用例。这套东西才是「质量门体系」真正的资产——它让任何一个团队都能在自己的内容类型上复用这套方法论。**skill 可以抄，方法论抄不走，因为它长在测试里。**

## 五、对做短剧生意的人，这套东西意味着什么

如果你是拿 AI 做短剧生意的老板，这几点更实际：

**第一，这套东西直接压的是「不可控的返工率」。** AI 短剧最贵的不是生成，是「跑完 200 集才发现角色崩了、场景穿帮了、钩子没兑现」。60 道门把这类返工从「事后抽查」变成「事前拦截」。

**第二，零依赖零 API key 意味着试错成本几乎为零。** 一整条管线跑起来只需要 Node 18+ 和你自己的会话额度。跑一遍全本大纲的成本，可能比请人喝一顿咖啡还低。**这种成本结构适合「先大量试、再集中投产」的策略。**

**第三，「剧本管戏、分镜管拍」这条边界值得单独记住。** 很多人做 AI 视频时把写戏和切镜搅在一起，结果改一句台词要重排几十个镜头，时间全耗在返工上。分开的代价是多一次交接，收益是**两个环节可以并行迭代**。

**第四，2–5 秒的切镜硬门，是可以直接抄的行业默认值。** 短剧观众的注意力节奏、生成成本、视频模型的时长上限，三条约束在这里交汇成一个数字。你自己拍短剧，这个数也该是 2–5 秒。

**第五，「误拦的门比没有门更糟」是所有 AI 工具产品的教训。** 如果你要把类似体系卖给自己的团队，**第一件事不是加门，是保证已有的门零误报**。一个误报一次的工具，团队就再也不用了。

## 六、最后

`shuohao-skills` 不是一个「AI 短剧生成器」，它甚至不生成视频。
