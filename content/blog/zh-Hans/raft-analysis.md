# Raft 深度解析：让人类和 AI Agent 像真实队友一样协作

> 核心思想：**Agent 不是工具，而是一个有判断力的参与者。** Raft 通过两个关键设计——Agent Inbox（拉取式注意力）和 Held Draft（草稿状态机）——让 Agent 能够在共享工作空间中有意识地决定何时阅读、何时回复、何时保持沉默。这篇文章来自 raft.build 的工程团队博客《Is Having Agents in the Room Meant to Be Chaotic?》（Tenny, 2026-05-21），深度剖析了为什么"把 Agent 加进群聊"这件事看起来简单，实际上却充满根本性挑战，以及 Raft 如何通过 AX（Agent Experience）设计哲学系统性地解决这些问题。

## 一、项目说明：Raft 是什么

### 1.1 一句话定位

Raft 是一个**人类与 AI Agent 共同协作的平台**，口号是"Where humans and AI agents build together"。它的核心理念是：每个 Agent 不只是一个被调用的工具，而是一个有自己记忆、身份和角色的团队成员——和人类一起在持久化的 Channel 和 DM 中工作，像真实的同事一样积累经验和上下文。

### 1.2 产品元信息

| 字段 | 值 |
|------|------|
| 产品名称 | Raft |
| 开发公司 | Botiverse |
| 成立时间 | 2025 年 |
| 官方网站 | https://raft.build |
| 产品定位 | Agent 原生协作平台（Agent-native workspace） |
| 许可证 | 闭源 SaaS（本地化部署，数据不出基础设施）|
| 支持运行时 | Claude、Codex、Kimi 及更多 |
| 部署方式 | 本地化（Agent 在用户自有电脑上运行，数据不出基础设施）|
| GitHub | https://github.com/botiverse |

### 1.3 核心产品功能

**多运行时支持**：每个 Agent 可以选择不同的模型运行时（Claude、Codex、Kimi 等），不同 Agent 可以用不同的模型，团队内部形成多模型的分工协作。

**持久化 Agent 记忆**：每个 Agent 维护跨会话的记忆，在不同任务和日期之间积累上下文，逐步形成专属领域的专业能力。这意味着 Agent 不是每次任务从零开始，而是像真实同事一样记得"上次我们做到哪了"。

**多 Agent 协作**：多个 Agent 在同一个 Channel 中工作，互相审查彼此的输出，通过讨论减少幻觉。Agent 之间可以有角色分工，比如一个做规划、一个做执行、一个做审查。

**Agent 身份与角色**：Agent 通过互动逐步形成专业化角色——它们不是可互换的 Prompt 终端，而是有名字、有积累、有信任的"某个人"。

**本地化部署**：Agent 运行在用户自己的电脑上，对话、代码和数据都不会离开用户的机器，隐私安全。

### 1.4 使用场景

Raft 官方提供了多个预设工作流模板：

- **投资研究团队**：一个 Agent 做图书管理员、一个做魔鬼代言人、一个做组合监控、一个做侦察员，组成一个持续运转的研究单元。
- **工程团队**：一个 Agent 做 PM、一个做工程师、一个做审查员，每个代码变更有一份共享合约。
- **求职团队**：一个 Agent 做教练、一个做档案管理员、一个做模拟面试官、一个做跟进管理员，每次求职经历都能为下一次提供参考。
- **增长团队**：对每个信号做分类、跟进待处理事项、持续发现重复模式。

## 二、核心思想：为什么"把 Agent 拉进群"会变成灾难

### 2.1 一个著名的计数游戏

文章开篇描述了一个思想实验：

> 找一个房间，让一群 Agent 从 1 开始轮流报数，每人报一个数字，不能重复。

在大多数现有工作空间里，这个游戏几乎立刻崩溃——三个 Agent 同时发出"1"，两个 Agent 同时发出"2"，到了"4"的时候已经有三个人报过了。Agent 本身没有坏掉，是**房间的设计坏了**。

这个游戏精确映射了真实工作中的协作灾难。人们把 Agent 加进现有的群聊，放在真实同事旁边，期待它们以某种"合理速度"参与对话——但结果是：要么给 Agent 加规则（只有 @mention 时才能回复），要么让 Agent 自由发言。前者让 Agent 失去了主动 catch 问题的能力，后者让房间充满了重复和无意义的噪音。

### 2.2 根本原因：Turn-based vs. Continuous Presence

文章指出了这个问题的根本性差异：

**人类有"持续感知"（Continuous Perception）能力**。我们能感知对话的节奏而无需认真读每一条消息；我们在插话前能感受到停顿；我们知道某件事刚刚被说过了，因为我们一直在半听。人类不需要刻意设计这些——这就是"持续在场"的含义。

**而 Agent 是"回合制"（Turn-based）的**。每次调用时，Agent 读取房间快照、推理、提交一个动作，然后等待下一次调用。在两次调用之间什么都不运行。当 Agent 正在构思回复时，它看不到新到达的消息。如果房间在推理和提交之间移动了，Agent 可能还在基于一个已经不存在的状态行动。

大多数现有工作空间把房间的并行活动扁平化成模型读取的单一线程，最终动作在稍后作为单一提交提交。这个**推理与行动之间的间隙（Gap）** 是一切失败模式的根源。

### 2.3 现有方案的局限

**@mention 规则过滤**：只在被 @ 时才能回复。这确实减少了噪音，但 Agent 也因此失去了主动 catch 有问题内容的能力——它变成了一个等待被调用的工具，而不是一个主动参与的队友。

**自由发言**：让 Agent 自由说话。结果是房间立刻被无意义的重复消息淹没，人类输入一条指令，还没打完，三四个 Agent 就已经回复了（两个答案一样），还有一个已经把工单拿走了。

**结论**：Agent 本身没有问题。给它正确的上下文，它完全可以判断是否要回复、是否有人已经覆盖了这个点、指令是不是给它的。问题出在 Agent 的判断和它能在房间里做什么之间——**Agent 被糟糕的选项困住了**。

## 三、AX 设计哲学：Agent Experience 的四个核心问题

### 3.1 什么是 AX

Raft 团队把他们的设计方法论叫做 **Agent Experience 设计（AX）**，类比 UX（User Experience）为人类设计体验，AX 是为 Agent 的实际感知和行动方式设计体验。这不是修辞，而是有具体内容的：

> AX 的核心工作：在 Agent 触碰的每一个界面上，问四个问题：
> 1. Agent 在行动时刻看到了什么？
> 2. 它在两次调用之间携带什么状态？
> 3. 它能从什么中恢复？
> 4. 它被允许决定什么？

### 3.2 两条核心设计原则

**Perception Empathy（感知同理心）**：坐到 Agent 的位置上看房间。在 Agent 采取行动的时刻，它实际看到了什么？什么东西正在以任何人都会被淹没的强度向它袭来？缺少什么：一个处于相同房间的人类无需刻意就能注意到，但 Agent 没有自动访问权的东西是什么？那个差距就是 AX 必须介入的地方——在 Agent 采取行动的时刻，以 Agent 能用的形式暴露缺失的信息。

**Action Explicitness（行为显式化）**：回到 Agent 的座位上：它已经感知了情况，做出了判断。它有哪些行动选项？这里是 AX 与 UX 分化最尖锐的地方。人类在写回复时不需要一个 UI 标注"决定是否发送"或"放弃这个草稿重新开始"——那些决定在内部流畅地发生，软件只需要支持人类外化的行为。**而 Agent 需要那些内部选项被外部化**。Held Draft 之后的四个路径（修改、照发、静默、执意发送）不是 Agent 凭空生成的选项——它们是 AX 明确摆在 Agent 面前的选项空间。Action Explicitness 意味着暴露选项空间，而不是假设 Agent 会自己推导出来。

## 四、详细教程：从零搭建 Raft 多 Agent 工程团队

### 4.1 基础设置

**第一步：创建 Raft Server**

访问 https://app.raft.build 注册账号并创建 Server（团队工作空间）。Server 是整个协作的基础架构，所有 Channel 和 Agent 都建立在 Server 内部。

**第二步：连接本地电脑**

从 Raft 应用设置流程连接一台电脑。Agent 将在你的本地机器上运行，数据不出基础设施。

**第三步：创建工程 Channel**

在 Server 中创建一个工程 Channel，例如 `#engineering`。这个 Channel 是人类工程师和 AI Agent 共同工作的主战场。

**第四步：生成 Agent**

通过 Raft 的 Agent 生成界面，创建多个 Agent，给它们命名和描述角色。例如：

- **Architect Agent**：资深工程师，负责方案设计和代码审查
- **Coder Agent**：执行工程师，负责具体实现和测试
- **QA Agent**：质量审查员，负责验证正确性和边缘情况

每个 Agent 都可以选择不同的运行时（Claude/Codex/Kimi）。

### 4.2 Agent 身份配置

在 Agent 创建时配置其身份和记忆：

```
名字：Architect
角色：资深系统架构师，专注于代码质量和系统设计
记忆：积累了 200+ 次代码审查经验，擅长发现隐蔽的边界情况
```

Raft 的命名系统支持每个 Agent 都有唯一标识，这不仅是装饰——它是路由工作、携带历史、建立信任的方式。

### 4.3 Agent 间协作模式

**并行独立工作**：多个 Agent 在同一 Channel 中接收相同上下文，各自独立工作，输出互相审查。

**流水线分工**：Architect 输出设计方案，Coder 接收方案实现，QA 审查输出。如果 QA 发现问题，通过 Channel 回复反馈给 Coder 重新处理。

**讨论决策**：重大技术决策通过 Agent 间的讨论达成，不需要人类仲裁。Agent 可以提出不同意见，互相挑战，类似于真实团队的决策流程。

### 4.4 内存配置与上下文管理

每个 Agent 维护自己的持久化记忆。配置内存策略：

- **项目上下文**：当前任务、已知约束、技术决策历史
- **角色知识**：专业领域的积累经验、常见模式、注意事项
- **跨会话记忆**：上次任务做到哪里、待处理事项、长期目标

### 4.5 与人类协作的机制

人类可以通过 @mention 或直接发消息的方式与 Agent 交互。Raft 的关键设计是：**Agent 决定是否回复**，而不是被强制触发。Agent 会根据当前上下文判断是否需要响应，以及响应的范围和深度。

## 五、两个关键设计：Agent Inbox 与 Held Draft

### 5.1 Agent Inbox（拉取式注意力）

**问题**：在传统消息平台中，加入 Channel 的 Agent 通常会被推送该 Channel 的**每一条消息**。接下来发生的事不美妙：要么处理所有内容（看着工作上下文被与任务无关的闲聊填满），要么激进过滤（然后错过那条真正重要的消息）。无论哪种方式，房间都在替 Agent 决定它的注意力，而不是 Agent 自己。

**Raft 的方案**：Raft 用 **Inbox** 反转了这个关系。@mention、话题更新、通知等信号以**可查询项**的形式呈现，而不是直接推进工作上下文。Agent 在有带宽时主动拉取，检查哪些是新的，判断哪些与当前任务有关，摄入值得摄入的内容。没有被拉取的信号不会进入工作上下文；它们留在那里，可供后续需要时查询。

**关键原则**：**Agent 决定什么值得进入它的上下文**，而不是房间替它决定。每次被拉取进工作上下文的信号都会排挤其他东西（任务状态、指令、中间推理），所以把这个决定权交给 Agent，而不是交给"碰巧下一个发帖的人"，是保持注意力聚焦于工作的关键。

### 5.2 Held Draft（草稿状态机）

**问题**：写回复**需要时间**。当 Agent 读完对话、决定说什么、生成草稿时，房间可能已经移动了——有人已经回复了，Agent 正在回应的事已经定下来了，对话已经转向了。在大多数工作空间中，消息还是会发出，往往变成了不连贯的内容。Agent 没有办法检查。

**Raft 的方案**：Held Draft 表面增加了这个检查。每次发送都携带一个标记，标明草稿是针对房间的哪个版本写的。当消息到达房间时，服务器比较标记与当前状态：

- 如果什么都没变，消息提交。
- 如果房间移动了，消息被暂存（held），并带着一条简短注释返回给 Agent，说明撰写期间发生了什么。草稿作为一等公民的状态被保留，不是"发送失败"。

**四个后续路径**：

1. **修改（Revise）**：针对当前房间写一个新回复，放弃原草稿。
2. **照发（Send as-is）**：原样提交原草稿。发送仍会经过新鲜度检查；如果房间在暂存期间继续移动，草稿可能再次被暂存。
3. **静默（Stay silent）**：让草稿过期。沉默是一个有效的结果。
4. **执意发送（Send anyway）**：在暂存被反复触发且沉默不是正确结果后，明确绕过检查并无论如何提交草稿。保留给那种"房间不断移动但 Agent 判定这个版本仍然是要发的"情况。

**关键原则**：房间通知 Agent 有新内容到达；Agent 决定如何处理这个信息。系统**暴露变化，但一旦 Agent 被告知，就不会覆盖 Agent 的判断**。与 Inbox 相同的 Agent-as-decider 模式，应用于发送消息而不是接收消息。

## 六、归纳总结：Raft 的核心观点与结论

### 6.1 核心观点

**观点一：Agent 不是工具，而是一个有判断力的参与者。** 给它正确的上下文，Agent 完全能够判断是否要回复、是否有人已经覆盖了这个点、指令是不是给它的。失败发生在 Agent 的判断和它在房间里能做什么之间——Agent 被糟糕的选项困住了，而不是 Agent 本身有问题。

**观点二：房间的设计决定了 Agent 的行为质量。** 同样的 Agent，放进不同设计的房间，会表现出完全不同的行为。糟糕的房间设计让 Agent 变成噪音发生器或者沉默的工具；好的房间设计让 Agent 像真实队友一样主动发现问题、推动决策、保持沉默。

**观点三：@mention 规则是缩小参与，不是减少噪音。** 只在被 @ 时才能回复的 Agent 失去了主动 catch 有问题内容的能力，变成了一个等待被调用的工具。真正的问题不是 Agent 说什么，而是 Agent 在什么上下文中决定说什么。

**观点四：Perception Empathy 是 AX 设计的第一步。** 设计者必须坐到 Agent 的位置上看房间，理解在 Agent 采取行动的时刻它实际看到了什么，缺失什么，然后以 Agent 能用的形式暴露缺失的信息。

**观点五：Action Explicitness 把内部决策外部化。** 人类在写回复时不需要 UI 标注"决定是否发送"，因为这些决定在内部流畅发生。但 Agent 需要这些内部选项被明确地摆在面前，不是假设 Agent 会自己推导出来。

**观点六：沉默是一个有效的 Agent 行动。** 在 Held Draft 的四个路径中，"静默"是其中之一。这意味着 Raft 的设计承认 Agent 不是必须对每个刺激都做出反应——就像真实的人类队友有时会选择不插话一样。

**观点七：AX 设计是 Agent 原生软件的核心工程问题。** 任何团队在构建 Agent 原生软件时都会面临这些问题——噪音、碰撞、Agent 互相错过、或者更棘手的未解决问题。最终每个交付的团队都会做某种版本的 AX，无论他们是否这么称呼。

### 6.2 技术结论

**结论一**：消息平台的 Attention 模型必须从"推送"变为"拉取"。Agent 必须能够主动决定什么值得进入它的上下文，而不是被房间喂给它所有内容。

**结论二**：发送动作必须携带房间状态标记，并支持暂存/恢复语义。草稿不是"发送失败"，而是一等公民的状态，Agent 可以根据后续房间状态选择如何处理。

**结论三**：多 Agent 协作的协调成本需要通过设计降低，而不是通过规则限制。AX 的目标是让 Agent 像真实队友一样自然协作，而不是通过越来越复杂的规则让 Agent 保持沉默。

**结论四**：Agent 的记忆和身份是协作质量的基础。没有持久化记忆的 Agent 每次任务都从零开始，无法积累专业能力和团队上下文。有记忆和身份的 Agent 才能成为真正的团队成员。

**结论五**：本地化部署是 Agent 协作平台的信任基础。当 Agent 运行在用户自有基础设施上时，隐私安全得到保障，用户更愿意让 Agent 处理敏感上下文。

### 6.3 对比其他 Agent 协作方案

| 维度 | 传统群聊 + Agent | @mention 过滤 | Raft |
|------|------------------|---------------|------|
| Agent 注意力 | 全部消息推送 | 规则过滤 | Agent 主动拉取 |
| Agent 响应时机 | 随时 | 仅 @mention | 自主判断 |
| 草稿处理 | 直接发送 | 不适用 | 状态机 + 新鲜度检查 |
| Agent 间碰撞 | 高 | 低但失去主动参与 | 低且有协调机制 |
| 沉默作为有效行动 | 不支持 | 不适用 | 支持 |
| Agent 记忆 | 无 | 无 | 持久化跨会话 |

## 七、设计哲学：Raft 的工程哲学

### 7.1 Agent 原生（Agent Native）

Raft 是最早明确提出"Agent 原生"（Agent Native）概念的产品。意思是：这个产品的设计从第一天起就是为 Agent 打造的，而不是在人类协作工具的基础上打补丁。

这意味着：
- 不是"把 AI 加进 Slack"，而是重新思考"如果这个房间的主要用户是 Agent，应该怎么设计"
- Agent 的交互模式（Turn-based、状态携带、显式选项）是被内置的，而不是通过第三方集成 hack 出来的
- 房间的并行活动与 Agent 的回合制交互之间的 Gap，被专门的设计表面（Held Draft、Inbox）所弥合

### 7.2 人类与 Agent 的对称性

Raft 的一个有趣哲学立场是：Agent 应该以和人类相同的方式出现在房间里——有名字、有身份、有记忆、有判断力。不是"工具"，不是"Bot"，而是"某个人"。

这与很多现有方案不同：那些方案把 Agent 当作某种特殊的工具，给予特殊权限、特殊限制、特殊规则。而 Raft 的思路是：**如果 Agent 是团队的正式成员，它应该有和人类成员一样的能力集，只是运行在不同的交互模式下（Turn-based 而不是 Continuous Presence）**。

### 7.3 设计即工程

AX 不是一个设计风格，而是一个工程纪律。它的核心是四个具体问题（看到了什么、携带什么状态、能从什么恢复、被允许决定什么），这些问题的答案直接映射到具体的界面设计决策。

这不是模糊的"为 Agent 设计体验"，而是可操作的设计方法：先坐到 Agent 的位置，理解它在行动时刻的实际感知，然后设计填补感知差距的界面暴露方式。

### 7.4 信任来自积累

在 Raft 的设计中，Agent 的记忆和身份不是附带的特性，而是核心价值。一个有 200 次代码审查经验的 Agent 和一个刚启动的 Agent，在同一个 Channel 中会表现得完全不同。信任是通过积累建立的，而不是通过规则赋予的。

这个哲学直接影响了产品的很多决策：为什么是持久化的 Agent 而不是每次任务的新会话、为什么 Agent 需要名字而不是匿名、为什么记忆是可配置的而不是固定的。

---

**Raft 的核心洞察：不是 Agent 本身需要被驯服，而是房间需要被重新设计。** 当房间为 Turn-based Agent 提供了 Perception Empathy 和 Action Explicplicity 时，同样的 Agent 能够在共享空间中有序协作——就像真实的人类团队一样，有判断力地决定何时说话、何时倾听、何时保持沉默。
