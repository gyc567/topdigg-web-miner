# 435 星的 article2media：真正值钱的不是 AI 会写稿，是它把「感觉不对」翻译成脚本能拦的指标

**结论先行：** GitHub 上有个 435 星、65 个 fork 的开源项目叫 article2media，做的是把一篇文章或一条视频，一键变成能直接发的小红书图文、杂志长图、公众号排版和 AI 配音的口播视频。

它有 10 个能力、12 套主题、每种产出自动验收，零 npm 依赖，只要 Node 22 和一个 Chrome。

但如果你只把它当成「又一个 AI 写作工具」，你会看错它的重点。

**这个项目最值得老板抄走的，不是那 10 个能力，是它的验收纪律：把「太急了」「一直在闪」「这个主题不好」这种模糊反馈，翻译成 4.5 字/秒、0 处闪断、版面 0 个错误这种机器能卡的指标。**

这套东西可以直接搬进你自己的内容团队、你的 AI 工具链、你交付给客户的 SOP。我把它拆给你看。

---

**一、项目说明：它到底是什么**

article2media 是一组开源的 Claude Code / Codex Skill，同时也是一个 Claude Code 插件。

作者是 LeiLiu（GitHub：threerocks），MIT 许可，2026 年 11 月 8 日建仓，一周内冲到 435 星。仓库是 JavaScript，77 个 .mjs 文件，约 12400 行代码。

它的输入是：

- 文章：X（Twitter）长文、帖子、线程、任意网页、微信公众号文章、本地 Markdown，或者你直接粘贴的正文；
- 视频：抖音、YouTube、B 站链接，本地视频或音频，`.srt` / `.vtt` 字幕。

视频先被转成逐字稿文章，后面走的流程和文章完全一样。

它的输出是十二种形态：

| 产出 | 规格 | 适合发在哪 |
|---|---|---|
| 总结长图 | 1080 宽单栏手机版，1 到 4 页；加 `--wide` 出 1200 宽双栏杂志版 | 微信、朋友圈、微博 |
| 卡片组 | 小红书 3:4（1080×1440），另有 4:5、1:1、9:16；6 种封面版式，可穿插整页金句、大数字、整页图 | 小红书、IG、抖音图文 |
| 封面多版本 | 同一篇出几版封面，不同版式或不同钩子 | 挑封面、分开发布比效果 |
| 轻量形态 | 一页看完、金句图、问答卡 | 高频更新、给整组卡片引流 |
| 公众号排版 | 内联样式、图片内嵌，可直接粘贴进编辑器；另出 2.35:1 头图和 1:1 封面 | 公众号 |
| 口播视频 | 1080×1920 竖屏，逐字同步动画，本地 AI 配音加字幕 | 抖音、视频号、小红书视频 |
| 原文长图 | 一字不改，只做排版 | 完整保留原文 |
| 原文卡片 | 全文按顺序分页成卡片 | 全文发小红书 |
| 全文译文 | 外文逐段译成中文，结构逐块对应 | 外文搬运 |
| 白板论证 | 一条纵向推理主干：问题、前提、证据、矛盾、转折、结论 | 看清作者怎么得出结论 |
| 漫画 | 黑白分镜，角色前后一致 | 用故事讲清一个机制 |

**关键设计是「能力独立，组合自由」。** 十个能力每一个都是一个独立的 skill，只靠工作目录里的文件交接：`article.md`（原文）、`article.zh.md`（译文）、`content.json`（改写稿）、`rewrite.md`（改写稿的文章形态）。

所以你可以只抓取、只翻译、只排版，也可以把长图、小红书、公众号一次做完。

**二、详细教程：从零跑通第一个产出**

**第 1 步：安装**

推荐用 Claude Code 插件，一次装好全部 11 个 skill：

```bash
claude plugin marketplace add threerocks/article2media
claude plugin install article2media@article2media
```

也可以用 skills CLI，同时装给 Claude Code 和 Codex：

```bash
npx skills add threerocks/article2media -g -a claude-code -a codex -y
```

`-g` 是全局安装（Claude Code 装到 `~/.claude/skills/`，Codex 装到 `~/.agents/skills/`），不加 `-g` 就只装进当前项目。`-y` 跳过确认，`-l` 只列出不安装。

手动安装的话注意：**仓库根目录不是 skill 目录，要同步整个 `skills/` 目录**。

```bash
git clone --depth 1 https://github.com/threerocks/article2media.git ~/code/article2media
rsync -a ~/code/article2media/skills/ ~/.claude/skills/
rsync -a ~/code/article2media/skills/ ~/.agents/skills/
```

只拷单个能力而旁边没有 `article2media` 时，脚本会直接报「找不到共享引擎」，因为所有能力的脚本都在 `article2media/engine/` 里。也可以用环境变量 `ARTICLE2MEDIA_ENGINE=/path/to/skills/article2media/engine` 指过去。

**第 2 步：检查环境**

```bash
bash scripts/install.sh
```

这个脚本只告诉你缺什么、怎么装，**它自己一个东西都不会下载**。

它会检查：Node 22+ 和任意 Chrome / Chromium（必需）、ffmpeg（口播视频要）、Codex CLI 登录或 OpenAI / Gemini 的 key（AI 插画和漫画要）、Apple Silicon 加 mlx-audio 加 VoxCPM2（本地配音）、mlx-whisper（逐字对齐和无字幕视频转写）、yt-dlp（YouTube 和 B 站字幕）。

在中国大陆网络下，主题字体默认从 Google Fonts 和 jsDelivr 加载，经常拉不动。这时候跑一次：

```bash
node skills/article2media/scripts/fonts.mjs
```

约 65 MB，把主题字体镜像到本地缓存，之后所有出图不再联网。渲染过程本身从不下载任何东西。

**第 3 步：在 Claude Code 里调用**

一键组合用总入口：

```
/article2media https://x.com/thedankoe/status/2117664712532123680
/article2media https://example.com/post 小红书
/article2media ./my-essay.md 公众号
/article2media https://x.com/… 翻译成中文发公众号
/article2media https://x.com/… 长图、小红书、公众号都要
/article2media https://www.bilibili.com/video/BV… 小红书
/article2media links.txt 批量，每篇出小红书和长图
```

也可以直接用单个能力（插件里名字带 `article2media:` 前缀）：

```
/article2media:wechat-layout ./my-essay.md
/article2media:image-cards ./my-essay.md 原文卡片
/article2media:video-transcript https://www.bilibili.com/video/BV…
/article2media:article-translate article2media-out/x-…/article.md
```

产出写在当前目录的 `article2media-out/<slug>/` 下。

**第 4 步：不经过 Claude，直接跑脚本**

每个能力都有自己的脚本入口，不依赖 Claude 也能跑：

```bash
K=skills
node $K/article-fetch/scripts/fetch.mjs "https://x.com/…/status/…"
node $K/video-transcript/scripts/transcribe.mjs "https://www.bilibili.com/video/BV…"
node $K/article-rewrite/scripts/check.mjs <slug>/content.json
node $K/article-rewrite/scripts/export.mjs <slug>/content.json
node $K/long-image/scripts/long.mjs <slug>/content.json --theme all
node $K/image-cards/scripts/cards.mjs <slug>/content.json --ratio 3:4
node $K/image-cards/scripts/cards.mjs <slug>/content.json --covers
node $K/wechat-layout/scripts/wechat.mjs <slug>/article.md --theme quiet
node $K/explainer-video/scripts/video.mjs make <slug>/video/video.json
node $K/logic-whiteboard/scripts/whiteboard.mjs <slug>/article.md
node $K/article-comic/scripts/comic.mjs make <slug>/comic.json
```

长图和卡片还支持 `--out 目录`、`--page 1,3`、`--scale 2`、`--format jpeg --quality 90`、`--max-height 7600`、`--brand brand.json`、`--issue 13`、`--html-only`。公众号另有 `--title`、`--digest`、`--cover-title`、`--kicker`、`--hero`。

**第 5 步：批量处理和发布闭环**

批量模式下，把链接写进一个文本文件：

```bash
node $K/article2media/scripts/batch.mjs init links.txt --name 本周 --spec "cards:3:4,long,wechat"
node $K/article2media/scripts/batch.mjs next 本周
node $K/article2media/scripts/batch.mjs checklist 本周
```

`batch.mjs init` 负责抓取和建看板，Claude 按 `next` 一条条做，做完一篇再做下一篇。抓取失败、正文太短、疑似付费墙的会被单独列出来等你确认，不会卡住整批。

做完每篇有一份发布清单 `publish.md`：上传顺序、备选标题、正文文案、标签、平台硬性限制检查（小红书标题不超过 20 字、正文不超过 1000 字、图不超过 18 张；公众号标题不超过 64 字、摘要不超过 120 字）。

发布之后把数据告诉它：

```bash
node $K/article2media/scripts/stats.mjs add <slug> --platform xhs --views 1200 --likes 80 --saves 150
node $K/article2media/scripts/stats.mjs report
```

报告会按平台对比各主题、各封面版式的收藏率和互动率。**样本不足 5 条的组会明确标注「样本不足，仅供参考」**，不会让你凭两三篇帖子的差别下结论。

**第 6 步：自测（如果你在本地改代码）**

```bash
node tests/run-all.mjs --quick
node tests/run-all.mjs
node tests/unit.mjs
node tests/visual.mjs
node tests/eval-score.mjs <目录> --ref <目录>
```

`run-all.mjs` 是自测矩阵：4 篇示例文章乘 7 种版式乘 12 套主推主题，一共 504 次渲染，每次都要求 0 个版面错误。`visual.mjs` 是像素级视觉回归，`eval-score.mjs` 是换模型时的质量打分。

**三、三条路径：原文、总结、翻译**

这是整个项目最关键的设计决策，也是老板最容易抄走的一条。

很多工具只有一个「AI 总结」按钮，你想要原文它也没辙。article2media 把这件事做成了一个明确的分流规则。

| 你说的 | 走哪条路 |
|---|---|
| 排版、原文、全文、一字不改、原样、`-f` | 原文路径：直接交给呈现能力 |
| 总结、提炼、改写、重点、干货 | 改写路径：先 `article-rewrite`，再呈现 |
| 翻译、译成中文、搬运外文 | 翻译路径：先全文翻译，再按原文路径呈现 |
| 都没说，要长图或卡片 | 默认改写 |
| 都没说，要公众号 | 默认原文排版 |
| 走原文路径，但原文语言和目标语言不同 | 先翻译，再原文排版 |

**这里有个很反直觉的默认值：公众号默认不总结。**

也就是说，你把别人的文章丢给它说「发公众号」，它给你的是一字不改的原文排版。只有你明确说「总结」，它才改写。

**对老板的意义：** 团队里做内容，最容易出的事故不是排版丑，是「AI 帮我总结一下」这句话。总结一次，作者的原意就掉一层，掉到第三层就变成了成功学的空话。把默认设成「不总结」，等于给团队装了一道默认不越权的门。

**四、设计哲学：六条硬规矩**

**1. 内容与风格分离**

主题只是一组 CSS 变量加少量结构覆盖。换主题只需重新渲染，不重写内容。

这意味着同一份 `content.json` 可以渲染成 12 套主推主题中的任何一套，也可以同时出长图、卡片和公众号。

**2. 零 npm 依赖**

只用 Node 22 内置的 WebSocket 和 fetch，直接驱动本机已有的 Chrome。不用 puppeteer，不用 playwright，不用任何需要下载浏览器的包。

**3. 图里不放字**

这是整个项目最聪明的一个决定。

AI 画图最大的问题之一是中文字会画错。article2media 的做法是：**生成的图片里不含任何文字**，所有文字，包括标题、图表标签、漫画对白、视频字幕，都用 HTML 排版，再由无头 Chrome 截图。

这带来两个后果：字永远不会乱码，随时能改；更重要的是，**程序能把渲染出来的文字读回来检查**。

**4. 能力探测，不强求**

出图（Codex CLI 到 OpenAI 到 Gemini）、本地配音（VoxCPM2 到 edge-tts 到系统语音）、逐字对齐、视频转写，全都是先探测再选用。缺了就降级或者明确告诉你缺什么，**从不自动下载或安装任何东西**。

**5. 模型做判断，脚本做测量**

Claude 负责理解和写作：规划结构、改写标题、决定哪一节配柱状图、哪一节配流程图、核对数字。它产出的是一份只有内容、没有任何样式的 `content.json`。

排版、截图、配音、对齐、混音、验收，全部交给脚本。

**6. 合规前置**

6 款随包音色全部只凭文字描述设计，不模仿任何真人。克隆音色只留在本机个人音色库，使用时审片会提醒确认授权。成片首帧和 MP4 元数据都带 AI 生成标识，每张图都署原文出处。

关于声音，项目的结论很清醒：**用 AI 把克隆来的声音再合成一遍，不算新声音。** 依据是《民法典》第 1023 条第二款（对自然人声音的保护参照适用肖像权保护的有关规定），以及 2024 年 4 月北京互联网法院的判例（一般听众能从 AI 合成声音里认出是谁，这个声音就同样受保护）。所以音色库按版权分成两层：公开音色随项目分发，本机个人音色库只供本人制作。

**五、自动验收：每种产出都有自己的检查器**

这是这个项目和「让 AI 直接出图」最本质的区别。

AI 生成的东西最怕「看起来差不多」。所以每种产出都有自己的验收，不合格直接报错退出，而不是交给人用眼睛去找。

| 产出 | 检查项 |
|---|---|
| 改写稿（和原文比对） | 原文里找不到的数字、别人的文章写成第一人称、原文配图一张没用、原文的具体数字和人名工具名用上了多少、中文里夹杂英文普通词；正文太薄、数据面板和整页卡偏少、大数字和标题对不上、同一句话重复、「该避开什么」写成了该做的事、页脚写了制作过程、没写备选标题 |
| 总结长图、卡片、封面 | 文字溢出、截断、元素重叠、单字成行、页面过高、图片加载失败、字体按家族检查、卡片溢出、图表过小、自动省略了什么 |
| 原文长图、原文卡片、公众号排版 | 原文块账本逐块比对（卡片跨卡拼接）、解析覆盖、来源 SHA-256 锁定、实际字体、卡片溢出、张数上限、公众号残留样式、标题长度 |
| 全文翻译 | 块数与结构逐块对应、代码与图片原样、疑似未翻译或漏译、数字是否丢失 |
| 白板论证 | 论证账本：每段原文都要进入某一步，或写明省略理由 |
| 漫画 | 对白、旁白和音效字不越出分格 |
| 口播视频 | 安全区、首句不超过 5 秒、首个画面不超过 2.5 秒、画面静止不超过 5 秒、旁白语速、字幕停留与闪断、成片逐帧字幕丢帧、逐句配音质检、响度 |
| 发布清单 | 小红书标题不超过 20 字、正文不超过 1000 字、图不超过 18 张；公众号标题不超过 64 字、摘要不超过 120 字 |

每个脚本都以 `✓ / ⚠ / ✗` 逐行报告，最后汇总成「版面检查：N 个错误，M 个提示」。**只要有错误，脚本就以非零码退出。**

其中「原文块账本」是最狠的一道：每个可见文本块都登记进账本，渲染后在浏览器里逐块读回比对。**改一个字、调一次顺序、漏一块或重复一块，都会失败。**

**六、归纳总结：8 条观点，以及它们对老板的含义**

**观点 1：这个项目的本质是「验收系统」，不是「生成系统」。**

十个能力只是皮，验收才是骨。生成能力谁都能接模型，验收纪律需要几千次迭代。

**对老板：** 评估任何 AI 工具，先看它「怎么知道自己做错了」。答不上来的，产出质量全靠你肉眼兜底，一个团队一天只能产三条。

**观点 2：把「感觉不对」翻译成指标，是唯一能规模化的高质量手段。**

项目的作者记下过一句反馈：「做解说整体语速都不能太急，这个是大忌。」他们没有只改代码，而是测了参考音频的语速，定下标准约 4.5 字/秒，单段超过 5.2 字/秒判为偏快，偏快的句子换种子重生成，还快就在保持音高的前提下放慢。改完同一条视频的旁白从每秒 5.97 字降到 4.27 字。

**这条规则现在写进了审片脚本。下次谁再改代码，机器会替他们记住那句「太急了」。**

**对老板：** 你团队里那些「这里不够高级」「这个感觉怪」的反馈，如果不能变成数字，就永远是玄学，永远靠某个人在盯。把它们一条条量化，是内容工业化里最便宜的一步。

**观点 3：机器检查必须有，人眼也省不掉。**

项目做新中式主题时选了一款好看的标题字体，版面检查全部通过，可人一看成品，所有的「回」字都是一个实心黑块。字体文件本身就是坏的，程序检测不出来。

从那以后每款新字体都要先用「回图国圆品器噩」这几个字试一遍。

**对老板：** 你的质检流程要同时有自动检查和人眼抽检。只做自动检查，会漏掉「技术上合格但人类看着难受」的那一类；只做人眼检查，产能上不去。

**观点 4：功能能做，不代表应该做。**

背景音乐试了三次：在线免版权曲库、程序合成的和弦铺底、本地 AI 作曲（光模型就 11 GB）。最后一个都没留。

原因很简单：太重了，而且平台 App 里加背景音乐只要几秒钟。

**对老板：** 这是我在这整个项目里看到的最值钱的一条取舍。团队做 AI 工具链最容易犯的错，是「能加的功能都加上」。每加一个功能，你就多一份维护成本、多一个失败点、多一个用户不知道怎么用的入口。**减法比加法难，因为加法有人夸，减法只有你受益。**

**观点 5：合规必须在第一天就做对，事后补的成本远高于一开始就做对。**

**对老板：** 你的 AI 工具链如果涉及客户数据、素材版权、声音肖像权，事后整改的代价是当初写对规则的十倍。这条适用于你给客户交付的所有 AI 方案。

**观点 6：换模型这件事，要测，不要猜。**

项目自带换模型回归测试：用 3 篇文章对比 Haiku 和 Opus 的「改写到小红书卡片」。

结果是：规则层面（客观分）Haiku 从 Opus 的 70% 到 95% 提到 100% 以上，规则都能守住；读者层面（盲评，不知道哪组是谁做的，三轮换位）Haiku 是 Opus 的 85% 到 91%，平均约 88%。差距主要在理解：漏掉原文的核心方法、把两个相近的数字混为一谈、配图放错节。

**对老板：** 这就是「小模型写稿 + 大模型审一遍」的现实天花板，88%。别指望换个便宜模型就省钱，得先测你在乎的那个维度。

**观点 7：默认「不总结」，是比默认「更聪明」更重要的设计。**

**对老板：** 你给客户交付 AI 工作流时，第一件事应该是把默认行为调成最保守的那个。用户主动要什么再给什么。

**观点 8：一个功能做得好的标志，是它有闭环。**

出图只是一半。围绕「发出去并且有效果」，项目做了一整套：封面多版本、品牌包、轻量形态、批量、发布清单、发布数据记录与对比报告。数据只存在你本机，攒够样本后，选主题指南会把它当作两个同样合适的选项之间的裁决依据。

**对老板：** 这是内容和投放之间那条断链。绝大多数内容团队做了内容就扔进发布器，再也没有回头看数据，所以你永远不知道哪种做法有效。**闭环不需要大系统，先记 10 条数据就够开始。**

**七、几个必须说清楚的边界**

- **本地配音**：VoxCPM2 目前只在 Apple Silicon 上运行，其他机器用 edge-tts 或系统语音。
- **出图**：AI 插画和漫画需要出图能力，Codex CLI 登录（ChatGPT 账号就行）或者 OpenAI、Gemini 的付费 key。
- **背景音乐**：视频目前没有背景音乐，得自己在平台 App 里加。
- **X 抓取**：依赖 FxTwitter，它不可用时需要手动粘贴正文。
- **视频输入**：本地语音识别需要 Apple Silicon。YouTube 在有的网络下要求登录确认，抖音有时要浏览器 cookie，这时候要么同意复用浏览器状态（`--cookies-from-browser chrome`），要么把视频保存到本地再传文件。
- **听感**：音色和语速的最终判断仍然要靠人耳。
- **Codex 沙箱**：默认不允许启动 Chrome，出图会报「Chrome 意外退出」，需要给这一步放行。

还有一个细节值得记：视频转文字时，**机器翻译的字幕轨和 B 站弹幕都不能用**。前者不是说话人的原话，后者是观众评论。文字来源按可信度排序是：人工字幕、平台按原语言生成的自动字幕、本地 Whisper 识别。

**八、如果你只抄三件事**

**第一抄：给每一个 AI 产出配一个「不通过就非零退出」的检查器。** 哪怕只有五条规则，也比全靠人眼强。

**第二抄：把团队口头反馈里最常出现的那 3 到 5 条感觉，变成可测量的数字。** 「太急了」变成 4.5 字/秒，「一直在闪」变成 0 处闪断，「太长了」变成 15 秒。

**第三抄：默认行为调保守。** 不总结、不润色、不脑补。用户主动要才给。

这三条不需要你先装 Node 22、不需要你先有 MacBook Pro、不需要你先把 Codex 登录好。**今天下午就能在你自己的内容流水线里试第一条。**

这个项目本身，我把它理解为一次诚实的实验：它证明了一件事，**AI 内容生产真正稀缺的不是产能，是判断力**。十个能力谁都能做，把判断力写成规则并且让机器替你盯着，才是护城河。
