# FDE Guide 深度解析：在自主性之前先工程化价值——面向 FDE 与 AI 工程师的生产级交付方法论

> 核心思想：**Tokens 是输入（Tokens are an input）。自主性是设计选择（Autonomy is a design choice）。被接受的结果才是产品（Accepted outcomes are the product）。** davidahmann/fde-guide 是作者 David Ahmann（云、数据与 AI 平台负责人，前 Field CTO）维护的独立开源指南与工程套件，目标只有一个：**把一条真实的客户或内部工作流，变成一个可度量、可运营的 AI 服务。** 它的第一原则是"在自主性之前先工程化价值"——从一个模型或 agent 拓扑出发是错的，要从**工作本身和它被接受的结果**出发。生产级 AI 系统不能只产出貌似合理的答案，它必须知道：谁有权行动、哪条信息是当前的、失败如何被限制、完成如何被验证、整个服务成本多少、谁能运营它或叫停它。Agent 只是组件选项之一；对每个关键决策，要在确定性软件、优化、经典 ML、检索、基础模型调用、有界 agent 工作流与人工审查之间做比较，选择**最小的充分机制（smallest sufficient mechanism）**，并保留它的证据、权威、成本、回退与退役路径。该项目的"12 因子 AI 价值工程"把这一原则转成显式的价值、验证者、采纳、权威、成本、证明与生命周期门禁。

## 一、项目说明

### 1.1 它是什么？

本文解析的是 **GitHub 开源仓库 `davidahmann/fde-guide`**——副标题为 *"Value engineering and production architecture for FDEs, applied-AI engineers, product teams, and operators"*（面向 FDE、应用型 AI 工程师、产品团队与运营者的价值工程与生产架构）。它定位为"一份独立的开源指南和工程套件"，用于**把真实客户或内部工作流转化为可度量、可运营的 AI 服务**。

它不是又一个 agent 框架，而是一套**工程方法 + 可执行证据**的复合体：方法（The Guide）教你怎么想，手册（The Handbook）支撑你的判断，工程套件（The Engineering Kit）让主张、权威、行为与变更可检视、可测试。三者是同一方法的三种深度，不是三套独立框架。

**三种深度，按需取用：**

| 层级 | 何时使用 | 入口 |
|------|---------|------|
| **The Guide（指南）** | 想要心智模型、核心原则与完整交付循环，约 20 分钟 | `guide/README.md` |
| **The Handbook（手册）** | 正在评估、设计、交付、移交或运营一条真实工作流 | `playbooks/` 生命周期 playbooks + `library/00-start-here.md` |
| **The Engineering Kit（工程套件）** | 需要实现工件、架构、机器可读契约、发布控制、可执行示例或测试 | `examples/`、`blueprints/`、`templates/`、`controls/`、`schemas/`、`operations/`、`tests/` |

### 1.2 关键数据与信息

- 仓库：`https://github.com/davidahmann/fde-guide`（Apache-2.0 许可，21 stars / 2 forks，17 commits，含 `CITATION.cff` 引用元数据）
- 作者：**David Ahmann**——云、数据与 AI 平台领导者，具备 Field CTO 经验；独立项目，不代表任何现任或前任雇主的背书
- 定位：不需要特定模型、云或 agent 框架；不是可落地的运行时、认证或目标组织评审的替代品
- 治理资产：`AGENTS.md`（仓库工作契约）、`catalog.json`（受治理工件注册表）、`llms.txt`（紧凑机器导航索引）
- 可执行基线：Node.js 22+，`npm ci --ignore-scripts && npm run test:reference && npm run test:evals && npm run test:hybrid`
- 两个教学系统：**受控写入**示例（invoice-exception，发票异常解决）+ **混合系统**示例（shipment-risk-triage，货运风险分诊）
- 十个可选 agent 技能：`$qualify-ai-workflow`、`$engineer-ai-value`、`$select-ai-mechanism`、`$design-production-ai-system`、`$build-ai-evaluation`、`$secure-ai-action-boundary`、`$review-ai-production-readiness`、`$operate-ai-service`、`$transfer-ai-service`、`$productize-field-learning`（仅指令，不授予任何工具/凭证/权限/批准/证据）
- 业务流组合：异常到解决（exception-to-resolution）、信号到调查（signal-to-investigation）、风险到优先行动（risk-to-prioritized-action）、请求到激活（request-to-activation）；垂直画像含医疗接入协调、金融服务调查、工业运营响应

### 1.3 它解决什么问题？

文章开头就点出核心痛点：**AI 有一个记账问题（AI has an accounting problem）。** 团队度量 token、模型调用、生成的代码、部署的 agent、"号称节省的工时"——这些度量描述的是智能的生产与消耗，**并没有确立任何有价值的事情发生**。组织最终为的是被改变的结果：发票异常被解决并在账本中确认；货运案件在影响服务前到达正确的协调人；发布到达生产、通过检查并保持健康。

**一个被接受的结果（accepted outcome）** 是一个完成的、被独立验证者、权威系统或负有责任的评审者接受为正确的工作单元。AI 价值工程把这个结果与合格需求、采纳、归因、全成本与风险连接起来。

它解决的问题因此是：**如何把"AI 活动"变成"被接受的结果"？如何确保交付的系统不是 demo、不是提示词、不是模型调用、不是 agent、不是仪表盘，而是一个对真实工作的有主变更（owned change）**——带有被接受的结果、可信的验证者、有界的权威、全成本的价值主张、运营团队与退役路径。

## 二、核心思想

### 2.1 一句话世界观

> **"Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."**
> （**Tokens 是输入。自主性是设计选择。被接受的结果才是产品。**）

这是全项目的座右铭，也是它与大多数"agent 狂热"内容的分界线：**最大化智能、token、自动化或自主性都不是目标，目标是在被接受的成本与风险上限内改进一个有主的结果。**

### 2.2 在自主性之前先工程化价值

> **"Start with the work and the accepted outcome—not with a model or agent topology."**
> （**从工作与被接受的结果出发——而不是从模型或 agent 拓扑出发。**）

生产级 AI 系统必须回答的七个问题：谁可以行动、哪条信息是当前的、失败如何被限制、完成如何被验证、整个服务成本多少、谁能运营它、谁能叫停它。Agent 是一个组件选项；对每个关键决策，比较 7 种机制（确定性软件 / 优化 / 经典 ML / 检索 / 基础模型调用 / 有界 agent 工作流 / 人工审查），选择最小的充分机制，并保留其证据、权威、成本、回退与退役路径。

### 2.3 FDE 的四项职责与"有主变更"的输出

一个前向部署工程师（Forward-Deployed Engineer, FDE）把**模糊的运营问题**变成**产生可度量结果的受支持软件服务**。工作横跨四项职责：

1. **发现（Discovery）**：理解工作、判断、延迟、风险与价值实际发生在哪里。
2. **产品（Product）**：决定用户应该改变什么、什么应保持人工、本地或手动。
3. **工程（Engineering）**：构建能改进工作流的最小可靠系统。
4. **运营（Operation）**：证明结果、移交所有权、支持服务、从生产中学习。

**输出不是 demo、提示词、模型调用、agent 或仪表盘**，而是一个**对真实工作的有主变更**：带有被接受的结果、可信的验证者、有界的权威、全成本的价值主张、运营团队与退役路径。同一方法适用于公司内部——内部应用型 AI 工程师即使没有 FDE 头衔，也必须连接业务上下文、产品判断、软件架构、采纳与生产运营。

### 2.4 一条贯穿始终的交付循环

整个仓库只遵循一个生命周期（7 阶段），不为每个客户、模型或框架创建平行方法：

```
观察工作 → 章程化价值与范围 → 选择机制 → 构建一个受控切片 → 用案例与用户证明 → 上线并移交所有权 → 运营、学习或退役 → （回到章程）
```

每个阶段都以**决策 + 可被他人检视的证据**结束。停止、收窄或重新设计薄弱的工作是有效结果——一个漂亮的模型分数、赞助人、续约、上线或使用数字，**无法平均掉失败的价值、权威、安全、所有权或生产门禁**。

## 三、详细教程：7 阶段交付循环 + 12 因子价值工程

### 3.1 阶段 1：先观察工作，再设计系统（Observe）

**上下文提取不是收集所有文档，而是发现做出关键设计决策所需的最小运营真相。** 与执行、接收、评审和支持该工作的人一起观察真实案例，记录：

1. 触发点与工作界面；
2. 正在做的决策；
3. 输入及其权威来源；
4. 被允许的行动与最大可容忍影响；
5. 正常路径、异常、变通做法与恢复；
6. 拥有业务结果的人；
7. 能独立接受结果的人或系统；
8. 将运营变更后工作流的团队。

**访谈产生假设；操作者走查、源工件、系统 trace 与对账记录产生更强的证据。** 如果工作流只在幻灯片里是清晰的，发现就没有完成。

警告：**在问"工作流、策略、源系统或交接是否应该被修复"之前，不要自动化一个变通做法。** AI 能让一个破碎的流程跑得更快，同时让底层问题更难被看见。

### 3.2 阶段 2：工程化价值契约（Charter）——一个用例可构建的七个字段

一个用例在它的结果**能被拥有、被度量、被质疑**时才可构建。在架构之前定义这些字段：

- **合格人群（Eligible population）**：哪些工作可以合法使用该系统，含排除项。
- **基线（Baseline）**：当前性能、状态、日期、人群与置信度。
- **被接受的结果（Accepted outcome）**：工作被独立接受的事件——不是模型"生成"或"完成"了。
- **验证者（Verifier）**：确立接受的人、规则、对账或真相源事件。
- **目标与护栏（Target and guardrails）**：期望的变化，以及绝不能变差的东西。
- **归因（Attribution）**：团队如何区分系统效应与其他变化。
- **全成本（Full cost）**：发现、交付、变更、模型、基础设施、工具、人工审查、支持、事故、恢复与维护。
- **残余损失（Residual loss）**：未包含在其他收益或成本项中的预期或已实现损害。
- **所有者（Owner）**：对指标及其驱动的决策负责的角色。

有用的运营单位：

```text
每个被接受结果的成本 =
  总运营与分摊生命周期成本
  / 独立接受的结果数
```

```text
已实现净价值 =
  被接受结果的可归因价值
  + 不重叠的避免损失
  − 生命周期成本
  − 未净额化的残余损失
```

**把预测、已证明的试点证据与已实现的生产价值分开。** 不要把狭窄的试点年度化，除非有显式、有主的推断。不要通过节省时间、单位价值、避免损失或减员来重复计算同一收益。

### 3.3 阶段 3：选择最小的充分机制（Select）

**"用 AI"不是架构决策。** 把工作流分解成关键决策步骤，为每一步单独选择机制：

| 机制 | 适合 | 警示信号 |
|------|------|---------|
| **确定性软件** | 稳定规则、转换、验证、路由、授权 | 自然语言歧义被藏进脆弱的 if-else 分支 |
| **优化算法** | 分配、调度、排序、规划（有显式目标与约束） | 目标或约束无法被拥有或度量 |
| **经典 ML** | 重复预测（有标签、校准的不确定性、漂移监控） | 不存在代表性结果或反馈路径 |
| **检索** | 证据必须跨受治理来源查找 | 检索输出被允许成为策略或权威 |
| **基础模型调用** | 有界的解释、提取、分类或起草 | 流畅的输出被当作已验证的事实 |
| **有界 agent 工作流** | 多步判断确实依赖变化的证据或工具使用 | 步骤是已知的，普通工作流代码会更简单 |
| **人工审查** | 判断弱可验证、高风险，或策略要求问责 | 审查被用来掩盖不可用系统或无界工作量 |

一个生产系统可以组合多种机制。保持每条路径可观察、可测试、可替换、可计成本。**模型路径不会削弱身份、授权、数据、发布或普通软件工程控制。** 只有在有界多步判断真正有用时才加 agent；只有当权限、工具、上下文、所有权或延迟的**真实差异**证明协调成本合理时才加多个 agent。

### 3.4 阶段 4：构建一个受控的垂直切片（Build）

第一个切片应穿过**真实的接口与控制边界**，而无需尝试完整产品。它应演示：

- 一个代表性触发点与用户；
- 具有真实权限行为的权威上下文；
- 选定的决策路径；
- 最终操作者工作界面；
- 模拟、暂存、可逆或以其他方式有界的影响；
- 显式的失败与升级状态；
- 遥测、成本与接受证据；
- 有主的恢复或回退路径。

**在试点期间就开始采纳与移交。** 接收团队应在交付团队退出前，配对参与评估、发布、支持、策略变更、事故、回退与退役。

**预先声明试点的最大时长、证据截止点，以及独立的（技术 / 操作者 / 采纳 / 价值 / 经济 / 生产就绪）毕业门禁。** 一个 demo 不应因为打动了赞助人就悄悄变成生产。

### 3.5 阶段 5：在代表性工作上证明主张（Prove）

**评估是"在声明条件下的发布主张"，不是永久分数。** 使用代表性正常案例、困难切片、已知异常、对抗性输入、依赖失败、策略变更、超时、重试、取消、恢复与人工审查容量。**保留重放结果所需的完整环境与行为版本。**

分离三个问题：

1. **能力（Capability）**：机制能执行任务吗？
2. **行为（Behavior）**：整个系统走对路径并安全停止吗？
3. **结果（Outcome）**：工作流是否在护栏内为目标人群改进了被接受的结果？

确定性检查对封闭不变量最强；统计度量需要分母与不确定性；模型裁判需要校准的 rubric 与人工比较；生产反馈不能静默污染保留集，也不能让候选模型控制自己的评估者。通过**离线评估 → 影子运营 → 金丝雀 → 命名生产段**等有界阶段晋升；**先定义回退再上线**。

### 3.6 阶段 6：运营服务并移交所有权（Launch + Operate）

**生产是一个反复出现的决策，不是最后的部署步骤。** 监控整个系统：被接受的结果、价值、采纳与护栏；来源、权限、新鲜度与对账；路径、模型、提示词、工具与策略版本；延迟、成本、重试、步骤与终止原因；被拒/被禁/重复/效果未知/回读不匹配事件；评审者负载、纠正、放弃、培训与支持；所有者连续性、事故就绪、回退与退役能力。

**移交在接收团队能不靠交付团队的英雄主义运营、变更、恢复、支持与退役该服务时才算完成。文档本身不证明运营能力，演练才证明。**

### 3.7 阶段 7：把现场学习变成产品能力（Field learning）

FDE 工作的复利优势不是可复用的客户数据或堆砌的自定义代码，而是**把本地上下文与可移植的工程知识分离**的能力。默认保持客户/业务单元特定的：策略、阈值、身份、权限、机密数据、来源细节与运营决策。可复用的候选包括：契约形状、失败类别、评估方法、工作界面模式、集成原语、控制、runbook 与平台缺口。

**只有证据显示在独立环境中反复出现、候选已消毒、存在目的地与所有者、目标特定验证成功、走正常发布路径时，才产品化。** 先分类（客户配置 / 目标自有扩展 / 共享产品或平台能力 / 有时限实验 / 被禁或延期），再做实现。**不要制造依赖，保留负面与停止的证据，保留退出路径。**

### 3.8 教程核心：12 因子 AI 价值工程（Valuemaxxing）

这是全项目的"账本"框架——把 AI 活动换算成被接受的结果：

| # | 因子 | 一句话要点 |
|---|------|-----------|
| 1 | **观察真实工作** | 别自动化幻灯片里的流程；变通做法不自动等于领域专长（`FDE-002`） |
| 2 | **拥有结果** | 先定义运营结果再选技术；"生成回复"是输出，"解决异常并在账本确认修正余额"才是结果（`FDE-001`, `VAL-001`） |
| 3 | **界定合格工作** | 明确哪些工作合格哪些不合格；先声明分母再算采纳率；"处理大多数简单案例的系统"可能比"处理少数昂贵案例的系统"价值更低（`VAL-001`） |
| 4 | **建立反事实** | 先度量当前工作流再声称改进；前后对比图不自动是因果证据，声明已知混杂因素与归因方法局限（`VAL-001`, `VAL-002`） |
| 5 | **命名验证者** | 生产系统不应是它是否成功的唯一裁判；验证者必须能否决结果；接受 ≠ agent 走到工作流末尾（`FDE-001`, `EVA-001`, `REL-003`） |
| 6 | **工程化工作流与采纳** | 技术成功但没人用 = 零价值；如果用户必须重建每个结果才敢信，工作就没有被自动化（`FDE-003`, `ADP-001`, `ADP-002`） |
| 7 | **使用最小充分智能** | 别一开始就决定问题需要 agent；分解成决策再逐个比较；升级困难案例而不是让每个决策都走最强模型（`ARC-004`, `ARC-005`） |
| 8 | **界定权威与损失** | 能力不授予权威；单个被允许的行动可以组合成不可接受的结果，审查完整行动路径（`IAM-003`, `SEC-004`, `REL-001/003/005`） |
| 9 | **为整个服务定价** | Token 只是成本之一；更便宜的模型可能让周边工作流更贵；技术正确的结果仍可能经济上不可接受（`CST-001`, `CST-002`） |
| 10 | **在代表性工作上证明** | 成功的演示证明路径可行，不证明系统可上线；试点预先声明最大时长、证据截止、决策所有者与独立毕业门禁（`EVA-001/003`, `DEL-001`） |
| 11 | **度量可归因的已实现价值** | 合格工作→到达工作流→完成工作流→被接受结果→度量的业务影响→持续净价值；报告不采纳、覆盖、返工、评审者负载、事故、恢复与全成本（`VAL-002`, `OPS-004/006`, `CST-001`） |
| 12 | **基于证据扩张、约束或退役** | 自主性与投资必须靠前进的成果赢得继续的权利；更强的基准、更大的模型或更高的使用数字不自动证明更多权威（`VAL-003`, `ADP-002`, `OPS-007`） |

**四个硬门禁（硬性，不可平均）：**

1. 一个有主、可度量的结果（owned outcome）
2. 一个可信的独立验证者（credible independent verifier）
3. 有界的权威与预期损失（bounded authority and expected loss）
4. 全成本后仍为正的、合理的价值主张（plausible positive value case after full cost）

任一门禁缺失，正确的决策可能是 `defer`（推迟）、`redesign`（重新设计）或 `do_not_build`（不构建）。其余因子按 **0 — 未定义 / 1 — 已声明 / 2 — 已证明** 评分；分数支持对话，不是认证，强因子不能平均掉失败的门禁。

**价值公式：**

```text
预期净价值 =
  合格量 × 预期采纳率 × 预期增量被接受结果率 × 每个被接受结果的价值
  − 预期生命周期成本
  − 未从避免损失或单位价值净额化的预期残余损失
```

### 3.9 教程示例 1：受控写入系统（invoice-exception，发票异常解决）

演示目标：**模型提议；可信软件授权并提交；真相源回读证明结果。** 目标流：

```text
发票异常事件 → 收集账本/供应商/策略证据 → 提议解决方案 → 验证不变量
  → 授权并暂存 → 批准确切提案摘要 → 幂等重新授权并提交
  → 对账任何'效果未知'超时 → 回读账本状态 → 完成回执 | 补偿 + 事故
```

核心机制与不变量（这就是"受控写入"的示范）：

- `resolution_commits(tenant_id, business_operation_id) <= 1`（幂等：一个业务操作只能提交一次）
- 提交前运行时发布摘要 == 准入的解决方案发布摘要；提交的发票修订 == 当前发票修订；提交的提案摘要 == 批准的提案摘要；策略修订 == 当前策略修订
- 调用者租户 == 发票租户；每个数据/影响边界都检查当前调用者作用域与当前策略修订
- `committed == true` 只在真相源回读之后；`effect_unknown` 在重试或完成前对账
- `completed == true` 只在可信回执与回读证明验证之后；步骤、墙钟时间与成本在声明运行时预算内；**`model_access(credentials) == false`（模型永远接触不到凭证）**

配套工件：可执行运行时 `reference-loop.mjs`、授权策略 `authorization-policy.mjs`、类型化工具契约（读/暂存/提交/回读）、能力清单与出处记录、威胁模型、评估用例（授权提交 / 未授权写入 / 重复重试 / 修订漂移重试 / 提示注入）、独立评分器、评估报告与仅评审的解决方案发布。回归覆盖：授权、租户隔离、陈旧策略、重复重试、批准时机、发布撤销、回执验证、效果未知恢复与真相源回读。

### 3.10 教程示例 2：混合系统（shipment-risk-triage，货运风险分诊）

证明 **AI 系统不必 agent 优先**：经典 ML 打分 → 确定性策略路由 → 可选模型解释 → 人工保留运营决策。四种机制在一个有界工作流里组合，每个组件都有选型记录（`intelligence-selection.md`）、评估用例与回归测试。它是"混合智能系统蓝图"的可执行伴侣。

### 3.11 系统设计的八个显式层

模型是一个更大软件与运营边界内的一个组件。设计这些层（对应 `design-production-ai-system`）：

- **领域与状态（Domain and state）**：对象、身份、修订、生命周期状态、不变量与真相源系统
- **上下文（Context）**：来源、权限、出处、新鲜度、充分性、信任与失效
- **行为（Behavior）**：代码、规则、模型路径、提示词、工具、护栏与兼容性
- **权威（Authority）**：调用者或工作负载身份、租户、范围、策略、批准与最大影响
- **能力（Capabilities）**：类型化输入输出、精确目的地、凭证模式、失败契约、重复安全与回读
- **运行时（Runtime）**：持久状态、取消、超时、资源预算、重试、熔断与显式终止状态
- **工作界面（Work surface）**：持久工件、证据、状态、不确定性、替代方案与被允许的人工行动
- **运营（Operation）**：trace、服务目标、告警、runbook、变更路径、回退、所有权与退役

**核心行动规则**：模型可以提议（propose）。可信软件授权并提交（authorize and commit）。真相源回读（source-of-truth readback）证明结果。秘密与凭证保持模型可见上下文之外；在执行关键影响（consequential effect）的边界重新检查当前身份、租户、范围、策略、发布准入与批准；用稳定的业务操作身份推导重复安全；产生影响后在权威系统中验证结果，再报告完成。

### 3.12 架构不可妥协项与反模式

**不可妥协项：**

- 模型使用时：模型提议，确定性软件验证、授权、执行、持久化并验证关键工作（`ARC-002`）
- 每个组件都有命名的目的、版本、所有者、权威上限、证据、成本分配、监控、回退与退役路径（`ARC-005`, `DEL-001`）
- 真相源状态、身份、批准与完成证明位于提示词与瞬时模型上下文之外（`CTX-001`, `IAM-001`, `REL-003`）
- 发布单元绑定数据、领域、智能组件、工具、策略、评估、用户界面与运营——不只是代码（`DEL-001`）
- 基础模型或 agent 被保留是因为它在要求的护栏下改进了被接受的结果，而不是因为它新颖或可用（`ARC-004`, `VAL-002`）

**反模式：** 把确定性策略决策称为"agent 推理"；把模型路径当作架构而状态/访问/影响/恢复仍隐式；给调度、分配、验证或分类问题加 LLM 而不比较更简单机制；训练或路由 ML 模型却没有稳定标签、错误度量、漂移监控或所有者；优化推理成本却忽略工具、评审、恢复与客服成本；把没有状态转换、信任边界、失败行为或发布测试的架构图当作完整。

## 四、设计哲学

### 4.1 "AI 有记账问题"：从活动度量转向结果度量

设计哲学的起点是对现状的批判：**团队度量 token、调用、代码、agent 与"声称节省的工时"，这些只描述智能的生产与消耗，不确立任何价值发生。** 组织最终为被改变的结果买单。因此"valuemaxxing（价值最大化）"不意味着最大化自动化——它意味着**从一个人可验证、可运营、可停止的系统中最大化持久净价值**。

### 4.2 "在自主性之前先工程化价值"：模型不是起点

项目的第一原则与行业主流叙事相反：**不要从"用哪个模型"或"要什么样的 agent 拓扑"开始，从工作与被接受的结果开始。** Agent 是一个组件选项。对每个关键决策，7 种机制（确定性软件/优化/经典 ML/检索/基础模型/有界 agent/人工）逐一比较，选最小充分机制。**"更 AI"可能意味着工作流从未被正确分解。**

### 4.3 "能力不授予权威"：信任的最小化设计

**模型永远只能提议。** 可信软件（确定性代码）负责授权、执行、持久化与验证关键工作。权威绑定到工作流、行动者、租户、目的、任务、目标、时长与后果；单个被允许的行动可以组合成不可接受的结果，所以要审查完整行动路径。真相源状态、身份、批准与完成证明永远在提示词与瞬时模型上下文之外——**秘密与凭证模型永远接触不到（`model_access(credentials) == false`）**。

### 4.4 "验证者必须能否决"：生产系统不能给自己打分

评估三问分离能力/行为/结果；**生产系统不应是它是否成功的唯一裁判**——验证者（确定性检查、真相源对账、独立评估、下游确认或可问责的人工评审者）必须能否决结果。"接受"比"agent 走到工作流末尾"要求更多。这个哲学与"别让 agent 自我验证"一脉相承，但把它升级成了**价值契约里的一个硬字段（命名验证者）**。

### 4.5 "评分支持对话，门禁不可平均"：证据伦理

0/1/2 评分框架与 4 个硬门禁的分立是全项目最锋利的哲学主张：**演示与复合分数不能平均掉失败的门禁；预测、已证明试点与已实现价值必须分开；零是证据，不是默认值。** 停止、收窄或重新设计薄弱工作是有效结果——强模型分数、赞助人、上线数字都不能掩盖失败的价值/权威/安全/所有权/生产门禁。**评估是"声明条件下的发布主张"，不是永久分数。**

### 4.6 "变通做法不是领域专长"：对现场的谦逊

观察真实工作（而不是幻灯片里的流程）；分类每个观察到的行为为保留/修复/移除/升级。**AI 能让破碎流程跑得更快，同时让底层问题更难被看见。** 现场学习的复利优势是把本地上下文与可移植工程知识分离的能力；不要制造依赖，保留负面与停止证据，保留退出路径。

## 五、归纳总结：观点与结论

### 5.1 核心观点清单

1. **价值定义：** 被接受的结果（独立验证者/权威系统/可问责评审者接受为正确的工作单元）才是产品；token 与自动化只是输入与手段。
2. **起始点：** 从工作与被接受的结果出发，而不是从模型或 agent 拓扑出发；Agent 是一个组件选项，不是架构。
3. **最小充分机制：** 对每个关键决策在 7 种机制间比较并选最小充分者；"用 AI"不是架构决策；更 AI 可能意味着工作流从未被正确分解。
4. **观察优先：** 先观察真实工作（操作者走查/源工件/系统 trace）再设计；访谈只产生假设；别自动化幻灯片里的流程，也别在修复前自动化变通做法。
5. **价值契约字段：** 合格人群/基线/被接受结果/验证者/目标护栏/归因/全成本/残余损失/所有者——九字段先于架构。
6. **12 因子 + 4 硬门禁：** 有主结果 / 可信独立验证者 / 有界权威与预期损失 / 全成本后仍正的价值主张；任一缺失 → defer / redesign / do_not_build；0/1/2 评分支持对话但不可平均门禁。
7. **权威边界：** 能力不授予权威；模型提议、可信软件授权提交、真相源回读证明；秘密与凭证永远在模型上下文之外；幂等（一个业务操作一次提交）与效果未知对账是硬不变量。
8. **采纳与运营：** 技术成功但没人用 = 零价值；移交以"接收团队可运营/变更/恢复/支持/退役"为完成标准（演练而非文档）；生产是反复决策而非最后部署步骤。
9. **反 agent 优先：** 混合系统示例证明确定性策略 + 经典 ML + 人工审查可以是正确架构；只有有界多步判断真正有用时才加 agent。
10. **现场学习：** 复利优势 = 分离本地上下文与可移植知识；产品化需跨独立环境复现证据 + 消毒 + 目的地所有者 + 正常发布路径；不要制造依赖。

### 5.2 关键金句（值得 memo 的）

- "Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."（**Tokens 是输入，自主性是设计选择，被接受的结果才是产品。**）
- "Start with the work and the accepted outcome—not with a model or agent topology."（**从工作与被接受的结果出发，而不是从模型或 agent 拓扑出发。**）
- "Capability does not grant authority."（**能力不授予权威。**）
- "The model may propose. Trusted software authorizes and commits. A source-of-truth readback proves the result."（**模型可以提议；可信软件授权并提交；真相源回读证明结果。**）
- "AI has an accounting problem."（**AI 有一个记账问题。**）
- "The system producing the work should not be the sole judge of whether it succeeded."（**生产工作的系统不应是它是否成功的唯一裁判。**）
- "A workaround is not automatically domain expertise."（**变通做法不自动等于领域专长。**）
- "A more capable model will not repair an undefined task."（**更强的模型不会修复一个未定义的任务。**）
- "The point is not to use more AI. The point is to make the outcome worth the system required to produce it."（**重点不是用更多 AI，而是让结果值得为产生它所需的系统。**）
