# anything2explainer 深度解析：给一个主题，产出一条代码画出来的讲解视频

## 引子：你想让 AI 讲清楚一件事，但视频是个麻烦

设想一个很具体的需求。

你刚读完一篇论文，或者刚搞明白一个技术概念，想发一条三分钟的科普视频到视频号。选题有了，稿子也大致想好了。现在卡住的是：画面怎么办？

找素材？版权不清，而且拼起来的素材永远拼不成一条有逻辑的片子。找 AI 视频生成模型？目前生成的片段接不上、字写不对、每帧都在漂。用口播数字人？技术上没问题，但一个会说话的脑袋不会解释任何机制，它只是念稿。

再退一步，让 AI 编程 agent 写代码来画每一帧？

这个方向是对的，但立刻会撞上第二个问题：Remotion 本身只给你一个画布，它不告诉你一部片子该长什么样。第一个 agent 画出来的镜头漂亮，第二个 agent 画出来的像 PPT，第三个直接忘了字幕带在哪。五个 agent 的产出拼在一起，像五家不同的公司做的。

那到底该怎么做？

anything2explainer 给出的答案很直接：别只写代码，把整套方法也写出来。它把"怎么拍一条 AI 生成的科普视频"这件事，拆成了风格规范、动效词汇表、构图与光的硬规则、agent 分工协议、量化质检脚本，再加一条完整的样片作为质量标尺。

这不是一个能跑的命令行工具，它更像一本写给 AI 的电影制作手册。

## 一、项目说明：仓库里到底装了什么

### 1.1 一句话定位

输入一个主题，或者一篇你想改成视频的文章，输出一条 1280×720 的 H.264 MP4：带 TTS 配音、逐词对齐的字幕、章节卡、顶部 HUD 和底部章节进度条，中文或英文都行。

关键在于每一帧都是代码画出来的。没有素材库，没有生成式视频模型，也没有从别人视频里拿的任何一帧。

作者 Vincentwei1021 在 CITATION.cff 里的定位是"software"，发布于 2026-09-09，许可用的是 PolyForm Noncommercial 1.0.0，非商用免费，商用需要事先授权，但用它做出来的视频归你自己。

### 1.2 它不是 CLI

这一点值得单独说，因为很多人会拿它当工具去试，试用完发现"没反应"。

仓库里装的是让 AI 编程 agent 把片子做出来的整套方法。真正会被执行的只有三样东西：

- 一个可编译的 Remotion 4 模板工程（`template/`），你用 `new_project.sh` 把它复制成工作目录；
- 一堆写给主会话和各个 agent 看的规范文档（`reference/`）；
- 一条已经做完的样片（`examples/rag/`），连同它的调研底稿、解说词、分镜表、44 个镜头的源码和 5 份 QC 报告。

作者给 skill 装了一个 Claude Code 的徽章和一个 Codex 的徽章，也就是说它是被这两种 agent 加载的"技能包"，不是让人敲命令的软件。

### 1.3 仓库结构速览

```
SKILL.md                  流程主干：9 个阶段、4 个确认点、质量标尺
reference/                写给主会话和各 agent 的规范
  style-guide.md            安全区、调色板、字体、图元目录、版式规律
  motion-vocabulary.md      入场/强调/光效/离场/运镜的公式与帧数
  composition-and-light.md  主体尺寸三档、光跟主角、高光时刻编排、QC 量化判据
  narration-guidance.md     口播文案写作原则（纯英文，已译中文）
  narration-storyboard.md   解说词格式与预算、配音参数、分镜令牌、镜头模式表
  research-brief.md         研究员 prompt 与事实规则
  agent-build-rules.md      构建 agent 协议
  agent-qc-rules.md         QC agent 协议
  prompts.md                六种 agent 的 prompt 模板
  lessons.md                五部片子的踩坑记录与根因
template/                 可编译的 Remotion 4 工程
  src/common/               雾底、星点、点阵波、glitch、缓动、字幕、进度条
  src/ui.tsx  src/fx.tsx    图元与调色板/光效、纵深、运镜图元
  src/overlay/              片头、章节卡、HUD、流程轨、片尾
  scripts/                  配音、分镜、still、测渲、渲染、QC 度量脚本
examples/rag/             样片全套纸面文件与成片帧
examples/contrast/        6 组反例/正例帧对照
```

`examples/contrast/` 这个目录特别值得注意，它是一张"评分表"。左边是作者 2026-09-08 用 skill 做的另一部片《eCPM 与广告竞价》的帧，右边是样片《RAG 与知识库》的帧，六组对照，每组都指向一个具体缺陷：主角太小、主角没光、高光时刻没编排、结果项字太小、背景撒碎屑、收尾没象征物。

### 1.4 和其他工具的区别

作者自己列了一张对比表，我把它当成选型依据：

| 工具类别 | 产出 | anything2explainer 的不同 |
|---|---|---|
| 生成式视频模型（Sora、Veo、Runway） | 从 prompt 合成素材 | 产出是确定性的代码不是像素。画面上每个数字都能追到一个来源 URL，任何一帧都能靠改一个镜头文件修好 |
| 数字人 / 主播工具（HeyGen、Synthesia） | 一个数字主播念稿 | 不要主播。用动效图解讲机制，由旁白驱动画面 |
| 手写 Remotion / Motion Canvas | 一个可编程的视频画布 | 它在画布之上交付整套方法：调研 → 解说 → 分镜 → 并行构建 → QC，带风格规范、动效词汇表和一条样片作为标尺 |
| Manim | Python 数学动画 | agent 驱动的端到端流水线，带 TTS 对齐字幕、章节与 QC；React / TypeScript 而非 Python |

第二行那个"不要主播"的决定，比听起来重要得多。数字人视频的视觉信息量等于零，你只是把稿子念了一遍。而动效图解可以同时展示结构、顺序和数量。README 里有一句很到位的表述：解说负责理由、后果、比较和判断，画面负责结构、顺序和数量。

## 二、核心思想：为什么坚持用代码画

### 2.1 三条不可让步的原则

**第一，画面全部代码绘制。** 可选的实拍 B-roll 只允许免版权来源，并且要登记 MANIFEST（sha256、来源 URL、许可、用途）。不能使用任何现有视频的帧或片段。

**第二，事实必须有出处。** 画面上出现的每个数字、年份、机构、人名和英文术语，都必须能在这一部片子的调研文档里找到来源 URL。调研没核实的内容，不上画面，也不进配音。

**第三，全片一个贯穿示例。** 解说和画面用同一个例子从头到尾。样片用的是"差旅报销"这个场景：问句是「差旅报销的上限是多少？」，幻觉的答复是「每天 1000 元，全国统一」，正确答复是「住宿上限每天 600 元[1]，一线城市 800 元[2]」，来源是「员工手册 p.12」和「差旅补充规定 2025」。所有组共用同一套示例文本，这是硬约束。

第二条是整个项目最有价值的设计。因为视频的观众无法点击来源，一旦一个数字错了就是错了，纠错的成本远高于文章。把它前置成"调研阶段不核实就不许上画面"，比事后靠 QC 从像素里认字要可靠得多。

### 2.2 "代码画"到底换来了什么

这是理解这个项目的关键。视频生成模型和代码渲染看起来都是"让电脑画出画面"，但换来的东西完全不同。

**确定性。** 每一个动画都是帧号的纯函数，随机数用带种子的 `rnd(...)`，文字宽度是算出来的而不是在 DOM 里量出来的。所以重新渲染一遍，出来的帧是完全一样的。视频生成模型做不到这一点，同一个 prompt 跑两次给你两个东西。

**可编辑性。** 任何一个镜头出问题，agent 改一个 `SCxx.tsx` 文件里的一个数字，重新渲染。视频生成模型做不到这一点，你只能重新生成整段，而且不保证这次更好。

**可溯源性。** 画面上每个数字都能追到调研文档里的一个 URL。因为画面本来就是从那份文档"画"出来的。

**可验证性。** 这是最被低估的一条。因为画面是代码，所以可以静态分析。`selfcheck.py` 能在不渲染的情况下，扫描所有镜头源码，数出有几处闪烁、把它们和分镜表里的白名单对账、把所有会上画面的字面量抽出来和事实清单对账。这三件事几秒钟跑完，而 QC agent 是从像素里查的，看不到没被抽到的帧。作者在 `lessons.md` 里说得很直接：这三个检查抓到的都是 QC 从像素查不到的问题。

### 2.3 一个反直觉的判断

很多人第一反应是"AI 画视频应该用生成模型，代码渲染是老派做法"。作者用一组数据反驳了这个判断。

他拿自己用 skill 做的《eCPM 与广告竞价》和样片《RAG 与知识库》逐帧对比，两片动效数量、节奏、柔光总面积几乎完全相同：

| 指标（成片逐帧，内容区） | 广告竞价 | RAG 样片 |
|---|---|---|
| 每帧平均变化量 / 动效事件每分钟 | 0.47 / 72 | 0.56 / 76 |
| 最大物体高度中位数 | 172px | 219px |
| 最大物体 <110px 持续 ≥1.5s 的时长占比 | 29% | 12% |
| 源码光效词 halo / sweep / ghost | 0 / 0 / 0 | 14 / 12 / 5 |
| 源码 skew / perspective / rotate | 1 / 0 / 4 | 7 / 1 / 15 |

差距全在"画多大、谁发光、高光时刻怎么编排"这三件事上，跟"动得多不多"没关系。

这解释了一个很多人会踩的坑：初版 skill 写了安全区、白名单、归零、节拍这些纪律项，新片在这些项上甚至做得更好，但"主体该画多大、光该打在谁身上"只在做样片的那个人脑子里。结果就是画面小而暗、四轮 QC 全过还是难看。

修法不是加动效，是加硬规则。这是 `composition-and-light.md` 存在的全部理由。

## 三、详细教程：从零跑通一条片子

下面是完整的 9 阶段流程。阶段 0 到阶段 8，加上穿插其中的 4 个确认点。

### 3.1 阶段 0：建项目（5 分钟）

```bash
git clone https://github.com/Vincentwei1021/anything2explainer.git
ln -s "$PWD/anything2explainer" ~/.claude/skills/anything2explainer   # Claude Code
ln -s "$PWD/anything2explainer" ~/.codex/skills/anything2explainer    # Codex
```

依赖：

```bash
# Node ≥18（模板的 npm install 会装 remotion 4.0.507 / react 19）
brew install ffmpeg          # 抽帧 / 转码，必需

python3 -m venv ~/.venvs/a2e && source ~/.venvs/a2e/bin/activate
pip install 'edge-tts==7.2.8' numpy pillow scipy   # edge-tts 必须锁版本
```

`edge-tts` 那个锁版本不是强迫症。README 里写得很清楚：它跟踪一个微软的端点，跨版本会坏，7.2.0 之后需要显式请求词边界。`scipy` 只有 `frame_metrics.py` 用得到。

只做英文片的话再装 `kokoro soundfile` 和 `espeak-ng`。

树莓派和 ARM 机器上作者也验证过，有三处不同：脚本是 `#!/bin/zsh` 所以要装 zsh，Remotion 没有 linux-arm64 的无头浏览器要指向系统 Chromium（`REMOTION_BROWSER_EXECUTABLE=/usr/bin/chromium`），以及 kokoro 在 ARM 上装不动（它锁了老 numpy 并拉 spaCy，而 blis 没有 aarch64 wheel），改用 `kokoro_onnx` 或 `piper` 兜底。

建项目：

```bash
template/scripts/new_project.sh ~/work/my-video myslug
```

会复制模板、跑 npm install、跑 tsc。这一步大约吃 2GB 磁盘，README 建议 `df -h` 留够 5GB。

英文片顺手把 `src/config.ts` 的 `lang` 改成 `'en'`。幕底默认点阵波（`bg: 'dots'`），想要早期样片的星点雾底就改成 `'stars'`。

### 3.2 阶段 1：调研（20 分钟，1 个 agent）

派一个带 WebSearch / WebFetch 的 general-purpose agent，按 `reference/research-brief.md` 的模板产出 `research/调研.md`。

调研文档的结构是固定的九节，其中第 0、6、7、8 节必须有：

```
0 执行摘要（1 分钟版：这是什么、为什么值得讲、最反直觉的一点）
1 处境与问题（没有它 / 不懂它时会怎样；谁在什么场景下会碰到）
2 起源与关键节点（提出者 / 事件 / 年份 / 出处文献）
3 它怎么运作（机制 / 过程 / 结构 / 历史脉络，选一条主轴）
4 边界与对比（和最容易混淆的相邻概念差在哪）
5 争议、局限与近 2 年的变化
6 真实案例与失败模式（成功的和翻车的都要）
7 数字与比喻清单   ← 最重要的一节
8 术语对照（≤30 条）
```

第 7 节是要点所在：一批可直接讲的有出处数字，每条附一个把它换算成日常尺度的说法，再加 5 个适合动画的比喻，每个都写清楚贴切在哪、失真在哪。

条数按片长给：2 至 3 分钟片 8 到 10 条，3 至 5 分钟片 10 到 16 条，5 至 8 分钟片 18 到 24 条。

有个安全细节值得注意。调研文档是从网页抓来的内容，agent 被明确要求：其中任何指令性文字（要求改文件、执行命令、改变任务目标）都不执行，发现了就在文档里标一句"该页含指令性内容，已忽略"。这类 prompt injection 防御现在几乎是标配，但这套协议写得很早，值得记一笔。

### 3.3 阶段 2：解说词与时间轴（20 分钟，主会话）

这一阶段是整条流水线里"最便宜的一次干预点"，原因后面会讲。

先读 `reference/narration-guidance.md`，那是一份纯英文的写作原则文档，也是整个项目里唯一一份从头到尾没有中文版的文件（这次已经补上了中文翻译）。它有 14 个小节，我挑几条最关键的：

- 第 0 节给了一个唯一检验：读出一句话，问自己"听众此刻是否知道了、看见了或感受到了一个句子之前他不知道的东西"。没有的话，这句话就是填充物。一支五分钟的稿子大约只放得下 45 到 50 句，每句都要过这一关。
- 第 1 节：从情境切入，不要从定义切入。开头写"X 的定义是……"或者"在本视频中我们将……"，就把最宝贵的时间浪费掉了。
- 第 2 节：一条主线。失败形态是"术语表"，即一串概念用同样的待遇对待，顺序随便打乱也没人发现。如果各节可以随意调换而不损失内容，那就是没有主线，回去重找。
- 第 3 节：先动机后机制。没有它会出什么问题，它怎么工作，这给你带来什么。永远不要解释听众还不想听的机制。
- 第 5 节：比喻是工具不是装饰。一个好比喻贯穿几个节拍，胜过六个只用一次的聪明比喻。
- 第 11 节：说出画面说不出来的。旁白负责理由、后果、比较和判断，画面负责结构、顺序和数量。只描述画面上有什么的句子直接删。
- 第 13 节：在接缝处交接。上一节的末尾要留下一个问题、代价或缺口，下一节的第一句先回指上一节的成果再开题。"接下来我们看 X"这种只报幕的过渡要删。

解说词格式长这样：

```
# CHAPTER 1 章名（≤6 字，进度条章名）
一句话|按竖线切成字幕块|每块 ≤16 字        ← 一行一句
同一段的下一句                                ← 段内句之间只隔 10 帧
                                              ← 空行 = 段落分隔：一段 = 一个镜头
新的一段（= 下一个镜头）
## gap 20                                     ← 可选：额外插空白
```

竖线只切字幕，不影响朗读。空行是镜头边界，这一条是全片结构的地基。

样片的解说词开头是这样的，可以直接感受一下节奏：

```
大模型很聪明|但它有三个天生的短板
第一|它的知识有截止日期|训练之后发生的事|它一概不知
第二|它读不到你公司内网里的文档|也不知道你昨天刚写的会议纪要
第三|遇到不知道的问题|它不会说我不知道|而是一脸自信地编一个答案|这就是幻觉
怎么办|重新训练一遍|成本太高|而且明天数据又变了
于是工程师们想出了一个办法|让模型开卷考试
考试前先把资料整理成一本手册|答题时先翻手册|再作答
这套方法就是今天的主角|RAG|检索增强生成
```

注意它没有一句在介绍概念，全部在讲处境。

确认点 2 就是在这里：把解说词全文、章节划分、字数和预估时长贴给用户，问"这版文案可以吗"。章名和 HUD 小节名单独列一行，因为进度条上就这几个词，作者还给了个自检三问：只看这几个词，没看过片子的人能说出每章讲什么吗？每个都是名词短语吗？连起来是不是一条看得懂的主线？

作者专门写了反例。第六片被用户点名，进度条章名是「感觉还行 / 搭台留痕 / 两把尺子 / 诊断与证明」，这是评价句和俏皮话，观众瞄一眼猜不出内容。正例是样片的「为什么要RAG / 知识库构建 / 检索与生成 / 评估与进阶」，抄出来给没看过片子的人，他也能说出每章讲什么。

确认点 3 紧接着问一句"配音有没有偏好的 TTS"。没有就用默认：中文 edge-tts `zh-CN-YunxiNeural`（云希，男声，原速不加速，约 5.5 字/秒），英文 kokoro-82m `am_liam`（Liam，男声）。有偏好就用自己的 TTS 生成成品 wav 放进 `public/assets/<slug>/audio.wav`，再手填 `src/common/timeline.ts` 和 `subs.ts`，后续流程完全不变。

然后跑配音：

```bash
python3 scripts/tts_build.py
```

它逐句合成，用 WordBoundary 切出字幕块，输出配音 wav、帧级时间轴和字幕表。停顿策略写在脚本里：段内句间 10 帧，段末再加 20 帧，章前 45 帧。

**停顿只放在段末，不放在每句之后。** 这一条是用户反馈逼出来的，加每句都停会让整片显得拖。段末 30 帧差不多 1 秒，观众觉得"这句话讲完了，画面也落位了"，然后才切。

脚本还会在终端列出末块不足 45 帧的段末句，带 `¶` 标记。那些句子后面要加 `## gap 15-30`，或者在分镜时把末拍元素前挂到上一块。

跑完核对成片时长是否落在用户要的区间，差超过 15% 就加删句子重跑，别靠改语速硬凑。

然后就冻结。定稿之后不再改词，因为每个镜头的帧号都硬编码在构建组的代码里，改一个字就要全片重对位。

### 3.4 阶段 3：分镜（25 分钟，主会话）

写 `script/storyboard_src.md`，用令牌代替帧号，然后渲染成 `分镜表.md`：

```bash
python3 scripts/render_storyboard.py
```

令牌长这样：`{S12.from}` `{S12.to}` `{S12.c3}`（第 3 个字幕块起始帧）`{C2}`（第 2 章起始帧）`{TOTAL}`，可以带偏移，比如 `{S12.from-8}`。

每个镜头一行，列是：镜头 / 帧 / 节拍 / 画面 / 动效 / **主角·尺寸** / **光**。

后两列是后加的，这也是最值钱的一次改版。原来分镜表只有"画面"和"动效"，构建组就不知道该把主体画多大、光该给谁，结果主体中位高度只有 172px，主角全是无光白线框。补上这两列之后，样片是 219px。

动效列每行末尾必须有「持续：…」和「停留：…」两句：

- **持续**：这个字幕块的动词靠哪个动作撑到下一拍（数据流、脉冲光点沿箭头跑、逐行打字、逐格点亮、生长、旋转、闸门开合、队列压紧）。没有其它运镜的镜头写「1.0→1.05 慢推」。**不写漂浮、飘动、呼吸。**
- **停留**：末拍元素落位帧到离场起点的帧数，≥30，目标 30 到 45。不够的三选一：末拍元素前挂、回文案加 `## gap`、并入相邻镜头。

分镜表末尾的「全局约束」要写七块内容：示例语境、事实清单、闪烁白名单、复用图元清单、章界清单、高光时刻清单、扫光白名单，外加 §9 持续动作与落位停留的规则全文。

### 3.5 阶段 4：覆盖层与图元（10 分钟，主会话）

模板自带片头、章节卡、HUD、流程轨、片尾，图元库在 `src/ui.tsx`，光效和运镜图元在 `src/fx.tsx`。你只需要按主题补 2 到 5 个语义图标进去。

样片补的是 `DocIcon`（文档）、`DBIcon`（数据库）、`ChunkCard`（文本块）、`LLMIcon`（大模型）。

然后出一张 still 看一眼：

```bash
scripts/still.sh Overlay 40,<章节卡帧>,<有轨帧>,<片尾帧> <绝对路径> ov
```

### 3.6 阶段 5a：打样（15 分钟，1 个 agent）

只派 G1（第 1 章上半），完工后渲前 30 秒：

```bash
scripts/preview.sh 30
```

这是确认点 4。用户要改的东西（配色、字号、语速、片头、示例语境）在这里一次改完。

作者对这一点的判断非常清醒：在这里改一次是 1 个组的成本，等整片渲完再改是全部组的成本。

### 3.7 阶段 5b：并行构建（40 分钟，其余各组各 1 个 agent）

组数按片长定，样片档 8 组，派 G2 到 G8。每组 5 到 7 个镜头，一个镜头一个文件 `src/shots/Gn/SCxx.tsx`。

派单用 `reference/prompts.md` 的构建 prompt，附 `reference/agent-build-rules.md`，并且要把 G1 作为已验收的风格样例点名让它们读。

这里有几个硬约束，是构建协议里反复强调的：

- 帧号 `N = useCurrentFrame() + F0`，所有动画是 N 的纯函数，随机只用 `rnd()`，禁用 `Math.random`，不要用 useState / useEffect 做动画。
- 只能改 `src/shots/Gn/**`，不碰 Main / Root / common / 别的组。
- 硬切前离场必须归零：用 `opacity = 1 − (n/N)^1.5`，不能用每帧 6.7% 的 exitFade（末帧还剩 40% 到 60% 会"啪"）。
- 入场轨迹不得穿字幕带：自下滑入 Δ ≤ 120，要从画外进来就用侧向滑入 Δ 260 到 320。
- 性能红线：禁 `feConvolveMatrix`，`filter: blur()` 的 σ ≥ 1，单帧 DOM 节点 ≤ 600，SVG filter 实例 ≤ 6。违反会让整片渲染慢 10 到 50 倍。
- 完工前必须跑 `npx tsc --noEmit`、每镜头至少出 6 张 still、30 帧测渲，以及 `python3 scripts/motion_check.py <Gn>`。

最后这条是最新的，量化的是持续动作和落位停留：每镜头最长静止 ≤3 秒，末拍稳定期 ≥30 帧。

### 3.8 阶段 6：渲染（5 分钟）

```bash
npx tsc --noEmit
VER=v1 scripts/render.sh
```

8000 帧约等于 4 分半片长，渲 3 到 4 分钟，concurrency 6。产出 `renders/<slug>_v1.mp4` 加 `fin_frames/`。

然后主会话自己拼 6 张 contact sheet 通读一遍，再跑：

```bash
python3 scripts/frame_metrics.py --out qc/frame_metrics_v1.md
```

这一步量的是：每镜头最大物体高度、主角区柔光面积、紫色碎片指数、静止段。

### 3.9 阶段 7：QC 与修复（60 到 90 分钟）

每章 1 个 QC agent，按 `reference/agent-qc-rules.md` 跑，输出 `qc/qc_v1_Cn.md`。按组派修复 agent，一个 agent 只修一到两组。

渲 v2，2 个复验 agent 逐条核 v1 的问题加回归通读，小修，渲 v3。

终检要做四件事：闪烁白名单扫描、扫光白名单核对、frame_metrics 构图与光复核、motion_check 成片复测。

作者反复强调一件事：**组级 motion_check 过了不等于成片过。** 第四片 v1 组级 48 个镜头全部达标，成片复测却有 11 个镜头超限，3 个是真静，8 个只有小面积动作。原因是组级是低分辨率渲染，读数偏松。所以流程里成片复测是必须的，不能省。

### 3.10 阶段 8：交付

产出 `交付说明.md`：成片、配音来源、事实出处、示例语境、质检结论、已知保留项、目录。片尾默认署名 `built by Anything2Explainer skill`，`config.builtBy` 设成空字符串可以去掉。

然后把新经验写回 `reference/lessons.md`。这一条让整个仓库变成一个持续学习的系统，前面五部片的教训都还躺在那。

## 四、多 agent 分工协议：一条片子要开多少个 agent

这是整个项目里最"工程"的部分，也是别人照搬不走的东西。

### 4.1 六种角色

`reference/prompts.md` 定义了六种 agent prompt 模板，加上 `research-brief.md` 和两份规则文档，一共八份文件构成了完整的调度协议。

| 角色 | 数量 | 职责 | 产出 |
|---|---|---|---|
| 研究员 | 1 | 带 WebSearch/WebFetch 查证事实 | `research/调研.md` |
| 构建组 | 8（样片档） | 每组 5–7 个镜头，一个镜头一个文件 | `src/shots/Gn/**` + `BUILD_NOTES.md` |
| QC | 每章 1 个 | 按书面判据逐帧检查 | `qc/qc_vN_Cn.md` |
| 修复 | 每 1–2 组 1 个 | 修 QC 报告里的条目 | 代码 + BUILD_NOTES 追加小节 |
| 复验 | 每两章 1 个 | 核 v1 问题是否真修好 + 回归通读 | `qc/qc_vN+1_recheck_C**.*.md` |
| 终检 | 1 | 闪烁合规、扫光白名单、frame_metrics、motion_check 成片复测 | `qc/qc_vN_final.md` |

### 4.2 派单的第一条纪律：一个 agent 只派一件重活

作者在 `lessons.md` 里写死了这条：构建 5 到 7 个镜头算重活，QC 一章算重活，修 1 到 2 组算重活。第二件只派轻活。

理由是他踩过坑：读过大量图片的 agent 再派重活，有大约 30% 的概率直接阵亡，报 "input too long"。

这跟另一个常见误区正好对着：QC agent 被要求"边查边 append"到文件，不是建议，是硬要求。有一片一个 QC agent 攒到最后写盘，跑了一小时零产出、消息也不回，只能 TaskStop 重派。理由很简单：如果它中途被打死，前面积累的结论全丢了。

### 4.3 并发上限：pane 是全机共享的

这是最反直觉的一条。作者在第三片踩到：pane 上限比上次更早撞上，同时开着 14 个其他会话，派到第 5 个 agent 就 `respawn pane failed: fork failed: Device not configured`。

修法是按 4 个一波派，一波完成并释放后再派下一波，派单前先 `ListAgents` 看全机占用，预留 1 到 2 个 pane 给后面的 QC 和修复轮。

这一条在 Claude Code 和 Codex 里都是一样的，作者在 prompt 模板末尾专门写了一段"派单与看门狗"：完成的 agent 及时 TaskStop 释放，被 API 错误打死的先 SendMessage 叫一次，10 分钟零产出就 TaskStop 重派（重派时明确告诉它"复用磁盘上的半成品，只补未完成部分"），每 30 到 40 分钟核一次各组 index.ts 和 BUILD_NOTES 的 mtime。

### 4.4 不要照抄 agent 的自评

作者抽验过一个组的自评："中间年份模糊不可读"——实际出图清晰可读，那个组自己在复盘时也承认这条自评过于乐观。

但他的结论不是"agent 会撒谎"，而是两句一起说：报告要抽验，但也别急着断定 agent 说错了，先把证据看全。另一条他查下来是自己误读，报告其实是对的。

### 4.5 构建组会发现分镜表本身的错

这是作者最看重的资产之一。第三片最有价值的三条改进全部来自构建组：价值柱公式与画面标注矛盾、年份转盘的事实合规漏洞、以及据此主动偏离不给毫秒数做计数。

他的处理方式是：一条一句话裁定，然后把裁定推广成全片通则写回分镜表，而不是只批准这一个单点改动。

配套的还有一条硬性要求：构建组合理偏离（换示例文本、加中文全称、改拓扑）只要有出处就放行。

### 4.6 主会话自己也要做静态检查

作者不满足于只靠 QC。他自己保留三项不渲染就能跑的检查：帧覆盖静态分析（帧区间空洞与重叠）、源码字面量与事实清单对账、闪烁白名单源码级计数。

这三项几秒钟跑完，抓到的全是 QC 从像素查不到的问题。第四片里，源码对账一次性抓出一个实时计数器——画面上显示"本秒 +2405"，正下方灰小字写"一天几十亿次"，两者差 30 倍，四个 QC agent 全漏了。

## 五、归纳总结：这个项目的核心观点

读完整套协议，我把它的观点归纳成七条。

### 观点一：AI 创作的质量瓶颈不在生成能力，在规范

这个项目所有 agent 的产出质量都很依赖规范密度。`reference/` 下面十一份文档，加上模板里的一百多个组件和函数，代码量其实不大，规范的体量比代码还厚。

对照 `lessons.md` 里的记录就能看出规范的作用：初版 skill 有安全区、白名单、归零、节拍这些纪律项，新片在这些项上做得比样片还好，但"画多大、谁发光"没写，新片就小而暗。规范里没写的东西，agent 不会自己想到。

### 观点二：确定性和可编辑性比画面惊艳更重要

第 2.2 节已经展开过了。核心是：因为画面是代码，所以能静态分析、能精确修一帧、能追到来源。这三条加起来，比"这一帧很好看"值钱得多。

一个直接的推论是：不要用生成模型做这个活。

### 观点三：约束要写在明面上，不要指望 agent 领会

"全片一个贯穿示例"、"每镜头一个主角"、"每镜头最多一处闪烁"——这些不是建议，是硬规则，而且要能被机器检查。

`selfcheck.py` 存在的意义就在这儿：它把"闪烁白名单"从一句口号变成了一次计数对账。白名单里有 23 项，脚本扫出来必须正好 23 处，多一处少一处都算问题。

作者举过一个反面例子：分镜表里"glitch"这个词如果只写在一格，构建 agent 会给所有文字加闪烁，成片出来 102 处，用户直接否决。后来改成"每镜头最多 1 处 glitch，只给该镜头的重点词"，降到 21 处才过。

### 观点四：叙事质量取决于有没有主线，不取决于信息量

`narration-guidance.md` 第 2 节和第四片的复盘是同一件事的两面。第四片第一版 48 句按参考书的小节顺序写，用户第一反应是"太死板无趣"；按写作原则独立重写的版本盲评 8.2 对 4.3。

根因不是文笔，是没有主线。章可以随意调换顺序而不损失，那就是没有主线。

这里有个值得学的做法：作者把"怎么写得不无聊"从"分镜规范"里拆出来，单独成了一份 `narration-guidance.md`，并且在 SKILL.md 里规定阶段 2 必读。`narration-storyboard.md` 不再规定固定章法，只保留格式、预算和画面接口，镜头模式表的左列也改成题材无关的"画面关系类型"。

**规范要按抽象层级放对位置。** 叙事原则是通用的，挂在具体题材的模板下面就会被当成模板。

### 观点五：先定稿再配音，因为帧号会被硬编码

这是整条流水线里最反直觉的工程决策，也是四个确认点的设计依据。

一旦配音定稿，帧号就写进了每个镜头的代码里。改一个字 = 全片重对位 = 所有构建组重跑。所以作者把确认点 2（解说词定稿）放在配音之前，并且在 README 里说得很直接：这是全流程最便宜的一次干预点。

反过来说，第一、第二个确认点比第三、第四个更值钱。第一个（时长与语言）决定了句数、镜头数、构建组数，也就是这条流水线的规模；第二个（文案定稿）决定了一旦错了要重跑多少。

### 观点六：量化判据要分清"组级"和"成片"

第四片留下的教训：组级 motion_check 48/48 全部达标，成片复测 11 个镜头超限。

低分辨率渲染读数偏松。作者的修法是把组级渲染改成 0.5 倍加 JPEG q80，并让 `--frames` 模式多给一列"最长静止段内全分辨率变化像素数"，用来区分真静（<800）和小面积动作（800–2500）。

还有一条更细的：小面积动作的修法是**加大幅度**，不是加元素。运动元素更亮更大更密、主角本体 30 帧呼吸 ±2%，而不是往上糊更多小图标。

这个区分很关键。"给静止的物体加漂浮、飘动、呼吸"是明确禁止的，作者给的理由是：动作必须是动词本身的动作，找不到动词动作的镜头宁可静着，静止 ≤3 秒不是缺陷。

### 观点七：教会 agent 之后，还要教它怎么被考核

这一条我觉得是最容易被忽略、也最有价值的。

作者不满足于"让 agent 写代码"，他给 agent 写了判据、写了量化脚本、写了终检清单、写了"每个镜头至少给出一行结论（OK 也要写）"这种看似机械的要求。

甚至有一条是关于反例的：`examples/contrast/` 里放了 6 组反例帧，构建 agent 开工前必须先用 Read 看 `contrast_sheet.jpg` 和至少 6 张 `ref_*.jpg` 建立标尺。

这是把"品味"变成"可传递的参照物"。品味没法写进 prompt，但可以给一组对照帧。

## 六、设计哲学拆解

把散落在各处的原则归拢一下，这个项目的设计哲学大概是这七条。

### 6.1 颜色即语义

调色板里每一个颜色都有固定含义，没有一个是"好看"就用了：

| 颜色 | 值 | 语义 |
|---|---|---|
| PURPLE | #6630F8 | 当前重点 / 激活 / 品牌 |
| ORANGE / CORAL | #F05F41 | 指标数字、警示、"另一方"、查询点 |
| RED_DEEP | #EC081F | 深红警示块（幻觉、不靠谱） |
| GREEN | #8FF740 | 绿勾（正确） |
| GREY 系 | #A0A0A1 起 | 非重点文字、灰块、网格线 |

规则是"一帧里紫色重点不超过一处大面积"。配色不是审美问题，是信息问题。

### 6.2 光只给当前的主角

主角必带光（`GLOW_PURPLE` 双层紫柔光，或脚下 `HaloRing`，或大字紫硬投影 `6px 6px 0 PURPLE`），配角不发光。

光有三个层次：白 bloom（结构线条常驻）< 紫柔光（主角常亮 + 当前重点）< 白闪（事件，3–6 帧）。全片只用这三种，光的颜色只用紫、橙、红。

还有几条精细的规则：主角光 30 帧周期呼吸 ±15%；重点转移时前一处的光 8 帧内灭掉；离场时光先灭（6 帧）再整体淡出，不要带着满光硬切。

### 6.3 三档尺寸，不容第四档

主角 ≥170px 或大字 ≥96px 且整行宽 ≥300px；配角 60–110px；标签与说明 22–30px。配角 ≤4 个，标签 ≤6 个。

"三档之外不再有第四种尺寸"这条约束的价值在于，它自动淘汰了"这个图标要不要稍微放大一点点"这类无穷的微调。

配套的判据是空场：内容区最大物体高度 <110px 持续 >45 帧是中度缺陷，<80px 持续 >45 帧是重度。

### 6.4 扫光是最贵的一招，全片最多两次

三轮紫光横扫 + 舞台光线 + 幽灵轮廓这套登场型编排，是全片最贵的视觉效果，作者给的预算是 **≤2 处**：核心概念首次登场必有 1 处，第 2 处可选给结尾回扣。

理由是用户反馈。第五片 47 个镜头用了 8 处三轮扫光，用户看成片说"太频繁"。样片 44 个镜头只用了 1 次。

分镜表里为此单列一个"扫光白名单"，不在名单里的镜头一律不用 `LightSweep` / `StageLine` / `GhostText`，`selfcheck.py` 按文件计数，终检按帧核对。

这是一个很值得学的设计：与其在 prompt 里说"少用闪亮效果"（模型听不懂），不如给一个硬配额和一张白名单。

### 6.5 持续动作 + 落位停留

这是全项目最晚成型、也最重要的运动学规则，它对应两种相反的失败：

- **"入场即停"**：元素按节拍进来就停着等下一拍，只有柔光呼吸。第四片量化后：4/6 镜头静止帧 42% 到 72%，最长静止 2.8 秒。
- **"落位即切"**：按"不许静止 >30 帧"修过了头，47 镜头 34 处推近、48 句"持续"，末拍元素刚落位就进入末 8 帧离场。用户原话是"所有动画刚刚落位，马上就切到了下一个镜头，几乎没有停留"。

规则一是**持续**：每个字幕块讲的动词，画面上要有一个持续到下一拍的动作；元素入场后不许完全静止超过 3 秒（90 帧）；但**不为凑指标给静止的物体加漂浮、飘动、呼吸**。

规则二是**停留**：每个镜头末拍元素落位后要有 30 到 45 帧（1 到 1.5 秒）稳定期再离场。稳定期内不新增元素、不运镜、不换 HUD，已在跑的动词动作可以继续。运镜不进末拍。

时间从哪来？用户裁定的：允许成片比纯语音长 5% 到 8% 换停留。停顿只放在段末，不放在每句之后。

作者在文档里把这套规则和它的量化脚本 `motion_check.py` 一起交付，而不只是写在规范里。

### 6.6 衔接要写清两侧

作者踩过一个很典型的坑。如果分镜表只写"硬切"，两边会各自理解成"我不动、你从节拍帧才入场"，结果组界出现 6 到 8 帧空场，一片里 5 处。

所以规定写法是："A 末 8 帧归零淡出 + 轻微下摇；B 首帧起首批元素 SoftIn"。

配套的还有承接优先于清场：一个节拍讲完的短句跟在前一镜头里，用承接位移 16 帧让位，不要为它清场重画。

章界更严格：章首第一个镜头必须承接上一章末镜头的主角或象征物（同组件同参数，可缩小移位），解说同时要承上启下。作者给的反例是"章首从零起头"和"章首只报幕"，两者的区别是：报幕不要，承上启下要。

### 6.7 事实合规是审美问题

这一条最有意思。表面上是 QC 规则，实际上是设计哲学。

作者的判据是：画面上出现的每个数字都必须能追到来源。带来的直接设计后果是：

- 计数动画的中间值也是"上画面的数字"。年份 1995→1998 线性计数会让 1995、1996、1997 清晰可读 4 到 6 帧；毫秒 0→120 会闪出"37 ms""88 ms"。这些都不在事实清单内，所以要么让它不可读，要么不做计数。
- 让年份不可读要够狠：blur 6.3→1.3px 中间年份仍清晰可读；12→2px 时倒数第二个年份仍可辨约 2 帧；最终 12→9px 全程 + 落定帧归 0 才干净。作者把这封成了模板里的 `YearRoll` 组件。
- 示例数据（型号、相似度分、金额）在交付说明里标"示意值"。

这不是在为难作者自己，这是在保护观众。视频没法点击来源，没法核对，观众只能信你。

## 七、局限、质疑与后续看点

### 7.1 三个我要先说清的现实限制

**第一，它不是一个"输入主题就出片"的产品。** 它需要人（或者说需要一个 agent 主会话）在四个点上做决策：时长与语言、解说词定稿、配音引擎、前 30 秒样片。四个确认点一个都省不掉，作者也没打算省。

从"给你一个输入就能拿到成片"的角度看，这离产品还很远。但从"让 agent 独立完成一条片子"的角度看，这已经很远了。

**第二，成本不低。** 样片档 8 个构建组并行 40 分钟，加两轮 QC 60 到 90 分钟，整条流程约 2 小时，磁盘 2GB 起。而且这还是在你自己已经有 Remotion 熟练度的前提下。

**第三,授权是个坎。** PolyForm Noncommercial 1.0.0，非商用免费，商用要事先获得作者授权。做科普、教程、个人项目没问题，想用在商业产品上得先谈。

### 7.2 我认为最值得追问的两个问题

**第一个问题：这套方法在没有作者在场的机器上能复现吗？**

整个仓库的语气是"一个人做了一条又一条片，每次踩坑就写回 lessons.md"。协议的完备性高度依赖这些踩坑记录，而它们是 2026-09-07 到 09-10 之间四天里攒出来的。

这种"经验沉淀型"文档的优点是每一条都有真实返工支撑，分量足；风险是它只在作者那台机器、作者那套 Claude Code 配置、作者那个 pane 上限的环境里被验证过。README 说"Linux 应该能行，Windows 未测试"，树莓派跑通了，这已经算诚实的交代，但毕竟不是"任何人任何机器都能跑"。

**第二个问题：这条流水线的瓶颈到底是什么？**

作者把所有注意力放在了"让画面变好"上——主体尺寸、光、高光时刻、扫光配额、持续动作、落位停留，全是视觉。但他自己在 `lessons.md` 里承认过一件更有意思的事：

> 风格传递（2026-09-08 复盘）：skill 写了禁令没写审美驱动……但「画多大、谁发光、高光时刻怎么编排」只在做样片的人脑子里。

也就是说，他花了大量篇幅治"AI 画面做得烂"这个症状，动了两年。但从 `lessons.md` 的整体结构看，**真正稀缺的不是审美规则，是"怎么把一个人的审美判断拆成可传递、可检查、可迭代的形式"这套方法论**。这个项目目前是在这个方向上的一次成功尝试，而不是一套已经成熟的通用方法。

一个旁证是他自己的复盘结论："差距不在『动得多不多』，别往加动效的方向修。"这句话的价值在于它是一个否定性判断——排除了一个方向，而不是给出了一个方向。真正难的是找到该往哪修。

### 7.3 后续可以期待什么

- **竖屏。** README 明确说不支持 9:16，模板和所有安全区规则都假设 1280×720 横屏。短视频平台基本是竖屏的，这是最明显的一块空白。
- **更多语言。** 现在只支持中英，各有一套语速模型、字幕预算和默认音色。`lang` 字段的架构留了扩展口子。
- **更高质量的 TTS。** 现在的路径是"自带 TTS"——用户自己生成成品 wav，手填时间轴。作者明确说了默认的 edge-tts 和 kokoro"够用但不是最好"。这意味着整条流水线对语音克隆、强制对齐这类技术是开放的。
- **反例库的扩充。** `examples/contrast/` 现在只有 6 组，而且正例全部来自同一部片（样片）。多几部不同题材的正例，对传递审美标准会有帮助。

### 7.4 那个最值得学的设计决定

如果只能从这个项目带走一样东西，我选这个：

**把"品味"变成"参照物 + 判据 + 计数器"三件套。**

- 参照物：`examples/contrast/contrast_sheet.jpg` 里的 6 组正反例帧，agent 开工前必须看。
- 判据：`composition-and-light.md` 里的尺寸三档、光的归属、空场阈值、扫光配额。
- 计数器：`selfcheck.py` 数闪烁白名单，`frame_metrics.py` 量主体高度和柔光，`motion_check.py` 测静止时长。

单靠前两样，agent 会理解但会走样。加上第三样，偏差会被立刻发现。

作者在第四片结尾给了一个很实在的观察：当一组 agent 反馈"中间年份模糊不可读"时，实际出图清晰可读。他没有把这当成 agent 不可靠，而是把"从源码静态抽取所有会上画面的字面量，和事实清单对账"补成了一个检查步骤。

**这就是一个能持续改进的系统该有的样子：每次失败都变成一个新的检查项，而不是一次性的抱怨。**

## 八、一句话总结

anything2explainer 把"让 AI 做一条科普讲解视频"这件事，从一个提示词问题变成了一个工程问题。

它不生成像素，它生成确定性代码；它不靠模型领会审美，它靠参照物、判据和计数器传递审美；它不指望 agent 一次做对，它把每次返工写进 lessons.md 变成下一片的检查项。

对一个想做技术内容的人来说，这个仓库最实用的可能不是那 9 个阶段，而是那 11 份 `reference/` 文档里攒下来的东西：主体该画多大，光该打给谁，高光时刻怎么排，扫光最多用几次，停顿该放在哪，为什么"入场即停"和"落位即切"都是缺陷，以及怎么用三个几秒钟跑完的脚本，去检查 agent 到底有没有做到。
