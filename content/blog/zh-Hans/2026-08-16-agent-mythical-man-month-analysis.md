# 《人月神话》的 2026 重读：为什么加十个 subagent 一小时做完，和招十个人一个月做完是同一个诅咒

## 文章背景与项目简介

1975 年，Fred Brooks 写完《人月神话》（The Mythical Man-Month）——他管过 IBM OS/360，那是 1960 年代人类做过的最大一次软件工程。项目结束后他没写技术总结，而是写了一本关于"为什么大项目总是延期、为什么加人只会更慢、为什么概念完整性是设计的最高目标"的书，成了整个软件行业的地基。

五十年后，一位署名 meari 的作者在 GitHub 上发布了 **agent-mythical-man-month-2026**（中文名《agent 时代的人月神话》）——以 1995 年二十周年纪念版为底本，**把 Brooks 的每一章在 2026 年的 AI Agent 语境里重写了一遍**。这本书/仓库要回答一个问题：

> 写代码这件事从"人在键盘上敲字"变成"人和一个语言模型对话"，介质发生了根本变化。Brooks 描述的那些老病，在这个新介质上还在不在？

作者的答案是——**全在，而且几乎每一条都在人机协作的日常里以新形态重现**：

- 加十个 subagent 一小时做完，跟 1975 年"招十个人一个月做完"是同一个诅咒。
- 开三个平行会话试三种思路，跟 1975 年"多派几组人试试不同方案"是同一个心理反应。
- 让 agent 自主完成一整个项目，跟 1975 年"外包给一个独立小组"面对的是同一个概念完整性问题。

更有意思的是这本书**本身就是它自己论证的一次运行**：一位持有目的的作者加多位 agent 协作完成——Fable 5 写了每一章的初稿，Opus 4.7 陪着修完十八章，Sonnet 5 完成了英文版和日文版翻译。项目获得 129 颗星，正文以 CC BY-NC-SA 4.0 授权，共三语版本（中文/英文/日文）、每语 18 章加一篇序、外加三个 EPUB 合集。

**这篇文章的定位**：先用大白话讲清楚这个项目说了什么，再把它拆成可消化的教程与观点清单，最后给出不留情面的综合评价。

## 核心思想总览：老命题的新形态

序章把 Brooks 原书的骨架拆成**三个骨节**，然后论证这三者在 agent 时代原样成立：

1. **软件的困难来自它本身，不来自工具。** 工具一茬一茬换代——汇编器、结构化编程、面向对象、敏捷、容器化——每一茬都有人喊"银弹来了"。Brooks 1986 年的《没有银弹》给出通用反驳：软件的根本困难在概念构造、规格说明、判据裁决这几层，工具能消灭偶然复杂度，消灭不了本质复杂度。2026 年这句话依然成立：LLM 是很强的工具，但它消化不了上下文里没有的东西。
2. **管理软件的困难，主要是管理沟通与判断。** 项目一大，最贵的不是编码和测试，是让所有人对齐同一个概念。Brooks 花了大半本书讨论沟通的组织形式：外科手术队伍、体系结构师与实现的分离、工作手册、里程碑与自欺。2026 年变的是判断在哪里做出（现在有一部分做出者不是人）、如何被记录（现在有一部分记录物是提示词）、如何被沟通（现在有一部分沟通是 token）——**"判断需要被组织"这件事没变**。
3. **文档不是记录，是决策的载体。** 写文档的行为迫使上百次细小决定显形，这些细小决定就是项目的骨头。不写文档，决定只在个别人头脑里、随时会消失；写文档，就是在给项目铸骨。

合起来一句话：**软件工程的核心是判断的组织。技术在变，判断的组织学问不变。** 忽视这一点的团队，会用最先进的 agent 系统重演最古老的失败模式。

### 三代读者

- **第一代（1975–1995）管人**：几十人的团队怎么组织、进度怎么估算、如何避免加人陷阱。
- **第二代（1995–2025）管代码**：敏捷时代，拿走的是概念完整性、模块化、迭代开发、文档等价于设计。
- **第三代（2024 之后）管 agent**：你不是在管人，也不完全是在写代码，你在**编排一群非人执行者，同时保持整体的一致性**。管理对象是全新的物种，管理原理却惊人地熟悉——因为 Brooks 讨论的从来不是"人"这个物种的特殊性，而是"**多主体协作完成大型概念构造物**"这件事的一般规律。

这本书是写给第三代读者的。

## 核心命题一：harness 是状态机，LLM 是被调用的函数

项目最反直觉的一个论断：**agent 系统的主角不是 LLM，是 harness（托管 agent 的脚手架）。**

"脚手架"这个比喻容易误导——它让你以为 LLM 是聪明的大脑，harness 只是给它配了手脚。项目纠正了这个方向：

> 确切地说：harness 是一个状态机，它负责发起 LLM API 请求调用，提供工具，管理上下文。在这个状态机里，LLM 是那个被调用来给"下一步该做什么"出主意的函数。它是资源，被状态机的每一轮消费一次。真正让 agent 变成 agent 的是那个循环，是状态机每一轮的运转。没有那个循环，LLM 只是一次函数调用；有那个循环，才有 agent。

状态机是计算机科学最古老的概念之一：任何时刻处在某个明确状态、根据输入转移到下一状态并产生动作。红绿灯、ATM 机、洗衣机背后都是状态机。harness 的状态大致是：等用户输入、决定下一步、调用工具等返回、调用 LLM 等回复、任务完成。

这带来两条反复使用的推论：

1. **agent 的行为质量是 harness 设计的产物，不只是 LLM 能力的产物。** 同一个模型放在不同 harness 里表现天差地别——书里绝大多数关于 agent 系统的判定，判的是 harness，不是模型。
2. **agent 系统的失败模式很多不在 LLM 那一层，在状态机那一层。** LLM 说了对的话，但 harness 没把这句话正确路由；LLM 提出正确的怀疑，但 harness 没有"接受怀疑"这个状态。**你换更强的 LLM 也解决不了这些问题，因为它们不在 LLM 那一层。**

## 核心命题二：LLM 没有记忆，只有上下文——上下文是唯一变量

LLM 每次被调用时，看到的只有这次调用被塞进去的那段文字。它没有你的历史、没有前几轮对话的记忆、没有任何跨调用的持久状态。

"它记得我们前面说过什么"的体验从哪里来？从 harness 里来。**harness 在每次调用前，把对话历史打包塞进上下文，一起交给 LLM**——用户感受到"它有记忆"，实际是"harness 每次都替它带了一份完整的往事简报"。

由此得到全书最锋利的定位：

> 所有关于 agent 的技术工作，最终都可以归结为一个问题：这一次调用，该往上下文里放什么？

上下文的质量**完全决定**输出质量。Brooks 的每一条原理在 2026 年的操作含义都是"上下文该怎么组织"：

| Brooks 的原理 | 2026 年的操作含义 |
|---|---|
| 概念完整性 | 上下文里的概念不能来自多个互不相识的头脑 |
| 外科手术队伍 | 支持角色帮你构造上下文，主刀持有目的 |
| 文档假设 | 文档是上下文的源码，代码是从上下文编译出的产物 |
| 里程碑设计 | 停止条件必须在上下文里显式表达 |
| 没有银弹 | 模型能力再强也解不掉"上下文里没有的东西"这个约束 |

## 核心命题三：停机问题——agent 时代的终止判定

这是全书最有理论野心的一章，也是我看来最值得记住的贡献。

harness 有一个"任务完成"的状态。传统状态机里，这个状态由外部信号触发（ATM 的"结束"按钮、洗衣机的定时器）。但 harness 想让 **LLM 自己决定什么时候停**——"任务完成了吗"被作为一次调用交给 LLM 回答。这个安排看起来自然，实际上撞上了计算机科学最老的一堵墙：**停机问题**。

图灵 1936 年证明：没有程序能独立、可靠地判断任意程序（包括它自己）会不会停下。这是自我指涉带来的**结构性障碍**，跟机器多强、算法多聪明无关——给它加十倍算力、更好的模型、更长的思考时间都没用，因为矛盾是逻辑上的，不是资源上的。

把这条定理带到 agent 上：LLM 是软件，harness 是软件，两者组合的 agent 系统就是一段程序。而且"该不该停"和"会不会停"在 agent 系统里被实现抹掉了界限——harness 把"任务完成了吗"的回答直接接成循环的终止条件。**agent 停机问题是图灵停机问题的一个实例，说类比都把关系说远了。**

有一个可以让步的地方：如果任务的完成条件已经形式化到能被机器验证（跑通这几个测试就算完、这个方程解出来就算完），那这个特定实例的停机是可判定的——SWE-bench 这类基准能跑，就是落在可判定的角落里。

但一旦完成条件不能被完全形式化（做一件让用户满意的事、写一份能通过评审的报告），LLM 就要独立决定停不停。据此序章下了那个大胆的预言：

> 在完成条件不能被完全形式化的任务上，没有 LLM 调用程序能独立决定自己该在什么时候停下。

两条直接推论：

1. **任何号称"agent 能自主完成任务"的系统，都在赌 LLM 能可靠判断停止条件。** 在判据明确的实例上赢率不错；在判据处境化的实例上赢率极低——因为判断"该停了"要回到形式化不了的处境信息里，正好落在停机问题的不可判定区。这与"没有银弹"是同一件事的两种说法：本质困难不能被 LLM 消化，而且是原则上之外，不是"再看一眼就能消化"的那种之外。
2. **给 agent 系统设计外部止损，是不能省的一步。** 既然 LLM 不能自己知道该停，就必须由 harness 状态机从外部强制：最多几轮、最多多少 token、同一错误几次后停、超预算停。这些约束要写进状态机的转移条件，不能靠 LLM 自觉。行业里叫"资源上限"或"预算"，其深层理由就是这条预言。

> 停机问题这个词五十年前是理论计算机科学的一个专业术语。2026 年它是每个 agent 用户每天都在踩的坑。

## 核心命题四：Brooks 定律的双重形态

"人月神话"指那个迷思：人和月可以互换——十个人一个月等于一个人十个月。Brooks 的原话是"无论安排多少位女性，婴儿仍需要九个月才能出生"。2026 年的翻译：

> 理解一个问题仍需要一个持有全景的主体投入连续时间，无论开多少个 subagent 平行工作。

项目把 Brooks 定律在 agent 时代拆成**双重形态**：

- **温和版**：向一个落后进度的 agent 项目增加平行会话，会让它更晚。
- **严酷版**：向一个落后进度的 agent 项目增加**从空白状态启动的自主运行**，它甚至不会"更晚"——它**原地不动**：账单在涨，没有积累。

严酷版比温和版更值得警惕，因为它对应的是 2026 年最流行的错误用法：任务完不成，就"再开几个 agent 并行重试"。每个新 agent 从空白状态出发，重新理解一遍问题，产生新的一批试探性改动——没有全景的持有者，所有并行都在原地打转。

## 核心命题五：Vyssotsky 命题——未定义的地方即失败

第 13 章引入 Vyssotsky 的命题：

> 许许多多的失败完全源于那些产品未精确定义的地方。

人团队里，需求文档的空白会被有经验的成员用"本地约定"补上。但 agent 时代这个空白更危险：

> 你给 agent 一份需求文档。agent 读完，开始工作。文档里没有的部分（就是你以为不用说的 E），agent 会用它对你意图的猜测填补。它的猜测可能是好的，也可能是坏的。

而且危险是双重的：agent 用**训练语料里的平均值**来填补空白（而不是你的本地约定）；**agent 不会问**——它猜了就直接继续，猜错也不留物理痕迹，事后无从排查。人可能犹豫、可能反问，agent 不会。

## 核心命题六：目的命题

第 15 章提出"目的"（Purpose）是链条最上游的判据："为什么我要 X 而不是 Y？"它**不能被完全表达**——凡是不能被表达的东西，就不能被正确实现。这条命题的实操含义：项目里必须有一个持有目的的主体（哪怕是一个人），目的不能委托给 agent，因为表达不出来的东西 agent 无从实现。

## 没有银弹：四个本质困难在 2026 年一条没被消灭

第 16 章是全书的理论心脏。Brooks 1986 年论证软件有四个**本质困难**（任何技术都无法消除）：

1. **复杂度**（Complexity）——软件描述的是抽象概念系统，复杂度随规模非线性增长；
2. **一致性**（Conformity）——软件必须顺应无法推导的人为约定；
3. **可变性**（Changeability）——软件被要求永远在变（因为它容易变）；
4. **不可见性**（Invisibility）——软件没有几何形态，结构多维、画不出来。

2026 年的判断是：**四条一条没被消灭，每一条都在当前的 agent 生态里按了指纹。**

- **复杂度**：agent 产出的代码多十倍，但每行代码附带的复杂度也多十倍；
- **一致性**：agent 擅长已知约定，对本地/未见过的约定灾难性失败；
- **可变性**：更快的反馈回路反而提高了需求变更的频率；
- **不可见性**：agent 的内部推理不可见——你看到的是输出，不是实际的计算。

结论：**LLM/agent 是软件史上对"偶然复杂度"最有力的一次清除，但它们没有触及"本质困难"——所以它们不是银弹。** 项目还补了一句锋利的话：LLM 是 1986 年那段专家系统展望的完成态，它最强的贡献是把最优秀从业者的经验分发给所有人——而"这条预言和'没有银弹'是同一件事的两种说法：前者说判据装不进软件，后者说困难不住在表达层。一个从可计算性说，一个从工程经济学说，指向同一堵墙。"

## 设计哲学：外科手术队伍——一人主刀 + agent 支持团队

Harlan Mills 1971 年提出"外科手术队伍"：**一位主程序员（主刀）持有概念完整性**，周围围着一圈支持角色（副驾驶、编辑、测试员、工具匠等）。Brooks 认为这是小团队保持概念完整性的最优解，但五十年来一直没有大规模落地——因为找不到"愿意花大成本围着一个主刀转"的组织。

2026 年的答案是：**支持团队不再需要人这种昂贵资源来担任。**

> 这就是当代最小可用软件编制：一个人做主刀，一群 agent 担任支持团队。除主刀外，其他角色几乎都可以由 agent 出任，且大多比 1975 年任何真人担任这些角色时都称职。

## 设计哲学：三个 10x 的乘法效应

第 3 章提出 agent 时代的三重十倍差：

1. **模型档位** 10x（最强模型 vs 最弱模型）；
2. **harness 质量** 10x（同一个模型在不同 harness 里）；
3. **架构师能力** 10x（人的能力差异）。

三者是**乘性**叠加，不是加性：10 × 10 × 10 = 1000x。一位优秀架构师 + 强模型 + 优秀 harness，对一位平庸架构师 + 弱模型 + 粗糙 harness，差距可达千倍。这解释了为什么"换最强模型就能变强"是幻觉——模型只是三个乘数之一。

## 设计哲学：审计权 vs 修正权

这是全书对"人在回路"最尖锐的澄清：

- **审计权**（Audit rights）：能看到输出、能读日志；
- **修正权**（Correction rights）：能在过程中修改工件而不必重启。

> Mills 的外科手术队伍隐含一个前提：主刀是有刀的。手术台上发现出血点，主刀直接处理，不必缝合、火化、换一个病人从头再来。这个刀就是修正权。

很多号称"人在回路"的产品只给审计权，不给修正权——你像只能看片子的医生，写完报告转给下一个班次；下一个班次接手病人时看不到你的诊断，从头再看一遍片子。**能诊断、不能治疗，不是人在回路，是人在旁听。**

## 设计哲学：文档即源码 + 五份关键文档

第 10 章是全书方法论枢纽，口号只有一句：

> **文档是源码，代码是编译产物。**

文档的真正价值不是让后来者查阅（那是副产品），是**让当下的作者把自己的想法逼出来**——书写活动需要上百次细小决定，正是这些决定让人从迷惑现象中得到清晰策略。2026 年，文档→代码的翻译被 agent 大幅自动化，"文档即源码"第一次成为可执行的工程方法：文档含糊，agent 的解释就错误地填空；文档清晰，编译就成功。

五份关键文档：

1. **需求规格说明书**——条文级、可寻址（agent 可以引用"按 4-3-2 条执行"）；
2. **决策日志**——每个重大决策附理由与勘误历史；
3. **当前热清单（NOW.md）**——正在做什么、不做什么，"做完即删"；
4. **协作规范**——项目规则（先讨论再编码；测试断言不是金标准）；
5. **预算与资源**——API 成本、token 消耗。

### 可落地的工程实践

项目不只是理论，每章都带着可直接执行的实践：

1. **入职材料模式（第 7 章）**：每个新 agent 会话 = 一次新员工入职。项目工作台 = 四份文档：条文级需求、决策日志、NOW.md 热清单、协作规则（AGENTS.md / CLAUDE.md）。
2. **侦察兵/试点（第 11 章）**：正式开发前，先拿一个小的代表性任务当"侦察兵"跑一遍。成本是几分到几美元，跳过它的代价是几天。把教训写下来，然后重新开始。
3. **执行前的独立评审（第 13 章）**：写完规格 → 开新会话 → 让 agent 找歧义 → 修复 → 重复 → 才开始实现。这是 2026 年版的"独立测试组评审规格"。
4. **会话重置规则（第 11 章）**：长会话会积累熵（矛盾的假设、过期的决定）。会话变混乱时 → 把结论冻结进文档 → 开新会话 → 重新加载文档。经验法则：约 50+ 轮就该考虑重置。
5. **先讨论再编码（第 7 章）**：agent 会用训练平均值填补模糊需求。纪律是：歧义点浮出水面并被验证之前，不开始编码——把"假设 → 验证"提前到执行之前。

## 归纳总结：这个项目的核心观点

1. **Brooks 的老病在 agent 时代全在**，且以新形态重现——加 subagent、开平行会话、让 agent 自主完成项目，分别对应加人、多方案并行、外包这三种 1975 年的经典陷阱。
2. **判 harness，不判模型**——agent 的行为质量主要是 harness 设计的产物；换更强的模型解决不了状态机层面的失败。
3. **上下文是唯一变量**——agent 工程的一切归结为"这次调用往上下文里放什么"；Brooks 的每条原理都是上下文组织原理。
4. **停机问题不是理论**——"agent 能不能自主停下"就是停机问题的一个实例；形式化不完全的任务上，自主停机不可判定，外部止损不可省略。
5. **没有银弹**——四个本质困难（复杂度、一致性、可变性、不可见性）一条没被消灭；LLM 是史上最强的偶然复杂度清除器，但不是银弹。
6. **最小可用软件编制 = 一人主刀 + agent 支持团队**——概念完整性必须由一个人持有，支持角色可以全部交给 agent。
7. **审计权不等于修正权**——只有审计权的"人在回路"是旁听，不是协作。
8. **文档是源码，代码是编译产物**——agent 时代这句话第一次真正可执行。

## 我的几个独立观点

**1. 这个项目最值钱的不是结论，是"把经典逐章重跑"这个方法本身。** 它示范了一种可复用的知识生产方式：拿一本经过时间检验的书，一章一章问"这条原理在新介质上还成立吗？"，而不是泛泛而谈"AI 改变了软件工程"。这种精度让它避免了大多数 AI 评论文章的空洞。

**2. "上下文是唯一变量"是对"模型越大越好"迷信的精确解药。** 当你意识到每次调用塞进去的东西决定了输出质量，你立刻明白为什么同样的模型在不同人手里表现天差地别——差距在上下文工程，不在模型。这也是为什么这个项目把文档的地位抬到如此之高。

**3. 停机问题预言的表述非常克制，这反而增加了它的分量。** 它没有说"agent 永远不能自主停止"，而是限定在"完成条件不能完全形式化的任务"上，并明确承认严格证明目前做不到、更强模型会让反例变多。这种诚实的边界感，在充斥着确定性宣言的 AI 内容里是一股清流。

**4. "审计权 vs 修正权"是我见过对人在回路最锋利的一刀。** 大量工具宣称"human-in-the-loop"，实际只是让人在事后看日志——能诊断，不能治疗。这个区分值得成为每一个 agent 工具的产品审查标准：用户能不能在运行中直接改，还是只能看完报告转班？

**5. Opus 4.8 被排除在致谢之外是全书最妙的元叙事。** 一个 agent 因为识别不出 harness 注入的 system-reminder、把自家提示当作 prompt injection 报警，而它写进书里的这一章恰好是"agent 系统的失败模式很多不在 LLM 那一层，在状态机那一层"——书自己用自己的论证证明了自己。

**6. 严酷版 Brooks 定律应该贴在每个团队的墙上。** "再开几个 agent 并行重试"是最诱人的错误操作：从空白状态启动的自主运行不会让项目更晚——它会原地不动，账单在涨，没有积累。预算的深层理由不是什么资源纪律，是停机问题。

## 综合评价：价值与局限

### 价值

- **理论精度罕见**：把停机问题、状态机、上下文工程这些概念精确地连起来，而不是堆术语。
- **每章都可落地**：入职材料、侦察兵、独立评审、会话重置、先讨论再编码——不是口号，是可直接照做的流程。
- **三语完整**：中文原版 + 英文/日文全译，且翻译本身也是 agent 协作的产物，具有示范意义。
- **元叙事自洽**：这本书的创作过程就是它论证的一次运行，作者把"一位持有目的的作者加多位 agent"写进了正文。

### 局限

- **三语而非五语**：项目本身只有中/英/日三语，面向全球读者的覆盖有限（本博客按仓库规范补全为 5 语）。
- **无代码、无实证数据**：纯文本理论项目，"1000x"乘性效应是推理而非测量，9x 矩阵等沿用 Brooks 1975 数据，未在 agent 时代重新标定。
- **写作对象是第三代读者**：假设读者已熟悉 agent 系统（哪怕只是偶尔用 Claude Code/Cursor/Codex）；完全没接触过 agent 的读者需要先补基础。
- **部分断言依赖特定模型版本**：致谢里的 Fable 5 / Opus 4.7 / Sonnet 5 是写作时的模型生态，模型迭代很快，这部分内容会随时代老化（但核心论证不受影响）。

## 适用人群

- **重度 agent 用户**（Claude Code / Cursor / Codex）：你会在这本书里看到自己踩过的每一个坑被精确命名。
- **团队管理者**：为什么加 subagent 不加速、为什么需要一人持有全景、为什么文档必须条文级——这些答案比任何"AI 管理心得"都扎实。
- **LLM/agent 工具开发者**：harness 状态机、审计权与修正权、外部止损——每条都是产品设计原则。
- **软件工程师**：从"管代码"到"管 agent"的过渡指南，概念完整性、文档即源码这些老原则有了新用法。

**不太适合**：完全没接触过 agent 的纯新手（建议先上手用一两次 agent 工具再读），以及想找"10 条 AI 效率技巧"的速成读者（这本书给的是原理，不是技巧）。

## 结语

1975 年 Brooks 写下的不是一本关于那个时代的书，而是一本关于"多主体协作完成大型概念构造物"的一般规律的书。五十年后，管理对象从人换成了 agent，但判断需要被组织这件事没有变——变的是判断在哪里做出、如何被记录、如何被沟通。

《agent 时代的人月神话》把这套规律逐章重跑了一遍，证明了两件事：**老病全在**，以及**这本书本身就是它自己论证的一次运行**。它最锋利的三章——人月神话、提纲挈领、没有银弹——分别对应资源分配、文档地位、银弹边界，合起来就是半个世纪软件工程的地基。

> 停机问题这个词五十年前是理论计算机科学的一个专业术语。2026 年它是每个 agent 用户每天都在踩的坑。

这句话，就是这本书的缩影。
