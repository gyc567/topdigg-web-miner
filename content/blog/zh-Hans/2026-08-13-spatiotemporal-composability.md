# 时空可组合性：重新定义动态软件架构的编程范式

## 项目与论文介绍

**paper** 是 cordiverse 组织发布的一项学术预印本论文（2026年8月草稿），提出了一种名为**动态组合（Dynamic Composition）**的编程范式，旨在解决现代软件架构中组件之间动态交互和依赖管理的根本性问题。

### 核心问题：为什么需要动态组合？

传统的软件架构强调模块化和组合性，但在运行时动态加载、替换和组合组件方面存在显著不足。现代应用场景——从微服务架构到前端框架的热模块替换（HMR），再到插件系统——都对运行时组合提出了更高要求。

论文指出，当前的编程范式在处理以下场景时显得力不从心：

- **热模块替换**：在不重启应用的情况下动态更新代码模块
- **插件系统**：运行时加载和卸载功能扩展
- **响应式依赖管理**：当依赖项发生变化时自动更新依赖方
- **事务性回滚**：在组件失败时完全撤销其所有副作用

## 核心设计哲学

### 两个正交维度

论文识别出组合性的两个根本维度，它们相互独立却又共同决定了系统的表达能力：

### 1. Temporal Composability（时间可组合性）

**时间可组合性**指的是移除组件时**完全撤销其副作用**的能力。传统的资源管理只关注获取和释放（acquire/release），但忽略了在组件生命周期中产生的更深层副作用。

举例来说，当一个组件执行了以下操作：
- 修改了全局状态
- 创建了后台任务
- 注册了事件处理器
- 建立了网络连接

时间可组合性要求：移除该组件时，这些副作用必须被**完全、可预测地撤销**，仿佛该组件从未运行过。

### 2. Spatial Composability（空间可组合性）

**空间可组合性**指的是**声明和响应式管理组件间依赖关系**的能力。在一个组件系统中，组件不是孤立的——它们依赖于其他组件提供的数据和服务。

空间可组合性关注的是：
- 组件如何**声明**其依赖
- 当依赖项**变化**时，组件如何**响应**
- 依赖关系的变化如何**传播**到依赖它们的组件

### 为什么需要两个维度？

论文的核心观点是：**时间和空间的可组合性是正交的，不能相互替代**。

- 只有时间可组合性：组件可以被安全移除，但无法管理依赖关系
- 只有空间可组合性：依赖关系被声明和管理，但没有撤销机制

两者结合才能实现真正的动态组合系统。

## 核心概念详解

### Revertible Effects（可撤销效应）

#### 概念起源

传统的 **Effect** 描述的是程序在执行过程中对外部世界产生的**可见影响**——如文件操作、网络请求、状态修改等。Effect 系统（如 Haskell 的 mtl、Effect-TS）允许程序员以类型安全的方式追踪和管理这些副作用。

**Revertible Effects** 在此基础上增加了一个关键能力：**跟踪逆变换（inverse transformation）**。

#### 核心思想

每个 Effect 不仅描述了"做什么"，还附带了一个**撤销操作（reverter）**的上下文。当需要移除组件时，系统可以执行这个撤销操作来恢复状态。

```typescript
// 概念性示例
interface RevertibleEffect<State, Effect> {
  perform: (state: State) => Effect;
  revert: (state: State, effect: Effect) => State;
}
```

#### 应用场景

1. **数据库事务**：自动回滚未提交的更改
2. **UI 状态管理**：撤销用户操作
3. **资源获取追踪**：精确释放所有已分配资源
4. **日志审计**：记录并可撤销的操作历史

### Reactive Coeffects（响应式协同效应）

#### 概念起源

**Coeffect** 概念来自函数式编程，描述的是函数**需要什么**才能执行——即函数的**上下文依赖**。例如，一个读取配置的函数"需要"配置数据；一个记录日志的函数"需要"日志记录器。

传统的 Coeffic 系统关注的是**静态依赖声明**，而 **Reactive Coeffects** 将其扩展为**动态、响应式的依赖管理**。

#### 核心思想

当组件依赖的上下文发生变化时，系统**主动通知**该组件，而不是让组件轮询或手动检查。这种模式借鉴了响应式编程（Reactive Programming）的思想，但应用于依赖注入的领域。

```typescript
// 概念性示例
interface ReactiveCoeffect<T> {
  // 声明依赖
  dependsOn: () => T[];
  // 当依赖变化时的回调
  onChange: (newValue: T, oldValue: T) => void;
}
```

#### 与传统依赖注入的区别

| 特性 | 传统依赖注入 | Reactive Coeffects |
|------|-------------|-------------------|
| 依赖解析时机 | 构造时 | 运行时动态 |
| 变化通知 | 无 | 有（推模式） |
| 依赖追踪 | 显式 | 隐式声明 |
| 懒加载支持 | 有限 | 原生支持 |

### Context Types（上下文类型）

#### 统一 effect 和 coeffect

论文提出了一个统一的概念框架，将 **Effect**（组件对外部的影响）和 **Coeffect**（组件对外部的依赖）统一为**上下文类型（Context Types）**。

在传统的 effect/coeffect 系统中，这两个概念是分开处理的。Context Types 提供了一个统一的类型系统，可以在其中同时表达：

- **产出效果（produced effects）**：组件产生的副作用
- **消费协同（consumed coeffects）**：组件需要的依赖
- **效果追踪（effect tracking）**：追踪已执行的效果以便回滚
- **协同解析（coeffect resolution）**：动态解析依赖并传播变化

#### 形式化定义

```typescript
// Context Type 的概念性形式
interface ContextType<S, E, C> {
  // 状态类型
  state: S;
  // Effect 类型（可撤销的效果）
  effects: RevertibleEffect[];
  // Coeffect 类型（响应式依赖）
  coeffects: ReactiveCoeffect[];
}
```

## Cordis 元框架架构

### 框架概述

**Cordis**（拉丁语"心脏"）是实现论文思想的**概念性框架**，展示了如何在实践中应用动态组合的理论。

### 核心组件

#### 1. 核心库（@cordis/core）

负责最基础的机制：
- **Effect 追踪**：跟踪所有可撤销的效果
- **Coeffect 解析**：管理依赖解析和变化传播
- **Context 管理**：维护运行时的上下文状态

#### 2. 组件系统（@cordis/component）

提供了动态组合的**组合机制**：

```typescript
// 组件定义示例（概念性）
const myComponent = component({
  name: 'my-component',
  // 声明依赖的 coeffects
  coeffects: [databaseService, configService],
  // 提供或触发 effects
  effects: [loggingEffect],
  // 组件逻辑
  setup(ctx) {
    // 使用依赖
    const db = ctx.coeffects.databaseService;
    // 执行操作
    ctx.effects.log('Hello');
  },
  // 可选的拆卸逻辑
  teardown(ctx) {
    // 清理工作，effects 会被自动撤销
  }
});
```

#### 3. 声明式加载器（@cordis/loader）

用于**声明式地加载和配置组件**：

- 声明式依赖：描述组件需要什么，而不是手动注入
- 配置协调：管理组件的配置和初始化顺序
- 生命周期管理：处理组件的创建、更新和销毁

#### 4. 热模块替换（HMR）能力

Cordis 框架特别强调了**热模块替换**能力，这是动态组合的实际应用：

- **增量更新**：只更新变化的组件，不影响其他组件
- **状态保持**：在更新过程中保持必要状态
- **自动清理**：移除旧组件的 effects，应用新组件的 effects

## 动态组合演算

### Calculus of Dynamic Composition

论文提出了**动态组合演算（Calculus of Dynamic Composition, CDC）**，这是对动态组合理论的**元理论（meta-theory）**描述，提供了形式化的数学基础。

### 演算的核心要素

#### 1. 组件（Components）

组件是动态组合的基本单位，每个组件包含：
- **接口（Interface）**：描述组件提供的服务和依赖
- **实现（Implementation）**：组件的具体逻辑
- **效果追踪（Effect Traces）**：记录组件执行过程中的效果

#### 2. 组合器（Compositors）

组合器定义了组件如何组合：
- **串行组合**：一个组件的输出作为另一个的输入
- **并行组合**：多个组件独立运行，共享状态
- **覆盖组合**：新组件替换旧组件

#### 3. 撤销语义（Reversion Semantics）

定义了在移除组件时：
- 哪些效果需要被撤销
- 撤销的顺序是什么
- 如何处理部分撤销失败的情况

### 形式化保证

动态组合演算提供了以下形式化保证：

1. **可组合性定理**：组合后的组件仍然保持时间/空间可组合性
2. **撤销完整性**：移除组件时，所有效果都被完全撤销
3. **依赖传递性**：依赖关系的变化正确传播到所有依赖方

## 关键观点总结与结论

### 核心贡献

1. **识别了两个正交维度**：时间和空间可组合性共同构成了动态组合的基础

2. **提升了 effect 和 coeffect 概念**：
   - Revertible Effects 将 effect 从"追踪"提升到"可撤销追踪"
   - Reactive Coeffects 将 coeffect 从"静态声明"提升到"动态响应"

3. **统一的形式化框架**：Context Types 统一了 effect 和 coeffect 上下文

4. **实际框架实现**：Cordis 展示了理论的实际可行性

### 重要观点

> "动态组合不是关于如何编写组件，而是关于组件如何在运行时相互作用、依赖和撤销。"

### 局限性

论文也诚实指出了其局限性：

- 目前仅是**概念验证**，性能开销尚未优化
- **形式化证明**仍在完善中
- 对于**大规模系统**的可扩展性有待验证
- **实际应用案例**还不够丰富

## 应用场景和实践意义

### 适用场景

1. **前端框架**
   - 热模块替换（HMR）
   - 响应式状态管理（如 Redux 的时间旅行调试）
   - 插件系统

2. **后端服务**
   - 微服务架构中的动态服务编排
   - 数据库事务的嵌套管理
   - 资源获取和清理的精确追踪

3. **嵌入式系统**
   - 组件的确定性加载和卸载
   - 资源受限环境下的精确资源管理

4. **IDE 和开发工具**
   - 实时编程环境
   - 增量编译和更新

### 实践意义

对于软件开发者的实际价值：

| 方面 | 当前状态 | 引入动态组合后 |
|------|---------|---------------|
| 组件卸载 | 手动清理资源 | 自动完全撤销 |
| 依赖变化 | 手动检查更新 | 自动响应通知 |
| 热更新 | 有限支持 | 原生支持 |
| 状态回滚 | 手动实现 | 框架级支持 |

### 未来展望

动态组合范式为以下方向提供了理论基础：

- 更安全、更易推理的运行时组合系统
- 原生支持热更新的编程语言和框架
- 自动化的资源管理和清理
- 形式化验证的运行时系统
