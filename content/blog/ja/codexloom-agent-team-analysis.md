# CodexLoom — Multi-Agent から Agent Team へ：AI エージェントをツールから真のチームへ

> **ひとことで言うと**：CodexLoom は、複数の独立した Codex Thread を「長期的に責任を持ち、協力でき、Human が統治する」Agent Team へ織り上げるための働き方であり、プロダクトです。その核心的な問いは、**複数のエージェントはいつ本当に Team になるのか？** —— 同時に動き始めたときではなく、異なる長期的責任を担い始め、お互いを見つけられ、直接協力し、継続的に収束させ、Human の統治のもとで本物の仕事を共に進めるときです。

## 🎬 オープニング：ある「偶然の」外部発信

記事の冒頭はとてもドラマチックです。

著者はもともと、1ヶ月以上かけて作った CodexLoom プロジェクトの Landing Page を先に公開し、ゆっくり磨き上げるつもりでした。ところが Web 担当の Agent が公開指示を受けると、既存の協力関係に従って、対外コミュニケーション担当の **Community Agent** に通知しました。Community Agent は「大ニュースだ」と素材を急いでまとめ、Feishu（飛書）のグループに投稿してしまいました。

著者が気づいたときには、**メッセージはすでに送信されていました**。

これは「制御不能」に見えますが、著者は「彼ら」はよくやったと感じています。なぜなら、そのプロセス全体で：

- 著者はエージェントの間に立って、次に誰に振るかを自ら選んでいない
- Context を手で運んだり、結果を伝えたりしていない
- 仕事は既存の**責任・協力関係・承認の境界**に沿って前に進んでいた

この「偶然」こそが Agent Team の価値を証明しています：**協力の責任が Human から Agent に移れば、仕事はもはや Human がすべてのステップを自らつなぐ必要がなくなります。**

## 🧠 核となる考え方：なぜ複数の Agent ≠ Agent Team なのか

これが記事全体の土台です。

これまで私たちは「単一のエージェントをどう強くするか、より長く複雑なタスクをどう完遂させるか」に関心がありました。しかし単一エージェントの能力には限界があり、多くの人が複数のエージェントを同時に使い始めました。**エージェントが増えると、本当のボトルネックは単一エージェントが何をできるかではなく、それらをどう組織化するかになります。**

著者は非常に鋭い判断を示します：

> **複数のエージェントは、自動的に Agent Team にはならない。**
>
> すべての仕事が依然として Human による入口の選択、背景の整理、Context の運搬、あるエージェントの結果を次のエージェントへ渡すことを必要とするなら、それらのエージェントは本質的に独立したツールの集合にすぎません。Human は依然としてシステム全体で唯一の Router であり、事実上のボトルネックです。

著者は「継続的な責任の線」モデルでエージェントの進化経路を説明します：

1. **Task** —— 一回限りの境界が明確な仕事（仕事の単位）
2. **Long-running Agent** —— 同じ種類の責任が持続する主体を持つ（ライフサイクル）
3. **Domain Agents** —— Scope の拡大と能力の劣化の後に分化する専門境界（分業）
4. **Human Router** —— 複数エージェント出現後、協力のボトルネックが Human に移る（ボトルネックの移動）
5. **Agent Team** —— 責任・関係・引き継ぎ方が外化され、協力の責任が Agent に移る（組織）

> **中核的判断**
>
> 本物の仕事が繰り返し戻ってくることで Long-running Agent が生まれ、Scope の拡大と能力の劣化が複数の Domain Agents を生み、エージェントの分化が協力のボトルネックを Human に集中させる。

エージェントの分化は、複数のエージェントを生み出すだけです。Human の頭の中に隠れていた責任・関係・引き継ぎ方が徐々に外化され、協力の責任の一部が Human から Agent に移って初めて、本当の Team になり得るのです。

## 🏗️ 詳細チュートリアル：Multi-Agent から Agent Team への6ステップ方法論

以下、著者の原文の章構成に沿って、実行可能な6ステップのチュートリアルに整理します。各ステップが1つの重要な問いに答え、対応する CodexLoom の仕組みを示します。

### ステップ1：Task Agent から Long-running Agent へ

**問い：エージェントはなぜ長期存在する必要があるのか？**

多くの人がエージェントを使い始めるとき、直面するのは Task です。新しい Thread を作り、何を完了させるかを伝え、エージェントは現在の Context に基づいてツールを呼び出し、タスクを実行し、結果を出します。タスクが完了すれば、その仕事も終わります。

しかし本物の仕事は、互いに独立した Task の連続ではありません。**Task は完了できても、その背後にある責任は終わりません。**

- 記事が書き終わっても、その後も修正が続く
- ページが公開されても、その後も反復が必要
- 今日調べた会社は、来月には新製品・新資金調達・新データを持って再び視野に入る

戻ってくるたびに単純な繰り返しではありません。前回の背景・判断・失敗は依然として有用であり、Human が与えた修正・好み・境界も次の仕事に影響を与え続けるべきです。

> **Task は仕事の一片であり、本物の仕事は絶えず流れる責任の線です。**

毎回新しいエージェントを作るなら、人は背景を説明し直し、好みを伝え直し、境界を定義し直し、さらには**すでに修正済みの失敗を踏み直す**ことになります。繰り返されるコールドスタートの深いコストは Token ではなく、**毎回協力関係を再構築すること**です。

だから最も自然な選択は、エージェントを同じ Thread に残し、次回は前回の仕事から続けることです。過去の仕事、人の修正、Summary・Memory・Skill などの仕組みで保存された経験が次のラウンドに影響を与え始めます。このとき、Task Agent は **Long-running Agent** になります。

> Long-running とは単に1つの会話を長く引き延ばすことではなく、同じ種類の責任が持続する主体を持つようになることです。

### ステップ2：「誰が何に責任を持つか」を Human の頭の外へ

**問い：エージェントが分化した後、なぜボトルネックは Human に移るのか？**

エージェントが便利になればなるほど、人はより多くの仕事を任せます。最初は記事を書かせ、次に資料探し、事実調査、コンテンツ管理、さらにページ・SEO・対外発信まで任せます。異なる仕事の高解像度の Context・作業方法・専門的判断が混ざり始め、エージェントは遅くなり、品質が下がり、繰り返しの修正が必要になります。

**Domain は最初から描かれた領域ラベルではなく、継続的な使用・Scope の拡大・能力の劣化の中で徐々に現れる仕事の境界です。** それは「どの仕事が同じエージェントが長期に担当するのに適し、どの仕事を切り出すべきか」に答えます。

分化後、個々のエージェントの Context 圧力は下がりますが、新しい問題が現れます：**協力は依然として Human の頭の中で起きています**。新しい仕事ごとに、人はどのエージェントを探すかを判断し、終わった後は人が結果を読み、使えるか判断し、次のエージェントに渡します。

> エージェントは並行実行できても、Human は依然として1つずつ読んで、判断し、ルーティングするしかありません。エージェントが増えるほど、Human が維持すべき Context と協力関係も増えます。

**解決策：すべてのエージェントを安定した識別可能な長期主体にする。**

CodexLoom が最初にすることは、エージェント同士がすぐにメッセージを送り合うようにすることではなく、すべてのエージェントに **Profile** を持たせることです。Profile は組織にとって非常に重要な3つの問いに答えます：

- **Identity** —— それは誰か
- **Domain** —— それが長期的に何に責任を持つか
- **Scope** —— どこで止まるか、何がその仕事ではないか

重要な点：Profile はエージェント作成時に一度だけ書くものでは**ありません**。より正確な順序は：

> **そうではない**：エージェント作成 → Profile 記入 → Domain Agent の完成
>
> **そうである**：本物の仕事が境界を露呈 → Profile が現在の理解を保存 → その後の仕事が検証と修正を続ける

Profile は最終的な答えではなく、**この Team が現在採用している組織仮説**です。

その上で、CodexLoom は3つの構造でチーム関係を記録します：

- **Organization** —— parent/child の長期的責任境界を記録（より大きな責任の下に安定した子責任が分化したか）
- **Collaboration** —— 方向性を持つ長期的協力インターフェースを記録（2つの独立 Domain の間に繰り返し現れる協力境界）
- **Activity** —— 一定期間内に実際に起きた Message 協力を記録（実行の証拠）

> **重要な区別**：Profile・Organization・Collaboration は**宣言**（組織仮説）を保存し、Activity は**実行の証拠**を記録します。この2つは互いに代替できず、自動的に相互検証もされません。Collaboration を書いたからといって両者がうまく協力している証明にはならず、頻繁にメッセージを送り合っても自動的に長期的 Collaboration にはなりません。

**検証基準（最初の分水嶺）**：

> **重要な問い**
>
> 仕事に協力が必要なとき、現在のエージェントは「誰に聞けばいいか」と Human に振り返るしかないのか、それとも自分の Scope・直接の関係・能動的に照会した Profile に基づいて、次の候補 Domain Owner を判断できるのか？

### ステップ3：エージェント同士の直接協力（Agent Message）

**問い：候補責任者を特定した後は？**

現在のエージェントが境界に達した後もまず Human に戻って報告しなければならないなら、Human は依然としてシステム全体の人手バスであり、「誰に振るかを判断する」ことから「すべての仕事をつなぐ」ことに役割が変わっただけです。

**解決策：エージェント同士が直接協力関係を築く。Agent Message から始める。**

Message には明確な送信者と受信者がおり、このコミュニケーションが相手からの結果返却を期待するかどうかも示します。それは受信者自身の長期的 Thread に入り、受信者は自分の Profile・直接の関係・蓄積された専門 Context で理解・処理します。**送信者の完全な Thread・全履歴・プライベート Context はコピーされません。**

かつて Human の頭と手で起きていたプロセス：

```
仕事が境界を越えたことを検知
  ↓ より適切なエージェントを見つける
  ↓ なぜそのエージェントなのか説明する
  ↓ 必要な Context を引き渡す
  ↓ 処理を待つ
  ↓ 結果を持ち帰る
```

これはエージェント間で直接起きるようになります。

**Message の3つのコミュニケーション意図：**

- **request** —— 相手に判断・行動・結果の返却を求める（`--response required`）
- **notification** —— 相手が知るべき状態変化を同期する（返信不要）（`--response none`）
- **reply** —— request に回答し、結果は元の Message に沿って戻り、真の因果関係を保持する

CLI の例：

```bash
# 境界のあるリクエスト：相手に判断/行動/結果の返却を求める
loom msg TARGET --from SELF --subject "境界のあるリクエスト" \
  --response required --body "現在の問題、境界、証拠の要件、返却義務"

# 状態同期：返信不要
loom msg TARGET --from SELF --subject "状態または事実" \
  --response none --body "変化、影響、検証の入口"
```

**ベストプラクティス：エージェントのコミュニケーションは「一度にすべてを言い切ること」ではない**

送信者と受信者はそれぞれ長期に蓄積された Context を持っています。受信者は Prompt を埋めるのを待つ空白の実行器ではありません——送信者が知らない事実を知っているかもしれず、異なるツールや専門的判断を持ち、問題の前提自体が間違っていることに気づくかもしれません。

送信者が最初の Message で全てを完全に定義しようとすれば、それは受信者に「あなたは何を知っているか、問題がなぜ起きたか、どの結論に達すべきか」を押し付けることになり、送信者自身の盲点を協力に持ち込むことになりがちです。

実践から生まれた原則：

- 相手が何を知っているかを仮定せず、原因や結論も相手に押し付けない
- 最初の Message は相手が正しく始められれば十分であり、背景を一度に尽くす必要はない
- 次のラウンドは、あらかじめ書かれた質問リストを機械的に追うのではなく、相手の実際の返答に基づいて続ける
- 各ラウンドは新しい情報か決定をもたらすべきで、Context が十分になったら速やかに収束する

> **ベストプラクティス**
>
> 良い多ラウンドコミュニケーションは、完全なメッセージを機械的に分解することではなく、前のラウンドの実際の返答を次のラウンドの新しい Context にすることです。
>
> 多ラウンドも多ければいいわけではありません：責任境界・入力・承認の前提・結果の還流がすべて明確なら、自己完結型の handoff が通常より効果的です。

> **境界**
>
> Message が配信されたことは、受信者の Turn がその入力を受理したことを示すだけであり、受信者が理解・同意・正しい判断をしたことを示すのでは**ありません**。処理状態が完了を示すのも、その実行が正常に終了したことを意味するだけで、業務結果が完了したことや、新しいツール・本番・対外権限を得たことを意味し**ません**。

### ステップ4：Message はコミュニケーション、Topic は収束を担う

**問い：複数のエージェントと複数の段階にまたがる仕事で、唯一の現在バージョンをどう保つか？**

1つの仕事が、まず Content Agent が命題を整理し、次に Research Agent が事実を検証し、Product Agent が製品実装を確認するかもしれません。途中で新しい材料の待機、Human の選択、外部事実の変化もあるかもしれません。各エージェントは自分の担当部分を完了しても、**誰も全体がどこまで進んでいるかを知らない**かもしれません。

これらの状態を最後まで Human が Message を1つずつ読み、異なる Thread に入り、頭の中で完全な進捗図を組み立てる必要があるなら、Human は「コミュニケーション Router」から「プロジェクト状態 Router」に変わっただけです。

**解決策：Topic —— クロスエージェント仕事のための唯一の収束構造。**

> **中核的判断**
>
> すべてのエージェントに同じ Context を共有させることではなく、クロスエージェントの仕事に明確な現在バージョンと、最終収束を担当する1つのエージェントを持たせることです。

Topic はエージェントをグループチャットに引き込むものでは**ありません**。各 Topic にはちょうど1つの **Responsible** がいます：

1. Human / Owner が方向・選択・修正を Responsible に渡す
2. Responsible が Message を通じて異なる **Participant** に境界のある問いを派遣する
3. Participant は自分の Thread で専門作業を行う（共通チャットウィンドウには入らない）
4. 部分的な結果が Responsible に戻り、Responsible が Topic を更新する

> グループチャットが全員が同時に話す会議室のようなものなら、Topic は**明確な主担当者を持つ協力事項ファイル**のようなものです。仕事が現在採用しているバージョンを保持しますが、参加者それぞれの専門作業スペースを代替しません。

Topic は継続的に保存します：

- Responsible が維持する `current brief`（現在採用している事実・判断・次のステップ・制約）
- 各 Participant が何に責任を持つか
- 仕事が誰を・何を待っているか
- 重要な証拠アンカーと段階的結果がどこにあるか
- Topic が現在収束済みとマークされているか

**Responsible は「何でも自分でやる」のではありません**。その責任は他のエージェントに代わって専門的判断を下すことではなく、全体の継続性を維持することです：問題の分解、適切な Participant の選定、部分結果の吸収、衝突と待機の特定、現在バージョンの更新、最終結果の返却。

> **協力の境界**
>
> **ローカルでの完了は、協力の完了を意味しない。** 部分的な結果・証拠・制約・次のステップが Responsible に戻り、仕事の現在バージョンに統合されて初めて、その責任移転は本当に閉じます。

**Artifact：正式な結果に安定したバージョンを**

クロスエージェント仕事の成果物は、調査レポート・スクリーンショット・コード・章の草稿・evidence ledger など様々です。CodexLoom は **Artifact** で引き渡す必要のあるファイルのスナップショットを保存します——安定した ID・ファイル情報・チェックサムを持ち、元ファイルが後で変更されても、公開済みのスナップショットは変わりません。

> `current brief` は「私たちがこの仕事を今どう理解しているか」を説明し、Artifact は「この判断が具体的にどのファイルバージョンに対応するか」を保存します。

**Needs You：正しい場所で Human を呼び戻す**

エージェントに Human の事実・選択・Review・承認が欠けているとき、それは Human に代わって答えることができず、曖昧な「次はどうする？」を投げ返すべきでもありません。まず説明しなければなりません：現在どの仕事を進めているか、どの事実が確定しているか、具体的に人のどの判断が欠けているか、どの選択肢と影響があるか、Human が答えた後どこから元の仕事を再開するか。CodexLoom はこの経路を **Needs You** と呼びます。

> Human はすべてのエージェントの間に立って各ステップを押す必要はありません。ほとんどの仕事は前に流れ続けます。本当に人の事実・トレードオフ・Review・承認が必要なときだけ、Human は正確な仕事の位置に呼び戻されます。
>
> Needs You を作成したことは承認を得たことにはなりません。Human の回答も明示的に与えられた範囲だけをカバーします——「下書きを続けて」とだけ同意されたなら、エージェントは「直接公開してよい」と解釈できません。

### ステップ5：Overview —— 変化し続ける Agent Team を統治可能にする

**問い：エージェントが2つから20個になるとき、Human は Team 全体が実際にどう働いているかをどう見るのか？**

Human の注意力は有限です。すべてのエージェントの完全なプロセスを読もうとすれば、すぐに情報に溺れます。これは人間のチーム管理とよく似ています：管理者は全員の完全な作業記録を読むことで組織を運営できません。Team が大きいほど、まず高いレベルから実行を観察する必要があります。

> **本当の統治の問い**
>
> Human は現在の Agent Team が起きている仕事にまだ適しているかをどう知るのか？宣言された構造と実際の実行が乖離し始めたとき、調査して調整するための手がかりをどこに見つけるのか？

**解決策：Overview —— 実行観察とトリアージの入口。**

Overview は「今日どれだけのエージェントが動いたか」を示す賑やかなダッシュボードではなく、エージェントに成績ランキングを付けるものでもありません。エージェント状態・Codex Turn・Needs You・Inbox・外部 Connection・キュー・Token 記録に散らばっていた実行シグナルを1つの入口に圧縮します。いくつかのコアビューを含みます：

- **Status** —— 今どのエージェントが実行中か、何が Human を待っているか、Inbox に滞留があるか、外部 Connection が問題を残したか；Daily Activity が実行・Turn・Token を時間軸に揃える
- **Capacity** —— Turn 実行、新しい仕事の待機（**New-work wait**：新しい追跡可能な仕事がキューに入ってから初めて実際に処理されるまでの時間）、現在の backlog、仕事の発生源、待ち行列の証拠を表示
- **Token Usage** —— input / cached input / output / reasoning output / model calls の日付・エージェント・モデル間の分布を表示

**リーン管理の視点：リソース効率 vs フロー効率**

リソース効率は各局所が十分に活用されているかを気にし、フロー効率は1つの仕事がエンドツーエンドでスムーズに進むかを気にします。Agent Team も同じです：

> 常にフル負荷でありながら、すべての下流を待たせているエージェントは、追求する価値のある効率ではありません。局所的な忙しさを Team 全体のボトルネックに変えているだけかもしれません。

**最も重要な原則：Signal は Diagnosis ではない。**

- 忙しいことは価値を意味せず、低い実行は無用を意味せず、Token が多いことはより良い結果を意味せず、待機は自動的にエージェント不足を証明しない
- Overview は組織を自動的に理解しません：Profile を自動的に読んで仕事が境界を越えたか判断することも、Collaboration と Activity を自動的に照合することもありません
- 低い Activity は低い価値ではなく、高い Activity も高いパフォーマンスではありません——「ここは調査する価値があるかもしれない」と伝えているだけです

完全な統治ループは：

> **統治ループ**
>
> Signal の発見 → Evidence への掘り下げ → 原因の判断 → 介入の選択 → 次の本物の仕事での検証。

最後の介入もエージェントの分割や追加とは限りません：方法に問題があれば Skill と作業方法を変え、ツールが不足すればツールを追加し、ルーティングが間違っていれば Collaboration を調整し、権限が塞がっていれば承認ゲートを修正します。**問題が長期的に繰り返し Domain 境界から来るときだけ、責任の分割・統合・再定義を検討すべきです。**

> **Human の新しい位置**
>
> Human は Agent Team から消えたのではなく、すべての仕事の人手 Router から、Team 全体を観察・追及・診断・調整する Owner へと上に移動しました。

### ステップ6：External —— Agent Team を実際の外部関係に入れる

**問い：内部 Team が成熟した後、エージェントは外部へのサービスを直接助けられるか？**

個人にとって本当に希少な資源は時間と注意力です。すべての対外仕事が最終的に本人に戻らなければならない——ニーズの理解、内部エージェントの組織化、結果の確認、直接の返信——ならば、内部 Agent Team がどれほど強力でも、改善されるのは主に個人の効率です。**成熟した Domain 能力が明確なアイデンティティと責任境界の下で外部に入れるときだけ、エージェントは効率向上ではなく能力拡張をもたらします。**

**しかしエージェントが外部に出ると、リスクモデルが変わります：**

- 内部には長年の暗黙の協力があり、外部の人はこのエージェントがどのような修正を受けてきたか、知識と権限の境界を知らない
- 同じ不正確な文は、内部では単なる作業誤差でも、外部では製品事実・組織の立場・成立した約束と理解されるかもしれない
- 外部入力はデフォルトで信頼できません：誤った背景を提供する人、エージェントが何を見られるか探る人、内部情報の開示を誘導する人、ルールを迂回させる人、攻撃さえ試みる人がいるかもしれません

**解決策：外部は単一の管理された入口に直面する。**

CodexLoom は Provider Bot を Team 全体に直接接続しません。外部ユーザーは、設定された Address と Membership を通じて、**その Address を所有する長期エージェント**（Interface Agent は組織形態であり、ハードコードされたタイプではありません）に入ります——内部 Profile・Thread・ツール・認証情報への直接入口ではありません。

主要な概念：

- **Connection** —— Provider app / bot / account / tenant の接続・能力・健全性を確立
- **Agent Address** —— 外部アイデンティティを長期エージェントにバインドし、「どのエージェントがこのアイデンティティで外部に現れるか」に答える
- **Conversation Membership** —— このエージェントが現在の Conversation でなぜ存在するか、どの役割を果たすか、どの guidance に従うか、コミュニケーション境界（どのインバウンドメッセージがトリガーになるか、結果が外部返信にどうマッピングされるか、返信のみか能動送信も許すか、どの `trust-domain` ラベルを使うか）を記録

> 同じエージェントの長期アイデンティティは安定を保てますが、各外部関係での局所的役割と行動境界は**個別に統治**されなければなりません。1つの Membership は対応する Conversation にのみ適用されます。

**外部リクエストの完全な経路：**

```
Provider event
  ↓ Connection / Address / Membership
  ↓ Inbox / Handling
  ↓ Interface Agent primary Thread
  ↓ 任意の内部エージェント協力
  ↓ Outbox
  ↓ provider result / receipt
```

- Interface Agent は内部 Profile と宣言された関係を照会し、Message や Topic を通じて境界のある仕事を候補 Domain Owner に渡せます——しかし External は正しい内部エージェントを自動的に選択しません
- 内部 Domain Agent は外部の役割を迂回して、Provider に結果を送る権限を直接得ることはできません
- **Outbox** はターゲット・内容・冪等情報・送信試行・状態・Provider の返却結果を保存し、外部アクションを追跡可能にします
- **Provider receipt** は Provider が当時 message 識別子を返したことを証明するだけであり、相手が読んだ・理解した・受け入れたことを意味せず、ましてや業務効果が発生したことを意味しません

**Human は外部結果の境界を保持します：**

> 答えを知ること、表現の草案を作ること、既存の質問に返信すること、能動的に公開すること、他人に代わって約束すること、現実の副作用を持つ行動を実行することは、まったく異なる権限レベルです。

エージェントが仕事に事実・選択・Review・承認が欠けていると判断したとき、Needs You で現在の仕事を一時停止し、Human に明確な質問をできます。Human はもはやすべての Context を運びませんが、**外部結果の最終的な境界は依然として保持します**。

## 🔧 CodexLoom プロダクト説明：何を織り上げるのか

冒頭の「偶然の」外部発信に戻ります。本当に価値があるのは「エージェントが自動でメッセージを送れること」ではありません——**自動化は Agent Team を意味しない**のです。あらかじめ書かれた Workflow に従って最初のエージェントから最後のエージェントまで実行すれば Team と呼べるなら、私たちはプログラムのノードをエージェントに置き換えただけです。

CodexLoom がすることは、Codex がすでに提供する強力な Thread を Agent Team に織り上げることです：

- 1つの Thread を**長期的に存在するエージェント**にし、安定した Identity・Domain・Scope を持たせる
- 異なるエージェントが互いの Profile と宣言された関係を照会し、**Message** で直接協力できるようにする
- クロスエージェントの仕事を **Topic** を通じて Responsible が維持する現在バージョンに保つ
- Human が本当に事実・選択・Review・承認を必要とするときに入り直せるようにする（**Needs You**）
- Owner が **Overview** で Team の実際の実行を観察できるようにする
- 最後に、統治された **External** を通じて内部能力を顧客・コミュニティ・協力関係に持ち込む

**CLI コマンド早見表：**

```bash
# チームビュー
loom team                  # 現在の Team の全体ビュー
loom team <agent>          # エージェントの完全な Profile・隣接関係・Activity を表示
loom team links <agent>    # エージェントの宣言された関係を表示
loom profile get <agent>   # Identity・Domain・Scope を読み取る

# Agent Message
loom msg TARGET --from SELF --subject "境界のあるリクエスト" --response required --body "..."
loom msg TARGET --from SELF --subject "状態または事実" --response none --body "..."
```

**WebUI ビュー：** Team ページは Directory・Organization・Collaboration・Activity の4ビューを提供し、Overview は Status・Capacity・Token Usage を提供し、Topic Current・Needs You・External（Inbox / Outbox）ページもあります。

## 🎨 設計哲学

著者が記事で繰り返し強調する境界が、CodexLoom の設計哲学を構成しています。「何でないか」の定義は「何であるか」より重要です：

1. **Profile は組織仮説であり、能力の証明ではない。** 「今、採用する価値のある責任境界」を保持し、「このエージェントが能力を証明した」ことの証明ではありません。宣言は共同作業のベースラインであり、能力・記憶・承認の証明ではありません。

2. **宣言 ≠ 実行の証拠。** Organization / Collaboration は宣言された責任構造であり、Activity は実際に起きた協力の証拠です。別々に記録され、互いに代替できず、自動的に相互検証もされません。

3. **ローカル完了 ≠ 協力完了。** 部分的な結果が Responsible に戻り、現在バージョンに統合されて初めて、責任移転は本当に閉じます。

4. **状態 ≠ 結果。** Message の `delivered` は仕事が正しいことを意味せず、Topic の `resolved` はすべての現実の結果が完了したことを意味せず、External receipt は相手が読んだ・受け入れた・業務効果を得たことを意味しません。

5. **Signal は Diagnosis ではない。** 指標の役割は Owner がシステムを理解し改善するのを助けることであり、エージェントをランキングすることではありません。低い Activity ≠ 低い価値、高い Activity ≠ 高いパフォーマンス。

6. **Membership は権限システムではない。** 局所的役割とコミュニケーションポリシーを扱います。`trust-domain` は記録と制約のためのラベルであり、セキュリティサンドボックスではありません。

7. **エージェントに代わって判断しない。** CodexLoom はエージェントのための「正しい人」を自動的に見つけず、境界が満たされたかを自動的に検証せず、繰り返しの往来を自動的に Collaboration に昇格させません。誰に頼るか、境界が満たされたかは、依然としてエージェントと Human の判断です。

8. **最小で可逆的な介入。** 統治は一度きりの Reorg ではなく、継続的な改善ループです：問題を露呈させ、原因を調査し、できるだけ小さく可逆的な調整を試し、次の本物の仕事で結果を検証します。実際に成立した変更だけが Profile・Organization・Collaboration・Skill に沈殿します。

9. **安定したエージェント、動的な Team。** エージェントは Domain で経験を蓄積できるほど安定し、Team はモデル・ツール・業務・外部環境の変化に適応できるほど動的でなければなりません。安定しているのは長期的責任主体であり、動的であるのは現在の組織仮説です。

10. **自動化 ≠ Agent Team。** 本当の Team は長期的に存在する責任主体の集合です：それぞれが Domain で経験を蓄積し、自分が何に責任を持ちどこで止まるかを知り、協力が必要なときはお互いを見つけ、直接コミュニケーションし、継続的に収束します。Human が方向と重要な境界を保持し、本物の仕事とともに進化し続けます。

## 💡 まとめ：主要な視点と結論

1. **複数のエージェントは自動的に Agent Team にはならない。** すべての仕事の入口・Context・結果・次のステップが依然として Human に集まるなら、それは「人が手配する必要のあるツール一式」にすぎません。

2. **ボトルネックの移動が進化の原動力。** 単一エージェントの過負荷が Domain 分化を促し、Human Routing の過負荷が複数のエージェントを Agent Team へ進化させます。

3. **責任の外化が分水嶺。** Multiple Agents から Agent Team への最初の分水嶺は：エージェントが協力を必要とするとき、Human に聞くしかないのか、それとも自分の Scope・直接の関係・照会した Profile から次の候補 Domain Owner を判断できるのか？

4. **協力の責任は移転し、階層化する。** Human Router が担っていた仕事は分解されます：送信者はなぜ協力が必要か判断し Context を渡し、受信者は自分の専門 Context で問題を修正し、収束担当エージェントが部分結果を統合し、Human は方向・重大な選択・Review・承認を保持します。

5. **多ラウンドコミュニケーションの価値は修正にある。** 良い多ラウンドコミュニケーションは、前のラウンドの実際の返答を次のラウンドの新しい Context にすることであり、完全なメッセージを機械的に分解することではありません。境界が明確なら、自己完結型の handoff がより効果的です。

6. **Topic はクロスエージェント仕事の「単一の真実源」。** 共有されるのは現在の状態であり、すべての Context ではありません。1つの Topic にはちょうど1つの Responsible がおり、Participant は自分の Thread で作業を続けます。

7. **Human の新しい位置は Owner であり、消滅ではない。** Human はすべての仕事の人手 Router から、Team 全体を観察・追及・診断・調整する Owner へと上がり、注意力を本当に人を必要とする場所に使います。

8. **外部化は能力拡張であり、効率向上ではない。** 成熟した Domain 能力が明確なアイデンティティと検証可能な行動境界で外部に入るとき、Agent Team は内部生産性システムから、継続的に外部へ提供する組織能力になります。

9. **最終的な答え：** 複数のエージェントはいつ本当に Team になるのか？—— 同時に動き始めたときではなく、異なる長期的責任を担い始め、お互いを見つけられ、直接協力し、継続的に収束させ、Human の統治のもとで本物の仕事を共に進めるときです。

## 🗺️ 適用シーンと読み方の提案

**記事は章ごとの読み方の提案をしています：**

- まず「なぜ複数のエージェント ≠ Agent Team なのか」を理解したい → プロローグ、01、07 を読む
- すでに複数エージェントを運用していて Human Routing に疲弊している → 02、03、04 を重点的に読む
- エージェントの負荷・ボトルネック・Scope 調整・Team Governance に関心がある → 05 を直接読む
- エージェントを Slack・飛書・顧客・コミュニティなどの実際の外部関係に入れたい → 06 を直接読む
- CodexLoom の製品ロジックを完全に理解したい → 最初から最後まで読む

**適した人：**

- 3つ以上の AI コーディングエージェント（Codex、Claude Code、Cursor など）を同時に運用している開発者
- 「エージェントは増えたのに、人がより忙しくなった」と感じるチーム
- Multi-Agent 協力・エージェント統治・AI チーム組織に興味のある研究者とアーキテクト

**適さないシーン：**

- エージェントを使い始めたばかりで一回限りのタスクを扱う（まずプロローグ、01、07 で枠組みを作る）
- 単一エージェントの深い作業だけが必要なタスク（Team レベルの協力構造は不要）

## 📝 結論

CodexLoom は「より多くのエージェントを同時に開く」ためのツールではなく、独立した Codex Thread を、**長期的に責任を持ち、協力でき、Human が統治する** Agent Team に織り上げるものです。

そのロードマップは明確で抑制的です：

1. **Task → Long-running**：同じ種類の責任に持続する主体を持たせる
2. **Long-running → Domain Agents**：境界を実際の摩擦から現れさせ、分化させる
3. **Domain Agents → Agent Team**：責任・関係・引き継ぎ方を Human の頭から外化する

対応する製品メカニズムは層をなして進みます：**Profile**（私は誰か、何に責任を持つか、どこで止まるか）→ **Message**（エージェント同士が直接コミュニケーション）→ **Topic**（クロスエージェント仕事の収束）→ **Overview**（チームが統治可能）→ **External**（現実世界への参入）。

> **最終的な問い**：複数のエージェントは、いつ本当に Team になるのか？
>
> **最終的な答え**：同時に動き始めたときではなく、異なる長期的責任を担い始め、お互いを見つけられ、直接協力し、継続的に収束させ、Human の統治のもとで本物の仕事を共に進めるときです。

**1つの Codex Thread から、長期的に責任を持ち、協力でき、統治でき、現実世界に入ることもできる Agent Team へ。それが CodexLoom です。**
