# Motion2MixamoRig 徹底解説：実写動画から Mixamo キャラクターを作る、このプロジェクトは何が正しかったのか

先に結論。

いま手元に Mixamo キャラクター（Adobe が無料で配布しているスケルトンのセット）があって、実写の動作を当てたいとします。従来は外注するかモーションキャプチャ機器を買うしかなく、どちらも 1 件あたり数千人民元から数万元人民元という価格でした。

Motion2MixamoRig はこれを、Python 環境を構築して動画を入れ、十分ほど待てば、Blender や Unity にそのまま放り込める `.glb` が手元に来る状態に変えました。

**しかしこのプロジェクトが本当に見る価値があるのは、どれだけ節約できるかなのではなく、「動作移行」という問題を解くその独自の方法です。**

その完全なパイプライン、6 つの重要な問題の解法、そしてコードのコメントに隠されたデザイン哲学をすべて分解します。

---

## 一、プロジェクト説明：そもそも何をするのか

Motion2MixamoRig は MaxLiu22 が開発し、Apache-2.0 ライセンスで、2026 年 8 月 29 日にオープンソース化されました。現在の star は 1583、fork は 200 です。Python 実装で、`motion2mixamorig` パッケージは 10742 行、Blender プラグイン部分は 5922 行です。

### 一言で定義すると

**動画（または写真）1 本を入力すると、Adobe Mixamo のスケルトンで駆動され、完全なスキニングとアニメーションを持つ 3D キャラクターフイルを出力します。**

### 完全なパイプライン

```
视频 / 照片
    ↓  ① 预检（内容检查，不是存在性检查）
    ↓  ② 人体动作提取（GVHMR，24 个 SMPL 关节）
    ↓  ③ 脚部接触检测（4 通道静态置信度）
    ↓  ④ 重定向到 Mixamo 骨骼（swing / twist 分解 + FK）
    ↓  ⑤ 脚部锁定（解析双骨 IK）
    ↓  ⑥ 落地校正（髋部垂直平移）
    ↓  ⑦ 蒙皮导出（GLB + 每骨骼旋转）
    ↓  ⑧ 自相交诊断（直接读 GLB 做线性混合蒙皮）
视频输入 → 4 个预览视频；照片输入 → 4 张预览图 + 360° 环绕对比
```

### 2 つの使い方

**Blender プラグイン（プログラマーではない人向け）**

GitHub Releases から該当プラットフォームの zip（現状 `macos-arm64` のみ）をダウンロードし、Blender で `Edit → Preferences → Get Extensions → ∨ → Install from Disk…` からインストールします。3D ビューで `N` を押してサイドバーを開き、`Install Runtime (one click)` を押すと独立した Python ランタイムが自動で入ります。あとは SMPL-X モデルを選び、Mixamo FBX を選び、動画を選び、`Generate Motion` を押します。

**コマンドライン（開発者向け）**

```bash
m2mr doctor          # 检查资产和依赖，缺什么告诉你去哪下
m2mr run             # 用 assets/video/ 里最新的视频 + Y_Bot.fbx
```

プラグインの中核となる設計は**Blender の Python に触らない**ことです。プラグイン自体は PyTorch も GVHMR も OpenCV も import せず、外部プロセスを起動するだけです：

```text
<external-python> -m motion2mixamorig.cli run ...
```

この外部 Python は、プラグインがワンクリックで `~/Motion2MixamoRig` にインストールしたランタイムか、ユーザーが自分で指定した venv のどちらかです。この分離が非常にきれいにできていて、Blender 同梱の Python のバージョンや pip 環境の地獄を避けられます。

## 二、詳細チュートリアル：ゼロから最初の動作を通す

### ステップ 0：アセットの準備

これらのファイルはリポジトリには同梱されていません（それぞれの研究ライセンスと Adobe の利用規約が関係するため）、自分で入手する必要があります：

| 置くもの | 置く場所 | 入手元 |
|---|---|---|
| SMPL-X 人体モデル | `assets/body_models/smplx/SMPLX_NEUTRAL.npz` | [SMPL-X](https://smpl-x.is.tue.mpg.de/) に登録して NPZ 版をダウンロード |
| Mixamo キャラ FBX | `assets/mixamo/Y_Bot.fbx` | Adobe アカウントで [Mixamo](https://www.mixamo.com) にログインしてダウンロード |
| 動作動画 | `assets/video/<name>.mp4` | 1 人だけ、頭から足先まで常に画面内であること |
| ポーズ写真（任意） | `assets/image/<name>.jpg` | 同上、`--image` と併用して使う |
| MANO 右手モデル | `assets/body_models/mano/MANO_RIGHT.pkl` | [MANO](https://mano.is.tue.mpg.de/) に登録して Models & Code をダウンロード |

**初心者が最も踏みやすい落とし穴**：Mixamo からダウンロードしたファイル名は `Y Bot.fbx`（間がスペース）ですが、デフォルトの読み込みパスは `Y_Bot.fbx`（アンダースコア）で、1 文字違います。名前を変えればデフォルトのキャラクターになります。変更しなくても構いませんが、見つからない場合はプログラムが `assets/mixamo/` 内の最初の `.fbx` を自動で使います。

**素材の要件**は厳しすぎます：画面には 1 人しかダメで、頭から足先まで常に画面内にあり、出画してはいけません。`m2mr doctor` と `m2mr run` は事前チェックの段階で人数を検出し、2 人いたら即停止します。十分かけて抽出する無駄をしません。

### ステップ 1：インストール

```bash
git clone https://github.com/MaxLiu22/Motion2MixamoRig.git
cd Motion2MixamoRig
python -m venv .venv && source .venv/bin/activate

pip install --upgrade pip setuptools wheel \
  && pip install "numpy>=1.26" \
  && pip install --no-build-isolation "chumpy==0.70" \
  && pip install -e .
```

あの `--no-build-isolation` は任意項目ではありません。`chumpy` は GVHMR の依存関係チェーン上にある古いパッケージで、その setup スクリプトが pip を import するため、pip のデフォルトの隔離ビルド環境では必ず `No module named 'pip'` で落ちます。先に隔離を切って単独でインストールする必要があります。

さらに ffmpeg の導入も推奨します（`brew install ffmpeg` か `apt install ffmpeg`）。なくても動きますが、出力される動画に音声がなく、エンコード形式もブラウザで直接再生できません。

### ステップ 2：健康診断

```bash
m2mr doctor                 # 只查身体这一路
m2mr doctor --detect-hands  # 连手指检测的文件和 Python 包一起查
```

`doctor` がやることは「ファイルがあるか調べる」よりも遥かに細かいです。ファイルの**中身**まで見ます。実際に多い失敗はファイルの欠落ではなく、ファイルの中身が間違うことだからです：

- SMPL-X の頂点数は 10475、SMPL は 6890。頂点数でモデル系統を識別し、**ファイル名は見ない**（誰かが SMPL を SMPLX に改名するのを防ぐため）
- FBX の先頭 12 バイトのマジックナンバーで Binary 形式かを判定し、ASCII FBX は拒否する
- 16 フレームを抽出して YOLO の人数検出を行い、2 人なら利用不可と判定する
- 面積比が 1.5% 未満の「切手サイズの人」（観客、ポスター）を除外し、2 人目がそれより大きければ警告する

### ステップ 3：最初の実行

```bash
m2mr run
```

初回実行では推論重み 約 5 GB が `weights/` にダウンロードされます（GVHMR、HMR2、RTMPose/ViTPose 2D ポーズ、YOLOv8 人体検出）。このダウンロードは 1 回だけです。

CPU 上で 30 秒のクリップを処理する場合：初回は 8 から 15 分、重みが揃った後は 3 から 5 分です。リターゲットとレンダリングは通常 1 から 2 分。

**重みのダウンロードは自動ですが、推論重みのライセンスはこのプロジェクト管轄外です**。README には上流のライセンスが 1 つずつ明記されており、責任あるやり方です。

### ステップ 4：キャラクターを変えても抽出をやり直さない

このツール全体で実用性が最も高い設計です。

人体動作の抽出が遅い工程で、リターゲットは速い工程です。そこでスケルトンを単独のファイルに保存します：

```bash
m2mr run --skeleton outputs/20260829_193205_dance/skeleton_motion.npz \
         --rig assets/mixamo/Vampire.fbx
```

**数分が数十秒になります。** 同じ動作に好きなだけ Mixamo キャラクターを当てはめられ、コストはほぼリターゲット部分だけです。

### ステップ 5：指を追加する

```bash
m2mr run --video assets/video/dance.mp4 --detect-hands --hand-smooth 0.08
```

`--detect-hands` は HaMeR の手部モデルを有効にし、人体から手首を切り出し、GVHMR がすでに選んだフレーム上で指の回転を推定して `skeleton_motion.npz` に書き込み、Mixamo の 30 本の指骨を駆動します。

必ず知っておくべきことが 3 つあります：

1. **所要時間は 2 倍**。手部検出は身体抽出の上に重なるので、並列ではありません。
2. **初回は 2.7 GB 追加で**重みが `weights/hamer/` にダウンロードされます。
3. **スケルトンを再利用するときは flag を重ねなくてよい**。`skeleton_motion.npz` にすでに手部動きが入っていれば、`--skeleton` が自分で指を駆動します。入っていなくても身体キャッシュが隣にあれば、`--detect-hands` を付けると身体を再実行せずに指だけ補えます。キャッシュが消えたときだけ動画を再実行します。

`--hand-smooth` は指回転の平滑化秒数で、デフォルトは 0.08、0 を入れれば生の推定値になります。

### ステップ 6：診断を見る

```bash
m2mr diagnose outputs/<run>                        # 重算诊断
m2mr diagnose outputs/<run> --visualize            # 额外生成 diagnostics.html
m2mr diagnose outputs/<run> --threshold-cm 2       # 只报深度超过 2 cm 的
```

`m2mr run` は毎回、出来上がったキャラクターに自己交差（体の部位が別の部位に食い込む。たとえば手が頭に入るようなもの）がないか自動で検査し、`diagnostics.json` に書き込みます。ターミナルには 1 行の要約が出力されます：

```
diagnostics: 14 self-intersection(s) over 116 of 719 frames, deepest 7.87 cm
```

**重要な設計を 1 つ挙げておきます**：検査に失敗しても実行は失敗しません。**報告は情報であって、ゲートではありません。** 判断権は利用者に委ねられています。

`diagnostics.html` はより完全な報告書です：元動画とキャラクターを並べる、時間軸、クリック可能な問題リスト、3D ビューは three.js を CDN から読み込み。床にはマーカーが固定されています（0.5 メートルごとに十字、1 メートルごとに大きい十字、原点は緑）、これによりキャラクターが歩いているのか滑っているのかを判別できます。

### ステップ 7：手動アノテーションと部分修正

目で見なければ分からない問題があります：足が滑った、膝が跳ねた、手が体に届いていない。これらは `diagnostics.json` には**含まれません**。

`diagnostics.html` は自己交差トラックの上に琥珀色のアノテーションレーンがあり、フレーム範囲をドラッグ選択して In / Out を入力し、問題を書き込めます。右側の Notes リストに一覧が出て、行をクリックするとそのフレームにジャンプします。**Download notes** はアノテーションと自己交差リストをまとめて `<動画名>_review.json` に保存します。

このファイルには正式な schema があります：`m2mr-review-v1`。

```json
{
  "schema": "m2mr-review-v1",
  "run": "20261024_032240_beat_it_shotaro_test_input_compatible",
  "video": "/absolute/path/to/assets/video/beat_it.mp4",
  "rig": "/absolute/path/to/assets/mixamo/Y_Bot.fbx",
  "fps": 30,
  "frame_count": 554,
  "manual_annotations": [
    {"id": "n1", "start_frame": 380, "end_frame": 410, "start_s": 12.667, "end_s": 13.667, "note": "left foot slides"}
  ],
  "self_intersections": [
    {"kind": "self_intersection", "parts": ["left_hand", "left_thigh"], "ranges": [[372, 373], [378, 381]], "max_depth_cm": 7.37, "also_in_rest_pose": false}
  ]
}
```

この JSON をキャラクターフイルやスケルトンファイルと一緒に AI や開発者に渡すと、**アノテーションされたフレーム区間だけ**を対象に Mixamo アニメーションを作り直し、新しいディレクトリに書き出します。**元の実行結果はそのまま保持されます**。

**この「上書きしない、増分での修正のみ」という設計は、このプロジェクトが同種の中でエンジニアリングの成熟度で上回っていると思う点である。**

### ステップ 8：Blender に読み込む

`File → Import → glTF 2.0 (.glb/.gltf)`。

迷いやすい点がいくつかあります：

- カメラが空の方を向いている場合は、キャラクターのメッシュを選択して `View → Frame Selected`
- 頭と手にある球の集まりはスケルトンの表示でメッシュではありません。Outliner で `Icosphere` とアーマチュアを非表示にして、**スキニングされたメッシュだけが見える状態にしてください**
- シーンの FPS は `run.json` から読み、時間軸を 0 から `n_frames - 1` に設定し、フレーム番号が `diagnostics.json` と一致します
- キャラクターは FBX のジオメトリ 1 つにつき 1 オブジェクトです（Y Bot は 2 つ：`skinned_mesh_0_Alpha_Surface` と `skinned_mesh_1_Alpha_Joints`）

### ステップ 9：写真モード

```bash
m2mr run --image assets/image/pose.jpg
```

写真 1 枚から静的 3D ポーズを復元し、動画とまったく同じリターゲット経路を通します。出力は `images/` 配下の 4 枚の画像（動画版と同じ視点）、加えて `before_after_360_compare.mp4` です：左に元写真、右に 10 度刻みの完全周回したキャラクター。

**`--video` と `--image` を同時に渡すことはできません。**

## 三、6 つの難題とその解法

この節が全文の核心です。動作移行は「A の関節角度を B のスケルトンに移植する」ように見えますが、実際にやると 6 つの独立した穴があります。

### 難題一：Mixamo スケルトンの静止ポーズをどう読むか

Mixamo の元 FBX は各ジョイントのバインド向きを `PreRotation` に符号化しています。しかし多くの人が Blender や Cinema 4D で開いて再書き出しすると、この情報が書き換えられたり、最悪失われます。

局所オイラー角で静止ポーズを再構築すると、得られる関節座標系は間違っており、**しかも階層が深くなるほど誤差が大きくなります**：静止ポーズが違い、スキニングが崩れ、アニメーションを一切付けなくても間違っています。

**このプロジェクトの解法は 3 段階優先のバインド行列復元です**：

1. FBX の `Pose` / `PoseNode.Matrix`（あればこれを使う）
2. Skin cluster の `TransformLink`（Pose 記録がない場合これを使う。複数メッシュが同じジョイントにつながっている場合は、残りの行列に最も近いものを選ぶ。回転行列は平均化できないため）
3. 局所変換プロパティ（どれも無いジョイントは通常末端骨）

作者は `docs/c4d-fbx-support.md` に検証データも貼っています：元の Mixamo FBX と Cinema 4D 書き出し版で、コアボーンはいずれも 25 本、rig 全体で 33 本、静止 FK 行列の最大誤差はそれぞれ `1.7e-14` と `3.2e-14`、静止スキニング誤差は `6.5e-14` cm と `2.0e-13` cm。

**しかも回帰はありません**：同じ `skeleton_motion.npz`（787 フレーム）で変更前後を Y Bot で走らせると、ボーンごとの回転の差は `4e-7` 以内（浮動小数点の精度）、Blender でのスキニング済み頂点位置の差は 0.5 マイクロメートルです。

### 難題二：リターゲティングの数学的骨格

プロジェクト全体のリターゲットコアは 1 行の式で、`kinematics.py` の冒頭にコメントとして書かれています：

```
M_local = T_bind * R_bind * R_anim
M_world = M_parent_world * M_local
```

要点は 3 つ：

**R_anim はバインド向きに対する増分**であり、絶対向きではありません。これがこのアーキテクチャの土台です。これがあれば、同じアニメーションを静止ポーズの異なるどんな rig にも乗せられます。

**Mixamo の静止ボーン長は決してスケールされません**。キャラクターの腕が長いままなら長いままで、アニメーションは向きだけを変え、比率は変えません。多くのツールが犯す誤り（人の体比率に合わせるためにボーン長をスケールする）で、一度スケールすると二度と戻せません。

**完全なバインド回転を使う FK**。あるライブラリでは `PreRotation` を別に保持していますが、このプロジェクトでは `MixamoBone` 上の互換エイリアスとして残すだけで、実際の計算は完全な局所バインド向きを通ります。

`retarget.py` には自己検査関数 `verify_rest_fk` もあります：`R_anim` が単位行列のとき、FK は FBX の静止ポーズを厳密に再現しなければならず、誤差が `1e-4` を超えたら即例外を投げます。**これは「バインド回転の合成を間違えた」という問題を、実行途中に現れる妙な動作ではなく、起動時に落ちるハードエラーに変えるものです。**

**Swing / Twist 分解**は標準的な手法です：各ボーンの回転を「どちらを向いているか」と「その向きのまわりにどれだけ回っているか」に分けます。プロジェクトでは `SWING_TARGETS`（ボーン → swing の決定にどの人体の関節方向ベクトルを使うか）、`AIM_CHILD`（ボーンの静止軸をどの子ボーンが決めるか）、`MIXAMO_TO_HUMAN`（Mixamo ボーン → SMPL ジョイントの対応付け）などの表を多数維持しています。

ここにあるコメントは特に読む価値があり、非常に具体的な罠を説明しています：

> Neck/Head は SMPL の neck→head 方向に沿って狙ってはいけない。そのベクトルは約 9 センチしかありません。首から頭蓋骨へのオフセットで、垂直方向と 50 から 70 度ずれます。それに沿って狙うと、Mixamo の著しく長い首骨と頭骨が暴れます。`spine3→head` が安定した上向き方向です（頭蓋骨は胸の上にあります）。同時に Human の head ジョイントは使い続けます。ジョイントの対応は neck→Neck、head→Head のまま変更しません。

**もう 1 つ**。Mixamo の Neck→Head と Head→HeadTop の静止平行移動は局所 +Y に沿っていません（前方への +Z オフセットを持ちます）。そのオフセットを狙うと首骨と頭骨が傾きます。そのため Neck/Head は局所 +Y を揺らすように変更されました。

このコメントの密度は、作者がこれらの具体的な問題に喰われてきたことを示しています。

### 難題三：足が床で滑る

これはすべての動作移行ツールの古典的な失敗です。足は床に固定されたままのはずなのに、リターゲットされたキャラクターの足が床の上を滑り回ります。

**このプロジェクトの解法は 2 層です。**

1 層目が**足ロッキング**（`foot_lock.py`）です。GVHMR は各フレームについて 4 つのジョイントの「静止信頼度」を予測します：左足踵、左足掌、右足踵、右足掌。踵と掌は**独立してロック**されるため、平らに踏む場合、つま先立ちの場合、踵で着地する場合の 3 通りそれぞれが、実際に地面に触れている部位を固定します。

信頼度の処理には**ヒステリシス**を使っています：接触に入るには 0.8 以上の信頼度が必要で、退出は 0.5 まで落ちれば十分です。`ENTER_CONF = 0.8`、`EXIT_CONF = 0.5`。この設計は臨界値付近で接触を on/off 往復させることを防ぎます。揺らぎ自体よりも、揺らぎから生じる動きのほうが悪いのです。0.1 秒より短い接触区間はそのまま捨てます。

各接触区間ではロック位置を**その区間の平均位置**に固定します。補正量は区間の両側に短いフェードアウトウィンドウを持ちます。これにより振っている脚がバウンドしません。

**掌が踵より優先されます**。コメントがその理由を説明しています：2 つのアンカーは異なる接触区間から来るもので、その間に剛的な足長の関係はありません。両方とも固定しようとすれば足がねじれます。そのため足掌と足踵の両方が接地している場合は足掌を固定します。足は元の世界向きを保つので、つま先立ちでも固定された足掌を中心に回転します。

続いて**解析的な 2 ボーン IK** です：`UpLeg` と `Leg` を足首の目標に解いて、膝は元の屈曲平面内に保ちます。**脚を伸ばしてもアンカーに届かない場合、胴体全体を平行移動**させ、接地しているすべての腰ジョイントが到達できるようにし、2 つの腰ジョイントはこの平行移動を共有します。**ここでは何も床に吸着させません**。接触中のドリフトを取り除くだけです。

2 層目が**接地補正**（`ground.py`）です。足ロッキングが固定するのは「足がいる位置」ですが、それはスケルトンのジョイントの高さであって床の高さではありません。キャラクターの足裏はボーンのジョイントより下にある距離があり、しかも復元された高さは 1 本の動画の中で漂うため、結果としてキャラクターが浮いたり地面にめり込んだりします。

解法は、**足裏 = その部位で最も低いスキニング済み頂点**（踵は `Foot`、足掌は `ToeBase` / `Toe_End`）です。着地フレーム上で腰を垂直に平行移動し、その最下頂点が `y = 0` に来るようにします。着地区間は自分の最下フレームのオフセット量を保つので、歩いている間に足は持ち上がっても沈み込みません。浮遊フレームは前の着地区間から次の着地区間へ滑らかに遷移し、**これによってジャンプの高さが保たれ、歩と歩の間の緩やかなドリフトも取り除かれます**。

2 つの工程の効果は `run.json` に記録されます：`foot_lock` と `ground` の 2 つのセクションです。

**詳細に注意**：たとえ `--no-foot-lock`（元のリターゲットを維持、足は滑る）を付けても、接地補正は**依然として実行されます**。接地とドリフト防止は別のものだからです。

### 難題四：2D ポーズ推定の左右反転

RTMPose / ViTPose は外見でフレームごとに左右を判断し、**メモリがありません**。画面の中の人物が体を回転した瞬間に、1 フレームでラベルを間違えると、全身が 3D の中で原地で 180 度回転してしまいます。

プロジェクトの `stabilize_kp2d.py` のコメントはこの仕組みを非常に明確に説明しています：

> 1 フレームの**向きの符号**は肩の `sign(x_left - x_right)` です（肩が重なったときは腰を使います）。2 つの事実がルールを動かします。
>
> - 本物の 180 度の回転は側面視を通り、そこで向きの符号が変わり、肩幅がほぼゼロになります（「狭い」フレーム）
> - ラベルの反転は孤立しています。わずかな数のフレームだけ符号が逆で、符号が一致するフレームに囲まれており、肩幅は満杯です

したがってルールは、**狭いフレームで動画をセグメントに区切り、各セグメント内で RTMPose のラベルの多数値を取る**、というものです。セグメント内で符号が逆の連続区間が約 0.33 秒より短ければ反転と判定して元に戻します。長く「速すぎて側面視が現れなかった」本物の回転として残します。

狭いフレームが 2 つの一致したセグメントの間にある場合は、その符号に強制的に割り当てます（側面視付近でも反転が起きうるため）。狭いフレームが 2 つの不一致なセグメントの間にある場合は、回転が進行中であることを意味するので、推定器のラベルを残します。

**このルールは顔を見ないので、帽子やマスクも影響しません**。しかもすべての判断は単一の転換フレームではなく区間全体に基づいており、**1 つの悪いフレームが動画全体を誤った状態にロックしてしまうことはありません**。

修正の記録は CHANGELOG にあり、数字が説得力があります：**素早い 0.5 秒の回転を含むダンスクリップで、方向の誤ったフレームが 642 フレーム中の 320 フレームから 3 フレームに減りました。**

また、既存のキャッシュを再実行するときは `vitpose_raw.pt` のバックアップから再安定化し、**直前のルールの出力を基点にはしません**。この細部は、作者が設計の段階で「ルールは反復する、历史的データが汚染されてはいけない」と考えていたことを示しています。

### 難題五：指のリターゲティング

`--detect-hands` を有効にすると、HaMeR が推定するのは MANO のジョイント回転です。そして MANO のジョイント回転は**親相対**で、**手モデル自身の座標系**で表されています（MANO は各静止フレームが単位行列だからです）。Mixamo の指骨のアニメーションチャンネルも親相対ですが、そのボーン**自身の静止座標系**で表されています。

したがって変換は**純粋な基底変換**になります：

```
R_anim[b] = D_bᵀ · (C · R_mano[j] · Cᵀ) · D_b
```

- `C`：MANO の手座標系 → Mixamo の Hand ボーンの静止座標系。2 つの静止ポーズの手部座標系（手首→中指1、人差し指1→小指1）から算出
- `D_b`：指骨 b の Hand 骨に対する静止世界回転

**この変換は最初から最後まで実測であり、手書きは一切ありません**。コメントに「左手なら X 軸を反転」みたいな記述はありません。

HaMeR は単一画像モデルなので、元の回転はフレームごとに揺れます。`load_hand_motion` は**有効度で重み付けした時間方向ガウシアン**で平滑化し、隣接フレームから短い検出の穴を補います。

### 難題六：結果が良いかどうかをどう知るか

これは私が最も過小評価され、しかも最も価値のある部分だと考えています。

**「見た目が正しいか」とは検査せず、完成したファイルそのものを検査します。**

`diagnose.py` は `mixamo_character.glb` を直接読み、**ファイル自身のスキニングウェイト**（線形ブレンドスキニング。どの glTF ビューアーとも同じ）で毎フレームを配置し、身体部位どうしの交差を検出します。

**要点は、検査対象が出力された GLB であり、メモリ上の中間状態ではないことです。** これはつまり、利用者が実際に手にするものを測っていることであり、書き出し工程で混入しうるあらゆる誤りを含んでいます。

設計上の詳細がいくつかあります：

- **関節でつながっている部位は比較しません**。上腕と前腕、胴体と大腿は、皮膚が関節箇所では元々重なったり混ざったりするため、どのポーズでも「交差」しています。`_ADJACENT` セットがこれを除外します。
- **自己交差だけを検査し、床は検査しません**。コメントは率直に書いています：床との接触には床の定義が必要ですが、このツールにはまだそれがありません。
- **フレーム番号は 0 始まり**で、Blender で glTF を読み込んだ後のタイムラインと一致します。
- **同じ部位の組で 3 フレーム以下の間隔の区間は 1 つにまとめます**。報告が断片で埋まるのを避けるためです。
- 深さのデフォルトしきい値は 1 cm で、`--threshold-cm` で調整できます。

そして `diagnostics.html` です。これは自己完結型の HTML レポートで、元動画とキャラクターを並べる、時間軸、クリック式の問題リスト、3D ビューは CDN から three.js を読み込みます。**床にはマーカーが固定されています**（0.5 メートルごとに十字、1 メートルごとに大きい十字、原点は緑）、これによりキャラクターが動いているのか静止しているか判断できます。

**この床のマーカーはコミュニティからの提供です**。CHANGELOG には X 上の @_____eddie_____ からの提案と、具体的なリンクが載っています。床のマーカーは HTML レポートと、Blender への取り込み時に追加される `Floor Markers` メッシュの両方に現れます。

そして**手動アノテーションのレーン**です：琥珀色のトラック、フレーム範囲をドラッグして問題を書き起こし、`m2mr-review-v1` の JSON として保存。ブラウザは localStorage に `m2mr-review-v1:<元glb>:<フレーム数>:<fps>` というキーで保存するので、**HTML を再生成してもアノテーションは失われません**。

**ソフトウェアの境界線がはっきりしています：機械が調べられるもの（自己交差）は機械が調べ、目で見ないと分からないもの（足の滑り、膝の跳ね）は人間が記録する。両者の担い手は異なり責務も異なりますが、納品物としては統合できます。**

## 四、まとめ：6 つのデザイン哲学

ここまで分解してきたものを俯瞰すると、常に息を貫く 6 つのデザイン哲学が抽出できます。それらは README に書かれたスローガンではなく、コードから読み取れるものです。

### 哲学一：単一の真実の源、座標系は一度的だけ定める

`tpose_calibration.py` の冒頭にはこう書いてあります：

> Mixamo Skeleton T-pose ↕ 一つのグローバル較正 ↔ character Rig rest T-pose
>
> T-pose の検査プログラムもアニメーションのリターゲットもこのモジュールを import するので、プロジェクト内には**ただ 1 つ**の Front / Right / Up の規約しかありません。

さらに鋭いのは後半です：

> **ここには一切の手動補正がありません**：解剖学的軸方向は骨位置から実測され、整列には `B_rig @ B_skel.T` が使われ、**極座標/SVD の行列式の補正も、ボーンごとの 90/180 度のパッチもありません**。

**「パッチに頼らない」という姿勢が、このプロジェクトの技術的品格の最適な注脚です。**

アニメーション移行のような問題では、「あるボーンに特別な処理を加える」ことが最も楽な道であり、同時にシステムを保守不能にする最も楽な道でもあります。このプロジェクトはその道を明確に拒否し、幾何学的実測から規約を導いています。

### 哲学二：エラーは起動時にクラッシュさせる、画面では異常にしない

`verify_rest_fk` は典型的な例です：単位アニメ回転は静止ポーズを厳密に再現しなければならず、誤差が `1e-4` を超えると即例外を投げます。

同じ考え方として `checks.py` の内容検査（ファイル名ではなく頂点数でモデル系統を識別する）、そして `run.json` に毎回記録される `rest_fk_error` と `rest_skin_error_cm` があります。

**検証はリリース前の最後の手作業工程ではなく、システムの一部です。** どの層にも自己検査があり、間違えたら即座に止まります。

### 哲学三：機械の判断と人の判断は分けるが、納品は統合する

`diagnostics.json` は機械が調べられるもの（自己交差、深さ、フレーム区間）を保存します。`m2mr-review-v1` は人間にしか見えないもの（足の滑り、手が届かない）を保存します。

前者は JSON で、プログラムが読みます。後者も JSON で、プログラムが読みますが、内容はレビュー担当者自身の言葉であり、**入力されたまま保存され、1 文字も変更されず、どの言語で書いてもどの言語で保存されます**。

そして両者を同じファイルに統合する目的は明確です：**このファイルを 1 回の修正タスクの完全な入力にする**ことです。AI や開発者が受け取れば、どのフレームを直すべきか、何を直すべきかが分かります。

### 哲学四：増分を優先し、絶対に上書きしない

前に触れましたが、単独で取り出す価値のある 1 本です。

- キャラクターを変えても抽出を再実行しない（`--skeleton`）
- 指を補っても身体を再実行しない（キャッシュが残っているとき）
- 修正はアノテーションしたフレーム区間だけに行い、**新しいディレクトリ**に書く
- 再安定化は直前のルール出力ではなく元のバックアップから計算する

**「新しいディレクトリ、既存を上書きしない」という約束によって、全体の手順は安全に何度も反復できます。** 修正が失敗しても、元の結果が残っています。

### 哲学五：失敗は報告するが、出力を止めない

自己交差の検査に失敗しても `m2mr run` は失敗**しません**。診断は情報であって、ゲートではありません。

これはとても成熟した判断です。開発者は自分の手を頭に入れてしまったことが**自分**の問題であり、ツールの問題ではないことを知っています。ツールは問題を定量化して渡すことで、判断権は本人に帰します。

**もしツールが「問題が検出された」という理由だけで結果を拒否して、ユーザーを修正に追い立てると、むしろ摩擦を増やすことになります。**

### 哲学六：ライセンスと制約を目立つ場所に書く

`NOTICE.md` は独立した文書として、各上流コンポーネントの条項を明確に列挙しています：

- **GVHMR**（SIGGRAPH Asia 2024）：非商用の研究用途限定
- **SMPL-X**：MPI の登録ゲート。商用は別途契約が必要
- **MANO**：MPI の登録ゲート
- **Mixamo FBX**：製品とともに配布可。ただし素材パックとして再配布は不可
- **YOLOv8**（Ultralytics）：**AGPL-3.0**
- 各ポーズおよび HMR のチェックポイント：それぞれの研究ライセンス

結論はとても率直です：

> 上流コンポーネントの制約により、**エンドツーエンドの pipeline は実質的に非商用/研究用途に制限されます**。このリポジトリ自身のライセンスが何かとは関係ありません。

README にも同じ段落が繰り返されています。ユーザーガイドではさらに直接的に、**Motion2MixamoRig は非商用利用のみ**と書かれています。

**作者は「コードが Apache-2.0 である」という事実で、チェーン全体の実際の制約を覆い隠すようにしませんでした。** これはオープンソースプロジェクトでは珍しい誠実さです。

## 五、このプロジェクトをどう見るか

いくつかの自分の判断を述べます。

### 本物の痛点を選んだ

Mixamo キャラクターは Adobe が無料で全用户提供しているスケルトンアセットです。Blender や Unity のユーザーにとってキャラクターに困ることはほとんどなく、困る其一は**動作**です。モーションキャプチャ機器や外注は 1 件数千人民元から数万元人民元で、「歩きやダンスの動きが 1 つだけ欲しい」というニーズは、これまで基本的に低コストの解法がありませんでした。

このプロジェクトはコストを「5 GB の重みのダウンロード + 十分程度の待ち時間」まで圧縮しました。**独立ゲーム開発者、アニメーション学習者、ツール開発者にとって、これは 0 から 1 のステップです。**

### 技術的な重みはモデルではなく幾何にある

GVHMR で人体動作を抽出するこのステップは、他にもできます。**本当に難しいのはその先の一連の幾何とキネマティクスの問題**です：バインド向きをどう読むか、静止ポーズをどう検証するか、足をどう固定するか、接地をどう補正するか、左右をどう安定化するか、指先の座標系をどう変換するか。

これらの作業のどの一つも「モデルを走らせる」だけでは解けず、**座標系とキネマティクスを理解して初めて書けるもの**です。**10742 行のコードの中で、実際にモデルを呼んでいる部分は小さく、大部分は幾何です。**

### ドキュメントの密度が異常に高い

コードコメントには「なぜこうで、ああではない」という具体的な推論が詰まっていて、「回転行列を計算する」みたいな空っぽな文言ではありません。上で引用したように、たとえば「そのベクトルは約 9 センチしかなく、首から頭蓋骨へのオフセットで、垂直方向と 50 から 70 度ずれます」は、まさに 1 つのバグの起点を説明しています。

AI エージェントも開発に参加できるようにしたプロジェクト（`AGENTS.md` は AI 向けです）にとって、このコメントの品質は AI が正しく直せるかどうかを直接決定します。

### コミュニティの意見の吸収が速い

床のマーカーは X 上の特定の人物からのもので、修正するとすぐ CHANGELOG に署名付きでリンクが添えられます。Cinema 4D の FBX 対応も PR #8 からのもので、同様に署名されています。

**まだ 0.1.x 段階にあるプロジェクトにしては、反復の密度もフィードバックのループもかなり成熟しています。**

### 冷水を注ぐ

**第 1 に、今は実験段階です。** README の冒頭には `Motion2MixamoRig is currently experimental` と書かれており、**現時点でテスト済みのプラットフォームは macOS Apple Silicon のみ**で、Windows と Linux は未テスト、プラグインも macos-arm64 の 1 プラットフォーム分の zip しかありません。

**第 2 に、非商用の制約は硬いものです。** 前に述べましたが、もう一度強調する価値があります：**このプロジェクトで作ったアニメーション資産を商用できるかどうかは GVHMR と SMPL-X の条項によって決まるのであって、このリポジトリが Apache-2.0 かどうかでは決まりません。** 商用を検討するチームは自分で契約を取りに行く必要があります。

**第 3 に、性能の上限は単眼動画そのもので制約されます。** 一視点では遮蔽された手足、誤った深度推定は、いずれも情報量の欠落であってアルゴリズムで補えるものではありません。歩行やダンスのような明確な動作が主戦場であり、複数人のインタラクション、大きな遮蔽、物を手に持つといったシーンでは、README の「1 人で、頭から足先まで常に画面内」という条件が、最初から参加を戒める意味です。

**第 4 に、CPU 上では非常に遅いです。** 30 秒クリップに 3 から 5 分。この規模なら個人利用は許容範囲ですが、バッチ生産には重すぎます。GPU があればずっと速くなりますが、README の時間データはすべて CPU 環境のものです。

### 最後の観察

このプロジェクトの CHANGELOG とドキュメントを隅々まで読んだ私が最も感動したのは、いかなる技術的細部でもなく、**「何が調べられ、何が調べられないか」という境界線への誠実さ**でした。

自己交差を調べるのは、自己交差が幾何判定でき、その結果をセンチメートルに量化できるからです。足の滑りを調べないのは、足の滑りには意図と地面の理解が必要だからです。地面接触には定義された床が必要だが、このツールにはまだそれがないと明示的に書いています。検出されためり込みを実行の失敗にしないのは、それが利用者の問題だからです。

**これは自分の境界を知っていて、しかも越境のふりをしない打算を持つプロジェクトです。**

最初の話に戻ります：ちょうどアニメーション作業が待っている Mixamo キャラクターがあるなら、このリポジトリは一読の価値があります。
