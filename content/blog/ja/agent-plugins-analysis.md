# Agent Plugins 徹底解説：Amazon・Cursor・Microsoft・OpenAI・Vercel が共同策定した AI エージェントプラグインの可搬標準

> 核心思想：**Agent Plugins は、再利用可能なコンポーネントを可搬プラグインにパッケージングするための、オープンでベンダーニュートラルな標準（v1.0.0）である。** これは現実の断片化問題を解決する：AI エージェントの各クライアントは、同じ中身のコンポーネントを積んでいても独自のプラグイン形式を発明しており、作者はクライアントごとにコンポーネントを組み替えたり複製したりしなければならない。Agent Plugins はすべてを統一しようとはしない。定義するのは「相互運用性の最小公約数」だけだ——共有コンポーネントは 1 つの予測可能な構造を使い、配布・インストール・権限・ユーザー体験・クライアント固有の機能は各クライアントの管理下に残る。Amazon、Cursor、Microsoft、OpenAI、Vercel のコアメンテナーからなる**技術運営委員会（TSC）**が推進するこの標準は、「可搬性」と「クライアントの自律性」を同時に仕様へ書き込んでいる：ディレクトリ＝パッケージ、ルート直下の `plugin.json` を唯一の適合フロアに、`skills/` と `mcp.json` を固定コンポーネント位置に、リバースドメイン名前空間をクライアント拡張の出口に。10 の明確な設計判断が同じ問いに答える：**最小の仕様面積で、最大のエコシステム相互運用性をどう買うか。**

---

## 1. プロジェクト概要

### 1.1 それは何か？

**Agent Plugins** は、再利用可能なコンポーネントを AI エージェントを拡張する可搬プラグインにパッケージングするための**オープンでベンダーニュートラルな標準**である。その **v1.0.0 仕様**は、ちょうど 2 種類のコンポーネントタイプに統一された共有形式を定義する：

- **Agent Skills**（`https://agentskills.io/specification` が定義するスキル形式）
- **MCP servers**（`https://modelcontextprotocol.io/specification` が定義する Model Context Protocol サーバー）

互換クライアント（AI エージェントツール、開発ツール）は、これらのプラグインを一貫して発見・ロードできる。

### 1.2 主要データ

- 公式サイト：`https://agent-plugins.org`
- 仕様リポジトリ：`https://github.com/agentplugins/agent-plugins-spec`
- 仕様バージョン：**1.0.0**（ステータス：Working Draft）
- ライセンス：**Apache-2.0**（仕様テキスト＋付随ドキュメントは Apache-2.0 / CC-BY-4.0 の二本立て）
- 初期 TSC コアメンテナー：**Amazon、Cursor、Microsoft、OpenAI、Vercel**
- ガバナンス：コミュニティ主導のオープン仕様プロジェクト。役割は**企業ではなく個人**が保持し、単一ベンダーがコアメンテナー過半数を支配することはできない
- 成果物：仕様テキスト（`spec/1.0.0.md`）、プラグインマニフェスト JSON Schema、MCP 設定 JSON Schema、適合性チェックリスト
- 付随ドキュメント：`plugin-authors`（作者ガイド）、`client-implementers`（クライアント実装ガイド）、`schemas`（機械可読 Schema）、`llms.txt` / `sitemap.md`（ドキュメント索引）

### 1.3 何を解決するのか？

**問題：プラグイン形式の断片化。** AI エージェントクライアント（Claude Code、Cursor、OpenAI 系ツール、各種エージェントフレームワーク…）は、同じ中身のコンポーネントを含んでいても各自が独自のプラグイン形式を定義している。結果として、クライアント A 向けにパッケージングしたプラグインは、クライアント B が使う前に改造が必要になることが多く、作者はクライアントごとにコンポーネントを組み替え・複製し続けなければならない。

**答え：相互運用性フロアを定義する。** Agent Plugins は、クライアント間で可搬な部分だけを標準化する——共有コンポーネントは 1 つの予測可能な構造を使う——一方、配布・インストール・権限・ユーザー体験・更新・クライアント固有の機能は各クライアントの管理下に残る。仕様は意図的に規定しない：インストール元・レジストリ・マーケットプレイス、有効化/更新/キャッシュの UX、権限プロンプト・信頼ポリシー・サンドボックス、スキルをユーザーやモデルにどう見せるか、クライアント拡張の内部動作。

## 2. 核心思想

### 2.1 相互運用性の最小公約数

Agent Plugins の設計は「大統一」ではない——可搬な部分の**共有形式だけ**を明確に標準化する。仕様はこう述べている：

> Agent Plugins defines a small interoperability floor for the parts that can be portable across clients.（Agent Plugins は、クライアント間で可搬な部分のために小さな相互運用性フロアを定義する。）

これは繊細な境界線だ：**標準化されるのは「パッケージング」であって「ランタイム」ではない。** プラグインがどう発見・インストール・実行・提示・認可されるかは、引き続き各クライアントが決める。標準が保証するのは「同じパッケージを、互換クライアントなら誰でも理解できる」ことだけだ。

### 2.2 ディレクトリ＝パッケージ

Agent Plugin は**ディレクトリ**である——zip でも、レジストリから取得するバンドルでもない：

```text
my-plugin/
├── plugin.json          # 必須：マニフェスト。プラグインと対象仕様バージョンを識別
├── skills/              # 任意：Agent Skills の固定位置
│   └── summarize/
│       ├── SKILL.md
│       ├── scripts/
│       └── references/
├── mcp.json             # 任意：MCP サーバー設定
└── com.example.client/  # 任意：クライアント拡張ディレクトリ（リバースドメイン）
```

パッケージ単位としてディレクトリを選ぶことには 4 つの直接的な利点がある：**標準ツールで検査できる**（`ls`、`cat`、`git`）、**開発中にその場で編集できる**、**特別なツールなしでバージョン管理できる**、**発見の間接層がない**。

### 2.3 2 つの固定コンポーネント位置

v1 はちょうど 2 種類のコンポーネントタイプを定義し、それぞれに固定位置がある：

- **Skills** → `skills/`：`SKILL.md` を含む各直接子ディレクトリが 1 つのスキル（深い階層の再帰検索はしない）
- **MCP servers** → `mcp.json`：ルート直下の JSON 設定ファイル

固定位置が重要な理由：`plugin.json` はこれらを上書きできず、コンポーネント設定をインライン化もできない——**発見ルールはすべてのクライアントで同一**であり、クライアントは代替ソースや優先順位のロジックを実装する必要がない。

### 2.4 オープン開発と公開ガバナンス

- 提案と技術的意思決定は**公開**され、より広いエコシステムの参加が開かれている
- 新機能や実質的な変更のアイデアは**GitHub Discussions** から始まり、提案は「具体的な可搬性ニーズ＋実装者の支持」を立証しなければならない
- 技術憲章（Technical Charter）はパッケージ形式とは別に定義され、役割は**個人**が保持し、企業の座席ではなく、単一ベンダーがコアメンテナー過半数を支配できない

## 3. 設計哲学

仕様末尾の **Design Decisions** 付録は、このプロジェクトの設計哲学を理解する最良の入り口だ——なぜその選択をしたのかを 1 つずつ説明している。核心は以下の 10 項目：

### 3.1 なぜアーカイブ形式ではなくディレクトリベースの発見なのか？

`zip`/`tar.gz` やレジストリバンドルは検査に特別なツールが必要だ。ディレクトリなら `ls`/`cat`/`git` で検査でき、開発中にその場で編集でき、特別なツールなしでバージョン管理できる。**固定のルート直下位置**（`skills/`、`mcp.json`）は、発見の間接層・代替ソースの優先順位・マニフェスト設定——各クライアントが本来実装しなければならない複雑さ——を排除する。

### 3.2 なぜ v1 は Agent Skills と MCP だけなのか？

この 2 つは**プロジェクト外部に成熟した仕様がすでにあり**（agentskills.io、modelcontextprotocol.io）、意味のあるクロスクライアント採用もあるからだ。他の提案コンポーネントタイプ——commands、hooks、agents、rules、LSP servers——は、安定した可搬契約を作るにはまだクライアント固有すぎるため、**形式が収束するまで v1 には入らない**。これは「最小のエンドツーエンドを先に出す」という古典的なエンジニアリング原則だ：合意のある 2 タイプを先に標準化し、不確実性は未来に残す。

### 3.3 なぜルート直下の `plugin.json` が適合フロアなのか？

適合するすべてのクライアントは、プラグインルートの `plugin.json` を**必ず**チェックしなければならない。これによりプラグイン作者には、**すべてのクライアントにわたって存在が保証される単一のマニフェスト**が与えられる——作者はクライアント固有のパス知識を一切持つ必要がない。

### 3.4 なぜ可搬マニフェストは閉じた Schema なのか？

ルート直下の `plugin.json` は正確に 10 個のトップレベルフィールドだけを許可する：`$schema`、`name`、`version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords`、`extensions`。閉じた Schema は**厳密な検証・タイプミス検出・Schema 駆動のキー補完**を可能にする。クライアントの実験的フィールドは任意のトップレベルフィールドを占有できず、`extensions` のリバースドメインキーに収められる。未知のトップレベルフィールドは Schema 違反のままだが、クライアントはプラグイン全体を拒否する代わりに**報告して無視する**——未来に余地を残す寛容さだ。

### 3.5 なぜクライアント拡張にリバースドメインなのか？

リバースドメイン識別子は、中央のクライアント名レジストリを必要としない**非中央集権的な衝突回避の慣習**を提供する。同じ識別子をマニフェストデータ（`extensions` キー）とクライアント固有ディレクトリ（トップレベルディレクトリ名）の両方に使え、どちらの表現も独立して存在できる。拡張ディレクトリはトップレベルに保たれ、プラグインのレイアウトをフラットで慣習駆動に保つ。

### 3.6 なぜ明示的な MCP 設定形式なのか？

既存クライアントは互換性のない MCP 設定形状を使い、トランスポートの推論方法も異なる。Agent Plugins は、どのクライアントネイティブ形式からも独立した意味を持つ**明示的な閉じたユニオン**を定義する。Streamable HTTP と旧 HTTP+SSE を区別することで、各エントリに**曖昧さのない初期トランスポート**が与えられ、接続失敗後のフォールバック動作は可搬形式の外に置かれる。

### 3.7 なぜクライアントは標準 MCP トランスポートを 1 つだけサポートすればよいのか？

Stdio と Streamable HTTP は異なるデプロイ・セキュリティモデルに役立つ。MCP 対応クライアントすべてにローカルプロセス実行とリモート HTTP 接続の両方を要求すると、可搬設定形式を変えずに**実装面と信頼面を拡大**することになる。各サーバーエントリが自身のトランスポートを宣言するため、クライアントは未サポートのエントリをスキップしつつ、独立したサーバーとコンポーネントのロードを続けられる。

### 3.8 なぜ Schema は仕様バージョンと共有するのか？

`plugin.json` と `mcp.json` の Schema は、独立したバージョン系列ではなく Agent Plugins 仕様バージョンを使う。これにより作者とクライアントは**1 つ**の可搬形式バージョンを理解すればよく、混合バージョンのパッケージを防ぎ、`$schema` が完全な検証・解釈契約——JSON Schema では表現できない要件も含む——を選択できる。仕様リリースのたびに未変更の Schema を再公開するのは、3 つの独立した互換性タイムラインを晒すよりはるかに小さな保守コストだ。

### 3.9 なぜ設定の相対パスではなくプラグイン変数なのか？

MCP サーバーの引数は実行時に絶対パスを必要とすることが多い。`${PLUGIN_ROOT}` は、バンドルファイルのための曖昧さのないクライアント解決**アンカー**を提供する。`${PLUGIN_DATA}` は、更新時にパッケージ内容が置き換わっても永続する、クライアント管理の**書き込み可能な状態ディレクトリ**を識別する。`command` フィールドは補間を使わない：`./` パスはプラグインルートに対して直接解決され、裸の名前はプラットフォームの実行ファイル検索規則を使う。**`command` を 1 つのトークンとして扱う**ことで、クライアントがユーザー作成のシェルコマンド文字列を解析・エスケープする必要がなくなる。クライアントは継承環境と `PATH` 動作が異なるため、Agent Plugins は設定された環境上書きを標準化するが、裸コマンド検索はクライアント定義のままにする——プラグイン相対コマンドが決定的なバンドル実行を提供する。

### 3.10 なぜコンポーネント障害は致命的でないのか？

MCP サーバーが起動・接続に失敗しても、クライアントはプラグインの残りのコンポーネントの**ロードを続ける**。スキルと MCP サーバーの両方を提供するプラグインは、1 つのサーバーが利用不能になっただけで全体が使えなくなるべきではない。仕様は非致命的なコンポーネント障害を**診断要件**と組み合わせ、障害が沈黙ではなく可視になるようにしている。

## 4. 詳細チュートリアル

### 4.1 最小プラグインの作成（hello-plugin）

最も小さく有用なプラグインは、ディレクトリ＋1 つのスキルで、3 ステップ：

```text
hello-plugin/
├── plugin.json
└── skills/
    └── greet/
        └── SKILL.md
```

**Step 1：`plugin.json` を作成**

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "hello-plugin"
}
```

**Step 2：スキル `skills/greet/SKILL.md` を作成**

```markdown
---
name: greet
description: Greet the user and offer help.
---

Greet the user and offer help.
```

**Step 3：ロード**

スキル対応クライアントは `plugin.json` を読み、`skills/` の直接子ディレクトリをスキャンし、各 `SKILL.md` を Agent Skills 仕様に照らして検証する。MCP サーバーを追加するには、同じ Agent Plugins Schema バージョンで `mcp.json` をプラグインルートに置く。

> 完全なマニフェストと実際のスキルを持つコピー可能なパッケージはこちら：`https://github.com/agentplugins/agent-plugins-example`

### 4.2 完全なマニフェストフィールド

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "plugin-name",
  "version": "1.2.0",
  "description": "Brief plugin description",
  "author": {
    "name": "Author Name",
    "email": "author@example.com",
    "url": "https://example.com"
  },
  "homepage": "https://docs.example.com/plugin",
  "repository": "https://github.com/example/plugin",
  "license": "MIT",
  "keywords": ["keyword1", "keyword2"],
  "extensions": {
    "com.example.client": {
      "setting": true
    }
  }
}
```

要点：

- **必須フィールドは 2 つだけ**：`$schema`（対象仕様バージョン識別子）と `name`（人間可読なプラグイン名）。欠落・型エラー・空 → クライアントはプラグインを拒否し、いかなるコンポーネントも発見・実行してはならない
- `version` はセマンティックバージョニング（SemVer）が推奨され、更新チェックとキャッシュの鮮度に使われる
- `author` オブジェクトは `name`/`email`/`url` の 3 フィールドのみ許可
- 明示的な制約以外では、メタデータフィールドは JSON 型でのみ検証される——`version` が正しい SemVer でない、URL/メールが認識されない、`license` が SPDX 識別子でない、という理由だけでプラグインを拒否してはならない
- 未知のトップレベルフィールド → 報告して無視し、ロードを継続（非致命的）

### 4.3 プラグイン名の制約

`name` は次のすべてを満たさなければならない：

- 長さ **1〜64 文字**（両端含む）
- 文字セットは**小文字英数字、`-`、`.`** のみ
- **先頭と末尾は英数字**でなければならない
- **連続する `--` や `..` は不可**（単一の `.` は可、例：`acme.tools`）

有効：`my-plugin`、`acme.tools`、`lint3r`、`a`
無効：`My-Plugin`（大文字）、`-start`（先頭ハイフン）、`has--double`（連続ハイフン）、`too.many..dots`（連続ピリオド）、空文字列

### 4.4 Agent Skills のパッケージ化

- 固定位置 `skills/`。`SKILL.md` を含む**直接子ディレクトリ**ごとに 1 つのスキルと数える。深い階層の**再帰検索はしない**
- スキル自体は Agent Skills 仕様（`SKILL.md` 形式、frontmatter、`scripts/`/`references/`/`assets/` レイアウト）に準拠しなければならない
- 準拠しないスキル → **そのスキルをスキップ**し、他のスキルのロードを継続（無効なスキルは報告することが推奨される）

```text
skills/
└── deploy/
    ├── SKILL.md          # name: deploy
    ├── scripts/
    │   └── rollback.sh
    └── references/
        └── runbook.md
```

### 4.5 MCP サーバーの設定（mcp.json）

`mcp.json` は JSON オブジェクトで、トップレベルフィールドは `$schema` と `mcpServers` のちょうど 2 つでなければならない。各サーバーエントリは `type` フィールドを含み、以下の閉じた変種のいずれか 1 つに正確に一致しなければならない：

**stdio（ローカルプロセス）**

```json
{
  "type": "stdio",
  "command": "./bin/validator",
  "args": ["--data", "${PLUGIN_DATA}/validator"],
  "env": {
    "CONFIG": "${PLUGIN_ROOT}/config.json"
  },
  "cwd": "${PLUGIN_ROOT}"
}
```

要点：

- `command` は**単一の実行可能トークン**（裸の名前、または `./` で始まるプラグイン相対パス）でなければならず、シェルコマンド文字列ではない。`command` でのプレースホルダー展開はしない
- `cwd` を省略した場合、プラグインルートがサブプロセスの作業ディレクトリになる。`cwd` はプラグイン相対パス、`${PLUGIN_ROOT}` 始まり、`${PLUGIN_DATA}` 始まりの 3 形式のみ許可
- `args`/`env`/`cwd` は `${PLUGIN_ROOT}` と `${PLUGIN_DATA}` の展開をサポートする

**Streamable HTTP（リモート）**

```json
{
  "type": "streamable-http",
  "url": "https://deploy.example.com/mcp",
  "headers": {
    "X-Tenant": "public-tenant"
  }
}
```

**旧 HTTP+SSE（非推奨）**

```json
{
  "type": "sse",
  "url": "https://legacy.example.com/sse"
}
```

リモートの要点：

- `url` はユーザー情報やフラグメントを含まない絶対 HTTP/HTTPS URL でなければならない。非ループバックエンドポイントは**HTTPS 必須**
- ヘッダー名は大文字小文字を区別しない。大文字小文字だけが異なる同名の重複エントリは無効
- **ヘッダー値は可視のパッケージデータであり、機密メカニズムではない**——ヘッダーに認証情報を埋め込んではならない。v1 は OAuth 設定や可搬の資格情報参照フィールドを定義しない。認可の発見・ユーザー操作・資格情報の保存はクライアント管理

**トランスポートサポート要件**：MCP 対応クライアントは `stdio` と `streamable-http` の少なくとも 1 つをサポートしなければならない（両方のサポートが推奨される）。`sse` は任意。クライアントは初期接続試行で `type` が宣言するトランスポートを使わなければならず、その試行が失敗した場合のフォールバック動作は Agent Plugins では定義されない。

### 4.6 プラグイン変数：PLUGIN_ROOT と PLUGIN_DATA

プラグインサブプロセスを起動するクライアントは、各サブプロセスに 2 つの環境変数を**必ず**提供しなければならない：

- `PLUGIN_ROOT`：ファイルシステム解決後のプラグインルートの絶対パス——プラグインに**同梱される**スクリプト・バイナリ・設定ファイルの参照に使う
- `PLUGIN_DATA`：クライアント管理の永続データディレクトリの絶対パス——`node_modules`、仮想環境、生成コード、キャッシュなど、**更新をまたいで永続すべき**状態に使う（クライアントは起動前に作成し、書き込み可能にし、更新をまたいで保持しなければならない。アンインストール時に削除してよい）

展開ルール：

- 展開は**単一・非再帰**のテキスト置換であり、置換で導入されたテキストはさらなるプレースホルダーをスキャンされない
- 展開は `args` の各文字列要素、`env` の各文字列値、`cwd` 文字列に適用される。`env` キー、`command`、固定コンポーネント位置には**適用されない**
- 認識されないプレースホルダー風テキストはリテラルのまま残る。クライアントは他のプレースホルダー/環境変数展開を行ってはならない
- サーバーの `env` オブジェクトは `PLUGIN_ROOT` や `PLUGIN_DATA` という名前のエントリを**含んではならない**（予約変数はクライアントが供給する。違反するとそのサーバーエントリは無効になる）
- `env` 値も可視のパッケージデータであり、認証情報を埋め込んではならない

### 4.7 適合クライアントの実装

**ロードシーケンス（クライアント視点）**：

1. ファイルシステム解決後のプラグインルートを確立する
2. `$schema` が選択するローカルサポート Schema を使ってルート `plugin.json` を特定し検証する
3. 致命的なマニフェスト違反ではプラグインを拒否する。明示的に非致命的なケースは報告して無視する
4. サポートする各コンポーネントタイプを固定位置から発見する
5. 各コンポーネントタイプ/エントリに定義された失敗境界を適用する
6. 実装したクライアント拡張名前空間を適用し、他はすべて無視する

**最小クライアント要件**（適合性の要点）：

- ディレクトリパスからプラグインをロードできる
- 閉じた `plugin.json` Schema を検証し、未実装の `extensions` メンバーは値の内容を検証せずに無視する
- サポートする各コンポーネントタイプを固定位置で発見する
- MCP をサポートする場合：`stdio` と `streamable-http` の少なくとも 1 つをサポートし、`PLUGIN_ROOT`/`PLUGIN_DATA` を提供して実行時設定値で展開する
- `command` を単一の実行可能トークンとして解決し、プラグインルートをデフォルトの作業ディレクトリにする
- **少なくとも 1 つのコンポーネントタイプ**（スキルか MCP）をサポートする——段階的採用は明示的に許されている：スキルのみのクライアントでも適合できる

**失敗分離**：未知のコンポーネントタイプ → 無視。1 つのコンポーネントに隔離された失敗は、独立して有効なコンポーネントのロードを妨げてはならない。失敗は報告することが推奨されるが、コンポーネントタイプ・トランスポート・拡張をサポートしていないこと自体はエラーではない。

## 5. 論点のまとめ（視点と結論）

1. **断片化は、今日の AI エージェントエコシステム最大の相互運用性コストである。** 各クライアントが独自のプラグイン形式を持ち、作者は繰り返し再パッケージングを強いられる。Agent Plugins の判断：ランタイムを統一するより、**パッケージング契約**を統一する——それが最も低コストで、最も広い合意が得られる標準化の入り口だ。

2. **「大統一」ではなく「相互運用性フロア」こそ正しい野心だ。** 仕様は意図的に配布・インストール・権限・UX・サンドボックス・クライアント拡張を各ベンダーに委ねる。この自制こそが、Amazon、Cursor、Microsoft、OpenAI、Vercel という競合他社を同じテーブルに着かせた——誰も自社ランタイムを完全に明け渡したくないからだ。

3. **合意のある 2 タイプを先に標準化する。** v1 が Agent Skills と MCP だけをカバーするのは、成熟した外部仕様があるからだ。commands、hooks、agents、LSP servers などはまだ収束途上——「形式が収束してから v1 に入れる」は、時期尚早な標準化を防ぐ教科書的な防御だ。

4. **閉じた Schema＋寛容な処理は、未来に余地を残す知恵だ。** 未知のトップレベルフィールドは非致命的（報告して無視）で、クライアントの実験はリバースドメインの `extensions` に収められる——可搬契約の厳密性を守りつつ、エコシステムが名前空間内で自由に実験できるようにする。

5. **セキュリティは設計に組み込まれるものであって、スローガンではない。** プラグインパスはプラグインルート内に留めなければならず（`../` エスケープを拒否）、`command` はシェル解釈されず、ヘッダー/env は明示的に「機密メカニズムではない」とされ、非ループバックエンドポイントは HTTPS のみ、OAuth は明示的にクライアントに委ねられる——すべてのルールが攻撃面を縮小する。

6. **失敗分離がプラグインエコシステムをより堅牢にする。** 1 つの MCP サーバーが落ちても、プラグイン全体を落とすべきではない。非致命的なコンポーネント障害＋診断報告要件が、「部分可用」をデフォルトの姿勢にする。

7. **段階的採用こそが標準普及の鍵だ。** クライアントはスキルのみ、MCP のみ、あるいは 1 つのトランスポートのみをサポートできる——標準は段階的採用の明確な適合パスを残し、参入障壁を劇的に下げる。

8. **ガバナンスの設計が標準の信頼性を決める。** 企業の座席ではなく個人が役割を持ち、単一ベンダーが過半数を持たず、TSC 会議は公開され、提案は GitHub Discussions から始まる——これらの条項が、競合他社からなる標準組織に長期信頼の基盤を与える。
