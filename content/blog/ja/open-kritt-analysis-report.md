# open·kritt 深度解析：AI エージェントを編成して実際のコード脆弱性を発見する

> 核心理念：**open·kritt は複雑なセキュリティ監査を小さな集中タスクに分解し、複数の AI エージェントを並行実行し、構造化ワークフローで重複削除済み、ランク付け済み、検証済みのセキュリティ発見を出力するオープンソース AI セキュリティ研究プラットフォームです。** コードベース全体を AI モデルに投入して「脆弱性を探せ」と指示する粗いアプローチとは異なり、open·kritt はタスク分解と集中分析を重視します——エージェントに小さくて明確なタスク（例：「あるファイルの特定の関数を分析する」）を割り当てることは、コードベース全体をスキャンさせるよりもはるかに効果的です。この理念は実際のセキュリティ研究から来ています：Kritt チームはバグ報奨金ハンター名 **Blockian** のもとで **150 万ドル以上**を獲得しており、open·kritt は社内ツールのオープンソース版です。

---

## 1. プロジェクト概要

### 1.1 什么是 open·kritt？

**open·kritt** は**オープンソースで自己ホスト型の AI セキュリティ研究プラットフォーム**であり、AI エージェントを編成して実際のコード脆弱性を発見します。核心理念は、大きなモデルをコードベース全体に向けて「脆弱性を探せ」と指示する代わりに、研究を**小さく明確に定義されたタスク**に分解し、複数の AI エージェントを並行実行し、結果を検証可能でランク付け可能な発見として統合することです。

プラットフォームは Kritt チームによって開発され、チームメンバー Harel Rom（@harel-coffee）と Gabriel Balko（@GabiCtrlZ）が共同所有しメンテナンスしています。プラットフォームは **AGPL-3.0** オープンソースライセンスを使用しています。

### 1.2 主要データ

- GitHub リポジトリ：`https://github.com/Kritt-ai/open-kritt`
- 公式サイト：`https://kritt.ai`
- ドキュメント：`https://docs.kritt.ai`
- ライセンス：**AGPL-3.0**
- 技術スタック：フロントエンド（React/Vite）+ バックエンド（Express/Prisma/PostgreSQL）+ エンジン（Python/Codex または Claude Code）+ Docker
- CLI ツール：`./kritt`（リポジトリ組み込み、インストール不要）

### 1.3 プロジェクト構造

```
open-kritt/
├── backend/           # Express + Prisma REST API
├── frontend/          # React/Vite UI
├── engine/            # スキャン実行エンジン（Python）
├── docs-site/         # Mintlify ドキュメントサイト
├── database/          # PostgreSQL 初期化
├── scripts/           # CLI スクリプト
├── kritt              # リポジトリ組み込み CLI ツール
└── docs/              # セキュリティ脅威モデルなどのドキュメント
```

## 2. コア機能

### 2.1 ワークフロー

ワークフローは**再可能なブルーガーデン**です——エンジンが深度順に実行し、各ステップの出力を次のステップに供給するプロンプトステップのツリー構造です。

**主要な特性：**
- **ステップ（Steps）**：各ステップはプロンプト + 期待される JSON 出力形式
- **深度（Depth）**：ステップは深度別に整理され、深度 0 はエントリーポイント、深度が深いほどタスクが具体的
- **マルチ出力（Multi-output）**：1 つのステップが複数の結果を生成し、次の深度の並行タスクに供給
- **構造化出力**：各ステップは出力形式（string/number/boolean/array/object）を宣言し、すべてのキーはグローバルに一意

### 2.2 スキャン

スキャンはワークフローをターゲットコードベースに適用する実行ユニットです：
- **リモートリポジトリ**（GitHub owner/repo + commit_sha）と**ローカルリポジトリ**をサポート
- 依存リポジトリ設定をサポート
- `repo_scope` によるスキャン範囲限定をサポート
- 累積分析のための繰り返し実行（`repeat_runs`）をサポート

### 2.3 ポストスクリプト

ポストスクリプトは**各発見専用の後処理ステップ**であり、ワークフロー完了、重複削除、ランク付け後に実行されます：
- 発見の検証
- 概念実証（PoC）の構築
- レポートの作成
- 格付け、タグなどのメタデータの追加

### 2.4 重要度ランカー

重要度ランカーは**Markdown ルール**であり、モデルに発見の優先順位付け方法を指示します。これらはカスタマイズ可能で、ターゲットプロジェクトの脆弱性分類標準に適応できます。

## 3. 核心理念と設計哲学

### 3.1 タスク分解哲学：小さく集中したタスク > 大きく曖昧なタスク

open·kritt の核心理念からの重要な洞察：**「AI をコードベース全体に向けて『脆弱性を探せ』と指示すると、通常は見つかりません。しかし、AI を特定のファイルの特定の関数に向け集中した質問すると、きっと見つけてくれます。」**

この理念は open·kritt のすべてのアーキテクチャ決定の基礎です：

1. **ワークフロー分解**：複雑なセキュリティ監査を深度递增のステップツリーに分解
2. **並行実行**：各深度で複数のタスクを並行実行し、コンテキストウィンドウを最大限活用
3. **コンテキスト効率**：エージェントのコンテキストウィンドウは実際の分析作業に使用され、巨大なコードベースのナビゲートではない

### 3.2 組み込みワークフロー

open·kritt には 2 つの実用ワークフローがプレインストールされています：

#### 外部フロー分析（External Flow Analysis）

これはチュートリアル例ではなく、チームが実際の研究で使用したワークフローです。外部制御入力を生産エントリーポイントから具体的なセキュリティ敏感動作まで追跡します：

1. **エントリーポイントの列挙**：コードベースをスキャンし、外部から到達可能なエントリーポイントと攻撃者制御入力を処理するハンドラを特定
2. **到達可能フローの追跡**：各エントリーポイントに対して、検証結果、認可境界、状態変更、外部呼び出し、敏感シンクを含む実質的に異なる生産パスを列挙
3. **各フローの調査**：各下流エージェントに 1 つの到達可能フローを検証させます。サポートされる攻撃者パスを持つ具体的な脆弱性、または無発見スタブのみを返します

> この分解戦略はコンテキストを節約します：エントリーポイントとフローは一度だけマッピングされ、各最終エージェントは 1 つの具体パスにコンテキストウィンドウを費やします。

#### Cosmos ABCI Panic Halt Review

Go ベースの Cosmos アプリケーション向けで、生産 ABCI パスでの panic がコンセンサスを停止させる可能性があります：
1. **ABCI メソッドの列挙**：哪些 ABCI メソッドとフェーズハンドラが生産アプリケーションに接続されているかを証明
2. **panic クラスの調査**：各到達可能メソッドに対して 4 つの集中レビューを扇出——明示的 panic、算術 panic、nil ポインタ panic、境界または型 panic

### 3.3 発見 schema の強制性

最深ステップ（ターミナルステップ）は固定の**発見 schema**を出力する必要があり、すべての発見が一貫して比較可能であることを保証します：
- `explanation`、`file_path`、`line`、`malicious_input_example`、`summary`
- `trigger_flow`、`vulnerability_type`、`malicious_actor`
- オプションの `exploitable`

この必須制約は、すべての発見が統一的に処理、重複削除、ランク付けできることを保証します。

### 3.4 自己ホスト優先

open·kritt は**自己ホスト**をデフォルトかつ推奨される展開方法として明確に選択しています：
- ユーザーは自分のインフラストラクチャ、データ、認証情報を所有
- Codex ログイン（推奨）、OpenAI API Key、Anthropic API Key、OpenRouter をサポート
- バックエンドにはデフォルトでアプリケーションレベル認証が含まれておらず、ユーザーがネットワーク層で追加する必要があります

## 4. 詳細なインストールと設定のチュートリアル

### 4.1 前提条件

- Git
- Docker Desktop または Docker Engine + Docker Compose プラグイン
- Node.js 20 以上（CLI 用のみ）
- モデルアクセス認証情報（Codex ログイン推奨、または API Key）

### 4.2 クイックインストール

```bash
# 1. リポジトリをクローン
git clone https://github.com/Kritt-ai/open-kritt && cd open-kritt

# 2. 対話型 CLI 設定を実行
./kritt

# 3. フルスタックを起動
./kritt start
```

起動後、http://localhost:5173 にアクセスしてフロントエンド UI を開きます。

### 4.3 モデルアクセス設定

| オプション | 説明 |
|-----------|------|
| **Codex ログイン**（推奨） | 対象となる ChatGPT/Codex サブスクリプションへのアクセスをガイド付きデバイスフローで使用 |
| `OPENAI_API_KEY` | OpenAI Platform API Key + Codex ハーネスを使用 |
| `ANTHROPIC_API_KEY` | Claude Code + Anthropic API 請求を使用 |
| `OPENROUTER_API_KEY` | OpenRouter を介して互換性モデルをルーティング |

`GITHUB_TOKEN` はオプションであり、プライベート GitHub リポジトリまたはその依存関係をクローンする必要がある場合にのみ必要です。

### 4.4 手動 Docker 設定

```bash
# 環境変数テンプレートをコピー
cp .env.example .env
chmod 600 .env

# .env に 1 つの Provider 認証情報を設定：
# OPENAI_API_KEY, CODEX_API_KEY, ANTHROPIC_API_KEY, または OPENROUTER_API_KEY

# 必要なディレクトリを作成
mkdir -p .data/codex
chmod 700 .data/codex

# 起動
docker compose up --build
```

### 4.5 サンプルデータをロード

```bash
docker compose exec backend npm run seed
```

サンプルデータは附加的で幂等であり、既存のデータを保持します。

## 5. 最初のスキャン完全チュートリアル

### 5.1 ワークフローを作成

1. **Workflows → New workflow** を開く
2. **Blank workflow** を選択し、名前を付けて説明を追加
3. ステップを追加：

**深度 0 - 列挙（Entry Point）**
- 名前：`Enumerate Entrypoints`
- 内容：このコードベース内のすべての外部から到達可能なエントリーポイント（HTTP ルート、API エンドポイント、ユーザー入力処理関数）を識別
- 出力形式：`endpoints` (array)
- **Multi-output** をチェック

**深度 1 - 分析（Analysis）**
- 名前：`Analyze Endpoint`
- 内容：エントリーポイント `{{endpoint}}` を分析し、可能性のある注入点、データフロー、セキュリティ敏感操作を特定
- 出力形式：`findings` (array)、各発見は `vulnerability_type`、`file_path`、`line` などを含む
- 深度 0 のキーを参照：`{{endpoint}}`

**深度 2 - ターミナル（Terminal）**
- 名前：`Document Finding`
- 内容：発見された脆弱性を詳細に記録し、攻撃パスと概念実証を提供
- 出力形式：すべての必須の発見 schema キーを含む必要がある

### 5.2 ポストスクリプトを作成

1. **Post-scripts → New post-script** を開く
2. **Blank post-script** を選択
3. 内容の例：

```
発見 "{{summary}}" - {{file_path}}:{{line}} にある {{vulnerability_type}} を評価。

戻り値：
- severity (string): CRITICAL, HIGH, MEDIUM, または LOW
- confidence (string): HIGH, MEDIUM, または LOW
- recommendation (string): 修正推奨
```

### 5.3 重要度ランカーを作成

1. **Severity Rankers → New ranker** を開く
2. 脆弱性タイプとコンテキストが重要度レベルにマッピングされる方法を定義する Markdown ルールを書く

### 5.4 スキャンを実行

1. **Scans → New scan** を開く
2. ワークフローを選択
3. ターゲットを設定：リモート（GitHub owner/repo）またはローカル
4. モデル、プロバイダー、ハーネスを選択
5. ポストスクリプトとランカーを添付
6. 提出して起動

### 5.5 結果を表示

スキャン完了後、任意の發現を開いて完全レポート、概念実証、ポストスクリプト出力を表示。

## 6. セキュリティモデルと脅威分析

### 6.1 信頼境界

| コンポーネント | 役割 | 信頼レベル |
|---------------|------|-----------|
| フロントエンド | UI（React/Vite） | オペレーター面向 |
| バックエンド | REST API + Postgres（Express/Prisma） | オペレーター面向、**デフォルトで認証なし** |
| データベース | PostgreSQL — ワークフロー、スキャン、発見 | 信頼されたストア |
| エンジン | スキャンを要求、リポジトリをチェックアウト、ハーネスを実行 | **信頼できないコードとプロンプトを分析** |
| executor-view | 読み取り専用ビュー | オペレーター面向 |

### 6.2 主要な脅威と緩和策

#### 1. 信頼できないコードとプロンプトインジェクション

エンジンは攻撃者によって制御されるコード分析し、リポジトリにはエージェントを操作するように設計されたコンテンツ（プロンプトインジェクション）が含まれている場合があります。

**緩和策：**
- ツール有効ジョブは各自捨て可能なコンテナで実行
- コンテナは書き込み可能なジョブごとチェックアウトディレクトリとコピーされたジョブホームを持つ
- ジョブは Docker ソケット、データベース、プロジェクト `.env`、他のジョブをマウントしない
- ハーネス出力は schema 制約の JSON
- 草稿生成呼び出しはモデルツール、ユーザー規則/設定、セッション永続化を無効化

#### 2. シークレットの漏洩

侵害/注入されたエージェントは認証情報を読み取ったりデータを送信したりしようとする可能性があります。

**緩和策：**
- `.env` と provider ログイン/認証情報ストア（両方とも gitignored）にシークレットを保存
- **範囲が狭く、短期間**の `GITHUB_TOKEN` を優先使用（読み取り専用、必要なリポジトリのみ）
- プロバイダーキーを定期的にローテーション
- スキャンランナーは**デフォルトで直接アウトバウンドインターネットアクセス**を持つ（エージェントの研究、ツールインストール、依存関係取得のため）

#### 3. モデルプロバイダーへのデータ流出

スキャンはデフォルトでコードを外部エンドポイントに送信します。

**緩和策：**
- 機密コードをスキャンする前にデータの行き先を理解
- データの處理方式がコードの機密性と一致するモデルエンドポイントを選択
- プロバイダーのデータ保持条項をレビュー

#### 4. API 認証なし露出

`/api/*` は**デフォルトで認証がありません**。

**緩和策：**
- パブリックインターフェースにバインドしない
- 自分の認証/授權プロキシをバックエンド API と UI の前に配置
- プロキシ層で認証、ネットワーク制御、レート制限を適用

### 6.3 安全な展開チェックリスト

- [ ] 完全スタックを**専用の VM または Docker ホスト**で実行
- [ ] 直接インターネットアクセスがポリシー適合しない場合、ホストレベル出口制御を追加
- [ ] バックエンド API と UI の前に**認証を配置**
- [ ] **最小、短期間**の `GITHUB_TOKEN` を使用；プロバイダーキーをローテーション
- [ ] **データ處理**がコードの機密性と一致するモデルエンドポイントを選択
- [ ] `.env` と `.data/` 認証情報ストアを私有に保つ；決してコミットしない

## 7. 主要な洞察と結論

### 7.1 核心理念

**洞察 1：タスク分解は AI セキュリティ研究の鍵**

open·kritt にとって最も重要な洞察は、複雑なセキュリティ監査を小さくて集中したタスクに分解することは、大きなモデルで whole の問題を解決しようとするよりもはるかに効果的だということです。これは人間のセキュリティ研究者の実際の仕事方法々と一致しています——専門家は同時に whole のコードベースを审视せず、特定のエントリーポイント、データフロー、関数に集中します。

**洞察 2：構造化出力は発見の質を強制する**

すべてのターミナルステップに固定の発見 schema（必須キーを含む）を出力させることは、すべての発見が統一的に処理、重複削除、ランク付けできることを保証します。これは AI 出力品質管理の重要な実践です。

**洞察 3：自己ホストは信頼の基礎**

自己ホストをデフォルトの展開として選択することは、コードセキュリティの深い理解を反映しています——ユーザーは自分のデータ、認証情報、インフラストラクチャを制御する必要があります。これは欠落している機能ではなく、意識的な設計上の決定です。

**洞察 4：実際のバグ報奨金経験が製品設計を推進**

open·kritt は理論的なプロジェクトではありません。それは実際のセキュリティ研究から来ており、チームメンバーは Blockian のもとで 150 万ドル以上のバグ報奨金を獲得しています。組み込みワークフローはチュートリアル例ではなく、実際のセキュリティ研究の実践を反映しています。

**洞察 5：セキュリティと機能性のバランス**

open·kritt の設計はセキュリティと機能性のバランスを取っています——エージェントはツールをインストールしターゲットを研究するためにインターネットアクセスを必要としますが、プラットフォームは分離と監視メカニズムを提供します。これは信頼できないコードを扱うための実用的な必要性です。

### 7.2 ユースケース

- **セキュリティ研究者**：プロンプト、データ、モデルの制御を放弃せずに AI を研究プロセスに統合
- **セキュリティ指向開発者**：安全なコードの作成と監査のための AI 支援を受ける
- **バグ報奨金ハンター**：脆弱性発見ワークフローを体系化して効率を向上
- **セキュリティチーム**：内部コードベースの継続的なセキュリティ監査を実施

### 7.3 制限事項

- デフォルトでアプリケーションレベル認証がない；ユーザーが自分で追加する必要がある
- 外部モデルプロバイダーに依存；データ流出リスクが存在
- Docker インフラストラクチャが必要；一部のユーザーには複雑さが増す可能性
- 信頼できないコードのスキャンには専用の分離環境が必要

### 7.4 結論

open·kritt は AI エージェント編足をセキュリティ研究に適用する成熟したプラットフォームです。その核の価値は：

1. **タスク分解方法論**：複雑な監査を管理可能な集中タスクに変換
2. **実世界検証**：実際のバグ報奨金経験得来
3. **自己ホスト制御**：ユーザーはデータとインフラストラクチャを所有
4. **構造化発見出力**：検証可能、ランク付け可能、アクション可能な結果

コードセキュリティを真剣に入手するチームと個人にとって、open·kritt は実用的で原則的なソリューションを提供します。その設計哲学——集中したタスク分解、構造化出力、自己ホスト制御——は AI 支援セキュリティ研究のベストプラクティスを表しています。
