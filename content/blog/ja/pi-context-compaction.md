## はじめに

AI支援コーディングの分野において、コンテキストウィンドウの制限は開発者を困扰してきた主要な課題の一つです。LLMで長いコーディングセッションを行う場合、会話履歴が常に増加し、最終的にモデルの処理能力を超えてしまい、リクエストが拒否したりコンテキストが切り詰められたりします。Piコーディングアシスタントは**Compaction（圧縮）メカニズム**を導入することで、この問題にエレガントに対応しました。

本稿では、Piコーディングアシスタントのコンテキスト圧縮メカニズムを詳細に解析し、その設計哲学、コアアルゴリズム、ベストプラクティスについて探求します。

## 問題の背景

### LLMのコンテキストウィンドウ制限

最新の大規模言語モデル（LLM）は、限定的なコンテキストウィンドウを持っています。Claudeシリーズモデルを例にとると、コンテキストウィンドウは32Kから200Kトークンです。これは以下のことを意味します：

- モデルが1回のリクエストで処理できるトークン数は固定されている
- コーディングセッションの進行とともに、会話履歴が蓄積される
- 履歴がコンテキスト制限を超えると、LLMはリクエストを拒否するか、早期のコンテキストを失う

### 長いセッションの課題

実際のソフトウェア開発では、コーディングセッションは数時間甚至は数日にわたる必要があります。開発者は：

- 同じファイルを複数回修正する
- アーキテクチャ設計と実装の詳細を議論する
- 以前の技術的決定を振り返る
- 複雑なデバッグシナリオに対処する

これらの要件は、限定的なコンテキストウィンドウと鋭い矛盾を形成しています。

## コア設計哲学

Piコーディングアシスタントのコンテキスト圧縮メカニズムは、**重要な情報を保持し、冗長な内容を圧縮する**というコアコンセプトに基づいています。

### レイヤードメモリ戦略

Piはコンテキストを処理するためにレイヤードメモリ戦略を採用しています：

1. **最近の会話**：最近のメッセージを完全に保持し、コンテキストの連続性を維持
2. **初期の会話**：要約圧縮を通じて、コア情報を保持しながらトークン消費を削減
3. **ツール結果**：常に完全に保持，它们与ツール呼び出し密に結びついているため

### 切り詰めではなく要約

単純なコンテキスト切り詰めとは異なり、Piは履歴メッセージを圧縮するために**構造化要約**を使用します。このアプローチは：

- 会話のセマンティックな完全性を保持する
- セッションをまたいで完全なコンテキストを復元できる
- 複数のモデル間での移植性をサポートする

## Compaction圧縮メカニズムの詳細

### 動作原理

Compaction圧縮メカニズムは以下のステップで動作します：

```
┌─────────────────────────────────────────────────────────────┐
│                    圧縮トリガー条件                          │
│  contextTokens > contextWindow - reserveTokens              │
│  デフォルトreserveTokens: 16,384                            │
│  デフォルトkeepRecentTokens: 20,000                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ステップ1: 分割点を見つける                                  │
│  最新メッセージから後方に歩き、keepRecentTokens（デフォルト   │
│  20k）に達するまで続ける                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ステップ2: メッセージを抽出                                  │
│  前の境界から分割点までのメッセージを収集                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ステップ3: 要約を生成                                        │
│  LLMを呼び出して構造化形式の要約を生成                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ステップ4: エントリを追加                                    │
│  要約とメタデータを含むCompactionEntryを保存                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ステップ5: コンテキストを再構成                              │
│  要約 + 最近のメッセージを使用して次のリクエストに備える        │
└─────────────────────────────────────────────────────────────┘
```

### 分割点ルール

有効な分割点には以下が含まれます：

| メッセージタイプ | 分割可能 | 説明 |
|---------------|---------|------|
| ユーザーメッセージ | ✓ | ユーザーからの自然言語入力 |
| アシスタントメッセージ | ✓ | LLMの応答内容 |
| BashExecutionメッセージ | ✓ | コマンド実行結果 |
| カスタムメッセージ | ✓ | 拡張カスタムメッセージ |
| ツール結果 | ✗ | 常にツール呼び出しと一緒に保持される |

### 要約形式

Piが生成する要約には、以下の構造化フィールドが含まれます：

```json
{
  "目標": "プロジェクトのコア目標または現在のタスク",
  "制約と好み": "技術的制約、コードスタイルの好みなど",
  "進捗": {
    "完了済み": ["完了したマイルストーン1", "完了したマイルストーン2"],
    "進行中": "現在進行中の作業",
    "ブロック済み": "遇到したブロック問題"
  },
  "主要な決定": "行われた重要な技術的決定とその理由",
  "次のステップ": "次の作業計画",
  "重要なコンテキスト": "覚えておくべき重要な情報",
  "ファイル追跡": ["file1.py:変更内容", "file2.js:変更内容"]
}
```

### トリガーメソッド

Compaction圧縮には2つのトリガーメソッドがあります：

#### 1. 自動トリガー

以下の条件が満たされたときに自動的にトリガーされます：

```
contextTokens > contextWindow - reserveTokens
```

ここで：
- `contextWindow`：モデルのコンテキストウィンドウサイズ
- `reserveTokens`：予約済みトークンバッファ（デフォルト16,384）

#### 2. 手動トリガー

ユーザーは`/compact`コマンドでcompressionを手動でトリガーできます：

```
/compact
```

これは、大量の新しい会話を行うことを知っている場合に便利です。

## 2つの要約メカニズムの比較

Piコーディングアシスタントは、2つの補完的な要約メカニズムを実装しています：

| 機能 | Compaction圧縮 | Branch要約 |
|------|---------------|-----------|
| **トリガータイミング** | コンテキストがしきい値を超えるか/compactコマンド | /treeナビゲーションでトリガー |
| **目的** | 分岐の切り替え時にコンテキストを保持 | コンテキストオーバーフローを防止 |
| **ユースケース** | 長いセッションでの継続的なコーディング | 分岐切り替え時のコンテキスト保存 |

### Compaction圧縮

- **自動トリガー**：contextTokensがcontextWindow制限に近づいたとき
- **手動トリガー**：ユーザーが積極的に`/compact`を呼び出す
- **保持内容**：最近の20Kトークンの完全な履歴 + 早期履歴の要約

### Branch要約

- **トリガータイミング**：`/tree`コマンドで異なる分支に移動したとき
- **目的**：分支の切り替えがコンテキ스트を失わないようにする
- **保持内容**：切り替え前の分支の完全な要約

## 設定とチューニング

### 基本的な設定

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

### パラメータの説明

| パラメータ | デフォルト値 | 説明 |
|----------|------------|------|
| `enabled` | true | 圧縮メカニズムを有効にするかどうか |
| `reserveTokens` | 16384 | 圧縮トリガー前のトークンバッファ |
| `keepRecentTokens` | 20000 | 保持する最近のトークン数（5-20会話ターン） |

### チューニングの提案

1. **keepRecentTokensの増加**：より多くの最近の会話の完全コンテキストを保持する必要がある場合
2. **reserveTokensの削減**：コンテキストウィンドウが大きいモデルでは、予約を減らすことができる
3. **トークン使用の監視**：ログを通じて圧縮トリガーの頻度を観察し、パラメータを調整する

## 拡張メカニズム

Piの圧縮メカニズムはイベントを介した拡張をサポートし、カスタムの要約ロジックを可能にします。

### イベントタイプ

#### session_before_compact

自動圧縮または`/compact`の前でトリガーされ、以下を許可します：

- カスタム要約内容
- 追加のコンテキスト情報の追加
- デフォルトの圧縮プロセスのスキップ

#### session_before_tree

`/tree`ナビゲーションの前でトリガーされ、以下を許可します：

- 分岐切り替えのための特別な要約の準備
- 分岐固有のコンテキスト情報の保存

### カスタム要約の例

```python
# session_before_compactイベントで要約をカスタマイズ
def on_session_before_compact(session_context):
    # カスタムコンテキスト情報を追加
    session_context.add_metadata("build_status", "passing")
    session_context.add_metadata("test_coverage", "85%")
    return session_context
```

## 使用例とベストプラクティス

### 例1：長いセッション開発

```bash
# 新しいコーディングセッションを開始
$ pi "ユーザー認証モジュールの実装を助けてください"

# 複数回の会話を実施
$ pi "パスワードリセット機能を追加"
$ pi "二要素認証を実装"
$ pi "OAuth2ログインを追加"

# コンテキストが制限に近づくと、Piは自動的に圧縮
# [Pi] コンテキスト圧縮が自動的にトリガーされ、セッション要約が生成されました

# コーディングを継続、コンテキストは完全に保持
$ pi "次にセッション管理を追加"
```

### 例2：手動トリガー圧縮

```bash
# 大量の新しい会話を行う前に手動でトリガー
$ pi "次にデータアクセス層全体をリファクタリングします"
$ /compact

# [Pi] コンテキストが圧縮され、重要な情報が保持されました
# 新しいリファクタリング作業を開始
$ pi "すべてのSQLクエリをORMを使用するように変更"
```

### 例3：Branch要約

```bash
# 分岐間を切り替え時にコンテキストを保持
$ pi "feature/payment分岐で作業しています"
$ /tree feature/payment

# [Pi] 現在の分岐の要約が生成されました

# 別の分岐に切り替え
$ /tree feature/refactor

# [Pi] feature/payment分岐からの要約を読み込み、作業 продолжитьことができます
```

### ベストプラクティス

1. **定期的な手動圧縮**：大規模なりファクタリングの前には手動で`/compact`をトリガーする
2. **分割点に注意**：どの内容が保持され、どの内容が圧縮されるかを理解する
3. **トークン使用の監視**：ログ内のトークン使用状況を关注する
4. **拡張イベントのを活用**：`session_before_compact`でプロジェクト固有のコンテキストを追加する
5. **要約の可読性**：セッションをまたいだ理解のため、要約形式を清晰に保つ

## 主要なポイントまとめ

### コアバリュー

1. **コンテキスト制限の突破**：インテリジェントな圧縮により無制限のコーディングセッションを実現
2. **コンテキストの連続性の維持**：要約が重要な情報を保持し、セッションの継続をサポート
3. **モデル間移植性**：プレーンテキスト要約形式が異なるモデル間で汎用であることを確保

### 技術の亮点

1. **レイヤードメモリ戦略**：最近の会話を完全に保持し、初期の会話を構造的に要約
2. **インテリジェントな分割点**：メッセージタイプベースのインテリジェントな分割でセマンティックな完全性を確保
3. **自動と手動の組み合わせ**：異なる使用シナリオのニーズに適応
4. **イベント拡張メカニズム**：高度なカスタム要約ロジックをサポート

### 適用シナリオ

- 長時間開発セッション
- 歴史的決定の振り返りが必要な複雑なプロジェクト
- 複数分岐並行開発シナリオ
- 異なるセッション間でコンテキストの連続性を維持する必要があるプロジェクト

## 結論

Piコーディングアシスタントのコンテキスト圧縮メカニズムは、LLMコンテキストウィンドウ制限を解決するエレガントなソリューションです。最新の会話を完全に保持し、初期の会話を構造的に要約することで、重要な情報を失うことなくコンテキスト制限を超えないという目標を達成しています。

このメカニズムはコーディング効率を向上させるだけでなく、AI支援プログラミングの発展に新たなアイデアを提供します。LLMのコンテキストウィンドウが不断扩大するにつれて、圧縮メカニズムも進化し続け、開発者によりスムーズなコーディング体験を提供します。
