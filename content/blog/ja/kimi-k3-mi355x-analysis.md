# Kimi K3 × AMD MI355X 徹底解説：メモリは堀（モート）なのか？

> 核心理念：**メモリは堀（モート）である。** オープンソースモデルが膨張し続けるなか——GLM-5.2 の 753B、DeepSeek V4-Pro の 1.6T、そして Kimi K3 の 2.8T パラメータへ——推論の臨界ボトルネックはもはや計算能力ではなく、「モデル重み + KV キャッシュ」を誰が VRAM に収められるかである。AMD MI355X は 288GB の HBM 容量と B300 の約 2.4 倍安い価格で、2.8T モデルという規模において初めて、NVIDIA に対する優位を**測定可能で、実用的で、定量化可能**な現実へと変えた。

## 一、プロジェクト概要

### 1.1 これはどんな記事か？

これは **Wafer AI**（YC S25 出身の AI 推論最適化スタートアップ）による技術ブログ記事『Is memory the moat?』（メモリは堀なのか？）で、著者は Ian Ye、公開日は 2026 年 7 月 31 日。チームが **8 枚の AMD MI355X 上で、オープンソースモデル Kimi K3（2.8T パラメータ）を 952 token/s/ノード のスループットで稼働**させ、NVIDIA の B200・B300 と厳密なスループット・コスト比較を行った記録です。

これは単なる「モデルを動かせた」証明ではなく、三つの力の交差点です：

1. **月の暗面（Moonshot AI）**——前例のない巨大サイズのオープンソースモデルを公開；
2. **AMD**——CUDA エコシステムを迂回しても、ROCm がフロンティアモデルを本番レベルで稼働できることを証明；
3. **Wafer AI**——自社開発のエージェント最適化能力で、MI355X の価格性能比を限界まで引き出した。

### 1.2 三つの主人公：モデル、GPU、プラットフォーム

**主人公その 1：Kimi K3（2.8T パラメータのスパース MoE オープンソースモデル）**

Kimi K3 は月の暗面が公開したスパース混合専門家（MoE）モデル。総パラメータは 2.8 兆ですが、各トークンで活性化されるのは約 1040 億のみ。オープンソースの**新時代の幕開け**を宣言しています——能力がトップのクローズドモデルに迫るだけでなく、「オープンなモデルはどこまで大きくできるか」の天井を 3T 級に引き上げたからです。

- 総パラメータ：**2.8T**
- 活性化パラメータ：**約 104B（1040 億）/トークン**
- コンテキスト長：**1M トークン**（1,048,576）
- アーキテクチャ：MoE + 長文脈アテンション最適化
- オープンソース形態：完全な重みを公開

**主人公その 2：AMD MI355X（288GB メモリの CDNA アクセラレータ）**

MI355X は AMD Instinct シリーズのアクセラレータで、CDNA 4 アーキテクチャ（GFX 9）ベース。1 枚あたり **288GB の HBM3**、約 **8 TB/s** のメモリ帯域幅を持ちます。「メモリが足りない」超大規模モデルにとって、この容量こそが最大のセールスポイントです。

- メモリ：**288GB HBM3**
- 発表：2025 年 6 月
- 位置づけ：Blackwell（B200/B300）の**非 NVIDIA 代替**

**主人公その 3：Wafer AI（推論最適化スタートアップ）**

Wafer AI は Y Combinator S25 バッチのスタートアップで、「AI エージェントによる GPU 推論カーネルの自動最適化」を特徴とする serverless 推論サービスを提供。Qwen、GLM、DeepSeek、Kimi などのオープンモデルに OpenAI 互換の推論 API を提供し、哲学は「1 ワットあたりの知能を最大化する」（Maximize intelligence per watt）。この記事はその証明となるブログです。

### 1.3 なぜこの記事に注目すべきか

CUDA/NVIDIA が 10 年以上支配してきた領域において、「中国のオープンソース 2.8T モデル + AMD GPU + 推論最適化スタートアップ」の組み合わせは、「CUDA の堀は揺るがない」というコンセンサスへの最も鋭い挑戦のひとつです。さらに貴重なのは、この記事が**空虚なマーケティング論ではなく、数字・根本原因分析・修正コードを備えた第一級のエンジニアリング記録**であることです。

## 二、核心理念：メモリは堀

### 2.1 見落とされがちな変数：モデルは「太り」続けている

記事冒頭は、進行中のトレンドを指摘します：**モデルの能力は上がっているが、サイズはさらに速く上がっている。**

- GLM-5.2 は **753B**（0.75T）パラメータ；
- DeepSeek V4-Pro は **1.6T** パラメータ；
- Kimi K3 は一気に **2.8T** パラメータへ。

パラメータが増えるほど、デプロイは高価で困難になります。Kimi K3 を稼働させるには **1.5TB 超の VRAM** が必要です——これは 1M トークンの KV キャッシュを確保する前の話です。

### 2.2 Kimi K3 を稼働させる数少ない道

Kimi K3 をデータセンターで動かすには、事業者には現実的な選択肢が三つしかありません：

- **8 枚構成の B300 ノード**：1 枚あたり 288GB、収まるが非常に高価；
- **8 枚×2（計 16 枚）の B200 ノード**：TP16 に分割するが、ノード間通信のペナルティを背負う；
- **8 枚構成の MI355X ノード**：こちらも 1 枚あたり 288GB、収まり、しかもはるかに安価。

注目すべきは、B300 のほかに、**非 NVIDIA かつ 288GB を持つ唯一の GPU が AMD MI355X である**こと。これが記事タイトルの核心です——**モデルが「ノードをまたぐ必要がある」ほど大きくなったとき、メモリ容量そのものが障壁になる。**

この論理では、MI355X は「性能王」ではなく「**収容能力王**」です。

### 2.3 MI355X の B200 に対する「容量圧倒」

- **8×MI355X ノード** 1 台で約 **2.3TB** の VRAM を提供し、TP8 の単一ノードで Kimi K3（重み + 1M トークン KV キャッシュ）を収容可能；
- **8×B200 ノード** 1 台は約 **1.5TB** のみで収まらず、**TP16 の 2 ノード構成**への拡張を余儀なくされる。

この「収まらない」部分が B200 の弱点を露呈させます：**ノード間通信オーバーヘッド**。B200 はデコードのクリティカルパス上でノード間 all-reduce（RoCE v2、約 195 Gb/s）を実行する必要があり、MI355X は単一ノードで完結します。

> Wafer の表現は鋭い：「ノード間ペナルティは B200 唯一の構成上の弱点だが——**まさにそこが論点だ**：MI355X の VRAM 容量優位は、Kimi K3 という規模で初めて、測定可能で実践的な利益に転化した。」

### 2.4 数字で語る：MI355X vs B200 vs B300

1,024 トークン入力 / 400 トークン出力のベンチマークで、「ノードあたり」で測定した比較（価格は公開 GPU 市場レート）は以下の通り：

- **単一ストリーム・デコード**：MI355X **118 tok/s**、B200 90 tok/s、B300 172 tok/s
- **ピーク総スループット / ノード**：MI355X **952 tok/s**、B200 約 249 tok/s（16 枚合計 498 を 2 ノードに按分）、B300 1,568 tok/s
- **ピーク総スループット / 単一 GPU**：MI355X **119 tok/s**、B200 31 tok/s、B300 196 tok/s
- **$/GPU-hr あたりのピーク（性能対価格比）**：MI355X **48 tok/s/$**、B200 7 tok/s/$、B300 33 tok/s/$

> **結論：**「総スループット」では B300 が依然 MI355X を約 1.65 倍リード。しかし「1 ドルあたりのスループット」では、MI355X（48）が B300（33）を約 1.45 倍、B200（7）を約 **7 倍**引き離します。性能対価格比の王者は疑いなく MI355X です。

参考公開価格：MI355X 約 **$2.50/GPU-hr**、B300 約 **$6.00**、B200 約 **$4.25**。

## 三、技術アーキテクチャと実践：MI355X で Kimi K3 を動かす

### 3.1 朗報：Day-0 サポート

Wafer は多くの人が見落とす前提を指摘します：Kimi K3 は AMD で **Day-0 サポート**——重み公開当日から ROCm 上で動作します。これは AMD と月の暗面の深い協力関係（Kimi 2.6 時代に UMBP、KV キャッシュスケジューリング、AITER 長文脈アクセラレータを共同設計）に由来します。つまり Wafer の仕事は「動かせるか」ではなく「スループットをどう絞り出すか」でした。

### 3.2 投機的デコード（Speculative Decoding）

- Kimi K3 は**ドラフトテンソルを持たない**（MTP なし、EAGLE なし）；
- 唯一の有効経路は**外部ブロック拡散ドラフト**：RadixArk の **Kimi-K3-DSpark**；
- CUDA ではそのまま動くが、ROCm では最初のバグに遭遇：

```text
NameError: name 'top_k_renorm_prob' is not defined.
```

### 3.3 バグ修正：カーネル不足ではなく定義不足

これは記事全体で最も見応えのあるエンジニアリングの再検証です。Wafer の調査プロセス：

- sglang の accept-sampling 検証器には、ターゲット分布を構築する 2 つの経路があります：
  - **dense 経路**：`top_k_renorm_prob` を呼び出す；
  - **sparse 高速経路**：`torch.topk` を直接使用。
- CUDA ビルドは `sgl_kernel` から `top_k_renorm_prob` をインポートしますが、**ROCm ビルドは top-p カーネルの別名のみを用意し、`top_k_renorm_prob` を未定義のまま残しています**——gfx950 には別名を張れる top-k renorm カーネルが存在しないためです。
- その結果、リクエストが dense 経路に落ちると、検証器が `NameError` を投げ、スケジューラ全体を巻き添えにクラッシュします。

**修正**：top-k renorm は小さな演算です——モデルの確率ベクトルから上位 k 個を残し、残りをゼロにし、合計が 1 になるよう再スケールするだけ。`sort` と `masked_fill` と割り算、それだけです。Wafer はこれを sglang の ROCm サンプリング分岐に差し込むだけで、CUDA ビルドが `sgl_kernel` から得るのと同じ計算を再現しました。カスタムカーネルは不要です。

> 重要な教訓：**ROCm でエラーに遭遇したとき、最初に思い浮かぶのは「カスタムカーネルが必要だ」だが、多くの場合は「定義が一つ欠けているだけ」である。** 今回は未定義の関数名が原因——問題は「カーネルがない」のではなく「どこかでエクスポートされていない」ことでした。

**最適化効果**（投機的デコード修正・強化後）：

- 単一ストリーム・スループット **約 2.2 倍**；
- 中負荷時のストリームあたり **約 1.7 倍**；
- ピーク総スループット **+18%**；
- さらに重要なのは、ピーク総スループットが**より高い並行度**（投機なしの c24 ではなく c64）で達成されたこと——実運用に近い状態です。

### 3.4 Prefill 最適化：decode tok/s は「愚か者の金」

記事の最も鋭い指摘：**decode tok/s はしばしば「愚か者の金（fool's gold）」——過度に美化され、ユーザーが実際に待つ最初のトークンまでの時間（TTFT）は軽視されている。**

**ベースライン**：同じ 172k トークンのコールド prefill で、MI355X は約 **51 秒**、B300 は約 **23 秒**。1M コンテキストのモデルでは、多くのワークロードが巨大な（時にコールドの）prefill を持ち、数分の prefill でノード群全体が遊休化しかねません。

**根本原因は 1 つのカーネル**：Kimi K3 は ROCm 上で低速な汎用 Triton attention にフォールバックしていました。**高速な AITER MLA prefill カーネルがロードされなかった**ためです。原因はカーネル不足ではなく**形状不一致**：

- K3 は TP8 でランクあたり **12 個のアテンションヘッド**；
- AITER の MLA 経路は 4、8、16 の倍数のみサポート。

**修正**：ヘッド数を **12 から 16 にゼロパディング**し、高速カーネルを実行、出力から本当の 12 ヘッドを取り出すだけです。

**結果**：同じ 172k コールド prefill で、AITER MLA prefill は約 **13k tok/s** の定常状態（Triton フォールバックは約 4–7k tok/s）を達成し、**prefill が約 2–3 倍高速化**。これは総スループットは変えません（デコードは不変）が、**ユーザーが最初のトークンを待つ時間**を直接変えます。

## 五、ベンチマーク結果：数字で語る

### 5.1 Wafer の実測：MI355X vs B200 vs B300（Kimi K3 稼働時）

詳細は 2.4 を参照。ここでは**一文の結論**を：

- **性能対価格比**：MI355X **48 tok/s/$** —— B200（7）の約 **7 倍**、B300（33）の約 **1.45 倍**；
- **総スループット**：B300（1,568）が依然トップですが、MI355X（952）は大半の本番シナリオをカバーできます；
- **単一ストリーム体験**：MI355X 118 tok/s（B200 より約 31% 良好）、B300 の 172 tok/s には及ばず。

### 5.2 重要な洞察：なぜメモリ容量が「勝負の分かれ目」になったのか

- B200 は Kimi K3 を収容するため **TP16 の 2 ノード構成**を強いられ、デコードのクリティカルパスにノード間 all-reduce が乗ります；
- MI355X は「重み + 1M コンテキスト KV」を **TP8 の単一ノード**で収容し、ノード間ペナルティなし；
- つまり、**容量優位（288GB）が、比較可能で測定可能な性能・コスト優位に直接換算された**のです。

## 六、設計哲学：なぜ「メモリは堀」が 2026 年の真実なのか

### 6.1 モデルサイズの軍拡競争は「大容量メモリ」に有利

Kimi K3 の 2.8T は「大きいほど強い、強いほど大きい」という**軍拡競争**です。モデルが大きくなるほど、大容量メモリの GPU だけがそれを支えられ、これこそ AMD が参入する絶好の位置です——**ピーク演算性能の競争ではなく、「収容できるか + トークンあたりコスト」の競争**です。

### 6.2 AMD：性能を追わず、「容量 + コスト」を追う

AMD はソフトウェア面で CUDA に長年遅れを取ってきましたが、今回は戦い方を変えました：

- **単一カードの演算性能で戦わず**、**288GB の大容量メモリ + 2.4 倍の低価格**を提供；
- **ROCm に全力投球し、Day-0 サポートを実現**——馴染みのモデルを初日から動かせる；
- 「容量 × コスト」で「フロンティアモデルを稼働する資格」を再定義。

### 6.3 輸出規制が皮肉にも AMD に有利に働く

大きな背景があります：**NVIDIA のハイエンドチップは中国への輸出規制対象**（H100/B200 クラスは「推定拒否」）。これにより中国の AI チームは代替経路を探さざるを得ません：

- **AMD** が「コスト効率が良く合法的な」選択肢に——価格が低く、規制の監視が緩く、最も厳しい拒否枠には該当しない；
- すると「**中国のフロンティアモデル + AMD カード + コスト重視のスタートアップ**」が**好循環**を形成：モデルが大きいほど大容量メモリが必要 → AMD が安価な大容量を提供 → より多くのチームが AMD を採用 → より多くのベンダーが ROCm 最適化に投資 → ソフトウェア差が急速に縮まる。

### 6.4 Wafer の究極の主張：エージェント最適化が「CUDA 独占」を終わらせる

- Wafer の信念：CUDA カーネルが与えられるのを待つより、**AI エージェントでカーネルを自動最適化する**；
- この記事の結論は大胆な主張を含みます：**「AMD での SOTA は目前である」（SOTA on AMD is imminent）**；
- 最後は挑発的な問いで締めくくられます：**「Is the CUDA moat dead?」（CUDA の堀は死んだのか？）**

## 七、総括：見解と結論

### 7.1 核となる見解

1. **メモリ容量は次世代モデルのハードルである**。モデルが単一ノードに収まらなくなったとき、「重み + KV キャッシュ」を収められる者がデプロイ競争に勝ちます。
2. **ハードウェアは「性能対価格比」で選ぶ**。MI355X の 48 tok/s/$ は B200 の 7 倍、B300 の 1.45 倍——文句なしのコスパ王です。
3. **AMD のソフトウェア差は（特にエージェントによって）急速に縮まっている**。Wafer は「定義不足 / 形状」の 2 つの小さなバグ修正だけで本番級の性能を回復。カスタムカーネルはゼロでした。
4. **TTFT こそユーザーが実際に感じる体験**。decode tok/s は美化されがちで、最初のトークンまでの遅延こそ本物。だから prefill 最適化（12→16 ヘッド、AITER）は見せかけではなく、ユーザーの待ち時間を直接削減するのです。

### 7.2 開発者への示唆

- デプロイ前に問うべき：**この GPU のメモリは「重み + コンテキスト」を収容できるか？** ——「GPU 枚数 / 演算性能」を追うより重要です。
- decode tok/s に惑わされない——**まず最初のトークンまでの遅延を見る**こと。
- ROCm のエラーに遭遇したら冷静に調査：**多くは「未定義 / 形状不一致」であり「カーネル不足」ではない**——一行の修正で済むことが多い（`top_k_renorm_prob`、12→16 ヘッドは生きた例）。

### 7.3 結び

最後にタイトルの問いに戻ります：**CUDA の堀は死んだのか？**

「堀」をピーク性能スコアと定義するなら、まだ明らかに死んでいません。しかし「**お金でどれだけの知能を買えるか**」と定義するなら——この記事はこれ以上ないほど明快な答えを提示しています：**メモリは新たな堀となり、AMD + 中国オープンソースの組み合わせが、その堀をさらに深く掘り続けている。**

今後注目すべきシグナル：オープンモデルのサイズが上昇し続け、AMD の Day-0 サポートが当たり前になり、推論フレームワークが ROCm 向けにより深く最適化されるにつれて——「**N カードでなければならないのか**」の答えは、「もちろん」から「必ずしもそうではない」へと変わりつつあります。
