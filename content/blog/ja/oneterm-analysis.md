# OneTerm 深度解説：VeOps オープンソース・バスティオンホスト — 4A セキュリティ概念に基づくエンタープライズ級アクセスセキュリティと運用監査ソリューション

> コアイデア：**バスティオンホストの本質は「すべてのサーバーへの唯一の入り口」——散らばったリモートアクセスを単一のセキュアなノードに集約する。** OneTerm は VeOps が開発したオープンソースのエンタープライズ・バスティオンホストで、**4A セキュリティ概念**（認証 / 認可 / アカウント / 監査）を基盤に、**Go バックエンド + Vue.js フロントエンド + Apache Guacamole プロキシ** により認証から監査までの完全な運用セキュリティスタックを構築。SSH、RDP、VNC、Telnet、MySQL、PostgreSQL、MongoDB、Redis などのマルチプロトコルアクセスをサポートし、セッション録画と再生、コマンドテンプレート制御、時間/IP アクセスポリシー、OAuth2/LDAP/CAS シングルサインオン、SFTP ファイル転送、VeOps CMDB とのワンクリック資産同期を提供。`docker compose up -d` 一本でデプロイ可能——エンタープライズ運用の「セキュリティ上の入り口」問題を最も軽量に解決する。

## 1. プロジェクト概要

### 1.1 これは何か？

**OneTerm** は VeOps（維易科技）が開発した**エンタープライズ・バスティオンホスト**（ジャンプサーバー）。核心的なポジショニング：**ユーザーとサーバーの間にセキュリティチェックポイントを設ける**——すべてのリモート接続が OneTerm の認証と認可を通過して初めてターゲットサーバーに到達できる。

**4A セキュリティ概念**に基づく：

- **Authentication（認証）**：誰ですか？（ユーザー名/パスワード、MFA、OAuth2/LDAP/CAS）
- **Authorization（認可）**：何にアクセスできますか？（ロールベースの細粒度権限）
- **Account（アカウント）**：ユーザーアカウントと認証情報の統一管理
- **Audit（監査）**：何をしましたか？（全操作ログとセッション録画）

### 1.3 何の問題を解決するか？

エンタープライズにはリモート管理が必要なサーバーが数十〜数百台ある。従来の方法——すべてのサーバーに SSH ポートを直接公開——はパスワードの分散管理、運用監査の不在、侵害時の甚大な被害範囲を招く。OneTerm の答え：**バスティオンホストを唯一のエントリポイントとする**——すべての接続が認証と認可を通過し、すべての操作が記録され、パスワードが一元管理される。たとえ一台のサーバーが侵害されても、攻撃者は横方向に移動できない——すべてのトラフィックが OneTerm を経由するため。

## 2. コアイデア

### 2.1 4A — 安全運用の「4つの柱」

OneTerm の設計はすべて **4A** を中心に展開：

- **Authentication（認証）**：誰ですか？ユーザー名/パスワード、MFA、OAuth2、LDAP、CAS SSO をサポート
- **Authorization（認可）**：何ができますか？コマンドレベルまで細かい RBAC
- **Account（アカウント）**：認証情報の一元管理、パスワード自動ローテーション
- **Audit（監査）**：何をしましたか？全操作ログ、セッション録画と再生、コマンドリスク分類

### 2.2 単一エントリポイント — 攻撃面の最小化

OneTerm は 1 ポートのみ公開（デフォルト 8666 Web + 2222 SSH）。すべてのサーバーは内部ネットワークにある。攻撃者が OneTerm を突破しても、認可されたリソースしか見えない——内部ネットワーク全体ではなく。これは**攻撃面最小化**の教科書的実践。

### 2.3 セッション録画 — 事後調査の「ブラックボックス」

すべてのユーザーセッションは完全に録画・保存される（ローカル、S3、OSS、COS、MinIO、Azure Blob などの複数バックエンドをサポート）。セキュリティインシデント発生時、管理者は動画再生のようにユーザーの完全な操作シーケンスを再生できる——これはコンプライアンス監査の中核要件。

### 2.4 CMDB 連携 — 資産としてのコード

OneTerm は VeOps CMDB（同様にオープンソース）と深く連携し、ワンクリック資産インポートをサポート。これによりバスティオンホストの資産インベントリが企業 CMDB と同期され、手動メンテナンスの煩雑さとエラーを排除。

## 3. アーキテクチャ

### 3.1 サービス構成（Docker Compose）

OneTerm は 5 つの Docker サービスで構成：

- **oneterm-api**：Go バックエンド API（ポート 2222 SSH / 8888 HTTP）
- **oneterm-guacd**：Apache Guacamole デーモン（RDP/VNC/Telnet プロキシ、ポート 14822）
- **mysql**：MySQL 8.2.0（ポート 13306）
- **redis**：Redis 7.2.3（ポート 16379）
- **oneterm-ui**：Vue.js フロントエンド + Nginx（ポート 8666）
- **acl-api**：ACL 権限サービス（Flask/Python、ポート 5000）

### 3.2 バックエンド構造

```
backend/
├── cmd/server/main.go           # エントリポイント
├── internal/
│   ├── api/                     # HTTP API レイヤー（コントローラー、ミドルウェア、ルーター、Swagger）
│   ├── connector/protocols/     # プロトコルハンドラ：ssh.go、guacd.go、telnet.go、web.go、db/
│   ├── guacd/                   # Guacamole 接続管理
│   ├── service/                 # ビジネスロジック（アカウント、資産、認可、セッション）
│   ├── repository/              # データアクセスレイヤー
│   ├── model/                   # データモデル
│   ├── sshsrv/                  # SSH サーバー実装

│   └── tunneling/               # SSH トンネル管理
└── pkg/storage/providers/       # ストレージバックエンド：s3、oss、cos、obs、oos、minio、azure、local
```

## 4. 設計哲学

### 4.1 「シンプルで軽量」は意図的

README は冒頭で強調：**「A Simple, Lightweight, Flexible Bastion Host.」** 巨大な運用プラットフォームを目指すのではなく、「アクセスセキュリティ + 監査」に特化。これにより `docker compose up -d` でデプロイでき、運用チームが複雑なシステムを学ぶ必要がない。

### 4.2 4A はスローガンではなくアーキテクチャ制約

OneTerm における 4A は壁に貼られた標語ではなく、厳格なアーキテクチャ制約：すべての接続はまず認証、次に認可、すべての操作は監査、すべてのアカウントは一元管理。この 4 つが欠けたらバスティオンホストではない。

### 4.3 オープンソースだが機能は劣化しない

オープンソースでありながら、OneTerm はエンタープライズ・バスティオンホストの本質的機能をカバー：MFA、LDAP/OAuth2/CAS SSO、コマンドテンプレート制御、時間/IP アクセスポリシー、マルチストレージバックエンド、CMDB 連携。オープンソース版を「機能削減」していない——AGPL-3.0 がコードの持続的開放を保証。

### 4.4 成熟したコンポーネントを活用、再発明しない

OneTerm は RDP/VNC プロキシを自作せず、Apache Guacamole（実績のあるリモートデスクトップゲートウェイ）を統合。権限システムも自作せず、独立した ACL サービスを使用。この「巨人の肩に乗る」戦略により、OneTerm はバスティオンホストの中核ロジック（認証、認可、監査）に集中できる。

## 5. ステップバイステップチュートリアル

### 5.1 クイックデプロイ（デフォルトパスワード）

```bash
git clone https://github.com/veops/oneterm.git
cd oneterm/deploy
docker compose up -d
```

`http://127.0.0.1:8666` にアクセス。ユーザー名 `admin`、パスワード `123456`。

### 5.2 セキュアデプロイ（カスタムパスワード）

```bash
git clone https://github.com/veops/oneterm.git
cd oneterm/deploy
./setup.sh          # インタラクティブなセキュアパスワード生成
docker compose up -d
```

### 5.3 ポートマッピング

- **8666**：Web UI（Nginx + Vue.js）
- **2222**：SSH プロキシ
- **13306**：MySQL
- **16379**：Redis
- **14822**：Guacamole（RDP/VNC/Telnet プロキシ）

### 5.4 開発環境セットアップ

```bash
# フロントエンド開発（ホットリロード）
./dev-start.sh frontend

# バックエンド開発（ホットリロード）
./dev-start.sh backend

# 完全環境
./dev-start.sh full

# 停止
./dev-start.sh stop
```

**要件**：Docker、Node.js 14.17.6+、Go 1.21.3+

### 5.5 サーバーへの接続

デプロイ後：

1. 資産を追加（サーバー IP、ポート、プロトコル）
2. ユーザーを作成し、認可ルールを割り当て
3. ユーザーがログイン → ワークステーション → ターゲットサーバーを選択 → 接続
4. ブラウザで Web ターミナル（SSH）または Guacamole クライアント（RDP/VNC）が開く

### 5.6 セッション録画と再生

接続後、すべての操作が自動録画される。管理者は：

- アクティブセッションを表示（リアルタイム監視）
- 過去セッションを再生（完全な操作のリプレイ）
- セッションログをエクスポート

### 5.7 コマンド制御

認可ルールでコマンドテンプレートを設定：

- **許可コマンドホワイトリスト**：特定のコマンドのみ許可
- **禁止コマンドブラックリスト**：危険操作をブロック（`rm -rf`、`drop database` など）
- **コマンドリスクレベル**：リスク別分類、高リスクコマンドには二次承認が必要

### 5.8 CMDB 連携

VeOps CMDB がデプロイされている場合、ワンクリックで資産をインポート——CMDB のサーバー情報がバスティオンホストに自動同期され、手動入力の必要がない。

## 7. まとめ（観点と結論）

プロジェクトとデータから、いくつか考察すべき点がある：

1. **バスティオンホストの価値は「技術的複雑さ」ではなく「ポリシーの実行力」にある。** 多くの企業がバスティオンホストを持っていても誰も使わない——運用担当者が面倒くさがり、直接 SSH するから。OneTerm の Web ターミナルとワンクリックデプロイがハードルを下げ、「ポリシーの実行」を実現可能にする。シンプルさは怠惰ではなく、セキュリティ戦略を実際に機能させる手段。

2. **4A は安全運用の最小完備集合。** 認証が「誰か」を、認可が「何ができるか」を、アカウントが「どう管理するか」を、監査が「何をしたか」を解決——この 4 つの次元が運用セキュリティの中核的ニーズをカバー。OneTerm は巨大な運用プラットフォームになろうとせず、4A を深く做的。

3. **Docker Compose デプロイは「軽量」の最良の表現。** 一コマンドで 6 サービスを起動、ゼロから 30 分で利用可能——中小企業にとって大きな魅力。複雑さは Docker イメージにカプセル化され、運用チームは Go コンパイル、Vue.js ビルド、MySQL 設定を理解する必要がない。

4. **Apache Guacamole は「車輪の再発明をしない」模範。** RDP/VNC プロキシは極めて複雑なプロトコル実装。OneTerm は自作せず Guacamole を統合——バスティオンホストの中核ロジック（認証、認可、監査）に集中できる。

5. **AGPL-3.0 は二刃の剣。** コードの持続的開放を保証（すべての変更をコミュニティに貢献）するが、SaaS サービスを構築する企業は変更をオープンソース化する必要がある——商用コンテキストでは懸念材料になり得る。

6. **CMDB 連携は「資産としてのコード」の実践。** バスティオンホストの資産リストを手動維持するとすぐに陳腐化。CMDB との連携により資産が自動同期され、バスティオンホストが常に「保護が必要なサーバー」を把握できる。
