# npm サプライチェーン危機深度解析：唯一「防止する方法がない」と言われる主流パッケージマネージャー

> 核心思想：**npmエコシステムの「防止できない」は技術的限界ではなく、意図的な選択の結果である。** デフォルトでのインストールスクリプト実行、パッケージ所有权検証の欠如、40段嵌套の依存関係ツリー，这些设计选择使每一次 `npm install` 都成为一场信任传递的赌博。当 Go/Rust 生态系统用强类型标准库和内置加密验证将供应链风险压制到接近零时，npm は「利便性優先」を選択し、代償としてコミュニティ全体が数ヶ月ごとに「完全に避けられない」災害を経験している。Kevin Patelはこの風刺的なブログ記事で、新聞体（journalistic satire）の筆致で这个生态级笑话背后的系统性 failure を暴いている。

---

## 一、プロジェクト説明

### 1.1 本文の背景

本文が解析する元の内容は、**Kevin Patel**（Application Security Engineer @ NISC）が **2026-05-15** に公开发表したブログ記事 **《'No Way To Prevent This,' Says Only Package Manager Where This Regularly Happens》** である。記事は典型的な**風刺的新聞体（journalistic satire）**を採用している——表面上是模仿地方报纸灾难题材の报道形式，实际上是对npm生态系统性失职の鋭い批判である。

元の стать の核心的な風刺構造は次のとおり：虚构の「npmサプライチェーン攻撃が全球インフラ崩溃」を提示し、コミュニティの「完全に避けられない」という論調を受け入れ、そして反撃する——**Go、Rustなどのエコシステムでは類似の事件の発生率はゼロである。** 風刺の矛先は攻撃者本身ではなく、npmの設計選択に向かっている。

### 1.2 現実の背景：npmサプライチェーン攻撃の реальные случаи

風刺の素材は以下の実際に发生过のnpmサプライチェーン攻撃から：

**event-stream事件（2018）**：攻撃者flatmapはnpmのMaintainer権限移転メカニズム exploit して人気の `event-stream` パッケージ（週150万ダウンロード）を支配し、Copay Bitcoin ウォレット専用の悪意のあるコードを注入、約500万米ドル相当の暗号通貨を窃取した。攻撃者は3人の元のMaintainerの信頼を得て、コードレビューなしで发布権限を取得した。

**colors.js / faker.js事件（2022）**：人気パッケージの著者Marak Squiresは故意に無限ループを插入し、数百万のパッケージに依存するアプリケーションをクラッシュさせた——「大企業がオープンソースを无偿利用しながらも回报しない」ことへの怒りから。これらは**能动的悪意**であり、サプライチェーン乗っ取りではないが、npmの依存関係伝播の脆弱性を暴露した。

**npmフォントフィッシングパッケージ事件**：攻撃者は人気のフォントパッケージ名に似たフィッシングパッケージ（typosquatting）を公开发表し、開発者を誘導して悪意のあるパッケージをインストールさせた。

**依存関係混乱攻撃**：攻撃者はプライベートパッケージ名をパブリックnpm registryに登録し、ローカルプライベートregistryが利用できない時にビルドスクリプトが依存関係を乗っ取ることを利用した。

### 1.3 npmエコシステムの規模

問題の深刻さを理解するには、npmの規模を知る必要がある：

- npm registryは**世界最大のコードregistry**であり、**200万個以上**のパッケージを托管
- 典型的な сучасних Node.js アプリケーションの依存関係ツリーの深さは**40段以上**
- 中規模のNode.jsプロジェクトは依存関係チェーンを通じて**数百甚至は数千個**のパッケージに間接的に依存している可能性がある
- ほとんどの開発者は直接の依存関係のみをレビューし、传递依存関係を手动でレビューすることは绝不会
- npmはデフォルトで `preinstall`、`install`、`postinstall` スクリプトを実行する——这些スクリプトは `npm install` プロセスと同じシステム権限を持っている

## 二、攻撃向量分析

### 2.1 主な攻撃面

npmサプライチェーン攻撃の核心的な攻撃面：

**1. パッケージ乗っ取り（Package Takeover）**

npmの権限移転メカニズムは最大の単一脆弱性である。Maintainerはパッケージの所有権を無条件に任何人迁移できる。攻撃者は以下の方法で人気パッケージの支配権を取得する：

- 非アクティブなMaintainerに連絡し、パッケージのメンテナンス権を高价で購入
- 他人になりすまして権限移転 요청を発生
- Maintainerの怠慢を利用（公開メールアドレスがフィッシングメールを受け取る）
- Maintainerが長期的にissueに応答しない時にパッケージを乗っ取る

所有権を取得すると、攻撃者は任意バージョンの任意コードを公开发表できる。該パッケージに依存するすべてのアプリケーションは次に `npm install` 時に自動的に悪意のあるバージョンをプルする。

**2. インストールスクリプト実行（Install Script Execution）**

npmはデフォルトで `package.json` で定義された `preinstall`、`install`、`postinstall`、`prepublish`、`prepare`、`preshrinkwrap`、`postshrinkwrap` スクリプトを実行する。これらのスクリプトは以下のことができる：

- ファイルシステムの読み書き
- 任意のシステムコマンドの実行
- 環境変数の窃取（APIキー、トークン、証明書を含む）
- 永続的なバックドアの確立
- 追加の悪意のあるペイロードのダウンロードと実行

これらのスクリプトはCI/CD環境でも同样に実行され、CI/CDは通常高権限凭证を保持している。

**3. 依存関係伝播（Dependency Propagation）**

npmの依存関係解決メカニズムは間接的な依存関係に直接の依存関係と同等の実行権限を付与する。攻撃者は以下ができる：

- 人気パッケージの間接的な依存関係になる（依存関係の依存関係）
- 底層ツールパッケージを更新する時に悪意のあるコードを注入
- 依存関係衝突メカニズムを通じて悪意のあるバージョンのインストールを強制

**4. Typosquatting（域名仿冒式パッケージ名攻撃）**

攻撃者は人気パッケージ名に似たパッケージ名（`react` → `reack`、`lodash` → `1odash`など）を登録し、開発者のタイプミスを exploit して悪意のあるパッケージの導入を誘導する。

### 2.2 攻撃の経済学

サプライチェーン攻撃がこれほど頻繁发生的根本理由は**経済学**：一个パッケージを攻撃し、一度投資で無限の収穫。

- 開発コスト：ほぼゼロ（既存のオープンソースインフラを利用）
- 潛在收益：一个の 패키지가数千のプロジェクトに依存 →数十億回のインストール →每次インストール都執行攻撃コード
- 発見確率：極めて低い（コードは特定の条件下でのみトリガーされ、数ヶ月後にようやく検出される可能性がある）
- 責任追及確率：ほぼゼロ（npmのToSには実質的な保証がなく、攻撃者は法的なグレーゾーンにいる）

## 三、設計哲学批判

### 3.1 npmの設計哲学：「利便性が正義」

npmの設計選択は其の歴史的背景から理解できる：

- **2009年に誕生**：当時セキュリティ意識は今ほど高くなく、JavaScriptは主にブラウザスクリプト用
- **快速イテレーション駆動**：npmは開発者体験と发布速度をセキュリティより優先
- **Unixからの信頼モデル継承**：パッケージのMaintainerは善意で、ネットワークは信頼achableという仮定
- **後方互換性優先**：セキュリティ欠陥知っていても既存依存関係チェーンを壊すことを躊躇

npmのスローガン「build amazing things」は問題を説明している：その設計目标是開発者が**急速に驚異的なものを構築**できるようにすることであり、**安全に構築**することではない。利便性とセキュリティは多くの設計で矛盾し、npmはほとんど常に利便性を選んだ。

### 3.2 「予防する能力がない」か「予防することを選択しない」か？

Kevin Patel元の стать の核心的論点は：npm当局の「防止できない」は**意図的な構造的不作為**である。

npmは実際には**できる**：

- パッケージ移転にクールダウン期間と多要素検証を要求
- `postinstall`スクリプトを含むパッケージに警告マークを付ける
- パッケージの暗号化署名強制検証を実装
- 依存関係セキュリティスコアリングシステムを確立
- 高権限パッケージ（週10万回以上ダウンロード且つスクリプトあり）に人手監査を実施
- lockfilesの完全なハッシュ検証をサポート（既に存在するが、強制力が不十分）
- パッケージ所有権の公開紛争メカニズムを実装

しかし这些都是**发布コストを増大**させ、npmの他のregistryに対する**競争力**を低下させる。だからnpmは精巧な言い訳を選んだ：**「我々は被害者に心を寄せます」**、そして运营を継続する。

### 3.3 信頼伝達チェーンの崩壊

現代ソフトウェアエンジニアリングは「信頼伝達」に基づいている：

```
開発者 → npmを信頼 → パッケージの著者を信頼 → パッケージの依存関係を信頼 → 依存関係の依存関係を信頼 → ...
```

npmはこのチェーンを荒唐無稽な程度（40段）に延長したが、**信頼検証メカニズム**を何も確立しなかった。每一跳都是暗黙の信頼であり、暗号化検証も署名保証もない。

これは**Go modules**の設計と鲜明的对比をなす：Goは言語レベルで暗黙のネットワーク依存関係を制限し（`go.mod`は明示的に宣言する必要がある）、`go.sum`を通じて暗号化検証を提供する。Rustの `crates.io` には類似の問題があるが、その標準ライブラリの完备性により外部パッケージへの依存関係が减少している。

## 四、跨エコシステム比較

### 4.1 Goエコシステム：標準ライブラリ優先戦略

Goの設計哲学は「バッテリー 포함」（batteries included）：

- 標準ライブラリはほとんどの日常開発ニーズをカバー（HTTP、JSON、暗号化、データベース、テスト）
- 開発者は典型的なwebサービスを完成させるために十数個の外部パッケージを導入する必要はない
- `go mod`は明示的な依存関係宣言を要求し、`go.sum`暗号化検証を提供する
- エコシステム規模が小さく、監査が更容易

**結果**：Goプロジェクトの依存関係ツリーは通常**3-5段深さ**しかなく、でもっぱらGo公式メンテナンスのパッケージである。

### 4.2 Rustエコシステム：型安全性+強い依存関係管理

Rustの `cargo` と `crates.io` はより良いデフォルトセキュリティを提供する：

- **型システム**は多くの攻撃をコンパイル時に捕捉できる（整数オーバーフロー、空ポインタ逆参照）
- `Cargo.lock`はすべての依存関係の暗号化ハッシュを含み、強制検証される
- Rust標準ライブラリも同様に相当に完备しており、多くのシナリオでは外部依存関係が不要
- crates.ioはより厳格なパッケージ发布監査メカニズムを持っている

**結果**：Rustプロジェクトのサプライチェーン攻撃ケースは極めて少ない。

### 4.3 npmの構造的不利

| 次元 | npm | Go modules | Rust crates |
|------|-----|------------|------------|
| 標準ライブラリ完备性 | 低（多くの基本機能は外部パッケージが必要）| 高 | 高 |
| 依存関係ツリー深さ | 40+段 | 3-5段 | 5-10段 |
| 暗号化署名検証 | オプション | 必須（go.sum） | 必須（Cargo.lock） |
| インストールスクリプト実行 | デフォルト有効 | なし | なし |
| パッケージ发布監査 | 極めて低い | 中等 | 中等 |
| サプライチェーン攻撃頻度 | 高（定期的） | 極めて低い | 極めて低い |

## 五、防御実践ガイド

### 5.1 開発者と企業の即時アクション

**1. 依存関係ツリーの監査**

```bash
# npm auditを使用して既知の脆弱性をチェック
npm audit

# Socketセキュリティ分析を使用（より深く）
npx @socket-security/analyze

# 依存関係ツリーを可視化（異常な深さをチェック）
npm ls --depth=10

# postinstallスクリプトをチェック（危険信号）
grep -r "postinstall" package-lock.json
```

**2. 依存関係バージョンのロック**

```bash
# npm-shrinkwrap.json または package-lock.jsonを使用
# CI/CDが --frozen-lockfileを使用することを確認
npm ci --frozen-lockfile
```

**3. .npmrcを使用してスクリプト実行を制限**

```bash
# グローバルでinstall scriptsを無効化（危険パッケージの手動有効化が必要）
npm config set ignore-scripts true

# またはプロジェクト内で
# .npmrc
ignore-scripts=true
audit=false
```

**4. プライベートregistryを使用した分離**

```bash
# Verdaccioプライベートregistryを構築
docker run -d -p 4873:4873 verdaccio/verdaccio

# またはGitHub Packages / npmjs orgのプライベートパッケージを使用
```

**5. CI/CDパイプラインの強化**

```yaml
# GitHub Actionsの例
- name: Install dependencies
  run: npm ci --ignore-scripts
  env:
    NPM_TOKEN: ${{ secrets.NPM_READ_ONLY_TOKEN }}
```

### 5.2 組織レベルでの長期的方案

**1. パッケージ導入プロセスの確立**

- セキュリティスコアのない外部パッケージの直接導入を禁止
- すべての新パッケージにセキュリティレビューを要求（Socket、Snykまたは類似ツールを使用）
- 内部ミラーを確立し、監査済みパッケージのみを許可

**2. 依存関係最小化原則**

- Node.js標準ライブラリを優先的に使用
- 各外部依存関係のリスク/ベネフィット比を評価
- 使用されなくなった依存関係を定期的にクリーンアップ

**3. 異常の監視**

- `npm install`のネットワークアクティビティを監視（異常なダウンロードがあるか）
- 依存関係パッケージの发布頻度を監視（突然大量更新的パッケージは妥協の兆しかもしれない）
- npmセキュリティ公告を購読（npm.io/advisories）

### 5.3 LLMプログラミング使用時の特別な注意事項

AIコーディングアシスタント（Claude Code、Cursor、Copilot）を使用する際、サプライチェーンリスクは増幅される：

**問題**：

- LLMはセキュリティ履歴を考慮せず「適切に見える」パッケージを導入する傾向がある
- AI生成コードには通常大量の `npm install` コマンドが含まれる
- AIは `postinstall` スクリプトの危険性を能動的に警告しない

**提案**：

- `.npmrc`でプロジェクトデフォルトとして `ignore-scripts=true` を設定
- AI使用時にSocketリアルタイム分析を有効化
- 定期的に `npm audit` を実行してAIが導入した依存関係をチェック
- 「AI許可リスト」をメンテナンスし、監査済み安定パッケージのみを許可

## 六、設計哲学サマリー

### 6.1 npmの失敗の深層原因

npmのサプライチェーンセキュリティ問題は「セキュリティ技術が不十分」ではなく、**設計哲学の根本的な偏差**である：

1. **利便性 > セキュリティ**：npmは各設計意思決定ポイントで利便性を選んだ。これは早期には合理的だったが、npmがグローバルインフラになった後、この選択の結果は構造的に増幅された。

2. **信頼 > 検証**：npmはすべてのMaintainerが善意であると假设し、有効な検証メカニズムを確立しなかった。これは2009年には合理的だったが、今日は明らかに不十分である。

3. **速度 > 品質**：npmの发布流程は極めて速いが、实质的な監査がない。これは開発者を引きつけたが、攻撃者のため的大门も开いた。

4. **成長 > セキュリティ**：npmは（一旦GitHubに買収された）商業实体として、成長圧力を持っている。これは「体験を下げる」セキュリティ措施の追加を嫌がらせる。

### 6.2 他のエコシステムがなぜよりいいのか

GoとRustは開発者がより賢いからではなく、より安全的だからでもなく：

- **設計時にセキュリティをコア制約として定位した**から（Goの `go mod`は最初から署名検証を持っていた）
- **標準ライブラリが十分に完备しており**、外部依存関係を减少できる
- **コミュニティがより小さく、工学的紀律，注重**、あまり「快速发布」文化がない

### 6.3 根本的問題：オープンソースのインセンティブ構造

サプライチェーン攻撃の根源はオープンソースのインセンティブ構造問題である：

- **Maintainerには**パッケージのセキュリティを保証するための十分なリソースがない
- **使用者には**依存関係を監査する意識も（能力も）ない
- **プラットフォームには**发布速度を低下させるセキュリティ措施を追加する動機がない
- **攻撃者には完全な動機がある**：一度投資で無限の収穫

これはnpmだけで解決できる構造的問題ではなく、プラットフォーム、開発者、企業セキュリティチームを含む業界全体が共同して新しい規範を確立する必要がある。

## 七、归纳まとめ

### 7.1 核心的観点リスト

1. **「防止できない」は構造的選択であり、技術的限界ではない**：npmはもっとができるが、やらないように选择了——セキュリティ措施会增加便利性を低下させ、競争力に影響するから。

2. **40段依存関係ツリーは信頼チェーンの災害である**：毎回 `npm install` は整个依存関係チェーンへの暗黙の信頼であり、暗号化検証も署名保証もない。

3. **インストールスクリプトはデフォルトで有効なトロイの木馬である**：npmはデフォルトで `postinstall` などのスクリプトを実行し、これらのスクリプトは完全なシステム権限を持ち、サプライチェーン攻撃の主なベクターである。

4. **パッケージ所有権移転メカニズムは最大の単一脆弱性である**：攻撃者は購入、フィッシングまたはソーシャルエンジニアリングを通じて人気パッケージの支配権を取得し、悪意のあるバージョンを公开发表できる。

5. **Go/Rustの对比は偶然ではない**：Goの標準ライブラリ完备性 + 強制署名検証 + 短い依存関係チェーン；Rustの型システム + Cargoロックファイルの強制検証——これらは設計選択であり、偶然の優位ではない。

6. **サプライチェーン攻撃の経済学は攻撃者に極めて有利である**：開発コストはほぼゼロ、潛在收益は数十亿美元、発見確率は極めて低く、責任追及確率はほぼゼロ。

7. **AIプログラミング時代のリスクは増幅される**：LLMはセキュリティ履歴を考慮せずパッケージを導入し、AI生成コードはサプライチェーンリスクを高める。

8. **即時の防御は可能である**：`npm config set ignore-scripts true`、npm ci、Socketなどのツールを通じて、開発者は組織レベルでリスクを显著的に低下させることができる。

9. **根本的な解決にはエコシステムレベルの変更が必要である**：单一のnpm設定では構造的問題を解決できず、プラットフォーム、開発者、企業セキュリティチームが共同して新しい規範を確立する必要がある。

10. **風刺の真の意味**：Kevin Patelの風刺的 стать は気になる真実を指している——npmコミュニティは既に「数ヶ月ごとのサプライチェーン災害」を「ただのオープンソースの代償」として正常化した。この慣習本身就是問題の一部である。

### 7.2 一言まとめ

> **npmのサプライチェーン危機は「不運」ではなく「設計選択」の結果である——利便性がセキュリティの上に置かれ、信頼が検証の上に置かれ、成長が品質の上に置かれると、毎回 `npm install` は信頼伝達の発券となり、Go/Rustは異なる設計選択で证明する：この発券は必須ではない。**

### 7.3 操作可能な提案早見表

| アクション | 緊急度 | 複雑度 |
|---------|--------|--------|
| `npm config set ignore-scripts true` | 即時 | 極めて低い |
| `npm install` の代わりに `npm ci` に切り替え | 即時 | 低い |
| `npm audit` を実行して高リスクの脆弱性を修正 | 24時間以内 | 低い |
| 高リスクパッケージをレビュー（ダウンロード量大 + スクリプトあり）| 今週 | 中 |
| Socketセキュリティ分析を導入 | 今週 | 中 |
| プライベートnpm registryを構築 | 今月 | 高 |
| パッケージ導入セキュリティ監査プロセスを確立 | 今四半期 | 高 |
| 重要なサービスをより安全な依存関係管理方案に移行 | 長期的 | 極めて高い |
