# Loop Engineering オレンジブック徹底解説：Loop Engineering って何？もう聞くな——「プロンプター」から「システム設計者」へ

> 核心思想：**AI に手動でプロンプトする人であるのをやめよう——代わりに AI にプロンプトするシステムを設計しよう。** 2026年6月、Peter Steinberger、Anthropic の Claude Code 責任者 Boris Cherny、Google の Addy Osmani という3人の業界の人物が、ほぼ同じ週に同じ転換を独立に口にした。花叔（HuaShu）はそれを無料・オープンソースの『Loop Engineering オレンジブック』にまとめた：より良いプロンプトの書き方を教えるのではなく、仕事を自動で見つけ、割り当て、検査し、記録し、次の一手を決めるループ・システムの設計を教える。**あなたの仕事はもう「エージェントにプロンプトすること」ではない——「ループを書くこと」だ。**

### 1.4 何を解決するのか？

この2年間、コーディングエージェントから価値を引き出す方法は決まっていた：良いプロンプトを書く → コンテキストを共有する → 返答を読む → 次のプロンプトを書く。**人間は一ターンずつツールを握っていた。** Loop Engineering はこの時代の終焉を宣言する：今やあなたは、仕事を見つけ、配り、検査し、記録し、次の一手を決めるシステムを構築する——**エージェントを突つくのはあなたではなくシステムだ。** この本はそのシステムを構築するための実践マニュアルである。

## 2. 核心思想

### 2.1 パラダイムシフト：「プロンプター」から「システム設計者」へ

- 従来のやり方：人間がプロンプトを書く → AI が実行 → 人間が検査 → 人間が次のプロンプトを書く。
- Loop Engineering のやり方：人間がループを設計 → ループが自動で AI にプロンプト → AI が自律実行 → ループが自動検証 → ループが自動記録。
- **人間は「オペレーター」から「アーキテクト」になる**——あなたの価値はより良いプロンプトを書くことではなく、より良い制御システムを設計することになる。

> "I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."（もう Claude にはプロンプトしない。Claude にプロンプトして次に何をすべきか決めるループが動いている。私の仕事はループを書くことだ。）——Boris Cherny（Anthropic Claude Code 責任者）

> "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."（もうコーディングエージェントにプロンプトすべきではない。エージェントにプロンプトするループを設計すべきだ。）——Peter Steinberger

### 2.2 4層スタック：prompt → context → harness → loop

```
prompt（プロンプト）→ context（コンテキスト）→ harness（足場）→ loop（ループ）
```

- **Prompt**：単一の指示。
- **Context**：エージェントに与える作業素材。
- **Harness**：単一エージェント実行の足場——ツール、完了基準、フィードバックループ。
- **Loop**：外側のシステム——タイマーで動き、ヘルパーを生み出し、検証し、状態を記憶し、次の一手を決める。

Loop Engineering は **Harness Engineering の一階層上**にある：harness は単発実行を武装し、loop はシステム全体を武装する。

### 2.3 1つのループの5つの動き + メモリ

| 動き | ループ内での役割 |
|------|-----------------|
| **自動化（Automations）** | スケジュールで自律的に発見 + トリアージ |
| **ワークツリー（Worktrees）** | 並行作業する2つのエージェントが互いに踏み合わないようにする |
| **スキル（Skills）** | エージェントが本来推測するしかないプロジェクト知識を書き留める |
| **プラグイン/コネクタ（Plugins/Connectors）** | エージェントを既存ツール（MCP）に接続する |
| **サブエージェント（Sub-agents）** | 片方がアイデアを出し、別の片方が検査する |
| **+ メモリ/状態（Memory）** | markdown ファイル、Linear ボード——単一の会話の外にあり「何をしたか、次に何をするか」を保持するもの |

### 2.4 メーカー/チェッカー分離：なぜ AI は自分のコードを採点できないのか

本書は一章を割いて、**コードを書く AI は自分のコードを採点できない**と論じる。生成と評価は別々のエージェント（または別々のモデルインスタンス）に分離しなければならない——著者はこれを **"GANs for prose"（散文版 GAN）** と呼ぶ。`/goal` コマンドはこの原則の具現だ：検証可能な停止条件が成立するまで働き続け、**完了したかを検査するのは別の独立した小モデル**——コードを書いたエージェントは採点者ではない。

## 3. 詳細チュートリアル：9章でループ全体を理解する

本書は **4部・9章** 構成。章ごとに解説する。

### 3.1 §01–§02 それは何か：定義と「1週間の起源物語」

- **§01 定義**：Loop Engineering の正確な定義と境界——プロンプトのアップグレードではなく、プロンプトの外側にあるシステム層。
- **§02 起源**：2026年6月のバイラルな1週間、3人の業界人物（Peter Steinberger、Boris Cherny、Addy Osmani）が同じ転換を独立に命名した。そして **prompt → context → harness → loop** の4層スタック。

### 3.2 §03 1つのループの5つの動き

§03 では各動きが実際のループ内でどう働くかを詳述：スケジューリングは発見とトリアージを担当、ワークツリーは並行性を隔離、スキルは知識を永続化、コネクタは実ツールに接続、サブエージェントは制作と検査を分離——そして「6番目のもの」としてのメモリ。

### 3.3 §04 ループを組み立てる6つの部品

- 5つの動きを自分のツールに写像すると6つの部品になる：**スケジューラ、ワークツリー、スキルファイル、プラグイン/コネクタ、サブエージェント定義、状態ストア**。
- 主要プリミティブは2大ツール間でほぼ**一対一対応**：

| プリミティブ | ループ内での役割 | Codex App | Claude Code |
|-------------|-----------------|-----------|-------------|
| **自動化** | スケジュールで発見 + トリアージ | Automations タブ、`/goal` | 定期タスク、`/loop`、`/goal`、hooks、GitHub Actions |
| **ワークツリー** | 並行フィーチャーを隔離 | スレッドごとに内蔵ワークツリー | `git worktree`、`--worktree`、`isolation: worktree` |
| **スキル** | プロジェクト知識を固定化 | `SKILL.md`、`$name` で呼び出し | `SKILL.md`（同一フォーマット） |
| **プラグイン/コネクタ** | ツールに接続 | MCP コネクタ + プラグイン | MCP サーバー + プラグイン |
| **サブエージェント** | 生成と検証 | `.codex/agents/` の TOML | `.claude/agents/` のタスクサブエージェント |
| **状態** | 進捗を追跡 | markdown または Linear | markdown（`AGENTS.md`）または MCP 経由の Linear |

### 3.4 §05 なぜ AI は自分のコードを採点できないのか

- **検証原則**：コードを書くエージェントはコードを採点できない——「メーカー」と「チェッカー」は分離しなければならない。
- これが `/goal` の設計根拠：独立した小モデルが「完了したか」を検査する（例：「test/auth 配下の全テストが通り、lint がクリーン」）。

### 3.5 §06 3つの実在ループ

1. **Addy の朝のトリアージループ**：毎朝自動化が実行 → トリアージスキルが昨日の CI 失敗・未処理 issue・最近のコミットを読む → 発見を markdown ファイルか Linear ボードに書く → 価値のある発見ごとに隔離ワークツリーを開く → サブエージェントが修正案を起草 → 2番目のサブエージェントがプロジェクトスキルと既存テストに照らしてレビュー → コネクタが PR を開き ticket を更新。
2. **Stripe の Minions**：Stripe の自律コーディングシステムで、**毎週約1,300 PR を処理**——流水線型ループエンジニアリングの本番規模の実例。
3. **スケジューリングの現実**：時間駆動実行は独自のエンジニアリング課題を生む——状態管理、障害復旧、人間の監督。「タイマーで動く」はタダではない。

### 3.6 §07 4つのコスト（自律が深まるほど鋭くなる）

1. **検証負債（Verification Debt）**：無人で動くループは無人でミスもする。メーカー/チェッカー分離は「完了」に意味を与えるが、それでもそれは証明ではなく主張だ。
2. **理解腐敗（Comprehension Rot）**：ループが自分が書いていないコードを速く出荷するほど、存在するものと実際に理解しているもののギャップは大きくなる。滑らかなループは理解負債をより速く育てる——ループが作ったものを読まない限り。
3. **Token 爆発（Token Blowout）**：制約のないループは膨大な token を消費しうる。「token が豊富か貧乏か」で使い方は天と地ほど違う。停止条件の入念な設計が不可欠。
4. **認知的降伏（Cognitive Surrender）**：ループが自分で回ると、意見を持つことをやめて与えられたものをそのまま受け取る誘惑に駆られる。**判断を伴って設計するならループは解毒剤だが、考えることを避けるために使うなら促進剤になる。同じ行為、正反対の結果。**

### 3.7 §08 エンジニアの立場に留まる

- ループは仕事を変えるが、**あなたを仕事から消し去りはしない**。
- まったく同じループを組んでも、人は正反対の結果を出す——深く理解した仕事を加速するために使う人と、仕事の理解そのものを避けるために使う人。

> "The loop doesn't know the difference. You do."（ループは違いを知らない。知っているのはあなただ。）

### 3.8 §09 今日から始める：最初のループを構築する（ハンズオン）

**ステップ1：小さな雑務を選ぶ**
繰り返し発生し、明確な受け入れ基準がある小さなタスクを選ぶ（例：毎日の issue トリアージ、毎日の CI スイープレポート）。

**ステップ2：スケジュールを決める**
頻度とトリガーを決める。Claude Code の定期タスク/`/loop`、GitHub Actions の cron、または Codex の Automations タブを使う。

**ステップ3：スキルを書く**
「このプロジェクトはどう動くか、なぜこのやり方をしないのか」を `SKILL.md` に書く——ループの各周回はコールドスタートなので、スキルこそが「外化された意図」だ。

**ステップ4：状態を整える**
`STATE.md`（または Linear ボード）を作り、「何をしたか、次に何をするか」を記録する——これがメモリ、6番目のものだ。

**ステップ5：メーカー/チェッカーを分離する**
`.claude/agents/` か `.codex/agents/` に2つのサブエージェントを定義する：片方は起草、もう片方はスキルとテストに照らしてレビュー。**コードを書く側は採点しない。**

**ステップ6：第1週は報告のみ、自動修正なし**
ループに発見のみを出力させ、コードは編集させない。出力を読み、間違った部分を修正する——**あなたは依然としてエンジニアだ。**

**ステップ7：徐々に手綱を緩める**
第1週は報告のみ → 第2週は隔離ワークツリーで修正を試行 → 確認できてから自動マージを検討。`AGENTS.md` やスキルの各行は、具体的な過去の失敗に遡れるべきだ——**各行は稼いで手に入れる。**

### 3.9 ツール & コマンド早見表

- Claude Code：`/goal`（検証可能な停止条件まで実行）、`/loop`（周期で再実行）、定期タスク/cron、hooks、GitHub Actions、`git worktree`/`--worktree`、`isolation: worktree`、`.claude/agents/`
- Codex App：Automations タブ（プロジェクト/プロンプト/周期/環境を選択）、トリアージ受信箱、スレッドごとの内蔵ワークツリー、`.codex/agents/` TOML
- 両者共通：`SKILL.md` スキル形式、MCP コネクタ、プラグイン配布

## 4. 設計哲学

### 4.1 「システムを構築せよ、プロンプターになるな」

中心哲学：**一ターンずつエージェントを駆動するのをやめ、外側のシステムを一度設計して自分で駆動させる。** あなたの仕事はオペレーターからアーキテクトへ。ループは再利用・バージョン管理・監査が可能——プロンプトは使い捨てだ。

### 4.2 ループは Harness の上にある

Loop Engineering は **Harness Engineering のまるごと一階層上**。harness = 1回のエージェント実行を武装する。loop = タイマーで動き、ヘルパーを生み出し、仕事を検証し、状態を記憶し、次の一手を決める外殻。

### 4.3 ラチェット原理：すべてのミスがルールになる

**"Every mistake becomes a rule."** エージェントがミスを犯したら、二度と起こらないように制約を足す。`AGENTS.md` やスキルの各行は具体的な過去の失敗に遡れるべきだ——**各行を稼ぐ**（Earn each line）。ループは複利的だ：ミスはルールに吸収され、ルールは次の周回でシステムを強くする。

### 4.4 ワークツリーは並行性の規律

2つのエージェントが同じファイルを書く = 2人のエンジニアが同じ行にコミットする頭痛。Git ワークツリーが解決する：独立した作業ディレクトリ、独立したブランチ、共有リポジトリ履歴——**編集は物理的に干渉できない。**

### 4.5 スキルは外化された意図

エージェントは毎回コールドスタートする。スキルとは「外側に書き留められた意図」——規約、ビルド手順、「なぜこのやり方をしないのか」。スキルがなければループは毎周回ゼロからプロジェクトコンテキストを導き直す。スキルがあれば、ループは**複利**で成長する。

### 4.6 製品は収束している、発散していない

Claude Code、Cursor、Codex、Aider、Cline——**それらは基盤モデル同士よりも互いに似ている。** モデルは異なるが、harness のパターンは収束している。これは業界が「生成モデルを出荷できるものに変える」耐荷重足場を見つけつつある証拠だ。

> "A decent model with a great harness beats a great model with a bad harness."（凡庸なモデル + 優れた harness は、優れたモデル + 粗末な harness に勝る。）

## 5. まとめ：見解と結論

1. **プロンプトの時代は終わり、ループの時代が始まっている。** 3人の業界リーダーが同じ週に同じことを独立に言った——これは誇大広告ではなく、業界コンセンサスの形成だ。人間は「プロンプター」から「システム設計者」へ。

2. **ループの価値は複利であり、単発ではない。** プロンプトは使い捨て、ループは再利用・バージョン管理・監査可能な資産。ミスはラチェット原理でルールに吸収され、ルールは毎周回システムを強くする。

3. **メーカー/チェッカー分離は安全性の基盤。** AI は自分のコードを採点できない——本書で最も硬い技術的論点。生成と評価は分離しなければならず（"GANs for prose"）、独立した小モデルが「完了」を検査する。

4. **自律は無料ではない。4つのコストは自律が深まるほど鋭くなる。** 検証負債、理解腐敗、token 爆発、認知的降伏——`/goal` の停止条件、隔離ワークツリー、人間ゲートはすべて、この4つのコストにブレーキをかけるために存在する。

5. **同じループ、違う人、正反対の結果。** "The loop doesn't know the difference. You do." ループは増幅器だ：深く理解する人も、理解を避ける人も加速させる。**エンジニアの立場に留まること（Stay the engineer）だけが正しい姿勢だ。**

6. **第1週は報告のみ、自動修正なし。** 新システムの最初の1週間は発見のみを出力し、コードを編集しない——まずシステムの挙動への理解と信頼を築き、それから権限を緩める。これが Loop Engineering の安全哲学だ。

7. **ツールの収束は、業界が耐荷重壁を見つけたことを意味する。** 主要コーディングエージェントの harness パターンの収束は、「モデルを出荷できるものに変える」足場が検証された証——業界全体へのパラダイムシグナルだ。

> "Build the loop. But build it like someone who intends to stay the engineer, not just the person who presses go."（ループを構築せよ。しかし、ただスタートボタンを押す人ではなく、エンジニアであり続けるつもりの人が構築するように。）
