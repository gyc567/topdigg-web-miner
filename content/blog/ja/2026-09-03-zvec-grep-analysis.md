# zvec-grep深度解析：セマンティック検索と字句検索を統合するローカルファーストAI開発アシスタント

> **コア思想：zvec-grep（略称zg）はセマンティック検索、BM25字句排序、精确な正規表現マッチングを1つのローカルファースト検索口に統一し、人間開発者とAIプログラミング助手が同じインデックスを共有する。解決するコアの問題は——AI Agentがコードベースで「テーマ設定を処理する場所」を見つける必要があるとき、正確なキーワードを知らない場合でも、正しい場所を見つけながら、すべてのデータをローカルに保つ方法。**

---

## 一、プロジェクト背景とコア位置づけ

### 1.1 なぜzvec-grepが必要なのか？

AIプログラミング助手が爆発的に普及した時代に問題になる矛盾：

- **精密検索**（ripgrep）： 찾는キーワードは知っているが、具体的な位置がわからない
- **セマンティック検索**（ベクトル検索）： 做りたいことは知っているが、どの単語を使えばいいかわからない

例えば、「テーマ設定の永続化を処理するコード」を見つけたい場合、"theme preference persistence"や"loadTheme"で検索するかもしれない。前者はセマンティック関連だが単語が一致しない；後者は精密だが先に変数名を推測する必要がある。

さらに複雑な問題は**AI Agentの検索困境**。Claude CodeやCodexのようなAIプログラミング助手がローカルリポジトリで答えを探す必要があるとき、二つの選択肢に直面する：
- キーワード検索を使う（セマンティック関連だが言い回しの異なるコードを見落とす可能性）
- セマンティック検索を使う（リモートAPIに依存、プライバシーリスクあり）

zvec-grepの答えは：**両方必要、ローカルファースト。** ripgrepの精密マッチング、BM25の字句排序、ベクトル検索のセマンティック発見を統一し、すべてローカルで実行、コードを任何のリモートサーバーにアップロードする必要がない。

### 1.2 プロジェクト基本情報

| 指標 | データ |
|------|--------|
| プロジェクト名 | zg (zvec-grep) |
| 基盤エンジン | zvec (アリババ OSS) |
| 技術スタック | ripgrep + BM25 + ベクトル検索 + RRFフュージョン |
| インストール | npm install -g @zvec/zvec-grep |
| Node.js要件 | Node.js 22+ |
| 対応プラットフォーム | macOS、Linux、Windows |
| 対応AI Agent | Codex、Claude Code、Qwen Code、Qoder、Cursor、OpenCode |
| プロトコル | ローカルMCPサーバー、デフォルトでloopbackのみlisten |

## 二、コア技術原理

### 2.1 検索の三銃士：字句 + セマンティック + 精密

zvec-grepのコアエンジンは2つの互补的な検索路徑を提供する：

**路徑一：インデックス検索（Indexed Retrieval）**

に適している：意図、関連コンセプト、ランキングされたキーワード

データソース：ワークスペースインデックスのBM25/FTSとベクトルデータ

 작동 방식：
1. **ベクトル検索**：クエリテキストをベクトルにエンコードし、ベクトル空間でセマンティックに類似したコンテンツチャンクを見つける
2. **BM25字句検索**：クエリに字句分析を適用し、関連用語を含む文書を見つける
3. **RRFフュージョン（相互ランキングフュージョン）**：ベクトル検索とBM25のランキング結果を相互ランキングフュージョン算法で統合

**路徑二：管理ripgrep（Managed ripgrep）**

に適している：已知のテキスト、記号、パス、正規表現

データソース：ワークスペースファイルを直接スキャン、インデックス不要

特徴：窮挙検索、正規表現で精密に定位可能。

### 2.2 RRFフュージョン：ハイブリッド検索が強い理由

RRF（相互ランキングフュージョン）は情報検索分野の古典的算法で、核心となるアイデアは：**もしある結果が複数の検索方法で同時に高くランクされていたら、最終結果でも高くランクされるべき。**

このハイブリッド方式は以下の弱点を避ける：
- 純粋なベクトル検索：「セマンティック類似だがキーワード不一致」
- 純粋なBM25：「キーワード一致だがセマンティック無関係」

### 2.3 構造認識のコンテンツ抽出

zvec-grepはファイルを単なるテキストとして扱わず、不同なファイルタイプに対して異なる抽出器を使用し、役立つ構造情報を保持：

| ファイルタイプ | 抽出器 | 保持する情報 |
|-------------|--------|------------|
| コード（C/C++/Go/Java/JS/TS/Python/Rust） | CodeExtractor | 記号、署名、パンくずリスト、周囲のソース |
| Vue/Svelteコンポーネント | CodeExtractor | `<script>`ブロック |
| Markdown | MarkdownExtractor | 見出しセクション、パンくずリスト |
| 設定ファイル（JSON/YAML/TOML/CSV） | TextExtractor | プレーンテキストチャンク |
| プレーンテキスト文書 | TextExtractor | プレーンテキストチャンク |
| 画像（明示的に含む必要あり） | ImageExtractor | 画像コンテンツ（マルチモーダルEmbedding必要） |

## 三、アーキテクチャ詳解

### 3.1 システムアーキテクチャ図

```
ユーザー層
  │
  ├── 人間/スクリプト ──→ zg CLI
  │
  └── AI Agent ──→ MCP Client ──→ ローカルMCPサーバー

実行層
  │
  └── Router ──→ Direct（直接実行）または Server（サーバー実行）
                      │
                      ▼
               ┌─────────────────┐
               │  zvec-grep エンジン │
               └────────┬────────┘
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
   インデックス検索    管理ripgrep       インデックス構築
   (BM25+ベクトル      (精密テキスト+     (スキャン+
    +RRFフュージョン)  正規表現)        抽出+
                                         埋め込み)

データ層
  │
  ├── ワークスペースファイル ──→ 直接スキャン
  │
  └── ワークスペースファイル ──→ .zvec-grep/ インデックスディレクトリ
```

### 3.2 ローカルファーストのセキュリティ境界

| データタイプ | デフォルト動作 | 認証要否 |
|------------|--------------|---------|
| ワークスペースファイルスキャン | 完全ローカル | 不要 |
| ローカルEmbeddingモデル | 完全ローカル | 不要 |
| ワークスペースインデックスストレージ | 完全ローカル（~/.zvec-grep/） | 不要 |
| MCPサーバー | loopbackのみlisten | 不要 |
| リモートEmbedding API | 明示的認証必要 | 每次ユーザー確認 |

## 四、詳細なインストールと使用教程

### 4.1 環境要件

- Node.js 22.0.0以上
- npmまたはyarn
- 対応OS：macOS、Linux、Windows

### 4.2 インストール手順

**ステップ1：グローバルインストール**

```bash
npm install -g @zvec/zvec-grep
```

**ステップ2：インストール確認**

```bash
zg help
zg version
```

**ステップ3：デモワークスペース作成**

```bash
mkdir zg-demo && cd zg-demo

curl --retry 3 --retry-all-errors --progress-bar -fL \
  -o alice-in-wonderland.txt \
  https://raw.githubusercontent.com/GITenberg/Alice-s-Adventures-in-Wonderland_11/master/11.txt

curl --retry 3 --retry-all-errors --progress-bar -fL \
  -o sherlock-holmes.txt \
  https://raw.githubusercontent.com/GITenberg/The-Memoirs-of-Sherlock-Holmes_834/master/834.txt
```

**ステップ4：インデックス構築**

```bash
zg index --embedding local/potion-retrieval-32m
```

**ステップ5：クエリ実行**

```bash
# セマンティック検索
zg query --human "An unseen creature left a few marks. What did the detective infer?" --limit 3

# 字句検索
zg query --fts "marks" --limit 5

# 正規表現検索（インデックス不要）
zg query --rg -n "detective" sherlock-holmes.txt
```

### 4.3 コードリポジトリのインデックス作成

```bash
cd /path/to/your/project

zg index \
  --embedding local/potion-code-16m-v2 \
  -g "src/**" \
  -g "docs/**" \
  -g "!dist/**" \
  -t ts
```

### 4.4 Embeddingモデル選択ガイド

| 使用シナリオ | 推奨モデル | 特徴 |
|------------|----------|------|
| 高速コードリポジトリインデックス | local/potion-code-16m-v2 | 小型静的Model2Vecモデル、1024トークン制限 |
| 高速英語ドキュメント検索 | local/potion-retrieval-32m | 検索最適化静的モデル、512次元ベクトル |
| 高速多言語ドキュメント検索 | local/potion-multilingual-128m | 101言語対応、256次元ベクトル |
| コード特化Transformer | local/jina-embeddings-v2-base-code | コード指向、多言語、8192トークンコンテキスト |
| ローカルモデルランタイムなし | qwen/qwen3.7-text-embedding | リモートAPI、128Kトークンコンテキスト |

**デフォルトモデル設定：**

```bash
zg config model set local/potion-code-16m-v2 --default
```

### 4.5 AIプログラミング助手との統合

```bash
# Claude Codeにインストール
zg install --target claude --yes

# すべてのAgentにインストール
zg install --target all --yes
```

## 七、設計哲学

### 7.1 ローカルファーストはただの スローガンではない

zvec-grepのローカルファーストにはいくつかの意味がある：

- **データはマシーンから離れない**：ファイルスキャンはローカル、指數ファイルはローカルに保存
- **インデックスの再利用**：一度インデックスすれば、CLIとすべてのAI Agent間で共有可能
- **プライバシーと性能の均衡**：ローカルEmbeddingモデルは完全にローカル実行；リモートEmbeddingは明示的認証必要

### 7.2 Agent指向の検索設計

従来の検索エンジンは人間指向——大量の結果を返し、人間が関連性を判断させる。

zvec-grepはAI Agent指向——少量の高品質な精密定位された証拠を返し、Agentのツール呼び出し回数とコンテキスト消費を減少させる。

**三つの重要指標：**
1. **より少ないツール呼び出し**：1回の精密検索が複数の粗い検索を代替
2. **より少ないトークン消費**：コンパクトな証拠チャンクはファイル全体より効率的
3. **より少ないノイズ**：ランキングとフィルタリングが無関係な結果を後に配置

## 八、まとめ

### 8.1 zvec-grepが解決する問題

**コアの問題：AI Agentのローカルコードベースでの検索困境**

zvec-grepの解決策：RRFフュージョンを使ってベクトル検索とBM25字句排序を統一——すべてローカルで実行。

### 8.2 主要な優位性

1. **ハイブリッド検索**：セマンティック発見 + 字句アンカー + RRFフュージョン
2. **ローカルファースト**：ファイルとインデックスがマシーンから離れない
3. **Agentネイティブ**：MCP統合で主要AIプログラミング助手がローカル検索能力を自动獲得
4. **構造認識**：コード記号、署名、パンくずリストを保持
5. **インデックス再利用**：一度のインデックス、CLIとすべてのAgentで共有
6. **柔軟なEmbedding選択**：小型ローカルモデルから大型リモートAPIまで

### 8.3 一言でまとめる設計哲学

> **zvec-grepのコアの洞察：AIプログラミング助手に必要なのはより強力なリモートモデルではなく、よりインテリジェントなローカルインデックスと検索。** セマンティック検索と精密マッチングを融合することで、AI Agentは「コードが何をするか理解し」「それがどこにあるかを見つける」ことを同時に実現——これすべてがローカルで完了、一行のコードも漏らさない。
