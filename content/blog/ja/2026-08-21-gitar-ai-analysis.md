# Gitar AI 深掘り：実際にコードを修正するコードレビュー

> 核心思想：**「コードレビューはコメントを残すことではなく、実際にコードを修正すること」**——Gitar は従来のコードレビューツールのようコメントを残すだけは行わず、CIの失敗原因を自動分析し、根本原因を特定した上で、直接PRに修正をプッシュします。Uberの開発スタックを構築したチームを発祥とし、2026年にSonarSource（SonarQube親会社）に加入し、企業向けコード品質エコシステムの一部となりました。

## 一、プロジェクト概要：コードレビューの次なる進化

Gitar は元Uberエンジニアが構築したAIコードレビューツールで、その位置づけは**「コードを修正するコードレビューボット」**です。

従来型のコードレビューツールとの根本的な違い：

| ツール種別 | 代表例 | 実施すること | 実施しないこと |
|-----------|-------|-------------|---------------|
| **従来型Botレビュー** | GitHub Actions、一部のAIレビューツール | コメントを残す | コードを修正しない |
| **Gitar** | Gitar | コメントを残す＋**修正を直接プッシュ** | 手動マージが必要 |

ユーザー証言が最も説得力を持っています：

> "Gitar has been a big help in maintaining the OpenMetadata open-source repository. Its code reviews are consistently actionable and relevant, not generic bot feedback, and it has caught real bugs and security vulnerabilities that reviewers might have missed."
> — Sriharsha Chintalapani、Co-founder & CTO、Collate（OpenMetadata）

### 主要データ

- **ユーザー規模**：130人以上のエンジニアチーム、1100以上のコードリポジトリ（Altruist）
- **統合範囲**：GitHub、GitLab、Buildkite、CircleCI、Bitrise、Harness
- **対応CIタイプ**：ビルドエラー、テスト失敗、lintエラー、flaky test
- **チーム背景**：Uber開発スタックチーム出身、2026年にSonarSourceに参加

### 一言で表すなら

**Gitar = AIコードレビュー + CI失敗自動修復 + 自然言語ルールエンジン**、すべてがPRインターフェース内で完了し、外部ツールへの切り替えが不要です。

## 二、手順解説：5分でセットアップ

### 2.1 環境要件

- GitHubまたはGitLabアカウント、少なくとも1つのorganizationに対して管理者権限を持っていること
- 開いているPR（またはPRを作成できるリポジトリ）
- 14日間無料トライアル、クレカ不要

### 2.2 インストール手順

**ステップ1：Gitarにログイン**

[app.gitar.ai](https://app.gitar.ai) にアクセスし、GitHubまたはGitLabアカウントでログインします。

**ステップ2：コードリポジトリを接続**

<Tabs>
  <Tab title="GitHub">
    「Install」をクリックし、Gitar GitHub Appをorganizationにインストールします。全リポジトリまたは特定のリポジトリのみをauthorizeできます。
    
    > 💡 後からGitHub organization設定の「Installed GitHub Apps」でリポジトリ権限を変更できます。
  </Tab>

  <Tab title="GitLab">
    GitLab接続にはサービスアカウント＋サービスアカウントトークンを使用します：
    
    1. 最上位のGitLabグループ配下に**サービスアカウント**を作成（Settings → Service accounts）
    2. サービスアカウントトークンを生成。`api`、`read_api`、`read_user`、`read_repository`、`write_repository`権限が必要
    3. 接続したいグループにサービスアカウントをOwnerロールで招待
    4. Gitarダッシュボードにトークンを入力して接続完了
  </Tab>
</Tabs>

**ステップ3：統合を接続（任意）**

Gitarはissueトラッキングツールやオブザーバビリティツールからコンテキストをプルできます。このステップでJira、Linearなどを接続できますが、後から設定 добавитьできます。

**ステップ4：Gitarを動作させる**

接続完了後、Gitarはリポジトリで初期スキャンを行います。効果を確認するには2つの方法があります：

- **新しいPRを開く**：変更を含むPRを作成すると、Gitarは接続済み全リポジトリで自動的に実行されます
- **既存のPRで試す**：ダッシュボードの「Try Gitar on Open PRs」カードを見つけ、既存のPRに対するレビューをトリガーします

**ステップ5：Gitarのフィードバックを確認**

数分後、GitarはPRに**ダッシュボードコメント**を投稿し、分析の概要を含みます。

、その後の流れ：
- **CI失敗** → Gitarが失敗原因を分析し、根本原因分析を投稿。auto-applyが有効な場合、Gitarは直接修正コミットをプッシュします
- **コードレビュー** → Gitarは問題のあるコード行にインラインレビューコメントを投稿し、ダッシュボードコメントにサマリーを投稿します
- **コメントコマンド** → Gitarのコメントに返信し、自然言語で変更をリクエストできます

> ⚠️ **重要**：Gitarは**絶対にforce-pushをしません**。すべての修正は新しいコミットとして追加され、コード履歴が完全に保持されます。

## 三、コア機能の詳細

### 3.1 AIコードレビュー

GitarはGitHubおよびGitLab上のPRを自動レビューし、セキュリティ、バグ、パフォーマンス、エッジケース、コード品質に関するAI駆動のフィードバックを提供します。

**対応レビュードメイン：**

| ドメイン | 内容 |
|---------|------|
| **セキュリティ分析** | 脆弱性、安全でないパターン、入力検証 |
| **バグ検出** | ロジックエラー、ヌルポインタリスク、エッジケース |
| **パフォーマンス分析** | アルゴリズム計算量、データベースクエリ、メモリ使用量 |
| **コード品質** | 可読性、保守性ベストプラクティス |

**レビュー出力方式：**

1. **インラインレビューコメント** — 未解決の発見事項すべてが対応するファイルと行に投稿され、フィードバックは読んでいるコードの場所に直接届きます
2. **ダッシュボードコメント — Code Reviewセクション** — 全体的な判定、重要度分類、解決済み発見事項の追跡を表示するサマリービュー

**カスタムコードレビュー指示：**

`.gitar/review/`ディレクトリにmarkdownファイルを追加して、レビュープロセスをカスタマイズできます。Gitarは`@`構文で他のファイルを含めるをサポートしています：

```
your-repo/
  .gitar/
    review/
      gotchas.md
    documents/
      rust_best_practices.md
```

`.gitar/review/gotchas.md`での使用方法：
```markdown
@../documents/rust_best_practices.md
@shared/common_rules.md
```

### 3.2 CI失敗分析と自動修復

これがGitarの最も価値のある機能です——**CIがなぜ失敗したかを教えるだけでなく、修正まで行ってくれます**。

**ワークフロー：**

1. GitarがCIログを読み取り、失敗したステップを特定
2. 失敗の根本原因を確定
3. PRのダッシュボードコメントに詳細説明を投稿
4. auto-apply設定に基づき、承認を待機または直接修正をプッシュ

**対応失敗タイプ：**

| 失敗タイプ | 例 |
|-----------|-----|
| ビルドエラー | コンパイル失敗、import欠落、型エラー |
| テスト失敗 | アサーション破損、setup欠落、期待値エラー |
| Lintエラー | コードスタイル違反、フォーマット問題 |
| Flakyテスト | レースコンディション、タイミング問題、非決定論的動作 |

**CI Retry（無関係失敗の自動リトライ）：**

GitarはPR変更无关のCI jobsを自動リトライできます——例えばflaky test、一時的なインフラ障害、ターゲットブランチ引起的失敗など。pipeline内で失敗がPR无关と分類された場合、これらのjobsは手動操作なしで再実行されます。

**Multi-Iteration修復：**

CI失敗は単一イテレーションで解決できない場合があります。Gitarは複数ラウンドの修復をサポートしています：

1. Gitarが元のCI失敗の修復をプッシュ
2. CIが更新されたブランチで再実行
3. CIが再度失敗した場合、Gitarが新しい失敗を再分析
4. Gitarが再度修復を試み、以前の試行の完全履歴を考慮

このループはCIが成功するか、Gitarがこれ以上の進展不可と判断するまで自動的に続きます。

### 3.3 Repository Rules：自然言語ワークフロー自動化

Repository Rulesを使用すると、pure markdownファイルで自動化ワークフローを定義でき、**コードを書く必要はありません**。

**クイックスタート：**

```bash
mkdir -p .gitar/rules
```

`.gitar/rules/security-review.md`を作成：

```markdown
---
title: "Security Review"
description: "Require security team review for sensitive changes"
when: "PRs modifying authentication or encryption code"
actions: "Assign security team and add label"
---

# Security Review

When sensitive code is modified:
- Assign @security-team as reviewer
- Add "security-review" label
- Post comment with security checklist
```

**ルールトリガータイミング：**

- PRオープン時 — すべての適用ルールに対して完全評価を実行
- 新しいコミットがPRにプッシュされた時 — 評価を再実行し、自動化をトリガーする可能性あり
- CIがPRで失敗した時 — CI関連自動化をトリガー
- PRメタデータ更新時 — タイトル、説明、レビュアー、ラベルの変更
- PRクローズまたはマージ時 — マージ後ワークフローを有効化

**対応アクション：**

- **コメント投稿**：PRにコメントまたはインラインコードレビューを投稿
- **ラベル適用**：検出条件に基づいてラベルを追加または削除
- **レビュアー割り当て**：変更検出時に特定のレビュアーを割り当て
- **コード変更提案**：コード変更を提案または実行

**統合サポート：**

- **Jira**：PRをJiraチケットにリンクし自動的にissueステータスを更新
- **Linear**：PRをLinear issueにリンクし自動的にステータスを更新
- **Slack**：Slackチャンネルに通知を送信
- **カスタムMCP（Enterprise）**：独自のMCPサーバーをカスタム統合として接続

### 3.4 フィードバックとインタラクション

Gitarは豊富なインタラクション方式を提供します：

| インタラクション方式 | 操作 |
|-------------------|------|
| `gitar fix`に返信 | 提案された修復を適用 |
| ワンボタン適用 | GitHubでは提案修復のチェックボックスをオン、GitLabではチェックマーク絵文字でリアクト |
| findingに返信 | 「this is intentional」や「already fixed」とコメントすると、Gitarが返信を処理してfindingをクローズ |
| Resolve/Unresolve | GitHubまたはGitLabでfindingスレッドをresolveすると、リアルタイムでfindingをdismiss |
| 曖昧な返信 | 返信が曖昧な場合、Gitarは推測せずに質問を投げて確認 |

## 五、設計哲学：四つの基本原則

### 5.1 修正不止是发现

传统コードレビューツールの哲学は**「問題を発見し、開発者に伝える」**です。Gitarの哲学は**「問題を発見し、問題を修正する」**です。

これはシンプルに聞こえますが、実装には以下が必要です：
- CI失敗の根本原因を理解する（単なる表面的なエラーメッセージだけでなく）
- 効果的なコード修正を生成する（単なる提案だけでなく）
- 修正後にCIが通過するかを検証する（単にプッシュ而已ではなく）
- 成功まで複数イテレーションで反復する（単一試行而已ではなく）

これは完全に異なる製品形態です——**Gitarは審査員ではなく、ジュニアエンジニアの役割**であり、レビューも可能ですが、実際の修正もできます。

### 5.2 CI-Aware：コードを孤立して見ない

多くのAIコードレビューツール**はコードのみを見て、CIは見ません**。これによりよくある問題がじます：レビュー時は問題ないように見えますが、CIが通りません。

Gitarの設計は**CI-Aware**です：
- コードレビューとCI分析は同じ製品の2つの機能であり、2つの独立したツールではありません
- CI失敗時、Gitarは分析して修正し無視しません
- 修正が新しいCI失敗を引き起こした場合、Gitarは自動的にリトライします

### 5.3 ゼロ設定スタート。工作流程を変更する必要なし

Gitarのデフォルト体験は**インストールしてすぐ使えます**：

- 動作にルール設定が不要
- ブランチ戦略の変更が不要
- 新しいCLIツールの学習が不要
- すべてのインタラクションが既に利用中のPRインターフェース内で完了

これにより導入ハードルが下がります——チームのためにGitarを使用するためにプロセスを変更する必要がありません。

### 5.4 SonarQubeエコシステムとの協調

Gitarは2026年にSonarSource（SonarQube親会社）に加入しました。这意味します：
- Gitarは**動的分析**（PRレベルのリアルタイムレビューと修正）を担当
- SonarQubeは**静的解析**（より広範なコードベースレベルの品質チェック）を担当
- 両者は補完し合い、コード品質の完全なライフサイクルをカバー

これは賢明な位置づけです——GitarはSonarQubeを置き換えようとはせず、「PRリアルタイムレビューと修正」というSonarQubeがカバーできないシナリオを埋めています。

## 六、重要な見解と示唆

### 見解1：AIコードレビューの「ラストマイル」は修正

現在の市場のAIコードレビューツール（CodeRabbit、Copilot Reviews、一部の开源Bot）はすべて「問題を発見し、開発者に伝える」段階にとどまっています。この段階の限界は：

- 開発者は問題を自分で理解する必要がある
- 開発者は修正コードを自分で書く必要がある
- 開発者は自分でCI検証を実行する必要がある

Gitarの価値提案は直接**「ラストマイル」**を切り込みます：単に問題を知らせるだけでなく、直接修正して検証までを行います。省かれるのは「問題発見」の時間だけでなく、「修正＋検証」の時間全体です。

### 見解2：「Uber開発スタック出身」は最も信頼性の高い推薦

Gitarの創業チームはUberの開発スタックチーム出身です。Uberは世界上規模最大エンジニアリング複雑性が最も高いテック企業の1つであり、その開発スタックは数万エンジニア、数千コードリポジトリの検証を経ています。

この背景意味します：
- Gitarは「理想情況」から設計されたものではなく、「超大チームの実態あるワークフロー」から出発しています
- 機能取捨選択は「実演」ではなく「実用」に偏っています
- CI、コードレビュー、大規模コードベース管理について成熟した認識を持っています

### 見解3：PRインターフェース内で全操作を完了することは正しい製品判断

多くの開発ツールの問題は**コンテキスト切り替えが必要**なことです：レビューはGitHubで見、CI詳細はCIシステムで見、コードはIDEで修正、問題はJiraで記録します。

GitarはPRインターフェース内で全操作を完了することを選択しました，这意味します：
- 開発者は別のツールのURLを覚える必要はありません
- コードレビュー、CI分析、ルール自動化がすべて同じ場所で行われます
- コンテキスト切り替えコストがゼロです

### 見解4：Repository Rulesが自然言語でワークフローを定義するのは正しい方向

従来のCI/CD設定（GitHub Actions、GitLab CI）はYAMLファイルを書き、ワークフロー構文を理解し、複雑な条件ロジックを処理する必要があります。

GitarのRepository Rulesは**自然言語**でワークフローを定義します：
- 「When PRs modifying authentication code」と書く——YAML条件を書く 대신
- 「Assign security team and add label」と書く——YAMLアクションを書く代わりに
- ルールファイルはmarkdownであり、普通テキストエディタで管理できます

これは正しいです。**ワークフローは人間が読むべきものであり、マシンが解析する設定ファイルであるべきではありません**。

### 見解5：SonarSourceに参加することはGitarの最適な出口

Gitarは独立発灭ではなくSonarSourceに参加することを選択しましたが、これは成熟した製品判断です：

- SonarQubeは世界上最大のコード品質ユーザーベースを持っています
- GitarはSonarの営業・流通ネットワークを活用して企業ユーザーにリーチできます
- SonarQubeは「PRリアルタイムレビューと修正」能力を欠いており、Gitarはこの空白を埋めます

ユーザーにとって，这意味しますGitarはより長い製品ライフサイクルとより安定した企業サポートを持つことになります。

### 見解6：Auto-applyには信頼が必要だが、建立する価値はある

Gitarのauto-apply機能は、AIが直接あなたのブランチにコミットをプッシュすることを意味します。これはチームがAIの修正能力に自信を持つことが必要です。

この信頼を構築するには：
- AIの修正精度が高い（ユーザーフィードバックは「無効なコメントを1つも見たことがない」）
- すべての修正は新しいコミットであり、決してforce-pushしない（コード履歴が完全に保持）
- 複数イテレーション機構により、修正が新しい問題を引き起こすことを防止

信頼が構築されれば、auto-applyの効率性向上は的巨大です——開発者はCI失敗後に自分でデバッグし、修正を書き、プッシュし、CIを再実行する必要がありません。

## 七、SonarQubeとの関係

多くの方が質問します：GitarとSonarQubeの違いは何ですか？衝突しますか？

| ディメンション | Gitar | SonarQube |
|-------------|-------|-----------|
| **分析タイミング** | PR作成/更新時（リアルタイム）| CI/CDパイプライン中または定时スキャン |
| **分析範囲** | PR変更の增量 | コードベース全体 |
| **コア機能** | レビュー + **修正** | 静的解析 + 品質ゲート |
| **ワークフロー** | PRインターフェース内で完了 | 独立Web UI |
| **修正機能** | 自動修正プッシュ | 問題位置と提案を提示 |
| **ユーザー** | 開発チーム | 開発チーム + 安全/コンプライアンスチーム |

**両者は補完関係であり、代替関係ではありません：**

- GitarはPRレベルのリアルタイムレビューと修正を担当
- SonarQubeはコードベースレベルの静的解析与技术債管理を担当

GitarがSonarSourceに参加したことで、両者の統合がさらに進み、PRからコードベースまで完全なコード品質カバレッジを提供します。

## 九、結語

Gitarの最大価値は「又一个AIコードレビューツール」ではなく、**コードレビューの役割を再定義したこと**です。

従来ツールは審判官です：問題を発見し、開発者に通知し、自分では動きません。

Gitarはチームメイトです：問題を発見し、根本原因を分析し、実際に修正し、結果を検証します。

審判官からチームメイトへの转变は、AIが開発プロセスにおける役割升级の縮図です。Gitarは単に「ここに問題がある」と告げるだけでなく、直接その 작업을替你を行います。それがAIプログラミングツールのあるべき姿です。
