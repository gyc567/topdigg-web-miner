# anything2explainer 徹底解説：テーマを一つ渡せば、コードで描かれた解説動画が仕上がる

## 序章：AI に一つのことを説明させたいのに、動画は厄介だ

とても具体的なニーズを仮定してみよう。

論文をちょうど読み終えた、あるいはある技術概念を 理解した状態で、3 分間の解説動画を動画チャンネルに投稿したい。テーマは決まり、原稿の骨子もだいたい描けている。ここで詰まっているのは画面である。

素材を探す？ 著作権が曖昧だし、寄せ集めた素材が論理のある一本の映像になることはまずない。AI 動画生成モデルを使う？ 現状では生成されたクリップがつながらず、テキストが間違えられ、毎フレームが揺れる。ナレーション用のアバターを使う？ 技術的には問題ないが、喋る頭はメカニズムを何も説明しない。原稿を読み上げるだけだ。

さらに一歩退いて、AI コーディング agent に 1 フレームずつ描くコードを書かせるのはどうか。

この方向は正しいが、すぐに 2 つ目の問題に突き当たる。Remotion 自体が用意しているのは画布だけで、作品がどうあるべき姿かは教えてくれない。1 つ目の agent が描いたショットはきれい、2 つ目の agent が描いたものは PPT みたい、3 つ目は字幕帯がどこにあるかすら忘れている。5 つの agent の成果物を突き合わせると、5 つの別会社が作ったみたいになる。

では、どうすればいい？

anything2explainer の答えは率直である。コードだけを書くのではなく、方法論そのものを書けというのだ。「AI 生成の解説動画をどう撮るか」という一件事を、スタイル規格、モーションボキャブラリー、構図と光の硬いルール、agent 分担プロトコル、定量的な品質検査スクリプト、そして品質の物差しとなる完成サンプルの一本へと分解している。

これは実行できるコマンドラインツールではなく、AI 向けの映画制作ハンドブックに似た代物である。

## 一、プロジェクト説明：リポジトリの中身は何か

### 1.1 一行での位置づけ

テーマ、あるいは動画にしたい記事を入力すると、1280×720 の H.264 MP4 が出力される。TTS ナレーション、単語単位で整列した字幕、章カード、上部 HUD、下部のチャプター進捗バー付きだ。中国語でも英語でもよい。

重要なのは、すべてのフレームがコードで描かれていることである。素材ライブラリも、生成式動画モデルも、他人の動画から切り出した 1 フレームも存在しない。

作者 Vincentwei1021 は CITATION.cff 上の位置づけを "software" としており、公開日は 2026-09-09、ライセンスは PolyForm Noncommercial 1.0.0。非商用は無料で、商用は事前の許諾が必要だが、それで作った動画の権利は自分自身のものである。

### 1.2 これは CLI ではない

この点は単独で述べる価値がある。知っている人はこれをツールとして試したが、試し終わって「反応がない」と 拍子抜けになるからだ。

リポジトリの中身は、AI コーディング agent が作品を作り上げるための方法論一式である。 実際に実行されるものは 3 つだけである。

- コンパイル可能な Remotion 4 のテンプレートプロジェクト（`template/`）。`new_project.sh` で作業ディレクトリにコピーして使う。
- メインセッションと各 agent に向けた仕様文書の束（`reference/`）。
- すでに完成したサンプル作品（`examples/rag/`）。調査原稿、ナレーション台本、絵コンテ表、44 個のショットのソースコード、そして QC レポート 5 件が付属している。

作者は skill に Claude Code のバッジと Codex のバッジを付けている。つまりこれはこの 2 種の agent に読み込まれる「スキルパッケージ」で、人がコマンドを叩くためのソフトウェアではない。

### 1.3 リポジトリ構成の早見表

```
SKILL.md                  流程主干：9 个阶段、4 个确认点、质量标尺
reference/                写给主会话和各 agent 的规范
  style-guide.md            安全区、调色板、字体、图元目录、版式规律
  motion-vocabulary.md      入场/强调/光效/离场/运镜的公式与帧数
  composition-and-light.md  主体尺寸三档、光跟主角、高光时刻编排、QC 量化判据
  narration-guidance.md     口播文案写作原则（纯英文，已译中文）
  narration-storyboard.md   解说词格式与预算、配音参数、分镜令牌、镜头模式表
  research-brief.md         研究员 prompt 与事实规则
  agent-build-rules.md      构建 agent 协议
  agent-qc-rules.md         QC agent 协议
  prompts.md                六种 agent 的 prompt 模板
  lessons.md                五部片子的踩坑记录与根因
template/                 可编译的 Remotion 4 工程
  src/common/               雾底、星点、点阵波、glitch、缓动、字幕、进度条
  src/ui.tsx  src/fx.tsx    图元与调色板/光效、纵深、运镜图元
  src/overlay/              片头、章节卡、HUD、流程轨、片尾

examples/rag/             样片全套纸面文件与成片帧

```

`examples/contrast/` というディレクトリは特筆に値する。これはまさに採点表である。左側には作者が 2026-09-08 に skill で作った別の作品《eCPM 与广告竞价》のフレーム、右側にはサンプル作品《RAG 与知识库》のフレームが並び、6 組の対比のそれぞれが具体的な欠陥を指している。主役が小さすぎる、主役に光がない、高光时刻の编排がない、結果項目の文字が小さすぎる、背景に破片が散っている、締めに見栄えの象征物がない。

### 1.4 他のツールとの違い

作者自身が比較表を掲げている。選定の根拠として使わせている。

| ツール種別 | 成果物 | anything2explainer との違い |
|---|---|---|
| 生成式動画モデル（Sora、Veo、Runway） | prompt から素材を合成 | 成果物はピクセルではなく決定的なコードである。画面のどの数値にも出典 URL まで辿れる。どの 1 フレームもショットのファイルを 1 つ直せば修理できる |
| デジタルアバター／アナウンサー系ツール（HeyGen、Synthesia） | デジタル司会者が原稿を読む | 司会者は要らない。モーショングラフィでメカニズムを説明し、画面はナレーションで駆動する |
| 手書き Remotion / Motion Canvas | プログラミング可能な動画キャンバス | キャンバスの上側に方法論一式を納品する。調査 → ナレーション → 絵コンテ → 並列構築 → QC という流れに、スタイル規格、モーションボキャブラリー、品質の物差しとなるサンプル作品が付く |
| Manim | Python による数学アニメーション | agent 主導のエンドツーエンドのパイプライン。TTS 整列字幕、章、QC を伴う。Python ではなく React / TypeScript |

2 行目の「司会者は要らない」という判断は、見た目以上に重要である。アバター動画の視覚情報量はゼロであり、原稿を読み上げただけだ。一方のモーショングラフィは、構造・順序・数量を同時に見せられる。README には的確な一文がある。ナレーションは理由・結果・比較・判断を担い、画面は構造・順序・数量を担う。

## 二、コア思想：なぜコードで描き続けるのか

### 2.1 譲れない 3 つの原則

**第一、画面はすべてコードで描く。** 任意の実写 B-roll は著作権フリーのものだけを許し、さらに MANIFEST（sha256、出典 URL、ライセンス、用途）への登記を要する。既存動画のフレームやクリップは一切使用できない。

**第二、事実には出典が必ずなければならない。** 画面に出るすべての数値・年・機関・人名・英文用語は、その作品の調査ドキュメント内で出典 URL が見つからなければならない。調査で検証していない内容を画面にもナレーションにも載せない。

**第三、全編で一つの通例サンプルを貫く。** ナレーションと画面は最初から最後まで同じ例を使う。サンプル作品で使われたのは「旅費精算」というシーンである。問いは「差旅报销の上限是多少？」で、幻覚の回答は「每天 1000 元、全国统一」、正しい回答は「宿泊上限每天 600 元[1]、一线城市 800 元[2]」、出典は「员工手册 p.12」と「差旅补充规定 2025」。すべての章が同じサンプルテキストを共有する、これは硬い制約である。

2 つ目がプロジェクト全体で最も価値のある設計である。動画の視聴者は出典をクリックできない。数値が一つでも間違えば終わりで、訂正のコストは記事とは桁違いである。「調査段階で検証しなければ画面には載せない」という前倒しにすることは、後から QC でピクセルから文字を読み取るよりずっと信頼できる。

### 2.2 「コードで描く」は実際に何を買ってくるのか

このプロジェクトを理解する鍵がここにある。動画生成モデルとコードレンダリングはいずれも「コンピュータに絵を描かせる」ものだが、手に入るものはまったく違う。

**決定性。** すべてのアニメーションはフレーム番号の純粋関数であり、乱数はシード付きの `rnd(...)` を使い、文字幅は DOM で測るのではなく計算で出す。だから再レンダリングすれば出てくるフレームは完全に同一である。動画生成モデルにはこれができない。同じ prompt を 2 回回せば 2 つの別物が出てくる。

**編集可能性。** どのショットが 1 つでも問題があれば、agent は `SCxx.tsx` の 1 つの数値を直して再レンダリングする。動画生成モデルにはこれができず、クリップ全体をやり直すしかなく、次回のほうが良い保証もない。

**追跡可能性。** 画面に出るどの数値も、調査ドキュメント内の 1 つの URL まで辿れる。画面はもともとそのドキュメントから「描かれた」ものだからである。

**検証可能性。** 最も過小評価されている項目である。画面がコードだから静的解析ができる。`selfcheck.py` はレンダリングせずに、すべてのショットのソースコードを走査して、点滅が何箇所あるか数え、それを絵コンテ表のホワイトリストで突き合わせ、画面に出るすべてのリテラルを抽出して事実リストと突合できる。この 3 つは数秒で走り、QC agent はピクセルから調べるので、抽出されなかったフレームは見えない。作者は `lessons.md` で率直に言っている。この 3 つの検査が捉えるのは QC がピクセルからは追えない問題だ、と。

### 2.3 一つ反直感的な判断

多くの人の第一反応は「AI で動画を描くなら生成モデル、コードレンダリングは古いやり方」だ。作者はこの判断を 1 組のデータで否定する。

作者が skill で作った《eCPM 与广告竞价》とサンプル作品《RAG 与知识库》を 1 フレームずつ突き合わせたところ、両作品のモーション数、リズム、グローの総面積はほとんど同じだった。

| 指標（完成映像の逐フレーム、内容区画） | 広告竞价 | RAG サンプル |
|---|---|---|
| 1 フレームあたりの平均変化量 / 1 分あたりのモーションイベント数 | 0.47 / 72 | 0.56 / 76 |
| 最大物体の高さの中央値 | 172px | 219px |
| 最大物体 <110px が ≥1.5s 続く時間の割合 | 29% | 12% |
| ソースの光効果語 halo / sweep / ghost | 0 / 0 / 0 | 14 / 12 / 5 |
| ソースの skew / perspective / rotate | 1 / 0 / 4 | 7 / 1 / 15 |

差はすべて「どれだけ大きく描くか、誰が光るか、高光时刻をどう編成するか」の 3 つの話にあり、「動きの量」とは関係ない。

これは多くの人が踏む落とし穴を説明している。skill の初期版には安全区、ホワイトリスト、ゼロへの落とし込み、ビートといった規律項が書かれていて、新作はこれらの項目ではむしろ做得更好だが、「主体はどれほど多大に描くか、光は誰に当てたいか」だけは、サンプル作品を作った人の頭の中にしか存在しなかった。だからこそ画面は小さく暗く、4 ラウンドの QC を通ってもなお見栄えが悪かった。

直し方はモーションを追加することではない。硬いルールを追加することである。これは `composition-and-light.md` が存在する理由のすべてである。

## 三、詳細チュートリアル：ゼロから一本の作品を走らせる

以下は完全な 9 ステージのフローである。ステージ 0 からステージ 8、そしてその中に挟まれた 4 つの確認ポイント。

### 3.1 ステージ 0：プロジェクトの作成（5 分）

```bash
git clone https://github.com/Vincentwei1021/anything2explainer.git
ln -s "$PWD/anything2explainer" ~/.claude/skills/anything2explainer   # Claude Code
ln -s "$PWD/anything2explainer" ~/.codex/skills/anything2explainer    # Codex
```

依存関係：

```bash
# Node ≥18（模板的 npm install 会装 remotion 4.0.507 / react 19）
brew install ffmpeg          # 抽帧 / 转码，必需

python3 -m venv ~/.venvs/a2e && source ~/.venvs/a2e/bin/activate
pip install 'edge-tts==7.2.8' numpy pillow scipy   # edge-tts 必须锁版本
```

`edge-tts` のバージョン固定は気病ではない。README にははっきり書いてある。Microsoft のエンドポイントを追跡していて、バージョンをまたぐと壊れる、7.2.0 以降は単語境界の明示的なリクエストが必要になる。`scipy` は `frame_metrics.py` だけが使う。

英語作品の場合はさらに `kokoro soundfile` と `espeak-ng` を導入する。

ラズベリーパイや ARM 環境でも作者は検証済みで、違いは 3 点ある。スクリプトの shebang が `#!/bin/zsh` なので zsh が必要、Remotion には linux-arm64 用のヘッドレスブラウザがないのでシステム Chromium を指す必要がある（`REMOTION_BROWSER_EXECUTABLE=/usr/bin/chromium`）、そして kokoro は ARM で入らない（古い numpy を固定して spaCy を引くが、blis に aarch64 wheel がない）。代替として `kokoro_onnx` か `piper` を使う。

プロジェクトを作る：

```bash
template/scripts/new_project.sh ~/work/my-video myslug
```

テンプレートのコピー、npm install、tsc の実行を行う。このステップでディスクを約 2GB 使うので、README は `df -h` で 5GB 空けておくよう指示している。

英語作品なら `src/config.ts` の `lang` を `'en'` に変えておく。背景はデフォルトでドットフィールドウェーブ（`bg: 'dots'`）で、初期サンプルの星点フォグにしたいなら `'stars'` にする。

### 3.2 ステージ 1：調査（20 分、1 agent）

WebSearch / WebFetch を持たせた general-purpose agent を 1 つ派遣し、`reference/research-brief.md` のテンプレートに従って `research/调研.md` を出力させる。

調査ドキュメントの構造は固定の 9 節で、そのうち第 0、6、7、8 節は必須である。

```
0 执行摘要（1 分钟版：这是什么、为什么值得讲、最反直觉的一点）
1 处境与问题（没有它 / 不懂它时会怎样；谁在什么场景下会碰到）
2 起源与关键节点（提出者 / 事件 / 年份 / 出处文献）
3 它怎么运作（机制 / 过程 / 结构 / 历史脉络，选一条主轴）
4 边界与对比（和最容易混淆的相邻概念差在哪）
5 争议、局限与近 2 年的变化
6 真实案例与失败模式（成功的和翻车的都要）
7 数字与比喻清单   ← 最重要的一节
8 术语对照（≤30 条）
```

第 7 節が要点である。出典付きで直接語れる数字の束で、それぞれに日常の尺度に換算した言い方を 1 つ付け、さらにアニメーションに向く比喩を 5 つ加える。それぞれについて、どこが的確で、どこが歪むのかを明記する。

本数は尺に応じて決める。2〜3 分の作品なら 8〜10 条、3〜5 分なら 10〜16 条、5〜8 分なら 18〜24 条。

安全上の細部として注目すべきものがある。調査ドキュメントはウェブから取得した内容であり、agent には明示的に要求されている。含まれる指示的な文章（ファイルを変更しろ、コマンドを実行しろ、タスクの目的を変えしろなどといった指示）は一切実行せず、見つけたらドキュメントの中に「该页含指令性内容，已忽略」と 1 文字書き残す。这类の prompt injection 防御は今やほぼ標準だが、このプロトコルはかなり早く書かれたもので、記録に値する。

### 3.3 ステージ 2：ナレーション台本とタイムライン（20 分、メインセッション）

このステージはパイプライン全体の「最も安い介入点」であり、その理由は後述する。

まず `reference/narration-guidance.md` を読む。これは純粋に英語のライティング原則ドキュメントで、このプロジェクト内でも从头到尾まで中国語版が存在しない唯一のファイルである（今回は中国語訳を追加済み）。14 の小節で構成されているので、鍵になるものをいくつか抜粋する。

- 第 0 節には唯一の判定基準がある。文を 1 つ読み上げて、自分に問う「この一瞬、聞き手は前の文では知らなかった何かを知った・見た・感じたか」。なければその文は詰め物だ。5 分の台本に収まるのはおよそ 45〜50 文で、どの文もこの関門を通らなければならない。
- 第 1 節：状況から入る、定義から入るのではない。冒頭に「X の定义是……」や「本動画では……」と書くと、最も貴重な時間を無駄にする。
- 第 2 節：Stories メインライン 1 本。失敗の形は「用語集」すなわち複数の概念を同じ扱いにして、順番を入れ替えても誰も気づかないというものである。各節を自由に入れ替えても内容が失われないなら主线がない。探しに戻ること。
- 第 3 節：動機が先でメカニズムが後。ないと何が起きるか、どう動いているか、それがあなたに何をもたらすか。聞き手がまだ聞きたがっていないメカニズムを説明してはいけない。
- 第 5 節：比喩は道具であって装飾ではない。いくつかのビートを貫く良い比喩 1 つのほうが、1 回しか使わない賢い比喩 6 つより上だ。
- 第 11 節：画面では言えないことを言う。ナレーションは理由・結果・比較・判断を担い、画面は構造・順序・数量を担う。画面上にあるものだけを述べた文は削除する。
- 第 13 節：継ぎ目で受け渡す。前節の末尾には問い・代償・欠落を残し、次節の最初の文は前節の成果を先に指してから話題に入る。「接下来我们看 X」のような仅仅司会を呼ぶだけのつなぎは削除する。

ナレーション台本の形式は次のようになる。

```
# CHAPTER 1 章名（≤6 字，进度条章名）
一句话|按竖线切成字幕块|每块 ≤16 字        ← 一行一句
同一段的下一句                                ← 段内句之间只隔 10 帧
                                              ← 空行 = 段落分隔：一段 = 一个镜头
新的一段（= 下一个镜头）
## gap 20                                     ← 可选：额外插空白
```

縦線は字幕の分割に使われるだけで、読み上げには影響しない。空行はショットの境界であり、この 1 条の全編構造の土台である。

サンプルのナレーション台本の冒頭はこうなっており、リズムをそのまま感じることができる。

```
大模型很聪明|但它有三个天生的短板
第一|它的知识有截止日期|训练之后发生的事|它一概不知
第二|它读不到你公司内网里的文档|也不知道你昨天刚写的会议纪要
第三|遇到不知道的问题|它不会说我不知道|而是一脸自信地编一个答案|这就是幻觉
怎么办|重新训练一遍|成本太高|而且明天数据又变了
于是工程师们想出了一个办法|让模型开卷考试
考试前先把资料整理成一本手册|答题时先翻手册|再作答
这套方法就是今天的主角|RAG|检索增强生成
```

概念紹介の文が 1 つも、すべて状況の語りであることに注目する。

確認ポイント 2 はここにある。ナレーション台本の全文、章の区分、字数、推定再生時間をユーザーに見せて「この版の文案で大丈夫ですか」と尋ねる。章名と HUD の小節名は 1 行に分けて列出する。進捗バーに載るのはこの数語だけだからで、作者は自己チェックの 3 問も与えている。この数語だけを見たとき、影片を見ていない人も各章で何が話されるか言えるか。すべて名詞句か。並べると理解できる一本の主线になっているか。

作者は反例を具体的に書いている。6 本目の作品がユーザーから名を指され、進捗バーの章名は「感觉还行 / 搭台留痕 / 两把尺子 / 诊断与证明」だった。これは評価文と軽口であり、観客が一目で見ても中身がわからない。正例はサンプルの「为什么要RAG / 知识库构建 / 检索与生成 / 评估与进阶」である。これを影片を見ていない人に書き写せば、その人も各章で何が話されるかを言える。

確認ポイント 3 はすぐ続けて「配音有没有偏好的 TTS」と尋ねる。なければデフォルトを使う。中国語 edge-tts `zh-CN-YunxiNeural`（云希、男声、原速不加速、约 5.5 字/秒）、英語 kokoro-82m `am_liam`（Liam、男声）。希望があれば自分の TTS で完成 wav を作って `public/assets/<slug>/audio.wav` に置き、`src/common/timeline.ts` と `subs.ts` を手で記入する。以降のフローは完全に変わらない。

そしてナレーションを実行する。

```bash
python3 scripts/tts_build.py
```

文ごとに合成し、WordBoundary で字幕ブロックを切り出し、ナレーション wav、フレーム単位のタイムライン、字幕表を出力する。停止の戦略はスクリプト内に書いてある。段内の文間に 10 フレーム、段落末尾にもう 20 フレーム、章の前は 45 フレーム。

**停止は段落末尾だけに置き、すべての文の後には置かない。** この 1 条はユーザーからの指摘で決まったもので、毎文で止まるようにすると作品全体が重くなる。段落末尾の 30 フレームはおよそ 1 秒であり、観客は「这句话讲完了，画面也落位了」と感じ、それこそでカットされる。

スクリプトはさらに、最終ブロックが 45 フレームに満たない段落末尾の文を `¶` マーク付きでターミナルに一覧する。この文の後ろには `## gap 15-30` を足すか、絵コンテ化のときに最終ビートの要素を直前のブロックに吊り付ける。

実行後、完成映像の長さが希望範囲に収まっているかを確認する。差が 15% を超えたら、文の追加削除で組み直せ、語速の変更で押し通すな。

これで凍結する。確定後は語句を変更しない。各ショットのフレーム番号は構築グループのコードにハードコードされており、1 文字変えるだけで作品全体の再アライメントが必要になる。

### 3.4 ステージ 3：絵コンテ（25 分、メインセッション）

`script/storyboard_src.md` を書き、フレーム番号の代わりにトークンを使い、`分镜表.md` へレンダリングする。

```bash
python3 scripts/render_storyboard.py
```

トークンは次の形である。`{S12.from}` `{S12.to}` `{S12.c3}`（3 番目の字幕ブロックの開始フレーム）`{C2}`（第 2 章の開始フレーム）`{TOTAL}`。オフセットも付けられる。たとえば `{S12.from-8}`。

1 ショット 1 行で、列は 镜头 / 帧 / 节拍 / 画面 / 动效 / **主角·尺寸** / **光** である。

後ろの 2 列は後から足されたもので、これが最も価値ある改訂だった。もともと絵コンテ表には「画面」と「動效」しかなく、構築グループは主体をどれほど大きく描くべきか、光を誰に当てればいいか分からなかった。その結果、主体の高さの中央値は 172px に留まり、主役は全員光の当たらない白い線枠だった。この 2 列を足したあとのサンプルは 219px である。

動效列の各行の末尾には「持续：…」と「停留：…」の 2 文が必要である。

- **持续**：この字幕ブロックの動詞をどの動作で次の拍まで撑ぐか（データフロー、矢印に沿って走るパルス光点、行ごとのタイピング、枡ごとの点灯、成長、回転、隔壁の開閉、キューの圧縮）。ほかのカメラワークを持たないショットは「1.0→1.05 慢推」と書く。**漂浮、飘动、呼吸は書かない。**
- **停留**：最終拍要素の落位フレームから退场開始点までのフレーム数。≥30、目標は 30 から 45。足りない場合は 3 つのどれかを選ぶ。最終拍要素を前に吊り付ける、文案に戻して `## gap` を足す、近隣のショットに併合する。

絵コンテ表末尾の「全局约束」には 7 blocks を書く。示例语境、事实清单、闪烁白名单、复用图元清单、章界清单、高光时刻清单、扫光白名单、そして §9 の継続アクションと落位保持の規則全文も加上。

### 3.5 ステージ 4：オーバーレイと図元（10 分、メインセッション）

テンプレートには片頭、章カード、HUD、流程轨、片尾が既に付いており、図元ライブラリは `src/ui.tsx`、光効果とカメラワークの図元は `src/fx.tsx` にある。テーマに合わせて意味的アイコンを 2〜5 個追加するだけでよい。

サンプルで追加したのは `DocIcon`（文書）、`DBIcon`（データベース）、`ChunkCard`（テキスト塊）、`LLMIcon`（大規模モデル）である。

そして still を 1 枚出して確認する。

```bash
scripts/still.sh Overlay 40,<章节卡帧>,<有轨帧>,<片尾帧> <绝对路径> ov
```

### 3.6 ステージ 5a：試写（15 分、1 agent）

G1（第 1 章の前半）だけを派遣し、完了したら最初の 30 秒をレンダリングする。

```bash
scripts/preview.sh 30
```

これが確認ポイント 4 である。ユーザーが変えたいもの（配色、字号、语速、片头、示例语境）はここで 1 回で変更し切る。

作者のこの判断はきわめて清醒だ。ここで 1 回直すコストは 1 グループ分だが、作品全体をレンダリングし終えてから直すのは全グループのコストになる。

### 3.7 ステージ 5b：並行構築（40 分、残りの各グループに 1 agent ずつ）

グループ数は尺に応じて決め、サンプルの区分では 8 グループ、G2 から G8 を派遣する。各グループは 5〜7 個のショット、1 ショット 1 ファイルで `src/shots/Gn/SCxx.tsx` である。

指示の出し方は `reference/prompts.md` の構築 prompt を使い、`reference/agent-build-rules.md` を添え、さらに G1 を验收済みのスタイル見本として名指しして読ませなければならない。
ここにはいくつかの硬い制約があり、構築プロトコルの中で繰り返し強調されている：

- フレーム番号 `N = useCurrentFrame() + F0`、すべてのアニメーションは N の純関数、乱数は `rnd()` のみ、`Math.random` は禁止、useState / useEffect によるアニメーションは使わない。
- 変更できるのは `src/shots/Gn/**` だけで、Main / Root / common / 他のグループには触れない。
- ハードカット前の退場は必ずゼロに落とす： `opacity = 1 − (n/N)^1.5` を使う、毎フレーム 6.7% の exitFade は使えない（最終フレームに 40% から 60% が残ると「バシッ」と鳴ってしまう）。
- 入り軌道は字幕帯を貫通してはいけない：下方向からのスライド入りは Δ ≤ 120、画面外から入る場合は横方向のスライド入りで Δ 260 から 320。
- 性能のレッドライン：`feConvolveMatrix` は禁止、`filter: blur()` の σ ≥ 1、1フレームの DOM ノード数 ≤ 600、SVG filter インスタンス ≤ 6。違反すると作品全体のレンダリングが 10 倍から 50 倍遅くなる。
- 完了前には必ず `npx tsc --noEmit`、各ショットで still を最低 6 枚、30 フレームのテスト描画、そして `python3 scripts/motion_check.py <Gn>` を実行する。

最後のこの項目は最新のもので、継続アクションと落位静止時間を数値化している：各ショットで最長の静止は ≤3 秒、最終ビートの安定期間は ≥30 フレーム。

### 3.8 ステージ 6：レンダリング（5 分）

```bash
npx tsc --noEmit
VER=v1 scripts/render.sh
```

8000 フレームはおよそ 4 分半の尺で、レンダリングに 3 から 4 分、concurrency 6。成果物は `renders/<slug>_v1.mp4` と `fin_frames/`。

そしてメインセッション自身が 6 枚の contact sheet をつなげて通読し、その後次のように実行する：

```bash
python3 scripts/frame_metrics.py --out qc/frame_metrics_v1.md
```

このステップで計測するのは：各ショットの最大物体高さ、主角区のグロー面積、紫の破片指数、静止区間。

### 3.9 ステージ 7：QC と修正（60 から 90 分）

各章に QC agent を 1 つ、`reference/agent-qc-rules.md` に従って実行し、`qc/qc_v1_Cn.md` を出力させる。修正 agent はグループ単位で割り当て、1 つの agent が扱うのは 1 グループから 2 グループまで。

v2 をレンダリングし、2 つの再検証 agent が v1 の問題を 1 つずつ確認しつつ回帰通読を含む小修を行い、v3 をレンダリングする。

最終検査では 4 つのことを行う：グリッチホワイトリストのスキャン、ライトスイープホワイトリストの照合、frame_metrics による構図と光の再確認、motion_check による完成作品としての再測定。

作者は繰り返し 1 つのことを強調している：**グループレベルの motion_check に合格しても完成作品としての合格を意味しない。** 第 4 作品では v1 のグループレベル 48 ショットすべてが基準を満たしていたのに、完成作品としての再測定では 11 ショットが上限超過で、3 つは真の静止、8 つは小面積の動作だけだった。理由はグループレベルが低解像度でレンダリングされ、測定値が甘くなるためだ。したがってワークフローにおける完成作品としての再測定は必須で、省けるものではない。

### 3.10 ステージ 8：納品

`交付说明.md` を作成する：完成作品、音声の出典、事実の出典、サンプルの文脈、QC の結論、既知の保留項目、目次。デフォルトではエンドロールに `built by Anything2Explainer skill` と署名し、`config.builtBy` を空文字に設定すれば消せる。

そして新しい知見を `reference/lessons.md` に書き戻す。この 1 条によってリポジトリ全体が継続学習システムになり、これまでの 5 作品の教訓がすべてそこに残っている。

## 四、multi agent 分業プロトコル：1 作品にいくつの agent を起動するか

これがプロジェクト全体で最も「エンジニアリング」な部分であり、他の人がそのまま真似できない部分でもある。

### 4.1 6 種類のロール

`reference/prompts.md` は 6 種類の agent prompt テンプレートを定義しており、それに `research-brief.md` と 2 冊のルール文書を合わせて、合計 8 冊のファイルが完全なスケジュールプロトコルを構成している。

| ロール | 数量 | 担当 | 成果物 |
|---|---|---|---|
| リサーチ担当 | 1 | WebSearch/WebFetch で事実を査証する | `research/调研.md` |
| 構築グループ | 8（サンプル版） | 各グループ 5–7 ショット、1 ショット 1 ファイル | `src/shots/Gn/**` + `BUILD_NOTES.md` |
| QC | 各章 1 | 書面基準に沿ってフレームごとに検査 | `qc/qc_vN_Cn.md` |
| 修正 | 1–2 グループにつき 1 | QC レポートの各項目を修正 | コード + BUILD_NOTES への追記 |
| 再検証 | 2 章につき 1 | v1 の問題が本当に直ったか確認 + 回帰通読 | `qc/qc_vN+1_recheck_C**.*.md` |
| 最終検査 | 1 | グリッチの適合、ライトスイープのホワイトリスト、frame_metrics、完成作品としての motion_check 再測定 | `qc/qc_vN_final.md` |

### 4.2 割り当ての第 1 原則：1 つの agent には重作業 1 件だけ

作者は `lessons.md` にこのことをはっきりと書き残している：構築で 5 から 7 ショットは重作業、1 章分の QC は重作業、1 から 2 グループの修正は重作業。2 件目には軽い作業だけを渡す。

理由（作者が踏んだ罠）：大量の画像を読み込んだ agent に重作業を再割り当てすると、およそ 30% の確率でそのまま力尽きる、"input too long" と報告される。

これはもう 1 つのよくある誤解とちょうど対照的である：QC agent には「調べながら append する」ことが要求されるが、これは推奨ではなく硬い要求である。ある作品では 1 つの QC agent が最後にまとめて書き出し、1 時間走らせて成果ゼロ、メッセージにも反応せず、TaskStop して再割り当てするしかなかった。理由は単純で、途中で殺されたら、それまでに積み上げた結論がすべて失われるからである。

### 4.3 並行数の上限：pane はマシン全体で共有されている

これが最も直感に反する 1 条である。作者は第 3 作品でこれを踏んだ：pane の上限に前回より早く到達し、同時に他のセッションを 14 個開いており、5 つ目の agent を割り当てたところで `respawn pane failed: fork failed: Device not configured` となった。

対処法は 4 つずつ波に分けて割り当て、1 波が完了して解放されてから次の波を割り当て、割り当て前に `ListAgents` でマシン全体の使用状況を確認し、後続の QC と修正のラウンドのために 1 から 2 個の pane を空けておくこと。

この条は Claude Code でも Codex でも同じであり、作者は prompt テンプレートの末尾に「割り当てとウォッチドッグ」という段落を特に置いている：完了した agent は速やかに TaskStop して解放し、API エラーで殺されたものはまず 1 回 SendMessage で呼びかけ、10 分間成果物がなければ TaskStop して再割り当てする（再割り当て時には「ディスク上の半成品を再利用し、未完成部分だけ補え」と明示する）、30 から 40 分ごとに各グループの index.ts と BUILD_NOTES の mtime を確認する。

### 4.4 agent の自己評価をそのまま鵜呑みにしてはいけない

作者は 1 グループの自己評価を抜き取りで確認した：「中間の年号がぼやけて読めない」——実際に出力は鮮明に読めた、そのグループ自身も振り返りでこの自己評価が楽観的すぎたと認めている。

しかし彼の結論は「agent は嘘をつく」ではない、二つのことをセットで言っている：報告は抜き取り検査すべきだが、agent が間違えたと決めつけるのは早い、まず証拠を全部見ることだ。もう 1 つの項目は彼自身が読み違えており、報告は実際には正しかった。

### 4.5 構築グループは絵コンテ表そのものの誤りを見つける

これは作者が最も重んじている資産の 1 つである。第 3 作品の最も価値ある 3 つの改善はすべて構築グループから来た：価値棒の式と画面注釈の矛盾、年号ダイヤルの事実適合性の穴、そしてそれに基づいて自発的に「ミリ秒の数値を出さないカウント」方針をずらしたこと。

彼の処理方法は 1 つ 1 行で裁定を出して、その裁定を作品全体の通則に広げて絵コンテ表に書き戻すこと、たった 1 箇所の変更を承認するだけでは終わらせない。

関連するものとして、もう 1 つの硬い要求がある：構築グループの合理的逸脱（サンプルテキストの差し替え、中国語の正式名称の追加、トポロジーの変更）は、出典がわかれば通す。

### 4.6 メインセッション自身も静的検査を行う

作者は QC だけに頼ることに満足していない。 彼は 3 つの「レンダリング不要で走らせられる」検査を自分で保有している：フレーム被覆の静的解析（フレーム区間の穴と重なり）、ソースコードのリテラルと事実リストの突合、グリッチホワイトリストのソースレベルでのカウント。

この 3 つは数秒で走り終え、捕まえるのは QC がピクセルから探せない問題だけである。第 4 作品では、ソースの突合が一度に実時間カウンターを 1 つ掴んだ——画面には"This second +2405"と表示され、そのすぐ下の灰色の小文字には"one day several billion times"と書かれており、両者には 30 倍の差がある。4 つの QC agent 全員が見逃していた。

## 五、まとめ：このプロジェクトの中核となる主張

一連のプロトコルを通しで読めば、その主張を 7 つに归纳できる。

### 主張 1：AI 創作の品質のボトルネックは生成能力ではなく規範にある

このプロジェクトのすべての agent の成果物の質は、規範の密度に強く依存している。`reference/` 配下の 11 冊の文書、テンプレート内の 100 を超えるコンポーネントと関数、コード量そのものは大したものではなく、規範の体積はコードより厚いのだ。

`lessons.md` の記録と照らし合わせれば規範の働きが明白になる：初版の skill にはセーフエリア、ホワイトリスト、ゼロへの落とし、ビートといった規律項目があり、新作品はサンプル作品以上にこれらの項目做得で。汉arthman、しかし「どれだけ大きく描くか、誰が光るか」は書かれていなかったため、新作品は小さくて暗くなった。規範に書かれていないことを agent が自分で思いつくことはない。

### 主張 2：決定性と編集可能性は、画面が鮮やかであることより重要である

2.2 節ですでに展開した。核心は、画面がコードであるから、静的解析ができ、1 フレームを精密に直せ、出所まで辿れる。この 3 つを合わせたものは、「この 1 フレームがとても綺麗」よりもはるかに価値がある。

直接的帰結として：この仕事には生成モデルを使ってはいけない。

### 主張 3：制約は明面上に書く、agent に理解を期待するな

「作品全体で 1 つの通例サンプル」「各ショット 1 つの主角」「各ショットでグリッチは最大 1 箇所」——これらは提案ではなく硬いルールであり、しかも機械的に検査できるものでなければならない。

`selfcheck.py` が存在している意味はここにある：それは「グリッチホワイトリスト」を 口号的スローガンから 1 回のカウント突合へと変える。ホワイトリストには 23 項目あり、スクリプトが走らせた結果はちょうど 23 箇所でなければならない、1 つでも多くても少なくても問題である。

作者は 1 つの反面例を挙げている：絵コンテ表の中で "glitch" という単語が 1 マスにしか書かれていないと、構築 agent はすべての文字にグリッチを付け、完成作品として 102 箇所が出て、ユーザーは即座に却下した。その後「各ショットでグリッチは最大 1 箇所、そのショットの要点の語だけに」と改めたところ、21 箇所まで減らして通った。

### 主張 4：ナレーションの質は、情報の量ではなく主线があるかどうかで決まる

`narration-guidance.md` の第 2 節と、第 4 作品の振り返りは同じ事象の表と裏である。第 4 作品の初版 48 文は参考書の小節の順序どおりに書かれており、ユーザーの第一印象は「型にはまりすぎて退屈」。写作原則に沿って独立に書き直したバージョンの盲評は 8.2 対 4.3 だった。

根本原因は文筆ではなく、主線がないことにある。章を自由に並べ替えても損失がないなら、それは主線がないということだ。

ここで学びに値する手法がある：作者は「どう書けば退屈にならないか」を「絵コンテ規範」から切り離し、単独で `narration-guidance.md` としてまとめ、SKILL.md の中でステージ 2 に必読と規定した。`narration-storyboard.md` は固定の章立てを規定せず、フォーマット、予算、画面インターフェースのみを残し、ショットパターン表の左列も題材に依存しない「画面関係タイプ」に変わった。

**規範は抽象度に応じて正しい場所に置くべきである。** ナレーション原則は汎用的なものだが、具体的な題材ごとのテンプレート下に吊ると、テンプレートの 1 種類として扱われてしまう。

### 主張 5：配音は確定してから、フレーム番号がハードコードされるからである

これはワークフロー全体で最も直感に反するエンジニアリング上の判断であり、4 つの確認ポイントの設計根拠でもある。

一度配音が確定すると、フレーム番号は各ショットのコードに書き込まれる。一文字の修正＝作品全体の再位置合わせ＝すべての構築グループの再実行。作者はそのため確認ポイント 2（ナレーション確定）を配音より前に置き、README でも率直にこう書いている：ここがワークフロー全体で最も安価な介入ポイントである。

逆に言えば、確認ポイント 1 と 2 のほうが 3 と 4 より価値が高い。1 つ目（尺と言語）は文数、ショット数、構築グループ数、すなわちこのワークフローの規模を決める。2 つ目（文案確定）は間違えた場合にどれだけ再実行が必要になるかを決める。

### 主張 6：数値基準は「グループレベル」と「完成作品」を区別する

第 4 作品の教訓：グループレベルの motion_check は 48/48 すべて基準を満たしたのに、完成作品としての再測定では 11 ショットが上限超過だった。

低解像度レンダリングの測定値は甘くなる。作者の対策はグループレベルのレンダリングを 0.5 倍 + JPEG q80 に変え、`--frames` モードで「最長静止区間内の全解像度における変化ピクセル数」という列をもう 1 つ加えることで、真の静止（<800）と小面積の動作（800–2500）を区別できるようにした。

さらに細かい条項も 1 つある：小面積の動作の直し方は**動きの大きさの加算**であって、要素の加算ではない。動く要素はより明るく、より大きく、より密にし、主角本体は 30 フレーム周期で呼吸 ±2% とする、较小的な図形をwir 重ねるのではなく。

この区別は決定的に重要である。「静止している物体に漂わせたり、揺らしたり、呼吸させたりを与える」のは明確に禁止されている。作者が与えた理由は：動作は動詞そのものの動作でなければならない、動詞の動作が見つからないショットはむしろ静止させたままでよい、静止 ≤3 秒は欠陥ではない。

### 主張 7：agent に教え終わったら、agent がどう評価されるかも教え込む

これは私が最も見落としやすく、同時に最も価値がある点だと思う。

作者は「agent にコードを書かせる」だけでは満足せず、agent のために判据を書き、量化スクリプトを書き、最終検査リストを書き、「各ショットについて少なくとも 1 行の結論を出す（OK でも書け）」という機械的に見える要求すら書いた。

さらに、反例に関する項目もある：`examples/contrast/` には 6 組の反例フレームが置かれ、構築 agent は作業開始前に必ず Read で `contrast_sheet.jpg` と最低 6 枚の `ref_*.jpg` を見て物差し（基準）を確立しなければならない。

これは「品味」を「伝達可能な参照物」に変えるという手法である。品味は prompt に書き込めないが、1 組の対照フレームとして与えることはできる。

## 六、設計哲学の拆解

各所に散らばった原則を集めると、このプロジェクトの設計哲学はおおよそ次の 7 つになる。

### 6.1 色は意味である

パレットの中のどの色にも固定の意味があり、「好看だから」で使われるものは 1 つもない：

| 色 | 値 | 意味 |
|---|---|---|
| PURPLE | #6630F8 | 現在の重点 / アクティブ / ブランド |
| ORANGE / CORAL | #F05F41 | 指標の数字、警告、「もう一方」、クエリポイント |
| RED_DEEP | #EC081F | 濃赤の警告ブロック（ハルシネーション、信頼できないもの） |
| GREEN | #8FF740 | 緑チェック（正しい） |
| GREY 系 | #A0A0A1 から | 重点外の文字、灰色のブロック、グリッド線 |

ルールは「1 フレーム内で紫の重点は大面積 1 箇所まで」だ。配色は美的問題ではなく情報問題である。

### 6.2 光は現在の主角にだけ当てる

主角には必ず光が付く（`GLOW_PURPLE` の 2 層の紫グロー、足元の `HaloRing`、あるいは大字の紫のハードドロップシャドウ `6px 6px 0 PURPLE`）、サブ要素は光らない。

光には 3 つの階層がある：白の bloom（構造線は常時）< 紫のグロー（主角は常時点灯 + 現在の重点）< 白フラッシュ（イベント、3–6 フレーム）。作品全体でこの 3 つだけを使い、光の色は紫・橙・赤だけにする。

さらに細かなルールもある：主角の光は 30 フレーム周期で ±15% 呼吸する。重点が移ったときは前の箇所の光は 8 フレーム以内に消す。退場のときは先に光を消す（6 フレーム）してから全体をフェードアウトさせ、光を消さないままハードカットしてはいけない。

### 6.3 サイズは 3 段、4 段目は認めない

主角 ≥170px、または大字 ≥96px かつ行全体の幅 ≥300px。サブ要素 60–110px。ラベルと説明 22–30px。サブ要素 ≤4 個、ラベル ≤6 個。

「3 段の外に 4 つ目のサイズを作らない」という制約の価値は、「このアイコンを少しだけ大きくすべきか」という無限の微調整を自動的に排除できる点にある。

配套设施の判据が空フレームである：コンテンツ区の最大物体の高さ <110px が 45 フレーム超継続すると中程度の欠陥、<80px が 45 フレーム超継続すると重度の欠陥。

### 6.4 ライトスイープは最も高価な一手的、作品全体で最大 2 回

3 回の紫光の横掃 + ステージの光線 + ゴーストの輪郭という登場型の演出は、作品全体で最も高価な视觉效果であり、作者が与えた予算は **≤2 箇所** である：核心概念の初登場には必ず 1 箇所、2 箇所目については最終の振り返りに回すのが選択肢。

理由はユーザーフィードバックである。第 5 作品は 47 ショットで 3 連のスイープを 8 箇所使い、ユーザーは完成作品を見て「多すぎる」と言った。サンプル作品は 44 ショットで 1 回しか使っていない。

絵コンテ表ではこのために「ライトスイープのホワイトリスト」を独立した列として設け、リストにないショットでは一律に `LightSweep` / `StageLine` / `GhostText` を使わない。`selfcheck.py` はファイル単位でカウントし、最終検査ではフレーム単位で照合する。

これは学びに値する設計である：prompt の中で「光る演出は控えめに」（モデルは理解できない）と言うのではなく、ハードな上限とホワイトリストを与えるほうがよい。

### 6.5 継続アクション + 落位静止

これがプロジェクト全体で最も遅く成立し、同時に最も重要な運動学ルールであり、2 つの正反対の失敗に対応している：

- **「入ったら停止」**：要素がビートに乗って入ってきて止まったまま次のビートを待つ。光はグロー呼吸だけ。第 4 作品を数値化したところ：6 ショット中 4 ショットで静止フレームが 42% から 72%、最長静止 2.8 秒。
- **「落ちたら即カット」**：「静止 30 フレーム超は禁止」で直し过头た結果、47 ショットで 34 か所のズームイン、48 文すべて「継続」、最終ビートで要素が着地するとすぐ最終 8 フレームの退場に入る。ユーザーの原文は「すべてのアニメーション刚刚落位，马上就切到了下一个镜头，几乎没有停留」。

ルール 1 は**継続**である：各字幕ブロックが語る動詞に対して、画面上には次のビートまで続くアクションが 1 つあること。要素の入場後は 3 秒（90 フレーム）を超えて完全に静止してはいけない。ただし**指標のためにだけ、静止した物体に漂わせたり揺らしたり呼吸させたりすることはしない**。

ルール 2 は**保持**である：各ショットの最終ビートで要素が着地してから、30 から 45 フレーム（1 から 1.5 秒）の安定期間を入れてから退場する。安定期間中は新しい要素を加えず、カメラワークも動かさず、HUD も変えない、走行中の動詞のアクションは継続していい。カメラワークは最終ビートには入れない。

時間はどこから来るのか：ユーザーが裁定した。完成作品を純音声より 5% から 8% 長くして保持と引き換えにすることを許可する。停止は段落末尾にだけ置き、毎文の後には置かない。

作者は文書の中でこのルール群とその量化スクリプト `motion_check.py` を一緒に納品しており、规范に書いただけではない。

### 6.6 衔接には両側をはっきり書き出す

作者は典型的な罠を踏んでいる。絵コンテ表が「ハードカット」とだけ書くと、両側がそれぞれ「自分は動かない、相手はビートのフレームから入る」と解釈し、結果としてグループ境界に 6 から 8 フレームの空フレームができ、1 作品中 5 か所もの発生となった。

そのため書き方が規定されている："A の最終 8 フレームでゼロへフェードアウト + わずかな下方向のパン；B は先頭フレームから最初の要素群を SoftIn"。

配套设施として、受け渡しが掃除より優先される：一个ビートで語りが終わる短い文は前のショットに付け、受け渡し移動 16 フレームでよけてやって、それのために場面を掃き出して描き直さない。

章の境界はさらに厳格である：章の最初のショットは前の章の最後のショットの主角か象徴物を受け継いだなければならない（同一コンポーネント同一パラメータ、縮小と移動は可）、同時にナレーションも承上啓下でなければならない。作者が挙げた反面例は「章の冒頭でゼロから始める」と「章の冒頭で幕だけ告げる」の 2 つであり、違いは：幕だけの記入は不可、承上啓下は可。

### 6.7 事実の適合は美的問題である

これが最も面白い。表面上は QC のルールだが、実体は設計哲学である。

作者の判据は：画面上に現れるすべての数字は、出所まで辿れるなければならない。これもたらされる直接的なデザイン上の結果：

- カウントアニメーションの中間値も「画面に出る数字」である。年の 1995→1998 の線形カウントでは 1995、1996、1997 が 4 から 6 フレーム鮮明に読めてしまう。ミリ秒の 0→120 なら "37 ms""88 ms" がちらつく。これらはすべて事実リストに含まれないので、読めなくするか、カウントをやめるかのどちらかにする。
- 年を判読不能にするには容赦なくやる必要がある：blur 6.3→1.3px では中間年もまだ鮮明に読める。12→2px では倒数 2 番目の年も約 2 フレーム判別できる。最終的に 12→9px かつ全期間 + 確定フレームでゼロにすることが初めて綺麗になる。作者はこの仕様をテンプレート内の `YearRoll` コンポーネントに封じた。
- サンプルデータ（型番、類似度スコア、金額）は納品説明の中で「示意値」と明記する。

これは作者自身を困らせているのではなく、観客を守ることである。ビデオは出典をクリックできず、照合もできず、観客はただ信じるしかない。

## 七、限界、疑問と今後の見どころ

### 7.1 先に言っておくべき 3 つの現実的な制限

**第一に、これは「テーマを入れれば作品ができる」という製品ではない。** 4 つのポイントで人（或者说 1 つの agent メインセッション）の判断が必要だ：尺と言語、ナレーション確定、配音エンジン、最初の 30 秒のサンプル。4 つの確認ポイントを 1 つも省略できず、作者も省略する気はない。

「入力を渡せば完成品が得られる」という視点で言えば、成品にはまだ遠い。だが「agent が 1 本の作品を独力で仕上げる」という視点で言えば、すでにかなり遠いところにいる。

**第二に、コストは安くはない。** サンプル版の 8 つの構築グループが 40 分並列で動き、QC が 2 ラウンドで 60 から 90 分、ワークフロー全体で約 2 時間、ディスクは 2GB から。そしてこれは自分自身がすでに Remotion に熟練している場合の話である。

**第三に、ライセンスが壁である。** PolyForm Noncommercial 1.0.0、非商用なら無料、商用なら作者事前の許諾が必要。解説、チュートリアル、個人プロジェクトなら問題ないが、商用製品に。截止 October 用したいならまず交渉が必要。

### 7.2 私が最も問い直したい 2 つの問い

**1 つ目の問い：この方法の作者のいないマシンで再現できるだろうか？**

リポジトリ全体の語調は「1 人が 1 本ずつ作品を作り、毎回つまずいてその都度 lessons.md に書き戻す」である。プロトコルの完全さはこのつまずきの記録に強く依存しており、それらは 2026-09-07 から 09-10 までの 4 日間で溜まったものである。

この「経験の沈澱型」文書の利点は、1 条 1 条に実際のやり直しの裏付けがあり、重みがあること。リスクは、それが作者のあのマシン、作者のあの Claude Code 設定、作者のあの pane 上限の環境でのみ検証されていることである。README は「Linux なら動くはず、Windows は未テスト」と書き、ラズベリーパイでも通ったと述べており、これはもう誠実な説明ではあるが、いずれにせよ「誰でもどこでも動かせる」わけではない。

**2 つ目の問い：このワークフローのボトルネックは本当に何なのか？**

作者はすべての注意力を「画面を良くする」ことに置いていた——主体サイズ、光、セットピース、ライトスイープの上限、継続アクション、落位静止、はすべて視覚的なものだ。しかし彼自身が `lessons.md` の中で、より面白いことを認めている：

> スタイル伝達（2026-09-08 振り返り）：skill は禁令を書いたが審美の駆動を書かなかった……しかし「どれだけ大きく描くか、誰が光るか、セットピースのどう組み立てるか」はサンプルを作った人の頭の中だけにある。

つまり彼は「AI の画面が酷い」という症状の治療に大量の紙幅を割き、2 年かけて動いた。しかし `lessons.md` 全体の構成から見ると、**真に希少なのは審美のルールではなく、「1 人の審美判断を、伝達可能・検査可能・反復可能EICな形に分解する方法」この方法論である。** このプロジェクトは現時点でその方向への 1 回の成功した試みであり、すでに成熟した汎用方法ではない。

旁証として他自己的振り返りの結論がある：「差距不在『动得多不多』，别往加动效的方向修。」 この文の価値は、それが否定的な判断——1 つの方向を排除した intriguing ものであり、方向を示したものではないことにある。本当に難しいのは、どこを直すべきかを見つけることである。

### 7.3 今後なにが期待できるか

- **縦持ち。** README は 9:16 はサポートしないと明記しており、テンプレートとすべてのセーフエリアルールは 1280×720 の横持ちを前提としている。ショート動画プラットフォームはほぼ縦持ちであり、これが最も明瞭な空白である。
- **より多くの言語。** 現在は中国語と英語のみで、それぞれに速度モデル、字幕予算、デフォルトの音色がある。`lang` フィールドの設計は拡張の余地を残している。
- **より高品質な TTS。** 現在の経路は「自作 TTS」——ユーザーが自分で 완성した wav を生成し、時間軸を手で埋める。作者はデフォルトの edge-tts と kokoro が「使えるが最高ではない」と明言している。这意味着ワークフロー全体は音声クローンや強制アラインメントといった技術に対して開かれている。
- **反例ライブラリの拡充。** `examples/contrast/` は今や 6 組のみで、正例はすべて同一の作品（サンプル）由来である。異なる課題的正例がもう少しあれば、審美基準の伝達に 도움이 될。

### 7.4 最も学びに値する設計上の決定

このプロジェクトから 1 つだけ持ち帰るとしたらこれだ：

**「品味」を「参照物 + 判据 + カウンター」の三つ組にする。**

- 参照物：`examples/contrast/contrast_sheet.jpg` にある 6 組の正反例フレーム。agent は作業開始前に必ず見る。
- 判据：`composition-and-light.md` にある 3 段のサイズ、光の帰属、空フレームの閾値、ライトスイープの上限。
- カウンター：`selfcheck.py` がグリッチホワイトリストを数え、`frame_metrics.py` が主体の高さとグローを測り、`motion_check.py` が静止時間を測る。

前の 2 つだけでは、agent は理解するが道を逸れる。3 つ目を足せば、逸れは即座に発見される。

作者は第 4 作品の結末で非常に現実的な観察を示した：ある agent グループが「中間の年号がぼやけて読めない」と報告した時、実際の出力は鮮明に読めた。彼はこれを agent の信頼性の問題とは見なず、代わりに「ソースコードから画面に出るすべてのリテラルを静的に抽出し、事実リストと突合する」ことを 1 つの検査ステップとして追加した。

**这就是一个能持续改进的系统该有的样子：每次失败都变成一个新的检查项，而不是一次性的抱怨。**

## 八、一言でまとめると

anything2explainer は「AI に科普解説動画を作らせる」ということを、1 つのプロンプトの問題から 1 つのエンジニアリングの問題へと変えた。

-IT ピクセルを生成するのではなく、決定的なコードを生成する。モデルを審美の理解に頼るのではなく、参照物・判据・カウンターで審美を伝達する。agent が 1 回で正解することを期待するのではなく、やり直しのたびに lessons.md に書き戻し、次の作品の検査項目に変える。

技術コンテンツを作りたい人にとって、このリポジトリで最も実用的なのは 9 つのステージではなく、`reference/` の 11 冊のドキュメントに積み上げられたものかもしれない：主体はどれくらいの大きさで描べきか、光は誰に当てべきか、セットピースをどう並べるか、ライトスイープは最大で何回か、停止はどこに置くべきか、なぜ「入ったら停止」も「落ちたら即カット」も欠陥なのか、そして 3 つの数秒で走り切るスクリプトで、agent が本当にそれを守ったかどうかをどう検査するか。
