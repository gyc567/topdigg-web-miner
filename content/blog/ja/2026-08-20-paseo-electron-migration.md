## 導入：創業者が自分を誤っていたことを認める

2026年5月28日、Paseo創業者の**Mo Boudra**は、テクノロジー圈を驚かせるようなブログタイトルを发表了：**「I was wrong about Electron」**（Electronのことを間違っていた）。

これは軽い自己批判ではない。このブログ記事の中で、BoudraはPaseoデスクトップアプリケーションの技術選定において経験した「心臓移植」——TauriからElectronへのフレームワーク移行の詳細な振り返りを記載している。

ちょうど**14.4kのGitHub Stars**を獲得し、コミュニティ广泛关注を集めたオープンソースプロジェクトにとって、このような率直な振り返りは極めて珍しい。更に难得的是，他没有止步于"认错"，而是把整个迁移决策链条、踩坑细节和心路历程完整地摊开在了所有人面前。

**この記事は技術選定についての公開レッスンである。**

## 一、Paseoとは？

技術的詳細に踏み込む前に、基本的な問いに答えよう：**Paseo到底是什么？**

Paseoは**デスクトップグレードのAIエージェントオーケストレーションプラットフォーム**であり、**同一个界面**で異なる厂商のAIコーディングアシスタント——**Claude Code、Copilot、Codex、OpenCode、Pi**——を呼び出すことを使命としている。

言い換えれば，又是另一个AIコーディングツールではなく、**統一的オーケストレーションレイヤー**である。どのAgentを使っても、Paseoの同一のインターフェースとワークフローで管理、切替、協調できる。

### コア機能一覧

| 機能 | 説明 |
|---|---|
| **マルチエージェント統一入口** | Claude Code、Copilot、Codex、OpenCode、Piに対応 |
| **ローカルファースト実行** | エージェントがローカルマシン上で実行され、開発環境に完全アクセス |
| **クロスデバイス同期** | iOS、Android、デスクトップ、Web、CLIの5平台統一体験 |
| **音声制御** | 音声入力をサポート、直接「話す」だけでタスクを実行 |
| **プライバシー完全保証** | テレメトリなし、トラッキングなし、強制ログインなし |
| **エンドツーエンド暗号化** | クロスデバイスペアリングは暗号化伝送を使用 |
| **オープンソース AGPL-3.0** | コードはオープン、社区驱动 |

### Paseoの建築哲学

Paseoの建築設計は明確な核心理念を反映している：**あなたのコードとデータは常にあなたの中にある**。

ローカルポート`6767`上で動作する**Node.js daemon**を通じて各エージェントプロセスをオーケストレーションする。すべてのクライアント（デスクトップ、モバイル、Web、CLI）は**WebSocket**でこのdaemonと通信する。クロスデバイスペアリングは**エンドツーエンド暗号化のrelayサービス**を通じて実装される。

この建築はいくつかの重要な優位性ををもたらす：

1. **自然なプライバシー保護**：コードは第三方サーバーを経由しない
2. **優れたパフォーマンス**：daemonはローカル開発環境と直接やりとりし、ネットワーク遅延がない
3. **高い拡張性**：TypeScript SDKにより 누구나Paseoの上に独自の統合を構築可能

## 二、技術的建築の詳細：1つのdaemon + 複数のクライアント

### 2.1 Monorepo構造

Paseoはmonorepo管理を採用し、コアパッケージは以下の通り：

```
packages/
├── server/    # Node.js daemon、エージェントプロセスオーケストレーション、WebSocket API、MCPサーバ
├── app/       # Expoクライアント（iOS、Android、Web）
├── cli/       # paseo CLIツール
├── desktop/   # Electronデスクトップアプリケーション
├── relay/     # relay伝送層と暗号化モジュール
└── website/   # 公式サイトとドキュメンテーションサイト
```

### 2.2 Daemonモードの動作原理

Paseo daemonはシステム全体の中枢神経である。以下の职责を担当：

- **エージェントライフサイクル管理**：各コーディングエージェントプロセスの起動、停止、監視
- **WebSocket API**：すべてのクライアントにリアルタイム通信インターフェースを提供
- **MCP（Model Context Protocol）サーバ**：各大AIモデルプロバイダーとの標準接続プロトコル実装
- **クロスプロセス調整**：複数エージェント間のコンテキスト伝播とタスク分散

daemonの起動は1行のコマンドで完了：

```bash
# Dockerデプロイ
docker run -d --name paseo \
  -p 6767:6767 \
  -e PASEO_PASSWORD=change-me \
  -v "$PWD/paseo-home:/home/paseo" \
  -v "$PWD:/workspace" \
  ghcr.io/getpaseo/paseo:latest

# CLI起動（ローカル開発）
paseo daemon start
```

### 2.3 WebSocketリアルタイム通信

すべてのクライアントはWebSocketで`localhost:6767`に接続，这意味着：

- デスクトップクライアントはエージェント出力ストリームをリアルタイムで確認可能
- モバイルクライアントはリモートでタスク進捗を監視可能
- CLIツールは任意のターミナルワークフローに埋め込み可能

```bash
# CLIでdaemonに接続
paseo connect --agent claude-code

# 現在のアクティブエージェントを確認
paseo status
```

### 2.4 TypeScript SDK：プロジェクトへのシームレス統合

Paseoの上に独自のツールやプラットフォームを構築したい場合は、公式の`@getpaseo/client` SDKを使用：

```typescript
import { createClient } from '@getpaseo/client';

const client = createClient({
  password: process.env.PASEO_PASSWORD,
  host: 'localhost',
  port: 6767,
});

// daemonに接続してアクティブエージェントリストを取得
const agents = await client.listAgents();
console.log('アクティブエージェント:', agents);

// 指定エージェントにタスクを送信
await client.sendTask({
  agentId: 'claude-code',
  prompt: '現在のプロジェクトのビルド速度を最適化',
});
```

## 三、TauriからElectronへの移行：完全な技術的振り返り

### 3.1 最初の選択：なぜTauriだったのか？

プロジェクト初期、Mo Boudraは多くの開発者と同様にElectronに偏見を持っていた——**サイズが大きい、メモリ消費が高い、起動が遅い**。彼らがTauriを選んだ理由は筋が通っていた：

- **Rustバックエンド**：パフォーマンスが優れる、メモリ消費が低い
- **小型バイナリパッケージ**：Tauriでパッケージ化されたアプリケーションはElectronよりずっと小さい
- **ネイティブwebview**：各プラットフォームで「ネイティブレベル」のパフォーマンスが得られると思っていた

これらは確かにTauriの реальные優位性である。しかし問題は、**理論的優位性と実際の展開の間には全エンジニアリングの現実が横たわっている**ことである。

### 3.2 問題1：Linux上のWebKitGTK噩梦

TauriはLinux上でシステムのバンドルWebKitGTKエンジンに依存しており、自分のブラウザランタイムをバンドルしない。

これにより3つのレベルの問題が発生する：

**（1）バージョンの断片化**
異なるLinuxディストリビューションがバンドルするWebKitGTKバージョンは大きく異なる。Ubuntu 22.04はWebKitGTK 4.1を使用しているが、Fedora 40はまだ4.0を使用している可能性がある。APIの微妙な差異だけで、同じ機能が2つのディストリビューションで全く異なる動作をする可能性がある。

**（2）Wayland互換性問題**
现代LinuxデスクトップはWaylandに移行中だが、WebKitGTKはWaylandでのIMEサポートやハードウェアアクセラレーションにまだ既知の問題がある。

**（3）実際のレイアウト差異**
同じCSS flexboxレイアウトは、macOSのWKWebView、WindowsのWebView2、LinuxのWebKitGTK下で異なるレンダリング結果になる可能性がある。Boudraはこう坦言した：「Centeringの問題を2日間デバッグして、それがUbuntu上でのみ発生することを発見した。」

### 3.3 問題2：通知システム：简单そうだが実は深い穴

デスクトップ通知は些細に見えるが、プラットフォーム適応能力を本当に試す機能である。

Paseoがサポートする必要があるもの：**通知をクリック → アプリウィンドウをフォーカス → 関連タスクにジャンプ**。

これは以下を精确に処理する必要がある：

- 通知のクリックイベントキャプチャ
- アプリウィンドウのアクティブ化とフォーカス管理
- クロスプラットフォーム動作の一貫性

Tauriの通知プラグインは基本機能を提供するが、**デスクトップ通知のクリック処理をサポートしない**。Boudraは複数のRust cratesを試したが——すべて、目標とするすべてのプラットフォームで完全な通知対話能力を一貫して提供できるものはなかった。

最終的に、各プラットフォームに**プラットフォーム固有のネイティブ通知処理コード**を書くことを強いられた。クロスプラットフォームの一貫性を追求するプロジェクトにとって、これは大きな皮肉である——クロスプラットフォーム問題を解決するために、より多くのクロスプラットフォーム問題を引き込んだ。

### 3.4 問題3：Daemonの複雑さ：Tauri Sidecarの実際の代价

PaseoのコアはNode.js daemonである。これはElectronエコシステムではほぼ自然な選択である——Node.jsはElectronにプレインストールされており、追加設定は不要である。

しかしTauriの方式是**Sidecar**（サイドカー）パターンである：

- Sidecarは**独立コンパイルされたバイナリ**であり、特定のプラットフォームとターゲットトリプル用にコンパイルされる
- 処理必要：クロスプラットフォームパッケージ化、ファイルパス解析、プロセス起動引数、権限設定、バージョンアップグレード
- 新しいターゲットプラットフォームが追加されるたびに、sidecarのコンパイルマトリックスが2倍に拡大する

Boudraの評価は核心を突いている：**「私は実際には『RustでElectron環境を再実装している』ことに気づいた——それもElectronより成熟していない形で。」**

### 3.5 移行プロセス：痛苦だが予想外に速い

移行を決定した後、チームは1週間でTauriからElectronへの切り替えを完了した。

Boudraは、このプロセスは大量の再書き込みを必要としたが、**予想よりずっと速かった**と特に言及した。理由は：

1. **アプリロジックは完全に変更不要**：すべてのビジネスコードはJavaScript/TypeScript層にあり、移行はこれに影響しない
2. **Electronツールチェーンはより成熟**：デバッグツール、Hotreload、エコシステムプラグインはすべてTauriより豊富
3. **クロスプラットフォームの一貫性でQAコストが大幅に削減**：各ディストリビューションごとに個別にデバッグする必要がなくなった

移行完了後の体験改善は全方向的であった：

- **クロスプラットフォームUIが一貫して表現**され、「Ubuntuではあのボタンが曲がっている」問題がなくなった
- **通知機能が正常に動作**し、クリック処理を含む
- **daemon管理が大いに簡素化**され、Node.jsランタイムはElectronプロセスに直接管理される
- **全体的に軽く感じられる**ようになり、これは最も予想外の発見かもしれない

### 3.6 移行後の振り返り：Tauriは悪くない，只是不适合

Boudraはブログ記事の结尾で特に強調した：Tauri本身は糟糕な選択ではない——特定のシナリオでは確かに非常に優れている。彼の過ちは**シーンのニーズを客観的に評価せず**、「雰囲気」でTauriを選んだことである。

> 「私はこの選択をしたのは、Rustが好きだったから、あるいはTauriがHNで大きな人気があったからだ。しかし私は本当に自問しなかった：私のアプリケーションシナリオ到底是什么か？」

この振り返りは任何の技術的詳細よりも価値がある。

## 四、設計哲学：Paseoから提炼されたエンジニアリング方法論

### 4.1 技術選定が答えるべき3つの問い

Paseoの移行経験は私たちに教える：技術選定は「この技術は良いか」だけを聞いてはならず、以下を問わなければならない：

**① 私の実際のシナリオ是什么か？**
Paseoはマルチエージェントオーケストレーションプラットフォームであり、以下が必要：

- 安定したクロスプラットフォームwebviewレンダリング（3つのプラットフォームすべてで完璧に一貫）
- Node.js runtime（daemonは本質的にNode.jsアプリケーション）
- 複雑な通知とウィンドウ管理

これらはすべてElectronの**コア機能**であり、附加機能ではない。これらのニーズに対して、Electronは「我慢して使用する」ではなく、「天生的に適応」する。

**② 私の制約境界はどこか？**
アプリケーションバイナリサイズが厳密な制約（例：10MB以下必須）であれば、Tauriが必須項目かもしれない。しかし「もう少し小さいといい」程度であれば、それに見合ったエンジニアリング複雑度のトレードオフを検討する必要がある。

**③ 私が受け入れ可能なメンテナンスコスト是多少か？**
Tauriのsidecarパターン、エコシステムの未成熟さ、plugin品質のばらつき——これらはすべて隠れたメンテナンスコストである。Boudraは最終的に気づいた：Tauriに使った追加の労力は、本質的にTauriのエコシステムの穴を補完する「車輪の再開発」をしていたのだ。

### 4.2 ローカルファーストは単純ではない

Paseoはローカルdaemon建築を選んだ，这意味着必须自己处理：

- プロセスライフサイクル管理
- WebSocket長接続維持
- クロスプラットフォームパスと権限処理

これは「コードを第三方APIに投げ入れる」よりも明らかに複雑である。しかしBoudraはこの更难な道を選んだ，因为**隐私和数据主权是不可妥协的**。

これはあるエンジニアリング哲学を体現している：**有时候、より複雑な技術実装はより重要な価値の守护である。**

### 4.3 クロスプラットフォーム一貫性はコアコンピテンシーであり、装飾品ではない

多くのフレームワークが「クロスプラットフォーム」を主張するが、UI、機能、体験すべてを一貫して実現できるものはほとんどない。Paseoが移行プロセスでWebKitGTK差異の解決に大量の花時間をかけたことは、**クロスプラットフォームの一貫性は自然に発生するものではなく、意図的に投資する必要がある**ことを物語っている。

デスクトップアプリケーション開発者がフレームワークを選択する際、「ターゲットプラットフォームのwebview差異」を必須評価項目として列表し、「書けばどこでも動く」と想当然に思わないべきである。

## 五、Paseo実践チュートリアル

### 5.1 Paseoのインストール

#### 方法1：デスクトップアプリケーション（初心者向け推奨）

[paseo.sh/download](https://paseo.sh/download)にアクセスし、対応プラットフォームのインストールパッケージをダウンロード。

#### 方法2：CLIツール

```bash
# グローバルにCLIをインストール
npm install -g @getpaseo/cli

# インストール確認
paseo --version

# daemonを起動
paseo daemon start

# 最初のアージェントを接続
paseo connect --agent claude-code
```

#### 方法3：Dockerデプロイ（サーバまたはヘッドレス環境向け）

```bash
docker run -d --name paseo \
  --restart unless-stopped \
  -p 6767:6767 \
  -e PASEO_PASSWORD=your-secure-password \
  -v "$PWD/paseo-home:/home/paseo" \
  -v "$PWD:/workspace" \
  ghcr.io/getpaseo/paseo:latest
```

> ⚠️ **セキュリティヒント**：`PASEO_PASSWORD`は必ず変更すること。デフォルトパスワードは本番環境で極めて安全ではない。

### 5.2 デスクトップ使用ガイド

インストール完了後：

1. Paseoデスクトップアプリケーションを開く
2. 初回使用時はdaemon接続パスワードを設定
3. 最初のアージェントProviderを接続（Claude Code / Copilot / Codexなど）
4. 統一されたインターフェースでタスクを作成、進捗を監視、エージェントを切り替え

Paseoは**音声入力をサポート**。インターフェース内のマイクアイコンをクリックすれば、音声でタスクを説明でき、通勤中や手が塞がっている時に最適。

### 5.3 モバイルでの使用

Paseoは同時にiOSとAndroidをサポートし、Expoで構築されている。対応Appをダウンロードし、デスクトップのペアリングQRコードをスキャンすれば、ローカルdaemonにリモート接続でき、クロスデバイスタスク管理が実現。

### 5.4 上級編：Paseo Skillsの使用

Paseoにはマルチエージェント協調のための3つの強力な組み込みSkillが备わっている：

#### `/paseo-handoff` — エージェント引き継ぎ

あるエージェントが一部の作業を完了した後、コンテキストを別のエージェントに完整に引き渡して作業を継続：

```
/paseo-handoff --from claude-code --to opencode --reason "より強いコードリファクタリング能力が必要"
```

#### `/paseo-advisor` — アドバイザーエージェント

「審査と提案」に專門的なアドバイザーエージェントを導入し、メ인エージェントのワークフローを邪魔せずにリアルタイムフィードバックを提供：

```
/paseo-advisor enable --mode realtime
```

#### `/paseo-committee` — マルチエージェント委員会

複数のエージェントを委員会として構成し、投票またはコンセンサスメカニズムで意思決定：

```
/paseo-committee create --agents claude-code,copilot,opencode --task "アーキテクチャレビュー"
```

### 5.5 TypeScript SDK 上級例

自動コードレビューパイプラインの構築：

```typescript
import { createClient } from '@getpaseo/client';

async function automatedCodeReview() {
  const client = createClient({
    password: process.env.PASEO_PASSWORD!,
    host: process.env.PASEO_HOST || 'localhost',
    port: 6767,
  });

  // エージェント出力ストリームをリスン
  client.on('agent:output', (event) => {
    console.log(`[${event.agentId}] ${event.type}: ${event.content}`);
  });

  // コードレビュータスクを開始
  const task = await client.sendTask({
    agentId: 'claude-code',
    prompt: `
      /workspaceディレクトリ下のすべてのTypeScriptファイルについてコードレビューを行ってください：
      1. 型の安全性をチェック
      2. 潜在的なnullポインタ例外を識別
      3. リファクタリング提案を出力
      出力形式：JSON
    `,
    options: {
      timeout: 300000, // 5分タイムアウト
      stream: true,
    },
  });

  console.log(`タスク提交、ID: ${task.id}`);
}

automatedCodeReview().catch(console.error);
```

## 六、結論：フレームワークに最优はなく、最も合适的だけがある

Paseoのストーリーで心を打つのは技術本身ではなく、創業者の**誤りを 인정し、公開で振り返る**率的さである。

BoudraはTauriのせいにはしなかった，也没有事后诸葛亮地说"我早知道Electron更好"。彼は正直に認めた：**彼は技術本身的魅力（Rust、パフォーマンス、小さいサイズ）に引き寄せられたのではなく、実際の需求に驱动されたのだ。**

これは技術選定における最も常见的な落とし穴である——**私たちは某个フレームワークが「更好だから」という理由で選ぶのではなく、それが私たちに「更好的感觉」を与えるからという理由で選んでいるのだ。**

Tauri vs Electronの議論について、Paseoは相当に説得力のある答えを出した：

- **Tauriが適している**：パッケージサイズに厳密な制約があり、UIインタラクションが简单で、複雑なネイティブ統合が必要ないツール類アプリケーション
- **Electronが適している**：安定したクロスプラットフォームUI表現が必要で、Node.jsエコシステムに依存し、複雑なネイティブシステム統合需求があるアプリケーション

そして優秀なエンジニアは**技術選好**ではなく**ビジネス需求**に基づいてこの問題に答えるべきである。
