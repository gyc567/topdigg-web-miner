## 一、Harperとは？一言で説明

**Harperは無料、オープンソースの英語文法チェッカーで、すべてのチェックはあなたのデバイス上で完結し、一バイトもクラウドに送信されません。**

Grammarlyを使ったことがあれば、Harperをその「オープンソース代替」と考えることができます — しかし、この比喩は実際にはHarperを過小評価しています。Harperの目的はGrammarlyを複製することではなく、より根本的な問いに答えることです：**文法チェックという行為は、本当に他人のサーバーにテキストを送信する必要があるのか？**

まずは基本情報を見てみましょう（以下のデータはすべてGitHub公式リポジトリと公式サイトで相互検証済み）：

| 項目 | 情報 |
|------|------|
| ポジショニング | ローカルファースト（local-first）の英語文法チェッカー |
| 作者 | Elijah Potter、現Automattic Code Wrangler |
| 名前の由来 | 小说家Harper Lee（『アラバマ物語』の作者）への敬意 |
| 技術スタック | Rust製、WebAssembly経由でブラウザで動作可能 |
| オープンソースライセンス | Apache-2.0、完全無料 |
| 所属 | 2024年11月21日にAutomattic（WordPress.comの親会社）に買収 |
| GitHubの人気 | 約13.4k Star、頻繁に更新継続中（2026年も集中的にリリース中） |
| 対応言語 | 英語のみ（英、米、加、豪、印の5方言を含む） |

## 二、誕生の背景：一人の開発者が業界の現状に抱いた「二重の不満」

Harperの作者Elijah Potterは公式READMEで次のように率直に語っています：彼はHarperを作った。なぜなら既存のツールにうんざりしていたからだ。彼の不満は逐一残す価値があります。なぜなら、それは二つの主流製品の構造的な問題を正確に突いているからです。

**Grammarlyへの不満：**

1. **高すぎ、かつ強すぎる** — サブスクリプション価格が高く、提案はしばしば文脈から離れ、「間違っていることが多い」；
2. **プライバシーの悪夢** — あなたが書くすべての文字がGrammarlyのサーバーに送信される。プライバシーポリシーではデータを売らないと書かれているが、大規模言語モデルの学習に使わないとは限らない；
3. **ネットワーク遅延がフローを破壊する** — チェックのたびにネットワークのラウンドトリップが発生し、推敲のリズムが損なわれる。

**LanguageToolへの不満：**

1. **メモリの怪物** — 数GBのメモリが必要で、さらに約16GBのn-gramデータセットをダウンロードする必要がある；
2. **遅すぎる** — 中規模のドキュメントのチェックに数秒かかる。

そこでPotterは自らに工学的目標を設定しました：チェック遅延を**ミリ秒レベル**に抑え、メモリ使用量を**LanguageToolの1/50以下**にし、かつ**完全にプライベート**であること。Harperはこの三つの制約条件下で生まれた産物です。

ここで注目すべき詳細があります：Harperの公式サイトには「10ミリ秒以内に提案」と書かれており、Automatticの買収発表では「20ミリ秒以内 — ある人気のオンライン文法ツールの所要時間の1%未満」とされています。二つの数字は基準が異なりますが、同じ結論を指しています：**ローカル計算の遅延は、クラウドソリューションよりも少なくとも二桁低い。**

## 三、中核原理：なぜ高速かつプライベートを実現できるのか？

この部分は「どうやって実現しているのか」を理解したい読者のために用意しました、できるだけわかりやすく説明します。

### 1. 大規模言語モデル不使用、ルールエンジンを採用

誰もが製品にLLMを詰め込んでいる時代において、Harperは逆張りの決断をしました：**チェックルールは完全に人手で作られた決定論的ルールで構成され、LLMの関与はなく、テレメトリもなく、クラウドのラウンドトリップもありません。**

これにより三つの直接的な利点が生まれます：

- **高速**：ルールマッチングは純粋なローカル計算で、Rustのパフォーマンスと極めて小さなメモリ使用量により、フィードバックはタイピング速度より速い；
- **安定**：同じ入力には常に同じ出力が得られ、大規模言語モデルのように「気分」で提案を与えることはない；
- **軽量**：エンジン全体は小さく、WebAssemblyにコンパイルでき、ブラウザタブ内で直接実行可能。

### 2. Rust + WebAssembly：一度書けば、どこでも動く

Harperの中核は`harper-core`（Rustライブラリ）であり、そこから三つの製品ラインが分岐しています：

- **harper-ls**：言語サーバー（LSP）、LSPプロトコルをサポートする任意のエディタに接続可能 — VS Code、Neovim、Helix、Emacs、Zed、Sublime Textを一度にカバー；
- **harper.js**：JavaScript/WebAssemblyラッパー、Obsidianプラグイン、ブラウザ拡張（Chrome/Firefox）、WordPressプラグインはすべてこれを基盤としています；
- **ネイティブアプリ**：デスクトップクライアント（最近のバージョンではSlackとDiscordシナリオもサポート）。

このアーキテクチャの巧妙な点は：**文法ルールは一つだけ管理し、配布チャネルはほぼ無限に広がる。** 新しいエディタサポートを追加するたびに、限界コストはほぼゼロです。これは典型的な「プロトコルの红利」 — LSPは元々コード補完のために設計されたプロトコルですが、Harperはそれを文法チェックの配布パイプラインに変えました。

### 3. コード内の「人の言葉」だけをチェック

開発者にとって特に親切な点：コードエディタ内では、Harperはコメントやdocstringなど自然言語部分のみをチェックし、変数名に口出ししません。これも「開発者のために生まれた」というタグの所以です。

## 五、鋭い見解：Harperの本当の価値と過大評価されている部分

### 見解一：Harperの堀は「無料」ではなく「決定論性」

多くの人はHarperを「無料のGrammarly」として分類しますが、これは表面的な見方です。本当の差別化は**アーキテクチャレベルの決定論性**です：ローカルで動作するということは、プライバシーが「ポリシー約束」ではなく「物理的事実」であることを意味します — データにはそもそもデバイスの外に出る通道がないのです。弁護士、ジャーナリスト、企業法務など、テキストの漏洩を絶対に許容しない人々にとって、この「漏洩できない」ことは「漏洩しない約束」よりも一段高い次元にあります。Grammarlyのプライバシー約束は信頼に依存しますが、Harperのプライバシーはアーキテクチャに依存しており、後者は一回の方針更新で覆すことはできません。

### 見解二：Automatticが買収したのは「Grammarlyキラー」ではない

2024年11月の買収時、多くの報道はHarperを「Grammarlyの競合」という物語に押し込めました。しかしAutomatticの動きを見れば明らかです：HarperをWordPress.com、WooCommerce、Jetpackに統合することを計画しています。**WordPressは世界全体の約40%のサイトを駆動している** — Automatticが欲しいのはGrammarlyのユーザーを奪うことではなく、WordPressエコシステム全体にライティングインフラを組み込むことです。Matt Mullenweg自身の言葉は明快です：「クラウドでやりすぎている、エッジには膨大なコンピューティング能力と可能性がある。」Harperは彼のエッジコンピューティング戦略の一ピースであり、GutenbergやPlaygroundと並列です。

言い換えれば：**Grammarlyはサブスクリプションビジネスを行い、Harperは買収されてプロトコル層になる。** これは全く異なる二つの戦争です。

### 見解三：「LLM不使用」は今日では逆に希少な資産

2026年現在振り返ると、Harperの最も常識に反する決断こそが、最も価値ある点です。すべてのライティングツールがより大きなモデルで競い合う中、Harperは別の道を証明しました：文法エラーの大部分（スペル、大文字小文字、主述一致、コロケーション）は**決定論的問題**であり、確率モデルはそもそも必要ないのです。これらの問題に大規模言語モデルを使うことは、ロケットでデリバリーするのと似ています — 高価で、遅く、たまに間違った住所に届けます。ルールエンジンはこの種の問題において、コストパフォーマンスと信頼性の面で、短期的に覆されることはないでしょう。

### 見解四：ただし神格化はしないこと — 天井もまた明らか

客観的に言えば、Harperの短所は長所と同じくらい顕著です：

1. **英語のみサポート**、しかもチームはまず英語を極限まで仕上げてから拡張すると明言しており、多言語対応はほど遠い；
2. **ルールエンジンには天井がある** — 意味理解、スタイル調整、トーン調整に関わるニーズはルールでは本質的に対応不可能で、まさにLLMソリューションの本領；
3. **誤検出と検出漏れが併存** — It's FOSSの実測タイトルは実に微妙だ：「私は気に入っている…ええっと、まあ」どれだけ熱心にルールを書いても（コミュニティの貢献者はほぼ毎日新しいルールを追加している）、カバー範囲は言語自体の複雑さに追いつけない；
4. **ビジネス化パスは未確定** — 完全無料 + Apache-2.0、その存続はAutomatticの戦略的忍耐に現時点では縛られている。

この部分を一言でまとめると：**Harperは「十分使える、信用できる、ゼロコスト」の最適解だが、「最強」の解ではない。** 勝利する戦場はプライバシーとスピードであり、知能の戦場ではない。

## 七、誰がHarperを使うべきか？始め方は？

**推奨ユーザー：**

- 英語技術ドキュメント、README、ブログを書く開発者（VS Code/Neovimユーザーはほぼゼロコストで導入可能）；
- Obsidianヘビーユーザー（公式プラグインですぐ使える）；
- プライバシーに敏感なテキストワーカー — 契約書、病歴、未公開原稿など、どのクラウドにも入れられないもの；
- 自社製品に文法チェック機能を組み込みたい開発者（`harper.js`または`harper-core`を直接統合）。

**非推奨ユーザー：**

- 中文またはその他の非英語チェックが必要なユーザー；
- 深い推敲、改作、トーン最適化を期待するユーザー — それはHarperの戦場ではない。

**導入パス：** 一般ユーザーはChrome/Firefox拡張機能をインストールするだけ；開発者は自分のエディタのLSP設定に`harper-ls`を登録；ObsidianユーザーはコミュニティプラグインマーケットでHarperを検索。すべてアカウント登録不要。

| **総合** | **8.0** | **特定シナリオの最適解、万能選手ではない** |

Harperは業界が忘れかけていた一つのことを証明しました：**すべての問題がクラウドでも、モデルでも、サブスクリプションでも必要とされるわけではない。** 工学的制約を極限まで追求すること自体が、一種の製品力です。もしあなたの仕事が「正確な英語を書く」ことであり、「驚くべき英語を書く」ことでないなら、Harperは現在この星球上で最もコストパフォーマンスの高い選択です — 結局、無料かつあなたのデータを売らないツールは、通常あなたも商品になる必要がないことを意味します。
