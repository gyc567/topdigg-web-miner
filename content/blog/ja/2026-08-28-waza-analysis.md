## はじめに

AI Agentが開発の現場に浸透する一方で、「AIに何をさせればいい thérapeut」という声が不绝れ聞こえる。問題が一つではないように、解決策も一つではない。だが、优秀的工程师は知っているmdash;艱苦な経験を通じて培われた习惯こそ、问题解決の真の武器だと。

tw93.github.io/Waza は、この沟を埋めるツールだ。8つのSlashコマンドを通じて、エンジニアリングの习惯をAI Agentが実行できるスキルに変換する。约束こそ自由mdash;设计哲学のその一文が、Wazaの全てを解说している。

## 1. 背景：なぜAI Agentはエンジニアリングの习惯を必要とするか

AI Agentは強力な生成能力を持つが、その力をどう使うかは用户提供しなければならない。これは泳ぎができる不等于水難救助の训练を受けていることと同じだ。代码生成能力和エンジニアリングの实践知は、本質的に别々の肌肉だからだ。

多くの開発者が経験적으로行うことを考えてほしい：

- 設計书類を作成する前に、その设计中身的妥当性を検証する
- バグの根本原因を特定するために、再現步骤とログを整理する
- コードレビューで、型安全な実装ができたかを確認する
- UIを実装する前に、プロトタイプと|アクセス|比尔|ユーザーディズ|

これらは「习惯」です。它们不是明确的步骤列表，而是通过 years of debugging, code reviews, and shipping products 学到的暗黙知。AI Agentはこの暗黙知を持たない。それどころか、セッションが新し每一次、同じ初歩的な問いから始めなければならない。

Wazaは、このgapに気づくかれた工程师が своих habit を Slash コマンドという形式で结构化し、复利用可能にしたものだ。結果は、1つのトリガーだけで起動し、一贯性のある出力を返す。这一点が、Wazaを単なるプロンプト集と决定的に区别つける。

## 2. 设计哲学

### 2.1 Less is More：8スキル×1トリガー

Wazaの提供するスキルは全部で8つ。各スキルは1つのSlashコマンドで启动し、1つの明确的 결과를返す。これは、多数のプロンプトを试みるのではなく、それぞれの行为を深く叩き达む选择だ。

各コマンドの詳細を以下に示す：

- `/think` - 設計検証
- `/hunt` - 根因特定
- `/check` - コードレビュー
- `/ui` - UIデザイン
- `/learn` - 6段階研究フロー
- `/read` - プラットフォーム対応読取
- `/write` - 自然文章
- `/health` - 6層Agent監査

1つのトリガー，这意味着入力の余地が減り、行動の一貫性が増す。约束があるからこそ、AI Agentは各スキルの「型」を正確に実行できる。

### 2.2 Structure is Efficiency

Wazaの各スキルは、次の3层の结构を持つ。

**结果契約（Result Contract）**
各スキルは、产出物の形式を明確に定义している。例えば `/think` は「 تصميم検証結果」を、`/health` は「6層監査レポート」を返す。产出物の形式が明らかだからこそ、结果の評価が简单になる。

**ハードルール（Hard Rules）**
各スキルには、絶対に踏むことのない線が引かれている。これらは「すべきでないこと」として明确规定されており、AI Agentが常识的な范畴を踏み越えることを 방지する。

**Gotchas（嵌阱集）**
各スキルには、その领域特有的嵌阱への警告が记载されている。例えば、分散システムの設計时应考虑的网络延迟问题，或并发编程时应注意のデッドロック回避。这些都是经验的结晶。

### 2.3 Project-Aware

Wazaの许多スキルは、プロジェクトコンテキストを自动的に活用する。現在のプロジェクト構造、语言構成、既存のコンポーネントを把握した状態でスキルを执行できる。这意味着、より文脈に即した、より実践的な助言が期待できる。

## 3. 8つのスキル详解

### 3.1 /think — 設計検証

`/think` は、设计书類やアーキテクチャ决定の妥当性を検証するためのスキルだ。设计は実装の前に检讨笔栖息、断ち切られるべき缲件的存在论的缺陷がある。

このスキルは以下の两点を確認する：

- **设计的完备性**：要件捕获漏れ、不明确な境界、矛盾した仕様が無いか
- **実装可行性**：選択された技術が要求されたスケール、温所性、开发速度をサポートできるか

出力がreturned的是一份结构化検証レポートだ。問題点がカテゴリ別に整理され、各項目に重大度评级と修正方向が记载される。これにより、设计段階での手戻りを大幅に削減できる。

### 3.2 /hunt — 根因特定

`/hunt` は、バグや障害の根本原因を特定するために設計された。现象ではなく原因に聚焦し、再現步骤とログの关联を体系的に分析する。

このスキルの核心は、「5Whys」的な思考フレームワークを结构化 형태로適用することだ。表面的原因を辿っていくごとに、「なぜ」を繰り返すことで、组织的な问题解決策となる。

出力がreturned的是根因分析レポートだ。各假设に対して证据の强度が评定され、最も可能性の高い原因に対して修正计划が提案される。

### 3.3 /check — コードレビュー

`/check` は、コードレビューを体系的に执行するスキルだ。手动レビューで見落とされがちなパターンを、结构的チェックリストに基づいて检出する。

レビュー维には以下が含まれる：

- **正确性**：边界条件の処理、エラー処理の完备性、型の安全
- **性能**：计算量の оценка、メモリアロケーション、パイプラインの効率
- **保守性**：命名の一貫性、関心の分离、ドキュメントの完备
- **セキュリティ**：入力検証、エスケープ処理 inúmerations

各issueには、重要度と修正优先度が标注される。チームでの運用を想定し、レビューコメントのフォーマットも统一されている。

### 3.4 /ui — UIデザイン

`/ui` は、ユーザーディズの分析からプロトタイプ生成まで、UI designのライフサイクル全体をカバーする。

このスキルは、以下のプロセスを структурировать：

- ユーザーニューヨ的需求を、具体的な功能要件に変換
- 信息アーキテクチャの设计と、、画面遷移の定義
- コンポーネントの分割と、状态の設計
- アクセシビリティの检讨

ポイントは、技术的实现可能性とユーザー石のトレードオフを同時に考虑する点だ。美的側面だけでなく、実装コストとユーザビリティのバランスを取った助言が返される。

### 3.5 /learn — 6段階研究フロー

`/learn` は、新しい技術要素や概念を体系的に学习するためのフレームワークを提供する。6段階の段階的アプローチで、表面的な理解ではなく、深層的な把握を目指す。

6段階の详细内容：

1. **概要把握** — Conceptと主要术语の理解
2. **原理理解** — 动作机制の背后的理論
3. **実践体験** — 最小構成での実装试验
4. **応用探索** — 実际のプロジェクトへの適用可能性
5. **限界理解** — 适用不可なケースの把握
6. **まとめと次のステップ** — 学習成果の体系化

各段階には明確な产出物が定义されており、学习进度の评估が容易になっている。

### 3.6 /read — プラットフォーム対応読取

`/read` は、多歧にわたる信息来源からの情报読取を、标准化された形式で整理するスキルだ。

対応プラットフォームには以下が含まれる：

- GitHub（リポジトリ、Issue、PR、Discussion）
- Hugging Face（モデルカード、数据集）
- arXiv（論文 abstract と本文）
- 技術博客（Qiita、Zenn、Dev.to）
- ドキュメンテーション（APIリファレンス、教程）

重要なのは、情報を単に妃型するだけでなく、结构化して要約する点だ。技术的な內容であれば、コード断片、政策的な內容であれば论点と根拠、というように內容の種類に応じた summarization が適用される。

### 3.7 /write — 自然文章

`/write` は、技術文章、会议事録、仕様书類などの写作をupportするスキルだ。technical writing の最佳实践に基づいて、明确で简洁な文章を作成する。

このスキルの特征は、読者对象と目的を明確に设定する点だ。初心者向け教程と、上級者向け深堀解説では、情報の深さとokusegiが异なる。読者の背景知识を تقديرし、それにあった密度の文章を生成する。

さらに、文章の構成 Sang 政治도支援する。导入・展开・まとめの基本構造だけでなく、technical writing に固有の「問題提起→解决方案提示→実装详細→評価」という流れも选择できる。

### 3.8 /health — 6層Agent監査

`/health` は、AI Agentの活動全体を包括的に監査するスキルだ。Agentの出力が正确性、安全性、効率性のいずれの観点でも健全であることを确认する。

6層の监查内容：

1. **論理的健全性** — 思考の连続性と論理的一貫性
2. **事実的正確性** — 提供される情报の事实確認
3. **安全性** — 有害内容の排除、プライバシーへの配慮
4. **効率性** — 资源使用量と実行時間の评估
5. **一貫性** — セッション跨での行动方针の一貫
6. **実用性** — 产出物は本当に役立つか

各層で何か問題が检出された場合、修正の方向性が具体的に提示される。これは、AI Agentを本番环境中で使用必须有ものの、Agent对自己的判断力を过信しすぎないためのafety net としても機能する。

## 4. インストール教程

### 4.1 npxコマンドでの利用

最も简单な利用方法は、npxコマンドで直接実行する方法だ。Node.js环境があれば、追加のインストール 없이即座に使用できる。

```bash
npx @tw93/waza [command] [options]
```

commandには上述の8つのスキル名（think、hunt、check、ui、learn、read、write、health）を指定する。optionsはスキルごとに异なるが、共通して `--project` でプロジェクトディレクトリを指定できる。

### 4.2 Claude Code向けネイティブプラグイン

Claude Codeを使用している場合、Wazaはネイティブプラグインとして統合できる。

```bash
# Claude Codeプロジェクトの設定に追加
claude code plugin install @tw93/waza
```

ネイティブ統合の利点は、プロジェクトコンテキストの自动認識だ。現在のブランチ、テスト状況、型定義ファイルを自動て参照しながらスキルを执行できる。

### 4.3 Codex向けネイティブプラグイン

OpenAI Codex（ChatGPT with Code Interpreter）を使用している場合は、别のパッケージが用意されている。

```bash
# Codex向け設定
npm install -g @tw93/waza-codex
```

Codexでは、的自然语言での指示からSlashコマンドへの转换が自动で行われる。「この設計を检讨して」のような自然な指示が、自動的に `/think` として解決される。

### 4.4 Claude Desktop向けネイティブプラグイン

Claude Desktop Applicationを使用している場合、以下の手順でインストールする。

1. 設定 → ベータ機能 → 拡張機能を有効化
2. 拡張機能ギャラリーから「Waza」を検索
3. インストールボタンを押下

Claude Desktop統合では、サイドパネルからWazaのスキルに直接アクセスできる。メインの 대화ウィンドウを占有することなく、バックグラウンドで咨询服务が利用可能だ。

### 4.5 Pi向けネイティブプラグイン

CursorやCopilot Chatなどの「Pi」型Agentでも、Wazaのスキルサブセットが利用可能だ。ベンダーごとに别々のパッケージがメンテナンスされている。

### 4.6 Statusline統合

Wazaは、主要なエディタやIDEのステータスラインにも統合できる。現在のプロジェクトの問題点を、Wazaのスキルを使ってチェックし、ステータスラインに результатを表示する。

現在対応しているのは：

- VS Code
- Neovim（lazy.nvim 経由）
- Helix
- Emacs（mode-line）

### 4.7 オプションルール

Wazaの动作は、オプションルールを通じてカスタマイズできる。

**project-rules.json**
プロジェクト固有のルールを定義する。コーディング規約、用語の一貫性、承認されたライブラリ一覧などを記載する。

**personal-rules.json**
個人個人の好みを設定する。コメントスタイル、日本語/英语の混在比率、出力フォーマットの好みを记载する。

**environment-rules.json**
環razol別のルールを定義する。開発環境、本番環境、CI環境它们不同的 требования を設定できる。

これらのルールは、スキル実行時に自動的に 참조 され、一貫性のある 출력을 可能にする。

## 5. 三部作：Kaku、Waza、Kami

tw93は、Wazaを含む3つのツール构成了「工程师のtools Trilogy」と呼ぶ套組だ。

### 5.1 Kaku（かく/コードを書く）

Kakuは、コード生成に特化したツール다。Wazaが「习惯」に聚焦するのに対し、Kakuは「实现」に聚焦する。生成的代码は、Wazaのスキルで 검증 되고、改善되는流程で連動する。

### 5.2 Waza（わざ/习惯を练习する）

Wazaは、本稿で解説した8つのSlashコマンドを通じて、エンジニアリングの习惯を结构化するツール다。设计レビュー、コードレビュー、根因分析这些都是、经验豊かなエンジニアであれば自然と行う活動を、体系的に実行可能な形式に转换する。

### 5.3 Kami（かみ/文书を出力する）

Kamiは、文書出力に特化したツール다。Wazaの `/write` が日常的な技術文章を目的とするのに対し Kamiは、仕様书類、APIドキュメント、 changelog といった、より正式的な文書を生成する。

### 5.4 三部作の连携

3つのツールは、それぞればらばらに使えるが、连携することで真価が現れる。例として以下の流程を考える：

1. `/think` で设计方案を検証（Waza）
2. 生成された设计方案を、Kakuでコードに落し込む
3. `/check` でコードレビュー（Waza）
4. `/health` で Agent 全体の健全性を確認（Waza）
5. Kamiでavadoc 生成（Kami）

この流程を通じて、问题の発见から解决、文書化までの一連の作业が、体系的に执行できる。

## 6. 5つの핵심적洞察

### 洞察1：约束が创造性を诱发する

Waza的设计哲学の核心は「约束こそ自由」である。これは逆説的に見えるが、実态は明白だ。无限の возможностей があると、决定疲劳动から何も选べなくなる。8つという制約られたスキル数、各スキルの明確な结果契约这些都是、不安感を减らし、最も重要な活動に集中できる环境を作る。

### 洞察2：暗黙知を形式知に変換する

エンジニアリング习惯の多くは、暗黙知として工程师の头の中に存在する。它们通过 years of debugging and code reviews 积累了难以言说的判断基準。Wazaは、この暗黙知を结构化されたスキルという形式知に変換するツール다。これににより、暗黙知の个人资产から、チームの共有资产への格上げが可能になる。

### 洞察3：Agentの自己过信防治

AI Agentは、自信满满の不正确な回答を生成することがある。この「AIの自信过度」は、实质的な问题を見落とす主要な原因다。`/health` の6層監査フレームワークは、この问题に対する体系的な对策だ。Agentが对自己的判断力を过信しないための、構造的なセーフティネットが整備されている。

### 洞察4：プラットフォーム横断の一貫性

情報の来源がGitHub、Hugging Face、arXiv、Web文章など、多歧にわたる现代において信息来源に依存しないfish qualityの出力が求められる。`/read` の 플랫폼対応读取機能は、この требование に応えている。内容の種類に応じた标准化された summarization により信息来源間のgapが埋まる。

### 洞察5：个人からチームへの拡大

Wazaの真のパワーは、个人利用からは解放される。プロジェクト固有のルール、チーム内の编码規約、承认された技术スタックこれらを options ルールとして定义することで、チーム全员が一贯した行动规范を共有できる。これは、個人の的习惯の标准化であり、チーム全体のエンジニアリング能力の底上げにつながる。
