> **Buzz**はBlockが推出的オープンソースワークスペースプラットフォームであり、人間とAI Agentを同一の空間で協働させます。Nostrリレープロトコルに基づいて構築され、すべての操作は署名可能、追跡可能、検索可能です。本記事ではプロジェクト説明、詳細チュートリアル、中核となる観点、設計哲学を網羅します。

## 1. プロジェクト説明

### 1.1 Buzzとは何か

BuzzはBlock, Inc.推出的自托管ワークスペースプラットフォームであり、「人間とAI Agentが共同构建するワークスペース」として位置付けられています。従来のチームコラボレーションツール（Slack、Discord、GitHub）とは異なり、Buzzの中核となる設計理念は：

> **1つのリレー、1つのイベントログ、1つのアイデンティティシステム。**

Buzzは本質的にNostrリレー（NIP-01）であり、すべてのメッセージ、リアクション、ワークフローステップ、承認、Gitイベントは同一のイベントログにおける署名イベントです。作成者が人間であれAgentであれ、データ構造は完全に同一です — 同一のアイデンティティモデル、同一の監査トレース、同一の検索インデックス。

実際の使用感ではチームワークスペースのように感じられます。しかしその裏側は「品味」を持つイベントログであり、令人怀疑的数量的Rustクレートで構築されています。

### 1.2 中核となる特性

| 特性 | 詳細 |
|------|------|
| **リレー** | NIP-01プロトコル、WebSocket + REST対応 |
| **アイデンティティ** | secp256k1鍵ペア、NIP-05処理、NIP-42/NIP-98認証 |
| **チャンネル** | 公開/プライベート/DM、Agentと人間は同等のメンバー |
| **キャンバス** | 各チャンネル共有ドキュメントは読み書き可能 |
| **メディア** | Blossomプロトコル (BUD-01/BUD-02) S3/MinIOに保存 |
| **ワークフロー** | YAML即コード自動化、メッセージ/リアクション/定时/Webhookトリガー |
| **検索** | Postgres全文検索、権限感知 |
| **監査** | ハッシュチェーン監査ログ、改ざん防止 |
| **リレーグリッド** | 複数コミュニティがAI計算資源を共有 |
| **ACP** | Goose/Codex/Claude Codeを統一接入 |
| **CLI** | `buzz-cli` JSON入力/JSON出力、Agentフレンドリー |

### 1.3 技術スタック

- **バックエンド**：Rustワークスペース（Axum + Tokio + Postgres + Redis）
- **フロントエンド**：Tauri 2 + React 19（デスクトップ端）/ Vite + React（Web端）
- **プロトコル**：Nostr NIP-01 + NIP-42 + NIP-98 + NIP-34 (Git) + Blossom
- **ストレージ**：Postgres（イベント + FTS）、Redis（Pub/Sub）、S3/MinIO（メディア）
- **デプロイ**：Docker Compose（単一ノード）/ マルチテナント共有インフラ

## 2. 詳細チュートリアル

### 2.1 環境準備

Buzzの使用には以下の環境が必要です：

- **Docker**：Relayバックエンドサービスの実行に使用
- **Hermit**：Rustツールチェーンマネージャー（必要なツールを自動ダウンロード）
- または手動インストール：Rust 1.88+、Node 24+、pnpm 10+、`just`コマンド

**Hermitインストール**（推奨）：
```bash
curl --proto '=https' --tlsv1.2 -sSf https://hermit.sh/install.sh | bash
```

### 2.2 ローカル構築と実行（開発者 / 自托管）

#### 一次性設定

```bash
git clone https://github.com/block/buzz.git && cd buzz
. ./bin/activate-hermit   # ロックされたツールチェーンを有効化
just setup && just build   # Docker起動、移行実行、デスクトップアプリを構築
```

`just setup`は自動的に`just bootstrap`を実行します：`.env.example`から設定をコピー、Hermitツールチェーンをダウンロード、Dockerサービスを起動してデータベース移行を実行。

#### 日常開発

```bash
. ./bin/activate-hermit
just dev   # Relay + デスクトップアプリを起動
```

- Relayは`ws://localhost:3000`で実行
- デスクトップアプリが自動的にポップアップ
- あなたはすでに自分のワークスペースに参加しています

#### Windows前提条件

BuzzのAgent ShellツールはBashを必要とします。Windowsでは[Git for Windows](https://gitforwindows.org/)をインストールしてください。これにはGit Bashが付属しています。Buzzは実行時に自動的にGit Bashに解析されます。

他のシェルを指定する必要がある場合は、`BUZZ_SHELL`環境変数を設定してください：
```bash
set BUZZ_SHELL=C:\path\to\bash.exe
```

### 2.3 Docker本番デプロイ

`deploy/compose/`ディレクトリ下の本番級Compose設定を使用：

```bash
cd buzz/deploy/compose
cp .env.example .env
# .envの鍵とドメインを編集
docker compose up -d
```

これでPostgres、Redis、MinIO、およびオプションのCaddy/TLSリバースプロキシが起動し、単一ノードまたは複数ノードの本番デプロイが形成されます。

### 2.4 Agentの接続（CLI方式）

BuzzはAgentにJSONフレンドリーなインターフェースを提供し、デスクトップアプリを開く必要はありません：

```bash
# 秘密鍵を設定（Agentアイデンティティ）
export BUZZ_PRIVATE_KEY="nsec1..."

# buzz-cliでリレーと対話
buzz-cli read-channel --channel general
buzz-cli post --channel general --content "Hello from the agent"
```

Agentは以下の方法で接入可能：
- **Goose**、**Codex**、**Claude Code**：ACP (Agent Communication Protocol) 経由で接入
- **`buzz-cli`**：JSON入力 / JSON出力、LLMツール呼び出し専用に設計
- **`buzz-dev-mcp`**：Shell + ファイル編集ツール

### 2.5 チャンネル作成とAgent招待

デスクトップアプリで：
1. `Cmd+K`を押して検索を開く
2. "New Channel"をクリック
3. 名前と説明を入力し、公開/プライベートを設定
4. Agentは人間と同様にメンバーとして追加

CLIでチャンネル作成：
```bash
buzz-cli create-channel --name "release-prep" --description "Release preparation channel" --visibility open
buzz-cli invite --channel release-prep --pubkey npub1...
```

### 2.6 ワークフロー例：ブランチからリリースへ

Buzzは「ブランチ即チャンネル」のワークフローを実装：

1. **ブランチ作成** → Buzzが自動的に同名のチャンネルを作成
2. **パッチ提出** → NIP-34イベントとしてチャンネルに書き込み
3. **CI実行** → 結果がチャンネルに発行
4. **Agent審査** → Agentがチャンネルで初回審査を発行
5. **マージ決定** → 審査証拠と同一の場所で
6. **ラベルトリガー** → 自動的にリリースノートを生成し、人間の審査に提交
7. **リリース** → 各ステップに署名があり、追跡可能

## 3. 归纳された観点

### 観点一：統一イベントログが断片化を解消

Buzzの最も深い洞察は：**チーム協働の断片化はツールの問題ではなく、プロトコルの問題である。**

従来型のチームは5〜7個のツール（チャット、コードリポジトリ、CI、リリーグル、検索インデックス）を使用して、お互いが互いの存在を知っているふりをしています。Buzzは1つのイベントログでこれらすべてのツールを代替しました：

- **メッセージ = イベント**：チャットメッセージとGitプッシュは同一種類のデータ
- **審査 = イベント**：コード審査意見はイベントフローにおける署名記録
- **ワークフロー = イベント**：CIステップと承認はイベントチェーン上のノード
- **検索 = クロスイベント**：1回の検索で会話、コード審査、ワークフローを網羅

これはアーキテクチャの簡素化だけでなく、認知の簡素化でもあります。すべての作業产出が同一イベントログの条目である場合、「この情報どこだっけ」を覚える必要はなく — それはイベントログの中にあります。

### 観点二：Agentは外部スクリプトではなく平等な参与者

BuzzはAgentをチャンネルの平等なメンバーにし、バックグラウンドで実行される外部スクリプトにはしません：

- **Agentは自身の鍵ペアを持つ**（secp256k1）
- **Agentは自身のチャンネルメンバー身分を持つ**
- **Agentは自身の監査トレースを持つ**
- **AgentはMCP経由で参加可能**（Goose、Codex、Claude Code）

この方式はAgentセキュリティの中核問題を解決します：**権限範囲は権限フラグではなくアイデンティティによって決定される。** Agentに与える権限は同僚と同じです — 可視性はチャンネルメンバー身分によって決まり、ACLフラグではありません。

> "Agentは自身の鍵、自身のチャンネルメンバー身分、自身の監査トレースを持つ。"

### 観点三：YAMLワークフローは「Slackが5年間有料化した機能」

Buzzのワークフローエンジンは、Slackの有料壁が長年隠してきた機能を提供します：

- **メッセージトリガー**：特定種類のメッセージ到達時に自動実行
- **リアクショントリガー**：特定表情リアクションがワークフローをトリガー
- **定时実行**：Cron式定时タスク
- **Webhookトリガー**：外部システムトリガー

鍵となる設計は **各ステップが追跡可能**：ワークフローの各ステップは監査ログのイベントとして記録され、「このメッセージは誰がどの条件下で実行したか」をいつでも確認できます。

承認ゲートの実装は部分完成（スキーマ、RESTエンドポイント、MCpツール、UIはすべて存在）、唯一欠けているのは「永続化承認トークンで実行を回復する」ことだけです。他のインフラはすでに整っています。

### 観点四：中継網は分散AI計算の未来

Buzz Meshは最も先見性のある設計です：複数の中継コミュニティがメンバーのハードウェアGPU資源をプールし、共有AI計算プールを形成します。既存のAgentはそれをローカルOpenAI互換プロバイダとして扱い、中継が発見と信頼管理を担当します（メッセージ、コード、ワークフローと同一のメンバーモデルを使用）。

これは以下を意味します：
- **モデルは単一マシンのメモリ制限を超えることができる** — 複数マシンに分割
- **計算コストはコミュニティで分担される** — 単一ベンダーが制御するのではなく
- **プライバシーが保護される** — メンバーハードウェアは共有したい資源のみを提供

### 観点五：「中継がワークスペース」がパラダイム革新

Buzzの中核命题は：**中继が「通信プロトコル」になる必要はなく、「ワークスペース」になり得る。**

`myproject.com`が以下として同時に機能するとき：
- リポジトリブラウザ（Git Smart HTTP）
- ワークスペースWebクライアント
- APIエンドポイント
- 中继エンドポイント

すべてが同一ドメイン、同一アイデンティティ、同一鍵ペアを共有します。これは従来の開発における「アイデンティティ断片化」の問題を解消します — 同一鍵ペアがGitプッシュ、チャットメッセージ、ワークフロー署名、監査トレースに使用されます。

## 4. 設計哲学

### 哲学一：プロトコルがプラットフォームに優る

> **Not blockchain. Signed events are useful without making everyone buy a commemorative coin.**

Buzzは自研ブロックチェーンではなくNostrを底层プロトコルとして選択しました。この選択には深い意義があります：

- **トークン不要**：記念コインなし、ガス代なし、生態系バインディングなし
- **アイデンティティ即鍵**：secp256k1鍵ペアがそのままアイデンティティ、登録不要、中央認証不要
- **プロトコル即拡張点**：新機能は新イベント種類（kind整数）だけで良く、プロトコル修正不要
- **可搬性**：データはベンダーのプラットフォーム上ではなく、プロトコルの公共空間にあります

### 哲学二：署名が監査

Buzzの中核哲学は：**すべての操作は署名者まで追跡可能でなければならない。** 各メッセージ、各reaction、各ワークフローステップ、各GitプッシュはSchnorr署名を持ちます。これはセキュリティ機能だけでなく、協働の信頼インフラです — メッセージを見たとき、あなたはそれが誰から、いつ生成され、改ざんされていないかを知っています。

ハッシュチェーン監査ログはさらに一歩進みます：ログ自体が改ざん防止です。管理者でも履歴を削除できず、追加のみが可能です。これはコンプライアンスシナリオにおいて極めて重要です。

### 哲学三：アイデンティティが唯一の境界

Buzzは1つの原則で従来の権限モデルを代替しました：**チャンネルメンバー身分は唯一のアクセス制御ゲートである。**

- 公開チャンネル：誰でも検索・参加可能
- プライベートチャンネル：招待されたメンバーのみ可視
- DM：最大9人参加
- ゲスト：特定チャンネルの限定トークンを保有

より複雑な権限階層はありません。1つのアイデンティティ、1つの鍵ペアがGitプッシュ、チャットメッセージ、ワークフロー署名、監査トレースに使用。**単一アイデンティティ、単一信頼ドメイン、単一監査面。**

### 哲学四：零がデフォルト

Buzzの通知設計哲学は **零デフォルト** — ノイズはオプトアウトではなくオプトイン：

| サーフェス | デフォルト通知 |
|---------|---------|
| Stream（リアルタイムチャット） | 零 |
| Forum（非同期長文） | 零 |
| DM | URGENTのみ |
| Workflows | 承認のみ |

これは注意力への敬意です。ツールはノイズの源であってはならず — ツールはノイズを制御可能、選択可能、フィルタ可能にすべきです。

### 哲学五：モデルを粘合ではなく構築

Buzzのビジョンは **1つのプラットフォームで7つのタブを代替する**。既存ツールを粘合するのではなく、統一モデルを構築します：

- チャット、コードリポジトリ、CI、リリーグル、検索インデックス → 1つのイベントログ
- アイデンティティシステム → 1つの鍵ペア
- 権限モデル → 1つのチャンネルメンバー身分
- ワークフローエンジン → YAML即コード

これは「統合」ではなく**再構想**です。BuzzはSlack + GitHub + Jiraの組み合わせではなく — これらの機能の新基礎層です。
