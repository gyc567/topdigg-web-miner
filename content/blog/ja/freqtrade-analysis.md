# Freqtrade 徹底解説：半年使って分かった、本当に暗号資産市場で稼げるのか

> コア思想：**Freqtrade は、オープンソースの暗号資産クオンツ分野で最もエンジニアリング品質の高いフレームワークであり、その一点に異論はない——しかし、それはツールであって答えではない。** 正しいアイデアをより良く実行することはできるが、間違ったアイデアを正しくすることはできない。この言葉は、長期にわたってクオンツ研究に従事し、Freqtrade を本番で半年間使い続けたユーザーによるもの（掘金ロングリード『半年 Freqtrade を使って、暗号資産市場で本当に稼げるのかを語る』、2026-04-26）。半年の体験は一つの判断に凝縮される：**「正直なバックテスト」こそ、このプロジェクトをあらゆる類似フレームワークから分かつ分水嶺である**——戦略が未来データを覗き見ていないかを能動的に検出する `lookahead-analysis` と `recursive-analysis` を内蔵し、確定足のみで判断し（リペイントなし）、「まず Dry-Run ペーパートレードを数ヶ月」を提案ではなくプロセスの一部として書き込んでいる。すべてのエンジニアリング上の決定は一つの目標を中心に回っている：**クオンツ取引で最も陰湿な失敗要因（未来データ漏洩、過学習、スリッページの幻想）を、実際に資金を投じる前に明らかにすること。**

## 一、プロジェクト解説：Freqtrade とは何か

### 1.1 一言での位置づけ

Freqtrade は Python で書かれた**オープンソースの暗号資産クオンツ取引フレームワーク**であり、GPL-3.0 ライセンス、ヨーロッパのコミュニティによって長期メンテナンスされている。その中核的な位置づけは：

> Python の基礎がある人が、自分の取引アイデアを自動実行されるアルゴリズム戦略に変換し、実際の取引所で稼働させられるようにすること。

つまり、戦略研究 → バックテスト → パラメータ最適化 → ペーパートレード検証 → 本番自動実行、という完全なクオンツのクローズドループである。

48.4k stars、111 リリース、31,465 コミット——これは週末プロジェクトではない。暗号資産クオンツコミュニティで長年の実取引による検証を経た、産業級のフレームワークである。

### 1.3 それは何ではないのか

「何であるか」と「何でないか」を同時に言うことが、このプロジェクトで最初に理解すべき点である：

**それは次のようなものではない：**

- ❌ 「コピペするだけで儲かる」ブラックボックスツール
- ❌ A 株（中国株式）取引システム（中国のユーザーが最も知っておくべき点）
- ❌ 安定収益の保証

**それは次のようなものである：**

- ✅ エンジニアリング品質が極めて高いクオンツ取引フレームワーク
- ✅ 戦略研究 → バックテスト → 最適化 → 本番取引のクローズドループツール
- ✅ 暗号資産市場のクオンツ研究におけるデファクトスタンダードの一つ

### 1.4 5 つの実行モード

同じボットが戦略を 5 つのモードで処理できる。これがアーキテクチャ全体を理解する鍵である：

| モード | 役割 | 重要ポイント |
|------|------|--------|
| **Backtesting（バックテスト）** | 過去の足で戦略パフォーマンスをシミュレート | ベクトル化計算、データ全体を一括投入、未来データ検出を内蔵 |
| **Hyperopt（パラメータ最適化）** | ベイズ最適化でパラメータ空間を自動探索 | Optuna / scikit-optimize ベース。最も強力で最も危険な機能 |
| **Dry-Run（ペーパートレード）** | 実相場でフォワードテスト、実際の注文は出さない | 公式要件：本番前に必ず通過すべき段階 |
| **Live（本番）** | 実際の取引所で自動取引を実行 | ccxt 経由で接続、API キーが必要 |
| **FreqAI（機械学習）** | ML モデルを戦略ライフサイクルに組み込む | 定期的なローリング再学習 + 予測シグナルをエントリー/エグジットロジックへ |

### 1.5 コアアーキテクチャとモジュール

公式ドキュメントと実使用から、主要なアーキテクチャ上の決定を再構成できる：

**戦略インターフェース（Strategy Interface v3）**：戦略は Python クラスであり、3 つのメソッドを実装する——`populate_indicators()`（テクニカル指標の計算）、`populate_entry_trend()`（エントリーシグナルの定義）、`populate_exit_trend()`（エグジットシグナルの定義）。シグナルは足の確定時に生成され、取引は次の足の始値で実行される。インターフェースバージョンは `INTERFACE_VERSION = 3` で、旧バージョンの戦略は v3 用語への移行が必要。

**データレイヤー（pandas DataFrame）**：Freqtrade は pandas で OHLCV 足データを保持する。**確定済みの完全な足のみが提供される**——未完成の足で判断することを "repainting"（リペイント）と呼び、Freqtrade は明確にサポートしない。これも正直な設計の一部である。すべてのシグナルロジックはベクトル化された書き方（`dataframe.loc[...]`）でなければならず、行ごとのループや `if dataframe['rsi'] > 30` のような非ベクトル化比較は禁止される。

**取引所抽象化（ccxt）**：すべての取引所接続は ccxt ライブラリに基づく。これが 1 つの設定で現物 12 社 + 先物 6 社の取引所をサポートできる理由であり、同時に上海・深圳の株式取引所や先物取引所とは無関係である理由でもある。

**研究用コマンド**：`lookahead-analysis`（未来データ検出）、`recursive-analysis`（再帰的バイアス検出）、`hyperopt`（パラメータ最適化）、`download-data`（データダウンロード）などが、完全な戦略研究ツールチェーンを構成する。

**運用スタック**：Telegram Bot（リアルタイム通知、ポジション確認、手動強制クローズ）+ FreqUI（内蔵 Web UI）+ Docker（公式 docker-compose.yml でワンコマンドデプロイ）。

### 1.6 習得タイムラインの現実的な見積もり

筆者は非常に現実的な習得コストの見積もりを示している（詳細は第 3 節のチュートリアル参照）。先に結論：

- Python 基礎 + クオンツ基礎あり：**4〜6 週間**で使えるバックテスト戦略ができる
- Python 基礎あり + クオンツ経験なし：**8〜12 週間**
- Python 経験なし：まず 3 ヶ月 Python を学んでから

## 二、コア思想：正直なバックテスト + ツールであって答えではない

### 2.1 力の源泉：アンチチートをツールに内蔵する

ほとんどのバックテストフレームワークは、未来データ漏洩があるかどうかを教えてくれない。Freqtrade は違う——**アンチチートを内蔵機能**にしており、ユーザーの自覚に依存しない：

```bash
freqtrade lookahead-analysis --strategy MyStrategy --timerange 20230101-20231231
freqtrade recursive-analysis --strategy MyStrategy
```

- `lookahead-analysis`：戦略コードが未来データを使っていないかを検出（例：`shift(-1)` の誤用で、次の足のデータで今の足の操作を決定している場合）。
- `recursive-analysis`：データウィンドウの不足により指標計算に再帰的バイアスが生じていないかを検出（例：`startup_candle_count` の設定不足で指標の前半の値が不安定）。

筆者の言葉：**「『年率 500%、最大ドローダウン 5%』を謳うオープンソース戦略を見かけたら、十中八九この 2 つの検出を通過していない。」** 彼自身の「完璧に見えた」戦略 2 つがこのコマンドに救われた。

### 2.2 完全なクローズドループ：研究 → バックテスト → 最適化 → 本番

Freqtrade の位置づけは「あなたに戦略を提供する」ことではない。**完全なパイプラインを提供する**のだ：データダウンロード → 戦略開発 → バックテスト → パラメータ最適化（Hyperopt）→ ペーパートレード検証（Dry-Run）→ 本番実行 → 運用監視（Telegram/FreqUI）。各段階に専用のコマンドとツールがあり、段階同士が相互に牽制する（Hyperopt の結果はサンプル外検証を通過しなければならず、本番の前には Dry-Run を通過しなければならない）。これが「クローズドループ」の価値である。

### 2.3 3 つの重要原則

1. **サンプル外検証**：Hyperopt 最適化では、データセットの最後の 20〜30% をサンプル外検証用に保留し、最適化に含めない。最適化したパラメータはサンプル外データで検証し、基準に達しなければやり直す。
2. **Dry-Run の規律**：Dry-Run と本番の最大の違いは——Dry-Run の注文は必ず「約定」するが、本番では価格変動により部分約定や不約定があり得る。2 週間から 1〜2 ヶ月の Dry-Run は必要であり、形ではない。
3. **特徴量の削減**：FreqAI で特徴量を無闇に積むと（100 個中 95 個がノイズ）ほぼ確実に過学習する。金融的な意味のある 10 個から始めて、段階的に検証する。

## 三、詳細チュートリアル：ゼロから Freqtrade を動かす

### 3.1 環境構築：なぜ Docker を使うべきか

最初の 1 週間で最もつまずきやすいのは TA-Lib のネイティブインストール——macOS と Windows では極めて失敗しやすい（C 拡張のコンパイルが必要）。**解決策は公式推奨の Docker**：

```bash
# リポジトリをクローン
git clone https://github.com/freqtrade/freqtrade.git
cd freqtrade

# 公式 docker-compose.yml でワンコマンド起動
docker compose up -d

# コンテナ内に入ってコマンド実行
docker compose exec freqtrade bash
```

`docker compose up -d` で環境問題の 90% を解決できる。コンテナ内で直接 `freqtrade` コマンドを使えばよい。Docker を使いたくない場合は `pip install freqtrade` でもよいが、TA-Lib の C 依存を自力で処理する必要がある（Linux では比較的スムーズ、macOS/Windows では詰まりやすい）。

### 3.2 設定と戦略テンプレートの生成

**設定（config.json）**：このファイルには 50 以上のフィールドがある（ペアリスト設定＝取引ペアの動的フィルタリング、資金管理＝毎回のポジションサイズ、取引所認証など）。**ネット上の設定ファイルをコピーしてそのまま使ってはいけない**。公式ジェネレータから始める：

```bash
# 設定テンプレートを生成
freqtrade new-config --config config.json
```

**戦略**：公式スキャフォールドでテンプレートを生成する。Freqtrade のコマンドはファイル名ではなく戦略の**クラス名**を使う点に注意：

```bash
# 戦略テンプレートを生成（AwesomeStrategy.py）
freqtrade new-strategy --strategy AwesomeStrategy

# --template minimal で空テンプレート、--template advanced でより複雑な例
freqtrade new-strategy --strategy AwesomeStrategy --template minimal

# 内蔵の SampleStrategy はテストにそのまま使える
freqtrade backtesting --strategy SampleStrategy
```

### 3.3 ダブル EMA 戦略を書く（完全な例）

戦略は `IStrategy` を継承した Python クラスであり、核となるのは 3 つのメソッド。以下は筆者の「ダブル EMA 戦略」の規範的な書き方：

```python
from freqtrade.strategy import IStrategy
from pandas import DataFrame
import talib.abstract as ta
import freqtrade.vendor.qtpylib.indicators as qtpylib


class EmaCrossStrategy(IStrategy):
    INTERFACE_VERSION = 3

    # 基本設定
    timeframe = "5m"                      # 5 分足
    startup_candle_count = 100            # ウォームアップ足数（EMA100 に必要）
    can_short = False                     # ロングのみ

    # リスクパラメータ
    stoploss = -0.02                      # ストップロス 2%
    minimal_roi = {"60": 0.01, "0": 0.03} # 60 分後に +1% で売却、即時 +3% で売却
    trailing_stop = False

    def populate_indicators(self, dataframe: DataFrame, metadata: dict) -> DataFrame:
        # 指標の計算：速い EMA と遅い EMA
        dataframe["ema_fast"] = ta.EMA(dataframe, timeperiod=10)
        dataframe["ema_slow"] = ta.EMA(dataframe, timeperiod=30)
        return dataframe

    def populate_entry_trend(self, dataframe: DataFrame, metadata: dict) -> DataFrame:
        # エントリーシグナル：速い EMA が遅い EMA を上抜け
        dataframe.loc[
            (qtpylib.crossed_above(dataframe["ema_fast"], dataframe["ema_slow"]))
            & (dataframe["volume"] > 0),
            "enter_long",
        ] = 1
        return dataframe

    def populate_exit_trend(self, dataframe: DataFrame, metadata: dict) -> DataFrame:
        # エグジットシグナル：速い EMA が遅い EMA を下抜け
        dataframe.loc[
            (qtpylib.crossed_below(dataframe["ema_fast"], dataframe["ema_slow"]))
            & (dataframe["volume"] > 0),
            "exit_long",
        ] = 1
        return dataframe
```

戦略を書く際に必ず覚えるべき鉄則：

- **ベクトル化**：バックテストではデータ全体が一度に `populate_*()` に渡される。`dataframe.loc[条件, 列] = 値` のベクトル化で書くこと。行ごとのループや `if dataframe['rsi'] > 30` のような書き方は禁止（pandas が `The truth value of a Series is ambiguous` を投げる）
- **インデックス参照禁止**：`df.iloc[-1]` は使わず、`df.shift()` で前の足を参照する
- **完全な dataframe を常に返す**：`open/high/low/close/volume` 列を削除・変更しない
- **`startup_candle_count` は十分に**：戦略が必要とする最長期間の足数に等しくする（EMA100 は 400 本必要）。不足すると前半の指標計算が不正確になる

### 3.4 バックテスト：最初の実行

```bash
# 履歴データのダウンロード（Binance の BTC/USDT、5m 足）
freqtrade download-data --exchange binance --pairs BTC/USDT --timeframe 5m --timerange 20230101-20240601

# バックテストの実行
freqtrade backtesting --strategy EmaCrossStrategy --timerange 20230101-20240601 --timeframe 5m
```

バックテストの出力には、収益、最大ドローダウン、シャープレシオ、勝率、取引回数などが含まれる。**注意：Freqtrade のバックテストはデフォルトでスリッページを計算しない**。ボラティリティの高い相場ではスリッページが大きな利益を食う。詳しくは第 5 節の「罠 1」参照。

### 3.5 Look-ahead 検出：バックテスト後に必ずやるチェック

バックテストの結果が良い ≠ 戦略が良い。Dry-Run や本番に入る前に、公式はこの 2 つの検出コマンドを実行することを要求する：

```bash
# 未来データ検出：戦略が未来を覗き見ていないか
freqtrade lookahead-analysis --strategy EmaCrossStrategy --timerange 20230101-20240601

# 再帰的バイアス検出：データウィンドウ不足による指標の不安定さ
freqtrade recursive-analysis --strategy EmaCrossStrategy
```

### 3.6 Hyperopt：パラメータ最適化の正しい姿勢（と間違った姿勢）

Hyperopt はベイズ最適化（内部は Optuna または scikit-optimize）で戦略パラメータ空間を自動探索する。例：RSI の閾値は 30、35、それとも 28？ ストップロスは 2% か 3% か？

**正しい使い方の結果**：基本戦略のシャープレシオを 0.8 から 1.4 に引き上げられる。実質的な意味がある。

**間違った使い方の結果**：500 回イテレーションして訓練データ上で「完璧な」パラメータを見つけたが、サンプル外では 40% の損失（筆者が実証済み）。

Hyperopt を正しく使うための 4 つの重要原則：

1. **サンプル外を保留**：データセットの最後の 20〜30% はサンプル外検証用に保留し、最適化に含めない
2. **イテレーションは ≤200 回**：それ以上は効果が逓減し、過学習リスクが急上昇する
3. **複数の Loss Function で交差検証**：`SharpeHyperOptLoss`、`CalmarHyperOptLoss` など。一つの目的関数だけを見ない
4. **サンプル外で必ず検証**：最適化したパラメータはサンプル外データで検証し、基準に達しなければやり直す

### 3.7 Dry-Run：ペーパートレードはプロセスであって形ではない

```bash
# config.json で設定
# {
#   "dry_run": true,
#   "dry_run_wallet": 1000,
#   "exchange": { "name": "binance", "key": "", "secret": "" }
# }

# ペーパートレードの開始（実相場でシミュレート、実際の注文なし）
freqtrade trade --strategy EmaCrossStrategy --config config.json
```

Dry-Run と本番の最大の違い：**Dry-Run の注文は必ず「約定」するが、本番では価格変動により部分約定や不約定があり得る。** 2 週間から 1〜2 ヶ月の Dry-Run は必要であり、形ではない。

### 3.8 本番と日常運用

ペーパートレードが合格したら、`dry_run` を `false` にして取引所の API キーを入力すれば本番である。日常運用は Freqtrade の加点ポイント：

**Telegram Bot**（スマホでほとんどの操作が可能）：

```text
/status table    # 現在の全ポジションを表示
/profit          # 全体の損益を表示
/forceexit BTC/USDT  # ペアを強制クローズ
/balance         # 口座残高を表示
```

**FreqUI**：内蔵 Web UI。ポジションのチャート、足、取引履歴をブラウザで確認でき、追加インストールは不要。

**サーバー要件**（本番推奨）：
- 最小構成：2GB RAM、1GB ディスク、2 vCPU
- FreqAI を動かす推奨構成：4GB RAM 以上、安定なら 8GB
- VPS の参考：Hetzner CX22（2vCPU / 4GB / 約 €5/月）、DigitalOcean Basic Droplet（2GB / $14/月）；中国の Tencent Cloud/Aliyun 軽量サーバー（2GB）は Binance へのネットワークに追加対応が必要な場合がある

### 4.5 5 つの罠（筆者実証済み——遠回りを防ぐ）

**罠 1：バックテストでスリッページを設定せず、本番で利益がスリッページに食われる。** Freqtrade のバックテストはデフォルトでスリッページを計算しない。暗号資産市場ではボラティリティの高い相場でスリッページが大きくなり得る。config で `slippage_protection` を必ず設定し、自分のペアのオーダーブックの深さを実測する。

**罠 2：Dry-Run が 2 週間良かったからそのまま本番へ。** Dry-Run の注文は必ず「約定」するが、本番では部分約定や不約定があり得る。2 週間から 1〜2 ヶ月の Dry-Run は必要であり、形ではない。

**罠 3：Hyperopt に全データを使って、「サンプル内で完璧な」パラメータを「最適化」してしまう。** クオンツで最も古典的な誤りの一つで、Freqtrade ユーザーも例外ではない。解決策は一つだけ：最後の 20〜30% のデータを保留し、Hyperopt 終了後にその部分で検証し、基準に達しなければ稼働させない。

**罠 4：FreqAI で特徴量を無闇に積む。** 100 個の特徴量を追加し、そのうち 95 個がノイズなら、モデルはノイズに過学習する。金融的な意味のある 10 個から始めて段階的に検証し、一度に大量に追加しない。

**罠 5：サーバー時刻の同期ずれ。** 公式ドキュメントの最初の項目：サーバーの時計は正確でなければならない。Linux で NTP 同期を設定：

```bash
timedatectl set-ntp true
```

これを無視すると注文のタイムスタンプが誤り、軽ければ注文失敗、重ければステートマシンが混乱する。

### 4.6 中国ユーザー向けの結論

- **A 株ユーザーは使えるか？使えない。** Freqtrade の取引所接続はすべて ccxt ベースで、ccxt がカバーするのは暗号資産取引所のみ。上海・深圳の株式取引所や先物取引所とは無関係。国内の代替案：**vnpy**（中国語コミュニティが最も成熟、A 株/先物/オプション対応）、**RQAlpha**（米筐 Ricequant 製、A 株特化、バックテスト品質が高い）、**backtrader + AkShare/Tushare**（柔軟性が最も高く、データソースは自分で組み立てる）。
- **暗号資産ユーザーは取引所をどう選ぶか？** 現物：Binance、Bybit、OKX、Kraken、Gate.io のサポートが最も完全（第一段階）；HTX、Bitget、BingX は対応しているが exchange-specific な設定が必要（第二段階）；その他は「使えるかもしれないが保証はない」。先物：Binance、Bybit、OKX、Gate.io のサポートは良好だが、レバレッジ取引の設定とリスク管理は現物よりはるかに複雑で、初心者は最初から先物に手を出すべきではない。Hyperliquid（DEX）は新規対応で、コミュニティのフィードバックでは安定性は普通、本番使用は慎重に。
- **Python ができない人でも使えるか？推奨しない。** 公式ドキュメントは明確に書いている："We strongly recommend you to have coding and Python knowledge."これは社交辞令ではない——戦略は Python クラス、バックテストのパラメータは Python の型アノテーション、Hyperopt のパラメータ空間は Python の関数呼び出し、FreqAI の特徴量エンジニアリングは pandas 操作である。まず 4〜6 週間 Python の基礎（入門チュートリアル + pandas 基礎）を学んでから Freqtrade を使うのが、最終的には時間の節約になる。

## 五、設計哲学

> 以下は 6 ヶ月の使用経験とプロジェクトアーキテクチャに基づく帰納（公式ドキュメントの原文ではない）。

### 5.1 正直さ最優先：アンチチートをツールに内蔵する

Freqtrade の最も深い哲学は**「バックテストの幻想」へのゼロトレランス**である。ドキュメントで未来データへの注意を促すだけではなく、`lookahead-analysis` / `recursive-analysis` を内蔵コマンドにし、「確定足のみ」をデータレイヤーの基本制約にしている。設計者の暗黙の信念：**クオンツトレーダーの最大の敵は市場ではなく、自分自身のバックテストレポートである**——年率 500% のバックテスト結果は、十中八九何らかの形のデータ漏洩である。アンチチートをアドバイスではなくツールにすることが、このプロジェクトで最も学ぶ価値のある設計判断である。

### 5.2 ツールであって答えではない：フレームワークは代わりに判断しない

Freqtrade の位置づけは驚くほど抑制的である：**戦略を提供せず、収益を約束せず、パラメータも代わりに選ばない**——ただ完全で相互に連動するパイプラインを提供するだけだ。背後にあるのは「インフラストラクチャ思考」：コンパイラがあなたの代わりに正しいプログラムを書かないように、クオンツフレームワークもあなたの代わりに儲かる戦略を探すべきではない。ユーザーの知性を前提とし、判断は完全に戦略作者に委ね、プロセス（Dry-Run、サンプル外検証）で誤った判断を実際の資金投入前に食い止める。

### 5.3 検証の規律：Dry-Run はプロセスであって形ではない

「まず数ヶ月 Dry-Run してから本番」は提案ではなくワークフローに書き込まれている。この設計は残酷な事実を認めている：**シミュレーション環境は常に本番より楽観的である**（注文は必ず約定し、スリッページもネットワーク遅延も部分約定もない）。Freqtrade の哲学は、より賢いシミュレータでその差を埋めることではなく、十分に長い実相場シミュレーションでその差をユーザーに曝すことを強制することである。検証は任意項目ではなく、プロセスの一部である。

### 5.4 エンジニアリング級の運用：クオンツ取引はまず運用問題である

Telegram Bot、FreqUI、Docker、ステートマシン、SQLite 永続化——Freqtrade は「動き出した後どうするか」を第一級の市民として扱う。クオンツフレームワークの成否はしばしば戦略ロジックではなく、7×24 稼働時の信頼性にある：サーバー時刻の同期（NTP）、混乱しない取引ステートマシン、切断時の再接続、リモート監視。このエンジニアリング級の運用スタックこそ、「産業級」という位置づけの根拠である。

### 5.5 モジュール化と組み合わせ性：ccxt 抽象 + 設定駆動

ccxt ベースの取引所抽象化により、現物 12 社 + 先物 6 社の取引所が同じ戦略コードを共有できる。戦略インターフェース v3 は戦略と実行エンジンを分離し、50+ フィールドの設定ファイルが資金管理・取引ペア選定・リスク管理をすべてパラメータ化する。設計哲学は**関心の分離**である：戦略作者はシグナルロジックだけを担当し、エンジンは実行とリスク管理を担当し、運用層は監視を担当する——各モジュールは一つのことだけを行い、インターフェースで通信する。これが習得障壁の高さも説明している：4 つのレイヤーを同時に理解する必要がある。

### 5.6 反過学習カルチャー：「サンプル外検証」を筋肉記憶にする

Hyperopt のイテレーション上限の推奨、20〜30% のサンプル外保留、複数 Loss の交差検証、FreqAI の特徴量削減原則——プロジェクト全体のツールとドキュメントは一つの理念を繰り返し叩き込む：**過学習はバグではなくデフォルト状態である**。「訓練データ上で完璧」な結果はすべて、サンプル外がそれを否定するまで過学習とみなす。このカルチャーは、どの単一機能よりも価値がある。

### 5.7 AI 時代：思考を支援しても検証を代替しない

筆者の現在のワークフローは Claude を開発プロセスに組み込む：戦略コードのレビュー（AI に look-ahead bias を探させる。一般的な問題の約 70% を発見でき、残りは Freqtrade の内蔵検出がバックストップ）、バックテスト結果の分析（AI に最大ドローダウンがどの市場環境に集中しているかを解釈させる）、FreqAI の特徴量エンジニアリングの議論（AI に文献上で予測力のある特徴量リストを出させる）。ただし**推奨しない**のは、AI に戦略を直接生成させてそのまま使うこと——生成されたコードは動くように見えても、ロジックが正しいことも look-ahead bias がないことも意味しない。これは Freqtrade の哲学と一貫している：**AI は思考を支援し、検証を代替しない。**
