# FDE Guide 徹底解説：自律性の前に価値をエンジニアリングする——FDE と AI エンジニアのための本番級デリバリー方法論

> 核心思想：**Tokens は入力（Tokens are an input）。自律性は設計上の選択（Autonomy is a design choice）。受け入れられた結果こそが製品である（Accepted outcomes are the product）。** davidahmann/fde-guide は、著者 David Ahmann（クラウド・データ・AI プラットフォーム責任者、元 Field CTO）がメンテナンスする独立したオープンソースのガイド＆エンジニアリングスイートであり、目標はただ一つ：**実際の顧客または社内ワークフローを、測定可能で運用可能な AI サービスに変えること。** その第一原則は「自律性の前に価値をエンジニアリングする」——モデルや agent トポロジーから出発するのは間違いで、**仕事そのものと、その受け入れられた結果**から出発する。本番級 AI システムはもっともらしい回答を出すだけでは不十分で、以下を知っていなければならない：誰が行動する権限を持つのか、どの情報が最新なのか、失敗はどう制限されるのか、完了はどう検証されるのか、サービス全体のコストはいくらか、誰が運用できるのか、誰が停止できるのか。Agent はコンポーネントの選択肢の一つに過ぎない；重要な決定ごとに、決定論的ソフトウェア・最適化・古典的 ML・検索・基盤モデル呼び出し・境界づけられた agent ワークフロー・人間レビューを比較し、**最小の十分メカニズム（smallest sufficient mechanism）** を選び、その証拠・権限・コスト・ロールバック・退役パスを保持する。このプロジェクトの「12 ファクター AI 価値エンジニアリング」は、この原則を明示的な価値・検証者・採用・権限・コスト・証明・ライフサイクルゲートへと変換する。

## 一、プロジェクト概要

### 1.1 それは何か？

本稿が解析するのは **GitHub オープンソースリポジトリ `davidahmann/fde-guide`**——副題は *"Value engineering and production architecture for FDEs, applied-AI engineers, product teams, and operators"*（FDE・アプライド AI エンジニア・プロダクトチーム・運用者のための価値エンジニアリングと本番アーキテクチャ）。それは「独立したオープンソースのガイド＆エンジニアリングスイート」と位置づけられ、**実際の顧客または社内ワークフローを、測定可能で運用可能な AI サービスに変える**ためのものだ。

これはまた別の agent フレームワークではなく、**エンジニアリング手法 + 実行可能な証拠**の複合体である：方法（The Guide）は考え方を教え、ハンドブック（The Handbook）は判断を支え、エンジニアリングスイート（The Engineering Kit）は主張・権限・振る舞い・変更を検証可能かつテスト可能にする。この3つは同一手法の3つの深度であり、3つの独立フレームワークではない。

**3つの深度、必要に応じて使う：**

| 階層 | いつ使うか | 入口 |
|------|---------|------|
| **The Guide（ガイド）** | メンタルモデル・中核原則・完全なデリバリーサイクルが欲しい場合（約20分） | `guide/README.md` |
| **The Handbook（ハンドブック）** | 実際のワークフローを評価・設計・デリバリー・移管・運用している最中 | `playbooks/` ライフサイクル playbooks + `library/00-start-here.md` |
| **The Engineering Kit（エンジニアリングスイート）** | 実装アーティファクト・アーキテクチャ・機械可読契約・リリース制御・実行可能例・テストが必要 | `examples/`、`blueprints/`、`templates/`、`controls/`、`schemas/`、`operations/`、`tests/` |

### 1.2 主要データと情報

- リポジトリ：`https://github.com/davidahmann/fde-guide`（Apache-2.0 ライセンス、21 stars / 2 forks、17 commits、`CITATION.cff` 引用メタデータ含む）
- 著者：**David Ahmann**——クラウド・データ・AI プラットフォームのリーダー、Field CTO の経験あり；独立プロジェクトであり、現職・前職の雇用主による推薦を意味しない
- 位置づけ：特定のモデル・クラウド・agent フレームワークを要求しない；導入可能なランタイム・認証・対象組織レビューの代替ではない
- ガバナンスアセット：`AGENTS.md`（リポジトリ作業契約）、`catalog.json`（ガバナンスされたアーティファクトレジストリ）、`llms.txt`（コンパクトな機械ナビゲーションインデックス）

- 10のオプション agent スキル：`$qualify-ai-workflow`、`$engineer-ai-value`、`$select-ai-mechanism`、`$design-production-ai-system`、`$build-ai-evaluation`、`$secure-ai-action-boundary`、`$review-ai-production-readiness`、`$operate-ai-service`、`$transfer-ai-service`、`$productize-field-learning`（指示のみ。いかなるツール/クレデンシャル/権限/承認/証拠も付与しない）
- 業務フローの組み合わせ：例外から解決へ（exception-to-resolution）、シグナルから調査へ（signal-to-investigation）、リスクから優先行動へ（risk-to-prioritized-action）、リクエストからアクティベーションへ（request-to-activation）；垂直プロファイルには医療アクセス調整・金融サービス調査・産業オペレーション対応を含む

### 1.3 それは何を解決するのか？

記事の冒頭で核心的な痛点が指摘される：**AI には会計問題がある（AI has an accounting problem）。** チームは token・モデル呼び出し・生成されたコード・デプロイされた agent・「節約されたと主張する工数」を計測する——これらのメトリクスは知能の生産と消費を記述するだけで、**価値ある何かが起きたことを確立しない。** 組織が最終的に求めるのは変化した結果である：請求書の例外が解決され台帳で確認されること；出荷案件が影響を与える前に正しいコーディネーターに届くこと；リリースが本番に到達し、チェックを通過し、健全であり続けること。

**受け入れられた結果（accepted outcome）** とは、完了し、独立した検証者・権限システム・責任を持つレビュアーによって正しいと受け入れられた作業単位である。AI 価値エンジニアリングはこの結果を、適格性要件・採用・帰属・フルコスト・リスクへと接続する。

したがって解決する問題はこうだ：**「AI アクティビティ」をどう「受け入れられた結果」にするか？配信されるシステムを、デモ・プロンプト・モデル呼び出し・agent・ダッシュボードではなく、実際の仕事に対する所有された変更（owned change）にするにはどうするか**——受け入れられた結果・信頼できる検証者・境界づけられた権限・フルコストの価値ケース・運用チーム・退役パスを備えたものに。

## 二、核心思想

### 2.1 一言の世界観

> **"Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."**
> （**Tokens は入力。自律性は設計上の選択。受け入れられた結果こそが製品。**）

これはプロジェクト全体のモットーであり、多くの「agent 熱狂」コンテンツとの分水嶺でもある：**知能・token・自動化・自律性の最大化は目的ではなく、受け入れられたコストとリスクの上限の中で、所有された結果を改善することが目的だ。**

### 2.2 自律性の前に価値をエンジニアリングする

> **"Start with the work and the accepted outcome—not with a model or agent topology."**
> （**仕事と受け入れられた結果から始める——モデルや agent トポロジーからではなく。**）

本番級 AI システムが答えなければならない7つの問い：誰が行動できるか、どの情報が最新か、失敗はどう制限されるか、完了はどう検証されるか、サービス全体のコストはいくらか、誰が運用できるか、誰が停止できるか。Agent はコンポーネントの選択肢の一つであり、重要な決定ごとに7つのメカニズム（決定論的ソフトウェア / 最適化 / 古典的 ML / 検索 / 基盤モデル呼び出し / 境界づけられた agent ワークフロー / 人間レビュー）を比較し、最小の十分メカニズムを選び、その証拠・権限・コスト・ロールバック・退役パスを保持する。

### 2.3 FDE の4つの職責と「所有された変更」という出力

フォワードデプロイエンジニア（Forward-Deployed Engineer, FDE）は、**曖昧な運用上の問題**を、**測定可能な結果を生むサポートされたソフトウェアサービス**に変える。仕事は4つの職責にまたがる：

1. **ディスカバリー（Discovery）**：仕事・判断・遅延・リスク・価値が実際にどこで起きているかを理解する。
2. **プロダクト（Product）**：ユーザーが何を変えるべきか、何を人間・ローカル・手動のままにすべきかを決める。
3. **エンジニアリング（Engineering）**：ワークフローを改善する最小の信頼できるシステムを構築する。
4. **オペレーション（Operation）**：結果を証明し、所有権を移管し、サービスをサポートし、本番から学ぶ。

**出力はデモ・プロンプト・モデル呼び出し・agent・ダッシュボードではない**——それは実際の仕事に対する**所有された変更**である：受け入れられた結果・信頼できる検証者・境界づけられた権限・フルコストの価値ケース・運用チーム・退役パスを備えたもの。同じ方法は企業内部にも適用される——社内のアプライド AI エンジニアは、たとえ FDE の肩書きがなくても、ビジネスコンテキスト・プロダクト判断・ソフトウェアアーキテクチャ・採用・本番運用を接続しなければならない。

### 2.4 全体を貫くデリバリーサイクル

リポジトリ全体はただ1つのライフサイクル（7段階）に従い、顧客・モデル・フレームワークごとに並行メソッドを作らない：

```
観察 → 価値とスコープの憲章化 → メカニズム選定 → 制御されたスライス構築 → ケースとユーザーで証明 → ローンチと所有権移管 → 運用・学習・退役 → （憲章に戻る）
```

各段階は**決定 + 他者が検証できる証拠**で終わる。弱い仕事を止める・狭める・再設計することは有効な結果である——美しいモデルスコア・スポンサー・契約更新・ローンチ・使用数は、**失敗した価値・権限・セキュリティ・所有権・本番ゲートを平均で帳消しにできない。**

## 三、詳細チュートリアル：7 段階デリバリーサイクル + 12 ファクター価値エンジニアリング

### 3.1 段階 1：システムを設計する前に仕事を観察する（Observe）

**コンテキスト抽出とは全ドキュメントを集めることではなく、重要な設計判断に必要な最小の運用上の真実を発見することだ。** その仕事を実行・受領・レビュー・サポートする人々と一緒に実際のケースを観察し、記録する：

1. トリガーポイントと作業インターフェース；
2. 下されている決定；
3. 入力とその権威的なソース；
4. 許可された行動と最大許容影響；
5. 正常パス・例外・回避策・回復；
6. ビジネス結果を所有する人；
7. 結果を独立に受け入れられる人またはシステム；
8. 変更後のワークフローを運用するチーム。

**インタビューは仮説を生む；オペレーターのウォークスルー・ソースアーティファクト・システムトレース・照合記録はより強い証拠を生む。** ワークフローがスライドの中でしか明確でなければ、ディスカバリーは完了していない。

警告：**「ワークフロー・ポリシー・ソースシステム・引き継ぎを直すべきか」と問う前に、回避策を自動化してはいけない。** AI は壊れたプロセスをより速く走らせ、同時に根本的な問題をより見えにくくする。

### 3.2 段階 2：価値憲章（Charter）をエンジニアリングする——ユースケースを構築可能にする7つのフィールド

ユースケースは、その結果が**所有・測定・疑問視できる**ときにのみ構築可能になる。アーキテクチャの前にこれらのフィールドを定義する：

- **適格母集団（Eligible population）**：どの仕事が合法にシステムを使えるか（除外を含む）。
- **ベースライン（Baseline）**：現在の性能・状態・日付・母集団・信頼度。
- **受け入れられた結果（Accepted outcome）**：仕事が独立に受け入れられるイベント——モデルが「生成」または「完了」したのではない。
- **検証者（Verifier）**：受け入れを確立する人・ルール・照合・真実源イベント。
- **目標とガードレール（Target and guardrails）**：期待される変化と、絶対に悪化させてはいけないもの。
- **帰属（Attribution）**：チームがシステム効果とその他の変化をどう区別するか。
- **フルコスト（Full cost）**：ディスカバリー・デリバリー・変更・モデル・インフラ・ツール・人間レビュー・サポート・インシデント・回復・メンテナンス。
- **残余損失（Residual loss）**：他の収益・コスト項目に含まれない予想または実現した損害。
- **所有者（Owner）**：メトリクスとそれに基づく決定に責任を持つロール。

役立つ運用単位：

```text
受け入れられた結果あたりのコスト =
  総運用・償却ライフサイクルコスト
  / 独立に受け入れられた結果の数
```

```text
実現済み純価値 =
  受け入れられた結果の帰属可能な価値
  + 重複しない回避損失
  − ライフサイクルコスト
  − ネットされていない残余損失
```

**予測・証明済みパイロット証拠・実現済み本番価値を分離する。** 明示的で所有された外挿がなければ、狭いパイロットを年次化しない。時間節約・単位価値・回避損失・人員削減で同じ利益を二重カウントしない。

### 3.3 段階 3：最小の十分メカニズムを選ぶ（Select）

**「AI を使う」はアーキテクチャ上の決定ではない。** ワークフローを重要な決定ステップに分解し、ステップごとにメカニズムを選ぶ：

| メカニズム | 適している | 警告サイン |
|------|------|---------|
| **決定論的ソフトウェア** | 安定したルール・変換・検証・ルーティング・認可 | 自然言語の曖昧さが脆弱な if-else 分岐に隠される |
| **最適化アルゴリズム** | 割り当て・スケジューリング・ソート・プランニング（明示的な目的と制約あり） | 目的・制約が所有・測定できない |
| **古典的 ML** | 繰り返される予測（ラベル・校正された不確実性・ドリフト監視あり） | 代表的な結果またはフィードバックパスが存在しない |
| **検索** | 証拠をガバナンスされたソースから検索する必要がある | 検索出力がポリシーまたは権威として扱われる |
| **基盤モデル呼び出し** | 境界づけられた説明・抽出・分類・ドラフト作成 | 流暢な出力が検証済みの事実として扱われる |
| **境界づけられた agent ワークフロー** | 多段階の判断が実際に変化する証拠やツール使用に依存する | ステップが既知で、普通のワークフローコードのほうが簡単 |
| **人間レビュー** | 判断の検証可能性が弱い・リスクが高い・ポリシーが説明責任を要求 | レビューが使えないシステムや無制限の仕事量を隠すために使われる |

本番システムは複数のメカニズムを組み合わせられる。各パスを観察可能・テスト可能・置換可能・コスト計算可能に保つ。**モデルパスはアイデンティティ・認可・データ・リリース・普通のソフトウェアエンジニアリングのコントロールを弱めない。** 境界づけられた多段階の判断が本当に有用なときだけ agent を追加する；権限・ツール・コンテキスト・所有権・レイテンシーの**実際の差異**がオーケストレーションコストを正当化するときだけ、複数の agent を追加する。

### 3.4 段階 4：制御された垂直スライスを構築する（Build）

最初のスライスは**実際のインターフェースとコントロール境界**を通り抜けるべきだが、完全なプロダクトを試す必要はない。以下を実演する：

- 代表的なトリガーポイントとユーザー；
- 実際の権限動作を持つ権威コンテキスト；
- 選択された決定パス；
- 最終的なオペレーターの作業インターフェース；
- シミュレーション・ステージング・リバーシブル、その他境界づけられた影響；
- 明示的な失敗とエスカレーション状態；
- テレメトリ・コスト・受け入れ証拠；
- 所有された回復またはロールバックパス。

**パイロット期間中に採用と移管を始める。** 受領チームは、デリバリーチームが撤退する前に、評価・リリース・サポート・ポリシー変更・インシデント・ロールバック・退役にペアで関与するべきだ。

**パイロットの最大期間・証拠締切・独立した（技術/オペレーター/採用/価値/経済/本番準備）卒業ゲートを事前に宣言する。** デモはスポンサーを感動させたからといって、静かに本番になるべきではない。

### 3.5 段階 5：代表的な仕事で主張を証明する（Prove）

**評価は「宣言された条件でのリリース主張」であり、永久的なスコアではない。** 代表的な正常ケース・困難なスライス・既知の例外・敵対的入力・依存関係の失敗・ポリシー変更・タイムアウト・リトライ・キャンセル・回復・人間レビュー容量を使う。**リプレイ結果に必要な完全な環境と振る舞いのバージョンを保持する。**

3つの問いを分離する：

1. **能力（Capability）**：メカニズムはタスクを実行できるか？
2. **振る舞い（Behavior）**：システム全体が正しいパスを通り、安全に停止するか？
3. **結果（Outcome）**：ワークフローはガードレール内で対象母集団の受け入れられた結果を改善したか？

決定論的チェックは閉じた不変条件に最も強い；統計的メトリクスには分母と不確実性が必要；モデル審判には校正されたルーブリックと人間比較が必要；本番フィードバックは保持セットを静かに汚染してはならず、候補モデルに自分の評価者をコントロールさせてはならない。**オフライン評価 → シャドウ運用 → カナリア → 名前付き本番セグメント**のような境界づけられた段階で昇格させる；**ロールバックを定義してからローンチする。**

### 3.6 段階 6：サービスを運用し所有権を移管する（Launch + Operate）

**本番は繰り返される決定であり、最後のデプロイステップではない。** システム全体を監視する：受け入れられた結果・価値・採用・ガードレール；ソース・権限・鮮度・照合；パス・モデル・プロンプト・ツール・ポリシーバージョン；レイテンシ・コスト・リトライ・ステップ・終了理由；拒否/禁止/重複/効果不明/読み戻し不一致イベント；レビュアー負荷・修正・放棄・トレーニング・サポート；所有者の継続性・インシデント準備・ロールバック・退役能力。

**移管は、受領チームがデリバリーチームのヒロイズムなしにサービスを運用・変更・回復・サポート・退役できるときに完了する。ドキュメント自体は運用能力を証明せず、ドリルが証明する。**

### 3.7 段階 7：フィールドラーニングをプロダクト能力にする（Field learning）

FDE 仕事の複利の優位性は、再利用可能な顧客データや積み上げたカスタムコードではなく、**ローカルコンテキストとポータブルなエンジニアリング知識を分離する能力**にある。デフォルトで顧客/ビジネスユニット固有に保つもの：ポリシー・閾値・アイデンティティ・権限・機密データ・ソース詳細・運用決定。再利用の候補には：契約形状・失敗カテゴリ・評価方法・作業インターフェースパターン・統合プリミティブ・コントロール・runbook・プラットフォームのギャップ。

**独立した環境で繰り返し出現する証拠・候補のサニタイズ・宛先と所有者の存在・対象固有の検証の成功・通常のリリースパスを通ること、これらが揃ったときだけプロダクト化する。** まず分類（顧客設定 / 対象所有の拡張 / 共有プロダクトまたはプラットフォーム能力 / 期限付き実験 / 禁止または延期）してから実装する。**依存関係を作らない。ネガティブ証拠と停止証拠を保持し、退出パスを残す。**

### 3.8 チュートリアルの核心：12 ファクター AI 価値エンジニアリング（Valuemaxxing）

これはプロジェクト全体の「台帳」フレームワーク——AI アクティビティを受け入れられた結果に換算する：

| # | ファクター | 一言ポイント |
|---|------|-----------|
| 1 | **実際の仕事を観察する** | スライドの中のプロセスを自動化しない；回避策は自動的にドメイン専門性ではない（`FDE-002`） |
| 2 | **結果を所有する** | 運用上の結果を定義してから技術を選ぶ；「返信を生成する」は出力、「例外を解決し台帳で修正残高を確認する」が結果（`FDE-001`, `VAL-001`） |
| 3 | **適格な仕事を定義する** | どの仕事が適格でどの仕事が不適格かを明確に；分母を宣言してから採用率を計算する；「大多数の簡単なケースを処理するシステム」は「少数の高価なケースを処理するシステム」より価値が低いかもしれない（`VAL-001`） |
| 4 | **反事実を確立する** | 改善を主張する前に現在のワークフローを測定する；前後比較チャートは自動的に因果証拠ではない——既知の交絡因子と帰属方法の限界を宣言する（`VAL-001`, `VAL-002`） |
| 5 | **検証者を指名する** | 本番システムは自分が成功したかどうかの唯一の審判であってはならない；検証者は結果を拒否できなければならない；受け入れ ≠ agent がワークフロー末尾に到達（`FDE-001`, `EVA-001`, `REL-003`） |
| 6 | **ワークフローと採用をエンジニアリングする** | 技術的成功だが誰も使わない = ゼロ価値；ユーザーが信じる前にすべての結果を再構築しなければならないなら、仕事は自動化されていない（`FDE-003`, `ADP-001`, `ADP-002`） |
| 7 | **最小の十分な知能を使う** | 最初に「問題は agent が必要」と決めない；決定に分解して1つずつ比較する；すべての決定を最強モデルに通すのではなく、困難なケースをエスカレーションする（`ARC-004`, `ARC-005`） |
| 8 | **権限と損失を境界づける** | 能力は権限を授けない；単独では許可された行動が組み合わさって受け入れられない結果になることがある——完全な行動パスをレビューする（`IAM-003`, `SEC-004`, `REL-001/003/005`） |
| 9 | **サービス全体に価格をつける** | Token はコストの一つに過ぎない；安いモデルが周辺ワークフローを高くするかもしれない；技術的に正しい結果でも経済的に受け入れられないことがある（`CST-001`, `CST-002`） |
| 10 | **代表的な仕事で証明する** | 成功したデモはパスが実行可能であることを証明するが、システムがローンチ可能であることは証明しない；パイロットは最大期間・証拠締切・決定所有者・独立卒業ゲートを事前宣言する（`EVA-001/003`, `DEL-001`） |
| 11 | **帰属可能な実現済み価値を測定する** | 適格な仕事→ワークフローに入る→ワークフローを完了→受け入れられた結果→測定されたビジネス影響→持続的な純価値；不採用・カバレッジ・リワーク・レビュアー負荷・インシデント・回復・フルコストを報告する（`VAL-002`, `OPS-004/006`, `CST-001`） |
| 12 | **証拠に基づき拡大・制約・退役する** | 自律性と投資は前進する成果によって継続の権利を勝ち取らなければならない；より強いベンチマーク・より大きなモデル・より高い使用数は自動的により多くの権限を証明しない（`VAL-003`, `ADP-002`, `OPS-007`） |

**4つのハードゲート（ハード、平均不可）：**

1. 所有された・測定可能な結果（owned outcome）
2. 信頼できる独立検証者（credible independent verifier）
3. 境界づけられた権限と期待損失（bounded authority and expected loss）
4. フルコスト後も正の・合理的な価値ケース（plausible positive value case after full cost）

いずれかのゲートが欠けていれば、正しい決定は `defer`（延期）、`redesign`（再設計）、または `do_not_build`（作らない）かもしれない。残りのファクターは **0 — 未定義 / 1 — 宣言済み / 2 — 証明済み** で採点する；スコアは対話を支えるものであって認証ではなく、強いファクターは失敗したゲートを平均で帳消しにできない。

**価値公式：**

```text
期待純価値 =
  適格量 × 期待採用率 × 期待増分受け入れ結果率 × 受け入れられた結果あたりの価値
  − 期待ライフサイクルコスト
  − 回避損失または単位価値からネットされていない期待残余損失
```

### 3.9 チュートリアル例 1：制御された書き込みシステム（invoice-exception、請求書例外解決）

デモ目標：**モデルは提案する；信頼できるソフトウェアが承認してコミットする；真実源の読み戻しが結果を証明する。** 目標フロー：

```text
請求書例外イベント → 台帳/ベンダー/ポリシー証拠を収集 → 解決策を提案 → 不変条件を検証
  → 承認してステージング → 正確な提案サマリーを承認 → 冪等に再承認してコミット
  → 任意の「効果不明」タイムアウトを照合 → 台帳状態を読み戻す → 完了レシート | 補償 + インシデント
```

中核メカニズムと不変条件（これが「制御された書き込み」の実演）：

- `resolution_commits(tenant_id, business_operation_id) <= 1`（冪等性：1つのビジネスオペレーションは1回しかコミットできない）
- コミット前のランタイムリリースダイジェスト == 許可されたソリューションリリースダイジェスト；コミットされた請求書リビジョン == 現在の請求書リビジョン；コミットされた提案サマリー == 承認された提案サマリー；ポリシーリビジョン == 現在のポリシーリビジョン
- 呼び出し元テナント == 請求書テナント；すべてのデータ/影響境界が現在の呼び出し元スコープと現在のポリシーリビジョンをチェックする
- `committed == true` は真実源の読み戻しの後でのみ；`effect_unknown` はリトライまたは完了の前に照合される
- `completed == true` は信頼できるレシートと読み戻し証明の検証後でのみ；ステップ・壁時計時間・コストが宣言されたランタイム予算内；**`model_access(credentials) == false`（モデルはクレデンシャルに決して触れられない）**

付随アーティファクト：実行可能ランタイム `reference-loop.mjs`、認可ポリシー `authorization-policy.mjs`、型付きツール契約（読み取り/ステージング/コミット/読み戻し）、能力インベントリと出処記録、脅威モデル、評価ケース（認可されたコミット / 未認可の書き込み / 重複リトライ / リビジョンドリフトリトライ / プロンプトインジェクション）、独立スコアラー、評価レポート、レビューのみのソリューションリリース。回帰カバレッジ：認可・テナント分離・古いポリシー・重複リトライ・承認タイミング・リリース取り消し・レシート検証・効果不明回復・真実源の読み戻し。

### 3.10 チュートリアル例 2：ハイブリッドシステム（shipment-risk-triage、出荷リスクトリアージ）

**AI システムは agent ファーストである必要がない**ことを証明する：古典的 ML スコアリング → 決定論的ポリシールーティング → 任意のモデル説明 → 人間が運用決定を保持。4つのメカニズムが境界づけられたワークフローの中で組み合わされ、各コンポーネントには選定記録（`intelligence-selection.md`）・評価ケース・回帰テストがある。これは「ハイブリッド知能システムのブループリント」の実行可能なコンパニオンである。

### 3.11 システム設計の8つの明示的な層

モデルはより大きなソフトウェアと運用境界の中の1つのコンポーネントである。これらの層を設計する（`design-production-ai-system` に対応）：

- **ドメインと状態（Domain and state）**：オブジェクト・アイデンティティ・リビジョン・ライフサイクル状態・不変条件・真実源システム
- **コンテキスト（Context）**：ソース・権限・出処・鮮度・十分性・信頼・失効
- **振る舞い（Behavior）**：コード・ルール・モデルパス・プロンプト・ツール・ガードレール・互換性
- **権限（Authority）**：呼び出し元またはワークロードアイデンティティ・テナント・スコープ・ポリシー・承認・最大影響
- **能力（Capabilities）**：型付き入出力・正確な宛先・クレデンシャルパターン・失敗契約・重複安全性・読み戻し
- **ランタイム（Runtime）**：永続状態・キャンセル・タイムアウト・リソース予算・リトライ・サーキットブレーカー・明示的終了状態
- **作業インターフェース（Work surface）**：永続アーティファクト・証拠・状態・不確実性・代替案・許可された人間の行動
- **運用（Operation）**：トレース・サービス目標・アラート・runbook・変更パス・ロールバック・所有権・退役

**中核となる行動ルール**：モデルは提案できる（propose）。信頼できるソフトウェアが承認してコミットする（authorize and commit）。真実源の読み戻し（source-of-truth readback）が結果を証明する。秘密とクレデンシャルはモデル可視コンテキストの外に保つ；重大な影響（consequential effect）を実行する境界で現在のアイデンティティ・テナント・スコープ・ポリシー・リリース許可・承認を再チェックする；安定したビジネスオペレーションアイデンティティから重複安全性を導出する；影響を与えた後、結果を報告する前に権威システムで結果を検証する。

### 3.12 アーキテクチャの非妥協事項とアンチパターン

**非妥協事項：**

- モデルを使用する場合：モデルは提案し、決定論的ソフトウェアが重要な仕事を検証・承認・実行・永続化・検証する（`ARC-002`）
- 各コンポーネントは名前付きの目的・バージョン・所有者・権限上限・証拠・コスト配分・監視・ロールバック・退役パスを持つ（`ARC-005`, `DEL-001`）
- 真実源の状態・アイデンティティ・承認・完了証明はプロンプトと一時的なモデルコンテキストの外にある（`CTX-001`, `IAM-001`, `REL-003`）
- リリースユニットはコードだけでなく、データ・ドメイン・知能コンポーネント・ツール・ポリシー・評価・ユーザーインターフェース・運用をバインドする（`DEL-001`）
- 基盤モデルや agent が保持されるのは、要求されたガードレールの下で受け入れられた結果を改善したからであって、新規性や可用性のためではない（`ARC-004`, `VAL-002`）

**アンチパターン：** 決定論的ポリシー決定を「agent 推論」と呼ぶこと；モデルパスをアーキテクチャとして扱い、状態・アクセス・影響・回復を暗黙のままにすること；より単純なメカニズムと比較せずに、スケジューリング・割り当て・検証・分類の問題に LLM を追加すること；安定したラベル・エラーメトリクス・ドリフト監視・所有者なしに ML モデルをトレーニングまたはルーティングすること；推論コストを最適化してツール・レビュー・回復・カスタマーサポートコストを無視すること；状態遷移・信頼境界・失敗挙動・リリーステストのないアーキテクチャ図を完全なものとして扱うこと。

## 四、設計哲学

### 4.1 「AI には会計問題がある」：アクティビティメトリクスから結果メトリクスへ

設計哲学の出発点は現状への批判である：**チームは token・呼び出し・コード・agent・「節約されたと主張する工数」を計測するが、これらは知能の生産と消費を記述するだけで、価値が起きたことを確立しない。** 組織は最終的に変化した結果に対して支払う。したがって「valuemaxxing（価値最大化）」は自動化の最大化を意味しない——それは**人が検証可能・運用可能・停止可能なシステムから持続的な純価値を最大化すること**を意味する。

### 4.2 「自律性の前に価値をエンジニアリングする」：モデルは出発点ではない

プロジェクトの第一原則は業界の主流ナラティブと逆である：**「どのモデルを使うか」や「どんな agent トポロジーにするか」から始めるのではなく、仕事と受け入れられた結果から始める。** Agent はコンポーネントの選択肢である。重要な決定ごとに、7つのメカニズム（決定論的ソフトウェア/最適化/古典的 ML/検索/基盤モデル/境界づけられた agent/人間）を1つずつ比較し、最小の十分メカニズムを選ぶ。**「より AI 的である」ことは、ワークフローが正しく分解されていないことを意味するかもしれない。**

### 4.3 「能力は権限を授けない」：信頼の最小化設計

**モデルは常に提案しかできない。** 信頼できるソフトウェア（決定論的コード）が重要な仕事の承認・実行・永続化・検証を担当する。権限はワークフロー・アクター・テナント・目的・タスク・目標・期間・結果にバインドされる；単独では許可された行動が組み合わさって受け入れられない結果になることがあるので、完全な行動パスをレビューする。真実源の状態・アイデンティティ・承認・完了証明は常にプロンプトと一時的なモデルコンテキストの外にある——**秘密とクレデンシャルにモデルは決して触れられない（`model_access(credentials) == false`）。**

### 4.4 「検証者は拒否できなければならない」：本番システムは自分自身を採点できない

評価の3つの問いは能力/振る舞い/結果を分離する；**本番システムは自分が成功したかどうかの唯一の審判であってはならない**——検証者（決定論的チェック・真実源の照合・独立評価・下流確認・説明責任のある人間レビュアー）は結果を拒否できなければならない。「受け入れ」は「agent がワークフロー末尾に到達した」よりも多くのことを要求する。この哲学は「agent に自己検証をさせるな」と同系だが、それを**価値憲章のハードフィールド（名前付き検証者）にまで昇格させている**。

### 4.5 「スコアは対話を支え、ゲートは平均できない」：証拠の倫理

0/1/2 採点フレームワークと4つのハードゲートの分離は、プロジェクト全体で最も鋭い哲学的見解である：**デモと複合スコアは失敗したゲートを平均で帳消しにできない；予測・証明済みパイロット・実現済み価値は分離しなければならない；ゼロは証拠であり、デフォルト値ではない。** 弱い仕事を止める・狭める・再設計することは有効な結果である——強いモデルスコア・スポンサー・ローンチ数字は、失敗した価値/権限/セキュリティ/所有権/本番ゲートを隠せない。**評価は「宣言された条件でのリリース主張」であり、永久的なスコアではない。**

### 4.6 「回避策はドメイン専門性ではない」：現場への謙虚さ

実際の仕事（スライドの中のプロセスではなく）を観察する；観察された各振る舞いを保持/修正/削除/エスカレーションに分類する。**AI は壊れたプロセスをより速く走らせ、同時に根本的な問題をより見えにくくする。** フィールドラーニングの複利の優位性は、ローカルコンテキストとポータブルなエンジニアリング知識を分離する能力にある；依存関係を作らず、ネガティブ証拠と停止証拠を保持し、退出パスを残す。

## 五、まとめ（見解と結論）

### 5.1 コア見解リスト

1. **価値の定義：** 受け入れられた結果（独立検証者/権限システム/説明責任のあるレビュアーが正しいと受け入れた作業単位）こそが製品；token と自動化は入力と手段に過ぎない。
2. **出発点：** 仕事と受け入れられた結果から始める——モデルや agent トポロジーからではなく；Agent はコンポーネントの選択肢であり、アーキテクチャではない。
3. **最小の十分メカニズム：** 重要な決定ごとに7つのメカニズムを比較し最小の十分なものを選ぶ；「AI を使う」はアーキテクチャ上の決定ではない；より AI 的であることは、ワークフローが正しく分解されていないことを意味するかもしれない。
4. **観察優先：** 実際の仕事（オペレーターのウォークスルー/ソースアーティファクト/システムトレース）を観察してから設計する；インタビューは仮説を生むだけ；スライドの中のプロセスを自動化せず、修正前に回避策を自動化しない。
5. **価値憲章のフィールド：** 適格母集団/ベースライン/受け入れられた結果/検証者/目標ガードレール/帰属/フルコスト/残余損失/所有者——9フィールドはアーキテクチャより先。
6. **12 ファクター + 4 ハードゲート：** 所有された結果 / 信頼できる独立検証者 / 境界づけられた権限と期待損失 / フルコスト後も正の価値ケース；いずれか欠如 → defer / redesign / do_not_build；0/1/2 採点は対話を支えるがゲートは平均できない。
7. **権限の境界：** 能力は権限を授けない；モデルは提案し、信頼できるソフトウェアが承認してコミットし、真実源の読み戻しが証明する；秘密とクレデンシャルは常にモデルコンテキストの外；冪等性（1つのビジネスオペレーションは1回コミット）と効果不明の照合はハードな不変条件。
8. **採用と運用：** 技術的成功だが誰も使わない = ゼロ価値；移管は「受領チームが運用/変更/回復/サポート/退役できる」ことが完了基準（ドキュメントではなくドリル）；本番は繰り返される決定であって最後のデプロイステップではない。
9. **agent ファーストへの反対：** ハイブリッドシステム例は、決定論的ポリシー + 古典的 ML + 人間レビューが正しいアーキテクチャになり得ることを証明する；境界づけられた多段階の判断が本当に有用なときだけ agent を追加する。
10. **フィールドラーニング：** 複利の優位性 = ローカルコンテキストとポータブル知識の分離；プロダクト化には独立環境をまたぐ再現証拠 + サニタイズ + 宛先所有者 + 通常のリリースパスが必要；依存関係を作らない。

### 5.2 覚えておきたい金言（memo に値する）

- "Tokens are an input. Autonomy is a design choice. Accepted outcomes are the product."（**Tokens は入力、自律性は設計上の選択、受け入れられた結果こそが製品。**）
- "Start with the work and the accepted outcome—not with a model or agent topology."（**仕事と受け入れられた結果から始める——モデルや agent トポロジーからではなく。**）
- "Capability does not grant authority."（**能力は権限を授けない。**）
- "The model may propose. Trusted software authorizes and commits. A source-of-truth readback proves the result."（**モデルは提案できる；信頼できるソフトウェアが承認してコミットする；真実源の読み戻しが結果を証明する。**）
- "AI has an accounting problem."（**AI には会計問題がある。**）
- "The system producing the work should not be the sole judge of whether it succeeded."（**仕事を生み出すシステムは、自分が成功したかどうかの唯一の審判であってはならない。**）
- "A workaround is not automatically domain expertise."（**回避策は自動的にドメイン専門性ではない。**）
- "A more capable model will not repair an undefined task."（**より高能力なモデルは未定義のタスクを修復しない。**）
- "The point is not to use more AI. The point is to make the outcome worth the system required to produce it."（**ポイントはより多くの AI を使うことではない。ポイントは、結果を、それを生み出すのに必要なシステムに見合うものにすることだ。**）

- **Graph Engineering Guide (2026)**（`graph-engineering-guide-2026-analysis`）：図エンジニアリングは「いつ agent をグラフに織るか」を議論する；fde-guide はより早い問いに答える——**このワークフローがシステムにする価値があるかどうか、メカニズムをどう選ぶか、結果をどう受け入れるか**を最初に決める。両者は補完的である：グラフは構造選択、FDE Guide は価値とガバナンスの前提。
