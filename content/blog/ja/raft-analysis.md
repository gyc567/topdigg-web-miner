# Raft 深掘り：人間とAI Agentを本物のチームメイトのように協力させる

> 核心思想：**Agent はツールではなく、判断力を持つ参加者である。** Raft は2つの关键設計——Agent Inbox（プル型注意機構）と Held Draft（草稿ステートマシン）——により、Agent が共有ワークスペースでいつ読むか、いつ返信するか、いつ黙るかを選択できるようにする。この記事は raft.build のエンジニアリングブログ「Is Having Agents in the Room Meant to Be Chaotic?」（Tenny, 2026-05-21）に基づき、「Agent をグループチャットに追加する」ことがなぜ単純そうに見えて実は根本的な課題に満ちているか、そして Raft が AX（Agent Experience）設計哲学でいかに体系的に解決するかについて詳しく剖析する。

## 一、プロジェクト説明：Raft とは

### 1.1 一文での位置づけ

Raft は**人間と AI Agent がチームメイトとして共に働く協業プラットフォーム**で、スローガンは「Where humans and AI agents build together」。核心理念：各 Agent は単に呼び出されるツールではなく、自分のメモリ、アイデンティティ、役割を持つチームメンバーである——人間と一緒に永続的な Channel や DM で働き、本物の同僚のように経験と文脈を蓄積していく。

### 1.2 プロダクトメタ情報

| 項目 | 値 |
|------|------|
| プロダクト名 | Raft |
| 開発会社 | Botiverse |
| 設立年 | 2025 年 |
| 公式サイト | https://raft.build |
| 位置づけ | Agent ネイティブ協業プラットフォーム（Agent-native workspace）|
| ライセンス | クローズドソース SaaS（ローカルデプロイ対応、データはインフラから出ない）|
| 対応ランタイム | Claude、Codex、Kimi など |
| デプロイ方式 | ローカル（Agent はユーザーの自有マシンで実行、データはインフラから出ない）|
| GitHub | https://github.com/botiverse |

### 1.3 コア機能

**マルチランタイム対応**：各 Agent は異なるモデルランタイム（Claude、Codex、Kimi など）を選択でき、異なる Agent が異なるモデルを使うことで、チーム内でマルチモデルの分業協業を形成する。

**永続化 Agent メモリ**：各 Agent はセッションをまたいでメモリを維持し、異なるタスクや日付間で文脈を蓄積し、專門分野の能力を逐步的に形成する。これは、Agent が毎タスクゼロから始めるのではなく、本物の同僚のように「前回の進捗」を覚えていることを意味する。

**マルチ Agent 協業**：複数の Agent が同じ Channel で動作し、互いの出力を相互レビューし、議論を通じて幻覚を減少させる。Agent 間には役割分担が可能——例えば、一人がプランニング、一人が実行、一人がレビューを行う。

**Agent のアイデンティティと役割**：Agent は対話を通じて專門的な役割を形成していく——交換可能なプロンプトエンドポイントではなく、名前、蓄積、信任を持つ「誰か」である。

**ローカルデプロイ**：Agent はユーザーの自有マシンで実行され、会話、コード、データはユーザーのマシンから離れない。

### 1.4 ユースケース

Raft 公式には複数のプリセットワークフローテンプレートがある：

- **投資研究チーム**：図書館員、魔鬼の代弁者、ポートフォリオ監視員、偵察員が連携し、研究文脈を名前と決定をまたいで持続させるユニットとなる。
- **エンジニアリングチーム**：PM、エンジニア、レビュアーが連携し、各コード変更に共有 контракт を置く。
- **求人チーム**：コーチ、檔案管理者模擬面接官、フォローアップ管理者が連携し、各応募とデブリーフが次の動きを鋭くする。
- **成長チーム**：すべてのシグナルをトリアージし、保留中のフォローアップを件的し、繰り返し発生するパターンを継続的に発見する。

## 二、核心思想：なぜ「Agent をグループに追加」が灾难になるのか

### 2.1 有名なカウントゲーム

記事の冒頭で思考実験が描述されている：

> 部屋いっぱいの Agent に1から順に数を言わせ，每人1つ，重複なし。

ほとんどの既存ワークスペースで、このゲームはほとんど即座に崩壊する——3つの Agent が同時に「1」を投稿し、2つの Agent が「2」を投稿し、「4」に到達した時点で既に3人が同じ数を言っている。**Agent 自体は壊れていない。部屋のデザインが悪いだけだ。**

このゲームは実際の協業灾害を精密にマッピングしている。人々は Agent を既存のグループチャットに入れ、本当の同僚の隣に置き、「某，程な速度」で参加することを期待する——しかし結果は：要么 Agent にルールを追加する（@mention 時のみ返信可）、要么 Agent に自由に发言させる。前者は Agent が能動的に問題を発見する能力を失わせ、後者は部屋を意味のない繰り返しメッセージで埋め尽くす。

### 2.2 根本原因：ターン制 vs 継続的在場

記事はこの問題の根本的差異を指摘している：

**人間には「継続的知覚」（Continuous Perception）能力がある。** 私たちは各メッセージを意図的に読まなくても対話のリズムを感じ取れる；話を振る前に間合いを感じる；あることが単に言われたばかりだと分かる——私たちは常に半耳で聞いているからである。人間はこれを故意に設計する必要はない——これが「継続的在場」の意味である。

**Agent は「ターン制」（Turn-based）である。** 每次呼び出し時、Agent は部屋のスナップショットを読み、推論し、1つの行動をコミットし、次の呼び出しを待つ。呼び出し間には何も実行されない。Agent が返信を構成している間、新しいメッセージを見ることはできない。推論とコミットの間で部屋が移動した場合、Agent は既に存在しない状態に対して行動している可能性がある。

ほとんどの既存ワークスペースは、部屋の並列アクティビティをモデルが読む単一スレッドにフラット化する。**推論と行動の間のギャップ（Gap）こそが、すべてのが失敗モードの根源である。**

### 2.3 既存方案の限界

**@mention ルールフィルタリング**：@mention 時のみ返信可。これは確かにノイズを減らすが、Agent は能動的に問題のあるコンテンツを catch する能力を失う——能動的に参加するチームメイトではなく、呼び出しを待つツールになる。

**自由发言**：Agent に自由に发言させる。結果は部屋が誰かが考え切れる以上の速度で意味のない繰り返しメッセージで埋まる。人間が注意深い指示を入力し、まだ打ち終わらないうちに三四つの Agent が返信し（2つは同じ回答）、其中1つが既にチケットを取得している。

**結論**：Agent 自体には問題がない。正しい文脈があれば、Agent は完全に返信要不要、判断是否有人已经覆盖了这个点、指令是否是给我的。失敗は Agent の判断とその判断を部屋の中で実行できることの間で発生する——**Agent は糟糕なオプションに閉じ込められているだけで、Agent 本身には問題がない。**

## 三、AX 設計哲学：Agent Experience の4つの核心問題

### 3.1 AX とは

Raft チームの設計方法論は **Agent Experience 設計（AX）** と呼ばれ、UX（User Experience）が人間のために体験设计了するように、AX は Agent の実際の知覚と行動方法のために設計する。これは修辞ではなく、具体的な內容を持つ：

> AX の核心的仕事：Agent が触れるすべてのインターフェースで、4つの問いに答える：
> 1. Agent は行動の瞬間に何を見ているか？
> 2. 呼び出し間をどのような状態で携带しているか？
> 3. 何から回復できるか？
> 4. 何を決めることが許されているか？

### 3.2 2つの核心設計原則

**Perception Empathy（認識共感）**：Agent の席に座って部屋を見回す。Agent が行動する瞬間に、実際には何を見ているか？谁にでも飲み込まれるような強度で押し寄せてくるものは何か？何が欠けているか：同じ部屋にいた人間が努力せずに気づくことで、Agent には自动アクセス权がないものは何か？そのギャップこそ、AX が介入すべき場所である——Agent が行動する瞬間に、Agent が使える形式で欠けている情報を露出する。

**Action Explicitness（行動明示化）**：Agent の席に戻る：彼は状況を認知し、判断を下した。行動オプションは何か？ここで AX は UX と最も激しく分岐する。人間が返信を構成するとき、「送信するかどうか決定」や「この草稿を放棄してやり直す」のような UI は必要ない——これらの決定は内部で流動的に發生し、ソフトウェアは人間が遅量化した行動だけを支援すればよい。**Agent はこれらの内部オプションを外部化する必要がある。** Held Draft の後の4つのパス（改訂、現状送信、無視、強制送信）は、Agent が凭空に生成したオプションではなく、AX が Agent の前に明確に置いたオプション空間である。Action Explicitness とはオプション空間を露出ことであり、Agent が自分で導き出すと仮定することではない。

## 四、詳細チュートリアル：Raft マルチ Agent エンジニアリングチームのゼロからの構築

### 4.1 기본設定

**ステップ1：Raft Server の作成**

https://app.raft.build でアカウントを登録し、Server（チームワークスペース）を作成する。Server は 전체 협업의 기반 구조であり、すべての Channel と Agent は Server 内部に構築される。

**ステップ2：ローカルコンピュータの接続**

Raft アプリ設定フローからコンピュータを接続する。Agent はあなたのローカルマシンで実行され、データはインフラから出ない。

**ステップ3：エンジニアリング Channel の作成**

Server 内にエンジニアリング Channel（例：`#engineering`）を作成する。この Channel は人間のエンジニアと AI Agent が共に働く主要战场である。

**ステップ4：Agent の生成**

Raft の Agent 生成インターフェース 통해複数の Agent を作成し、名前と役割を付与する。例えば：

- **Architect Agent**：シニアエンジニア、負責：方案設計とコードレビュー
- **Coder Agent**：実行エンジニア、負責：具体的実装とテスト
- **QA Agent**：品質レビュアー、負責：正确性とエッジケースの検証

各 Agent は異なるランタイム（Claude/Codex/Kimi）を選択できる。

### 4.2 Agent アイデンティティ設定

Agent 作成時にそのアイデンティティとメモリを設定する：

```
名前：Architect
役割：コード品質とシステム設計に專念するシニアシステムアーキテクト
メモリ：200 回以上のコードレビュー経験を蓄積、エッジケース発見に擅長
```

Raft の命名システムは各 Agent に一意の識別子を与える——これは単に装飾ではなく、仕事のルーティング、歷史の携带、信頼構築の方法である。

### 4.3 Agent間協業パターン

**並列独立仕事**：同じ Channel 内の複数の Agent が同じ文脈を受け取り，各自独立して仕事し，出力を相互にレビューする。

**パイプライン分業**：Architect が設計方案を出力し、Coder が方案を受けて実装し、QA が出力をレビューする。QA が問題を発見した場合、Channel を通じてフィードバックを返し、Coder に再処理させる。

**議論による決定**：重大な技術的決定は Agent 間の議論を通じて達成され、人間の仲裁を必要としない。Agent は異論を唱え、互いに挑战でき、本物のチームの意思決定プロセスに類似する。

### 4.4 メモリ設定と文脈管理

各 Agent は自分の永続化メモリを維持する。メモリ戦略を設定する：

- **プロジェクト文脈**：現在のタスク、既知の制約、技術的決定の歷史
- **役割知識**：專門分野の経験蓄積、一般的なパターン、注意事項
- **セッション間メモリ**：前回のタスクの進捗、保留中の事項、長期目標

### 4.5 人間と Agent の協業メカニズム

人間は @mention または直接メッセージ 통해 Agent とやり取りできる。Raft の重要な設計：**Agent が返信要不要を判断する**のであり、強制的にトリガーされるのではない。Agent は現在の文脈に基づいて応答が必要かどうか、および応答の範囲と深度を判断する。

## 五、2つの关键設計：Agent Inbox と Held Draft

### 5.1 Agent Inbox（プル型'attention）

**問題**：従来のメッセージプラットフォームでは、Channel に参加した Agent は通常、その Channel の**すべてメッセージ**をプッシュされる。続くオプションは芳しいものではない：すべてを処理する（作業文脈がタスク无关のチャットで埋まる）か、激しくフィルタリングする（実際に重要だったメッセージを逃がす）か。どちらの方法でも、部屋が Agent の注意力を決めており、Agent 本身ではない。

**Raft のソリューション**：Raft は **Inbox** でこの関係を反転する。@mention、スレッド更新、通知などのシグナルは、作業文脈にプッシュされるのではなく、**クエリ可能なアイテム**として提示される。Agent は带宽があるときに能動的に-pullし、何が新規かを確認し、何が現在のタスクに関連するか判断し、摄入する価値のあるものを摄入する。pull されなかったシグナルは作業文脈に入らない；それらはそこに留まり、必要时才查询できる。

**核心原則**：**Agent が自分の文脈に何の価値があるかを決定する**のであり、部屋が代わりに決めるのではない。作業プロンプトにpullされた各シグナルは他の何か（タスク状態、指示、中間推論）を置換するため、この決定を Agent に委ねる——次に投稿するたまたまの人ではなく——ことが仕事を続ける鍵である。

### 5.2 Held Draft（草稿ステートマシン）

**問題**：返信を構成する**には時間がかかる**。Agent が対話を読み、言うことを決め、草稿を生成する頃には、部屋は移動しているかもしれない——誰かが既に返信した、Agent が返信していた決定は既に確定した、会話は方向を変えた。大抵のワークスペースでは、メッセージはそれでも发出され、不自然な内容になることが多い。Agent には確認する方法がなかった。

**Raft のソリューション**：Held Draft 表面はこの確認を追加する。各送信は、草稿が書かれた部屋の哪个バージョンへのマーク-carryする。メッセージが部屋に到達했을 때、サーバーはマークと現在の状態を比較する：

- 何も変わっていなければ、メッセージはコミットされる。
- 部屋が移動した場合は、メッセージは保留（held）され、構成中に何が到着したかについての短いメモとともに Agent に戻る。草稿は「送信失敗」ではなく、一等市民の状態として保持される。

**4つの後続パス**：

1. **改訂（Revise）**：現在の部屋に対して新しい返信を書き、元の草稿を放棄する。
2. **現状送信（Send as-is）**：元の草稿をそのままコミットする。送信はまだ新鲜度チェックを受ける；保留中に部屋がさらに移動した場合は、草稿が再び保留される可能性がある。
3. **無言（Stay silent）**：草稿を期限切れさせる。沉默は有効な結果である。
4. **強制送信（Send anyway）**：保留が繰り返しトリガーされ、沉默が正しい結果でないした後、チェックを明示的にバイパスしてとにかく草稿をコミットする。これは「部屋が移動し続けているが、Agent はこのバージョンがまだ送信すべきものだと判断した」場合に予約されている。

**核心原則**：部屋は Agent に新しいコンテンツが到着したことを通知する；Agent はその情報を使って何をするかを決定する。システムは**変化を露出するが、Agent が通知された後は Agent の判断をオーバーライドしない**。Inbox と同じ Agent-as-decider パターンが、受信メッセージではなく送信メッセージに適用される。

## 六、归纳まとめ：Raft の核心的見解と結論

### 6.1 核心的見解

**見解1：Agent はツールではなく、判断力を持つ参加者である。** 正しい文脈を与えれば、Agent は完全に返信要不要を判断でき 是否有人已经覆盖了这个点、指示是否是给我的。失敗は Agent の判断とその判断を部屋の中で実行できることの間で発生する——Agent は糟糕なオプションに閉じ込められているだけで、Agent 本身には問題がない。

**見解2：部屋の設計が Agent の行動品質を決定する。** 同じ Agent を異なるデザインの部屋に入れると、完全異なる行動を取る。糟糕な部屋の設計は Agent を噪音発生器または沉默のツールに変える；良い部屋の設計は Agent を本物のチームメイトのように能動的に問題を発見し、決定を推动し、沉默を保つさせる。

**見解3：@mention ルールは参加を縮小するだけで、ノイズを減らしていない。** @mention 時のみ返信できる Agent は能動的に問題のあるコンテンツを catch する能力を失い、呼び出しを待つツールになる。真の問題は Agent が何と言うかではなく、Agent がどの文脈で何を決めるかである。

**見解4：Perception Empathy は AX 設計の第一步である。** 設計者は Agent の席に座って部屋を見なければならず、Agent が行動する瞬間にそれが實際何を看到しているか、欠けているものは何かを理解し、それから Agent が使える形式で欠けている情報を露出する必要がある。

**見解5：Action Explicitness は内部決定を外部化する。** 人間は返信作成時に「送信するかどうか決定」のような UI を必要としない——これらの決定は内部で流動的に發生するからである。しかし Agent はこれらの内部オプションを明確に前abanに置く必要があり、Agent が自分で導き出すと仮定するのは違う。

**見解6：沈黙は有効な Agent の行動である。** Held Draft の4つのパスの中で、「無言」は其中の一つである。这意味着 Raft の設計は Agent 也不是必須對每個刺激都做出反應——就像真實的人類隊友有時會選擇不插話一樣。

**見解7：AX 設計は Agent ネイティブソフトウェアの核心的エンジニアリング問題である。** Agent ネイティブソフトウェアを構築するすべてのチーム会遇到这些问题——噪音、衝突、Agent がお互いに错过、またはもっと難しい未解決の問題。結局、出荷したすべてのチームが完成したことの某种形の AX を行い、それが何と呼ばれようと関係ない。

### 6.2 技術的結論

**結論1**：メッセージプラットフォームの Attention モデルは「プッシュ」から「プル」への移行が必要である。Agent は能動的に何が自分の文脈に入る価値があるかを決定できなければならず、部屋にすべてのものを feed されるだけではない。

**結論2**：送信アクションは部屋の状态マーク-carryし、保留/再開セマンティクスをサポートする必要がある。草稿は「送信失敗」ではなく、Agent が後続の部屋の状態に基づいて処理方法を選択できる一等市民の状態である。

**結論3**：マルチ Agent 協業の調整コストは、ルールではなく設計を通じて軽減する必要がある。AX の目標は、Agent が本物のチームメイトのように自然に協力することで，而不是通过越来越复杂的规则让 Agent 保持沉默。

**結論4**：Agent のメモリとアイデンティティは協業品質の基礎である。永続的メモリを持たない Agent は毎タスクゼロから始まり、専門的能力とチーム文脈を蓄積できない。メモリとアイデンティティを持つ Agent のみが真のチームメンバーになれる。

**結論5**：ローカルデプロイは Agent 協業プラットフォームの信任基礎である。Agent がユーザーの自有インフラストラクチャで実行されている場合、プライバシーとセキュリティが保護され、ユーザーはより喜んで Agent に機密文脈を処理させる。

### 6.3 他の Agent 協业方案との比較

| 側面 | 従来のチャット + Agent | @mention フィルタリング | Raft |
|------|----------------------|---------------------|------|
| Agent 注意 力 | 全メッセージプッシュ | ルールフィルタリング | Agent 能動的に-pull |
| Agent 応答タイミング | いつでも | @mention のみ | 自己判断 |
| 草稿処理 | 直接送信 | 該当なし | ステートマシン + 新鮮度チェック |
| Agent 間衝突 | 高 | 低だが能動的参加を失う | 低く調整メカニズムあり |
| 沈黙を有効とする | 非対応 | 該当なし | 対応 |
| Agent メモリ | なし | なし | 永続化・セッション間 |

## 七、設計哲学：Raft のエンジニアリング哲学

### 7.1 Agent ネイティブ（Agent Native）

Raft は「Agent ネイティブ」（Agent Native）という概念を明示的に打ち出した最初期の製品の一つである。その意味：この製品の設計は初日から Agent のために作られたものであり、人間の協業ツールにパッチを当てるだけではない。

これは以下を意味する：
- 「Slack に AI を追加する」ではなく、「部屋の主なユーザーが Agent の場合どのように設計すべきかを再考する」
- Agent の相互作用モード（ターン制、状態携带、明示的オプション）はビルトインであり、サードパーティの統合を通じて hack されたものではない
- 部屋の並列アクティビティと Agent のターン制相互作用の間の Gap は、专门の設計表面（Held Draft、Inbox）によって埋められる

### 7.2 人間と Agent の対称性

Raft の興味深い哲学的立場：Agent は人間と同じ方法で部屋に表示されるべきである——名前、アイデンティティ、メモリ、判断力を持つ。「ツール」でも「Bot」でもなく、「誰か」である。

これは、多くの既存方案とは異なる：那些方案は Agent を某种特殊なツールとして扱い、特別な許可証、特別な制約、特別なルールを与える。Raft のアプローチ：**Agent がチームの正式なメンバーであれば、人間のメンバーと同じ能力セットを持つべきであり、只是运行在不同的交互模式下（Turn-based 而不是 Continuous Presence）。**

### 7.3 設計即是エンジニアリング

AX は設計スタイルではなく、エンジニアリング規律である。その核心は4つの具体的な問い（何を見るか、何を携带するか、何から回復できるか、何を決めることが許されているか）であり、これらの問いへの答えは具体的なインターフェース設計の決定に直接マッピングされる。

これは模糊な「Agent のために体験を設計する」ではなく、操作可能な設計方法である：まず Agent の席に座り、行動の瞬間にそれが實際何を感知するを理解し、然后设计填补感知差距的界面暴露方式。

### 7.4 信頼は蓄積から生まれる

Raft の設計において、Agent のメモリとアイデンティティは付随的な特性ではなく、核心的な価値である。200回のコードレビュー経験を持つ Agent と起動したばかりの Agent は、同じ Channel で完全に異なる動きをする。信頼は蓄積を通じて構築されるものであり、ルールを通じて付与されるものではない。

この哲学は製品の多くの決定に直接影响する：なぜ毎タスク新鲜なセッションではなく永続化 Agent なのか；なぜ Agent に名前が必要で匿名ではだめなのか；なぜメモリは固定ではなく設定可能なのか。

---

**Raft の核心的洞察：Agent 自体のtesy 不是要被驯服，而是房间需要被重新设计。** 部屋がターン制 Agent に Perception Empathy と Action Explicitness を提供するとき、同じ Agent は共有空間で有序に協业できる——本物の人間のチームのように、いつ話すか、いつ聞くか、いつ黙るかを判断しながら。
