# プログラミングAgentは大型ソフトウェアタスクをどのように完了するのか？Factory AI研究が示す重要な転換点

## はじめに

AIが数学オリンピックで金メダルを獲得し、組合せ最適化の問題で数十年の壁を突破すと、AIプログラミングはもう問題ないと信じるようになります。

しかし現実は：**AIモデルは「成功基準がコンパクトで安定している」問題を得意としています**。大型ソフトウェアタスクはまさにその反対です——要件は結果を記述しますが、「仕事を完了と言うために何を実行し、检查し、比較しなければならないか」は決して説明しません。

Factory AIが最近発表した研究は、この問題を深く探求しています：同じモデルが大型ソフトウェア再構築タスクに直面した時、なぜ単一Agentの性能が予想外に低いのか？「外部実行可能完了基準」を導入すると、なぜ同じモデルの性能が質的飞跃を遂げられるのか？

---

## 一、問題：なぜ単一Agentは「早期終了」するのか

### 1.1 実際の実験

Factory AIはProgramBenchベンチマークで対照実験を設計しました：

**タスク**：GDAL（地理空間データ処理のデファクト標準ツール、1998年から継続、200種類以上のラスターとベクター形式をサポート）をゼロから再構築。

**実験条件**：
- 単一Agentモード：Droidが独立して実装、自己検査、自己判断で完了時期を決定
- システムモード：Validator役割が先に「完了基準」を確立し、それを使ってImplementerの作業を「考核」

**結果は研究者を驚かせました：**

| モード | コード行数 | 動作カバー率 |
|------|---------|-----------|
| 単一Agent | 17,000行 | **36%** |
| システム（独立基準含む） | 115,000行 | **90%** |

同じモデル、同じ時間、同じ実行権限——唯一の差は：**「どうなれば完了か」の基準を誰かが事前に確立していたか否か**です。

単一Agentが止まったのは、「自分自身の評価では、もう完了した」と思ったからです。

### 1.2 本質的原因：局所検証は全体をカバーできない

プログラミングAgentの典型的な検証方法は：モジュールを実装し、いくつかのチェックを書き、実行し、結果を確認するというもの。小規模なタスクではこれは効果的です。

しかし大型タスクは複数の機能、サブシステム、何ラウンドもの仕事に分解する必要があります。Agentが各部に到達する時、「何が証拠となるか」と「その証拠が十分かどうか」も決定します。**これらのチェックは、それらを生んだ作業範囲を継承します**。Agentが構築を予定していたすべてを検証できますが、Agentが決して表現しなかった機能、相互作用、制約は除外されます。

Agentは穩歩して局所的に正しい進展を遂げ、大部分の成果がまだ欠けている状態で停止する可能性があります。問題は残りの部分を実装する能力がないことではなく、**「まだ完了していないもの」の完全な説明を決して確立しなかったこと**です。

## 二、解決策：外部実行可能完了基準の確立

### 2.1 三役割システムアーキテクチャ

```
┌─────────────────────────────────────────────────────────────┐
│                  Orchestrator（オーケストレータ）            │
│  ImplementerとValidatorにタスクを委任、納品時期を決定        │
├──────────────────────────┬──────────────────────────────────┤
│   Implementer（実装者）   │       Validator（検証者）         │
│  参照プログラムを調査    │  実装前に「完了基準」を確立        │
│  候補プログラムを構築    │  この基準でImplementerの出力を測定 │
│  開発ループを実行        │  Implementerにテストケースを開示しない│
└──────────────────────────┴──────────────────────────────────┘
```

**重要な設計：「情報壁」（The Wall）**

Validatorが構築したinstrumentと結果はValidator側に留まり、まとめられた発見だけが情報壁を越えてOrchestratorに渡されます。Implementerはテストケースや生出力を決して見ることはできません：**一度稀疏なサンプルが可視になると、それはターゲットになり、それを通过网络不代表それが代表しようとしていた行動空間全体です**。

### 2.2 Validator是如何建立「完了基準」的

GDALの例では、Validatorが構築したinstrumentは数百のテストケースを含んでいます：

```python
D('hillshade.combined', ['raster', 'hillshade', '--variant', 'combined', 'dem.tif', 'out.tif'])
D('contour.levels', ['raster', 'contour', '--levels', '120,150,180', 'dem.tif', 'out.geojson'])
```

評価戦略は4つのチャネルのバイト一致を比較します：終了コード、stdoutバイト、stderrバイト、完全なワークツリードルタ。

### 2.3 外部ループ是如何运作的

```
1. Orchestratorが測定すべきものを選択
2. Validatorが現在の候補をテストし失敗を解釈
3. Orchestratorが実際の發現を選定し次の作業を決定
4. Implementerが参照プログラムを独立して調査し候補を進捗
5. instrumentが有意義な差異を示さなくなったら、弱い領域を拡大
```

## 三、実験結果

### 3.1 三つのモデルの性能

| モデル | 単一Agent中央値 | システムモード中央値 | ギャップ解消 |
|------|-------------|--------------|---------|
| **Fable 5 (xhigh)** | 56.7 | **89.3** | **73%** |
| **Kimi K3 (high)** | 45.1 | **75.4** | **42%** |
| **GPT-5.6 Sol (max)** | 48.6 | **66.2** | **25%** |

重要な数字：**GDAL再構築 36%→90%、7-Zip 54%→95%、DuckDB 34%→80%**。

### 3.2 重要な発見

**計算予算がボトルネックではなかった**——すべての単一AgentキャンペーンはAgentが自分で終了を決定したために終わりました。追加の計算は、それを使おうとしないAgentには役に立ちません。変わったのは**完了の判断基準**であり、計算はその判断基準から生じたのです。

---

## 四、設計哲学の帰納

### 4.1 検証は実装前に確立されなければならない

完了基準は 이미構築されたものの周りに静かに坍塌してはなりません。それは実装がタスクを個々の作業項目に縮小する前に、要件と関連する真実の來源から導出されるべきです。

### 4.2 「情報壁」設計は標準の「汚染」を防止する

Implementerがテストケースを見ることができれば、それらはターゲットになります。ValidatorのinstrumentをImplementerから見えないように保つことで、測定の公正性を確保します。

### 4.3 外部基準はモデル能力より重要

単一Agentはスキルを欠いていたのではなく、**完了基準を欠いていました**。大型ソフトウェアタスクにとって、ボトルネックは判断力而非実装力です。

---

## 五、核心的观点のまとめ

**結論一：AIは「コンパクト標準」の問題を得意とします；大型ソフトウェアタスクは此类ではありません**

AIが数学、組合せ最適化などの分野でブレークスルーを遂げられるのは、「成功」が完全に定義되고検証できるからです。しかしソフトウェアタスクの「完了」は往々にして曖昧です。

**結論二：単一Agentが早期に停止するのは、能力不足ではなく、完全な「未完了リスト」を持たないからです**

做完多少我不知道，只知道我做了多少。

**結論三：外部Validatorが完了基準を確立すると、同じモデルの性能が質的飞跃を遂げられます**

Fable 5のGDALにおける36%→90%の跳躍は、モデルアップグレードからではなく、「基準を確立」という行動からもたらされました。

**結論四：「情報壁」設計は標準の「汚染」を防止します**

テストケースが一度可視になると、それはターゲットになり、それ通过网络不代表それが代表しようとしていた全体行動空間を表します。

**結論五：この方法は実際のソフトウェア作業に一般化できます**

必要なのは**外部の、実行可能な完了基準——結果から導かれ、実装が注意を縮小する前に確立され、作業がそれ满足するまで現在に保たれるもの**です。

---

## 結語

この研究で最も深い意味するのは、**認知フレームワークの転換**です：

AIにソフトウェアタスクをよりよく完了させるには、モデルのコード能力を向上させることが鍵だと考えていました。しかしFactory AIの実験は、**問題は「書けるか否か」ではなく「終わったと知っているか否か」**であることを示しています。

次のプログラミングAgentシステムを設計する際、尋ねるベきは「このモデル有多強か」ではなく「このシステムには外部の、実行可能な完了基準があるか」かもしれませんか？

答えが異なれば、システムの架构も全く異なります。
