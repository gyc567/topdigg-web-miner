# ttfx：ターミナル文字エフェクトを3.3MBの単一静的バイナリにコンパイルしたRust移植

## 記事の背景とプロジェクト概要

ターミナルで `fortune` や `cowsay` を実行したことがある人、あるいは `neofetch` でシステム情報を表示している人なら、コマンドラインの世界に「ちょっとした魔法」への渇望があることを知っているはずだ。[TerminalTextEffects](https://github.com/ChrisBuilds/terminaltexteffects)（略称 TTE）は、ChrisBuilds 氏によってその魔法を極限まで押し上げた——あなたのテキストをターミナル上で**解読・燃焼・爆発・流星雨**のように演出できる、37種類のエフェクトをすべてオープンソースで提供している。

しかし TTE には「幸福な悩み」がある。それは Python パッケージだということだ。ライブラリとしては完全に正しい選択だが、シェルパイプラインの中で生きる玩具としては、Python はインタプリタ、インストール手順、そして**最初のフレームが表示されるまでの約65ミリ秒の import 遅延**を意味する。

**ttfx** はその問題への答えだ。TTE の全37エフェクト、アニメーションエンジン、コマンドラインインターフェースを、**実行時依存ゼロの単一静的バイナリ**にコンパイルした Rust 移植版である——起動はわずか **0.5ミリ秒**、サイズは約 **3.3MB**。

> ttfx: Terminal text effects as a single static binary. Pipe text in, pick an effect:
>
> ```sh
> ls -la | ttfx decrypt
> cat banner.txt | ttfx beams
> fortune | ttfx --random-effect
> git log --oneline -10 | ttfx matrix
> ```

これは「Rust で書き直した」という普通の移植ではない。ttfx の野望は**パリティ完全一致（parity-exact）**だ。同じ入力、同じ設定、同じ乱数列を与えれば、生成されるすべてのフレームが Python オリジナルと**バイト単位で同一**になる。そしてその一致は目視ではなく、CI での機械的な検証によって証明されている。このプロジェクト自体が「真剣に移植するとはどういうことか」の教科書である。

## 核となる設計哲学

### 名誉は原作者に：移植は余計なことをしない

プロジェクト README の最初の一文は "Credit where it's due"（名誉はあるべきところに）だ：

> **これは ChrisBuilds 氏の TerminalTextEffects の移植版です。** すべてのエフェクト、アニメーションエンジン、コマンドラインインターフェースは彼らの設計によるものです——このプロジェクトはその作業を Rust に翻訳しただけで、**この芸術に独自のものを何も加えていません**。もし気に入ったなら、オリジナルにスターを付けてください。

この謙虚さは社交辞令ではなく、厳格な原則だ。エフェクトのアイデアまでもが「Please file *effect* ideas upstream, where they belong.（エフェクトのアイデアは本来あるべき場所、アップストリームに提出してください）」と明示的に案内されている。移植プロジェクトはプロダクトマネージャーにならず、翻訳者に徹する。

### Parity Port：バイト単位の一致、決して「雰囲気の再現」ではない

ほとんどの移植プロジェクトの受け入れ基準は「機能がだいたい同じで、見た目が似ている」だ。ttfx の基準は桁違いに厳しい：

> これは *parity port*（同等移植）であって、reimplementation-in-spirit（精神的な再実装）ではありません。同じ入力・設定・乱数が与えられたとき、ttfx は Python オリジナルと**バイト単位で同一のフレーム**を生成します——固定されたアップストリームチェックアウト（v0.15.0）に対して CI で機械的に検証されており、目視ではありません。

この検証体系は6つのテストスイートから構成される：

| スイート | チェック数 | 証明するもの |
|------|--------|---------|
| `tools/parity/run_suite.sh` | 354 | 全エフェクトのフレームストリームが、設定・シードをまたいでバイト単位で一致 |
| `tools/parity/tty_compare.sh` | 41 | 完全なターミナルバイトストリーム——キャンバス準備、カーソル移動、終了処理 |
| `tools/tests/cli_corpus.sh` | 19 | 終了コードと stdout/stderr のルーティング |
| `tools/tests/*_behavior.py` | pty | 実ターミナルでのみ現れる挙動：リサイズ再起動、シグナル終了 |
| `cargo test` | goldens + traces | イージング/ジオメトリ/グラデーションの値とエンジン状態機械 |

`./bin/test` で全スイートを一括実行できる——そしてこれこそ**まさに** CI がやっていることのすべてだ。

### 癖を意図的に再現する。「修正」はしない

これはプロジェクト全体で最も直感に反し、かつ最も深い設計判断だ。出力をバイト単位で一致させるために、ttfx は Python オリジナルの一連の「バグ」を**意図的に保存**しなければならない：

- **Python の銀行家丸め**（round-half-even）：Rust の `f64::round` はゼロから遠い方に丸める。`.5` の境界で挙動が異なるため、再現が必須；
- **グラデーションは浮動小数点補間ではなく整数の床除法で構築**：`(end - start) // steps` ——負の増分では Python の `//` は床方向、Rust の `/` はゼロ方向に切り捨てる。再現が必須；
- **ベジェ曲線の弧長近似が最後のセグメントを落とす**：アップストリームの10サンプルループのバグによりパスの長さが系統的に短くなり、`max_steps` がそれに依存する——**バグごと再現する**；
- **ループするシーンは毎ティック自分が完了したと報告する**：エフェクトはこの癖に依存して正しく終了する。

これらの落とし穴はすべて `plan.md` の「忠実度トラップ」リスト（全20項目）に記録され、Python の順序不定イテレーションを固定化した箇所は `docs/ordering-inventory.md` に記録されている。

**受け入れられた意図的な差異は2つだけ**：乱数生成器（ttfx は xoshiro256++ を使用し、CPython のメルセンヌ・ツイスタとは互換性がない。`--seed` は ttfx 内部では再現可能だが Python とは相互互換性がない）、そして Python プラグインエフェクトの非対応（そもそも読み込むインタプリタがない）。

### 書き写すのであって、再想像しない（Transcription, not reimagination）

移植戦略そのものが一つの哲学だ：

> 各 Python ファイルは1つの Rust ファイルに対応し、関数は名前と内部構造を保ち、微妙な箇所のコメントはアップストリームの行番号を参照する。2つの調査ドキュメント（エンジンアーキテクチャ＋エフェクトカタログ）が地図であり、固定されたチェックアウトが原文である。

翻訳であって翻案ではない。行単位で対応させ、「ついでに改善」しない。その直接的な報酬はこうだ：**書き写しが忠実である限り、乱数呼び出しの順序は自然に一致する**。そしてそれがバイト単位比較の前提条件なのだ。「ここはもっと良く書ける」という考えは、どんなものでも等価性を壊す。

### 単一静的バイナリの哲学

なぜターミナルの玩具にここまでやるのか？「パイプラインの中」と「ライブラリとして」は、まったく別の世界だからだ：

```
Python TTE（ライブラリとして）:    ttfx（パイプライ玩具として）:
  python3 インタプリタ      →    1つのバイナリファイル
  pip install             →    ダウンロードして即実行
  ~65ms import            →    0.5ms 起動
  実行時依存の山           →    実行時依存ゼロ
```

> TTE は Python パッケージです。ライブラリとしては正しい選択ですが、プロンプトパイプラインで生きるシェルの玩具としては、インタプリタ、インストール手順、最初のフレームまでの約65msのimportを意味します。ttfx は依存ゼロのバイナリで、0.5ミリ秒で起動します。**この違いこそが、このプロジェクトが存在するすべての理由です。**

### 決定論的検証：「ピクセル単位の一致」を検証可能にする

エフェクトはランダムなので、「フレーム単位の diff」は構造的に失敗する。ttfx の解法は、ランダム性を**注入可能な共有依存関係**に変えることだ：

1. **決定論的 RNG shim**：同じ xoshiro256++ を Rust（`rng.rs`）と Python（`tools/parity/shim.py`）の両方に実装し、テスト時には両側が完全に同一の乱数列を引き出す——前提として、移植版が Python と同じ順序で RNG を呼ぶことが必要だが、それはまさに忠実な書き写しが保証することで、harness が検証していることでもある；
2. **決定論パッチ**：すべての順序不定イテレーション（set 走査、dict 順序依存）を同じ正準順序に固定する；
3. **クロックパッチ**：matrix と thunderstorm は実クロックを読む。テスト時には仮想クロック（フレームごとに `1/frame_rate` を進める）に置き換え、決定論化する。

この「共有乱数源＋順序の固定＋仮想クロック」の方法論は、決定論的テストを行うあらゆるプロジェクトが参考にすべきものだ。

## 技術アーキテクチャの詳細

### Arena + ID が Python のオブジェクトグラフを置き換える

Python TTE の内部は相互参照のオブジェクト網だ。文字 ⇄ アニメーション/モーション/イベントハンドラ、イベントが Scene/Path/Waypoint オブジェクトを保持し、文字同士の `links`/`neighbors`……Rust では借用チェッカーに苦しめられる。ttfx の答えは古典的な **arena アーキテクチャ**だ：

- すべての `EffectCharacter` は `Vec` arena に格納され、`CharacterId(u32)` でアドレス指定される；
- Scenes/Paths は文字ごとのマップに格納され、`SceneId`/`PathId` でアドレス指定される；
- `neighbors`/`links` は ID のみを保持する；
- イベントテーブルは純粋なデータに退化する：`HashMap<(Event, CallerId), Vec<(Action, Target)>>`。

**`Rc<RefCell>` はどこにもない。** これは Rust で生き残るための策であるだけでなく、状態をスナップショット可能かつ比較可能にする——テストにとっては嬉しい副産物だ。

### 同期イベントディスパッチ（遅延キューなし）

Python のセマンティクスは繊細だ。イベントコールバックは**発火地点で即座に実行**され、`Path.step` の*途中*で発火することもある。例えばセグメントイベントは座標計算の前に発火し、`SET_COORDINATE` アクションはその後、move 自身の代入によって上書きされる。もし Rust 版が「遅延キュー」（tick 後に一括 drain）を使えば、乱数が完全に同じでも異なるフレームが生成される。

結論：**遅延キューは持たない。** すべてのエンジン・ステップ関数は `EngineCtx` のメソッドとして ID 経由で動作し、ソースの正確な発火地点で `handle_event` をインライン呼び出しし、Python のコールスタックと同様に深さ優先で再帰する。「バイト単位の一致のために、アーキテクチャが最も単純な形に追い込まれた」完璧な事例だ。

### 1つの Terminal と決定論的順序

Python は実行ごとに**2つ**の Terminal を構築する（1つは tty を所有し、もう1つはシミュレーションを所有する）。ttfx はこれを1つの `Terminal` と薄い `TtyWriter`（キャンバス準備、フレームレート制御、カーソル復元）に統合し、RAII の `Drop` が Python の `@contextmanager` を置き換える。

**「順序は挙動である。」** Python は挙動に関わる複数の箇所で順序不定の集合をイテレートする——エンジン内部だけでなく、エフェクト内部でも（middleout と unstable は集合を直接イテレートする）。ttfx のルール：

- Python が dict の値/項目をイテレートする箇所では、Rust は `Vec` + id ルックアップ、または挿入順序を保つマップを使う；
- レンダリングは可視文字を `(layer, character_id)` でソートする；
- tick は `active_characters` のスナップショットを `CharacterId` 順にソートする。

### Effect トレイト + 静的レジストリ

```rust
pub trait Effect {
    fn build(&mut self, ctx: &mut EngineCtx);          // Python __init__/build()
    fn next_frame(&mut self, ctx: &mut EngineCtx) -> Option<String>;  // __next__
}
```

`effects/mod.rs` は静的レジストリ（name → clap `Command` + コンストラクタ）を保持し、Python の `pkgutil` 動的ディスカバリを置き換える。`--random-effect` / `--include-effects` / `--exclude-effects` / `--seed` はすべてアップストリームどおりに動作し、ランダムに選ばれたエフェクトが**純粋なデフォルト設定**で実行されるという癖も含む。

### Python の形をした RNG

`rng.rs` は xoshiro256++ を基盤に、TTE が行うすべての呼び出し（調査でカウント済み）に一致する Python の形をしたメソッド群を実装している：

| メソッド | 呼び出し数 | セマンティクス（正確に固定） |
|------|---------|-------------------|
| `randint(a, b)` | 61 | 閉区間の整数 |
| `choice(&[T])` | 54 | `seq[randbelow(len)]` |
| `shuffle` | 13 | Fisher-Yates、Python の順序 |
| `randrange` | 13 | 半開区間 |
| `uniform(a, b)` | 12 | `a + (b-a)*random()` |
| `random()` | 12 | [0, 1) |

RNG は `EngineCtx` 上に置かれ、明示的にスレッド化される——**グローバルなし**。これはまさに parity harness を可能にする理由だ。

### クロック注入

matrix（`time.time()` を読む）と thunderstorm（`time.monotonic()` を読む）は実クロックに直接依存する。実クロックはパリティを実行速度に依存させる：`frame_rate=0` のとき、より速い実装はより多くのフレームを生成し、期限までに多くの乱数引き出しを消費する。解法は `EngineCtx` が `Clock` トレイトを保持することだ。本番実装は実時間を読み、parity 実装は仮想的（フレームごとに固定 `1/frame_rate` を進める）で、Python shim は同じ仮想クロックで `time.time`/`time.monotonic` をモンキーパッチする。

### pycompat：忠実度トラップの収容施設

「自然な翻訳が Python から静かに逸脱する」箇所はすべて `pycompat.rs` に集中し、各ヘルパーには Python 生成のゴールデン値に固定されたテストがある：

- `round_half_even`：銀行家丸め。すべての座標量子化、`Path.max_steps`、アニメーションフレームインデックスに使用；
- `floor_div`：床除法。グラデーションのチャネル増分に使用；
- `trunc`：切り捨て。`shift_color_towards` に使用。

さらに `geometry.rs` に忠実に再現された「倍行」の慣例（セルの縦横比）、`hexterm.rs` の逐語的な256色最近傍一致テーブル、`input.rs` の「ミニターミナルエミュレータ」（CSI のみの ANSI パーサ）……こうした詳細の積み重ねが「バイト単位の一致」を信頼できるものにしている。

## パフォーマンスデータ：移植する価値の証明

200×50 のターミナルキャンバスで、ペーシングを無効にし（`sleep()` ではなくスループットを測定）、アニメーション全体を1回レンダリングする：

| 200×50 セル | フレーム数 | ttfx | Python TTE | ttfx fps |
|-------------|------|------|-----------|----------|
| slide | 375 | 76 ms | 2,203 ms | 4,930 |
| beams | 732 | 181 ms | 5,564 ms | 4,050 |
| rings | 1,566 | 521 ms | 10,439 ms | 3,004 |
| waves | 633 | 374 ms | 8,745 ms | 1,693 |
| 起動 | — | 0.5 ms | 64 ms | — |

**結論**：壁時計時間に制約されない35のエフェクトでは、中央値で **27.5倍**の高速化（範囲 17.1倍–47.4倍）。時間ゲートされた2つのエフェクトだけが例外だ——`matrix` と `thunderstorm` は実行時間の大半を、どの実装も短縮できない固定アニメーション時間に費やすため、1.9倍と1.3倍にとどまる。ttfx がそこで得るのは、より短い時間ではなく、その時間枠内での**はるかに高いフレームレート**だ。

興味深いのは、パフォーマンス哲学の抑制だ。plan.md には明確に「Performance target: not a goal beyond 'never the bottleneck'」（パフォーマンスは目標ではなく、ボトルネックにならないことだけが目標）と書かれている。O(n²) のアップストリームアルゴリズム（outside-in ソート、グループ化スキャン）は**忠実性のためにそのまま保持**されている。なぜならターミナルスケールでは全く問題にならないからだ。パフォーマンスは正しいアーキテクチャの自然な結果であり、それ自体が目標なのではない。

## 37エフェクトの全貌

すべてのエフェクトは同じ入力（Omarchy ロゴ）に作用し、すべてのフレームは Rust バイナリから出力され、Python オリジナルとバイト単位で同一だ：

| エフェクト | 一言説明 |
|------|-----------|
| **beams** | ビームがキャンバス上を走り、背後にある文字を照らす |
| **binarypath** | 各文字の2進表現がそのホーム座標へ移動する |
| **blackhole** | 文字がブラックホールに飲み込まれ、外側へ爆発する |
| **bouncyballs** | 文字が弾むボールとなってキャンバス上部から落下する |
| **bubbles** | 文字が泡となって浮かび、落ちて弾ける |
| **burn** | キャンバス内を縦に燃え上がる |
| **colorshift** | ターミナル上で色が移り変わるグラデーションを表示 |
| **crumble** | 文字が色を失い、塵となって崩れ、吸い上げられて再形成される |
| **decrypt** | 映画のような解読エフェクト |
| **errorcorrect** | 一部の文字が誤った位置から始まり、順番に修正される |
| **expand** | 1点からテキストが展開する |
| **fireworks** | 文字が花火のように打ち上がり爆発して、定位置に落ちる |
| **highlight** | 鏡面ハイライトがテキストを走る |
| **laseretch** | レーザーがターミナルに文字を刻む |
| **matrix** | マトリックス・デジタルレイン |
| **middleout** | キャンバス中央の1行/1列からテキストが外側へ展開する |
| **orbittingvolley** | 4つのランチャーがキャンバスを周回し、文字の斉射を内側へ放って中央からテキストを構築する |
| **overflow** | 入力テキストがランダム順で溢れスクロールし、やがて整列する |
| **pour** | 指定した方向から文字を定位置に注ぎ込む |
| **print** | プリントヘッドが1行ずつ印刷し、ラインフィードとキャリッジリターンを行う |
| **rain** | キャンバス上部から文字が雨のように降る |
| **randomsequence** | 入力データをランダムな順序で印刷する |
| **rings** | 文字が散開し、回転するリングを形成する |
| **scattered** | テキストがキャンバスに散らばり、定位置へ移動する |
| **slice** | 入力を半分に切り、反対方向からスライドさせて配置する |
| **slide** | ターミナルの外から文字をスライドインする |
| **smoke** | 煙がキャンバスを覆い、通過する文字に色を付ける |
| **spotlights** | スポットライトがテキスト領域を捜索し文字を照らし、中央に収束して拡大する |
| **spray** | 1点からさまざまな速度で文字を噴出する |
| **swarm** | 文字が群れを成してターミナルを動き回り、定位置に落ち着く |
| **sweep** | キャンバスをスイープして無色のテキストを現し、逆スイープで色を付ける |
| **synthgrid** | グリッドが文字で満たされ、最終テキストへ溶け込む |
| **thunderstorm** | ターミナルに雷雨を作り出す |
| **unstable** | 乱れた状態で生成し、キャンバス端へ爆発させ、正しいレイアウトに再構成する |
| **vhstape** | 文字の行が左右にグリッチし、古い VHS テープのように詳細が失われる |
| **waves** | 波がターミナルを横切り、文字を残していく |
| **wipe** | テキストを拭き取って文字を明らかにする |

各エフェクトには独自のオプションがある——`ttfx <effect> --help` で確認できる。README の一部の GIF はループを視聴可能にするため時間フェーズを短縮している（例：`matrix --rain-time 3`）。それ以外はすべてデフォルト設定だ。

## 詳細な入門チュートリアル

### 1. ビルド

ttfx のビルドは非常に簡単で、Rust ツールチェーンだけでよい：

```sh
# 通常のリリースビルド（システム libc/libm/libgcc にリンク）
cargo build --release

# 完全静的 musl ビルド（約3.3MB、動的依存ゼロ）
cargo build --release --target x86_64-unknown-linux-musl
```

完全なテストスイートを実行する：

```sh
./bin/test        # 全6スイート（python3 が必要）
```

parity スイートにはアップストリームのコピーが必要で、初回実行時に固定コミットで自動クローンされる（`./tools/parity/fetch_reference.sh` は手動でも実行可能）。アップストリームはリポジトリに**ベンダリングされない**——「それは彼らのコードだからだ」。

### 2. 基本的な使い方

```
<プロデューサー> | ttfx [ターミナルオプション] <エフェクト> [エフェクトオプション]
```

すぐに使える4つの例：

```sh
ls -la | ttfx decrypt            # ディレクトリリストが解読される
cat banner.txt | ttfx beams      # バナーがビームに照らされる
fortune | ttfx --random-effect   # おまかせ（--include-effects/--exclude-effects で絞り込み可能）
git log --oneline -10 | ttfx matrix   # git ログがデジタルレインに
```

### 3. ターミナルオプション vs エフェクトオプション

ここはハマりやすい罠だが、ルールは単純だ：

- **ターミナルオプションはエフェクト名の前**：キャンバスサイズとアンカー、色処理、フレームレート、テキスト折り返し；
- **エフェクトオプションはエフェクト名の後**：各エフェクト固有のパラメータ。

```sh
ttfx --help                 # 全37エフェクト + ターミナルオプション
ttfx <effect> --help        # 1つのエフェクトのオプション
ttfx --print-completion bash|zsh   # shell 補完を生成
```

**オプション名とデフォルト値は `tte` と完全に一致する**——だから既存の `tte` 呼び出し（例：`ls | tte decrypt --typing-speed 2`）は、バイナリ名を入れ替えるだけで動作する。これは CLI 互換性目標の直接的な果実だ。

### 4. ターミナルオプションの例

```sh
# キャンバスサイズを固定し、実ターミナル寸法を無視（スクリプト/テストで多用）
ttfx --canvas-width 80 --canvas-height 24 --ignore-terminal-dimensions beams

# フレームレートを調整
ttfx --frame-rate 30 slide

# キャンバスを再利用（スクロールで場所を確保しない）
ttfx --reuse-canvas decrypt
```

### 5. 動作の詳細

- **入力**：stdin（tty の場合は空）、`--input-file`；空/空白入力 → stdout に `NO INPUT.`、終了コード1；
- **終了コード**：0 成功；1 実行時エラー（入力なし、エフェクトなし、ファイルエラー——メッセージは *stdout* へ；サポート外の ANSI シーケンス——メッセージは *stderr* へ。そう、本当にこの非対称なのだ）；2 使用法エラー（引数解析、argparse/clap の慣例）；
- **シグナル**：SIGINT はフラグ/self-pipe で記録され、*制御をメインループに返す*。通常の巻き戻しで RAII の終了処理が実行される（`Drop` 単独ではシグナル時に発火しない）。終了コード1、メッセージなし（KeyboardInterrupt の処理と一致）；
- **デコード**：厳格な UTF-8、損失のあるデコードなし；
- **対象範囲**：Linux と macOS。バイト単位の parity スイートは Linux/glibc に固定されている——Apple の libm は少数の超越関数を最後の1 ulp だけ異なる丸め方をするが、量子化が実フレームでは隠すものの、ビット単位の比較では表面化するからだ。

## 忠実度検証システム：検証可能な「バイト単位の一致」

このシステムこそ、プロジェクトで最も学ぶ価値のある方法論だ。3つの層に要約できる：

**第1層：共有乱数源。** 移植可能な xoshiro256++ を Rust と Python shim のそれぞれに実装する。shim は TTE を import する前に `random.randint/choice/shuffle/randrange/uniform/random` をモンキーパッチする。両側はこれで完全に同一の乱数列を引き出す——前提は RNG 呼び出し順序の一致であり、それは忠実な書き写しが保証し、harness が検証していることだ。

**第2層：順序の固定。** shim は plan.md §4.3 の目録にあるすべての順序不定イテレーション箇所（`BaseEffectIterator.update`、レンダリングのレイヤータイ、middleout/unstable のエフェクトレベル集合イテレーション、`BreadthFirst` の links 集合走査）にも、Rust 版と同じ正準順序へのパッチを当てる。

**第3層：「改造した TTE で parity を証明する」ことへの対抗。** shim は参照実装を変更するため、プロジェクトは別途監査を設けている：すべての決定論的（乱数なし、クロックなし）エフェクトと M0 前処理マトリックス全体は、完全に未改造の固定 CPython 実行ともバイト比較される。shim のパッチは構造上、順序/RNG/クロックの置換に限定される（diff は小さく、レビューされ、harness とともにコミットされる）。

**フレームキャプチャ**：Python 側は `frame_rate=0` + 固定キャンバスでエフェクトをイテレートし、各フレーム文字列を長さプレフィックス付きダンプに書き込む。Rust 側は隠しフラグ `--parity-dump <seed>` で同じことを行う。differ が2つのストリームを比較し、最初の不一致フレーム/行/列をデコード済みエスケープビュー付きで報告する。

**テストマトリックス**：エフェクトごとに2–3種類の入力テキスト（ASCII 複数行、色付き ANSI 入力、不均一な短い入力）× デフォルト設定 × そのエフェクトのオプションを試す1–2の非デフォルト設定。さらに M0 前処理のオプションマトリックススイート。PTY バイトストリームテストはフレームダンプを迂回し、疑似ターミナル下での両実装の**完全な出力ストリーム**を直接比較する：キャンバス準備、DEC 保存/復元、終了処理——`--reuse-canvas`/`--no-eol`/`--no-restore-cursor` のバリエーションと SIGINT パスを含む。

万一あるエフェクトの RNG インターリーブ順序がどうしても一致させられない場合（現時点ではゼロ）、tier-2 のフォールバックがある：構造的フレーム比較＋並置録画に対する手動の目視承認。目標は**tier-2 エフェクトをゼロにすること**だ。

## まとめ：重要な視点

### 視点1：言語選定は「ライブラリとしての身分」ではなく「生活環境」で決まる

TTE は Python 製で、ライブラリとしては完全に正しい。しかし同じツールが shell パイプラインに住むとき、65ms の import とインタプリタ依存は明確な弱点になる。**同じソフトウェアでも、ホスト環境が違えば必要な配布形態は異なる。** ttfx は「アルゴリズム改善のために書き直した」のではなく、ホスト環境により適した運び手に替えただけで、27.5倍の中央値高速化と0.5msの起動を手に入れた。

### 視点2：「ピクセル単位の一致」は機械的に証明できる

ほとんどの移植プロジェクトは人間の目で受け入れられる。ttfx は、**ランダム性を注入依存に変え**（共有 PRNG）、**順序を正準形に固定し**（ソート/挿入順）、**時間を仮想化する**（仮想クロック）だけで、「バイト単位の一致」がスローガンから CI の354項目の自動チェックに変わることを証明した。決定論はテストの基盤である。

### 視点3：移植の最高の美徳は抑制である

アップストリームの20箇所の「バグ」に直面して、ttfx が選んだのは**修正ではなく再現**だ——修正は等価性を壊し、等価性こそがこのプロジェクトのすべての価値だからだ。さらに「許可された差異リスト」（§5 deliberate divergences）を変更の唯一の正当な範囲として扱い、「TTE を『改善』するというスコープクリープ」をリスクとして明記し、緩和策まで用意している。**移植において、忠実さは賢さより希少である。**

### 視点4：パフォーマンスは正しいアーキテクチャの結果であり、目標ではない

plan.md の「パフォーマンスは目標ではなく、ボトルネックにならないことだけが目標」という逆説的な記述は深い：arena アーキテクチャ、同期イベント、明示的な RNG スレッド化——これらはすべて**等価性**のために作られた設計であり、結果的に27.5倍の高速化をもたらした。O(n²) アルゴリズムはターミナルスケールでは問題ないため保持されている。**まず正しく、それから速く。速さは正しさの副産物である。**

### 視点5：単一バイナリは「パイプライン玩具」という生態的地位への敬意

`<producer> | ttfx <effect>` という使い方は、極めて低い起動コストと摩擦のないインストールを要求する。3.3MB の静的バイナリ、実行時依存ゼロ、`--print-completion` による補完生成——すべての決定が「パイプラインの中で生きる」という生態的地位に奉仕している。さらに配布問題も解決する：ダウンロードして即実行、Python バージョン地獄はない。

### 視点6：オープンソースエコシステムの作法

「エフェクトのアイデアはアップストリームへ」、「アップストリームのコードはベンダリングしない（それは彼らのコードだから）」、「MIT ライセンスで原作者の著作権を併記」、「NOTICE で全文の謝辞」——**移植プロジェクトがアップストリームとどう共存するか**に、ttfx は教科書的な答えを示した。

## 適用シーン分析

### ttfx が輝くシーン

✅ **強く推奨：**

- **Omarchy ユーザー**：プロジェクトは Omarchy のために作られており、すぐに使える；
- **シェルヘビーユーザー**：`git log`、`ls`、`fortune` の出力をゼロコストで視覚的なショーに変えられる；
- **デモと画面録画**：ターミナルデモに「映画的な感覚」が欲しい、37エフェクトをプラグ＆プレイで；
- **CI/スクリプト環境**：0.5ms 起動＋静的バイナリ、コンテナでも動作する；
- **決定論を重視する開発者**：`--seed` でエフェクトを再現可能にでき、テストやチュートリアルのスクリーンショットに最適；
- **Rust 学習者**：`plan.md` 自体が「parity 移植のやり方」に関する優れたエンジニアリング文書。

⚠️ **要検討：**

- **Python プラグインエフェクトが必要なユーザー**：ttfx は TTE のプラグイン機構をサポートしない（インタプリタがない）；
- **Python 版と `--seed` を相互利用したいユーザー**：乱数アルゴリズムが異なり、実装間で再現できない；
- **Linux/macOS 以外のプラットフォーム**：Windows は対象外。

### 意図的に解決しないこと

- TTE の代替ではない（ライブラリ用途は Python 版を使い続ける）；
- エフェクトの「改善」は追求しない（アイデアはアップストリームへ）；
- ワイド文字は処理しない（1コードポイント＝1セル、TTE と一致、既知の制限として文書化）。

## Omarchy との関わり

ttfx は当初**Omarchy のためだけ**に生まれた——plan.md には「Linux only, targeted exclusively at Omarchy (Arch)」と書かれている。両者は一対だ：Omarchy は固執的で美しくモダンな Linux デスクトップを提供し、ttfx はそのデスクトップに同じく固執的なターミナルショーを提供する。後に macOS まで対応範囲が広がったが、血統は明確だ。これは「特定のディストリビューションのために極限まで磨き上げる」という生態的地位から育ったツールであり、すべての人を喜ばせようとする汎用プロジェクトではない。「特定のユーザー群のために最高を尽くす」という姿勢は、Omarchy の哲学と同根である。

## 結び

ttfx は表向きターミナルの玩具だが、実体は**移植エンジニアリングの宣言**だ。3つの稀有なことを示している：

1. **真剣さとは何か**——「機能の一致」ではなく「バイトの一致」であり、それを機械的テストで証明すること；
2. **抑制とは何か**——アップストリームの20の癖を再現し、「改善」をリスクとして明記し、「移植は余計なことをしない」と明言すること；
3. **正しいパフォーマンス観とは何か**——等価性のために設計したアーキテクチャが結果的に27.5倍の高速化をもたらし、パフォーマンス自体は決して目標にされないこと。

ターミナルで働き、少しの視覚的魔法が好きで、あるいは「大規模プロジェクトを別の言語に移植する方法」を考えているなら、ttfx の README、plan.md、37個のエフェクトGIFは、あなたの午後の時間を費やす価値がある。実行した瞬間、`ls -la | ttfx decrypt` が教えてくれるだろう：**0.5ミリ秒の起動遅延が、すべてのフレームが待つ価値のあるショーを買ってくれるのだと。**
