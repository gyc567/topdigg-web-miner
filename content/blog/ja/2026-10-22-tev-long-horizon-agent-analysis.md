# Tev 徹底解説：「latent world」でデータを作り、密結合酬で長期ホライズンの agent を訓練する

> 論文：*Tev: Scaling Long-Horizon Agentic Environments with Dense Progress Rewards*
> 著者：Wenbo Hu、Shraman Pramanick、Krishna Kumar Singh、Nanyun Peng、Kai-Wei Chang、Yong Jae Lee（Adobe Research + UCLA）
> 論文ホームページ：https://arxiv.org/abs/2610.18868 ｜ HTML 版：https://arxiv.org/html/2610.18868v1
> プロジェクトホームページ：https://tev-agent.github.io/
> モデル重み：https://huggingface.co/gordonhu/Tev-27B ｜ https://huggingface.co/gordonhu/Tev-320B

## 序章：データに塞がれた領域

過去 2 年間、AI Agent の能力曲線はおおむね「タスクがどれだけ長いか」で決まっていた。

短いタスクと中長さのタスクがスイートゾーンだ。SWE-Smith には 5 万の環境があり、TMAX-15K には 1.46 万、CLI-Gym、SETA、Endless Terminals にも数千から数万がある。これらのデータセットは十分に大きく、訓練 pipeline も十分に成熟していて、モデルは確かに進歩している。

だがタスクの時間軸を「数時間から数日」——本物のオープンエンドな数学問題、自動化 ML 研究、本番インシデントの根本原因分析——まで引き延ばすと、領域全体が壁にぶつかる。

この壁は 2 つの欠落で構成されている。

**1 つ目の欠落はデータだ。** 長期ホライズンのタスクは、人手で書かれた評価セットとしてしか存在しない。Agents' Last Exam（ALE）や Terminal-Bench（TB）のインスタンスは、どれも専門家が数週間もの時間を投入する必要がある。ALE-CM の全セットは数十から数百問しかなく、しかも評価にしか使えず、訓練には使えない。結果として、極めて厄介な構造的矛盾が生まれる。

> agent の訓練 corpus は多いが、どれも短い。長いタスクは確かに存在するが、わずかな人手評価セットに過ぎない。

その中間の「大規模な長期ホライズン訓練データ」は、完全に空白だ。

**2 つ目の欠落は報酬だ。** データを作ろうとしても、長いタスクの報酬は疎だ。終端報酬はタスクが完結したときにしか現れず、長いタスクにおけるモデルの通過率はしばしば 5% 乃至それ以下にしかならない。つまり GRPO のようなグループ内相対の強化学習アルゴリズムでは、サンプルグループの大多数がすべて失敗し、アドバンテージがどこもゼロになり、勾配への寄与が完全にゼロになる。

論文はこの事実を非常に具体的な数字で示している。タスクの通過確率が $p=0.05$、1 グループあたり $G=8$ 本の rollout ならば、**サンプルの 66% が完全に無駄になる**。$p=0.01$ なら無駄率は **92%** に達する。しかもこれはまさに、訓練の初期段階で policy が最も弱く、シグナルがもっとも必要な局面だ。

Tev という論文が行っていることを一言でまとめると、こうなる。

> **「正解が既知の世界」から逆向きにタスクを生成し、その世界の ground truth で訓練の一歩一歩を採点する。**

以下では、その中核的な考え方、手法の構造、実験の結論、そして再現チュートリアルを完全に分解していく。

## 一、中核思想：latent world ファースト（Latent-World-First）

### 1.1 従来のパイプラインとの根本的な相違

現在の主流な合成データ pipeline はおおむね次のようなものだ。言語モデルにタスク説明を生成させ、続いて対応する入力ファイルを生成させ、さらに検証器やテストケースを生成させる。チェーンのどこにも「正解」は存在せず、ありそうなものしかない。

この合成方式には周知の 3 つの問題がある。

1. **検証器が信頼できない。** 生成されたテストケース自体が間違っている可能性がある。
2. **タスクと検証器が噛み合わないことがある。** これが最も致命的だ。論文はこれを**アーティファクトドリフト（artifact drift）**と呼ぶ。環境・タスク・検証器がそれぞれ別々に生成され、それぞれ単体では成立するのに、合わせたとき別々の問題を語っていることになる。
3. **中間状態がない。** 終局が白黒二分であるだけで、agent がどのステップを正解したのか、目標にどれくらい近いのかが分からない。

Tev のやり方はチェーン全体をひっくり返す。

**まず latent world $W$ を構築する。** それはタスク領域の完全かつ正しい状態である。たとえば小売倉庫の顧客・商品・取引記録、分散 checkpoint のテンソルシャードとトポロジ、Kubernetes クラスタのリソースマニフェストなど。

この世界の中では、**正解は最初から存在する。** 世界そのものが「すべてが正常なときの姿」だからだ。

そして、この世界を**レンダリング（render）**して agent が実際に目にする入力ファイルにし、さらに**制御された可逆の破損**を与えることで、agent が受け取る初期ワークスペース $s_0$ が得られる。

決定的に重要なのはここだ。**latent world $W$ は、タスクプロンプト・入力ファイル・検証器・進捗スコアラーの 4 つの共通ソースとして同時に機能する。**

論文はこの関係を簡潔な式に書き下している。

$$E=(x,\;s_{0},\;\operatorname{ver}_{W},\;\Phi_{W}),\tag{1}$$

環境 $E$ を構成する 4 つの要素は、すべて同じ $W$ の関数である。

- $x$：タスクプロンプト（agent が見ることのできる唯一の説明）
- $s_0$：入力ディレクトリツリー（agent の初期ワークスペース）
- $\operatorname{ver}_{W}$：厳格な合格/不合格の検証器。$W$ に基づいて agent の出力ファイルを確認する
- $\Phi_{W}$：進捗ポテンシャル。3 章で詳しく述べる

この単一のアンカーは、根本からアーティファクトドリフトを排除する。ground truth は構造的に正しい。レンダリングは往復還元（round-trip）が可能だ。破損は宣言済みかつ可逆だ。したがって **agent の初期ワークスペース $s_0$ は完全に $W$ を決定する**——正解は agent が実際に見ている内容から計算でき、ソルバーを実行する必要がない。

### 1.2 3 つの推論

この設計の美しいのは、ほかの案では追加の道具が必要になる 3 つの問題がいつのまに片付いてしまうことにある。

**推論一：難度は運任せではなく制御可能なノブである。**

$W$ が先に作られるので、「少し大きくする」は純粋なコード操作であり、モデルに何かを再生成させる必要がない。スケールティア（scale tier、デフォルトは unit / small / full）が $|W|$ を制御し、ワークフロー DAG の依存深度が「正しい出力を得るために何段階完了させる必要があるか」を制御する。二つのノブは互いに独立している。

**推論二：中間状態は無料である。**

すべての正しい中間状態は $W$ のレンダリングなので、採点のために人手のステップ注釈は不要であり、process reward model を訓練する必要もなく、言語モデルを審判に据える必要もない。$\Phi$ は決定的であり、再現可能であり、モデル呼び出しはゼロである。

**推論三：限界コストが非常に低い。**

一つの環境の生成（参照ソルバー 2 本の実行、隠しテストスイートの封印、進捗ポテンシャルのプレビューを含む）の中央値は **CPU 時間 30 秒**（90 パーセンタイル 82 秒）、**モデル呼び出しはゼロ**である。これは人手による experts の作業時間（1 問あたり数時間）とは桁が違う。そして一度限りの generator 実装コストは、そのすべてのシードとスケールティアに摊薄される。

さらに攻めた主張として、論文は Tev-Gym はさらに規模化可能であり、coding agent に generator を書かせれば、generator がシード横断・スケールティア横断で大量の新規環境を量産でき、**全過程で一切モデルを呼び出す必要がない**と指摘している。

## 二、手法の解剖：6 段階の環境合成パイプライン

2.1 節では環境合成を 6 段階に分解する。pipeline の**どの段階にも言語モデルは参加しない**。

### 段階 0：タスクソース

ALE-CM の 7 つの計算・数学サブドメイン（Tev-Gym の 7 分野に対応）それぞれについて、まず**実際のタスク仕様プール**を構築する。

| サブドメイン | 名称 | カバレッジ範囲 |
|------|------|----------|
| 9.1 | Software Engineering | 機能実装、デバッグ、リファクタリング、テスト記述 |
| 9.2 | Data & Analytics Engineering | ETL/ELT パイプライン、レコメンド順位付けシステム、特徴量エンジニアリング |
| 9.3 | AI Engineering, Safety & CS Research | モデル訓練評価 pipeline、論文再現、checkpoint 管理、アラインメント実験 |
| 9.4 | Mathematical & Operations Research | 組合せ最適化、ゲーム均衡、応用数学と数論、確率推定とフィルタリング |
| 9.5 | Cybersecurity & Digital Forensics | リバースエンジニアリング、マルウェア設定抽出、ネットワークパケット解析、インシデントフォレンジック |
| 9.6 | Infrastructure Engineering & Cloud Operations | K8s 移行と設定、本番インシデント根本原因分析、OS ハードニング、IaC |
| 9.7 | Quantum Computing | 量子回路の構築とシミュレーション、誤り訂正符号の解析、ノイズシミュレーション |

仕様プールの出所には、インターネットから掘り返した仕様、MLE-bench の 82 の Kaggle コンテスト、そして量子計算ドメイン（いかなる benchmark もカバーしていない）用の公開参考資料（MQT Bench 回路スイート、Qiskit Experiments マニュアル、TeNPy の DMRG サンプル）がある。

プールから仕様にランダムサンプリングし、**各仕様ごとに自分で generator を 1 本書く**。ここでの境界に注意したい。generator は仕様の構造と難易度を参考にするが、その prompt・入力・答え・採点テキストを**決して複製しない**。

3 層のフィルタがある。

- **実現可能性フィルタ**：「ground truth が構造的に既知」で「純粋な CPU 上でバッチ実行可能」な仕様だけを残す。オンラインサービス、音声動画、重いツールチェーン、GPU kernel、オープンエンドな「最適化せよ」系タスクに依存するものは除外する。
- **類似度ゲート**：新規 generator のコード・仕様・生成データを登録済みのすべての generator と比較し、近い重複を拒否する。
- **敵対レビュー**：前 2 関を通過した仕様を攻撃し、隠れた近道や短すぎるホライズン、偽装された出所を探す。

### 段階 1：世界の構築

各 generator は**シード付きプログラム**である。`(seed, scale_tier)` が与えられれば latent world $W$ を手続き的に生成し、次の 2 つを行う。

1. **不変条件を検証する**：一意な識別子、妥当な接続、有限な度量。
2. **不具合計画（defect plan）を抽出する**：$W$ のどのレコード・シャード・フィールドが、どの宣言済み演算子によって破損されるかを厳密に指定する。

この不具合計画は「シード由来」なので、同じ generator でも 2 つの異なるシードでは必ず証明可能な異なる世界を生成する。

### 段階 2：ワークフローグラフ

環境のワークフローを**有向非巡回グラフ（DAG）**にコンパイルし、明示的な依存、並列性、各段階の意味的作業量推定を持たせる。たとえば小売倉庫 ETL シナリオでは次のようになる。

```
profile-sources → reconcile-facts / normalize-dimensions → load-facts
                → aggregate-validate → package-sidecars
```

**この DAG は $W$ の規模に基づいてコードが生成するもので、過程にモデルは参加しない。**

DAG には 2 つの重要な性質がある。

- **クリティカルパス**（最長の依存段階連鎖）がタスクの**ホライズン**を定義する。
- **各段階が進捗ポテンシャルの骨格を構成する**（3 章）。

ここで論文が選んだ方法論的な選択に注意したい。**実際の rollout 長 $T$ ではなく DAG のクリティカルパスでホライズンを測る**。$T$ は agent の寄り道によって水増しされるからだ。DAG の深さは構造的で、制御可能な量である。

### 段階 3：アーティファクトのレンダリング

$W$ を環境が宣言する公開インターフェースへ射影し、目標のラインフォーマットへ実体化する。

- CSV / TSV パーティション
- JSON レコード
- SQLite データベース
- safetensors シャード
- シンボルを除いたバイナリファイル
- インフラストラクチャマニフェスト

**レンダリングは $W$ の純関数である。** そして先に進む前に、pipeline は**往復還元できることを表明する**——すなわちレンダリング後のファイルから $W$ を厳密に復元できること。

### 段階 4：制御された破損

段階 1 の不具合計画をレンダリング済みファイルに適用し、スキーマドリフト、記録の重複と欠落、カテゴリドリフト、シャードインデックスの並べ替え、期限切れキャッシュなどを注入する。

破損されたツリー $s_0$ が agent の受け取るタスクであり、変更されていない $W$ が ground truth である。

### 段階 5 と段階 6：公開仕様と隠しテストスイート

**段階 5** は公開契約 $x$ を出力する。入力ロール、必要な出力アーティファクトとそのスキーマ、順序付き要件、権威ある優先順位ルール、利用可能なツールチェーン。agent が見ることのできる**唯一の**説明である。

**段階 6** は agent の視野の外で隠しスイートを封印し、検証のために使われる。

- **メタモルフィック変換（metamorphic transform）**：意味を保つ書き換えであり、**スコアを変えてはならない**。
- **陳腐化出力のカウンタファクトゥアル（stale-output counterfactual）**：それらしく見えるが誤った状態であり、**必ず不合格**と判定しなければならない。

この層の役割は、検証器が狭すぎるのを防ぎ、また「陳腐だがそれらしく見える結果を提出してごまかす」ことを防ぐことにある。

### 2.2 カバレッジ・較正と 8 つの適格ゲート

**多様性。** 各環境は **19 本のカバレッジ軸**でラベル付けされる。サブドメイン、規模、4 本のホライズン軸、ワークフロー段階、ツール機能、アーティファクトロール、関係型、破損カテゴリなどである。

論文は特に行動的軸の価値を強調する。ある軸の値を変えると、agent が**何を直すべきか**（破損カテゴリ）、**どう直すか**（ワークフロー段階、ツール機能）、**どのファイルを通して直すか**（アーティファクトロール、関係型）が変わる。

**制御可能な難度。** 2 つの制御項目がある。スケールティア（unit / small / full）は操作のホライズンを伸ばし、DAG の依存深度と破損カテゴリ数が「何段階完了させればよいか、どの順序で完了させる必要があるか」を決める。

具体的な数字で体感すると、3 つのスケールティアすべてでインスタンス化された generator では、入力ツリーの中央値は **17 ファイル / 51 KB（unit）** から **20 ファイル / 168 KB（small）**、さらに **28 ファイル / 586 KB（full）** へと増え、**ワークフロー DAG は一切変わらない**。

**8 つの適格ゲート（admission gate）。** 合成環境は、benchmark とは無関係な 8 つのゲートをすべて通過して初めて採用される。各ゲートは生成時に自動検査され、それぞれに名前を持つ失敗カテゴリが対応する。

| ゲート | 強制要件 | 対象とする失敗カテゴリ |
|------|----------|--------------|
| 報酬の因果性 | 各報酬成分は、原因が変異されたらスコアが落ちなければならない | 誤った結果を報酬している |
| 耐 gaming 性 | すべての **14 個の gaming probe** がスコア 0 でなければならない | 検証器の穴、近道が受理されている |
| ロール独立性 | 参照ソルバー / 代替ソルバー / 厳格検証器 / 進捗スコアラーの**コード閉包が互いに交差しない** | ソルバーとスコアラーが偏りを共有している |
| ソルバー整合性 | 独立に書かれた 2 つのソルバーは、すべてのシードで完全に同一の出力ツリーを生成しなければならない | 検証器だけ通過し、仕様が未解決 |
| 進捗の有効性 | 部分的に正しい状態で $0<\Phi<1$、参照軌跡に沿って単調に 1 まで上昇、後退時は負の増分 | 無効なプロセスシグナル |
| メタモルフィックの不変性 | 保義の書き換えがスコアを変えない、陳腐化出力は失敗しなければならない | 検証器が狭い、陳腐化した状態が受理される |
| 6 シード多様性 | 少なくとも 6 つのシードが異なる世界 identity / 共通ツリー hash / タスク ID を生成しなければならない | 退化した環境、テンプレートの反復 |
| 公開契約の衛生 | prompt と共通ツリーに、いかなる私有権威・参考答案・検証器コードも現れてはならない | 答えの漏洩 |

**gaming probe について。** 論文は 14 種の gaming 戦略を列挙している。空出力、スキーマ上は合法だが最小の出力、入力のコピー、単一シードのハードコード、パストラバーサル、プライベート参照などである。どの一種も厳格検証器と進捗スコアラーのもとで同時にスコア 0 でなければならない。

**ロール独立性**については、この条項は単独で強調する価値がある。要求は次のとおり。

$$\operatorname{ver}_W(\pi^{\mathrm{ref}}(s_0))=\Phi_W(\pi^{\mathrm{ref}}(s_0))=1,\quad \pi^{\mathrm{ref}}(s_0)=\pi^{\mathrm{alt}}(s_0)$$

参照ソルバー $\pi^{\mathrm{ref}}$（スコアがちょうど 1.0）と**独立に書かれた**代替ソルバー $\pi^{\mathrm{alt}}$ は、すべてのシードで完全に同一の出力ツリーを生成しなければならない。**一度でも食い違えば、仕様が未解決とみなし、その環境は即座に棄却される。**

論文はこの設計の意味をこう説明している。ソルバー監査は検証器から独立している。どのソルバーも検証器のコードを import しないので、2 つのソルバーの一致は**採点器についてではなく仕様そのものの証拠**になる。

## 三、密結合酬：進捗ポテンシャルから PPRS へ

### 3.1 終端報酬がグループ内相対 RL を「餓死」させる理由

まず GRPO のグループ内相対アドバンテージを見る。

$$\hat{A}_i=\frac{R_i-\operatorname{mean}(R_{1:G})}{\operatorname{std}(R_{1:G})+\epsilon}\tag{2}$$

ここで $R_i=\mathds{1}[\tau_i\ \text{passes}]$ であり、rollout が提出し、かつ厳格検証器 $\operatorname{ver}_W$ が受理したときだけ 1 になる。

**中心的な問題**：1 グループの $G$ 本の rollout がすべて失敗した場合、$R_1=\cdots=R_G=0$ となり、すべての $\hat{A}_i=0$ になる。このタスクは勾配への寄与がゼロであり、その $G$ 本の rollout はすべて無効になる。

無駄になる割合は $(1-p)^G$ である。

| 通過率 $p$ | $G=8$ のときの無駄グループ割合 |
|------------|---------------------|
| 0.05 | 66% |
| 0.01 | 92% |

論文はさらに厄介な問題を指摘している。**1 グループ内で成功が 1 本しかなくても、それほど劇的には改善しない。** その 1 本の陽サンプルは $G-1$ 本の陰サンプルと向き合わなければならず、すべての陰サンプルが同じ負のアドバンテージを受け取るため、勾配は**「わずかに手不及」と「まったく進展なし」を区別できない**。

長期ホライズンのタスクでは、訓練していないオープンソースモデルの $p$ は十分の一以下、しばしばそれ以下である。つまり「全失敗グループを捨てる」や「再サンプリング」といった手法は、長いタスクでは batch の大半をそのまま捨てていることになる。

### 3.2 進捗ポテンシャル：latent world に由来する決定的な目盛り

すべての Tev-Gym 環境は**進捗契約**を提供する。ノード集合 $V$ であり、各ノードは出力ワークスペースの検査可能な一つ一つの状態で、段階 2 のワークフロー DAG から導出される。ノードは重み $w_v>0$（$\sum_v w_v=1$）と、前提依存集合 $\mathrm{pre}(v)$ を持つ。

部分スコアラー $c_v(s)\in[0,1]$ は、latent world に対して agent の現在のワークスペース $s$ を直接採点する。

**信用は前提依存でゲーティングされる**（prerequisite-gated）。$\tilde{c}_v(s)$ は、$v$ 自身と、そのすべての直接・間接の前提ノードにおける部分スコアの最小値である。

したがって進捗ポテンシャルは次のようになる。

$$\Phi(s)=\sum_{v\in V}w_v\,\tilde{c}_v(s)\in[0,1]\tag{3}$$

この設計がもたらす 3 つの性質は、ゲートによって強制されている。

- **アンカー付き（耐 gaming 性）**：未変更の共通ツリーとすべての gaming probe は厳密に $\Phi=0$ を得る。厳格検証器が受理したときは厳密に $\Phi=1$ を得る。
- **単調（進捗の有効性）**：ノードの完了とともに上昇し、完了済み作業が壊されると下降する。
- **独立（ロール独立性）**：スコアラーのコード閉包は検証器および参照ソルバーと**互いに交差せず**、一方の欠陥が他方に継承されることはない。そしてこの採点コードは**共通ツリーと共に公開されない**。

論文は「拡張可能な報酬設計」を強調する。latent world はタスク生成より前に定義されるので、すべての正しい中間状態を直接レンダリングして $c_v$ で評価できる。これは**精確で決定的な**進捗フィードバックを、**人手のステップラベル不要、報酬モデルの訓練不要、言語モデル審判不要**で提供する。

これが主流の手法との最も本質的な相違点である。

### 3.3 PPRS：進捗ポテンシャル報酬シェーピング

1 本の rollout のワークスペース状態を $s_0,\dots,s_T$ とし、$s_0$ は未変更の共通ツリーなので $\Phi(s_0)=0$ とする。

ポテンシャルベース報酬シェーピング（PBRS、Ng et al. 1999）に従うと、各ステップのシェーピング報酬はポテンシャルの変化量である。

$$r_t=\Phi(s_t)-\Phi(s_{t-1})$$

rollout の総報酬は次のようになる。

$$R(\tau)=\mathds{1}[\tau\ \text{passes}]+\lambda\sum_{t=1}^{T}r_t=\mathds{1}[\tau\ \text{passes}]+\lambda\,\Phi(s_T),\tag{4}$$

ここで **$\lambda=0.25$ であり、すべての実験ランでこの値が使われる**。

ここには 4 つの設計上の詳細があり、いずれも個別に取り出す価値がある。

**詳細一：PPRS は最適 policy 不変性を意図的に崩さない。**

標準的な PBRS は終端ポテンシャルをゼロにすることで最適 policy 不変性を保証する。PPRS は $\lambda\Phi(s_T)$ を残し、**最適化対象を意図的に変更する**。これは明確な、リスクをになう逸脱であり、論文は付録で「何が保持され、何が保持されなかったか」を率直に論じている。

**詳細二：提出は状態ではなくアクションである。**

$\Phi$ が採点するのはワークスペースであり、終局項が採点するのは policy が**提出した**ワークスペースである。ターン予算や token 予算を使い切ったが提出しなかった rollout は、**終局採点を受けない**。$\lambda\Phi(s_T)$ だけを得る。図 4 にある「完全なビルドはできたが未提出」の rollout が $\Phi=1$ に達しながら終端報酬が 0 だったのは、このためである。

**詳細三：報酬は最終状態にしか依存しない。**

$\Phi$ はワークスペースの関数にすぎないので、$R(\tau)$ は最終状態 $s_T$ を通じてしか rollout に依存しない。つまり**異なる経路を通り、ステップの順序も実装も異なるが最終ワークスペースが同じ 2 本の rollout は、完全に同じ報酬を得る**。これにより、報酬が「過程のスタイル」に意図せず偏ることを防げる。

**詳細四：終端報酬の順位はいまだ最上位にある。**

$\Phi\le 1$ なので、合格した rollout は $1+\lambda=1.25$ を得て、失敗したあらゆる rollout より厳密に高い。したがって「完成度と引き換えに部分的な進展を得る」ことで得をする rollout は存在しない。付録 B は、ランダム policy のもとで選好が反転しうる条件について境界を与えている。

**GRPO に代入すると、飢餓問題は修正される。**

グループ内で合格した rollout がないとき、報酬は $R_i=\lambda\Phi(s_T^{(i)})$ になる。異なる rollout が進んだ深さが異なれば、これらの報酬も異なり、グループ内アドバンテージは非ゼロになり、**進展の深さで rollout が順位付けされる**。

論文の図 4 はこの効果を直感的に示している。同じリポジトリ環境で、$G=8$ のグループに rollout を並べ、各ラウンドでリアルタイムに採点している。

- **終端報酬のみ（赤）**：すべての rollout がスコア 0。
- **漸進的報酬**：2 本は不完全なリポジトリを提出（丸印）、5 本は 65k token のコンテキストを使い切り（バツ印）、1 本は完全なリポジトリをビルドした。

グループ内の報酬にようやく差が出て、勾配にようやく学習する対象が生まれた。

### 3.4 既存の手法との比較

| 手法 | 進展の粒度 | 追加モデル | 主な欠点 |
|------|---------|------------|---------|
| 終端報酬（疎） | 終局 | 不要 | 全失敗グループのアドバンテージがゼロ、66%–92% を無駄にする |
| 同報酬のフィルタ / 近い難易度のタスク選択 / experts プレフィックスの付与 | 終局 | experts プレフィックスが必要 | 問題を回避しただけで、batch を捨てる |
| 学習式ジャッジ | 中間 | 判定器の訓練が必要 | 追加のバイアスと訓練コストが発生する |
| テスト通過率などのプロキシシグナル | 粗い | 不要 | 終局の結果しか捉えない |
| **PPRS（本文）** | **各ワークフロー段階** | **不要** | latent world が正しく構成されていることの保証が必要 |

### 4.5 アブレーション実験

アブレーションは 9B 設定で行われた。

**データ構築方法のアブレーション：**

| 方法 | World | DAG | 隠し ground truth | シグナル | S@1 | S@5 | P@1 | P@5 | GPU-h/step |
|------|-------|-----|---------|------|-----|-----|-----|-----|------------|
| Qwen3.5-9B (base) | – | – | – | RL なし | 0.25 | 0.33 | 0.06 | 0.06 | – |
| **Tev-9B (ours)** | ✓ | ✓ | ✓ | ΔΦ + 終端 | **0.29** | **0.40** | **0.07** | **0.11** | 9.0 |
| Public-view verifier | ✓ | ✓ | LLM | 終端 | 0.24 | 0.35 | 0.04 | 0.06 | 22.3 |
| Prompt-first | LLM | LLM | LLM | 終端 | 0.23 | 0.32 | 0.06 | 0.06 | 11.8 |
| Sparse (終端のみ) | ✓ | ✓ | ✓ | 終端 | 0.25 | 0.32 | 0.06 | 0.06 | 16.7 |
| PPRS, pooled norm. | ✓ | ✓ | ✓ | ΔΦ + 終端 | 0.28 | 0.35 | 0.06 | 0.06 | 10.9 |
| Direct reward (additive) | ✓ | ✓ | ✓ | Φ + 終端 | 0.29 | 0.35 | 0.06 | 0.06 | 9.7 |

3 つの読み取り値：

**読み取り一：「LLM 生成に退行する」2 つの変種はいずれも効かず、しかもより高いコスト付出了。**

- **Public-view verifier**：モデルに agent の視点から検証器を書かせる（隠し ground truth を捨てる）。**88% のサンプルグループが訓練中に破棄され**、GPU コストは 22.3 GPU-h/step で完全版の 2.5 倍になった。
- **Prompt-first**（標準的な self-instruct ベースライン）：pipeline 全体を「まず prompt、次に入力・検証器・解法」に差し替える。latent world も DAG もない。

2 変種の S@1 はそれぞれ 0.24 と 0.23 で、**どちらもベースラインの 0.25 を超えない**。一方完全版は 0.05–0.06（S@1）と 0.05（P@5）で先行している。

**読み取り二：密結合酬は「整形」されなければならず、単なる「加算」であってはならない。**

- **Sparse（終端のみ）**：S@1 = 0.25、GPU コストは最も高い（16.7）。
- **PPRS, pooled norm.**（各 rollout ごとに正規化）：S@1 = 0.28 で改善したが、P@1/P@5 は動かなかった。
- **Direct reward (additive)**（$\gamma=0$、$\Phi(s_t)$ をそのまま加算）：S@1 = 0.29 だが、P@1 は依然として 0.06。

完全な PPRS は疎な報酬に対して **S@1 が 0.04 向上**し、**P@1 を 0.06 から 0.07 へ、P@5 を 0.06 から 0.11 へ引き上げた唯一の方案**である。

論文が additive が駄目な理由について説明している部分が非常に重要だ。**直接加算は高いポテンシャルの状態を繰り返し報酬付け合うが、信号を前方へ伝播しない**ため、より多くの rollout が提出前にコンテキストウィンドウを使い切り、より長い軌跡になる。完全な PPRS は return-to-go（$\gamma=1$）で進展を前方のアクションへ信用を伝播させ、**ターンインデックスごとのアドバンテージ正規化**によって後段ターンの信用を保持している（後段の小さい return を rollout 全体の平均と比べて失うのを避けるため）。

**読み取り三：27B 規模では差がさらに広がる。**

論文は明示的に指摘している。27B では、整形された報酬なら完了まで訓練できるが、**終端報酬のみで生成されるグループはほぼすべてアドバンテージがゼロで、1 ステップも最適化器を進められない**。

### 4.6 定性的事例：k8s 決済 API の根本原因分析

論文は ALE-CM の Coding & System ドメインの具体的な例を挙げている（モデルは 1 回の kubectl 取得、Deployment/HPA の YAML、そしてクラッシュした pod のログから，逐語証拠の文字列とロールバックの結論を含む JSON の根本原因レポートを書き出した）。

| モデル | スコア | 軌跡のポイント |
|------|------|---------|
| Claude Fable 5 | **0.97** | t14 でプローブ原因 `initialDelaySeconds: 5` とキャッシュウォームアップ `duration=6.67s` を引用し、ロールバックは安全でないと判定。t18–21 で 41 箇所の引用を逐語検算してから提出 |
| GPT-6 Astra | 0.75 | t6 でクラスタ状態と YAML を一括ダンプ。t8 で OOM kill と HPA の競合を確認するが、**ロールバックの安全性は未検証**（ウォームアップ測定を引用していない）ため、この成分点は付かない |
| Qwen3.8-27B base | 0.70 | t12–16 でダッシュと列間隔をバイト単位で照合し、`build_rca.py` を書いて正確に抽出。結論は `safe_to_rollback: false` |
| **Tev-27B** | **0.97** | t20 でプローブ原因を引用し**計画中の引用を逐語確認**。t30 で**ロールバックの判断を再考**し、結論は `safe_to_rollback: true` |

この事例で最も面白いのは Tev-27B の t30 である。「'started flapping after a routine chart-value change'… roll back first」→ `safe_to_rollback: true`。**早期的自分の判断を覆した**のだ。密結合酬の下では agent は「ワークスペースの上で正しい状態に一歩ずつ近づく」という継続的なフィードバックを得るので、「立ち戻って修正する」という判断が可能になる。終端報酬のみで訓練されたモデルのように、一度迷子になってしまえば引き返せなくなるのではなく。

### 5.2 構成統計

|---------|-----------|-------------|--------------|------------|---------|-------------|----------|

その他の主要数字：

- **バランス**：正規化エントロピースコア $\mathrm{Balance}=\exp(H)/K$ は、3 つの能力カテゴリで **0.89**、7 つのドメインで **0.91**（1 が完全な均等）。
- **ホライズン**：環境のホライズンの中央値は 6 つのワークフロー段階（範囲 3–12）、8 つの進捗ノード、6 つの報酬成分、2 箇所の注入破損（範囲 1–7）。agent に公開される入力は中央値 12 ファイル（最大 501）、合計 51 KB（最大 6.1 MB）、23 種類のライン形式（32 種類の拡張子）、タスク prompt は中央値 583 token（Qwen tokenizer、最大 944）。
- **base model の挙動**：学習 harness の下で、訓練していない Qwen3.8-27B は各 rollout において中央値で 19 回のツール呼び出しと 30k token の生成を行い、**52% の rollout が提出前に 65,536 token のコンテキストを使い切っている**。
- **難易度**：単一 rollout のプローブでは、**完全に解けた環境はわずか 3.2%**（平均スコア 0.06）である。これは純粋な終端報酬が绝大部分の corpus でほぼゼロになることを意味しており、ちょうど 3 章が対象とした regime だ。
- **最先端モデルでの到達可能性**：92 個の環境のサブサンプルでは、Gemini 3.6 Flash が pass@1 29%、pass@8 40% に達した。しかしそのうち 26 個の環境（さらに small/full ティアで追加プローブした 52 個の環境）では、**1 つも解けず**、答えを提出した rollout は最大でも 29% に過ぎなかった。**Tev-Gym は相当な割合が現在の書き方のままでは最先端モデルの能力を超えている。**

### 5.3 デコンタミネーション

- Tev-Gym には**どの環境も**、ALE-CM、TB 3.0、TB 4.0、TB 2.1 のいずれのタスクとも 13-gram や 8-gram を共有していない。
- 評価タスクからデータセットへの最近傍 prompt の Jaccard 指数の中央値：TB 3.0/4.0 は **0.13**、ALE-CM は **0.22**、同じ benchmark 内のタスク同士を比較した際の 0.24–0.25 および 0.28 と比較して。
- より根本的なのは**構造的デコンタミネーション**である。latent world はシード付きの程序的に生成されるので、任意の 2 環境の間で共通ツリーは異なり、いずれも評価インスタンスとも共有しない。

### ステップ 1：generator を書く（段階 1–4 の核心）

generator とは**シード付きの純関数** `make_world(seed, scale_tier) -> World` である。満たすべき条件は次のとおり。

```python
import random, hashlib

def make_world(seed: int, tier: str = "unit"):
    """生成潜在世界 W。必须是 seed 的纯函数，无副作用，无模型调用。"""
    rng = random.Random(seed)

    # 规模档位决定 |W|
    n_customers = {"unit": 30, "small": 240, "full": 480}[tier]
    n_tx_per_month = {"unit": 48, "small": 480, "full": 960}[tier]

    world = {
        "customers": [
            {"id": f"C{i:05d}", "name": f"cust_{i}"}
            for i in range(n_customers)
        ],
        "products": [
            {"id": f"P{i:05d}", "sku": f"sku-{i:04d}", "price": round(rng.uniform(1, 500), 2)}
            for i in range(n_tx_per_month)
        ],
        "transactions": [],
    }

    # ---- 不变量校验（阶段 1）----
    assert len({c["id"] for c in world["customers"]}) == n_customers, "ID 必须唯一"
    assert all(t["qty"] > 0 for t in world["transactions"]), "度量必须有限"

    # ---- 缺陷计划（阶段 1）：精确指明要损坏什么 ----
    defect_plan = {
        "operators": ["duplicate_records", "missing_records", "schema_drift"],
        "targets": rng.sample(range(len(world["transactions"])), k=2),
    }
    world["_defect_plan"] = defect_plan
    return world
```

**3 つの硬い規律：**

1. **純関数であること。** 時刻を読まない、環境変数を読まない、ネットワークを呼ばない、モデルを呼ばない。同じ `(seed, tier)` は完全に同じ世界を生成しなければならない。
2. **不具合計画は世界に書き込む。** 破壊はレンダリングの後に起こり、計画はシード由来である——つまり「何が破壊されたか」自体が世界の一部であり、独立に再構築できる。
3. **検証器のコードを import しない。** これはロール独立性ゲート”的要求であり、後述の採点段階でコード閉包が互いに交差しないことが検査される。

### ステップ 2：ワークフロー DAG を定義する（段階 2）

DAG はホライズンを決め、進捗ポテンシャルの骨格も決める。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Stage:
    name: str
    depends_on: tuple[str, ...]      # 显式依赖
    weight: float                     # 进度节点权重
    parallel_with: tuple[str, ...] = ()  # 允许并行

WORKFLOW = (
    Stage("profile-sources",   (),                    0.15),
    Stage("reconcile-facts",   ("profile-sources",),   0.25),
    Stage("normalize-dimensions", ("profile-sources",), 0.15),
    Stage("load-facts",        ("reconcile-facts", "normalize-dimensions"), 0.20),
    Stage("aggregate-validate",("load-facts",),        0.15),
    Stage("package-sidecars",  ("aggregate-validate",), 0.10),
)

def critical_path():
    """最长依赖链 = 任务跨度。这是结构性的度量，不受 agent 绕路影响。"""
    memo = {}
    def depth(s):
        if s.name in memo: return memo[s.name]
        memo[s.name] = 1 + max([depth(d) for d in s.depends_on], default=0)
        return memo[s.name]
    return max(depth(s) for s in WORKFLOW)
```

重みの和は 1 に正規化しなければならない（式 (3) の $\sum_v w_v=1$ に対応する）。

### ステップ 5：厳格な検証器と進捗スコアラーを書く（段階 5–6）

```python
# verifier.py —— 严格通过/不通过，只看最终产出
def verify(world, output_dir) -> bool:
    """对照 W 检查 agent 的输出文件。严格、确定性、无副作用。"""
    for path, checker in world["_verifiers"]:
        if not checker(world, os.path.join(output_dir, path)):
            return False
    return True

# progress.py —— 进度打分器，独立代码闭包
def partial_score(world, output_dir) -> dict:
    """对每个进度节点给出 [0,1] 的部分分数。"""
    return {v: checker(world, output_dir) for v, checker in world["_partial_scorers"].items()}

def progress_potential(world, output_dir) -> float:
    """式 (3)：前置依赖门控的加权求和。"""
    scores = partial_score(world, output_dir)
    gated = {}
    for v, s in scores.items():
        pre = world["_prereqs"][v]
        gated[v] = min([scores[v]] + [gated[p] for p in pre]) if pre else scores[v]
    return sum(world["_weights"][v] * gated[v] for v in scores)
```

前提依存ゲーティングの実装上の要点は、**必ずトポロジカル順に計算する**ことである。$\tilde{c}_v$ は前提ノードの $\tilde{c}$ に依存し、元のスコアだけでは足りないからである。

### ステップ 7：PPRS 報酬を実装する

```python
import numpy as np

LAMBDA = 0.25  # 论文中所有运行均为 0.25

def rollout_reward(workspace_states, passed: bool) -> float:
    """
    式 (4)：R(τ) = 1[passes] + λ * Φ(s_T)

    注意 telescoping：Σ ΔΦ = Φ(s_T) - Φ(s_0) = Φ(s_T)，因为 Φ(s_0)=0。
    """
    phi_final = workspace_states[-1]
    return (1.0 if passed else 0.0) + LAMBDA * phi_final

def grpo_advantages(rewards):
    """式 (2)：组内相对优势值。"""
    r = np.asarray(rewards)
    return (r - r.mean()) / (r.std() + 1e-6)
```

**学習における 3 つの設定上の要点**（論文が明示しているもので、もっとも間違えやすい部分である）：

1. **ターンインデックスごとのアドバンテージ正規化**（per turn）。rollout 全体での正規化（pooled）ではない。前者は後段ターンの信用を保持する。
2. **$\gamma=1$ の return-to-go**。進展を前段のアクションへ信用として伝播させる。
3. **$\lambda=0.25$**。

反面の実装と比べてみよう。

```python
# ❌ 反面：直接相加的奖励（论文消融里 S@1=0.29 但 P@1=0.06）
def bad_reward(workspace_states, passed):
    return (1.0 if passed else 0.0) + LAMBDA * sum(workspace_states)

# ❌ 反面：仅终止奖励（论文消融里 S@1=0.25，27B 上一个完整优化器 step 都走不出去）
def bad_reward2(workspace_states, passed):
    return 1.0 if passed else 0.0
```

**この 2 つの方法は S@1 上は見かけ上ほぼ同じだが、完全解出率 P@1 はベースライン水準のまま動かない。** 論文のアブレーション表はこの差によって「整形」と「加算」の実質的な違いを明らかにしている。

## 七、帰納的なまとめ：論文の主な主張と結論

### 主張一：長期ホライズンの agent のボトルネックはアルゴリズムではなくデータと報酬である

論文の枠組み全体は 1 つの観察の上に立っている。**オープンソースモデルの長期ホライズンタスクにおける失敗は、最適化アルゴリズムが劣っているからではなく、訓練データも実行可能な recipe も存在しないからである。**

2 つのボトルネックは絡み合っている。長いタスクは生成も検証も難しく、報酬は極めて疎だ。分けて解いてもだめだ——データだけを作れば疎な報酬の下で訓練が動かないモデルになり、密結合酬だけを設計して「正解が既知の世界」がなければ、ポテンシャルのスコア自体が信頼できない。

### 主張二：正しい合成の方向は「答えから問題を逆算する」にある

この主張は論文の具体的な実装よりも一般的なものだ。

> 「真の答えのない状態で言語モデルにタスク・入力・チェッカーを生成させる pipeline と異なり、私たちの latent world は正確な答え帳として働き、信頼できる検証を可能にする。」

論文はこれを、既知の解から逆算してタスクを作る成熟したファミリーに分類する。デノイジング、制御された誤り注入、コードミューテーション、環境の巻き戻し、指示の逆翻訳、手続き的なパズル生成。しかしそれらの違いはこうだ。**これらの手法が壊すのは単一アーティファクトの ground truth だが、Tev が壊すのは latent world 全体の 1 つのレンダリングである。**

この違いは原子性における違いを生む。タスク・検証器・進捗シグナルはすべて同じ世界の関数であり、互いに漂うことがありえない。

### 主張三：進捗報酬は「学習する」のではなく「証明できる」べきである

密結合酬の主流の手法は、process reward model を訓練するか、学習式ジャッジを使うか、言語モデルを審判に据えるかのいずれかである。いずれも追加モデル・追加バイアス・追加訓練コストをもたらす。

Tev のやり方はこうだ。**latent world はタスク生成より前に定義されるので、すべての正しい中間状態を直接レンダリングして決定的に評価できる。** critic は不要、judge は不要、人手のステップラベルも不要。

これは全文の方法論としてもっとも価値のある 1 行である。**「報酬はどこから来るか」という問題を、「報酬モデルをどう学習するか」から「ground truth が既知であることをどう保証するか」に変える。**

### 主張四：報酬シェーピングは「最適 policy 不変性」を意図的に崩さなければならない

標準的な PBRS は終端ポテンシャルをゼロにして最適 policy 不変性を保証する。PPRS は $\lambda\Phi(s_T)$ を残し、**最適化対象を意図的に変更する**。

これは明確なリスクの引き受けである。論文はそれを回避せず、付録で「何が保持され、何が保持されなかったか」を論じ、ランダム policy のもとで選好が反転しうる条件について境界を与えている。

**多くの論文はこの種の逸脱を隠したり存在しないふりをしたりする。Tev はそれを表に置いてみせる。** これは研究姿勢の問題である。

### 主張五：この領域ではデータ品質とデータ規模が逆向きになる

表 1 の読み方が反直感的だ。

| | SWE-Smith | Tev-Gym |
|---|---|---|
| 規模 | 50.1k | 1,170 |
| ドメイン数 | 1 | 7 |
| Agent 時間の中央値 | 2.0 min | 12.4 min |
| 漸進的報酬 | ✗ | ✓ |
| P@1 | 47% | 29% |

**Tev-Gym は既存 corpus の 1/40 の大きさしかなく、それでも最強の結果を支えている。** 長期ホライズンのタスクでは「環境の個数」はとっくにボトルネックではなく、**「その環境に検証可能な中間状態があるか」のほうが問題だ**からだ。

——これが 1,170 の環境で GPT-6 Astra に並べるモデルを訓練でき、5 万の環境では訓練できなかった理由も説明している。

### 主張六：アブレーション実験が与える操作可能な教訓

そのまま持ち出せる結論が 3 つある。

1. **モデル自身に検証器を書かせると、88% のグループが破棄され、2.5 倍の計算量、かつ劣化した性能になる。** LLM でチェッカーを生成して省いた時間は、訓練段階ではもっと高い形で返ってくる。
2. **密結合酬では「密度」よりも「形状」のほうが重要である。** 直接加算の $\Phi(s_t)$ は S@1 上は印象よく見える（0.29）が、P@1 はまったく動かない（0.06）——高いポテンシャルの状態を繰り返し報酬付け合うが信用を伝播しないため、agent はコンテキストを使い切るまでぐるぐる回ってしまう。
3. **規模が大きいほど、純粋な終端報酬の崩壊は彻底的である。** 27B では終端報酬のみで生成されたグループはほぼすべてアドバンテージがゼロで、**1 ステップも最適化器を進められない**。

### 結論

論文自身の結論段落はやくまで抑制的である。

> 我々は latent world ファーストのアプローチを提案し、検証可能な長期ホライズンの agent 訓練を拡張する。各タスクは既知の正しい latent world から逆向きに構築され、互いに紐づくファイルにレンダリングされ、制御された破損によって変更され、精确な検証と密結合酬の進捗報酬のために再利用される。我々はこの手法を Tev-Gym として実装し——7 分野にまたがる 1,170 の検証済み環境——ALE-CM 上の学習が 9B と 27B の両方のオープンソースモデルを改善し、その利得がホライズンの異なる Terminal-Bench タスクおよび 320B の base model にも転移できることを示した。

同時に明示的に認める局限もある。

> 現在の研究の一つの限界は、合成された terminal 環境に焦点を当てていること、そして最も困難な benchmark 上でもなお最先端の agent との間に差が残っていることである。新しくサポートするワークフローには追加の環境コンポーネントの記述と検証が必要となる。

## 八、設計哲学の解剖

論文の採った方針を哲学的な水準まで抽象すると、互いに支え合う 5 つの原則が見える。

### 原則一：単一アンカー原則（Single Anchor）

1 つの環境には ground truth のソースは 1 つだけある。すべての産物——タスク、入力、検証器、進捗シグナル——はその関数である。

**これに抗うのは「分散生成」のエントロピーである。** 4 つのコンポーネントが別々のプロセスで生成されると、その結合分布は漂う。共通のアンカーがあれば、漂流は構造的に起こりえない。

**推論**：「タスクを生成する」ステップと「答えを生成する」ステップの間でアラインメント作業をしていると気づいたら、順序を逆にすべきだ。

### 原則二：ground truth はタスクに先んじる（Ground Truth Precedes Task）

タスクは「生成」されるものではなく、「導出される」ものである。

agent 時代の前ならこの言葉は何の変哲もない。LLM がコンテンツを生成する時代になると、これは急峻になる。**あなたは、モデル自身が答えを知らない場所で、答えを必要とする問題を出題させるよう頼んでいる。** Tev の論文全体は、いかなる意味でもこの企てへの系統的な懐疑である。

### 原則三：決定性は学習に優る（Determinism Over Learning）

ある量が決定的に計算できるなら、その量を推定するモデルを訓練するな。

| ニーズ | 一般的な方法 | Tev の方法 |
|------|---------|---------|
| 各ステップの正誤を判定 | PRM / 学習式ジャッジを訓練 | 正しい中間状態をレンダリングして決定的に採点 |
| 最終的な正誤を判定 | テストケースを生成 | $W$ と照合して厳格に検証 |
| 難易度を判定 | モデルに試し走らせて採点 | 生成時に定義された構造量 |

**代償は、まず世界を正しく作らなければならないことだ。** だからこそ Tev は 6 シード多様性、双ソルバー整合性、ロール独立性監査に大量の工数を 투자する——**ポテンシャルが信頼できなければ、訓練チェーン全体が毒化されるからである。**

### 原則四：ゲートは規模に先んじる（Gates Before Scale）

不合格な環境は生成時にブロックし、下流の RL によるソフトフィルタリングに頼らない。

論文はこの選択を明示的に対比している。「検証をスキップし、下流の RL に解けないタスクをソフトフィルタさせる pipeline と不同的是、私たちは生成時にチェックを置く。密結合酬の進捗シグナルは因果性が強く gaming 耐性がある場合にのみ有用だからである。」

**この一文は全文でもっとも実用的な工学上の助言である。** データ生成側でサボった分は、訓練側で計算量の浪費とシグナルの汚染として返ってくる——論文のアブレーションにおける Public-view verifier の 22.3 GPU-h/step がその請求書だ。

### 原則五：過程そのものが産物（Process as Artifact）

進捗ポテンシャルは、**ノード集合 + 前提依存 + 重み**という明示的なデータ構造として定義され、黒箱スコアではない。

得られる利点は可解釈性だけではない。

- DAG のクリティカルパスがそのままホライズンの構造的尺度になる
- 前提依存ゲーティングが「上流がダメなら下流は点にならない」を自然に実現する
- アブレーション実験で「データが変えた」のか「報酬が変えた」のかを厳密に分離できる

**報酬が構造として明示的にモデル化されて初めて、監査でき、追及でき、分解できる。**

### もう 1 本の隠れた哲学的系譜：「コンテンツ生成」から「世界生成」へ

——これこそがこの論文の最も深い階層であると私は思う。

過去 2 年間、AI コンテンツ生成の範式はこうだった。**prompt を渡して、出力をサンプルする。** すべての品質問題——ハルシネーション、一貫性の欠如、検証不能——は、根源的な制約から生まれている。**モデルから独立した知識のソースが存在しない**ことだ。

Tev の採り方は範式を反転させる。**完全で正しい世界を渡して、すべての産物を導出する。** モデルは「知識のソース」から「問題の解者」へと退居する。

この枠組みの中では、

- ハルシネーションの問題は「レンダリングの往復還元が失敗する」という工学の問題になる
- 検証器の信頼性の問題は「コード閉包が交差するか」という静的検査の問題になる
- 報酬の疎性の問題は「ポテンシャル関数が単調か」という形式的な性質になる
- 難易度制御の問題は「スケールティア × 依存深度」という 2 つのノブになる

**もともと曖昧だった AI 問題の数々が、それぞれ証明可能・テスト可能・監査可能な工学の問題へと変換されていく。** これが「latent world ファースト」という手法の本当に価値がある部分だ——単なるより効率的なデータ生成の手ではなく、AI システムの問題を工学化する思考様式なのだ。

Tev-Gym がわずか 1,170 の環境で勝てる理由もこれで説明できる。**問題が正しく形式化されれば、データという「量」の次元の重要性は急激に低下するからである。**

## 九、限界、批判と今後の見どころ

以下は私の評価であり、論文の自己陳述ではない。

### 論文自身が認める局限

1. **合成された terminal 環境に焦点を当てている。** GUI、実際のオンラインサービス、多 agent 協業といったシナリオはカバーされていない。
2. **最も困難な benchmark 上でもなお差が残る。** TB 4.0-CM における Tev-27B の 0.10 は、Claude Opus 5 の 0.52 と比べれば桁違いに小さい。
3. **新しいワークフローのサポートには追加の投資が要る。** 分野を 1 つ追加するたびに generator・検証器・スコアラーを書き、8 つのゲートを通す必要がある。これは実際の人件費であり、論文はこれを量化していない。
4. **コードとデータは未公開。** プロジェクトホームページの Code と Data のボタンは今度も "soon" のままで、入手できるのはモデルの重みだけである。**つまり現時点ではデータセットの品質を独立に検証できず、直接再利用することもできない。**

### 私の追加の批判

**批判一：$s_0$ は本当に完全に $W$ を決定するのか？**

論文の論証はこうだ。レンダリングが往復還元可能である + 破損が宣言済みかつ可逆である ⟹ $s_0$ は完全に $W$ を決定する。しかしこの導出は「破損演算子の集合が閉じており、各演算子の逆が計算可能である」という前提に依存している。ある演算子（たとえば「カテゴリドリフト」）が特定的数据上で不可逆であるならば（異なる 2 つの元値が同じドリフト値へ写像される）、厳密には $s_0$ は $W$ ではなく $W$ の**同値類**しか決定できない。

論文は隠しスイートの「メタモルフィックの変換」と「カウンタファクトゥアル」がまさにこの種の曖昧さを扱うためにあると述べているが、公開ツリー層の決定性の議論には依然として境界があると思う。

**批判二：0.03 の base P@1 は低すぎるのではないか？**

Tev-Gym 上で未学習の Qwen3.8-27B は 3.2% の環境しか完全解けず、平均スコアは 0.06 である。これは「長期ホライズンのタスクは難しい」という現実に合致する。しかし同時に次を意味する。**訓練シグナルの大半は「本当に正解した」からではなく $\Phi$ から来ている。** モデルは「タスク自体の正しい解法」ではなく「ポテンシャル関数を登る経路」を最適化している可能性がある。

論文のメタモルフィックの不変性ゲートと陳腐化出力のカウンタファクトゥアルゲートはこの問題の一部を緩和している（それらは直接に「近道」に対峙する）。しかし「ポテンシャル関数の最短登攀経路に沿って最適化する」ことと「タスクを本当に理解する」ことのあいだの距離は、論文は直接測っていない。

**批判三：TB への一般化の結果は慎重に読むべきである。**

TB 3.0/4.0 の "CM" サブセットは、**各タスクが計算・数学ドメインに属するかを Claude で判定**して構成された。ただし部分集合と全体集合の高い相関（r=0.96 / r=0.97）は検証されているものの、これは部分集合の区分そのものに最先端モデルの判断が含まれることを意味する。Claude で作られた部分集合で Claude と比較対象のモデルを評価するこの循環性は致命的ではないが、読者が知っておくべき事実である。

**批判四：「最先端モデルに並んだ」という P@5 の表現は限定されるべきである。**

Tev-27B の P@5 = 0.28 は GPT-6 Astra および Claude Opus 5 の 0.28 と並ぶというきわめて目を引く数字だ。しかし：

- Tev-27B は Vanillux2 harness を使い、最先端モデルは Codex / Claude Code を使う。**harness 自体が agent の挙動に巨大な影響を与える**
- 最先端モデルは ALE-CM 上の S@5 が明らかに高い（0.58 対 Tev-27B の 0.54。かつ GPT-6 Astra は S@5/S@1 ともに 0.58）。これは**最先端モデルが「すでに正解したタスクをより彻底的にやり切る」**ことを示している
- P@5 = S@5 = 0.28 という「飽和」の形態と、Tev-27B の 0.16/0.28（S@1/P@5）の形態は、意味が異なる

**私の判断：これは実在し、再現可能な方向における顕著な進歩だが、「最先端モデルに並んだ」という表現は harness をまたいだ比較では割り引くべきである。**

**批判五：スケーラビリティのボトルネックは「generator を書くこと」に移る。**

論文は Tev-Gym は coding agent に generator を書かせることでさらに規模化でき、**モデル呼び出しは再び不要になる**と指摘している。しかし generator コード自体が 8 つのゲートを通らなければならず、双ソルバー整合性は「独立に書かれた 2 つのソルバーが一致すること」を要求する——**generator を 1 つ書くのは簡単だが、そのために独立した 2 つのソルバーを書いて一致させるのは、難易度がはるかに高い。**

規模が 1,170 から 10,000 へ押し上げられるとき、generator を人手審査する生産性が真のボトルネックになる。論文はこの点について触れていない。

### 后续看点

1. **コードとデータがいつ公開されるか**——これが最も重要な観察の窓になる。公開されれば、コミュニティは 1,170 環境の実際の品質を独立に検証できる。
2. **非 terminal 環境へ拡張できるか**（ブラウザ、GUI、実際のツールチェーン）——これが「latent world ファースト」が terminal タスク専用のコツなのか、それとも汎用パラダイムなのかを決める。
3. **コスト曲線**——新しい分野 1 つに何時間の人手が要るか。この数字が手法のスケール上限を決める。
4. **$\Phi$ と実際の解题能力の相関**——「ポテンシャルの高い軌跡は実際にタスクを解けやすいのか」を直接測定できれば、上の批判二に答えが出せる。
5. **Tev-320B の完全な評価**——論文は 320B バージョンを TB の部分集合でしか評価しておらず、ALE-CM 上の性能は未知である。

## 十、一言でまとめると

> **モデル自身に出題させたら、答えまで一緒に間違えてしまう。**
>
> Tev のやり方は順序を逆にする。先に完全で正しい世界を用意し、そこからタスク・入力・検証器・進捗の目盛りを導出する。答えが構造的に既知だから、検証は精確で、中間状態は無料になり、訓練シグナルは 1 歩ごとに密結合酬まで密にできる。
>
> 1,170 の環境、27B のオープンソースモデル 1 つで、Agents' Last Exam の計算・数学スライスにおいて Pass@5 が 0.28 に到達し、GPT-6 Astra と Claude Opus 5 に並んだ。同時に一度も見たことのない Terminal-Bench 4.0 のサブセットへゼロショットで転移し、P@1 が 150% 向上した。
>
> この領域の主要矛盾は、いつのまにか量的ではなく質の問題だった。**「答えはどこから来るのか」こそが鍵だ。**
