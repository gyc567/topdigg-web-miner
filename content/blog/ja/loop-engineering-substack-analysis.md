# Loop Engineering 徹底解説（Cobus Greyling 原著）：エージェントをプロンプトするのをやめ——仕事を探し、割り当て、検証するループを設計せよ

> 核心思想：**コーディングエージェントを逐ターンでプロンプトする立場から、システム（the loop）を設計する立場へのシフト。** Cobus Greyling は原著（2026-06-09）でこう定義する：あなたが設計したループが**仕事を発見し、エージェント（多くの場合はサブエージェント）にタスクを渡し、結果を検証し、状態を永続化し、次のアクションを決める**——スケジュールで動くか、ゴール達成まで。最も鋭い言葉は Anthropic の Claude Code 責任者 Boris Cherny：「もう Claude にはプロンプトしない。Claude にプロンプトして次に何をすべきか決めるループが動いている。**私の仕事はループを書くことだ。**」あなたが書くのはより大きなプロンプトではなく、エージェントを歯車にしたシステムそのものなのだ。

---

## 1. プロジェクト概要

### 1.1 これは何か？

本稿が解析するのは、**Cobus Greyling が Substack で公開した原著『Loop Engineering』**（`cobusgreyling.substack.com/p/loop-engineering`、**2026年6月9日**公開）。単なるブログ記事ではなく、AI ネイティブ開発のパラダイムを宣言する一節である。Cobus は Loop Engineering をこう定義する：

> **コーディングエージェントを逐ターンでプロンプトする存在から、仕事を発見し、エージェントにタスクを渡し、結果を検証し、状態を永続化し、次のアクションを決めるシステム（the loop）を設計する存在へ——それをスケジュールに沿って、あるいはゴール達成まで動かし続けること。**

ループは「**再帰的なゴール（recursive goal）**」と捉えられる（Addy Osmani の枠組み）：目的を定義し、AI が完了まで反復する。

### 1.2 主要データ

- 著者：**Cobus Greyling**、**Kore.ai チーフ・エバンジェリスト（Chief Evangelist）**
- 媒体：Substack（`cobusgreyling.substack.com`）
- 公開日：2026-06-09
- 概念の系譜：Context Engineering → Harness Engineering → **Loop Engineering**
- 併設 OSS リポジトリ：`github.com/cobusgreyling/loop-engineering`
- エコシステム：Anthropic『Effective harnesses for long-running agents』『When AI builds itself』、Addy Osmani の X ポスト、Peter Steinberger（OpenClaw 開発者）

### 1.3 何を解決するのか？

従来の AI コーディングのワークフローは**「プロンプトを書く→出力を読む→次のプロンプトを書く」**。人間は「一ターンずつツールを握っている」。問題はスケーラビリティ：10本の並行エージェントを個別にプロンプトできないし、プロンプターという役割は根本的に拡張できない。

答え（Loop Engineering）：**エージェントを使う小さな自律制御システムを構築する**こと。逐ターンでエージェントを駆動するのをやめ、スケジュールやゴール条件に至るまで自分で動くシステムを設計する。これが単発会話との本質的な違いだ。

## 2. 核心思想

### 2.1 三層の進化（まず全体像から）

記事は冒頭で業界全体の進化を整理する——これ自体がひとつの視点だ：

> 「（AI の世界は急速に進んでいる…）**Context Engineering** が新しいと思った頃、次に **Harness Engineering**…そして今は **Loop Engineering**だ。3つの層で、それぞれ違う問題を解いていると考えてほしい。」

Harness と Loop の役割分担：

- **Harness**：**一回の**エージェント実行の足場（ツール、完了基準、フィードバック）。
- **Loop**：**スケジュールでエージェントをつつき続け、ヘルパーを生み、自己に餌を与え続ける**外層。

### 2.2 一文での定義（Addy Osmani の枠組み）

> 「エージェントにプロンプトする人間である自分自身を置き換え、代わりにそれを行うシステムを設計すること。ここでのループは、目的を定義し、AI が完了まで反復する**再帰的なゴール**と考えることができる。」

### 2.3 二つの象徴的な言葉

- **Peter Steinberger**（OpenClaw 開発者）："You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."（もうコーディングエージェントにプロンプトするべきではない。エージェントにプロンプトするループを設計すべきだ。）
- **Boris Cherny**（Claude Code 責任者）："I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. **My job is to write loops.**（私の仕事はループを書くことだ。）"

> ツールの収束は印象的だ。Claude Code と OpenAI Codex はどちらも非常に似たプリミティブに落ち着きつつあり、**「ループの形状」はツール非依存になりつつある**。

## 3. 詳細チュートリアル：五大ビルディングブロック＋メモリ（核心の6部構成）

本記事の本題はここ。**本当に無人で動くループとは「一つの長いプロンプト」ではなく、6つの部品からなる小さなシステムである。** 5つは能力、6つ目は実行間で状態をつなぐ背骨（スパイン）だ。

### 3.1 ブロック1：自動化／スケジューリング（ハートビート）

> **ループの心拍。**
- スケジュールがなければ一回性のエージェントセッションにすぎない。あれば**リズムにのった発見とトリアージ**ができる。
- 「毎朝 CI を確認すべき」を、ターミナルを開くかどうかに関係なく起こる**何か**に変える。
- **Claude Code**：`/loop`、`/schedule`、`/goal`（検証可能な条件に達するまで実行。**別の独立モデル**が「完了」をチェックし、ワーカーが自分の宿題を採点しないようにする）。Hooks と GitHub Actions がその考えをチャット外の永続化へ運ぶ。
- **Grok**：`/loop [interval] <prompt>` ＋ 基盤スケジューラツール（`scheduler_create` / `scheduler_list` / `scheduler_delete`）。

> **ハートビートは賢くある必要はないが、信頼できなければならない。**

### 3.2 ブロック2：ワークツリー（安全な並行実行）

- 2つのエージェントが同時に同じファイルを編集＝**マージ事故の未然**。
- 隔離された git ワークツリー（または同等のチェックアウト）で、各エージェントが独自の作業ディレクトリを持ちながら履歴を共有する。
- 二大コーディングエージェントツールはこれを内蔵。サブエージェントは新規チェックアウトに起動され、並行作業が衝突しない。

> Grok では、サブエージェント生成時に `isolation: "worktree"` を渡す。**クリーンアップが大切**。孤児ワークツリーを残すループは、後悔するループだ。

### 3.3 ブロック3：スキル（永続的なプロジェクト知識）

> 各セッションでエージェントはコールドスタート。

- 規約、ビルドコマンド、レビュー基準、そして「そうしないのだ」と学んだ事件——これらはすべて外部化しなければならない。
- **スキルこそが intent debt（意図の負債）を返済する方法だ。**
- `SKILL.md`（＋任意のスクリプトと参照）が実行をまたいで生き残る知識を保持する。
- Claude Code は `CLAUDE.md` とスキルを使い、共有のためにプラグインとしてパッケージ化。Grok も同じパターン。

> スキルがなければ、**どのループ実行も「初日」になる**。

### 3.4 ブロック4：プラグイン／コネクタ（実ツールへの接続）

- **ファイルシステムしか読めないループは、提案しかできないループだ。**
- MCP ベースのコネクタによりループは「行動」できる：PR を開く、Linear チケットを更新する、Slack に投稿する、DB を照会する、runbook を起動する——ループはコメンテーターから**オペレーター**へ。
- MCP は共通基盤になり、あるツール向けのコネクタは別のツールへ移設できることが多い。

### 3.5 ブロック4：サブエージェント（メーカー／チェッカー分離）

> **コードを書いたエージェントは、自分の仕事を評すのは下手な。**

- これはモデル能力の限界ではなく、**構造的な問題**だ。
- 一方のエージェント（チーム）が探索と実装を担当し、**別の**エージェント（時にはより強いモデル、常に異なる指示）が仕様・スキル・テストに照らして検証する。
- 無人ループでは、**検証者こそが安心して離れられる根拠**。
- `/goal`は複数のツールで同じ原則を適用：**新しいモデル（a fresh model）**が停止条件を満たしたか判断する。

### 3.6 ブロック6：メモリ（永続の背骨）

> 上記すべてはセッション境界を自力では通過しない。

- ループは**外部**に読み書きしなければならない：`STATE.md`、`LOOP-STATE.json`、Linear ボードの一列、GitHub Project の一ビュー。
- 良い状態は3つの問いに答える：
  1. 私たちは今何に取り組んでいる？
  2. 前回は何を試し、結果はどうだった？
  3. 何か人間の対応を待っている？

> 複数日・複数実行のループでは、これは**交渉の余地がない**。**状態ファイルはしばしばループが生み出す最も重要な成果物である。**

## 4. 設計哲学

### 4.1 自動制御システムであって、より大きなプロンプトではない

精神的な核心：**Loop Engineering は単一プロンプトを長くすることではなく、自分自身を繰り返し呼び出すシステムを構築すること。** あなたの役割はプロンプターからシステム設計者へ移る。**レバレッジポイントは移った。**

### 4.2 ツール非依存の「ループの形状」

ツールの融合について記事は明確だ：Claude Code と Codex は非常に似たプリミティブに到達しており、**ループの形状はツール非依存になっている**。これは産業が標準的なオーケストレーションの脚本へ収束しつつあるシグナルだ。

### 4.3 メーカー／チェッカー分離の哲学

主要な引用全体に一つの哲学が流れている：最も堅牢なシステムは常に独立した検証者を持ち、**コードを書いたエージェントが自分の宿題を採点しない**。これは無人運用に必要な最低限の信頼である。

### 4.4 レバーか罠か——覚醒を促す結び

記事は冷静な警告で締めくくる：**"Cognitive surrender is the comfortable trap."（認知的降伏は居心地のいい罠だ）**。同じループ設計が、エンジニアの立場に留まる人を加速させることもできれば、誰かに判断を完全に放棄させることもできる。

> Build the loop like someone who intends to stay the engineer—not just the person who presses go.（エンジニアであり続けるつもりの人がループを構築せよ——ただスタートボタンを押す人ではなく。）

## 5. まとめ：見解と結論

1. **シフトの方向は明確**：「人間がプロンプト→エージェントが実行」から「人間がループを設計→ループが自動でエージェントにプロンプト」へ。
2. **階層**：Loop Engineering は「agent harness engineering」の一段上に位置する。
3. **形状**：ループはツール非依存化しつつある。
4. **定義**：再帰的なゴール——目的を定義し、AI が完了まで反復する。
5. **構造**：本当の無人ループは「五能力＋一メモリ」の6部システム。
6. **検証者が離れる理由**：独立検証が無人運用を信頼できるものにする。
7. **実践者の見解は一致する**：Peter Steinberger と Boris Cherny はともに「私の仕事はループを書くこと」という。
8. **現実を飛ばさない**：タスクコスト、理解負債、認知的降伏——理想化された物語が隠すべきではない現実コスト。
