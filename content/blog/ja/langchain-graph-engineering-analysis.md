# LangGraph 徹底解説：3年間のグラフエンジニアリング実践総括——グラフで信頼できるAgentを構築する完全ガイド

> 核心理念：**エージェントシステムをグラフ（graph）として表現することで、あなた（構築者）はシステムがどう動作すべきかについての先入観を、より制約された経路に押し込める——LLMの判断だけに頼るのではなく。** グラフエンジニアリング（graph engineering）は、prompt engineering、context engineering、harness engineering、loop engineering に続く、XのAIコンテンツ工場が生んだ最新の用語。用語は多いが、その背後にある理由は実に具体的だ：**LLMに仕事をさせるのは難しい**——LLMは新しいタイプの、頑健でない（non-robust）、非決定的（non-deterministic）なソフトウェアであり、私たちは常に新しい戦略を試して動かそうとしている。そして新しい戦略が新しい用語を生む。LangGraphはまさにこの直感に基づいて3年前に構築されたフレームワークで、現在**月間ダウンロード数65M+**、スタートアップと大企業の双方が利用している。人気の理由は一つのバランスを見つけたからだ：**決定的な経路とエージェンティックなステップの間のバランス**。システムをグラフで表現することは、本質的にあなたの世界知識をエンコードすること——プロンプトが運ぶドメイン知識があなたのエージェントを汎用ChatGPTと区別するように、グラフという「認知アーキテクチャ」も同様にドメイン知識を運ぶ。結果として、コードとモデルの推論が協働する：**モデルは価値を生む場所でのみ推論し、コードが残りを処理する。それゆえエージェントはより安く、より速く、より予測可能になる。**

## 一、背景：「グラフエンジニアリング」という用語はどこから来たか

### 1.1 用語の誕生

「グラフエンジニアリング（graph engineering）」は2026年7月の週末に浮上し、Peter Steinbergerのツイートがきっかけとなった。これはXのAIコンテンツ工場が生んだ最新の用語で、prompt engineering（プロンプトエンジニアリング）、context engineering（コンテキストエンジニアリング）、harness engineering（ハーネスエンジニアリング）、loop engineering（ループエンジニアリング）に続くものだ。

これらの用語を「流行語（buzzwords）」と呼ぶのは魅力的でかつ正確だが、それらが存在し生まれてくるのには理由がある：**それらは構築者が直面する現実の課題と設計判断を的確に記述している**。

### 1.2 なぜこんなに多くの用語があるのか

結局のところ、目標はLLMの力を利用して私たちのために役立つことをさせることだ。プロンプトを使おうが、エージェント、ループ、グラフを使おうが、それらは実装の詳細に過ぎない。これほど多くの用語が存在するのは、**LLMに仕事をさせるのが難しいから**だ：

- LLMは新しいタイプの**非頑健（non-robust）、非決定的（non-deterministic）**なソフトウェア
- 私たちは信頼できるように動かす新戦略を常に試している
- 新戦略 → 新用語

### 1.3 流行語の先：なぜグラフが合理的なのか

流行語はさておき、**エージェントシステムをグラフとして表現することは、LLMの力を活用する非常に合理的な方法だ**。具体的には：

> グラフはあなた（構築者）が、システムがどう動作すべきかについての**先入観（preconceptions）**をより制約された経路に押し込むことを可能にする——LLMの判断だけに頼るのではなく。より具体的には、エージェントに特定の経路を辿らせたいときに、行動をより緊密に制御できる。

まさにこの直感が、LangChainチームを3年前にLangGraphの構築へと駆り立てた。この種のエージェントシステムを構築するためのフレームワークとして。

### 1.4 主要データ

| 指標 | データ |
|------|------|
| 公開時期 | 約3年前（2023年頃） |
| 現在の月間ダウンロード数 | 65M+ 回/月 |
| 利用者 | スタートアップと大企業 |
| 核心的な売り | 決定的な経路とエージェンティックなステップのバランス |
| 構築者 | LangChainチーム（Harrison Chase ら） |

## 二、プロジェクト解説：LangGraphとは何か

### 2.1 一言でいうと

LangGraphは、**グラフ（graph）を用いて長期実行・ステートフル（stateful）なエージェントを構築・管理・デプロイするための、低レベルのオーケストレーションフレームワークかつランタイム**だ。

### 2.2 他のエージェントフレームワークとの違い

世の中には無数のエージェントフレームワークが存在する。LangGraphが人気を博したのは、**決定的な経路（deterministic paths）とエージェンティックなステップ（agentic steps）の間でバランスを取っている**からだ：

- 自由すぎるフレームワーク（純粋なエージェントループ）：モデルがすべてを決め、行動が予測不能
- 硬直すぎるフレームワーク（純粋なパイプライン）：オープンエンドなタスクを扱えず、モデルの能力を浪費
- LangGraph：**構造をグラフにエンコードし、自由はノード内部に残す**——決めるべきところは決定的に、エージェンティックであるべきところはエージェンティックに

### 2.3 3年間の実践総括としての位置づけ

この記事はLangChainチーム（Harrison Chase と Sydney Runkle）が2026年7月22日に公開した公式総括で、タイトルは『3 Years of Graph Engineering with LangGraph』——一言で言えば：**3年間、私たちはグラフでエージェントシステムを構築してきた。以下が学んだことだ。**

## 三、詳細チュートリアル：Agentをグラフとしてモデル化する方法

### 3.1 グラフの3要素

エージェントをグラフとしてモデル化することは、本質的に**ステートマシン（state machine）**を定義することだ：

| 要素 | 役割 | 内容 |
|------|------|------|
| **ノード（Nodes）** | 仕事をする | 決定的なコード、単一のLLM呼び出し、ツール呼び出し、または内部ループを持つ完全なエージェント |
| **エッジ（Edges）** | 次に何が起こるかを定義 | 決定的エッジ（固定フロー）；条件付きエッジ（ノード結果・現在の状態・外部シグナルに基づく） |
| **状態（State）** | グラフ内を流れるデータ | グラフが定義するワークフロー内を移動し、各ステップを結ぶ |

こう理解できる：**グラフがワークフローを定義し、状態がその中を流れ、エッジがステップ間の遷移を定義する。**

### 3.2 最小例：分類付きナレッジベースエージェント

これは原文が示す核心的な事例：ナレッジベースエージェントが3つのサブエージェントを使って検索する：

- **GitHubエージェント**：コード、issue、pull requestを検索
- **Notionエージェント**：内部ドキュメントとwikiを検索
- **Slackエージェント**：関連スレッドを検索

ワークフローには3つの固定フェーズがある：**分類（classify）→ 検索（search）→ 総合（synthesize）**。

LangGraphのPython APIでモデル化するとおよそ次のようになる：

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Literal

class AgentState(TypedDict):
    query: str
    source: Literal["github", "notion", "slack"]
    results: list

def classify(query: str) -> str:
    """分類ノード：質問がどの知識ソースに属するかを判断（モデル単一呼び出し、ツールなし）"""
    # LLMで判断：コード問題 → github；内部ドキュメント → notion；議論 → slack
    return "github"  # サンプル戻り値

def search_github(state: AgentState) -> AgentState:
    """検索ノード：GitHubエージェントがコード/issue/PRを検索"""
    return {**state, "results": search_code(state["query"])}

def search_notion(state: AgentState) -> AgentState:
    """検索ノード：Notionエージェントが内部ドキュメント/wikiを検索"""
    return {**state, "results": search_docs(state["query"])}

def search_slack(state: AgentState) -> AgentState:
    """検索ノード：Slackエージェントが関連スレッドを検索"""
    return {**state, "results": search_threads(state["query"])}

def synthesize(state: AgentState) -> AgentState:
    """総合ノード：検索結果を最終回答に合成（モデル単一呼び出し）"""
    return state

# グラフを構築
graph = StateGraph(AgentState)
graph.add_node("classify", classify)
graph.add_node("github", search_github)
graph.add_node("notion", search_notion)
graph.add_node("slack", search_slack)
graph.add_node("synthesize", synthesize)

graph.add_edge("classify", "github")   # 決定的エッジの例（条件付きにも変更可能）
graph.add_edge("classify", "notion")
graph.add_edge("classify", "slack")
graph.add_edge("github", "synthesize")
graph.add_edge("notion", "synthesize")
graph.add_edge("slack", "synthesize")
graph.add_edge("synthesize", END)

app = graph.compile()
```

このフローは**ファンアウト＆総合（fan-out and synthesize）**：1つの入力を複数の並列検索者に分配し、すべての結果を総合ステップに集約する。

### 3.3 グラフを使うべき場合

現実世界のエージェントワークフローには**予測可能な構造**があることが多い：

- **サポートエージェント**：問題を分類してから回答するかエスカレーションする
- **コーディングエージェント**：変更を提案する前にリポジトリを調査する
- **コンプライアンスワークフロー**：外部アクションの前に承認を得る

グラフを使えば**その構造を直接エンコードできる**：どの経路が合法か、どこでモデルに選択させるか、どこでモデルが毎回正しい判断をするのを期待する代わりにシステムが決定的な行動を強制すべきか。

> **重要インサイト**：システムをグラフとして表現することで、システムがどう動作すべきかについての**世界知識（world knowledge）**をエンコードしている。プロンプトが運ぶドメイン知識があなたのエージェントを汎用ChatGPTと区別するように、グラフという「認知アーキテクチャ（cognitive architecture）」も同様にドメイン知識を運ぶ。

**グラフを使う利益**：コードとモデルの推論が協働する——モデルは価値を生む場所でのみ推論し、コードが残りを処理する。それゆえエージェントは**より安く、より速く、より予測可能**になる。

### 3.4 グラフを使うべきでない場合

中には本質的によりエージェンティックなタスクがあり、それを決定的な経路に無理やり押し込むのは誤った選択だ。その場合、システムをグラフとして表現したくはない。代わりに**agent harness（エージェントハーネス/枠組み）**を直接使うべきだ。たとえばLangChainの**Deep Agents**。

**典型例：汎用ディープリサーチ（deep research）**。研究エージェントは計画、委任、検索、読解、総合を、事前に固定しにくい方法で行う必要がある。原文が明かしていること：

- LangChainは初期のディープリサーチを**事前定義されたLangGraphワークフロー**で構築した
- その後、**よりエージェンティックなコアループ（core loop）**へ移行した
- 著名なオープンソース実装 **GPT Researcher** も同じ移行を行った：グラフ状のマルチエージェントパイプラインをDeep Agentsに置き換え、計画・委任・コンテキスト管理が**ハーネスの中で創発（emerge）**するようにした——グラフにハードコードするのではなく

> **判断ルール**：ワークフロー構造が予測可能 → グラフを使い、構造を明示化する；ワークフローが本質的にオープンエンドな探索 → agent harnessを使い、構造を創発させる。

### 3.5 上級編：動的遷移とmap-reduce

構築時にすべてのエッジを定義したいとは限らない。ノードが実行時にどれだけの仕事を生成するかを決めることもある。**Map-reduceが典型的なケースだ**：

> 入力を複数の断片に分割し、各断片をワーカーに送り、結果を結合する。ワーカーの数は入力に依存し、事前には分からない。

LangGraphはこれを **`Send` API** で処理する——ノードが1つ以上の下流ノードへ動的に仕事をルーティングできるようにし、**すべての遷移を静的に定義する必要がない**：

```python
from langgraph.types import Send

def continue_to_sources(state):
    """動的ディスパッチ：入力に基づいて生成する検索タスクの数を決定"""
    return [
        Send("search", {"query": q})
        for q in split_into_queries(state["input"])
    ]

# グラフ内：source_routerノードはSendで仕事を複数のsearchノードへファンアウトし、
# search完了後はsynthesizeノードに集約される
```

これは重要だ。**有用なエージェントシステムは、既知の構造と実行時の可変性を混在させている**からだ：

- 研究がファンアウトしてから総合するのは分かっていても、ソースがいくつあるかは分からない
- supervisorがワーカーに委任するのは分かっていても、タスク開始まで具体的に誰に委任するか分からない
- **グラフは実行時にも柔軟性を必要とする**

## 四、本当に新しいものは何か

### 4.1 新しいのはグラフそのものではなく、ノードの中に入れられるもの

エージェントシステムをグラフとして表現することは新しいことではない——LangChainは3年間やってきた！ではこの「グラフエンジニアリング」の波で、実際に変わったものは何か？

寛大な解釈：**変わったのはノードの中に入れられるものだ**。

- **初期**：ノードは決定的なコードか単一のLLM呼び出し
- **現在**：エージェント自体が現実の仕事を任せられるほど信頼できるようになり——**1つのノードが完全なエージェント実行（agent run）になり得る**。あなたはLLM呼び出しをオーケストレーションしているのではなく、エージェントをオーケストレーションしている

### 4.2 ノードとしてのコーディングエージェント：新しく実用的になったパターン

**コーディングエージェント（coding agents）**は、現在の本番環境で最も効果的で影響力のあるエージェントの1つだ。コーディングエージェントをノードとしてより大きなグラフに埋め込むのは、**最近になって実用的になったパターン**だ。

**事例：docsエージェント（ドキュメントエージェント）**。Slackリクエストを：

> 例：「カスタムツールのドキュメントを追加してください」

**レビュー可能なpull request**に変える。このグラフの各ノードは、**決定的からエージェンティックへのスペクトラム**上の異なる位置に座っている：

| ステップの種類 | 内容 | 例 |
|---------|------|------|
| **固定ステップ（Fixed steps）** | 設定済みコードとAPI呼び出し | SlackとLinearの操作 |
| **モデルステップ（Model steps）** | ツールなしの単一LLM呼び出し | 分類器、総合ステップ |
| **エージェントステップ（Agent steps）** | よりオープンエンドな仕事 | reference docsエージェント、conceptual docsエージェントが各コードベースでオープンエンドな仕事を完了 |

> **核心インサイト**：ここでの決定性と自律性の混在こそが、このdocsエージェントを**予測可能で、強力で、効率的**にしている理由だ。

## 五、設計哲学：LangGraphとグラフエンジニアリングの世界観

### 5.1 グラフは認知アーキテクチャ

LangGraphの背後にある設計哲学の核心的主張は：

> **システムをグラフとして表現することは、システムがどう動作すべきかについての世界知識をエンコードすることだ。** プロンプトが運ぶドメイン知識があなたのエージェントを汎用ChatGPTと区別するように、グラフという「認知アーキテクチャ」も同様にドメイン知識を運ぶ。

**帰結**：よく設計されたグラフは、それ自体がドメイン知識の実行可能な形態だ——「システムがどう動作すべきか」をモデルのブラックボックス判断から解放し、構築者が検討・調整・検証できる明示的な構造にする。

### 5.2 決定的な経路とエージェンティックなステップのバランス

LangGraphが存在する理由は、**決定的な経路とエージェンティックなステップの間でバランスを取ること**だ：

- 「全自動」ではない——一部の経路は強制しなければならず、モデルに自由にやらせてはならない
- 「全パイプライン」でもない——ノード内部ではエージェンティックな自由を許す
- **原則：決めるべきところは決定的に、自律すべきところは自律的に、自由度はノード内部に収める**

### 5.3 ループは単純なグラフ

LangGraphチームの3年間の実地経験：**loop engineeringはgraph engineeringの代替ではなく、その簡易版だ**。XStateの作者David Khourshidが言うように：「ループとは、単に有向で循環するグラフである（a loop is just a directed, cyclic graph）。」

最も有力な証拠：**LangChainフレームワーク自体（単純なエージェンティックループに基づく）がLangGraph上に構築されている**。

### 5.4 モデルは価値を生む場所で推論する

グラフエンジニアリングの最終的な哲学目標は**コストと予測可能性の最適化**だ：

> コードとモデルの推論が協働する：モデルは価値を生む場所でのみ推論し、コードが残りを処理する。それゆえエージェントはより安く、より速く、より予測可能になる。

**やってはいけないこと**：モデルに得意でない固定ロジックをやらせること。**やるべきこと**：モデルに判断・総合・オープンエンドな理解で力を発揮させること。グラフはこの2つの能力を精密に階層化するための道具だ。

## 六、3年間の実践知見総括：学んだ3つのこと

### 6.1 第一に、エージェントグラフは通常DAGではない

本番のエージェントには**循環（cycles）**が必要だ：

- 失敗したツール呼び出しのリトライ
- ユーザーに欠落情報を尋ねる
- 検証後に回答を修正する
- 十分なコンテキストを得るまでツールを繰り返し呼ぶ
- 人間の入力を待つため一時停止してから再開する

**ループはエージェントシステムの核心的な構成要素**だ。だからエージェントグラフはDAG（有向非巡回グラフ）ではない可能性が高い。

### 6.2 第二に、ループは単純なグラフ

- loop engineeringはgraph engineeringの代替ではなく、その**簡易版**
- 1つのループ = 有向で循環するグラフ
- LangChain（単純なエージェンティックループに基づくフレームワーク）はLangGraph上に構築されている——**最も単純なグラフはLangGraphが表現できるもの**。両者は対立関係ではなく包含関係だ

### 6.3 第三に、動的遷移が重要

- 構築時にすべてのエッジを定義する必要はない
- ノードが実行時にどれだけの仕事を作るかを決めることがある（map-reduce）
- **Send API** によりノードは仕事を動的にルーティングでき、各遷移を静的に定義する必要がない
- 有用なエージェントシステム = **既知の構造 + 実行時の可変性**の混在

## 七、総括：核心的見解と結論

### 7.1 核心的見解リスト

1. **用語が多い ≠ 誇大広告**：graph engineeringなどの用語は構築者が直面する現実の設計判断を記述する；それらが存在するのはLLMに仕事をさせるのが難しいから
2. **グラフは合理的なパラダイム**：グラフは先入観を制約された経路に押し込み、必要なときに行動をより緊密に制御する——これがLangGraphの存在理由
3. **バランスこそLangGraphが人気の理由**：決定的な経路とエージェンティックなステップのバランスが、他のエージェントフレームワークと区別する
4. **グラフは世界知識をエンコードする**：グラフはプロンプトと同様にドメイン知識を運ぶ認知アーキテクチャであり、実行可能なドメイン知識の形態
5. **構造化タスクにはグラフ**：サポート分類、コーディング調査、コンプライアンス承認——予測可能な構造のワークフローはグラフで直接エンコード
6. **オープンエンドタスクにはハーネス**：ディープリサーチのような本質的にエージェンティックなタスクはagent harness（Deep Agents）を使い、計画・委任・コンテキスト管理を創発させる
7. **エージェントグラフはDAGではない**：循環（リトライ、質問、修正、一時停止）はエージェントシステムの核心
8. **ループは単純なグラフ**：LangChainはLangGraph上に構築されており、両者は包含関係であって対立ではない
9. **動的遷移は必須**：実行時まで仕事量が分からない（map-reduce）、Send APIのような動的ルーティングが必要
10. **本当の変化はノード内部**：現在ノードは完全なエージェント実行になり得る——あなたはLLM呼び出しではなくエージェントをオーケストレーションしている
11. **コーディングエージェントは新しい実用的ノード**：docsエージェント事例が決定的からエージェンティックへのスペクトラム上のノード混在を示す
12. **モデルは価値を生む場所で推論する**：最終目標はより安く、より速く、より予測可能なエージェント

### 7.2 判断クイックリファレンス

| シナリオ | 選択 | 理由 |
|------|------|------|
| ワークフロー構造が予測可能（分類→応答/エスカレーション） | グラフ（LangGraph） | 合法な経路を直接エンコード |
| 決定的な制御が必要（コンプライアンス承認） | グラフ（LangGraph） | モデルに期待するのではなくシステムが強制 |
| 実行時のファンアウトが必要（map-reduce） | グラフ + Send API | 静的定義なしの動的ルーティング |
| オープンエンドな探索（ディープリサーチ） | agent harness（Deep Agents） | 計画・委任・コンテキスト管理が創発 |
| 単一エージェントループ | グラフの最も単純な形態 | ループは有向循環グラフ |
| ノード内部に自由度が必要 | ノード内にエージェント | LLM呼び出しではなくエージェントをオーケストレーション |

### 7.3 構築者への示唆

1. **コードを書く前に構造を考える**：着手前に自問する——このワークフローのどこが予測可能か？どこでモデルを自由にすべきか？予測可能な部分を明示的なグラフにする
2. **グラフを盲信しない**：タスクがオープンエンドな探索なら、答えはグラフではなくハーネスだ
3. **ループを受け入れる**：リトライ、質問、修正は異常ではなくエージェントシステムの常態であり、グラフはそれらをサポートしなければならない
4. **自由度を正しい階層に置く**：決めるべき経路は強制し、自律すべきステップはノード内部に残す
