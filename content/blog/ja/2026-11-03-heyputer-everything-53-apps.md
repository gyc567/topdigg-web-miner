# HeyPuter の 53 個のワールドクラスのソフト：Excel、Slack、Photoshop、AutoCAD をすべて作り直した男がいる

結論が先です。

**第一に、これはまたひとつ「AI を被せただけのアプリ」ではなく、10 年かけて初めて達成できる長い走りです。** 私は HeyPuter/everything を丸ごとクローンしてアプリごとに読み解きました。アプリディレクトリ 51 個、うち 48 個がすでにデプロイ済み、JavaScript / TypeScript で 224 万行、テストファイル 8,711 個、フロントエンドフレームワークはひとつもありません（React も Vue も Svelte も無し）。バックエンドは Puter というクラウドプラットフォームに統一されています。これは「いちばん愚直な方法」で積み上げたソフトウェア帝国です。

**第二に、このプロジェクトで最も鋭い点は機能の追随ではなく、「サーバを持たない」ことをアーキテクチャに書き切った勇気です。** 24 個のアプリの README にすべて同じ一文が書かれています。「no server of its own」（自分の持つサーバは無い）。すべてのバックエンド機能（アカウント、ストレージ、データベース、KV、Worker、デプロイ）は Puter プラットフォームから来ます。つまり各アプリはどの静的ホスティング（AWS Amplify、オブジェクトストレージ、自前の Nginx）にも投げ込め、環境変数を 1 行も設定せず、API Key の申請も不要です。SaaS の常識からすると逆行する考え方です。

**第三に、多くのアプリは明示的に alpha 状態と記しています。** CAD の README の第一文は「Early alpha であり、実際のプロジェクトに依存しないでください、重要な作業は自分で控えを残してください」です。Records、Wiki、Expenses にも同様の警告があります。したがって正しい読み方はこうです。**公開されている、ソースコードをただで読めるアーキテクチャの範本**として読むべきであり、Office を直接置き換えられる製品ではない。

**第四に、このプロジェクトの最も価値のある部分は 53 個のアプリではなく、「バックエンドを書かず、フレームワークを使わず、ライセンスの赤線を踏まずに、本気で使えるプロ級ソフトウェアを作る方法論」一式です。** 以下ではその方法論を分解して解説します。実際に手を動かせるローカル実行チュートリアルも含みます。

## 一、プロジェクト説明：これは何なのか

### 1.1 一言でのポジショニング

The Everything Project の自己説明は「世界中のソフトウェアを再構築しオープンソースにする」です。Office から Slack、Photoshop から AutoCAD まで、プロプライエタリなソフトウェアの自由なオープンソース代替をすべて作り直し、ひとつの単一リポジトリ（mono-repository）にすべて収めました。

実ファイルから数えました（node_modules、dist、tests、vendor、tmp は除外）：

### 1.3 分類リスト

README は 51 個のアプリを 9 大カテゴリに分けています：

- **オフィス**（7 個）：Spreadsheet、Documents、Presentation、Whiteboard、PDF、Notes、Records
- **コラボレーション**（6 個）：Meetings、Teamchat、Email、Contacts、Calendar、Signatures
- **クリエイティブツール**（6 個）：Photo Studio、Video Studio、Vector Studio、Audio Studio、Music Studio、3D Studio
- **エンジニアリング**（4 個）：CAD、Parametric、Circuits、Building Design
- **生産性**（5 個）：Tasks、Projects、Wiki、Time Tracking、Surveys
- **財務**（4 個）：Accounting、Invoicing、Expenses、Cap Table
- **ビジネス**（13 個）：CRM、Help Desk、Contracts、POS、Inventory、Assets、Hiring、Shifts、Childcare、Field Service、Legal、Fleet、Property Management
- **開発者ツール**（1 個）：API Client
- **ゲーム**（5 個）：Chess、Backgammon、Checkers、Solitaire、Sudoku

**この 9 カテゴリの分布そのものが要求定義書です。** 世界中のソフトウェアのカテゴリ構成を誰かが本気で数え、そのマスをすべて埋めた。背後にあるのは稀に見る忍耐です。

### 1.4 ライセンス：落とし穴がある。先に言うべき

ルートリポジトリの LICENSE は MIT ですが、**サブアプリは統一されて MIT ではありません**。package.json を 1 つずつ確認した結果：

- **AGPL-3.0-only（9 個）**：3d、building-design、email、notes、pdf、presentation、spreadsheet、video-studio、whiteboard
- **MIT（7 個）**：accounting、calendar、help-desk、parametric、projects、records、survey
- **package.json に宣言なし（残り）**：多くはルートリポジトリの MIT が適用されますが、個別に確認が必要です

AGPL とはどういう概念か。誰かがネットワーク経由で当該ソフトウェアを使う場合（SaaS であっても）、完全なソースコードをユーザーに提供しなければなりません。GPL よりもさらに厳しい一層です。spreadsheet を商用クローズドソース製品に使いたいなら、AGPL が真っすぐ阻まれます。

さらに `documents` アプリの AGENTS.md には次のような硬いルールが書かれており、项目全体でいちばん価値のあるエンジニアリングガバナンスの一節だと考えています：

> AGPL ライセンスのコードや依存 관계を導入しないこと（直接、間接、vendored、リモートロードのいずれでも。 Proprietary なサードパーティのドキュメントエンジンも導入しないこと（テストやツール内も含めて）。公開されるすべてのバイナリには対応するソースコードと許容可能なライセンスが必要。依存関係の変更後は `npm run check:licenses` を実行する。**チェックを通すためにライセンスのホワイトリストを広げるな。まず実際のライセンスを精査しろ。**

最後の文が最も重要です。オープンソースプロジェクトがコンプライアンス検査で自己麻薬するのを防ぐガードレールです。

## 二、詳細チュートリアル

### 2.1 動作要件

| 項目 | 要件 |
|---|---|
| Node.js | 22.12+（一部のアプリは 24 LTS を推奨、3d は明確に 24 を要求） |
| npm | Node に同梱 |
| ブラウザ | WebGL2 対応のモダンブラウザ（Chrome / Edge / Firefox / Safari） |
| ディスク | フルクローンで約 1.8GB、依存インストール後はさらに増える |

### 2.2 クローンとローカル実行

```sh
git clone https://github.com/HeyPuter/everything.git
cd everything/src/spreadsheet
npm install
npm run dev
```

わずか 4 ステップです。`.env` 設定ファイルも、DB 初期化スクリプトも、Docker Compose もありません。

起動後にブラウザで開くアドレスは少し変なところがあります：

```
http://spreadsheet.puter.localhost:5173/
```

**この `puter.localhost` ドメインは意図的な設計です。** リポジトリのルートに `dev/puter-localhost.mjs` があり、これは Vite プラグインで、サーバが待ち受けを始めた後にローカル URL のホスト名を `<アプリ名>.puter.localhost` に書き換えます。原理は簡単で、ブラウザは `*.localhost` をすべてループバックアドレスに解決し、Vite も既定で `.localhost` のホスト名を受け付けます。よって `/etc/hosts` の書き換えもプロキシの設定も不要です。**20 行のプラグインでマルチアプリのローカル開発におけるドメイン分離が解決できました**。これは非常にきれいな設計です。

各アプリの vite.config ではこの共有プラグインを読み込んでいます：

```js
import puterLocalhost from '../../dev/puter-localhost.mjs';
```

### 2.3 他のアプリへの切り替え

すべてのアプリは同一リポジトリ内にあり、切り替えはディレクトリを変えるだけです：

```sh
cd ../3d            # 3D Studio、40 万行
npm install
npm run dev

cd ../documents     # ドキュメントエディタ
npm install
npm run dev
```

### 2.4 ログインしなくても使える

ここは非常に重要な点なので、单独で触れます。**多くのアプリはログインなしで作業できます。**

Spreadsheet の README にはこう書かれています：

> 使うためにログインする必要はありません。アプリは新しいスプレッドシートを直接開き、Puter が sign in を求めるのは保存、ファイルを開く、スプレッドシート一覧を表示するといった、初めてクラウドが必要な操作のときだけです。それまでは編集内容がタブ内（およびそのブラウザのローカル下書き）に留まり、ステータスピルは "Sign in to save" と表示されます。

Records、Presentation、CAD も同じパターンです。这意味着什么呢。このソフト群は完全にオフラインの状態でもローカルアプリとして扱えるということです。

- Spreadsheet：数式、チャート、書式がすべて機能する
- CAD：ローカル図面を開き、デバイスに保存し、リロード後にブラウザから復元できる
- PDF：PDF をローカルで開き、編集し、エクスポートできる
- Documents：`/playground.html` は単独で動作し、アカウントもクラウド SDK も不要

ログインが発生するのは 4 つの場面だけです。**クラウドへの保存、クラウドのファイルを開く、共同編集、バックエンド計算を必要とする機能**（Spreadsheet の `AI()` や `IMPORTDATA()` など）。

### 2.5 各アプリのビルドとテスト

スクリプトはアプリごとに多少異なりますので、必要なものを選んでください：

```sh
# 汎用：ユニットテスト

# 3d：フルチェックチェーン（ユニットテスト + 型チェック + 本番ビルド + ブラウザ E2E）
npm run check

# documents：ライセンス検査 + DOCX 準拠性検査

# pdf：サードパーティ表明書の生成 + ビルド + クロスブラウザ E2E

# ホワイトボード / 汎用：本番ビルド + ローカルプレビュー
npm run build

```

**E2E には先にブラウザのインストールが必要です：**

```sh
npx playwright install chromium

```

### 2.6 デプロイ：各アプリは独立した Amplify アプリ

リポジトリルートの 2 つのファイルがデプロイ一式を定義しています：

**`amplify.yml`** では、各 `src/xxx` ディレクトリが独立した Amplify アプリであり、ルートがそのサブディレクトリです：

```yaml
applications:
  - appRoot: src/whiteboard
    frontend:
      phases:
        preBuild:
          commands:
            - nvm install 22
            - npm ci
        build:
          commands:
            - npm run build
      artifacts:
        baseDirectory: dist
        files:
          - '**/*'
```

**`customHttp.yml`** はキャッシュ戦略を定義します。ファイル冒頭にある重要な説明に注意してください：

> Amplify は単一リポジトリのアプリに対するリクエストヘッダをリポジトリルートのこのファイルからのみ読み込むため、各アプリのヘッダは appRoot が自分のディレクトリにマッチするエントリに置いています。**このリポジトリからデプロイされるすべてのアプリには、エントリが 1 つ必要です。ヘッダを持たないアプリであっても同様です。エントリが見つからないアプリは Amplify がデプロイを失敗させます。**

キャッシュ戦略自体も学ぶ価値があります：

```yaml
- pattern: '/'
  headers:
    - key: 'Cache-Control'
      value: 'no-cache, max-age=0, s-maxage=0, must-revalidate'
- pattern: '/assets/*'
  headers:
    - key: 'Cache-Control'
      value: 'public, max-age=31536000, immutable'
```

エントリページは決してキャッシュされません（Vite の成果物にはハッシュが付きますが、エントリは古いリソースを指している可能性があるため）。ハッシュ付きのリソースは永久キャッシュです。この「エントリはキャッシュしない + リソースは immutable」の組み合わせはあらゆる Vite 静的サイトの標準構成ですが、ここでは人が覚えておくのではなく、設定ファイルに書き込まれ CI によって強制されています。

### 2.7 Puter プラットフォームへのデプロイ

一部のアプリには Puter 専用デプロイスクリプトが同梱されています。例として Spreadsheet：

```sh
npm run deploy:email-worker
```

Teamchat の仕組みはもっと攻めたものです。**すべてのワークスペースが、作成者の Puter アカウント上で自分専用の Worker を動かします。** 原文：

> ユーザーが最初にワークスペースを作成したとき、アプリは同梱の worker パッケージ（`public/worker/teamchat-worker.js`）を彼のドライブにコピーし、`puter.workers.create()` を呼び出します。この worker の KV とファイルシステムがすべてのデータを保持します。

つまり Slack 代替のマルチテナント分離は「テナントごとに独立した Worker インスタンス」で実装され、権限チェックは worker のすべてのルートで強制実行されます。

### 2.8 深掘り読解の 3 本のルート

3 文書だけを読むなら、この 3 本を強くおすすめします：

**① `src/documents/AGENTS.md`（27 行）**：最短ですが、情報密度は最高です。依存ポリシー、ライセンスの赤線、canvas エンジンのマイルストーン要件、OOXML 準拠性の記録方法を定義しています。核心は 1 条：

> ドキュメント変更、DOCX のシリアライズ、レイアウト、描画の 4 つを分離する。触れていない DOCX パッケージの構成要素は保持する。非対応の特性を含むドキュメントを開く場合はベストエフォートで処理し、安全な編集ができない場合は読み取り専用の近似にフォールバックする。**そして、非対応の内容を失う可能性があるセーブハンドラを付けないこと。**

この文の重みは相当なものです。「100% の互換性はできない」と認めつつ、できないときにどう見事に劣化させるかを規定している。黙ってユーザーのデータを消すのではなく。

**② `src/3d/ARCHITECTURE.md`（273 行）**：産業グレードの 3D エンジンのモジュール分割。中心概念は Depsgraph（依存グラフ）と COW（copy-on-write、コピーオンライト）スナップショットです：

> **型付き配列は、1 回 undo プッシュされた後はイミュータブルです。** 操作中にその場で変更したい場合は `data/cow.ts` の `cow(owner, 'key')`（undo ステップごとに 1 回だけコピー）を使うか、新しい配列をそのまま代入してください。

あわせて完全な operator 登録モデルも掲載されています：

```ts
registerOperators([{
  idname: 'mesh.subdivide',
  label: 'Subdivide',
  props: [...PropDef],
  poll: (ctx) => bool,
  exec: (ctx, props) => 'FINISHED' | 'CANCELLED' | void,
  undo?: boolean
}]);
```

**③ `src/spreadsheet/README.md`（1,200 行）**：これは「機能仕様書」レベルの文書であり、プロジェクト全体のドキュメント品質の基準です。510 以上の Excel 関数をカテゴリ別に一つずつ列挙し、`LAMBDA` の自己再帰、`GROUPBY` のグループ集計、`PIVOTBY` のクロスタブピボット、`@` 暗黙の交差演算子、`IMPORTXML` の XPath ノード抽出まで触れています。詳細さは Excel 関数ハンドブックとして直接使える水準です。

## 三、キーアプリの技術的見どころ

### 3.1 Spreadsheet：Excel 互換をどこまで実現しているか

510 以上の関数は基礎にすぎません。本当難しいのは以下の点です：

**ダイナミック配列**：`UNIQUE`、`FILTER`、`SORT`、`SORTBY`、`SEQUENCE`、`RANDARRAY`、`TRANSPOSE`、`TEXTSPLIT`、`VSTACK`、`HSTACK`、`WRAPROWS`、`TOCOL` がすべて spill（スピル）に対応し、`A1#` でスピル領域を参照でき、埋まっている場合は `#SPILL!` になります。

**Excel クエリ言語**：Sheets 風のクエリ文字列をそのままサポートしています：

```
=QUERY(range, "select A, sum(C) where B > 5 group by A order by sum(C) desc limit 10 label sum(C) 'Total'")
```

**エラーメッセージはプロダクトグレード**：`#NAME?` は「SUM という名前の関数はありません。SUM のことでしょうか？」と直接教えてくれ、`#REF!` はどのシートが欠けているかを指摘します。これはエラー報告ではなく「教材」です。

**AI をセルに直接書ける**：

```
=AI(prompt, [data])
=TRANSLATE(text, [from], [to])
=DETECTLANGUAGE(text)
```

`AI()` は思考中に `#BUSY!` を返し、同じプロンプトは一度しか尋ねず、F9 で再質問できます。

**本物の .xlsx ファイル**：保存されるものは本物の Excel ファイルで、Excel、Numbers、LibreOffice で開けます。往復のインポート/エクスポートは Excel ネイティブのチャート（折れ線、散布、積み上げ棒、積み上げカラム、Pareto 複合チャート）、テーマカラー、日付軸、隠し補助シート、名前付き数式のロケータラベルなど、数多くの細部にわたって対応しています。

**バックエンドサーバは無し**、すべて Puter.js に依存しています。

### 3.2 3D Studio：clean-room 実装による Blender 代替

このアプリの野心は最も怖いものです。モデリング、スカルプティング、UV、マテリアルノード / ジオメトリノード / コンポジター、アニメーションのリグ設定、物理シミュレーション、パストレーシングとリアルタイムレンダリング、動画編集、モーショントラック、Grease Pencil、スクリプティング——**すべてブラウザ内で動きます**。

技術選定：**純 TypeScript + three.js（WebGL2）**、フロントエンドフレームワークは完全不使用。

**Z 軸が上、単位はメートル、角度は内部でラジアンで保持**。プロパティ命名は広く使われる `bpy` スクリプト規約（`location`、`rotation_euler`、`hide_render`）に従っており、アニメーションパス、スクリプト、インポータが 1 対 1 で対応します。

ライセンスについて次のような声明があります：

> 本プロジェクトは独立しています。これは clean-room 実装であり、Blender のソースコード、アイコン、テーマ、その他のアセットは一切含みません。Blender 財団との Affiliation はなく、Blender 財団による承認も受けていません。

**clean-room 実装**はソフトウェアエンジニアリングにおいて最も難しい種類の「きれいさ」です。「ソースを読んで書き直す」のではなく「仕様とドキュメントだけを見てゼロから実装する」というやつです。3D の README にはこの方式の代償を突いた一文があります：

> `.blend` のインポートはアクティブなシーンと一般的なデータに対応しています（ボリューム、点群、ラインレンダー設定は含みません）。サポートされていないデータは、黙って失われるのではなく報告されます。**`.blend` でのエクスポートには対応していません。**

**AI アシスタント**部分の設計は見習う価値があります。シーンを読み取り、`bpy` 風 API に対してスクリプトを書いて実行し（失敗したスクリプトはロールバックされます）、API ドキュメントを参照し、ビューポートのスクリーンショットを撮って自己点検し、ユーザーが添付した参考画像 / PDF / テキストを読み取ります。**あるメッセージのために行ったすべての変更は、1 つの undo ステップにまとめられます。**

### 3.3 Documents：Canvas エディタの再実装

サードパーティのリッチテキストエディタを埋め込むのではなく、自前でレンダリングエンジンを書いています。

**2 つの動作モード**：

- `/playground.html`：単独のローカルエディタ、アカウントもクラウド SDK も不要
- `/mock.html`：メモリ内の Puter モックで、保存と再オープンをテスト
- `/`：実際の Puter クラウドストレージを使用

**フォントメトリクスの互換**：Calibri、Cambria、Arial、Times New Roman、Courier New にメトリクス互換の代替フォントを提供しています。「よく似ている」のではなく「組版結果が同じ」です。

**機能カバレッジ**：レビュー（コメントスレッド、トラッキング変更モード、受理 / 拒否、変更バー、レビューペイン）、参照（目次、フッター脚注、キャプション SEQ、相互参照 REF / PAGEREF、F9 フィールド更新）、ヘッダー/フッター、単一／二重取り消し線、カーニングとスタイル継承、コンテキストスペーシング、水平文字スケール 1% から 600%、文字間隔の拡張と圧縮、記号付きベースラインシフト、上付き/下付き文字、OOXML ハイライトパレット、継承されるテーマカラー、ページをまたぐテーブルとヘッダ行の繰り返し、フローティング画像（切り抜き、反転、回転、alt テキスト）。

**最も重要な正直さ**：ドキュメントは自分は何なのかを明示しています。

> これは制限付きエディタのプロトタイプです。ページプレビューには保存された単一セクションのサイズ / 余白と内蔵の Noto Sans フォントを使用しており、**ネイティブ DOCX レイアウトの完全な再現ではありません**。フィールド、コメント、トラッキング変更、複数セクション、入れ子テーブル、フローティング画像、自動段落間隔などサポートされていない構造は、編集に入る前に拒否されます。

最後の文が鍵です。**編集前に明確に拒否するほうが、ユーザーが編集後に内容が飲み込まれたことに気づくよりよい。**

### 3.4 Teamchat：機能リストより権限設計を見るべき

Slack の代替品、1,292 行の README ののうち、権限マトリクスに大きな紙幅が割かれています：

**ロール**：owner、admin、member、guest。ゲストは特定の 1 つのチャンネルに個別に招待され、招待リンクと招待コードは形が同じで、失効の挙動が同じで、ブルートフォース予算も同じです。**ゲストは自分がいるチャンネルと、そのチャンネルを共有している人しか見できず**、チャンネルの閲覧・参加・作成はできません。誰を招待することも、、見知らぬ人にメッセージを送ることもできません。これらはすべて worker がすべてのルートで強制実行しています。

**管理者はチャンネルの発言を制限できます**（お知らせチャンネル：全員読み取り専用とリアクションのみ、サイドバーにスピーカーアイコンを表示）、**スレッドの返信権限も個別に設定できます**（全員 / 管理者のみ / オフ）。これも worker が強制実行し、メンバーは自分で送信した古いメッセージを編集・削除できます。

**配信の正直さ**：原文は "Delivery is honest: a Puter worker only runs while handling a request"（worker はリクエストを処理している間だけ動作する）と書いています。口上の約束は約束にならない。

### 3.5 Whiteboard：「ファシリテーター型ワークショップ」を製品に組み込む

ホワイトボードは絵を描くだけではありません。会議のファシリテーション機構一式が組み込まれています：

- **リアルタイムリアクション**：8 種類の絵文字がキャンバス上に浮かび、ボードにも undo 履歴にも書き込まれず、リアルタイムの peer 接続が必要
- **挙手**：挙手の順番に表示され、スクリーンリーダーが変化を読み上げ、離脱すると自動的に下がる
- **ドット投票**：Miro 風のオブジェクトへのドット投票に加え、バッジ投票とアクセシブルなリスト投票にも対応、結果は公開時刻まで秘匿可能、時間制限あり、CSV / JSON にエクスポート可能
- **プライベートモード**：各人の新規付箋は他の人には裏向きのまま、ファシリテーターがまとめて公開するまで
- **アジェンダランナー**：順序付きフレームが所要時間と説明付きのステップになり、再利用可能なコンテンツとして保存すると、ファシリテーターの台本に元の所要時間を保ったまま挿入できる
- **追従デモ**：追従者は現在のスライドしか見られず、フレームの端でクリップされる

匿名モードはアプリ内で内容と氏名を隠しますが、README は明記しています。**これらは暗号化ではありません**。

### 3.6 CAD：幾何カーネルは自作

```
src/
  core/                # フレームワークなしのモデル（ユニットテスト可能）
    schema.js            # エンティティと図面のデータモデル
    drawing.js           # undo/redo 付きトランザクショナル描画
    spatial.js           # ピック・選択・スナップ用の R-tree 空間インデックス
    tessellate.js        # エンティティから表示リストへ（スタイル、ブロック、文字、塗りつぶし）
    geom/                # 幾何カーネル：交差、オフセット、トリム、 面取り...
    text/                # ストロークフォントとテキストレイアウト
```

コマンドラインはオートコンプリート、座標の複数記法（`x,y`、`@dx,dy`、`@distance<angle`、直接距離、角度ロックの `<angle`）、フィートインチと分数の入力、12 種のオブジェクトスナップ、極座標トラッキングをサポートしています。DXF のインポート/エクスポート（R2000 ASCII）は Web Worker 内で行われます。

### 3.7 PDF：「削除」を本当にやり切る

その安全な削除ロジックは非常に抑制的に書かれています：

> マークされたテキスト、画像の画素、描画、リンク、注釈は、上書きされるのではなく**ファイルから除去されます**。マークされたフォームフィールドは、出現するすべての箇所から除去されます。通常の処理ができない内容は一覧に出し、確認できるようにしています。

OCR は Tesseract によりデバイス上でローカル実行され、不可視のテキストレイヤーを追加することで、スキャン文書が検索可能・選択可能になります。デジタル署名は増分更新で追記され、先の署名も有効のままです。

## 四、デザイン哲学：なぜこれが教材になるべきか

### 4.1 「フレームワークなし」は節約ではなく、立場である

React が 40 万行あること自体は問題ではありません。問題は**それを必要とする理由を説明できるか**です。このプロジェクトの答えは「不要」です。

Vanilla JS + Vite の結果は、フレームワークのアップグレードによる破壊的変更なし、hydration 問題なし、仮想 DOM と実 DOM の不整合なし、そしてビルド成果物がそのまま読解できるコードであるということです。長期保守され、監査される可能性があり、他の実行環境へ移植される可能性があるプロ級ソフトウェアにとって、これはより安全な選択です。

**特に最も複雑な 2 つのアプリ、Documents と 3D** は、「フレームワークを書かない」という決定の最大の受益者です。ドキュメントエンジンはレンダリングとシリアライズの境界を精密に制御する必要があり、3D エンジンは WebGL のライフサイクルを直接制御する必要があります。この 2 つのシーンでフレームワークは邪魔になるだけです。

### 4.2 「バックエンド即プラットフォーム」：複雑さを 1 箇所に集める

すべてのアプリに "no server of its own" と書かれています。これは 3 つの帰結を生みます：

1. **アプリ側はゼロ設定**：環境変数も、API Key も、DB マイグレーションもありません。静的ホスティングで足ります。
2. **データ側は統一**：アカウント、権限、ストレージ、KV、Worker、デプロイがすべて同じ抽象を通るため、新規アプリの追加コストは極めて低い
3. **コラボレーションは自然に**：ストレージと Worker がプラットフォーム側にあるため、複数人での同期、データ整合性、権限チェックといった最も難しい部分はプラットフォームが統一して提供してくれる

**代償は、アプリがプラットフォームに強く依存することです。** これは明確なトレードオフで、無料のランチではありません。Puter.js を使うということは、あなたのアプリは Puter から独立して存在できないということです。

### 4.3 「黙って失わない」はプロジェクトを貫く鉄則

この原則は複数のアプリに繰り返し現れるので、单独に抜き出しました：

- Documents：*"非対応の特性を含むドキュメントを開く場合はベストエフォートで処理する……非対応の内容を失う可能性があるセーブハンドラを付けないこと"*
- 3D：*"サポートされていないデータは、黙って失われるのではなく報告されます"*
- PDF：*"通常の処理ができない内容は一覧に出し、確認できるようにしています"*
- Records（alpha）：*"機能は変わり、データは失われる可能性があります"*
- CAD（alpha）：*"特性は変わり、図面は失われる可能性があります、自分で控えを残してください"*

**これは「ユーザーのデータ安全」を「機能のデモ効果」より前に置く原則です。** 大部分のスタートアップにはできません。alpha 段階の alpha とは、すべてのボタンを光らせることだからです。しかしここでは README の第 1 段落で「依存しないでください」と書き、安全に処理できない操作はコードの段階で拒否しています。

### 4.4 「ドキュメント即仕様」

documents のドキュメント構成を見ると何をしているか見てわかる通りです：

```
src/documents/docs/
  conformance.md                          # 準拠性の記録
  docx-parity-roadmap.md                  # Word との乖離ロードマップ
  paragraph-property-coverage.md          # 段落プロパティのカバー状況
  run-property-coverage.md                # 文字プロパティのカバー状況
  field-code-coverage.md                  # フィールドコードのカバー状況
  table-property-coverage.md              # テーブルプロパティのカバー状況
  theme-structure-coverage.md             # テーマ構造のカバー状況
  shape-fill-outline-coverage.md          # 図形の塗りつぶしと輪郭のカバー状況
  comment-revision-property-coverage.md   # コメント／トラッキング変更プロパティのカバー状況
  ...（カバー状況ドキュメントは 20 以上）
  parity/                                 # 機能領域で分割した乖離リスト
    chrome.md, collab.md, design.md, draw.md, format.md,
    insert.md, mailings.md, pictures.md, references.md,
    review.md, tables.md, views.md
```

しかもルールは厳格です：

> 各エディタ機能について、該当する ECMA-376 / OOXML 条項とサポート済みサブセットを記録する。振舞いのテストと独立に生成した DOCX fixture を用意し、`npm run check:conformance` でブラウザのエクスポートを検証する。**機能の完成を宣言する前に、仕様レビューで見つかった差異を修正する。残った乖離は明示的に記録すること。schema を通ることは、完全な OOXML 準拠やレイアウト忠実度を意味しない。**

**「schema を通ることはレイアウト忠実度を意味しない」** という一文は、このドキュメント群の中で最も価値が高い一文です。ソフトウェアエンジニアリングによくある自己欺瞞を突き破ります。データモデルが合ったからといって、レンダリング結果が正しいとは限らない。

同程度の厳密さは Documents のテスト構成にも表れています。`tests/fixtures/` だけで数百個のディレクトリがあり、それぞれが細かな 1 つの機能に対応しています（`border-round-continuous`、`cjk-wrap`、`script-line-boxes`、`para-line-units-default-24`……）。一部の fixture ディレクトリには自らの README があり、その機能が何をするかを説明しています。

### 4.5 「AI は機能であり、主役ではない」

このプロジェクトで最も逆行している点は、**ほとんど AI について語らない**ことです。

Spreadsheet では AI はセル関数 `AI()` です。3D には AI アシスタントのサイドバーがあります。Whiteboard には AI 連携があります。しかしリポジトリ全体の物語の主線は「世界のソフトウェアの再構築」であり、AI は複数のアプリにおける 1 つの能力にすぎません。

「AI-native」「agentic」をタイトルに冠する今の潮流のオープンソースプロジェクトと比べると、このプロジェクトは昔ながらの職人のように見えます。**しかし、労力を注いだ場所には全力を注いでいます**：510 個の Excel 関数、4 万行の 3D ジオメトリとレンダリング、きれいなデータ構造、2,000 を超えるテスト fixture。これらは AI では書けません。数十年の領域知識の蓄積と忍耐が必要だからです。

### 4.6 「ライセンスコンプライアンスを CI に書き込む」

`check:licenses` はリマインダではなく、ビルドを止める門です（`prebuild` フック）。しかもルールは「チェックを通すためにホワイトリストを緩めること」を明確に禁じています。

AI が大量のコードを生成できる時代において、ライセンス汚染は最も起こりやすいコンプライアンス事故です。このルールはまさに今、必要なときに届きました。

## 五、まとめ：移行可能な 8 つの観点

**観点 1：プロ級ソフトウェアの堀はインターフェースではなくデータ構造にあります。** 3D の 40 万行のうち中核は `data/types.ts` のデータブロック表（objects、meshes、materials、node_groups、actions）と依存グラフ評価です。UI は殻で、データモデルが命。AI はインターフェースを書く手助けはできますが、成熟したドキュメントオブジェクトモデルは書けません。

**観点 2：「サーバレス」は「アーキテクチャ無し」ではなく、アーキテクチャへの投資を集中させるということです。** このプロジェクトは各アプリでユーザーシステム・権限・ストレージを繰り返し実装するのではなく、これらをプラットフォーム層に沈めて差別化機能に集中しました。プラットフォーム型スタートアップの標準的な道筋ですが、ここまで徹底するオープンソースプロジェクトは滅多にありません。

**観点 3：正直な劣化は、無茶な互換より価値があります。** Documents は非対応の構造を編集前に拒否する方が、「開いたように見えるが保存したら内容が失われる」という嘘の互換よりもよいと選びました。同じ判断力は 3D が `.blend` のエクスポートに専ら向いていることや、CAD が alpha を明示していることに現れています。**製品への信頼はこうやって積み上がります。**

**観点 4：ドキュメントの質がプロジェクトの上限を決めます。** Spreadsheet の 1,200 行の README はそれ自体が製品説明書であり、Documents の 20 を超えるカバー状況ドキュメントはエンジニアリング資産です。ほとんどのオープンソースプロジェクトの README にある「Contributing welcome!」の空白と比べれば、このプロジェクトのドキュメント密度は桁違いに高い。

**観点 5：テスト fixture はユニットテストよりも実際の複雑度に近づく。** Documents は細かな組版機能ごとに独立した fixture ディレクトリを作るため、大きな 1 つのテストファイルよりも回帰箇所を特定しやすい。**機能軸でテストを分割するほうが、関数軸で分割するより、バグが 발생하는実態に近い。**

**観点 6：「一貫性」を CI 契約にする。** `amplify.yml` はすべてのアプリにエントリを要求し、`customHttp.yml` は「エントリがなければデプロイ失敗」と明記し、`check:licenses` は `prebuild` に掛かる。**ルールは wiki ではなく設定ファイルに書く。** wiki は古びますが、CI は古びません。

**観点 7：AI はファイルフォーマットの中で citizen として一等地を占めるべきです。** Excel 関数としての `AI()`、組み込み関数としての `TRANSLATE()` は、「AI サイドバーを追加する」より有用です。ユーザーが欲しいのは**具体的なワークフローの中の 1 ステップ**であり、切り替える必要のある別ツールではないからです。

**観点 8：このプロジェクトに対する最も理性的な使い方は、製品ではなくアーキテクチャの教科書として扱うことです。** 序幕にもある通り「Early alpha」「do not rely on it for real projects yet」。したがって正しい読み方はこうです。**AGENTS.md、ARCHITECTURE.md、conformance.md を読んだうえで、自分に実際の事業上の制約がある場面で、その判断をコピーする。コードだけをコピーするのではありません。**

## 六、経営者の視点：このコードはビジネスとどう関係するのか

ここまではすべてエンジニアリングの視点です。商売をする人はこう問うかもしれません。これは私に何の役にするのか。

**第一に、これは実際の経験と現金で手に入れた「機能リスト」です。** 53 個のアプリは、個人の生産性から企業の運営までチェーン全体をカバーしています。何年이나このカテゴリでやっていて、 satisfactory なオープンソースの選択肢が見つからなかったなら、このリストを見て、すぐに出発点が見つかるかもしれません。

**第二に、ひとつの事実が証明されています。ソフトウェアの生産コストは崩壊していますが、どの部分が崩壊するのかをはっきりさせる必要があります。** 40 万行の 3D エンジン、25 万行の PPT エンジンの開発コストは AI の補助下で下がり続けます。**しかし Spreadsheet の 510 個の関数の境界ケース、Documents の数百の fixture の裏にある仕様知識は、AI が強くなっても自動的に生まれては来ません。** AI は実装は書けますが、「どの仕様条項をカバーすべきかを知っている」ことまでは書けません。

**第三に、「バックエンドを書かない」ことが実行可能なアーキテクチャスタイルになりつつあります。** もしあなたのビジネスで各アプリが自分のユーザーシステム・権限・ストレージを 1 セットずつ組み立てているなら、3 つ目のアプリで忍耐は尽きます。このプロジェクトの方法は、それらをプラットフォーム層に沈めることです。**SaaS を行う経営者にとって、これは技術選定の好みではなく、コスト構造の組み替えです。**

**第四に、最も価値高い点：データ主権はエンジニアリング対象にできます。** 「あなたのファイルはあなたのクラウドにある」は更新时间のように聞こえますが、実装レベルでは具体的な意思決定の集まりです。独自フォーマットではなく本物の `.xlsx` を保存すること、自前の構造ではなく本物の `.docx` を使うこと、黙って失わないこと、エクスポート経路を完全にすること。企業向けのサービスを行う経営者にとって、**これは顧客がロックインされず、产品がプラットフォームの方針変更に縛られないことを意味します。**
