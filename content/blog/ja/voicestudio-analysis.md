# VoiceStudio：ローカル・オープンソース音声ワークステーション——16 種の TTS + 11 種の ASR エンジンのアーキテクチャ解説と実践チュートリアル

> **プロジェクト URL**：https://github.com/debpalash/VoiceStudio
> **ライセンス**：AGPL-3.0（アプリケーションコード）；ダウンロードしたモデルは各上流ライセンスを保持
> **一言で言えば**：VoiceStudio は完全ローカルで動作するオープンソース音声プラットフォーム。音声クローン、ボイスデザイン、動画吹き替え、ディクテーション、転写、オーディオブック制作をカバーし、646 言語をサポート。アカウント、API キー、サブスクリプションは不要。

---

## 一、プロジェクト概要

### 1.1 ポジショニング

VoiceStudio（旧称 OmniVoice-Studio）は ElevenLabs のローカル代替を目指す。違いは機能数ではなくデータパスにある：音声とテキストはデフォルトでローカルに保持され、ネットワーク機能は明示的に有効化するオプションであってデフォルトの動作ではない。

| 次元 | VoiceStudio | ホスト型音声サービス |
|------|-------------|--------------|
| 適用場面 | プライバシー重視、オフライン、セルフホスト、高スループットの作業 | すぐ始められる、モデル管理不要 |
| データパス | デフォルトはローカル。リモート機能は明示的に有効化 | 音声とテキストはサービス提供者が処理 |
| コスト | ソフトウェアは無料、ハードウェアは自前 | サブスクリプション、ポイント、従量課金 API |
| オフライン使用 | モデルダウンロード後に利用可能 | 通常ネットワーク必須 |
| カスタマイズ余地 | ソースコード、エンジン、モデル、API、ルーティングすべて公開 | サービス提供者の選択肢に限定 |
| 保守責任 | ユーザーが更新、ディスク、算力を担当 | サービス提供者がインフラを担当 |

### 1.2 コアデータ

- 16 種の TTS エンジン、11 種の ASR エンジン。Model Catalogue で Ctrl/Cmd+E で切り替え
- 646 言語の TTS カタログ（実際のカバー範囲と品質は選択したエンジンに依存）
- プラットフォーム：macOS 13.3+（Apple Silicon）、Windows 10/11 x64、Linux x86_64（glibc 2.39+）、Docker
- 算力：CUDA、Apple Silicon MPS/MLX、ROCm（Linux）、CPU、オプションのリモート Worker
- インターフェース：デスクトップアプリ、ローカル REST/SSE/WebSocket API、OpenAI 互換オーディオ API、MCP Server
- ストレージ：音声、プロジェクト、設定、出力はデフォルトですべてローカル

### 1.3 機能一覧

| 機能領域 | 内容 |
|--------|------|
| 音声クローン | 短い参照音声でのゼロショット合成。3 秒で使用可能、5–15 秒でさらに良い結果 |
| ボイスデザイン | 年齢、アクセント、音高、スタイルをテキスト指示で記述し、新しい声を生成 |
| 動画吹き替え | 転写 → 翻訳 → 話者保持 → 合成 → 動画エクスポート |
| ストーリーとオーディオブック | 複数キャラクターの脚本、EPUB/PDF インポート、チャプター単位のレンダリング、.m4b エクスポート |
| ディクテーションウィジェット | システムワイドショートカット、リアルタイム転写、オプションのローカル LLM によるテキスト整形 |
| ボーカル分離 | Demucs で音声と背景音を分離 |
| 話者分離 | Pyannote と WhisperX の話者ラベリング |
| バッチキュー | 大量の音声/動画タスクをキューイング + ディレクトリ監視 |
| モデルカタログ | TTS/ASR/LLM モデルのインストール、アンインストール、選択、ルーティング |
| GPU 自動検出 | CUDA / MPS / ROCm / CPU のルーティング。エンジンごとに個別チェック |
| AI ウォーターマーク | AudioSeal で合成音声を埋め込みと検出 |
| MCP Server | Claude Code、Cursor などのクライアントに合成・転写ツールを提供 |
| 診断 | 自己チェック、エラーログ、マスキング済みサポートパッケージ |

### 1.4 プロジェクト構造

```
frontend/src-tauri/    Tauri v2 デスクトップシェル（Rust）：ウィンドウ、トレイ、ショートカット、アップデーター
frontend/src/          React UI、Zustand 状態管理、API とイベントクライアント、i18n
backend/api/           REST ルート、スキーマ、認証境界、ストリーミング出力
backend/services/      生成、吹き替え、音声処理、永続化
backend/engines/       分離されたオプションのエンジンアダプター
backend/worker/        認証付きリモート算力とタスク転送
omnivoice_data/        プロジェクト、音声、設定、ログ、SQLite 状態
scripts/ deploy/       開発、パッケージング、コンテナ、リリース、CI
```

アーキテクチャの層構造：Tauri デスクトップシェルが IPC で React UI に接続。UI は localhost:3900 の HTTP/SSE/WebSocket で FastAPI バックエンドに接続。バックエンド内部はエンジンレジストリ、吹き替え/音声/長文パイプライン、OpenAI 互換 API と MCP Server で、状態は SQLite + Alembic マイグレーションに保存される。

## 二、詳細チュートリアル

### 2.1 インストール

| プラットフォーム | パッケージ | 説明 |
|------|-----|------|
| macOS 13.3+ | Apple Silicon DMG | 初回起動時に右クリック → 開く で Gatekeeper を通過 |
| Windows 10/11 | x64 MSI | current-user ビルドを選べば管理者不要でインストール可能 |
| Linux | AppImage | x86_64、glibc 2.39+ |
| Docker | 複数プロファイル | CUDA、ROCm、CPU、Worker 専用 GPU |

Docker ワンライナー起動：

```bash
docker run -d -p 127.0.0.1:3900:3900 \
  -v omnivoice-data:/app/omnivoice_data \
  --name voicestudio \
  palashdeb/omnivoice-studio:stable
```

初回起動時に管理済みの Python 環境が作成され、デフォルトモデルがダウンロードされる。以降は再利用される。インストールしたくなければ Google Colab ノートブックでクラウド体験も可能（注意：Colab はリモート算力のため、アップロードした音声はローカルに残らない）。

### 2.2 5 分で音声クローンを動かす

1. VoiceStudio を開く → Voice Cloning
2. クリーンな人声サンプルを追加。3 秒で使用可能。5–15 秒でさらに良い結果
3. テキストを入力、言語を選択、Generate をクリック

注意：ゼロショットクローンでは、参照音声は「トレーニングデータ」ではなく「プロンプト」である。サンプルの条件：一人だけ、マイクに近い、音楽・ノイズ・残響なし、出力したいトーンと一致。長いサンプルが必ずしも良いわけではない。

### 2.3 ソースからの実行と開発

前提：Node 20+/Bun、Python 3.11+。

```bash
git clone https://github.com/debpalash/VoiceStudio.git
cd VoiceStudio
bun install
bun run desktop        # デスクトップ版。初回は uv で Python 依存を自動セットアップ
bun run dev            # ブラウザ UI
```

診断コマンド：

```bash
uv run python backend/main.py --diagnose --deep
```

### 2.4 OpenAI 互換 API

OpenAI クライアントの base_url をローカルバックエンドに向けるだけで既存コードが流用できる：

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:3900/v1", api_key="local")
with client.audio.speech.with_streaming_response.create(
    model="tts-1",
    voice="<profile-id>",
    input="Made on my own hardware.",
    response_format="wav",
) as response:
    response.stream_to_file("speech.wav")
```

cURL テスト：

```bash
curl http://localhost:3900/v1/audio/speech \
  -H "Content-Type: application/json" \
  -d '{"model": "tts-1", "input": "Made on my own hardware.", "voice": "default", "response_format": "wav"}' \
  --output speech.wav
```

| エンドポイント | 用途 |
|------|------|
| POST /v1/audio/speech | TTS。mp3/opus/aac/flac/wav/pcm を出力 |
| POST /v1/audio/transcriptions | STT。json/text/verbose_json/srt/vtt を出力 |
| WS /v1/audio/transcriptions/stream | リアルタイム PCM/WebM 転写。中間結果とセッション終了イベントを含む |
| GET /.well-known/voicestudio-speech | HTTP/WebSocket/MCP/ディクテーション制御トランスポートの検出 |
| GET /v1/audio/voices | ローカルの音声プロファイルとエンジンを一覧 |

### 2.5 MCP 接続

VoiceStudio は `http://localhost:3900/mcp` に MCP Server をマウントする。ツールは `generate_speech`、`clone_voice`、`transcribe` など：

```json
{
  "mcpServers": {
    "voicestudio": {
      "url": "http://localhost:3900/mcp"
    }
  }
}
```

stdio トランスポートを必要とするクライアントは内蔵 shim を使う：

```json
{
  "mcpServers": {
    "voicestudio": {
      "command": "python",
      "args": ["-m", "backend.mcp_shim"],
      "cwd": "/path/to/VoiceStudio"
    }
  }
}
```

### 2.6 エンジン選択：ハードウェアに合わせる

| ハードウェア | 推奨 TTS | 推奨 ASR | 理由 |
|------|----------|----------|------|
| Apple Silicon (M1–M4) | MLX-Audio、OmniVoice (MPS) | MLX Whisper、Parakeet MLX | ユニファイドメモリ。macOS で最低遅延 |
| NVIDIA GPU (8 GB+) | OmniVoice、CosyVoice 3 | WhisperX | 高忠実度ゼロショットクローン、語レベルタイムスタンプ |
| 低 VRAM / CPU のみ | PocketTTS、Sherpa-ONNX、KittenTTS | Moonshine、Faster-Whisper (int8) | 低メモリ、CPU 推論最適化 |

デバイスは自動検出（CUDA/ROCm/MPS/CPU）され、Settings → Performance & Device または `OMNIVOICE_DEVICE` で手動固定も可能。

## 三、設計思想

### 3.1 Local-first：ローカルファーストはデフォルトの状態であり、マーケティング用語ではない

コアワークフローはローカルに残る。ネットワーク機能（リモート Worker、外部 ASR エンドポイント）は明示的に有効化するオプションである。ループバック API 呼び出しはキー不要。リモートアクセスには PIN または API キーの共有が必要。ループバック ASR は HTTP で音声を機外に出さずに利用できる。ループバック以外のエンドポイントは HTTPS を強制し、リダイレクトを追跡しない。解析機能はデフォルトでオフで、有効にしてもホワイトリスト内のコンテンツなしメタデータのみを送信する——テキスト、音声、ファイル名、プロジェクトデータは送信しない。

### 3.2 エンジンはリストではなくポジション：engine-acceptance の採用メカニズム

VoiceStudio には 16 種の TTS エンジンが内蔵されている。エンジンの数は「各エンジンが各プラットフォームで動作する場合」にのみ資産であり、そうでなければサポートキューの山積みで、「初回起動から使える」という約束を損なう。したがって新しいエンジンは「ポジションへの採用」であり、「リストへの追加」ではない。

**ポジション表**（各ポジションには在任者が一人だけ）：

| ポジション | 在任者 |
|------|------|
| 最高のゼロショットクローン品質 | omnivoice |
| 最広の言語カバー | omnivoice |
| デフォルトモデル障害の隔離 | omnivoice-subprocess |
| 最速 CPU レンダリング / 最低遅延 | 空席 |
| 最高の中/日の表現力 | cosyvoice、indextts2 |
| CPU リアルタイム英語、極小サイズ | kittentts、supertonic3 |
| 最高の転写精度 | whisperx、faster-whisper |
| 最速の Apple Silicon 転写 | parakeet-mlx、mlx-whisper |
| 転写障害の隔離 | faster-whisper-isolated |

提案は「データで在任者からポジションを奪う」か、「誰もカバーしていないポジションを請負う」のいずれかでなければならない。「ベンチマークが悪くない」はポジションではない。

**採用基準**。一つでも欠ければ却下：

1. ポジション名を明記——どのポジションを奪うのか、なぜ在任者ではカバーできないのか；
2. ライセンスがクリーンで商用利用可能。重みとコードの両方を確認——この条件が最も多くの提案を終わらせる；
3. 全プラットフォームで利用可能か、明示的なオプションであること——CPU パスが必須。単一の加速カードしか動かないエンジンは、クラッシュではなく降格して動作可能でなければならない；
4. 既存のアダプターインターフェース（TTSBackend / SubprocessBackend）に適合し、コアパイプラインを変更しない。依存の衝突は sidecar で処理；
5. 同一 PR に CI スモークテストを添付。GPU がなければ sidecar をスタブ化できる；
6. 12 か月の steward（責任者）を指名。steward がいなければマージしない——これが「広さ」と「負債」の境界線；
7. 需要の証拠を提示：実際のリクエスト、実際のワークフロー、実際のユーザー。

**退出メカニズム**：2 バージョン連続で steward がおらずスモークテストを通過していないエンジンはアーカイブされる。アーカイブは評価ではなく、生き残るエンジンの信頼性を保つ手段である。**インターフェースに適合しないエンジンはツリーの外で生存できる**——アダプターインターフェースは公開されており、インストールすれば id で選択可能。プロジェクトは「良い外部エンジンをリンクする」ことを「半分しか保守されていない内部エンジンを抱える」より優先する。

### 3.3 能力の境界は明示的に失敗し、静かに降格しない

クローン非対応のエンジンは、吹き替えや音声ロックのバッチタスクで参照話者を保持できない。VoiceStudio の対応は**タスクを拒否する**ことであり、こっそりエンジンを替えることではない。予測可能な動作は、表面的な「なんでも動く」より優先される。

### 3.4 エージェント時代のためのインターフェース

同一のバックエンドが REST/SSE/WebSocket、OpenAI 互換オーディオ API、MCP Server、Rust 製ディクテーション制御 sidecar（Herdr、コーディングエージェント、VS Code、TUI がシステムワイドのディクテーションフローを起動可能）を同時に提供する。プロジェクトはリポジトリにエージェント skill も同梱している（`npx skills add debpalash/VoiceStudio`）。設計の前提は：人間は唯一の消費者ではなく、AI エージェントも一等のユーザーである。

### 3.5 責任の境界は製品に書き込む

AudioSeal の知覚不能ウォーターマークをデフォルトで統合し、合成音声の検出に使用する。使用前には話者の明示的なクローン承認が必要。アンインストールスクリプトは dry-run を先に実行してから削除する。倫理的要件はドキュメントの提案ではなく、機能の形で存在する。

## 四、まとめ：考察と結論

### 4.1 6 つのコアな考察

1. **ローカルファーストはアーキテクチャ上の決断であり、配布方式ではない。** データパス、認証境界（ループバックはキー不要/リモートは PIN 必須）、HTTPS 強制、解析のデフォルトオフ——すべての詳細に実装がある。プライバシーは設定項目ではなくデフォルトの状態。

2. **「エンジンが多いこと」は負債管理の問題。** engine-acceptance メカニズムはエンジン採用をポジション競争に変える：ポジション命名、データによる奪取、ライセンスの一票拒否、12 か月の steward、連続して保守されなければアーカイブ。このルールは複数のサードパーティモデルを統合したいあらゆるプロジェクトに適用できる。

3. **静かな降格はシステムの信頼を蝕む。** クローンできないエンジンが注文を受けてこっそり別エンジンに切り替われば、ユーザーが得るのは予測不能な結果。タスクを拒否する方が誤った出力より安い。

4. **アダプターインターフェースの公開 = エコシステム拡張はメインリポジトリを通らなくてよい。** ツリーの外のエンジンは id だけで接続できる。プロジェクトは「半分しか保守されていない内部エンジンを抱える」代わりに「良い外部エンジンをリンクする」ことで、保守面を縮小する。

5. **OpenAI 互換 API は最安の統合経路。** 既存の OpenAI クライアントは base_url を 1 行変えれば接続でき、エコシステムの移行コストはほぼゼロ。ツール系インフラにとって、主流プロトコルとの互換は新プロトコルの発明より得策。

6. **AGPL + モデルの層別ライセンスは誠実な設計。** アプリケーションコードは AGPL-3.0。デフォルトの OmniVoice 重みは CC-BY-NC（商用制限あり）、一部エンジンには MAU/収益でトリガーされる個別ライセンスがある（例：IndexTTS 2.5 は MAU が 1 億を超える場合に Bilibili の書面承認が必要）。アプリのライセンスはモデルのライセンスに取って代わらず、ユーザーは画面上でその注意を確認できる。商用利用前にエンジンごとに重みの条項を確認する必要がある。

### 4.2 適用場面

| 場面 | 推奨 |
|------|------|
| 個人クリエイターの吹き替え/オーディオブック | デスクトップ版を直接インストール。デフォルト OmniVoice で開始 |
| プライバシー重視の業界（医療、法律、メディア） | ローカルワークフロー + ループバック API。音声は機外に出さない |
| 高スループットのバッチ転写/合成 | Docker + バッチキュー + リモート Worker で算力を拡張 |
| エージェントに音声能力を追加 | MCP Server か OpenAI 互換 API で半日で接続 |

### 4.3 限界と注意点

- ベータ段階。公式は main ブランチより最新リリースの利用を推奨；
- 商用ライセンスはエンジンごとにモデルの重み条項を確認する必要がある。デフォルトエンジンの重みは CC-BY-NC；
- Intel Mac はローカル Python バックエンドを実行できない（PyTorch に利用可能な wheel がない）。リモートバックエンドへの接続のみ；
- 646 言語はカタログの上限で、実際の品質はエンジンによって変わる。マイナー言語は実測が必要；
- リモート Worker と外部 ASR エンドポイントを有効にするとデータはローカルを離れ、境界は設定次第。

## 五、結語

VoiceStudio のコア思想は一言に圧縮できる：**音声能力を、ユーザーが完全に制御できるローカルインフラにする。** ローカルファーストのデフォルト状態でプライバシーの問いに答え、ポジション制のエンジン採用で保守の問いに答え、明示的な失敗で信頼の問いに答え、OpenAI 互換と MCP でエコシステムの問いに答える。4 つの経路は同じ目標を指す：初回起動から使え、長期運用で足元をすくわれない。
