# 時空間結合性：動的ソフトウェアアーキテクチャを再定義するプログラミングパラダイム

## プロジェクトと論文の紹介

**paper** は cordiverse オーガナイゼーションが公开发表した学术予印本論文（2026年8月草稿）で、**動的結合（Dynamic Composition）** と呼ばれるプログラミングパラダイムを提案しています。これは现代的なソフトウェアアーキテクチャにおけるコンポーネント間の動的相互作用と依存関係管理の根本的な問題を解決することを目的としています。

### 核心的な問題：なぜ動的結合が必要か？

従来のソフトウェアアーキテクチャはモジュール性と結合可能性を強調していますが、実行時にコンポーネントを動的に読み込み、置き換え、結合することには显著な不足があります。マイクロサービスアーキテクチャからフロントエンドフレームワークのホットモジュール置換（HMR）、プラグインシステムまで、現代のアプリケーションシナリオはすべて実行時結合に更高的要件を要求しています。

論文は、現在のプログラミングパラダイムが以下のシナリオの處理に苦戦していると指摘しています：

- **ホットモジュール置換**：アプリケーションを再起動せずにコードモジュールを動的に更新
- **プラグインシステム**：実行時に機能拡張を読み込み、アンロード
- **反応的依存関係管理**：依存関係の変化時に依赖側に自動更新
- **トランザクショナルロールバック**：コンポーネントが失敗したときにすべての副作用を完全に元に戻す

## コア設計哲学

### 2つの直交次元

論文は、結合性の2つの根本的な次元を識別し、それらは相互に独立でありながらシステムの表現能力を共同して決定します：

### 1. Temporal Composability（時間的結合性）

**時間的結合性**とは、コンポーネントを削除ときに**その副作用を完全に元に戻す**能力を指します。従来のリソース管理は取得と解放（acquire/release）のみを対象にしていますが、コンポーネントのライフサイクル中に生成されたより深い副作用は無視しています。

 예를 들어、コンポーネントが以下を実行した場合：
- グローバル状態を変更
- バックグラウンドタスクを作成
- イベントハンドラを登録
- ネットワーク接続を確立

時間的結合性が必要とするもの：そのコンポーネントを削除とき、これらの副作用は**完全に、予測可能に元に戻され**、コンポーネントが決して実行されなかったかのようにする必要があります。

### 2. Spatial Composability（空間的結合性）

**空間的結合性**とは、コンポーネント間の依存関係を**宣言し、反応的に管理する**能力を指します。コンポーネントシステムでは、コンポーネントは孤立していません，它们は他のコンポーネントが提供するデータとサービスに依存しています。

空間的結合性が关注するもの：
- コンポーネントがどのように依存関係を**宣言**するか
- 依存関係が**変化**したとき、コンポーネントがどのように**反応**するか
- 依存関係の変化がどのように依赖するコンポーネントに**伝播**するか

### なぜ2つの次元が必要か？

論文の核心的な主張は：**時間と空間の結合性は直交しており、互いに代替できない**ということです。

- 時間的結合性のみ：コンポーネントは安全に削除できますが、依存関係を管理できません
- 空間的結合性のみ：依存関係は宣言・管理されますが、元に戻すメカニズムがありません

両者を組み合わせで初めて真の動的結合システムを実現できます。

## コア概念の詳細

### Revertible Effects（可逆エフェクト）

#### 概念的起源

従来の **Effect** は、プログラムが実行中に外部の世界に产生する**目に見える影響**を記述します——ファイル操作、ネットワークリクエスト、状態変更など。Effect システム（Haskell の mtl、Effect-TS など）により、プログラマーは型安全な方法でこれらの副作用を追跡・管理できます。

**Revertible Effects** はこの基础上に、**逆変換（inverse transformation）の追跡**という重要な能力を追加しています。

#### 核心的なアイデア

各 Effect は「何をするか」を記述するだけでなく、**元に戻す操作（reverter）** のコンテキストも添付しています。コンポーネントを削除する必要があるとき、システムはこの元に戻す操作を実行して状態を恢复できます。

```typescript
// 概念的な例
interface RevertibleEffect<State, Effect> {
  perform: (state: State) => Effect;
  revert: (state: State, effect: Effect) => State;
}
```

#### 適用シナリオ

1. **データベーストランザクション**：未コミットの変更を自動的にロールバック
2. **UI状態管理**：ユーザー操作を元に戻す
3. **リソース取得追跡**：割り当てられたすべてのリソースを正確に解放
4. **監査ログ**：記録され元に戻せる操作履歴

### Reactive Coeffects（反応型コエフェクト）

#### 概念的起源

**Coeffect** の概念は関数型プログラミングから来ており、関数が実行するために**必要とするもの**——つまり関数の**コンテキスト依存**を記述します。例如、コンフィグファイルを読み込む関数はコンフィグデータIOSが必要」し、ロギングする関数は「ロガーIOS必要」です。

従来の Coeffect システムは**静的依存宣言**に焦点在家里ですが、**Reactive Coeffects** はこれを**動的、反応的な依存関係管理**に拡張しています。

#### 核心的なアイデア

コンポーネントが依存するコンテキストが変化したとき、システムIOSコンポーネントに**積極的に通知**し、コンポーネントがポーリング或いは手動で確認するのを待ちません。このパターンは反応型プログラミング（Reactive Programming）のアイデア借用ですが、依存性注入の领域に応用しています。

```typescript
// 概念的な例
interface ReactiveCoeffect<T> {
  // 依存関係を宣言
  dependsOn: () => T[];
  // 依存が変化したときのコールバック
  onChange: (newValue: T, oldValue: T) => void;
}
```

#### 従来の依存性注入との違い

| 機能 | 従来のDI | Reactive Coeffects |
|------|---------|-------------------|
| 依存関係解決のタイミング | 構築時 | 実行時に動的 |
| 変化通知 | なし | あり（プッシュモデル） |
| 依存関係追跡 | 明示的 | 暗黙的に宣言 |
| 遅延読み込みサポート | 限定的 | ネイティブサポート |

### Context Types（コンテキストタイプ）

#### Effect と Coeffect の統一

論文は **Effect**（コンポーネントの外部への影響）と **Coeffect**（コンポーネントの外部への依存）を **Context Types**（コンテキストタイプ）として統一する概念フレームワークを提案しています。

従来の effect/coeffect システムでは，这两个の概念は別々に處理されていました。Context Types は次のことを同時に表現できる統一された型システムを提供します：

- **生成されたエフェクト（produced effects）**：コンポーネントが生み出す副作用
- **消費されたコエフェクト（consumed coeffects）**：コンポーネントが必要とする依存関係
- **エフェクト追跡（effect tracking）**：ロールバックのために実行されたエフェクトを追跡
- **コエフェクト解決（coeffect resolution）**：依存関係を動的に解決し、变化を伝播

#### 形式的な定義

```typescript
// Context Type の概念的な形式
interface ContextType<S, E, C> {
  // 状態タイプ
  state: S;
  // Effect タイプ（可逆的なエフェクト）
  effects: RevertibleEffect[];
  // Coeffect タイプ（反応的な依存関係）
  coeffects: ReactiveCoeffect[];
}
```

## Cordis メタフレームワークアーキテクチャ

### フレームワーク概述

**Cordis**（ラテン語で「心臓」）は、論文のアイデアを実装した概念フレームワークで、動的結合理論を实践中どのように適用するかを示しています。

### コアコンポーネント

#### 1. コアライブラリ（@cordis/core）

最も基礎的なメカニズムを担当：
- **エフェクト追跡**：すべての可逆的なエフェクトを追跡
- **コエフェクト解決**：依存関係解決と変化の伝播を管理
- **コンテキスト管理**：実行時のコンテキスト状態を維持

#### 2. コンポーネントシステム（@cordis/component）

動的結合のための**結合メカニズム**を提供：

```typescript
// コンポーネント定義の例（概念的な）
const myComponent = component({
  name: 'my-component',
  // coeffects を通じて依存関係を宣言
  coeffects: [databaseService, configService],
  // エフェクトを提供またはトリガー
  effects: [loggingEffect],
  // コンポーネントロジック
  setup(ctx) {
    // 依存関係を使用
    const db = ctx.coeffects.databaseService;
    // 操作を実行
    ctx.effects.log('Hello');
  },
  // オプションのティアダウンロジック
  teardown(ctx) {
    // クリーンアップ作業、 effects は自動的に元に戻されます
  }
});
```

#### 3. 宣言型ローダー（@cordis/loader）

**宣言的にコンポーネントを読み込み、設定**するために使用：

- 宣言型依存関係：コンポーネントが何を必要とするかを記述、手動注入ではなく
- 設定調整：コンポーネントの設定と初期化順序を管理
- ライフサイクル管理：コンポーネントの作成、更新、破棄を処理

#### 4. ホットモジュール置換（HMR）機能

Cordis フレームワークは動的結合の實際的な応用である**ホットモジュール置換**機能を特に強調しています：

- **増分更新**：変更されたコンポーネントのみを更新、其他には影響なし
- **状態の維持**：更新プロセス中に必要な状態を維持
- **自動クリーンアップ**：古いコンポーネントのエフェクトを削除。新しいコンポーネントのエフェクトを適用

## 動的結合calculus

### Calculus of Dynamic Composition

論文は動的結合理論の**メタ理論（meta-theory）**記述である**動的結合Calculus（Calculus of Dynamic Composition, CDC）**を提案し、形式的な数学的基盤を提供します。

### Calculus のコア要素

#### 1. コンポーネント（Components）

コンポーネントは動的結合の基本単位で、各コンポーネントは以下を含みます：
- **インターフェース（Interface）**：コンポーネントが提供するサービスと必要とする依存関係を記述
- **実装（Implementation）**：コンポーネント的具体的なロジック
- **エフェクトトレース（Effect Traces）**：コンポーネントの実行過程中のエフェクトを記録

#### 2. コンポジター（Compositors）

コンポジターはコンポーネントがどのように結合するかを定義します：
- **直列結合（Sequential Composition）**：あるコンポーネントの出力が別のコンポーネントの入力になる
- **並列結合（Parallel Composition）**：複数のコンポーネントが独立して実行され、状態を共有
- **オーバーライド結合（Override Composition）**：新しいコンポーネントが古いコンポーネントを置き換え

#### 3. 元に戻すセマンティクス（Reversion Semantics）

コンポーネントを削除ときに何を定義します：
- 哪些エフェクトを元に戻す必要があるか
- 元に戻す順序是什么
- 部分的な元に戻す失敗をどのように處理するか

### 形式的な保証

動的結合Calculus は以下の形式的な保証を提供します：

1. **結合可能性定理**：結合されたコンポーネントは 여전히時間的/空間的結合性を維持
2. **元に戻す完全性**：コンポーネントを削除とき、すべてのエフェクトが完全に元に戻される
3. **依存関係の推移性**：依存関係の変化がすべての依赖側に正しく伝播

## 主要な洞察、まとめ、結論

### コアな貢献

1. **2つの直交次元の識別**：時間的および空間的結合性が動的結合の基礎を共同して構成

2. **Effect と Coeffect 概念の昇華**：
   - Revertible Effects が effect を「追跡」から「可逆的な追跡」に昇華
   - Reactive Coeffects が coeffect を「静的宣言」から「動的反応」に昇華

3. **統一された形式的なフレームワーク**：Context Types が effect と coeffect コンテキストを統一

4. **実践的なフレームワーク実装**：Cordis が理論の実用性を実証

### 重要な視点

> 「動的結合はコンポーネントをどのように書くかではなく、コンポーネントが実行時にどのように相互作用し、依存し、元に戻すかについてです。」

### 制限事項

論文は制限事項についても正直に触れています：

- 现在は**概念実証**のみで、パフォーマンスオーバーヘッドはまだ最適化されていない
- **形式的な証明**はまだ改良中
- **大規模システム**への拡張性はまだ検証が必要
- **実践的な適用例**はまだ十分にない

## 適用シナリオと実践的な意義

### 適用可能なシナリオ

1. **フロントエンドフレームワーク**
   - ホットモジュール置換（HMR）
   - 反応的状態管理（Redux のタイムトラベルデバッグなど）
   - プラグインシステム

2. **バックエンドサービス**
   - マイクロサービスアーキテクチャでの動的サービスオーケストレーション
   - ネストされたデータベーストランザクション管理
   - リソースの取得とクリーンアップの精密な追跡

3. **組込みシステム**
   - コンポーネントの決定論的読み込みとアンロード
   - リソース制約環境での精密なリソース管理

4. **IDE と開発ツール**
   - ライブプログラミング環境
   - 増分コンパイルと更新

### 実践的な意義

ソフトウェア開発者への実際の価値：

| 側面 | 現在の状態 | 動的結合導入後 |
|------|---------|--------------|
| コンポーネントのアンロード | 手動でリソースをクリーンアップ | 自動的に完全に元に戻す |
| 依存関係の変化 | 手動で更新を確認 | 自動的に反応的に通知 |
| ホット更新 | 限定的サポート | ネイティブサポート |
| 状態のロールバック | 手動で実装 | フレームワークレベルでサポート |

### 今後の展望

動的結合パラダイムは以下の方向的のための理論的基盤を提供します：

- より安全で推論しやすい実行時結合システム
- ネイティブにホットアップデートをサポートするプログラミング言語とフレームワーク
- 自動化されたリソース管理与清理
- 形式的に検証された実行時システム
