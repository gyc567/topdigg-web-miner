# スター6800のshuohao-skills：AIショートドラマの真の敷居は生成ではなく、「誰が品質ゲートをコードとして書けるか」

**結論から：** GitHubに、スター6800、フォーク960超のオープンソースプロジェクト`shuohao-skills`があります。これは小説1冊を、そのまま動画モデルに発注できるショートドラマの量産パッケージに変えるものです。7つのスキル、6つの制作ステージ、60本の品質ゲート、1600を超えるセルフテストのアサーション。

しかし、このプロジェクトが本当に価値があるのはその7つのスキルではなく、逆潮流のことに踏み切った点です。**「チェックリスト」をプロンプトから追い出し、決定論的なコードとして書き、モデルがゲートを通れなければ先へ進めないようにしたのです。**

今年読んできた中で、これが最もきれいな「AIのエンジニアリング化」のサンプルです。以下で内側から分解して説明します。プロジェクトが何で、どう実行し、何の設計思想が隠れているのか、そして——ショートドラマのビジネスを展開している人にとって、この仕組みには価値がいくらあるのかを。

---

## 一、プロジェクト説明：ショートドラマの生産を六段階に分けたファイル・パイプライン

`shuohao-skills`の作者は「爍皓」（X: `@eternityspring`）。ライセンスはApache 2.0、2026年8月に着手し、2ヶ月余りでスター6800に到達。ポジショニングは一文で言えます。

> 各種Agent向けのAIショートドラマ制作スキル集合。小説1冊から、そのまま生成パイプラインに渡せる制作素材まで。

特定のAgentランタイムには縛られません。Claude CodeとCodexは「サポートされている2つの例であって、前提ではない」という位置づけです——Agentが`SKILL.md`を読め、Nodeスクリプトを実行できれば使えます。

### 1.1 七つの構成要素

| Skill | 何をする | 品質ゲート |
|---|---|---|
| `novel-outline` | 小説をショートドラマ用アウトラインの五点セットに脚色する：脚色説明、人物表、快感ポイント表、各話概要、資産一覧 | 14本 |
| `novel-characters` | アウトラインで決めた役割を人物設定集にする：人物像、外見プロンプト、音声プロンプト、三面図の版面指示 | — |
| `character-refs` | 本物の人物参考図を生成する：正面全身アンカー＋派生ビュー | 検査ゲート |
| `novel-art` | アート設定集：シーン一貫性アンカー、照明状態バリエーション、物語小道具表、背景白の切り抜き可能画像 | 10本 |
| `novel-script` | 脚本：シーン＋ビート列（アクションと台詞の交互）、話ごとの長さの決定論的換算、台詞集 | 10本 |
| `novel-staging` | 各シーンの開始配置：誰がどの物のどちら側に、座るか立つか、どの方角を向くか | 8本 |
| `novel-storyboard` | 絵コンテ：セグメント（≤15秒）→ カット（2〜5秒のハードゲート）→ カット絵、H3とSeedanceの量産パッケージ | 18本 |

フローは次のようになります。

```
小説原文 → 大綱 → キャラクター → アート → 脚本 → オープニング立ち位置 → 絵割り → 動画本番パッケージ
                ↑        ↕        ↕
              キャラクター ←──────┴────────┘
                └→ キャラクター参考図（絵割りに渡す）
```

`novel-characters` / `novel-art` / `novel-script`の3つは**双方向矢印**になっている点に注意してください。人物・アート・脚本は同期的に反復する3本の線で、カスケードではありません。これは意図的です。脚本を書いてる途中で「人物に配分がない」と気づいたら、アウトラインへ戻って直します。アート側で「小道具ではこの場面を支えられない」と気づいたら、脚本へ戻って直します。

### 1.2 成果物として何を提供する

各ステージが3点セットを成果物として出力します。`*.json`（機械が読む作業データ）、`*.md`（人が読むテキストのエクスポート）、`*-report.html`（ダブルクリックで開ける単一ページのレビュー・レポート）。

レポートは飾りではありません。`novel-outline`のレポートを例に挙げます。

- **KPIバンド**：総話数、快感ポイントの数、人物の格付け、主シーン数、生成の難所、改変の幅
- **快感リズム図**：物語のタイムライン上に各快感ポイントを表示し、空きがあれば軸に直接書き込む（「— 4話の空白 —」）。閾値超えは赤になる
- **話ごとの進行マトリクス**：60話 × 25人物のグリッド。縦に1列ずつ読むと、その話に必要なものが一覧になる
- **品質ゲート・パネル**：✓/✗がページに焼き込まれており、不合格項目には問題箇所のバナーが出る
- **JSONエクスポート**：ダウンロードされるのが`outline.json`そのもの

作者のポジショニングは明確です。**業界レビュー用の単一ページ・レポートであり、読者はこれを手に「中止するか否か」「生産計画を立てるか否か」を判断する。** レポートのデフォルトの納品形態が、アーカイブして埃をかぶるのではなく意思決定に使われることを決めています。

`novel-staging`はさらに一歩進み、納品するのは**操作可能なHTMLツール**です。各シーンごとに俯瞰の平面図があり、人が直接ドラッグして位置を入れ替え、クリックで座る／立つと方角を変え、編集後に「Export JSON」をクリックすれば新しい`staging.json`がダウンロードされます。JSONを手で直す必要はありません。

### 1.3 エンジニアリング上の制約

| 項目 | 要件 |
|---|---|
| Node | ≥ 18、**標準ライブラリのみ、npm依存ゼロ** |
| `API key` | **不要**、現在のセッション枠を使用 |
| Agent | `SKILL.md`を読めてNodeスクリプトを実行できるAgentなら何でも |
| 画像生成モデル | `character-refs`のみ必要（Qwen Image / Codex / GPT Image 2 / カスタムコマンド） |

依存ゼロという方針は技术的見世ではなく、**可搬性の前提条件**です。単一のskillを持ち出してコピーしても、動作する必要があるからです。

## 二、詳細チュートリアル：ゼロから一続きのパイプラインを走り切る

### 2.1 インストール

```bash
git clone https://github.com/eternityspring/shuohao-skills.git
cd shuohao-skills
./scripts/install.sh
```

インストールスクリプトのやることは地味です。各skillディレクトリを検出したAgentのskillsディレクトリへ**シンボリックリンク**します。リンクは複製ではないので、`git pull`の直後に即座に効きます。再インストールは不要です。

```bash
./scripts/install.sh novel-characters   # 1つだけインストール
./scripts/install.sh --codex            # codex にのみインストール
./scripts/install.sh --uninstall        # シンボリックリンクを削除
```

手動で設置することもできます。

```bash
ln -s "$PWD/skills/novel-characters" ~/.claude/skills/novel-characters
ln -s "$PWD/skills/novel-characters" ~/.codex/skills/novel-characters
```

設置後、まず自己テストを一巡実行し、環境に問題がないことを確認してください（この工程は飛ばさないこと）。

```bash
for f in skills/*/scripts/selftest.mjs; do node "$f"; done
```

自己テストはモデルを呼ばず、使用枠も消費しません。全件走破して約1秒です。**注意：上流では `macOS` + Node 24 でのみ検証済みで、Linuxおよびそれより低いバージョンのNodeは理論上は問題ありませんが未検証です。**

### 2.2 作業ディレクトリの規約（フラットにしないこと）

パイプラインを一通り走らせると、多数の`json` / `md` / `html`が生成されます。リポジトリで固定されているディレクトリ規約は次のとおりです。

```
<demo>/
├── outline/       ← <作品>-outline.json / .md / -report.html
├── characters/    ← <作品>-cast.json / .md / -report.html
├── art/           ← <作品>-art.json / .md / -report.html
├── script/        ← <作品>-script.json / .md / -report.html
├── staging/       ← staging-report.html（主要成果物）+ staging.json
├── storyboard/    ← <作品>-storyboard.json / .md / -report.html
│   ├── manifest.json
│   ├── E01-01/        ← export の絵割り本番パッケージ、セグメントごとに1フォルダ
│   └── E01-02/
├── docs/
└── scripts/
```

取りわけ注意すべき落とし穴がひとつあります。**セグメント用フォルダのさらに下にもう一層置かないこと**（たとえば`segments/`の中に入れること）。絵コンテレポート内の画像は相対パス`<段号>/f<切序>.png`で参照され、デフォルトではレポートhtmlとセグメントフォルダが同一階層であることを要求します。階層を1つ増やしてパスを直さないと、レポート内の画像は**静かに**すべて「未生成」のプレースホルダに化けます——上流の実測では、セグメントフォルダ10個を`segments/`へ移したところ、埋め込み画像が2枚から0枚になり、**レポートはエラーを出しませんでした**。

これが「静かな失敗」の典型例です。ファイルも画像も存在するが、リンクが間違っていて、ページは正常なふりをしています。

### 2.3 Stage 1：脚色アウトライン

```bash
node skills/novel-outline/scripts/novel-outline.mjs chunk <book.txt> <workdir>
node skills/novel-outline/scripts/novel-outline.mjs validate <workdir>/outline.json --stage beats
node skills/novel-outline/scripts/novel-outline.mjs validate <output>/<作品名>-outline.json
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<作品名>-outline.json --md   > <作品名>-outline.md
node skills/novel-outline/scripts/novel-outline.mjs render <output>/<作品名>-outline.json --html > outline-report.html
```

**このフローで最も価値のある鉄則は「先に決裁、次に細分化」です。**

骨格（どの線を切る、どの人物をまとめる、大ヒットを何話目に置くか）は、まず**スナップ版**をユーザーに出してOKをもらい、その後に限り各話概要を書きます。これは口約束ではなく、**フローのゲート**です。各話を書く前には必ず`validate --stage beats`を通す必要があり、快感の間隔やmajorのタイミングが間違っていればその場で止めます。

作者の論理はいたって現実的です。**スナップ版が間違っていても損失は骨格一巡ぶんで、各話まで書いてから方向が間違ったと気づくなら、全部が無駄です。** 60話の各話も分割して書き、1バッチは≤10話とします——後半を一口气に書けば必ず崩壊します。

14本のゲートは次のとおり。

| ゲート | デフォルト閾値 |
|---|---|
| 主人公グループ（男女主人公＋主要敵役） | 1〜5人 |
| 名のある重要脇役 | ≤ 10人 |
| 機能的役割（顔は出るが名前はない） | ≤ 10人 |
| 主シーンの上限 | **話数に応じて変動**：4 + ⌈話数/10⌉、5〜15に収める（6話→5、60話→10、110話で上限15） |
| 物語小道具の上限 | ≤ 8個 |
| 使い切りシーンに回避策がある | — |
| 快感の間に真空区間がない | ≤ 3話 |
| 第1話にフックがある | — |
| 大ヒットを最終話に寄せない | — |
| 各話の3欄がそろう（概要／フック／疑問点） | — |
| 3人以上の同一画面に分解案がある | — |
| 生成の難所が警告リストに入っている（雨のシーン／身体接触／群衆／手のクローズアップ） | キーワードスキャン |
| 参照の整合性：役がいない、空転シーンなし、IDが全て存在 | — |
| 概要は叙述体であり、引用符付き台詞がない | — |

2つの閾値の設計は分解して考える価値があります。どちらも「AIショートドラマ」と「実写ショートドラマ」の根本的な差を露呈しています。

**なぜ人物を3段階に分けたのか（一刀両断ではないのか）**：一刀両断では2つの異なる事柄が混同されます——「観客が覚えざるべき人物は誰か」と「制作が維持すべき顔の数」です。主人公グループの上限は配分と記憶負荷を守ります。脇役と機能的役割の上限は**AIキャラクター資産のコスト**を守ります（各段階で一貫性投資の度がまったく異なります）。機能的役割に「人物アークがない」のは正常です——医者は縫うために来るのであり、バリデータが無理eway求めることはありません。

**なぜシーン上限は実写劇よりかなり広いのか**：実写の時代「≤ 5つのロケ」は経済学でした（セットの組み込みに金がかかる）。AIショートドラマではシーンは生成されるので、**セットの組み込み費がない**ため、実写時代のあの経済学は成立しません。上限が残す意味は、シーンの**話跨ぎの一貫性資産**と観客の空間認知だけです。観賞性はそのままシーンの多様性に左右されるので、話数に応じて15まで緩めています。

ついでに。五点セットの5番目の「資産一覧」は**常にスクリプトが算出するもの**であり、モデルが手で書けば必ず漏れます。

### 2.4 Stage 2：人物設定

```bash
node skills/novel-characters/scripts/novel-characters.mjs seed <outline.json> > <workdir>/seed.json
node skills/novel-characters/scripts/novel-characters.mjs chunk <book.txt> <workdir>
node skills/novel-characters/scripts/novel-characters.mjs merge <workdir> --apply merges.json | tee <workdir>/merged.json
node skills/novel-characters/scripts/novel-characters.mjs validate <cast.json>
node skills/novel-characters/scripts/novel-characters.mjs render <cast.json> --html > cast-report.html
```

**seedの仕組みは、このアーキテクチャの汎用パターン**です。上流で既に決裁済みの事実（人物ID、名前、格付け、人物アーク、統合の由来）はスクリプトが決定論的に搬入し、空欄はこの層で初めて行うべき設計（別名、一言の人物像、外見プロンプト、音声）にします。ドキュメントに何度も強調されている一文があります。

> **これらの事実をモデルに考え直させてはいけません。**

同じ一文が`novel-art`、`novel-script`、`novel-staging`、`novel-storyboard`の4つのskillに、それぞれ一度ずつ登場します。**重複推論を避けることがAIパイプラインで最も安価な最適化**です。モデルが考え直すたびに、暴走する可能性がもう1回増える。

別名の統合について注目に値する細部があります。スクリプトができるのは**完全一致**による収束だけです（あるブロックで「陸」を「陸行遠」の別名として列挙していれば、2件は1人になります）。残りの`mergeCandidates`は意味的判断であり、スクリプトにはできません。人が／モデルが1件ずつ確認する必要があります。候補は名前の包含関係から生成されます（`「陸」⊂「陸行遠」`）が、作者は明確にこれを**強いシグナルであり判決ではない**と注記しています——同名の親子・兄弟は統合できません。「陸先生」と「行遠」には包含関係がないので、そもそも候補にも入らず、自分で発見するしかありません。

上流のサンプル『渡口』はこのテストケースを意図的に作っています。行商人は終始あだ名だけで、船頭は「おじさん」としか呼ばれなかっただけです。

### 2.5 Stage 3：アート設定

```bash
node skills/novel-art/scripts/novel-art.mjs seed <outline.json> > <workdir>/art.json
node skills/novel-art/scripts/novel-art.mjs validate <art.json> --cast <cast.json>
node skills/novel-art/scripts/novel-art.mjs render <output>/<作品名>-art.json --html > art-report.html
```

このskillの前提は骨に刻まれています。**これはAIによる生成であって、実写ではない。** ロケーション選定、セットの組み込み、配置、仕入れの工程はすべて存在しません。環境も小道具も、数十回生成しても同一の貌を保たなければならない資産です。そのためすべての納品物が一貫性を中心に設計されています。

| 納品物 | 何を解消するか |
|---|---|
| 一貫性アンカー（各シーン3〜5個） | 観客はこれでシーンを識別し、QCはこれで生成カットのずれを照合する |
| 時間帯ごとの照明バリエーション | AIで時間帯を変えるのは**再生成**であって、照明を当て直すことではない。各状態は完全なプロンプトに落とされる |
| 空シーン画像のプロンプト | 環境と人物は2層の資産であり、参考画像に人物が混入すると一貫性は完全に崩れる |
| バリエーションの仕組み（`variantOf`） | 新しいシーンの生成は安いが、バリエーションは親シーンの資産を再使うので一貫性が高い |
| 小道具の状態バリエーション | スーツケースの閉じた状態と開いた状態は2枚の参考画像になる——小道具には状態の弧があるが、シーンにはない |
| 小道具の寸法参照 | AIは手持の小道具を家具サイズで描画することが多い。プロンプトには寸法のフレーズが必要 |
| 小道具の背景白・手なし | 小道具画像はあらゆるカットに貼られるため、切り抜き可能である必要があり、小道具を持つ手は最も頻出する汚染である |

「小道具は物語小道具だけを受け付ける」という境界は明快です。クローズアップがあるか、話跨ぎするか、物語を担う場合は通常3〜8個です。シーンの調度はシーンアンカーへ、使い切りの手持ち小道具はカット単位のプロンプトで解決し、いずれも独立に資産としては起こしません。

「スーツケースのように人と動く小道具は、この層に属するべきです」——シーンアンカーや人物像に入れるのは誤りです。

10本のゲートのうち最も実用的な2本：**プロンプトは全文英語**（中国語のプロンプトを画像モデルに食わせると、一般に効果が悪く、これは自覚ではなくゲートが強制しているベストプラクティスです）、そして**プロンプトに人物名を含めない**（人物名は画像モデル自身が参考画像と関連づけるので、名前がむしろ干渉になります）。

### 2.6 Stage 4：脚本

```bash
node skills/novel-script/scripts/novel-script.mjs seed <outline.json> --eps 1-3 > <workdir>/script.json
node skills/novel-script/scripts/novel-script.mjs validate <script.json> --outline <outline.json> --art <art.json>
node skills/novel-script/scripts/novel-script.mjs render <output>/<作品名>-script.json --html > script-report.html
```

**前提は骨に刻まれています：脚本は演、絵コンテは撮る。** 台詞は何度も推翻し書き直す必要があり、カット分解に紐づけてしまうと一文変えるたびにカットを組み直すことになります。だからこの層にあるのは話・シーン・ビート列だけで、カット番号はありません。

ただし底線があります。**台詞は構造化データでなければならず、散文で書いてはならない。** 各台詞は独立したエントリ（話者＋台詞＋トーン）であり、アクションは独立したビートです。これがすべての決定論的検査の土台になります。

長さは**算出されます**：台詞は4.5字/秒で換算し、アクションは2.5秒/ビート。1話3分なら3分。超過も不足も、その場で止めます。生成工程まで流して初めて気づくことがないよう。

10本のゲートのうち、力量が光る2本があります。

- **フックは最初の3ビート内で具象化される**（`hookBeat`が宣言）——フックはラベルではなく第1ビートです。ショートドラマの生死線は紙面に落とす必要があり、モデルに「悬念を書いて」と覚えさせることに依存できません。
- **各シーンに最低1つのアクションビート**——台詞だけの場はラジオドラマであり、AI生成では描写すべき画面がありません。

書きすぎた場合はアクションビートを先に削り、次に台詞を圧縮します。足りなかった場合は**足すのは芝居であって水増しではない**——追加するのは挨拶ではなく衝突です。

### 2.7 Stage 5：開始配置（最も面白いskill）

```bash
node skills/novel-staging/scripts/novel-staging.mjs seed <script.json> --art <art.json> --outline <outline.json> > <workdir>/staging.json
node skills/novel-staging/scripts/novel-staging.mjs validate <staging.json> --script <script.json> --art <art.json>
node skills/novel-staging/scripts/novel-staging.mjs render staging.json > staging-report.html
node skills/novel-staging/scripts/novel-staging.mjs blocking staging.json
```

**なぜ配置だけを別に用意するのか。** ショートドラマの各動画セグメントは独立した生成で、各セグメントが自分で誰をどこに座らせるかを決めます。6人の群像劇で長テーブルを囲むシーンなら、第1セグメントではテーブルの端に名前のない客が5人増え、第3セグメントでは酒を持って座っている人が主角の服を着ています。

絵コンテの配置文はセグメントからセグメントへ順に渡できますが、各シーンの**第1セグメント**のその一文は絵コンテ自身が作文します——**人は見できず、直せません**。そこで絵コンテの前に各シーンの配置を先に1つ決めて、絵コンテはそれをそのまま写します。

手順は**まず図を認識し、その後に配置を決める**という順序です。シーン画像の主視点の中から、人が立つ場所、座る場所にある物（4〜20個）を認識し、名前と図上の枠、俯瞰平面上の位置を書きます。次に脚本に沿って、誰がどの物のどちら側に、その側へどれだけ沿うか、座るか立つか、どの方角を向くかを決めます。

2つの鉄則があります。

- **図に見えないものは書かない**（プロンプトにあり図にないものは一切書かない）——さもないと人が台に登ってしまい、セグメントごとに結果が変わります
- **`plan`は透視図から推算する**のであり、`box`の写しではない——透視のシーン画像における「テーブルの北側」は細長い隙間であり、前後の奥行きが言えないため、平置きにして上から見て初めてはっきりします

配置ルールも固定されています。**後から入ってくる人は開始時点にいない**；**脚本に他人が書いていなければ群衆はいない**；**認識できた物だけを使う**。

配置文はプログラムが書き、一字一句そのまま絵コンテへ渡します。

> 「胡二爷は第3排の座板に腰掛け、北を向いている。ほかの席は空席で、ほかに人はいない。」

このskillは2.2.0で追加されたもの（2026-10-14）で、いちばん新しいものであり、作者が実際のプロジェクトで踏んだ失敗を最もよく示すものでもあります。

### 2.8 Stage 6：絵コンテ

```bash
node skills/novel-storyboard/scripts/novel-storyboard.mjs seed <script.json> --eps 1-3 --aspect 16:9 > <workdir>/storyboard.json
node skills/novel-storyboard/scripts/novel-storyboard.mjs validate <storyboard.json> --script <script.json> --outline <outline.json> --cast <cast.json> --art <art.json>
node skills/novel-storyboard/scripts/novel-storyboard.mjs render <output>/<作品名>-storyboard.json --html > storyboard-report.html
node skills/novel-storyboard/scripts/novel-storyboard.mjs export <storyboard.json> --protocol h3 --out storyboard
```

**前提は骨に刻まれています：カットは生成されるので、1カット増やすコストはほぼゼロ。** したがってここではカット数を惜しみにません。上限はひとつだけ，つまり動画モデルが1セグメントで生成できる長さ（デフォルト15秒）です。

3層構造です。

```
セグメント（segment）= 1回の動画生成呼び出し、15秒以下、シーン跨ぎなし
 ├─ カット（cut）= セグメント内の剪切、2〜5秒ごとに1カット（ハードゲート）、それぞれ脚本のビートを担当
 ├─ 絵割り図     = カットごとに1枚的关键帧：メイン図は0.00秒に固定、サブ図は各自のカット位置に固定
 └─ H3 プロンプト  = セグメントごとに1条、複数図の整列指示 + [Shot k] カット時刻の一字一句照合
```

重要な仕組みがいくつかあります。

- **ビート宣言**：各カットは脚本のあるシーンのどの連続したビートをカバーするかを宣言し、シーンをまたぐことはできません——場面が変わればカットも変わります。これにより絵コンテと脚本の関係は**機械的に照合できる**ものになります。
- **会話の正反打を1セグメント内で一度に生成**：全景、Aのクローズアップ、Bのクローズアップはそれぞれ2〜5秒のカットで、各構図は自身のカット絵で制御されます。**文字で賭けることがありません**。
- **アライメント指示は書き出すのではなく、導出されたもの**：`Picture 2 aligns with the 3.00-second mark…`と`[Shot k] At 00:0X.XXX`は、すべてカットの秒数から導出されます。validateは**一字一句照合**します——秒数を変更してプロンプトを忘れると、その場で止めます。
- **H3とSeedanceの並列**：H3プロンプトはMiniMax公式のI2VA構造（アライメント指示＋`integrated_multimodal_description`＋`overall_soundscape`＋`non_diegetic_music`）を使い、Seedanceプロンプトは**スクリプトが公式構造に沿ってその場で組み立てる**もので、モデルは各カットの`shot`だけを書けばよく、秒数・番号・画像参照は書きません。
- **構図の定量化フィールド**：各セグメントの`blocking`（誰が左で誰が右、間隔）、各カットの焦点距離／カメラ位置／構図／視線の着地点／ピント／安定性。理由は至って明快で、参考画像だけから出力するとカット絵がないため、「どのくらいの距離、どのくらい画面を満たすか、誰がどこにいる、どこを目で見ている」という情報は**文字にするか、その場で消えるかの二択**です。実際には消えていたのがまさにそれで、画角が遠くなり、動き太小になり、人物の位置置き方が場当たりになっています。

18本のゲートのうち最も硬いのは次のとおりです。**カットの長さが2〜5秒はハードゲートであって提案ではありません**（3秒前後のショートドラマの注意リズム）。**台詞が収まる**（ビートを宣言した台詞の秒数≤カットの秒数、各カットごとに検査）。**1カットの同一画面は≤ 3人**（超えた場合は分解説明が必須）。**H3の台詞は一字一句**（句読点1つ変えると通りません）。**動画プロンプトに人物名を含めない**（H3とSeedanceの公式規格の要求）。

### 2.9 ページの統合とエクスポート

5つのステージのレポートは1枚の単一ページに統合できます。

```bash
node scripts/report.mjs --from <demoディレクトリ> --out report.html
```

**これはアセンブラであり、6つ目のskillではありません。** どのskillのコードもimportせず、それぞれの`render --html`を呼んで成果物を取得し、組み立てるだけです。結果として5つのskillは1行も変更されず、それぞれが引き続き独立して動作し、単独で持ち出せます。あるskillのレンダリングを変更すれば、こちらも自動的に追従します。

統合で解決すべき3つの事柄は、**すべてアセンブラの中で行い、skillには侵入しません**。

- **スタイルの混入**：5つのレポートは57個のクラス名を共有しており、そのうち13個は同名で定義が異なります（`.copy` `.kpis` `.badge` `.chip`…）。各セレクタにスコープ接頭辞を付けます
- **スクリプトの混入**：各レポートのスクリプトは`document.querySelector('.expo')`のようなグローバル検索で、1ページに統合すると最初の1件にしか当たりません——5つの書き出しボタンがすべて壊れます。`document`を差し替えたProxyを被せることで解決します
- **画像パス**：各レポートの画像が参照するのは、それぞれのjsonのディレクトリを基準とした相対パスなので、統合後は出力ファイルの位置に合わせて再計算します

アセンブラ自身も3つの穴を踏みました。現在その3つにはそれぞれ自己テストのアサーションが監視しています。

1. `<script type="application/json">`は各レポート内の埋め込み元JSONを読み書き用の**データ**です。スクリプトとして取り出して実行すると、ブラウザは`Unexpected token ':'`を投げ、5つのパネルが同時に壊れます
2. ルール間のCSSコメントが次のセレクタに粘着し、コメント内のカンマがセレクタを分断します——実測で18条のルールからスコープが抜けました
3. 人物レポートのサムネイルはインラインの`background-image:url(…)`を使い、`src`属性だけを見ると漏れます。現象は大画像が正常、サムネイルが404となり、原因の特定が難しく、切り分けに時間を要します

### 2.10 人物だけを単独で動かす（小説を脚色しない）

`character-refs`は小説に依存しません。

```bash
node skills/character-refs/scripts/character-refs.mjs config --model qwen --confirm-anchor yes
node skills/character-refs/scripts/character-refs.mjs intake-check <キャラクター>-intake.json
node skills/character-refs/scripts/character-refs.mjs gen <asset.json> --tier 1   # まずアンカーだけ出力
node skills/character-refs/scripts/character-refs.mjs gen <asset.json>           # 第2ティアを補う
node skills/character-refs/scripts/character-refs.mjs render <asset.json> --html > report.html
```

**中核ルール：一組の画像には根がただ一つ——正面全身アンカー。** これが唯一のテキストからの画像生成で、ほかはすべて「アンカー＋一句の編集指示」です。髪・顔・襟元の3種類のディテールには、確認済みの正面向きの顔アップ写真を追加します。画像どうしは互いに参照しません——したがってどれか1枚が崩れても、その1枚だけ作り直せばよく、**連鎖しません**。

段階別の画像出力です。

| 段階 | 内容 | いつ生成するか |
|---|---|---|
| 1 | 正面全身（アンカー） | 常に、1枚目 |
| 2（デフォルト） | 正顔の顔アップ、90°の側面、背面 | デフォルトで揃える |
| 3 | ディテール図（最大8枚） | 装いや衣装の一部にクローズアップがある場合 |
| 4（デフォルトでは出さない） | 45°の顔アップ | ユーザーが明確に求める場合 |

なぜデフォルトで第2段階まで出すのか。H3での実測によるものです。**正面全身だけを与えると、衣装も後ろ姿も正しいのに、顔が崩れます。顔アップを1枚加えると、顔が最も近くなります。**

**モデルは固定しません**：主図と派生図で別のモデルを使ってかまいません。一貫性は「同じモデル」ではなく「同じアンカー」から得られます（実測ではQwenのアンカー＋GPTの派生、GPTのアンカー＋Qwenの派生、同じグループ内の混在もすべてつなげられました）。

**凍結されるのは3つだけ**です。アンカーファイル（sha256）、画風のスナップショット、文字記述のフィンガープリント。どれか一つでも変わると、依存する画像は自動的に「期限切れ」扱いになります——削除はせず、マークを付けるだけで、旧バージョンはすべて残されます。

## 三、設計哲学：このプロジェクトが本当に言いたいこと

以下の8点が、私にとってこのリポジトリで最も価値のある部分です。

### 哲学一：チェックリストをモデルの自覚に委ねるものは、頼りにならない

これはプロジェクト全体の第一原理で、出所は`novel-outline`のREADMEに次の一文として書いてあります。

> **チェックリストをモデルの自覚に委ねるものは、頼りにならない。**

したがってすべてのゲートは`validate`の中の決定論的な検査であり、モデルに読ませる文章ではありません。14本、10本、10本、8本、18本、合計60本。

それに伴う要件はもっと厳しいものです。**セルフテストにはすべてのゲートに「突破用のケース」が用意されている**——わざと違反データを組み立て、バリデータが本当に検出することを確認します。本当に止められることの証明であり、恒真の偽テストではありません。

この点の重みはいくら見積もっても軽いません。ほとんどの「AIワークフロー」プロジェクトは「モデルに20条の要求を書いた、たぶん従うだろう」という水準で止まっています。ここでの要求はこうです。**要求を1条もモデルに話させない。コードに書け。** モデルの出力は確率的で、コードだけが決定的です。

### 哲学二：画像生成の瞬間にしか決められないことは、全部skillの外へ出す

これが2.0版の破壊的変更の中核であり、このプロジェクトで最も見落とされながら最もラディカルなトレードオフでもあります。

1.x版では、人物・アート・絵コンテの3つのskillが自分で画像生成し、モデルを選び、画風を定め、アスペクト比を管理していました。2.0はこれらをすべて削除しています。理由はchangelogにこう書いてあります。

> **画像生成の瞬間にしか決められないこと（どのモデルを使うか、どの画風か、どのアスペクト比か）は、全部skillの外に出した。skillはプロンプトと構造化データだけを渡す。**

これに伴う硬い制約はこうです。**skillは画像生成をしない。** `novel-art`のREADMEには明確に「『生成済み』と言ってはいけない——この工程はもう存在しない。納品するのはプロンプトだ」と書いてあります。

なぜそうするのか。モデルを選ぶ、画風を選ぶ、アスペクト比を選ぶのは**プロジェクトレベルの意思決定**であって、ステージレベルの意思決定ではないからです。同じ作品内の人物画像とシーン画像は、同じモデル、同じ画風、同じアスペクト比を使うべきです。これらのパラメータが3つのskillに散らばると、3箇所で重複設定するか（不整合のリスク）、共有設定の層を足すか（自己包含性を壊す）かの二択になります。外に出せばこのジレンマは消えます。

唯一の例外が`character-refs`です——それ自体が「その瞬間」そのものなので、画像生成の能力は保持しています。**ルールには例外を置き、例外には理由を説明できるようにする。**

### 哲学三：各skillは自己包含で、単独で持ち出せる

```
skills/<skill-name>/
├── SKILL.md          agent が読むワークフロー（必須）
├── README.md         人が読む説明
├── scripts/
│   ├── <name>.mjs    決定論的ツール、依存ゼロ
│   └── selftest.mjs  自己テスト、モデルを呼ばない（必須）
├── references/       必要に応じて読み込む詳細指示
├── examples/         同梱サンプル、テストフィクスチャも兼ねる
└── assets/           スクリーンショット
```

2つの硬い要件があります。`SKILL.md`が必ず存在すること、`scripts/selftest.mjs`が必ず存在し、かつ**モデルを呼び出さず、使用枠も消費しない**こと。

それに伴うAGENTS.mdの行動ルールはもっと厳しいです。

> **skillは自己包含で、単独で持ち出せること：第三者skill（公式skillを含む）に一切依存しないこと。外部のメソッドロジックを学んだ後は、リポジトリ自身のreferencesドキュメントに内化し、学習元の出典を明記すること。**

そのためH3の公式メソッドロジックは`references/h3-prompt.md`に内化されており、外部依存をぶら下げる形にはなっていません。

**この制約のコストは現実的なものです**：コードには重複があります（アセンブラは、各skillでCSS変数を統一するのではなく、57個のクラス名の混入を自分で解かなければなりません）。作者はそのコストを支払います——単独で持ち出して使えるskillの価値は、重複を消して得られるわずかな整潔さより遥かに大きくなるからです。

### 哲学四：モデルが書く4つと、スクリプトが計算する1つ

アウトラインの五点セットのうち、前の4つ（脚色説明、人物表、快感ポイント表、各話概要）はモデルが書き、5つ目（資産一覧）は**常にスクリプトが集計するもの**です。

理由は一言。「モデルが手で書けば必ず漏れる。」

同じ原則は随所に散らばっています。レポート内の人物数集計、大ヒットの一覧、シーン概要カードが担う快感ポイント——すべて算出済みで、モデルは1文字も書きません。

**判断基準はとても明快です：機械的に計算できるものは、絶対にモデルに渡さない。** 「モデルに数えさせる、計算させる、突き合わせる」類の作業は、コードであるべきです。

### 哲学五：先に決裁、次に細分化。間違っても損失は一巡だけ

前に述べたとおりなので展開はしません。ただ、その形だけは強調しておきます。**これはフローの助言ではなく、フローのゲートです。** 各話を書く前に必ず`validate --stage beats`を通らなければ、先へ進めません。

AIパイプラインの失敗には特殊な点があります。初期の小さな誤りは**連鎖的に拡大**し、大量の計算資源を無駄にします。骨格が間違えれば60話すべてが無駄になり、人物を間違えればアートも脚本もすべて作り直しです。**最も安い場所で止めること、それがAIパイプラインにおける唯一健全な設計です。**

### 哲学六：一貫性は「アンカー」に依存する。「同じモデル」には依存しない

人物参考図における「根は1つ、あとは派生」という考え方は、実はプロジェクト全体に貫いています。

- シーンの一貫性 → 各シーン3〜5個のアンカー
- 小道具の一貫性 → 状態バリエーション（閉じたもの、開いたもの各1枚）
- 人物の一貫性 → 正面全身アンカー、派生図はそれのみを参照
- 照明の一貫性 → 各話から逆算した具体的な状態、各状態は完全なプロンプトに落ちる
- 話跨ぎの一貫性 → バリエーションの仕組み`variantOf`、親シーンの資産を再利用

統合された思想はこうです。**「一貫性」という曖昧な事象を、受け渡せ、検証でき、バージョン管理できる具体的なファイル1つに圧縮する。**

### 哲学七：1文字ずつの照合に、人眼に依存しない

`validate`の多くのゲートは本質的に「逐字比較」です。

- H3プロンプトのアライメント指示は絵コンテの構造から導出されなければならず、1文字もずれてはならない
- 宣言された台詞は`<d>`ブロックに1文字ずつ現れる必要があり、句読点1つ変えると通らない
- カット点の時刻は、それまでのカット秒数の累積と等しくなければならない
- プロンプトの言語は`promptLang`と双方向に照合されなければならない

**「逐字」という言葉がキーワードです。** AIが生成したものに最もよく出るのは「完全に違う」ことではなく「正しいが、完全に正しいわけではない」こと——1文字違う、0.5秒違う。この種の偏差は肉眼では到底見つけにくいですが、流水線の上では、廃棄フィルムのように積み上がります。1文字ずつの照合は、この種の偏差を赤信号に変えます。

### 哲学八：ゲート失敗は蓄積し、statsがモデルで最もよく破るルールを教えてくれる

`novel-storyboard`は`validate`のたびにゲートの結果をカレントディレクトリの`.gates.jsonl`へ追記します。

```bash
node scripts/novel-storyboard.mjs stats
```

数十回蓄積したあとは、統計が**モデルが最もよく破っているルール**を教えてくれます。そうすればそのルールを修正すればいいのです。

これは自己進化的な設計です。しかも作者の扱い方は非常に抑制的で、節度があります。

> **ゲート失敗の蓄積は現在のところ novel-storyboard にのみ実装している。これは意図的にそうしている：実際のプロジェクトでしばらく使い、stats が出てきたものが本当に直すべきルールを指していることを確認してから、残り5つへ広げるか決める。誰も長く開かないなら、この機能は作るべきではない。広げるのは誤りを5つに複製するだけだ。広げる提案は自分から出すな。**

**「誰も長く開かないなら、この機能は作るべきではない」**——この言葉の重みは見た目よりも重い。それは自分が間違っている可能性を認め、そして「間違えたら消す」という判定基準をあらかじめ定めているのです。これは非常に健全なエンジニアリングの姿勢です：機能の価値は使用者によって証明されるものであり、設計者の熱意によって証明されるものではありません。

同種の抑制は「カットレシピ」の扱いにも現れています。レシピカードライブラリは任意のプラグインであり、カード内の**推奨画角とカメラワークには意図的にゲートを設けていません**。レポートに`≠`マークを付けるだけです。作者の理由はこうです。

> **レシピは語彙であって法典ではない。任意のプラグインは厳しくなれば誰も付けない。誤って止めるゲートは、ゲートがないより悪い。**

**「誤って止めるゲートは、ゲートがないより悪い」**——この言葉は単独で額に入れてもよい程です。品質ゲートが一度でも誤検知すると、ユーザーの反応は「このゲートにバグがある」ではありません。「このツールは余計に指摘してくる、もう使わない」です。ゲートシステムは一度信頼を失うと、存在しないのと同じです。

## 四、まとめ：8つの見解

このプロジェクトを踏まえて、私の判断を以下に示します。

**見解一：AIショートドラマの真の敷居は、「生成できるか」から「検収できるか」へと移った。**

モデルが5秒の動画を1本生成するのは、もう難しくないです。難しいのは、600話回して387話目の2番目が崩れていないかをどう知るかです。このプロジェクトは60の具体的な判定基準をコードとして書き上げた。これは「検収」を人手の目視から機械実行可能に変えたことを意味します。**この検収体系を最初に構築した者のみが、生産量を安心して上げられます。**

**見解二：チェックリストをコードとして書くことは、プロンプトを100条書くことより価値がある。**

これは本プロジェクトで最も移植可能な点です。どのAIワークフローにも当てはまります：プロンプトはソフト制約、コードはハード制約。違いは措辞の強さにではなく、**違反できるかどうか**にあります。

**見解三：AIパイプラインが本質を突いているかどうかを判断するには、「意思決定権」を誰に委ねているかを見ればよい。**

このリポジトリの姿勢ははっきりしています：構造、計数、検証、連結、エクスポート——すべてをコードへ。モデルには自身が本当に得意な2つのことだけが残ります：内容を書くこと。美観を判断すること。**分担が明確なほど、パイプラインは信頼になります。**

**見解四：一貫性は資産であって、雰囲気ではない。**

「雰囲気感」は形容詞です。「3〜5個のアンカー＋状態バリエーション＋寸法参照＋sha256凍結」は資産です。前者は生成のたびにぶれる可能性がありますが、後者は話跨ぎで再利用でき、QCでき、バージョン管理できます。**AIコンテンツ生産が最終的に競うのは、資産の管理能力であって、アイデアではありません。**

**見解五：「単独で持ち出せるか」は、よいアーキテクチャの試金石である。**

コンポーネントが単独で持ち出されて崩れないかどうかは、そのコンポーネントが文脈に隠れて依存しているかを露呈します。このリポジトリは自己包含を硬い要件として書き、代償はコードの重複、得られるのは**各skillを独立した製品として売れる**ことです。典型的な「制御可能な重複で構造の自由を買う」取引です。

**見解六：「必ず決裁する」を助言ではなくゲートにする。**

AIパイプラインの手戻りコストは極めて高い。方向を間違えれば後工程は無駄です。だから「先に決裁、次に細分化」はコードゲートとして書かれなければならず、フローチャート上の1文では不十分です。**AIが関わる流程では、意思決定点が早ければ早いほど硬い必要があります。**

**見解七：作者が「この機能は作るべきではない」と判断する勇気は、彼が作った機能そのものより学ぶべきだ。**

「誰も長く開かないなら、この機能は作るべきではない」「広げる提案は自分から出すな」——この2文はオープンソースプロジェクトの中では希少なものです。ほとんどのプロジェクトは機能を追加するだけで、自分の取り消し条件を先に書くことはまずありません。

**見解八：このプロジェクトの真の産物は7つのskillではなく、1600を超えるセルフテストのアサーションである。**

1600を超えるアサーション、モデルを呼び出さず、使用枠も消費せず、1秒で走り、すべてのゲートに突破用のケースがある。まさに「品質ゲート体系」の本質的な資産です——これによってどんなチームでも、自分のコンテンツ種別でこのメソッドロジックを再利用できます。**skillはコピーできますが、メソッドロジックはコピーできません，なぜなら它がテストの中に育っているからです。**

## 五、ショートドラマのビジネスを展開している人にとっての意味

AIでショートドラマのビジネスをしている経営者なら、以下の几点がより実際的です。

**第1に、この仕組みが直接抑えているのは「制御不能な手戻り率」です。** AIショートドラマで最も高くつくのは生成ではなく、「200話回して初めて人物が崩れ、シーンの矛盾に気づき、フックが実現されていないと分かる」ことです。60本のゲートは、この種の手戻りを「事後の抜き取り検査」から「事前の遮断」に変えます。

**第2に、依存ゼロ・API key不要は、試行錯誤のコストがほぼゼロであることを意味します。** パイプライン全体を走らせるのに必要なのはNode 18+と自分のセッション枠だけです。全巻分のアウトラインを1周させるコストは、人にコーヒー1杯をごちそうするより安いかも知れません。**このコスト構造は「まず大量に試し、次に集中的に量産する」戦略に適しています。**

**第3に、「脚本は演、絵コンテは撮る」という境界は単独で覚えておく価値があります。** AI動画を作るとき、多くの人は「芝居を書く」と「カットを刻む」を混ぜてしまい、台詞1文変えるたびに数十のカットを並べ替え直すことになり、時間がすべて手戻りに消えます。分離の代償は引き継ぎが1回増えることで、得られるものは**2つの工程を並行して反復できる**ことです。

**第4に、2〜5秒のカットのハードゲートは、そのまま流用できる業界標準値です。** ショートドラマの観客の注意リズム、生成コスト、動画モデルの長さ上限、この3つの制約がここで1つの数値に交差します。自分でショートドラマを撮るなら、この数も2〜5秒であるべきです。

**第5に、「誤って止めるゲートは、ゲートがないより悪い」は、すべてのAIツール製品が学ぶべき教訓です。** 同種の仕組みを自分のチームに導入するなら、**最初にやることはゲートを増やすことではなく、すでにあるゲートが誤検知ゼロであることを保証することです。** 一度でも誤検知したツールは、チームは二度と使いません。

## 六、おわりに

`shuohao-skills`は「AIショートドラマ生成機」ではありません。そもそも動画を生成しません。

彼が行っているのは、より基礎的で、より難しいことです。**AIショートドラマの生産過程におけるすべての「何が正解なのか」を定義し、その定義を機械が実行できる判定に変えること。**

スター6800が買っているのは、この認知的密度です。7つのskillが骨格、60本の品質ゲートが筋肉、1600を超えるアサーションが回帰テスト。**真の希少品は、プロンプトを書くモデルではなく、「何が正解なのか」を知っており、かつそれをコード化できる人です。**

AIショートドラマのツールを探しているなら、まず動画が撮れるかを見ずに、まず**検収基準をコードとして書く勇気があるか**を見てください。そこが分水嶺です。
