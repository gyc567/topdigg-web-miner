# 让AI不再输出"文字墙"：Answer Me With HTML让你的AI助手秒变可视化大师

## 引言：当AI输出的内容越来越难消化

想象这样一个场景：你向AI助手抛出一个技术问题，比如"TCP三次握手是怎么工作的"，然后得到的是——一堵密密麻麻的文字墙。

这可能是几百字的技术解释，可能是各种专业术语的堆砌，读完之后脑子里依然模糊。

Andrej Karpathy曾在推文中指出：**随着LLM能干的事情越来越多，人类越来越难跟上它的输出节奏。**比起读一大段文字，看一张图、一页网页要轻松得多。

那么问题来了：有没有办法让AI助手直接输出结构清晰、可视化的页面，而不是一堵让人头疼的文字墙？

**Answer Me With HTML** 就是这个问题的答案。

---

## 一、项目介绍：让AI用一页HTML回答复杂问题

**Answer Me With HTML** 是一个开源的Agent Skill（智能体技能），它的核心理念很简单：

> 当你向AI助手提出复杂问题时，它不再甩给你一堵文字墙，而是给你一页能看懂的HTML。

这页HTML可能是：
- 一张时序图，展示消息的来回传递
- 一张状态迁移图，清晰标注各种状态变化
- 一张架构图，帮你理清模块之间的关系
- 一张对比表，用✓ ✗标注出不同方案的优劣
- 一段讲解视频，边配音边画图

更惊人的是：**使用这个skill后，AI模型要写的token只有直接手写HTML的约1/8，速度却快了2.6倍。**

---

## 二、核心设计哲学：模型写内容，CLI做排版

### 2.1 为什么不让AI直接写HTML？

你可能会问：现在的AI写HTML已经很厉害了，为什么不直接让它输出HTML页面？

答案是：**AI写的大部分都不是内容。**

根据项目作者的实测，AI直接手写的HTML页面中：

| 页面的部分 | 占比 | 用skill后 |
|:---|---:|:---|
| SVG图：坐标和路径 | 47% | 由CLI生成 |
| CSS样式代码 | 15% | 由CLI生成 |
| HTML标签 | 17% | 由CLI生成 |
| 正文文字 | 21% | 模型来写（Markdown） |

AI模型要花将近80%的时间去写那些"架子"——CSS、SVG坐标、HTML标签，而不是真正的内容。

而且SVG坐标的计算尤其困难：**模型经常算错坐标，导致箭头指向空白处、标签被截断、网格留空洞。**

### 2.2 分工原则：让专业的人做专业的事

Answer Me With HTML 的设计哲学是**"模型写内容，CLI做排版"**：

- **模型（AI）**：只写内容，写成简洁的Markdown格式
- **CLI（命令行工具）**：负责选模板、排面板、套主题、画图、算坐标

这带来的好处是革命性的：

1. **速度快**：模型只写1/8的token，等的时间从31秒降到12秒（快了2.6倍）
2. **质量高**：CLI用专业算法计算布局，不再出现箭头乱指的问题
3. **成本低**：输出token减少约8倍，虽然实际花费只降15%（因为输入token不变），但对于高强度使用者来说仍然可观

### 2.3 "高频模式"：每个结论都自动出页面

这个skill最棒的功能之一是**"Always-on Mode"（高频模式）**：

打开后，**只要AI给出结论、总结、方案或对比，哪怕回答很短，它都会自动生成一页HTML**，让你在需要的时候可以回顾。

这意味着：
- 你不用每次都开口要页面
- 短结论也和长篇一样好读
- 页面会积累在本地文件夹，随时可查

## 三、详细安装教程

### 3.1 环境要求

- **Node.js 20** 或更高版本
- 支持的AI助手：Claude Code、Codex、Cursor、OpenCode、Pi等70+种Agent

### 3.2 方法一：让AI帮你安装（推荐）

最简单的方法，直接把下面这段话粘贴给你的AI助手：

```
帮我安装 Answer me with HTML：读 https://raw.githubusercontent.com/QingYunA/answer-me-with-html/main/INSTALL.md，照着做。
```

AI会自动帮你完成安装，并用TCP三次握手页面验证安装结果。

### 3.3 方法二：Claude Code插件安装

如果你用的是Claude Code，在里面执行：

```
/plugin marketplace add QingYunA/answer-me-with-html
/plugin install answer-me-with-html@answer-me-with-html
```

### 3.4 方法三：一条命令安装

打开终端，执行：

```bash
npx skills add QingYunA/answer-me-with-html
```

它会询问你要安装到哪个AI助手。

### 3.5 方法四：手动安装

```bash
# 克隆仓库
git clone --depth 1 https://github.com/QingYunA/answer-me-with-html.git /tmp/answer-me-with-html

# 复制到Claude Code
cp -R /tmp/answer-me-with-html/skills/answer-me-with-html ~/.claude/skills/answer-me-with-html

# 其他助手的skill目录：
# Codex: ~/.codex/skills/
# Cursor: ~/.cursor/skills/
# OpenCode: ~/.config/opencode/skill/
```

### 3.6 打开高频模式

建议打开"高频模式"，让AI每个结论都自动出页面。把下面这段话粘贴给AI：

> 帮我打开 Answer me with HTML 的高频模式：在你的全局规则文件里加一条规则——"[answer-me-with-html always-on] 只要回复里给出了结论、总结、方案、对比、评审或讲解，就同时用 answer-me-with-html skill 生成一页 HTML（日常结论用 2～4 个面板），先渲染页面，再写文字回复，回复最后附上页面的 file:// 链接，不要先写文字再渲染。哪怕回答很短也要出，不要因为答案不长就跳过。渲染时加 --no-open，不要弹出浏览器。闲聊、没有结论的一两句话、纯命令输出、我要求纯文本时除外。"

## 四、功能详解：你问什么，会得到什么

### 4.1 核心组件一览

| 组件 | 适合什么场景 |
|:---|:---|
| `flow` | 架构图、调用链、决策分支。自动布局，支持分组、判断框、数据库 |
| `sequence` | 时序图，几方之间按时间顺序来回发消息 |
| `tree` | 目录结构、模块关系、分类体系 |
| `timeline` | 历史演进、版本发布、阶段划分 |
| `limits` | 当前值和上限的对比（如资源使用情况） |
| `annot` | 逐词点评一句话（如文案批注） |
| `kv` | 元信息、图纸标题栏 |
| `callout` | 结论、提示、警告 |
| `ask` | 需要你在页面上做的决定，AI的建议项默认选中 |
| 代码块 | 从文件引用的真实代码，或手写的示意代码 |
| 表格 | 多维对比。单元格写`ok`/`no`/`warn`会变成 ✓ ✗ ! |

### 4.2 实际效果示例

当你问"Redis和Memcached怎么选"时，你会得到：
- 一张多维对比表，✓表示支持，✗表示不支持
- 最后AI会给出一个结论和建议

当你问"Kubernetes是怎么发展起来的"时，你会得到：
- 一张时间线，关键节点高亮标注
- 帮你理清技术演进的脉络

当你问"这个仓库的模块是怎么组织的"时，你会得到：
- 目录结构树
- 一张模块调用关系图

**但当你问"`ls`怎么看隐藏文件"这种一句话能说清的问题时，AI不会出页面**，它会直接给你一个简洁的答案。

### 4.3 三大主题风格

- **blueprint**：图纸风格，像工程制图一样严谨
- **shadcn**：卡片风格，现代简洁
- **paper**：适合长文阅读，清晰的阅读体验

默认情况下，CLI会根据内容自动选择：长文用paper，有图表用blueprint。

所有主题都支持亮色和暗色模式，页面上可以随时切换。

## 五、写作检查：让AI的输出更易读

### 5.1 ASD-STE100标准

这个skill内置了**ASD-STE100写作检查**。

ASD-STE100是一种受控英语，最早用于飞机维修手册。它的规则很具体：
- 句子不能太长
- 一个词只表达一个意思
- 操作步骤要用祈使句

Karpathy曾指出：**让LLM按这套规则写，读起来会清楚很多。**

### 5.2 检查规则

每次渲染时，skill会自动检查：

- **句子长度**：英文超过20词、中文超过35字会提醒
- **用词**：推荐常用词（"use"而非"utilize"，"before"而非"prior to"）
- **中文**：去掉空洞动词（写"优化"而非"进行优化"），避免含糊数量词（"尽快"、"若干"、"大概"）
- **被动语态**：英文被动语态会被标记
- **连续的的**：中文里连续三个以上"的"会被标记

默认只提醒，不拦着。如果你想更严格，可以设置`style: strict`拒绝不达标的稿件。

## 六、进阶功能：生成讲解视频

### 6.1 3Blue1Brown风格的视频

你可以直接说："给TCP握手做个3b1b风格的视频"，AI就会生成一段讲解视频。

### 6.2 工作原理

AI写的稿子和页面稿一样，只是每一步多了旁白：

```markdown
## 两端都在等待
```sequence
Client -> Server: SYN
Server -> Client: SYN-ACK
```
> 先是客户端开口，发一个 SYN，意思是"我想跟你建个连接"。
> [Server] 听到了，回一个 SYN-ACK："收到，我这边也没问题。"
```

`am video`会：
- 按旁白逐步画出图
- 镜头跟着方括号里的节点走
- 配音内嵌在页面里，**离线也能播放**
- 加`--mp4`可以另存视频文件

### 6.3 声音选项

- **ElevenLabs**（需要设置API Key）：效果最佳
- **系统语音**：macOS用Tingting（中文）、Samantha（英文）、Kyoko（日文）
- **本地TTS**：可以对接任何OpenAI兼容的TTS服务

## 七、核心观点总结

### 7.1 为什么这个项目重要

1. **解决AI输出的"最后一公里"问题**：AI能回答复杂问题了，但人类如何高效理解AI的输出？这个问题长期被忽视，而这个项目正是解决方案。

2. **重新定义人机协作**：不是让AI减少输出，而是让AI的输出更容易被人类消化。这是一种思维方式的转变。

3. **展示了"分工"的力量**：让专业的人做专业的事。AI擅长内容创作，CLI擅长布局计算。强行让AI两件事都做，既慢又差。

### 7.2 关键洞察

> **"模型写内容，CLI做排版"**——这是整个项目最核心的设计哲学。

它证明了一个重要观点：**不是所有事情都应该让大模型来做。有时候，一个好的CLI工具配合大模型，比让大模型独自完成所有事情要高效得多。**

### 7.3 使用建议

1. **打开高频模式**：不要每次都开口要页面，让AI养成出页面的习惯
2. **善用视频功能**：复杂的概念，一张图+一段讲解视频比文字解释清楚十倍
3. **利用写作检查**：让AI的输出更专业、更易读
4. **定期清理页面**：`am clean`可以清理积累的页面，避免占用太多空间
