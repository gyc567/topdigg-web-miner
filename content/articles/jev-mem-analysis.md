# Jev-Mem 全面解读：用 System-One/System-Two 架构革新 AI Agent 记忆系统

## 引言：AI Agent 的"记忆之痛"

当我们与一个 AI Agent 对话时，你是否曾好奇——它是如何记住我们之前聊过的一切的？它是如何从海量的对话记录、文档、事件中，快速找到回答当前问题所需的信息的？

这看似简单的问题，实际上是 AI Agent 领域最核心、也最棘手的挑战之一。

试想：如果每次提问，AI 都要从零开始"回忆"所有相关经历，那体验将灾难性的缓慢。但现实是——大多数 AI Agent 的记忆系统，要么**慢得像在翻箱倒柜**，要么**记了等于没记**。

最近，来自德克萨斯大学达拉斯分校的研究团队发表了一篇论文，提出了一个让人眼前一亮的解决方案：**Jev-Mem**。它从人类认知科学中汲取灵感，用 **System-One / System-Two 双系统架构**，彻底重新思考了 AI Agent 的记忆系统应该怎么工作。

今天我们就来深度拆解这个项目，看看它究竟解决了什么问题，又带来了哪些创新。

---

## 一、为什么 AI Agent 的记忆系统这么难？

要理解 Jev-Mem 的价值，我们先要理解当前 AI Agent 记忆系统面临的核心困境。

### 1.1 记忆管理的"决策之海"

一个看似简单的记忆系统，背后实际上埋藏着**大量高频决策**：

- **记忆类型判断**：这条新信息应该以什么形式存储？是一个事实？一个事件？一个观点？
- **关系推理**：这条新记忆和已有的记忆之间是什么关系？是因果关系？时序关系？还是只是语义相似？
- **查询路由**：用户问了一个问题，应该去哪个"记忆区域"找答案？
- **候选评分**：找到了多个可能相关的记忆，应该优先考虑哪些？
- **停止决策**：已经找到足够的证据了吗？还是应该继续搜索？

这些问题在每一次记忆构建和每一次查询时都会反复出现。在一个真实的 Agent 应用中，这些决策可能每秒发生数十次甚至数百次。

### 1.2 两种糟糕的解决方案

面对这些高频决策，当前主流系统采用了两种都不完美的策略：

**方案一：固定启发式规则**

用 if-else 规则写死决策逻辑。比如"如果查询包含 'when'，就走时间索引"。

优点是不需要调用 LLM，速度快。**但问题在于**：现实世界的问题千变万化，固定规则无法捕捉复杂的上下文关系，容易在非典型场景下出错，而且维护成本极高——每次规则冲突都要手动调解。

**方案二：让 LLM 做所有决策**

用 LLM 来处理上述所有决策，包括记忆类型判断、关系推理、候选评分等。

优点是决策质量高，能处理复杂场景。**但问题在于**：这些高频决策每一次都要调用 LLM，不仅**成本高昂**，而且**延迟严重**。想象一下，你问了一个问题，系统要调用好几次 LLM 只是为了"决定去哪里找答案"——还没开始真正回答，延迟就已经破秒了。

**这就是当前 AI Agent 记忆系统的根本矛盾：记忆管理决策既高频又复杂，但现有方案在"快"和"准"之间只能二选一。**

## 二、认知科学启发：System-One 与 System-Two

Jev-Mem 的核心创新，来自于认知科学中的一个经典理论：**双过程理论（Dual Process Theory）**。

### 2.1 人类的两种思维系统

心理学家 Daniel Kahneman 在《思考，快与慢》中系统阐述了人类思维的双系统模型：

- **System One（系统一）**：快速、自动、无意识的决策。比如识别表情、判断距离、简单加减法。它由长期进化形成，消耗能量少，但容易产生偏见和错觉。
- **System Two（系统二）**：缓慢、审慎、有意识的推理。比如做数学证明、填写税表、学习一项新技能。它需要集中注意力，消耗能量多，但更加准确和灵活。

人类的日常决策绝大多数由 System One 完成——正是因为有了 System One，我们才能在复杂环境中快速反应，而不会陷入"思考瘫痪"。System Two 则在最需要深度分析的场景才会被调用。

### 2.2 AI Agent 记忆系统中的双系统映射

Jev-Mem 将这个框架创造性地引入到 AI Agent 的记忆架构中：

- **System-One 控制器**：负责所有高频、结构化的记忆管理决策——记忆类型判断、关系推理、查询路由、预算分配、候选评分、证据评估、动态停止。这些决策输出空间有界（分类、路由选择、概率评分），不需要生成式 LLM，一个轻量级模型甚至规则引擎就能高效完成。
- **System-Two 推理引擎**：仅在检索完成后进行答案合成——理解问题、整合证据、生成回答。这才是 LLM 发挥威力的舞台。

**核心洞察**：记忆管理决策的高频性，决定了它们必须由 System-One 处理；答案合成的复杂性，决定了它必须由 System-Two 处理。两者各司其职，才能在效率和质量之间取得最优平衡。

## 三、Jev-Mem 核心架构拆解

### 3.1 三大组件

Jev-Mem 的架构由三个核心组件构成：

```
┌─────────────────────────────────────────────────────────┐
│                    User Query                            │
└─────────────────────────┬───────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│              System-One 控制器                          │
│  (记忆类型判断、关系推理、查询路由、预算分配、             │
│   候选评分、证据评估、动态停止)                            │
└─────────────────────────┬───────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│              多关系记忆平面                               │
│  (语义关系、时序关系、因果关系、实体关系)                  │
└─────────────────────────┬───────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│              System-Two 推理引擎                        │
│  (答案合成 - 仅在检索完成后调用)                          │
└─────────────────────────────────────────────────────────┘
```

**组件一：System-One 控制器**

这是 Jev-Mem 的"大脑"。它负责在记忆构建和检索的每一个环节做出决策：

- **记忆类型判断**：判断输入的观察结果应该以何种规范形式存储（事实、事件、观点等）
- **关系推理**：建立新记忆与已有记忆之间的关系图（语义、时序、因果、实体）
- **查询路由**：根据问题类型，决定搜索策略和优先级
- **预算分配**：决定在当前查询上投入多少"搜索预算"
- **候选评分**：对检索到的候选记忆进行相关性评分
- **证据评估**：判断当前已收集的证据是否足够回答问题
- **动态停止**：决定是继续搜索还是终止检索

**组件二：多关系记忆平面**

这是 Jev-Mem 的"仓库"。与传统的单一关系图不同，Jev-Mem 维护了一个**多关系记忆平面**，存储规范化的观察结果，并在其上维护四层独立的关系图：

**四层关系图：**

1. **语义关系（Semantic）**：基于内容相似性建立的连接。比如"狗狗会摇尾巴"和"狗狗摇尾巴表示开心"会因为语义相似而连接。

2. **时序关系（Temporal）**：基于时间顺序的连接。Jev-Mem 支持六种时序关系：before、after、during、contains、overlaps、same_time。比如"用户上午开会"和"用户下午写代码"构成 before 关系。

3. **因果关系（Causal）**：基于方向性影响的推断。比如"用户按了闹钟"导致"用户起床"，构成因果关系。

4. **实体关系（Entity）**：基于共享实体的连接。比如两条记忆都提到了"Mira"这个名字，它们就通过实体关系连接。

**关键创新**：这四层关系图**共享同一组规范记忆节点**，但独立建边。这意味着，同一对记忆节点可以同时参与多种关系类型（比如既有时序关系又有因果关系），支持真正多维度的问答场景。

**组件三：System-Two 推理引擎**

这是 Jev-Mem 的"嘴巴"。它只在检索完成之后才被调用，负责：
- 理解问题的深层意图
- 整合来自多关系图的证据
- 生成连贯、准确的回答

### 3.2 检索闭环控制

Jev-Mem 的检索不是一个一次性的 top-k 操作，而是一个**迭代反馈循环**：

```
查询 → 路由 → 锚点检索 → 图扩展 → 证据评估 → [继续？] → 停止 → 合成
                                     ↑
                                     └──────────── 反馈循环
```

每一步都由 System-One 控制：

1. **查询路由**：System-One 根据问题类型，决定先去哪个关系图搜索
2. **锚点检索**：在选定关系图中，找到初始的记忆锚点
3. **图扩展**：从锚点出发，沿关系边扩展，收集更多相关记忆
4. **证据评估**：System-One 评估当前收集到的证据是否充分
5. **自适应停止**：如果证据充分则停止，否则继续扩展

**这种设计的精妙之处在于**：它将"找什么"和"怎么答"分离。前者由 System-One 高效完成，后者才动用 System-Two（LLM）。这避免了传统 RAG（检索增强生成）系统中，检索质量差导致整个回答质量崩溃的问题。

## 四、实验数据：效率与质量的双重突破

说了这么多，Jev-Mem 实际效果如何？研究团队在 **LoCoMo benchmark** 上进行了全面评估。

### 4.1 LoCoMo Benchmark 是什么？

LoCoMo（Long Context Modeling Benchmark）是一个评估 AI 系统在长对话场景下记忆和推理能力的基准测试。它考察系统在多轮对话中能否准确记住和利用历史信息。

### 4.2 核心结果

| 方法 | 总体得分 | 记忆构建时间 | 平均查询延迟 |
|------|---------|------------|------------|
| Full Context | 0.481 | N/A | 1.74s |
| A-MEM | 0.580 | 3,636s | 2.26s |
| MemoryOS | 0.553 | 3,276s | 32.68s |
| Nemori | 0.590 | 1,044s | 2.59s |
| MAGMA | 0.700 | 1,404s | 1.47s |
| **Jev-Mem** | **0.777** | **158s** | **0.93s** |

### 4.3 数据解读

Jev-Mem 在三个维度上都实现了对现有最佳方法（MAGMA）的全面超越：

**质量维度**：
- 总体得分 **0.777**，比 MAGMA 的 0.700 提升了 **11.0%**
- 这意味着 Jev-Mem 不仅能找到更多信息，还能更准确地回答问题

**构建效率维度**：
- 记忆构建时间仅需 **158秒**，比 MAGMA 的 1,404秒快了 **6.6倍**
- 这意味着 Jev-Mem 可以在更短时间内构建更高质量的记忆索引

**查询效率维度**：
- 平均查询延迟仅 **0.93秒**，比 MAGMA 的 1.47秒降低了 **36.7%**
- 这意味着用户等待时间大幅缩短，体验更加流畅

**三重提升，同时实现，这在 AI Agent 记忆领域是前所未有的突破。**

## 五、实战教程：从安装到运行

### 5.1 环境安装

首先克隆项目仓库：

```bash
git clone https://github.com/libingzheren/Jev-Mem
cd Jev-Mem
```

创建 Python 3.11 虚拟环境并激活：

```bash
python3.11 -m venv .venv
source .venv/bin/activate
```

安装依赖：

```bash
pip install -r requirements.txt
```

### 5.2 配置文件

在项目根目录创建 `.env` 文件，填入你的 API Keys：

```bash
TYPESAFE_API_KEY=your-typesafe-key
OPENAI_API_KEY=your-openai-key
```

> **提示**：如果你没有 TypeSafe API Key，项目也支持纯 OpenAI 模式。如果只是想体验功能，可以先运行离线演示。

### 5.3 离线演示（无需 API Key）

最快体验 Jev-Mem 的方式是运行离线演示：

```bash
python -m jev_mem.demo
```

这个演示会使用预设的示例数据，展示 Jev-Mem 的记忆构建和查询全流程，非常适合理解系统工作原理。

### 5.4 构建和查询记忆

假设你有一些观察数据（格式为 JSON），可以这样构建记忆：

```bash
python -m jev_mem --mode build \
    --input examples/observations.json \
    --jev-config config/jev_mem.json \
    --cache-dir ./jev_mem_cache/app
```

构建完成后，用自然语言查询：

```bash
python -m jev_mem --mode query \
    --question "What reminder does Mira prefer?" \
    --jev-config config/jev_mem.json \
    --cache-dir ./jev_mem_cache/app
```

### 5.5 运行 LoCoMo 基准测试

如果你想在自己的环境中复现论文的基准测试结果：

```bash
python -m jev_mem.benchmarks.locomo \
    --dataset data/locomo10.json \
    --jev-config config/jev_mem.json \
    --sample 0 \
    --model gpt-4o-mini \
    --max-questions 10 \
    --category-to-test 1,2,3,4 \
    --best-of-n 1
```

参数说明：
- `--sample 0`：使用全部测试样本（设为其他值可以抽样测试）
- `--category-to-test 1,2,3,4`：测试所有四个类别的问题
- `--best-of-n 1`：每个问题采样1次

### 5.6 消融实验

Jev-Mem 的设计允许分别禁用读写控制，方便进行消融实验：

**禁用写入控制（仅保留读取控制）：**
```bash
python -m jev_mem.benchmarks.locomo ... --no-jev-write
```

**禁用读取控制（仅保留写入控制）：**
```bash
python -m jev_mem.benchmarks.locomo ... --no-jev-read
```

**MAGMA Baseline（无 Jev 配置）：**
```bash
python -m jev_mem.benchmarks.locomo ...
```

通过消融实验可以发现，System-One 控制在读写两个环节都发挥了关键作用，缺一不可。

## 六、设计哲学：五大原则

Jev-Mem 的设计背后有五大哲学原则，理解它们有助于你更好地应用这个框架。

### 原则一：认知分工（Division of Cognition）

不同类型的认知任务应该由不同的认知系统处理，而不是让一个通用 LLM 处理所有决策。这不仅是效率考量，更是对认知科学深刻洞察的应用。正如人类不会让大脑的"快思维"去写诗，也不会让"慢思维"去躲避迎面飞来的球。

### 原则二：控制平面抽象化（Control Plane Abstraction）

记忆管理决策本身应该成为一等公民，被显式建模和执行，而不是作为提示工程中的附属品或硬编码的启发式规则。在 Jev-Mem 中，System-One 控制器是一个独立的、可替换的组件，这意味着你可以用不同的模型实现，甚至未来可以用专门训练的小模型。

### 原则三：保留证据优于丢弃（Preserve Evidence）

Jev-Mem 默认保留所有有效观察，而非在摄入时就做不可逆的"存储/丢弃"决策。这样可以避免那些当下看起来不重要、但未来查询可能揭示其价值的细节被永久丢失。这是 Jev-Mem 与传统记忆压缩/摘要方法的核心区别——它相信"证据的价值可能在未来被重新发现"。

### 原则四：关系视图优于单一图结构（Multi-Relational over Single Graph）

语义、时序、因果、实体四种关系从同一组规范记忆节点出发，独立建图。这种设计允许同一对记忆节点同时参与多种关系类型，支持真正多维度的问答场景。比如，用户问"那次会议上讨论了什么？"需要时序关系；问"为什么最终做了这个决定？"需要因果关系；问"还有谁提到了类似的观点？"需要实体关系。

### 原则五：自适应检索优于固定检索（Adaptive over Fixed Retrieval）

检索是一个闭环控制过程而非一次性操作。每次扩展后都评估证据充分性、预期收益、缺失证据和未解矛盾，动态决定是否继续搜索。这避免了过度检索（引入无关记忆、分散推理注意力）和欠检索（遗漏关键证据）两个极端。

## 七、核心结论与展望

### 7.1 三大核心结论

通过深入分析 Jev-Mem，我们得出三个核心结论：

**结论一：效率与质量可以兼得**

传统观点认为，在 AI 系统中，效率和质量是一对矛盾体——要快就要牺牲准确，要准就要接受延迟。Jev-Mem 用实证证明，通过正确的架构设计，**效率和质量可以同时提升**。Jev-Mem 实现了质量提升（+11%）和效率提升（6.6 倍构建加速、36.7% 延迟降低）的双重收益，这在 AI Agent 记忆领域是前所未有的。

**结论二：System-One/System-Two 是记忆系统的新范式**

认知科学中的人脑双系统理论，不仅是人类认知的描述性理论，更可以成为 AI 系统设计的规范性原则。Jev-Mem 证明，将这一理论系统性地引入 AI Agent 记忆架构，能够带来实质性的性能提升。这为未来的记忆系统设计指明了方向。

**结论三：轻量级结构化决策胜过自回归生成**

对于输出空间有界、结构化的决策（如分类、路由选择、概率评分），typed probabilistic decisions 远优于 free-form LLM generation。这不仅是因为效率考量——在很多场景下，经过良好校准的结构化决策，在准确性上也优于 LLM 的自由生成。

### 7.2 局限性与发展方向

Jev-Mem 目前还有一些局限性值得关注：

- **System-One 控制器的实现**：当前版本的 System-One 控制器使用 LLM 实现，虽然比完整的 System-Two 推理更轻量，但仍有优化空间。未来可以用专门训练的轻量级模型替代。
- **关系类型的覆盖**：目前支持四种关系类型（语义、时序、因果、实体），但真实世界的知识图谱可能需要更多类型的关系。
- **跨模态记忆**：当前版本主要处理文本形式的观察结果，对图像、音频等多模态记忆的支持有待探索。

### 7.3 对行业的启示

Jev-Mem 的成功告诉我们，**AI Agent 的记忆系统，不应该只是"更多记忆"或"更快检索"的军备竞赛**。更深层的变革，来自于对记忆管理决策本质的重新思考。

当系统能够像人类一样，区分"快速判断"和"深度推理"，并让不同的认知系统处理不同类型的任务时，真正的效率提升才会发生。这不仅是 Jev-Mem 的贡献，更是它为整个行业指明的方向。
