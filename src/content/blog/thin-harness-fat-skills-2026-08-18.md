# Thin Harness Fat Skills：YC 公开的 AI Agent 架构哲学，5000 字深度解读

**作者：比特财商**

---

2026 年 3 月 31 日，Anthropic 意外将 Claude Code 完整源代码（512,000 行）发布到 npm 仓库。这一"意外"揭开了 AI 编程助手真正强大的秘密——不是模型本身，而是包裹在模型外面的那层"架构"。

Y Combinator 总裁 Garry Tan 随后在 X 上发表了一篇长文，系统阐述了他眼中的 AI Agent 架构哲学。这篇文章在 48 小时内获得了近百万次阅读，成为 2026 年 AI 开发领域最受关注的思想实验之一。

这篇文章的名字叫：**"Thin Harness, Fat Skills"**——薄架构，厚技能。

---

## 一、100 倍效率差距的真正来源

Steve Yegge 说了一句话在 YC 社区广泛流传：

> "使用 AI 编程 Agent 的工程师，比今天用 Cursor 和 Chat 的人效率高 10 倍到 100 倍；比 2005 年的 Google 工程师效率高约 1000 倍。"

这不是夸张，Garry Tan 说他亲眼见过、亲历过这个数字。

但问题在于：**当人们听到 100 倍这个数字时，他们找错了原因。**

- 更强的模型？❌ 用同样模型的人之间差距是 100 倍
- 更聪明的 AI？❌ 模型早就知道如何推理和写代码
- 更多的参数？❌ 模型本身没有本质区别

真正的差距是**架构**——是那层包裹在模型外面的东西。它决定了模型在什么时候、以什么方式、获得什么信息。

这就是"Thin Harness, Fat Skills"的核心洞察。

---

## 二、什么是 Harness（架构层）？

**Harness 是运行 LLM 的程序。** 它做四件事：

1. 让模型在循环中运行
2. 读取和写入你的文件
3. 管理上下文
4. 强制执行安全策略

**这就是它的全部职责。** 越薄越好。

**常见的反模式：** 把 Harness 做得太厚，把技能做得太薄。

你见过这种架构：
- 40+ 工具定义，占掉一半的上下文窗口
- God-Tools，每次 MCP 调用需要 2-5 秒
- REST API 包装器，把每个端点变成单独的工具
- 三倍 token，三倍延迟，三倍失败率

**正确做法：** 构建目的明确、快速、窄的工具。一个 Playwright CLI 每个浏览器操作 100ms 完成，而不是一个 Chrome MCP 截图-查找-点击-等待-读取需要 15 秒。**速度差距是 75 倍。**

软件不需要做得太"精致"。构建你恰好需要的那个东西，不多不少。

---

## 三、什么是 Skill（技能层）？

Skill 是一个**可复用的 Markdown 文档**，它教模型**如何做**一件事，而不是做什么事——用户提供"做什么"，技能提供"怎么做"。

这里有个关键洞察，大多数人完全错过了：

> **Skill 文件的工作方式类似于方法调用。**

它有参数。你用不同的参数调用它。同样的流程，因为传入参数不同，产生的能力完全不同。

看一个实际例子——一个叫 `/investigate` 的技能，有 7 个步骤：

1. 界定数据集范围
2. 建立时间线
3. 对每份文档做人物标注（diarize）
4. 综合分析
5. 正反两面论证
6. 引用来源
7. 输出结构化结论

它接受三个参数：`TARGET`（目标）、`QUESTION`（问题）、`DATASET`（数据集）。

**调用方式 A：** 把技能指向一位安全科学家 + 210 万封发现邮件 → 得到一位医学研究分析师，判断一名举报人是否被噤声。

**调用方式 B：** 把技能指向一家壳公司 + FEC 申报文件 → 得到一位法务审计员，追踪协调竞选捐款。

同样的技能，同样的 7 个步骤，同样的 Markdown 文件。

这就是关键：**技能描述的是判断过程和上下文。调用时提供的是真实世界的数据。**

这不是 Prompt Engineering，这是**软件设计**——用 Markdown 作为编程语言，用人类判断作为运行时。

## 四、什么是 Resolver（解析器）？

Resolver 是一个**上下文路由表**。当任务类型 X 出现时，先加载文档 Y。

技能告诉模型怎么做。解析器告诉模型**什么时候加载什么**。

一个真实场景：

开发者修改了一个 Prompt。没有 Resolver → 直接上线。有 Resolver → 模型首先读取 `docs/EVALS.md` → 其中规定：**"运行评估套件，比较分数，如果准确率下降超过 2%，回滚并调查。"**

开发者根本不知道评估套件存在。是 Resolver 在正确的时机加载了正确的上下文。

**Claude Code 就有内置 Resolver。** 每个 Skill 都有一个 description 字段，模型会自动匹配用户意图和 Skill 描述。你不需要记住 `/ship` 存在——描述本身就是解析器。

Garry Tan 分享了一个私人教训：他的 CLAUDE.md 曾经有 20,000 行。每个习惯、每个模式、每个曾经学到的教训全塞进去。模型注意力严重下降。Claude Code 直接建议他精简。

最终修复后只剩约 200 行——只是文档指针。Resolver 在需要时加载正确的那一个。**两万个字符的知识，随需随取，从不污染上下文窗口。**

## 五、Latent vs. Deterministic：最常见的架构错误

这个概念是整个架构的基石，也是最容易混淆的地方。

**Latent Space（潜在空间）** = 智能所在的地方。模型读取、解释、决定。判断、综合、模式识别。这一类工作需要模型的理解力。

**Deterministic（确定性）** = 信任所在的地方。同样的输入，同样的输出。SQL 查询、编译后的代码、算术运算。每一次都完全一样。

**最常见的架构错误：** 把错误的工作放在错误的一侧。

LLM 可以把 8 个人安排在一张晚餐桌前，考虑到每个人的性格和社会动态。**但让它安排 800 人，它会虚构出一个看起来合理但完全错误的座位表。** 这是一个组合优化问题，被强行塞进了潜在空间。

最差的系统：把应该在确定性空间的工作交给 LLM（慢、贵、不可靠）。
最好的系统：严格区分两者，把什么放在潜在空间、把什么放在确定性空间，执行得一丝不苟。

## 六、什么是 Diarization（人物标注）？

这是整个框架里最"人"的一步，也是让 AI 真正有用的关键。

Diarization 原本是语音识别领域的术语——区分谁在什么时候说了什么。在 AI Agent 架构中，Garry Tan 赋予它新的含义：

**模型读完一个主题的所有资料后，写出一份结构化画像——从数十甚至数百份文档中提炼出的单页判断。**

没有任何 SQL 查询能生成这个。
没有任何 RAG 管道能生成这个。
模型必须真正阅读、保持矛盾在脑中、注意到变化和时机，然后综合出结构化情报。

这是数据库查询和分析师简报之间的区别。

## 七、完整架构：三层结构

以上五个概念组合成一个简洁的三层架构：

```
┌─────────────────────────────────┐
│  Fat Skills（厚技能层）          │  ← 90% 的价值所在
│  Markdown 程序：判断、流程、     │
│  领域知识                        │
├─────────────────────────────────┤
│  Thin Harness（薄架构层）        │  ← 约 200 行代码
│  JSON 入，文本出。默认只读。      │
├─────────────────────────────────┤
│  Your Application（应用层）      │  ← 确定性基础
│  QueryDB, ReadDoc, Search,      │
│  Timeline                        │
└─────────────────────────────────┘
```

**核心原则是单向的：**

- 把智能**推上**到技能层
- 把执行**推下**到确定性工具层
- 让架构层**保持轻薄**

**这样做的结果：** 每次模型改进，自动提升每一个技能的智力水平，而确定性层保持完全可靠。

## 八、一个真实的学习循环系统

Garry Tan 展示了在 YC 实际运行的系统——2026 年 7 月，Chase Center，6000 名创始人参加 Startup School。

**背景：** 每位创始人有结构化申请表、问卷答案、1:1 导师谈话记录、公共信号（X 帖子、GitHub 提交、Claude Code 记录等）。

**传统方案：** 15 人项目团队阅读申请、做直觉判断、更新表格。200 名创始人时运行良好。6000 名时完全崩溃——没有人能在工作记忆中同时Hold住这么多画像。

**模型可以做到。** 具体分三步：

### 第一步：Enrichment（丰富化）

一个 `/enrich-founder` 技能拉取所有来源、运行丰富化处理、做人物画像标注，并高亮"创始人**说的**和**实际在建的**之间的差距"。

确定性层处理 SQL 查询、GitHub 统计、Demo URL 浏览器测试、社交信号拉取、CrustData 查询。每晚定时运行，6000 个画像始终保持最新。

人物画像标注能捕捉到任何关键词搜索都找不到的东西：

```
创始人：Maria Santos
公司：Contrail
说的： "AI 代理的 Datadog"
实际上：80% 的提交都在计费模块
她在建的是一个 FinOps 工具，只是伪装成了可观测性平台
```

这种差距——"说的"与"实际在建的"——需要同时阅读 GitHub 提交历史、申请表和导师谈话记录，并把三者同时放在脑中。没有任何嵌入相似度搜索能找到这个。模型必须阅读完整画像并做出判断。

**（这是把工作放在潜在空间的完美决策！）**

### 第二步：Matching（匹配）

这就是"技能即方法调用"的精髓所在。同一个匹配技能的三种调用，产生三种完全不同的策略：

| 调用 | 输入 | 输出 |
|---|---|---|
| `/match-breakout` | 1200 名创始人 | 按行业亲和力聚类，每组 30 人 |
| `/match-lunch` | 600 名创始人 | 跨行业偶发匹配，每桌 8 人，无重复 |
| `/match-live` | 当前在场的人 | 最近邻嵌入，200ms，1:1 配对 |

模型能做出任何聚类算法都做不出的判断：

> "Santos 和 Oram 都是 AI 基础设施，但它们不是竞争对手——Santos 是成本归属，Oram 是编排。把他们放在同一组。"
>
> "Kim 申请时写的是'开发者工具'，但他 1:1 谈话记录显示他在建的是 SOC2 合规自动化。把他移到金融科技/监管科技组。"

没有任何嵌入能捕捉 Kim 的重新分类。模型必须阅读完整画像。

### 第三步：The Learning Loop（学习循环）

活动结束后，一个 `/improve` 技能读取 NPS 调查问卷，对"中等"评分（不是差评，而是"还行"的那部分——系统几乎工作但没有完全工作的部分）做人物画像标注，提取模式，然后将新规则写回匹配技能：

```
当参会者说 "AI 基础设施"
  但初创公司 80%+ 代码在计费模块：
  → 分类为金融科技，而非 AI 基础设施

当两位参会者在同一组中已经认识彼此：
  → 惩罚邻近度
  → 优先新颖的引荐
```

这些规则被写回技能文件。下一轮运行时自动使用。**技能自我改写了。**

7 月活动：12% "中等"评分。下一场活动：4%。

技能学会了"中等"实际上意味着什么，系统无需任何人重写代码就变得更好了。

## 九、技能是永久升级

Garry Tan 在 X 上发过一条 Tweet，意外引发了大量共鸣：

> **你不能做一次性工作。如果我让你做某件事，而这件事以后还需要再做，你必须：**
> - **手动做第一遍，覆盖 3 到 10 个项目，展示输出**
> - **如果我批准了，把它编纂成技能文件**
> - **如果它应该自动运行，把它放上 Cron**
>
> **测试：如果我需要问你同样的事情两次，你失败了。**

这条推文获得了数千个点赞和收藏。人们以为这是一个 Prompt 技巧。不，它是架构设计。

**每一次你写下的 Skill，都是对系统的一次永久升级。**

- 永远不会退化
- 永远不会忘记
- 在你睡觉时凌晨 3 点也在运行
- 当下一个模型发布时，每个 Skill 自动变好——潜在步骤的判断力提升，确定性步骤保持完全可靠

**这就是获得 100 倍效率的方式。不是更聪明的模型。是厚技能、薄架构，以及把每件事都编纂成技能的纪律。**

系统会复合增长。构建一次，永远运行。

## 十、核心观点总结

### 1. 模型不是瓶颈
模型已经知道如何推理、综合、写代码。它失败是因为它不理解你的数据——你的 schema、你的规范、你问题的特定形状。**给模型正确的上下文，在正确的时间，足够的精准，不过度噪音。**

### 2. 架构决定一切
同样的模型，2x 的人用它做-fat harness with thin skills，100x 的人用它做 thin harness with fat skills。差距不在于模型，在于架构。

### 3. 技能是复利资产
每次你把一个流程编码成 Skill 文件，你就永久升级了系统。新模型来了，Skill 自动变强。确定性层永远可靠。

### 4. Latent vs. Deterministic 是架构的核心分界线
把判断类工作交给 LLM（潜在空间），把执行类工作交给确定性工具。混淆两侧是大多数 AI 系统低效的根本原因。

### 5. 学习循环是最强的护城河
系统能从"中等"反馈中提取模式并自我改进——把规则写回 Skill 文件。下一个事件自动应用更智慧的规则。**这才是 AI 系统真正的竞争优势。**
