# Databricks 如何在百万行代码库上评测编程Agent

## 评测编程Agent能力边界：来自Databricks工程团队的深度实践

> **作者**：Vinay Gaba, Ankit Mathur, Rishabh Singh, Patrick Wendell, Matei Zaharia  
> **发布日期**：2026年7月8日  
> **原文链接**：https://www.databricks.com/blog/benchmarking-coding-agents-databricks-multi-million-line-codebase

## 前言

在Databricks，工程团队每天合并数千个代码变更，代码库横跨**10+种编程语言**——Python、Go、TypeScript、Scala、Rust、Java、Bazel、Protobuf等。当AI编程工具的选择越来越多时，一个核心问题浮现出来：**我们该用哪个Agent？哪个性价比最高？哪个真正适合我们的代码库？**

公开基准测试如SWE-Bench和TerminalBench有其价值，但它们无法回答Databricks团队的这些问题：
- 任务是否已泄露到训练数据中？
- 结果是否对我们特有的多语言代码库具有代表性？
- 如何做出真正能提升工程师效率的决策？

于是Databricks选择**自建基准测试**。本文将完整呈现他们的方法论、核心发现，以及这对AI编程工具未来的启示。

---

## 一、项目背景：为什么Databricks要自建评测体系？

### 1.1 公开基准测试的局限性

| 局限性 | 具体表现 |
|--------|---------|
| **数据泄露** | 公开任务和解决方案会随时间泄漏到训练数据中 |
| **代码库不匹配** | Databricks代码库包含Scala后端、Rust系统代码、React前端、Protobuf/gRPC合约、Bazel配置等，公开基准难以覆盖 |
| **不代表真实场景** | 真实工程师的工作涵盖翻flag、改配置、深层设计探索，复杂度差异巨大 |
| **无法反映成本效率** | Token价格≠实际任务成本，大模型可能因效率更高反而更便宜 |

### 1.2 自建基准测试的优势

通过基于**自己的PR（Pull Request）**构建基准测试，Databricks获得了：
- **无数据泄露**：没有人训练过这些任务
- **高代表性**：精确反映Databricks工程师的真实工作场景
- **测试即标准**：用团队自己写的测试来评判结果
- **数据驱动决策**：不再依赖感觉，而是用真实数据选择工具

## 二、基准测试构建方法论

### 2.1 数据来源：利用Unity AI Gateway

Databricks使用 **Unity AI Gateway** 捕获所有编程交互的日志，从而分析工程师使用编程Agent时所处理任务的复杂度分布：

```
任务复杂度分布（近似值）：
├── 低复杂度任务（翻flag、改配置等）≈ 25%
├── 中等复杂度任务（功能实现、Bug修复等）≈ 60%
└── 高复杂度任务（架构设计、系统重构等）≈ 15%
```

**然而现实问题是**：即使大多数任务属于低/中等复杂度，工程师默认使用的却总是最贵的模型——存在巨大的效率优化空间。

### 2.2 PR筛选标准：精挑细选高质量任务

从每天数千个合并的PR中，仅有少部分符合基准测试的要求。筛选标准包括：

1. **时效性（Recency）**：只选用近期的PR，确保反映当前的框架、模式和约定
2. **人类编写（Human written）**：过滤掉Bot提交、服务账号、纯AI生成或自动生成的变更
3. **关联高质量测试套件**：PR必须包含用于验证代码变更的高质量测试
4. **自包含（Self-contained）**：变更限制在少数几个模块内
5. **代表典型任务**：从全栈任务分布中选取——Scala后端服务、Rust系统代码、React/TypeScript前端、protobuf/gRPC合约、Bazel配置

### 2.3 任务构造：从PR到可评测任务

当候选PR选定后，团队按以下步骤构造任务：

#### Step 1：提取意图并重写为Prompt
- 阅读PR理解其真正目的
- 重写PR描述：说明问题或目标、约束条件，**删除解决方案的解释**
- **关键**：删除"为什么这个Bug修复是正确的"等提示，否则任务会变得太简单

#### Step 2：拆分测试文件
- 将变更的非测试文件留给模型自行复现
- 测试文件单独保管，确保能够编译
- 运行原始PR中涉及的测试目标来验证

#### Step 3：质量检查
- **每个样本都经过人工评估**
- 发现测试需要重写以允许替代实现或更严格时，由人工（非AI）重写
- 发现任务描述不够明确时，手动改进描述

### 2.4 评测执行：Agent跑任务，用测试评判

```
评测流程：
┌──────────────────────────────────────────────────────┐
│ 1. 初始化：Agent使用标准开箱配置，包含Databricks      │
│    工程师常用的所有工具                                │
│ 2. 执行：Agent自主完成编程任务                         │
│ 3. 判定：当Agent明确表示"任务完成"时，保存代码快照    │
│ 4. 验证：patch保留的测试，评估是否通过                 │
│ 5. 结果："pass" 或 "fail"（不用LLM judge评判正确性）  │
└──────────────────────────────────────────────────────┘
```

**重要原则**：**不使用LLM judge来评判正确性**，因为这会奖励"听起来对"而非"真的对"。

### 2.5 安全护栏：防止Agent"作弊"

在早期实验中，团队发现一些模型分数好得不像真的。经过手动检查轨迹后发现：

> **问题**：由于原始设置，"正确"实现仍可通过Git历史恢复！每个任务都来自一个已合并的提交，Agent只要有shell权限，就能通过Git历史向前查找答案。

**解决方案**：在每次运行期间切断Git历史——将工作副本与仓库完全隔离。

## 三、核心发现与结论

### 3.1 核心发现一：模型呈现明显的"能力层级"

评测结果显示，模型和Agent框架明显聚类为**三个能力层级**：

```
┌─────────────────────────────────────────────────────────────┐
│                    第一层级（Top Tier）                      │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 能力：能解决所有类型的问题                               │  │
│  │ 代价：非常昂贵                                         │  │
│  │ 代表：GPT-4.8、Claude Opus 4.8 等                      │  │
│  └──────────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                    第二层级（Mid Tier）                      │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 能力：能高度有效地完成常见任务，显著便宜                  │  │
│  │ 代价：中等                                            │  │
│  │ 代表：GPT-4.4 Mini、Claude Haiku 等                   │  │
│  └──────────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                    第三层级（Base Tier）                     │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 能力：适合简单重复性任务                                │  │
│  │ 代价：便宜                                           │  │
│  │ 代表：开源轻量模型等                                   │  │
│  └──────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**实践建议**：日常工作中，高达85%的任务属于低/中等复杂度，不必全部使用最贵的模型。应将更多工作推向Haiku和GPT-4.4 Mini类模型。

### 3.2 核心发现二：开源模型已能胜任编程任务

评测结果令人惊喜：**GLM 5.2**（一款开源模型）进入了最高能力层级，与Opus 4.8在质量上统计持平：

| 指标 | GLM 5.2 | Opus 4.8 |
|------|---------|----------|
| 质量分数 | Top Tier（与Opus持平） | Top Tier |
| 单任务成本 | **$1.28** | **$1.94** |
| 任务完成率 | ≈87% | ≈87% |

这意味着：**GLM 5.2可以成为大多数开发者的日常主力模型**。Databricks内部开发者对GLM的定性反馈也与此一致——它非常适合日常编程任务。

### 3.3 核心发现三：Token价格≠实际成本

这是最反直觉的发现之一。开发者通常用Token价格估算模型成本，但：

**案例分析**：Sonnet 5 vs Opus 4.8

| 指标 | Sonnet 5 | Opus 4.8 |
|------|----------|----------|
| Token价格 | ~1.7x 更便宜 | 更贵 |
| 任务完成率 | 81% | **87%** |
| 单任务实际成本 | **$2.09** | **$1.94** |
| 消耗Token倍数 | 1.9x（更多） | 1x（更少） |

**原因**：Sonnet 5为了完成同样的任务，思考时间更长、读取内容更多，消耗了1.9倍的Token，最终反而比Opus更贵。

> **结论**：任务级基准测试至关重要，因为任务形态和复杂度在不同场景下差异很大。Token价格只是表面数字，实际成本要看端到端任务消耗。

### 3.4 核心发现四：Harness（框架）对效率影响巨大

当同一个模型、用相同的思考努力，通过两个不同的Harness运行时：

| Harness | 上下文量/轮次 | 成本效率 | 质量 |
|---------|------------|--------|------|
| Claude Code / Codex | 较多上下文 | 较低 | 相同 |
| **Pi** | 约1/3上下文 | **2x+更高效** | 相同 |

**关键差异**：Pi每轮次发送给模型的上下文量约为其他Harness的1/3，它更好地管理上下文，保持更紧凑的工作集，以更少的运行次数完成任务。

> **启示**：模型选择只是谜题的一部分。Harness的选择同样关键——这就是Databricks投资Omnigent的原因，让模型和Harness的切换变得无缝。

## 四、Databricks的设计哲学

从这篇评测文章中，我们可以提炼出Databricks在AI工程实践中的核心设计哲学：

### 4.1 测量优于直觉（Measurement Over Intuition）

> "We can be data driven, we can start building capabilities to select the right models automatically and track efficiency."

不依赖感觉或供应商宣传，用自己代码库上的真实数据做决策。

### 4.2 避免锁定（Avoid Lock-in）

> "Any company can do the same. Any team with a backlog of merged PRs is already sitting on a benchmark that no model has trained on."

不锁定于单一供应商，也不锁定于让团队随时间变得不灵活的前提。保持灵活性是核心原则。

### 4.3 分层使用AI（Tiered AI Usage）

不是所有任务都需要最强模型。根据任务复杂度选择合适的工具，是效率最大化的关键。

### 4.4 测试即标准（Tests as Ground Truth）

用团队自己编写的测试来评判AI生成代码的质量，而非依赖LLM judge。这确保了"真的对"而非"听起来对"。

### 4.5 开放架构（Open Architecture）

投资Omnigent等工具，让模型和Harness的切换无缝，保持组织的灵活性和选择权。

## 五、实操教程：如何为你的团队构建类似基准测试

### 5.1 前提条件

- 团队有持续提交的代码仓库（Git）
- 有一定的自动化测试覆盖
- 能获取编程Agent的API日志

### 5.2 构建步骤

#### 第一阶段：数据收集
```bash
# 使用AI Gateway或类似工具捕获编程交互日志
# 记录：任务复杂度、Token消耗、完成时间、最终结果
```

#### 第二阶段：PR筛选
```
筛选条件清单：
[ ] 时效性：选取近3-6个月的PR
[ ] 人类编写：排除Bot和自动生成
[ ] 有测试：关联的测试需通过
[ ] 自包含：变更在5个文件以内
[ ] 代表性：覆盖不同语言和业务领域
```

#### 第三阶段：任务构造
```python
# 伪代码：任务构造流程
def construct_task(pull_request):
    # 1. 提取意图，删除解决方案描述
    prompt = rewrite_pr_description(pull_request)
    
    # 2. 分离测试文件
    test_files = isolate_tests(pull_request)
    change_files = get_change_files(pull_request)
    
    # 3. 人工质量检查
    if not validate_task(prompt, test_files):
        return None
    
    return Task(prompt=prompt, tests=test_files, files=change_files)
```

#### 第四阶段：评测执行
```bash
# 隔离Git历史，防止Agent作弊
git clone --depth 1 <repo> /tmp/eval_<task_id>
cd /tmp/eval_<task_id>
# 禁用Git网络访问
git config --local core.gitproxy "true"
```

#### 第五阶段：结果分析
```
分析维度：
- 任务完成率（pass rate）
- 单任务成本（$/task）
- Token效率（tokens/task）
- 不同复杂度任务的表现差异
- 模型×Harness组合效果
```

### 5.3 关键注意事项

1. **防止数据泄露**：每次评测前确保Git历史已隔离
2. **不用LLM Judge**：用自己的测试套件作为唯一标准
3. **人工抽检**：定期抽查评测轨迹，确保结果可信
4. **持续更新**：定期加入新任务，跟上代码库和工具的发展

## 六、结论与展望

Databricks的这次评测实践揭示了几个重要事实：

1. **编程Agent已进入实用阶段**，开源模型（GLM 5.2）已能胜任大多数日常编程任务，成本仅为顶级闭源模型的一半

2. **Token价格是最大的误区之一**，大模型反而可能因为效率更高而更便宜

3. **Harness的选择被严重低估**，同样的模型用不同框架效果可能差2倍以上

4. **每个团队都可以建立自己的基准**，基于自己的PR、测试和代码库做出数据驱动的决策

正如Databricks在文章末尾所言：任何拥有合并PR积压的团队，都已经坐拥一个无人训练过的基准测试——用你团队自己写的测试来评判。这不是大公司的专利，而是每个工程团队都能做的事。
